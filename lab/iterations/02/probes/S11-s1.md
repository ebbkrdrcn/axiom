# Execution of the given program

## Step 1 — Validate first

The specification's execution procedure ("Executing a program", rule 1) requires:

> **Validate first.** Check rules V1–V10. If any is broken, do not execute. Report each broken rule by its number.

and the Validity rules table states:

> A program that breaks any of these rules is INVALID. It MUST be rejected as a whole and MUST NOT be executed in part.

Checking the program against V1–V10:

```
LOOP:review
  FORK
    → DELEGATE security-review
        VERIFY security-review
        WHEN security-review.rejected
          → BREAK
    → DELEGATE docs-review
        VERIFY docs-review
  JOIN
  TRANSITION "Reviewed"
EMIT review-summary
```

- **V1** (indentation): The nesting follows the stated rules — `FORK`'s two `→` branches, and each branch's continuation lines (`VERIFY …`, `WHEN …`) aligned under its `→` item, with `WHEN`'s own `→ BREAK` nested under it. No violation.
- **V2** (`BREAK` not inside a `LOOP`): The `BREAK` is lexically inside `LOOP:review`'s body (by way of the `FORK` branch and the `WHEN`). Not violated on its own.
- **V3** (`BREAK` inside a `FORK` branch, and the `LOOP` it would leave is outside that branch): **Violated.** The `BREAK` sits inside the first `→` branch of the `FORK` (under `WHEN security-review.rejected`). The innermost enclosing `LOOP` is `LOOP:review`, which contains the `FORK` — the `LOOP` is not itself nested inside the branch; rather the branch is nested inside the `LOOP`. That is exactly the case the rule and the `FORK` section describe as INVALID:

  > `BREAK` in a branch: INVALID (rule V3). To leave a loop based on a branch's result, `JOIN` first, then use `WHEN … → BREAK`.

  This program does the opposite: it puts the `WHEN … → BREAK` **inside** the branch, before the `JOIN`, instead of joining first and then breaking in the sequential flow that follows.
- **V4** (`→` placement / `FALLBACK` placement): The `→` items are under `FORK` (branches) and under `WHEN` (flow); there is no `FALLBACK` here. Not violated.
- **V5** (`AUTO` misuse): No `AUTO` in this program. Not applicable.
- **V6** (`WHEN` tests an undeclared outcome): `WHEN security-review.rejected` refers to `security-review`, and the program contains `VERIFY security-review`, whose possible outcomes are exactly `accepted`/`rejected`. Not violated.
- **V7** (duplicate `HITL` names, name reuse between `HITL`/`VERIFY`, empty/repeated answer lists): No `HITL` statements at all. Not applicable.
- **V8** (fallback flow not ending in `STOP`/`BREAK`): No `FALLBACK` in this program. Not applicable.
- **V9** (`JOIN` without a `FORK`, or `FORK` with fewer than two branches): The `JOIN` has a matching preceding `FORK`, and that `FORK` has two branches (`security-review`, `docs-review`). Not violated.
- **V10** (`WHEN` testing a subject a `FORK` branch establishes, before that `FORK` is joined, in the same flow): The `WHEN security-review.rejected` is *inside* the same branch that runs `VERIFY security-review` (it is not in the flow after the `FORK`/`JOIN` reading into a still-running branch), so this specific rule is not what is triggered here — the problem is V3, not V10.

## Conclusion: the program is INVALID

**Broken rule: V3** — `BREAK` is inside a `FORK` branch, and the `LOOP` it would leave (`LOOP:review`) is outside that branch.

Per the specification, an INVALID program:

- "MUST be rejected as a whole and MUST NOT be executed in part" (Validity rules), and
- "If any [rule] is broken, do not execute" (Executing a program, rule 1).

Therefore **no step-by-step execution trace can be produced** for this program, regardless of the injected events (`VERIFY security-review` establishing `rejected` while the `docs-review` branch is still running never gets evaluated, because execution never legitimately starts on an INVALID program). Reporting the violation is the specification-mandated output in place of a trace.

### Note on the injected events, for completeness

Even setting validity aside for a moment: the specification also states, in the `FORK` section, that a `VERIFY` inside a branch establishing `rejected` "does not abort a branch" and that the whole execution proceeds only after `JOIN` waits for *every* branch to complete, including one still running (here, `docs-review`). The program's shown structure attempts to short-circuit the loop straight from inside the branch, before the `docs-review` branch has necessarily finished and before any `JOIN` — which is precisely the pattern the specification calls out as invalid (V3) and explains how to fix (`JOIN` first, then `WHEN … → BREAK` in the sequential flow after the `JOIN`).

### Assumption

The specification does not state whether a request for "the step-by-step execution" of a program overrides the mandatory validation step; I assumed it does not — i.e., that "Validate first... If any is broken, do not execute" applies unconditionally, including when a trace is explicitly requested. This assumption is the specification's own explicit procedure, not an addition beyond it.

### What a corrected program's shape would look like (per the spec's own guidance, not executed here)

The specification itself indicates the fix: move the `BREAK` out of the branch, after a `JOIN`, e.g.

```
LOOP:review
  FORK
    → DELEGATE security-review
        VERIFY security-review
    → DELEGATE docs-review
        VERIFY docs-review
  JOIN
  WHEN security-review.rejected
    → BREAK
  TRANSITION "Reviewed"
EMIT review-summary
```

This is offered only to show which single change removes the V3 violation, per the specification's own stated remedy ("`JOIN` first, then use `WHEN … → BREAK`"); it is not an execution of the program that was actually given in the task, which remains INVALID as written.
