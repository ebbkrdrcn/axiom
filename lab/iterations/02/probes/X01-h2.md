# go_harness DSL Program

## DSL Code

```
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions Made

1. **Merge answer labels**: The two possible merge answers are named "approved" (to merge) and "declined" (not to merge), derived from common merge decision terminology in the specification examples.

2. **No conditional flow on verification result**: The requirement states "Delegate the implementation and verify it. Then a merge decision is needed." The word "Then" indicates the merge decision happens regardless of whether `VERIFY implementation` establishes `accepted` or `rejected`. The verification result is established but does not branch the flow.

3. **Direct merge decision without loop**: The requirement describes a single decision path, not a repeated cycle. No `LOOP` is needed.

4. **FALLBACK applies only to human non-response**: The `AUTO HITL` with `FALLBACK` is used such that:
   - If the agent can determine the decision with certainty, it is made (no `FALLBACK`)
   - If uncertain, the human is asked
   - If the human provides insufficient or no usable answer, the `FALLBACK` is triggered

5. **Process termination**: The program ends after the merge transition. `TRANSITION "Merged"` or `TRANSITION "Rework"` is the last action for successful human responses; `STOP` is the last action when the `FALLBACK` is triggered.

6. **No additional state management**: Only three process states are used: "Merged", "Rework", and "Blocked". These are set by explicit `TRANSITION` statements.
