# Execution of the given DSL program

## Step 1 — Validate first

Per **Executing a program**, rule 1: *"Validate first. Check rules V1–V10. If any is broken, do not execute. Report each broken rule by its number."*

The program is:

```
LOOP:review
  FORK
    → DELEGATE security-review
        VERIFY security-review
        WHEN security-review.rejected
          → BREAK
    → DELEGATE docs-review
        VERIFY docs-review
  JOIN
  TRANSITION "Reviewed"
EMIT review-summary
```

Checking it against V1–V10:

- **V1** (indentation): The nesting is consistent with the rules in **Indentation and scope**. `FORK` is the child of `LOOP:review`; the two `→` lines are `FORK`'s branches; `VERIFY security-review` and `WHEN security-review.rejected` are nested under the first `→` item (`→ DELEGATE security-review`), so they continue that branch's own sequential flow; `→ BREAK` is nested under `WHEN`, forming its flow. No violation.
- **V2** (`BREAK` not inside a `LOOP`): `BREAK` is inside `LOOP:review` (an enclosing loop exists). Not violated on its own.
- **V3** (`BREAK` inside a `FORK` branch, and the `LOOP` it would leave is outside that branch): **Violated.** The `BREAK` sits inside the first `FORK` branch (`→ DELEGATE security-review → VERIFY security-review → WHEN security-review.rejected → BREAK`). The only enclosing `LOOP` is `LOOP:review`, which contains the `FORK` itself — i.e. the `LOOP` is *outside* the branch, not nested inside it. The specification is explicit about exactly this shape: *"`BREAK` inside a branch: INVALID (rule V3). To leave a loop based on a branch's result, `JOIN` first, then use `WHEN … → BREAK`."* That is precisely this program's structure.
- **V4–V10**: No other rule is broken (two branches under `FORK`, one `JOIN` matching it, `WHEN security-review.rejected` refers to a `y` — `rejected` — that `VERIFY security-review` can establish, no `HITL`/`AUTO`/`FALLBACK` present, and the `WHEN` inside the branch tests an outcome established earlier in that *same* branch's own sequential flow, not a cross-branch or post-`FORK` reference, so V10 does not apply here).

## Conclusion

The program is **INVALID** — broken rule: **V3**.

Per the execution procedure, an INVALID program **MUST NOT be executed**, not even partially. No step-by-step trace can therefore be produced for it: producing one would mean running a statement (`BREAK` inside the `FORK` branch) that the specification declares invalid, which rule 2 of the execution procedure and the top-level definition of INVALID ("MUST NOT be executed") forbid.

## Assumption

The specification does not need any assumption to reach this conclusion: the offending pattern (a `BREAK` inside a `FORK` branch, leaving a `LOOP` that only encloses the `FORK` from the outside) is the exact case the spec itself uses to illustrate rule V3, and it also names the fix without prescribing it as part of this program: replace the in-branch `BREAK` with a `JOIN` after the `FORK`, followed by `WHEN security-review.rejected → BREAK` at the loop-body level. That rewritten form is not what was given, so it is offered only as context, not as part of the execution of the program as written.
