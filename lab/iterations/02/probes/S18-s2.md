# Analysis of the DSL Program

```
DELEGATE design
DELEGATE implementation
FORK
  → DELEGATE docs
  → DELEGATE changelog
EMIT release
```

This program is well-formed under the grammar: two top-level `simple` (`DELEGATE`) statements, followed by a `fork` with two `→` items (branches), followed by another `simple` (`EMIT`) statement. It has no `LOOP`, `WHEN`, `HITL`, `REQUIRE`, `JOIN`, or `BREAK`, so none of V1–V10 are implicated:

- V9 ("a `FORK` has fewer than two branches") does not apply — the `FORK` has exactly two `→` branches.
- There is no `JOIN` at all in this program, which is explicitly allowed: "No `JOIN` follows → continue immediately" (Quick reference, `FORK` row), and `JOIN` is only required if the program later needs to wait for the branches.

So the program is valid, and the questions can be answered directly from the execution rules.

---

## 1. Can `DELEGATE implementation` start before the design has been delivered?

**No.**

The spec is explicit on two points that combine to force this:

- Execution rule 1: "Statements run one at a time, in the order written. Each statement finishes before the next starts. Only `FORK` runs things concurrently."
- `DELEGATE` section: "The statement is done when the actor has delivered its result. The next statement starts only then. To delegate concurrently, use `FORK`."

`DELEGATE design` and `DELEGATE implementation` are two sequential top-level statements, not branches of a `FORK`. Since `FORK` is the *only* construct that introduces concurrency, and these two `DELEGATE`s are not inside one, `DELEGATE implementation` cannot begin until `DELEGATE design` is "done" — which, per the `DELEGATE` rule, means the design actor has delivered its result. The scenario states the design actor "takes a long time to deliver the design," but no matter how long, execution simply waits at `DELEGATE design` (rule 5, "Stop at a boundary": "If ... a result is not yet available, the execution waits there") before `DELEGATE implementation` can start.

---

## 2. When is `EMIT release` executed relative to the docs and changelog branches?

**Immediately after the `FORK` starts the branches — not after either branch finishes, and not "between" them in any guaranteed sense.**

The program contains a `FORK` with two branches (`DELEGATE docs`, `DELEGATE changelog`) but **no `JOIN`**. The `FORK` rules say:

- "`FORK` is reached → All branches start. Within a branch, statements run sequentially."
- "No `JOIN` follows → Execution continues immediately after the `FORK` while the branches run."

Since this program never writes a `JOIN`, execution does not wait for `docs` or `changelog` at all. As soon as the `FORK` statement starts both branches, the top-level flow proceeds straight to `EMIT release`, concurrently with the two branches still running in the background. So `EMIT release` runs essentially at the same time the branches begin, well before either branch is expected to complete — it is not sequenced after either branch's completion by anything in the DSL.

---

## 3. Is it guaranteed that docs exist when `EMIT release` executes?

**No — it is not guaranteed, and given the stated timing it is guaranteed that they do *not* yet exist.**

Because there is no `JOIN` between the `FORK` and `EMIT release`, nothing in the DSL makes `EMIT release` wait for the `docs` branch (or the `changelog` branch) to finish. As established in Q2, `EMIT release` executes immediately once the `FORK` starts the branches, running concurrently with them rather than after them.

Given the scenario's events — `docs` takes 1 hour and `changelog` takes 5 minutes to deliver, counted from when the `FORK` starts — and `EMIT release` runs immediately after the `FORK` (no delay is introduced by anything in between), `EMIT release` will execute long before the 1-hour `docs` delegation (and even before the 5-minute `changelog` delegation) has been delivered. So not only is completion of `docs` unguaranteed at that point, the given timings imply `docs` (and `changelog`) will definitely not yet exist when `EMIT release` runs.

If the program's intent were for `release` to depend on `docs` (and/or `changelog`), the spec's `JOIN` construct would be required before `EMIT release`:

```
FORK
  → DELEGATE docs
  → DELEGATE changelog
JOIN
EMIT release
```

Per the `JOIN` section, this "Waits until every branch of the corresponding `FORK` is complete," which would guarantee `docs` has been delivered before `EMIT release` runs. As written, however, the program has no such `JOIN`, so no such guarantee exists.

---

## Assumptions

The specification determines all three answers without ambiguity — no assumption beyond the text was needed. One point worth noting explicitly: the spec does not model "how long" a `DELEGATE` takes in DSL terms; the 1-hour/5-minute figures in the scenario are treated purely as real-world timing information confirming that these deliveries have not occurred by the time `EMIT release` (which runs with no intervening wait) executes — the DSL itself only requires knowing whether the `FORK` was joined, not the actual durations.
