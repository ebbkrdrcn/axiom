```text
LOOP:delivery
  DELEGATE implementation
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
EMIT source-code
```

## Assumptions

- **Identifier for the delegated/verified work is `implementation`.** The requirement says "delegate the implementation, then verify it" — `VERIFY implementation` is the natural subject matching the `DELEGATE implementation` result, since `VERIFY` must name a result and the outcome subject (`implementation.accepted` / `implementation.rejected`) must match a `WHEN` per V6.
- **Identifier for the correction work is `correction`**, as no more specific name is given ("delegate a correction").
- **Identifier for the emitted artifact is `source-code`**, taken directly from "emit source-code"; hyphens are permitted in identifiers per the syntax rules.
- **The loop label (`LOOP:delivery`) is arbitrary** — the spec states a loop name is only a label with no semantic effect, so any valid identifier works.
- **"Repeat from the start" after the correction requires no explicit statement.** Per the `LOOP` rules, when the last statement of the loop body finishes, the next iteration automatically starts at the first statement (`DELEGATE implementation`). Since `DELEGATE correction` is the last statement in the `rejected` flow and there is nothing after it in the loop body, the loop naturally restarts from `DELEGATE implementation`, matching "repeat from the start."
- **The order of the two `WHEN` checks (`accepted` before `rejected`) has no semantic significance**, since consecutive `WHEN`s are independent and mutually exclusive here (an outcome is either `accepted` or `rejected`, never both) — the order shown simply follows the order mentioned in the requirement text ("if it accepts... if it rejects...").
- **No `REQUIRE`, `HITL`, `FORK`, or `TRANSITION` is used**, because the requirement does not mention any prerequisite item, human decision, concurrency, or process-state change — only a repeated delegate/verify cycle with a conditional exit and a final emit.
- **The corrected work is not separately verified before the loop repeats.** The requirement only says "delegate a correction and then repeat from the start," not "verify the correction," so the next iteration re-delegates and re-verifies `implementation` as written, without an extra `VERIFY correction` step.
- **`EMIT source-code` runs exactly once, after the loop ends (via `BREAK`)**, since it is written outside/after the loop body at the loop's indentation level, matching "after the repetition ends, emit source-code."
