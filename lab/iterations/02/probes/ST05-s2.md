# Execution of the `polish` program

## Program

```
LOOP:polish
  WHEN draft.accepted
    → BREAK
  DELEGATE draft
  VERIFY draft
TRANSITION "Done"
```

Events: iteration 1 → `VERIFY draft` establishes `rejected`; iteration 2 → `VERIFY draft` establishes `accepted`.

## Validity (brief)

The program is well-formed under the given rules: `BREAK` is inside the `LOOP` it leaves (V2/V3 satisfied), the `WHEN` tests `draft.accepted`, and `draft` is the subject of a `VERIFY` producing `accepted`/`rejected` (V6 satisfied), and indentation follows the `LOOP` → `WHEN` → `→ BREAK` nesting (V1 satisfied). No `FORK`/`JOIN`/`HITL`/`REQUIRE` appear, so V4, V5, V7–V10 do not apply. It may be executed.

## Step-by-step trace

Per rule 7 of **Execution in ten rules**, before anything establishes `draft`'s outcome, every `WHEN` on it is false. The `LOOP` body is: `WHEN draft.accepted → BREAK`, then `DELEGATE draft`, then `VERIFY draft`. The first pass through the loop body is not itself logged as a step (matching the style of the specification's own complete example, where entering `LOOP:delivery` the first time produces no trace line — only a *return* to the top of the body is logged, as `loop again`).

```trace
1. WHEN draft.accepted -> false: skip
2. DELEGATE draft -> done
3. VERIFY draft -> outcome draft.rejected
4. LOOP:polish -> loop again
5. WHEN draft.accepted -> false: skip
6. DELEGATE draft -> done
7. VERIFY draft -> outcome draft.accepted
8. LOOP:polish -> loop again
9. WHEN draft.accepted -> true: run flow
10. BREAK -> break
11. TRANSITION "Done" -> state = "Done"
12. (end of program) -> end
```

### Explanation of the key steps

- **Step 1**: Execution reaches `WHEN draft.accepted` for the first time. No `VERIFY draft` has run yet, so `draft` has no outcome. By rule 7 ("Before anything establishes it, every `WHEN` on it is false"), the condition is false and the nested `BREAK` is skipped.
- **Steps 2–3**: `DELEGATE draft` completes, then `VERIFY draft` runs and — per the stated event for iteration 1 — establishes `draft.rejected`.
- **Step 4**: The body's last statement (`VERIFY draft`) is done, so per the `LOOP` rule the body starts again from its first statement (`WHEN draft.accepted`).
- **Step 5**: Second time reaching `WHEN draft.accepted`. The latest outcome of `draft` is `rejected` (from step 3), which is not `accepted`, so the condition is still false; the flow (`BREAK`) is skipped, and the loop does **not** stop here.
- **Steps 6–7**: `DELEGATE draft` completes again, then `VERIFY draft` runs and — per the stated event for iteration 2 — establishes `draft.accepted`, replacing the previous `rejected` value (outcomes hold their latest value; a new `VERIFY x` replaces it).
- **Step 8**: Body finishes again, loop restarts a third time.
- **Step 9**: Third time reaching `WHEN draft.accepted`. The latest outcome of `draft` is now `accepted` (from step 7), so the condition is true; its flow runs.
- **Step 10**: The flow is `→ BREAK`. `BREAK` leaves the innermost `LOOP` (`polish`) immediately; the remaining body statements for this iteration (`DELEGATE draft`, `VERIFY draft`) are not executed. Execution continues with the first statement after the loop.
- **Step 11**: `TRANSITION "Done"` runs, setting the current process state to `Done` (the latest, and only, `TRANSITION` in this program).
- **Step 12**: `TRANSITION "Done"` was the last top-level statement, so execution ends normally (rule 10).

## Answers

- **How many times is `DELEGATE draft` executed?** **2 times** — once in iteration 1 (step 2) and once in iteration 2 (step 6). It is not executed a third time because `BREAK` (step 10) exits the loop before the body reaches `DELEGATE draft` again in iteration 3.
- **What is the final state?** **`"Done"`** — set by the single `TRANSITION "Done"` statement (step 11), which runs once after the loop is broken out of.

## Assumption made

The specification's own complete example does not log a trace step for the very first entry into a `LOOP`'s body (only for a body restart, shown as `loop again`); it likewise does not log a step for the `LOOP:<name>` line itself on that first entry. Since the specification does not explicitly state whether the initial entry into a loop should appear as its own trace line, this answer follows the same convention as the specification's example: the first pass begins directly with the body's first statement, and `LOOP:polish` only appears in the trace when the body restarts (steps 4 and 8). This is a formatting choice for presenting the trace, not an ambiguity in the DSL's execution semantics — the sequence and outcomes of executed statements are identical either way, and the count of `DELEGATE draft` executions (2) and the final state (`"Done"`) are unaffected by it.
