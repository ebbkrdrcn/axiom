# Execution of the go_harness program

No violation.
- V2/V3 (`BREAK`): the only `BREAK` is inside `WHEN ship.yes`'s flow, itself inside a `→` item of `WHEN build.accepted`, inside `LOOP:release`'s body — not inside a `FORK` branch (the `FORK` was already `JOIN`ed earlier in the same iteration). Valid.
- V4 (`→` placement / `FALLBACK`): the single `→ FALLBACK` is directly under the `HITL` (`AUTO HITL:ship[...]`); no other misplaced `→`. Valid.
- V5 (`AUTO`): immediately followed on the same line by a decision `HITL:ship[yes, no](...)`. Valid.
- V6 (`WHEN` targets declared): `build.rejected`/`build.accepted` ← `VERIFY build`; `changelog.rejected` ← `VERIFY changelog`; `ship.yes` ← `HITL:ship[yes, no]`. All declared. Valid.
- V7 (names): `ship` is used only by one `HITL`, not reused by any `VERIFY`; its answer list `[yes, no]` has no repeats. Valid.
- V8 (fallback ending): the fallback under `AUTO HITL:ship` ends `→ TRANSITION "Stalled"`, `→ STOP`. Valid.
- V9 (`JOIN`/`FORK`): one `JOIN` matches the preceding `FORK`, which has exactly two branches. Valid.
- V10 (`WHEN` vs. un-joined `FORK`): `WHEN build.rejected`, `WHEN changelog.rejected`, `WHEN build.accepted` all appear after the `JOIN`, so they may safely test outcomes the branches established. Valid.

**The program is valid.** It may be executed.

## 1. Assumptions the specification leaves open

The spec does not fully determine two things needed to produce this trace, so I state what I assumed:

1. **Interleaving of concurrent `FORK` branches in the trace.** The DSL says branches run concurrently, but a trace is a single sequential list of steps. Following the convention used in the specification's own "Complete example" (branch 1 listed to completion, then branch 2), I list `VERIFY build` (branch 1) followed by `DELEGATE changelog` / `VERIFY changelog` (branch 2), in each iteration. No ordering guarantee beyond "both branches occur before `JOIN`" is implied by this choice.
2. **When `AUTO HITL:ship` is "certain."** The context gives an explicit, complete criterion ("ship exactly when build and changelog are both accepted in the same iteration") and states the agent has authority to ship. Since `WHEN build.accepted` is only entered when `build.accepted` holds, and `changelog`'s outcome for the same iteration is already established (from the `FORK`/`JOIN` earlier in that same iteration), the criterion fully determines the answer in every case reached in this program (no missing/contradictory information, no ambiguity). I therefore treat the decision as certain and within the agent's authority every time `AUTO HITL:ship` is reached, so the agent answers it directly and the human is never asked — consistent with "No human is available at any time" never being tested, since uncertainty never arises here.

## 2. Full step-by-step execution trace

```trace
1.  REQUIRE service-spec -> done
2.  DELEGATE build -> done
3.  FORK -> branches started
4.  VERIFY build -> outcome build.rejected
5.  DELEGATE changelog -> done
6.  VERIFY changelog -> outcome changelog.accepted
7.  JOIN -> joined
8.  WHEN build.rejected -> true: run flow
9.  TRANSITION "Fixing" -> state = "Fixing"
10. DELEGATE fix -> done
11. WHEN changelog.rejected -> false: skip
12. WHEN build.accepted -> false: skip
13. LOOP:release -> loop again

14. DELEGATE build -> done
15. FORK -> branches started
16. VERIFY build -> outcome build.accepted
17. DELEGATE changelog -> done
18. VERIFY changelog -> outcome changelog.rejected
19. JOIN -> joined
20. WHEN build.rejected -> false: skip
21. WHEN changelog.rejected -> true: run flow
22. DELEGATE changelog-fix -> done
23. WHEN build.accepted -> true: run flow
24. AUTO HITL:ship[yes, no]("Ship this build?") -> outcome ship.no
25. WHEN ship.yes -> false: skip
26. TRANSITION "Holding" -> state = "Holding"
27. LOOP:release -> loop again

28. DELEGATE build -> done
29. FORK -> branches started
30. VERIFY build -> outcome build.accepted
31. DELEGATE changelog -> done
32. VERIFY changelog -> outcome changelog.accepted
33. JOIN -> joined
34. WHEN build.rejected -> false: skip
35. WHEN changelog.rejected -> false: skip
36. WHEN build.accepted -> true: run flow
37. AUTO HITL:ship[yes, no]("Ship this build?") -> outcome ship.yes
38. WHEN ship.yes -> true: run flow
39. BREAK -> break
40. EMIT release -> done
41. TRANSITION "Released" -> state = "Released"
42. (end of program) -> end
```

### Notes on individual steps

- **Steps 24 and 37 (`AUTO HITL:ship`).** Per the "Who decides a `HITL`" table, since `AUTO` is present and the decision is certain and within the agent's authority (see assumption 2 above), the agent itself establishes `ship.no` / `ship.yes`; the human is never asked, and `FALLBACK` (reachable only on an insufficient/unavailable response) is never triggered in this run. Since the answer is established immediately rather than after an external wait, there is no separate `-> waiting` line for these steps (contrast with the specification's own worked example, where the decision *was* uncertain and so did produce a `waiting` step before the human's answer).
- **Step 26 (`TRANSITION "Holding"`).** Reached because, in iteration 2, `WHEN ship.yes` was false, so execution falls through to the next `→` item in `WHEN build.accepted`'s flow, which is `TRANSITION "Holding"`.
- **Step 39 (`BREAK`).** By the `BREAK` rule ("the remaining statements of the current iteration are not executed, including later `WHEN`s"), this also cancels the sibling `→ TRANSITION "Holding"` item that would otherwise follow `WHEN ship.yes` in iteration 3's `WHEN build.accepted` flow — it is correctly omitted from the trace. Execution resumes at the first statement after `LOOP:release`, i.e. `EMIT release`.
- **Step 41.** This is the program's own final `TRANSITION "Released"`, executed unconditionally after `EMIT release`, and it is the one that determines the final state (the latest `TRANSITION` always wins).

## 3. Final state

**`Released`**

(`TRANSITION "Released"` at the very end of the program is the last `TRANSITION` executed, so it overrides the earlier `"Fixing"` and `"Holding"` states set during iterations 1 and 2.)

## 4. How many times does `DELEGATE build` run?

**Three times** — once at the start of each of the three loop iterations (steps 2, 14, and 28), one per iteration until `BREAK` in iteration 3 ends `LOOP:release`.
