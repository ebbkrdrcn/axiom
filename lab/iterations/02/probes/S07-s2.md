# Analysis of the DSL program

```
DELEGATE data-migration
WAIT
VERIFY data-migration
WHEN data-migration.accepted
  → TRANSITION "Migrated"
```

## 1. What does `WAIT` wait for here?

The specification does not determine this, and says so explicitly for `WAIT` in general:

> "The DSL does not name the event. The surrounding process and the runtime determine it."

So from the DSL text alone, `WAIT` here is simply "suspend until an external event or response is available" (`WAIT` section) — it names no specific event, condition, or signal. Two things are worth noting from the spec that bear on this, without resolving it:

- `DELEGATE data-migration` is already, by definition, "done when the actor has delivered its result" — i.e. the preceding `DELEGATE` statement itself already waited for the actor's delivered result before `WAIT` was even reached.
- `WAIT` is a distinct statement from `DELEGATE`, so it is not merely re-stating "wait for the delegate's result" (that already happened). It suspends for some further external event/response not otherwise named in the program.

**The specification does not determine what that further event is** (it explicitly leaves this to "the surrounding process and the runtime," which are not given here). I therefore assume, as the most natural reading consistent with placing `WAIT` between the delegation and its verification, that it represents waiting for some external condition needed before verification can be performed (for example, an external confirmation that the migration has actually propagated/settled) — but this is my assumption, not something the DSL text fixes, since `WAIT`'s event is by design left unnamed by the DSL.

## 2. What executes immediately after `WAIT` ends?

Per the `WAIT` rule — "After the event, the next statement runs" — and rule 1 of the ten execution rules ("Statements run one at a time, in the order written"), the statement immediately following `WAIT` in program order is:

```
VERIFY data-migration
```

So `VERIFY data-migration` runs immediately once the awaited event occurs.

## 3. Does reaching `VERIFY data-migration` imply that the migration succeeded?

No. Nothing in the specification ties reaching a statement to any implied outcome. Specifically:

- `VERIFY <result>`: "Evaluates a result against the applicable acceptance criteria." It "establishes exactly one outcome: `<result>.accepted` or `<result>.rejected`" — the outcome is not known until `VERIFY` actually runs and establishes it; merely reaching the statement establishes nothing.
- Explicitly: "The completion of delegated work is not a successful verification." This directly says that having gotten this far (the `DELEGATE` finishing, then `WAIT` ending) does not itself mean success — evaluation via `VERIFY` is still required and could establish either `accepted` or `rejected`.
- More generally, per rule 9 ("The agent MUST NOT invent a response, a result, an outcome...") and the "Not yet established" rule under **Outcomes**, no outcome for `data-migration` exists before `VERIFY data-migration` actually executes and establishes it.

So reaching `VERIFY data-migration` only means the prior statements (`DELEGATE`, `WAIT`) are done; it says nothing about whether the migration will be judged `accepted` or `rejected`.

## 4. What happens if the awaited event never occurs?

Per the `WAIT` section: "There is no timeout. If the event never comes, execution stays at the `WAIT`."

So execution simply suspends indefinitely at that `WAIT` statement. No further statement in the program runs — `VERIFY data-migration`, the `WHEN` check, and the `TRANSITION "Migrated"` never execute — and execution does not end (no implicit `STOP`, no fallback, since `WAIT` has no `FALLBACK` mechanism defined in the DSL at all; `FALLBACK` only attaches to `HITL` or `REQUIRE`, per rule V4 and the **FALLBACK** section). The program remains blocked at `WAIT` forever, per rule 5 of the ten execution rules: "Stop at a boundary. If an event, response, or result is not yet available, the execution waits there. Do not assume what it will be."
