```text
LOOP:implementation
  DELEGATE implementation
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
EMIT source-code
```

## Assumptions

1. **Loop label is arbitrary.** The requirement says "repeatedly," but the DSL requires every `LOOP` to carry a `<name>`. Per the spec, "`<name>` is only a label. No statement refers to it," so the choice of label (`implementation`) has no semantic effect and any name would do.

2. **Shared identifier between `DELEGATE` and `VERIFY`.** The requirement says "delegate the implementation, then verify it," implying the verification evaluates the same thing that was delegated. I used the identifier `implementation` for both `DELEGATE implementation` and `VERIFY implementation`, matching the pattern the spec itself uses in its own `DELEGATE` example (`DELEGATE implementation` / `VERIFY implementation`) and in the "Complete example." The spec does not forbid a `DELEGATE` and a `VERIFY` from sharing a name (V7 only forbids a name shared between `HITL` and `VERIFY`, or between two `HITL`s).

3. **Mapping "accepts"/"rejects" to `VERIFY`'s fixed outcomes.** The spec states `VERIFY <result>` establishes exactly one of `<result>.accepted` or `<result>.rejected`, with no other possible outcomes. I mapped "the verification accepts it" → `implementation.accepted` and "the verification rejects it" → `implementation.rejected` directly, since these are the only outcomes the DSL allows and they align with the requirement's wording.

4. **Naming the correction work.** "Delegate a correction" gives no explicit identifier, so I chose the identifier `correction` (`DELEGATE correction`) as a descriptive name. The spec does not prescribe how `DELEGATE` arguments should be named beyond the identifier syntax (letters, digits, `-`, `_`, starting with a letter).

5. **Naming the emitted artifact.** "Emit source-code" was rendered as `EMIT source-code`, using a hyphenated identifier, which is valid per the grammar (`identifier = letter, { letter | digit | "-" | "_" }`).

6. **Order of the two `WHEN` checks.** I placed `WHEN implementation.accepted` before `WHEN implementation.rejected`, following the order the requirement mentions them. Per rule 3 ("Consecutive `WHEN`s are independent... there is no first match"), this ordering has no effect on behavior; it was chosen only for readability.

7. **No explicit "repeat" statement is needed.** "Repeat from the start" after a rejection is achieved implicitly: per rule 5 ("At the end of a loop body, the body starts again from its first statement"), once `DELEGATE correction` finishes and there are no more statements in that `WHEN` flow or in the loop body, the loop naturally restarts at `DELEGATE implementation`. No explicit jump/goto construct exists in the DSL, nor is one required.

8. **No `REQUIRE`, `HITL`, `FORK`, or `TRANSITION` were introduced.** The requirement does not mention any prerequisite item, human decision, concurrency, or process-state change, so none of those constructs were added. The DSL does not require them unless the requirement calls for them.

9. **`EMIT source-code` runs exactly once, after the loop, regardless of how many correction cycles occurred.** This follows directly from `BREAK`'s defined behavior ("leaves the innermost enclosing `LOOP` immediately... Execution continues with the first statement after that loop") and from placing `EMIT source-code` at the same indentation as `LOOP:implementation`, i.e., outside the loop body.
