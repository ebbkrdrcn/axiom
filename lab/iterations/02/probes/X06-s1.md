# Analysis of the go_harness Program

```
AUTO HITL:wording[short, detailed]("Short or detailed release notes?")
WHEN wording.short
  → DELEGATE short-notes
WHEN wording.detailed
  → DELEGATE detailed-notes
HITL:release[approved, rejected]("Approve the release?")
WHEN release.approved
  → EMIT release
```

All four answers below follow directly from the specification's rules on `HITL`, `AUTO`, and `WHEN`; no fact needed for the answers was left undetermined by the spec, so no assumptions were required.

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **wording** decision (`HITL:wording[short, detailed]`) may be answered by the agent — it is the only one of the two `HITL` statements written with `AUTO` immediately before it on the same line. The **release** decision (`HITL:release[approved, rejected]`) has no `AUTO` and per the "Who decides a `HITL`" table and the `HITL` section, it "MUST be replaced by an agent decision" only if marked `AUTO`; without it, "the human; the agent MUST NOT answer."

The condition under which the agent may answer the wording decision itself (rather than asking the human) is given by the `AUTO` section and its table:

- The agent may resolve it automatically **only if the decision is certain and within the agent's authority** — i.e., the agent "can determine one single answer from the list, based on the available information and the applicable criteria."
- If that condition doesn't hold ("anything else"), the human is asked "exactly as for a `HITL` without `AUTO`."

So: the agent may decide `wording` by itself, and only when it can single out exactly one of `short`/`detailed` with certainty (not merely high confidence) and has the authority to do so; otherwise even this decision goes to the human.

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No. `HITL:release[approved, rejected]` carries no `AUTO` marker. Per the spec's decision table, when `AUTO` is absent, "the agent MUST NOT answer" — the human decides, unconditionally. This holds regardless of how confident the agent is or how green the checks are: the spec is explicit that "`HITL` establishes a human decision boundary. It MUST NOT be replaced by an agent decision, unless it is marked with `AUTO`," and separately, even where `AUTO` *is* present, "a confidence score alone, however high, does not establish certainty." Here `AUTO` isn't present at all, so the point is moot — the release question must go to the human no matter how certain the agent is.

## 3. If the wording decision is not clearly determined, what happens?

"Not clearly determined" is exactly the uncertainty case the `AUTO` section defines (e.g., missing/contradictory information, ambiguous or missing criteria, more than one answer remaining reasonably compatible with the evidence, an unresolved interpretation, or lack of agent authority). In that case, per the `AUTO` table's "Anything else" row:

> The human is asked, exactly as for a `HITL` without `AUTO`. `FALLBACK` applies to the human's response as usual.

Concretely, applied to this program:

- The flow waits at `AUTO HITL:wording[...]`, now effectively treated like a plain `HITL`, and the human is asked "Short or detailed release notes?"
- This particular `HITL:wording` statement in the program has **no `→ FALLBACK`** attached.
- If the human then gives a usable response (clearly `short` or `detailed`), `wording.<answer>` is established and execution continues with the statement after the `HITL` (the two `WHEN` checks, exactly one of which will be true).
- If the response is insufficient or becomes unavailable (runtime stops waiting) and there is no `FALLBACK` — which is the case here — "Execution ends, as with `STOP`. No outcome is established." Both subsequent `WHEN wording.short` / `WHEN wording.detailed` would never be reached in that case since execution has already ended.

## 4. If the human answers the release question with "rejected", what happens?

`"rejected"` is one of `release`'s declared answers (`[approved, rejected]`), so it is a usable response. Per the `HITL` rules:

> Usable response → Establish the outcome (decision form only). Continue with the next statement after the `HITL` construct.

So:

1. `release.rejected` is established (replacing any prior value of that outcome).
2. Execution continues with the next statement, `WHEN release.approved`. Since the latest outcome of `release` is `rejected`, not `approved`, this condition is false and its flow (`→ EMIT release`) is skipped — "This is not an error. Execution does not wait."
3. The program has **no `WHEN release.rejected`** clause, so nothing else reacts to the rejection.
4. `WHEN release.approved` is the last top-level statement in the program. With it evaluated (and skipped), execution reaches the end and, per rule 10 ("When the last top-level statement is done, execution ends normally"), ends normally.

Net effect: the outcome `release.rejected` is recorded, `EMIT release` never runs, and the program terminates normally without emitting the release or taking any other explicit action on the rejection (the program simply doesn't define one).
