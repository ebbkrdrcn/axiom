# Analysis of the go_harness Program

```
DELEGATE design
DELEGATE implementation
FORK
  → DELEGATE docs
  → DELEGATE changelog
EMIT release
```

## 1. Can `DELEGATE implementation` start before the design has been delivered?

**No.**

Outside of a `FORK`, statements run strictly one at a time, in the order written, and each one finishes before the next starts (Execution rule 1: "Statements run one at a time, in the order written. Each statement finishes before the next starts. Only `FORK` runs things concurrently."). This applies directly to `DELEGATE`: "The statement is done when the actor has delivered its result. The next statement starts only then. To delegate concurrently, use `FORK`."

`DELEGATE design` and `DELEGATE implementation` are two ordinary top-level statements, not both under a `FORK`, so they are sequential, not concurrent. `DELEGATE implementation` is therefore not reached, and cannot start, until `DELEGATE design` is done — i.e., until the design actor has delivered its result. Since the events state that the design actor "takes a long time to deliver the design," `DELEGATE implementation` simply waits until that delivery happens; the program gives no mechanism for it to start any earlier.

## 2. When is `EMIT release` executed relative to the docs and changelog branches?

**`EMIT release` runs immediately after `FORK` starts the two branches, concurrently with them — it does not wait for either branch to finish.**

The `FORK` statement is written with no `JOIN` after it: the two `→` branches (`DELEGATE docs` and `DELEGATE changelog`) are followed directly by `EMIT release`, with no `JOIN` in between. Per the Quick reference: "`FORK` ... no `JOIN` → continue immediately," and the `FORK` table: "No `JOIN` follows → Execution continues immediately after the `FORK` while the branches run." This is reinforced by Execution rule 1, which singles out `FORK` as the one construct that runs things concurrently with the surrounding flow.

So the moment `FORK` is reached, both branches (`DELEGATE docs` and `DELEGATE changelog`) start running concurrently with each other, and — because there is no `JOIN` — execution of the main flow continues right away to `EMIT release`. Given the timing in the events (docs takes 1 hour, changelog takes 5 minutes), `EMIT release` fires essentially at the moment the `FORK` starts, before either branch has completed — well before changelog's 5 minutes and far before docs' 1 hour.

## 3. Is it guaranteed that docs exist when `EMIT release` executes?

**No — it is not guaranteed; in fact, under the stated timing, docs will *not* yet exist when `EMIT release` runs.**

Since the program has no `JOIN` after the `FORK`, nothing in the DSL causes `EMIT release` to wait for the branches. The specification is explicit that only a `JOIN` waits for branch completion ("`JOIN` — Waits until every branch of the corresponding `FORK` is complete"), and that without one, the continuation after `FORK` proceeds "while the branches run." There is no other rule that ties `EMIT`'s execution to the state of concurrently running branches.

Given the events — `docs` takes 1 hour and `changelog` takes 5 minutes after the fork starts, while `EMIT release` (per the answer to Q2) executes immediately when the fork starts — `EMIT release` will actually run before `docs` (and even before `changelog`) has been delivered. So not only is completion of `docs` unguaranteed at that point in general, the specific events given make it certain that `docs` does *not* exist yet when `EMIT release` executes.

## Note on what the specification does not determine

The specification does not define any semantics by which `EMIT release` would implicitly depend on data produced by the `FORK` branches (e.g., an implicit "join before emit"). It also does not specify how `EMIT` obtains or checks its content ("Semantic Principles": "`EMIT` defines an output, not its storage or transport mechanism"). If the intent of the program were for `EMIT release` to depend on `docs` and `changelog`, that would need to be expressed explicitly with a `JOIN` between the `FORK` and the `EMIT`; as written, the program does not do this, so I have not assumed such a dependency and analyzed the program exactly as written.
