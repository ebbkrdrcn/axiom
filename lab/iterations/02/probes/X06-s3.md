# Analysis of the DSL program

```
AUTO HITL:wording[short, detailed]("Short or detailed release notes?")
WHEN wording.short
  → DELEGATE short-notes
WHEN wording.detailed
  → DELEGATE detailed-notes
HITL:release[approved, rejected]("Approve the release?")
WHEN release.approved
  → EMIT release
```

This program contains two `HITL` decisions:

- `wording` — a decision, marked `AUTO`.
- `release` — a decision, **not** marked `AUTO`, and with no `→ FALLBACK` attached.

---

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **`wording`** decision may be made by the agent itself, because it is the only one written with `AUTO` directly before it on the same line (`AUTO HITL:wording[...]`). Per the spec's "Who decides a `HITL`" table and the `AUTO` section, `AUTO` applies only to the single `HITL` it is written on — here that is `wording`, not `release`.

The condition under which the agent may answer `wording` itself is:

> "the decision is certain and within the agent's authority" — i.e. the agent can determine **one single answer** from the list (`short` or `detailed`) based on the available information and the applicable criteria, and none of the uncertainty conditions listed under **AUTO** apply (missing/contradictory information; missing, ambiguous or contradictory criteria; more than one answer remaining reasonably compatible with the evidence; dependence on an unresolved interpretation; or the decision being outside the agent's authority).

If that condition holds, the agent establishes `wording.short` or `wording.detailed` itself and the human is not asked, and `FALLBACK` is not used for this decision (there is none written here in any case). If the condition does not hold, the human is asked "exactly as for a `HITL` without `AUTO`."

The `release` decision, having no `AUTO`, MUST NOT be answered by the agent under any circumstance: "`HITL` establishes a human decision boundary. It MUST NOT be replaced by an agent decision, unless it is marked with `AUTO`."

---

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No. The `release` `HITL` is written **without** `AUTO`:

```
HITL:release[approved, rejected]("Approve the release?")
```

The spec is explicit that a `HITL` "MUST NOT be replaced by an agent decision, unless it is marked with `AUTO`," and the "Who decides a `HITL`" table states that when a `HITL` has no `AUTO`, "the agent MUST NOT answer" regardless of certainty — "the human" always answers.

This is confirmed independently by the `AUTO` section's rule that "a confidence score alone, however high, does not establish certainty" — but that rule is not even the operative one here, since `AUTO` was never applied to this `HITL` in the first place. The agent must wait at the `HITL:release[...]` statement for a genuine human response; it may not treat green checks or its own confidence as a substitute answer, per rule 9 ("The agent MUST NOT invent a response, a result, an outcome, or a requirement").

---

## 3. If the wording decision is not clearly determined, what happens?

"Not clearly determined" corresponds to the spec's notion of uncertainty under `AUTO`. Per the `AUTO` table:

> "Anything else [i.e., not certain-and-within-authority] → The human is asked, exactly as for a `HITL` without `AUTO`. `FALLBACK` applies to the human's response as usual."

So:
1. The agent does **not** guess or pick an answer itself — `AUTO` "is not a request to guess."
2. The `HITL:wording[short, detailed]("Short or detailed release notes?")` question is put to the human, waiting at that statement exactly as a plain (non-`AUTO`) `HITL` would.
3. The human's response is then classified as usable, insufficient, or unavailable, as with any `HITL`.
   - A **usable** response (clearly selecting `short` or `detailed`) establishes `wording.short` or `wording.detailed`, and execution continues with the next statement (`WHEN wording.short`).
   - An **insufficient or unavailable** response would normally run the attached `→ FALLBACK`. **This program attaches no `FALLBACK` to the `wording` `HITL`.** Per the spec's `HITL` table, "Insufficient or unavailable, and there is no `FALLBACK` → Execution ends, as with `STOP`," and no outcome is established.

The specification does not state a numeric or otherwise mechanical threshold for "not clearly determined" / uncertain — it only lists qualitative conditions (missing/contradictory information, ambiguous or missing criteria, more than one answer remaining compatible with the evidence, dependence on unresolved interpretation, or the decision exceeding the agent's authority) and leaves the actual determination of uncertainty to "the runtime." I have assumed "not clearly determined" in the task's wording is exactly this spec concept of uncertainty, since the DSL defines no other applicable notion.

---

## 4. If the human answers the release question with "rejected", what happens?

`"rejected"` is one of the two listed answers for `release` (`[approved, rejected]`), so — assuming the human's reply clearly selects it (a "usable" response per the classification table) — the outcome `release.rejected` is established, and execution continues with the statement after the `HITL:release[...]` construct, i.e. `WHEN release.approved`.

At that point:
- `WHEN release.approved` is checked once: the latest outcome of `release` is `rejected`, not `approved`, so the condition is **false**. Its flow (`→ EMIT release`) is skipped, "This is not an error. Execution does not wait."
- There is no `WHEN release.rejected` in this program, and `WHEN` conditions are "never re-checked" once skipped or passed — a `WHEN` runs only if reached while true.
- `WHEN release.approved` is the last top-level statement in the program. With its flow skipped, there is nothing left to run, so execution ends normally per rule 10 ("When the last top-level statement is done, execution ends normally").

Net effect: the outcome `release.rejected` is recorded, `EMIT release` does **not** run, and the program ends without error, without emitting the release artifact, and without any state change (no `TRANSITION` in this program handles the `rejected` case at all).

**Note on what the specification does not determine:** this particular program defines no `WHEN release.rejected` branch and no `TRANSITION` for a rejection, so nothing in the DSL causes any further action (e.g., no state change, no notification) beyond what is described above. The specification does not prescribe that a "rejected" outcome must always be handled by the program — a program can legally decline to branch on an outcome it does not need — so this is a fact about *this* program's flow, not a gap in the DSL. No assumption beyond ordinary rule 2/3 (`WHEN` evaluation) and rule 10 (end of program) was needed to answer this.
