# Execution of the `polish` program

## Program

```
LOOP:polish
  WHEN draft.accepted
    → BREAK
  DELEGATE draft
  VERIFY draft
TRANSITION "Done"
```

Events: in iteration 1, `VERIFY draft` establishes `rejected`; in iteration 2, `accepted`.

## Validation

- `LOOP:polish` has a body (`WHEN`, `DELEGATE`, `VERIFY`) — valid per the `loop` grammar rule.
- `WHEN draft.accepted` tests `draft.accepted`; the program contains `VERIFY draft`, which can establish `draft.accepted` or `draft.rejected` — satisfies V6.
- `BREAK` is directly inside `LOOP:polish`'s body (not inside a `FORK` branch) — satisfies V2/V3.
- No `FORK`/`JOIN`, no `HITL`, no `REQUIRE` — V4, V5, V7, V9, V10 are not implicated.
- Indentation: `WHEN`'s `→ BREAK` is nested one level under `WHEN`, which is nested one level under `LOOP:polish`; `DELEGATE draft`, `VERIFY draft` and `TRANSITION "Done"` are all valid per **Indentation and scope**.

The program is valid; no rule is broken.

## Assumption

The specification does not explicitly define what "iteration 1" / "iteration 2" of a loop means when narrating events, but the complete example in the spec (the `delivery` loop) uses this same phrasing to mean successive passes through the loop body, counted from the first execution of the body (before any `LOOP:<name> -> loop again` line is even printed for entering the loop the first time — that line only appears when the body repeats). I follow that same convention here: "iteration 1" is the first pass through the body of `LOOP:polish`, and "iteration 2" is the pass that begins after the body finishes once. The `VERIFY draft` that runs during iteration 1 establishes `rejected`, and the one that runs during iteration 2 establishes `accepted`, per the given events. Nothing else needed to be assumed — the semantics of `LOOP`, `WHEN`, `BREAK`, `DELEGATE`, `VERIFY`, `TRANSITION`, and outcome visibility ("Before anything establishes it, every `WHEN` is false"; "Each subject holds its most recently established outcome") are all fully determined by the specification's rules.

## Step-by-step trace

Following the execution procedure (validate, then execute one statement at a time, tracking position / state / outcomes), and matching the trace conventions shown in the spec's complete example (a `LOOP:<name> -> loop again` line is emitted only when the body repeats, not on first entry):

```trace
1. WHEN draft.accepted -> false: skip
2. DELEGATE draft -> done
3. VERIFY draft -> outcome draft.rejected
4. LOOP:polish -> loop again
5. WHEN draft.accepted -> false: skip
6. DELEGATE draft -> done
7. VERIFY draft -> outcome draft.accepted
8. LOOP:polish -> loop again
9. WHEN draft.accepted -> true: run flow
10. BREAK -> break
11. TRANSITION "Done" -> state = "Done"
12. (end of program) -> end
```

### Walkthrough

- **Iteration 1**: `WHEN draft.accepted` is checked; `draft` has no outcome established yet, so per the rule "before anything establishes it, every `WHEN` on it is false," the condition is false and the flow is skipped. `DELEGATE draft` runs to completion. `VERIFY draft` establishes `draft.rejected` (per the given event). The body's last statement is done, so the loop restarts from its first statement.
- **Iteration 2**: `WHEN draft.accepted` is checked again; the latest outcome of `draft` is `rejected` (from iteration 1), which does not match `accepted`, so the condition is false and the flow is skipped again — a `WHEN` is checked fresh each time it is reached (rule: "consecutive `WHEN`s are independent... every one that is true runs," and more generally each reach of a `WHEN` is evaluated once, when reached). `DELEGATE draft` runs again. `VERIFY draft` now establishes `draft.accepted` (per the given event), replacing the previous outcome (latest value wins). The body finishes, so the loop restarts again.
- **Iteration 3**: `WHEN draft.accepted` is checked; the latest outcome of `draft` is now `accepted`, so the condition is true. The flow runs: `BREAK` executes, leaving the innermost loop (`LOOP:polish`) immediately. The remaining statements of this iteration (`DELEGATE draft`, `VERIFY draft`) are not executed, per `BREAK`'s rule that "the remaining statements of the current iteration are not executed."
- Execution continues with the first statement after the loop: `TRANSITION "Done"`, which sets the current process state to `"Done"` (replacing any prior state; there was none prior, so this is simply the first and only `TRANSITION`).
- `TRANSITION "Done"` is the last top-level statement, so execution ends normally (rule 10 of the ten execution rules).

## Answers

- **How many times is `DELEGATE draft` executed?** Twice — once in iteration 1 (result rejected) and once in iteration 2 (result accepted). It is not executed a third time, because in iteration 3 the `WHEN draft.accepted` at the top of the body is now true and `BREAK` leaves the loop before `DELEGATE draft` is reached.
- **What is the final state?** `"Done"` — set by the single `TRANSITION "Done"` statement that runs after the loop is broken out of.
