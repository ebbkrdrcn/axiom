# Execution of the given DSL program

## Program

```
FORK
  → DELEGATE lint
      VERIFY lint
      WHEN lint.rejected
        → STOP
  → DELEGATE docs
      EMIT docs
JOIN
EMIT build
```

## Validity check (informational)

Before executing, the program is checked against V1–V10. It is valid:

- `FORK` has two branches (satisfies V9's "fewer than two branches" clause).
- `STOP` inside a branch is not `BREAK`, so V3 (which only restricts `BREAK` in a branch) does not apply; `STOP` is permitted anywhere (Control / STOP section).
- The `WHEN lint.rejected` inside the lint branch tests an outcome (`lint.rejected`) established by a `VERIFY lint` that appears in the program, satisfying V6.
- The `WHEN` tests a subject established **within its own branch**, before any `JOIN`, not a subject that a *different, still-running* branch might establish — so V10 (which forbids testing, outside a `FORK`, a subject that an unjoined branch might still set) is not triggered.
- No `BREAK`, no duplicate `HITL`/`VERIFY` names, no bad indentation are present.

So the program may be executed.

## Relevant execution rules

- `FORK`: "All branches start. Within a branch, statements run sequentially." (statements run one at a time overall except that `FORK` itself runs branches concurrently — rule 1 of "Execution in ten rules").
- `FORK` table: **"`STOP` in any branch → The whole execution ends, including all other branches."**
- `STOP`: "No further statement runs anywhere, including other `FORK` branches. A pending `JOIN` never completes."
- Events given: `VERIFY lint` establishes `rejected`; at that moment the docs branch has executed `DELEGATE docs` but not yet `EMIT docs`.

## Step-by-step trace

```trace
1. FORK -> branches started
2. DELEGATE lint -> done
3. DELEGATE docs -> done
4. VERIFY lint -> outcome lint.rejected
5. WHEN lint.rejected -> true: run flow
6. STOP -> stop
```

Walkthrough:

1. `FORK` is reached: both branches start. From here on, the lint branch (`DELEGATE lint → VERIFY lint → WHEN lint.rejected → STOP`) and the docs branch (`DELEGATE docs → EMIT docs`) run concurrently.
2. Lint branch: `DELEGATE lint` completes.
3. Docs branch: `DELEGATE docs` completes. Per the stated events, at the moment `VERIFY lint` establishes its outcome, the docs branch is exactly here — `DELEGATE docs` done, `EMIT docs` not yet run/not yet done.
4. Lint branch: `VERIFY lint` evaluates the result and establishes the outcome `lint.rejected`.
5. Lint branch: `WHEN lint.rejected` is checked; the condition is true, so its flow runs (its only statement is `STOP`).
6. Lint branch: `STOP` executes. By the `FORK` rule "`STOP` in any branch → the whole execution ends, including all other branches" and the `STOP` rule "No further statement runs anywhere, including other `FORK` branches," the entire execution ends immediately.

Because `STOP` ends everything the instant it runs, the docs branch is aborted exactly where the events said it was (after `DELEGATE docs`, before `EMIT docs`), and nothing after the `FORK`/`JOIN` construct is reached at all.

## Answers

- **Is `EMIT docs` executed?** No. The docs branch had completed `DELEGATE docs` but had not yet run `EMIT docs` when `STOP` fired in the lint branch. `STOP` ends the whole execution immediately, including all other running `FORK` branches, so `EMIT docs` never runs.

- **Is `JOIN` completed?** No. `STOP` ends execution before the flow ever reaches `JOIN`. Even independently of that, the spec is explicit that "a pending `JOIN` never completes" once `STOP` has fired — the docs branch was not complete, so `JOIN`'s wait condition ("every branch of the corresponding `FORK` is complete") was not met, and now never will be, because execution has ended.

- **Is `EMIT build` executed?** No. `EMIT build` is the top-level statement after `JOIN`, which is never reached: `STOP` in the lint branch ends the entire execution immediately, so no further statement runs anywhere in the program, including `JOIN` and `EMIT build`.

## Assumptions

The specification defines the *effects* of concurrent execution precisely (e.g., what `STOP` does, what counts as branch completion) but does not prescribe a total order for interleaving concurrent branches' steps in a trace — it only says statements within one branch run sequentially, and branches run concurrently. The step-by-step trace above orders the lint- and docs-branch steps according to the relative timing explicitly given in the task's "Events" description (docs branch has finished `DELEGATE docs` but not `EMIT docs` at the moment `VERIFY lint` resolves), which is the only ordering the specification's data lets us pin down; no other interleaving is asserted or needed to answer the three questions, since the outcome (`STOP` aborts everything) is the same regardless of the exact interleaving before that point.
