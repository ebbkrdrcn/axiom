```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

- **Identifiers for the delegated work/result.** The requirement says "the implementation" without giving it a name. I used the identifier `implementation` for both `DELEGATE implementation` and `VERIFY implementation`. This is permitted: V7 only forbids a name being shared between a `HITL` and a `VERIFY` (or reused across two `HITL`s); it does not restrict `DELEGATE` names, and the spec's own example under `DELEGATE` pairs `DELEGATE implementation` with `VERIFY implementation` the same way.

- **HITL name and answer labels.** The requirement describes "a merge decision," "the decision to merge," and "the decision not to merge," but does not give a decision name or answer identifiers. I named the decision `merge` and used the answers `approved` / `declined` (the same pair used in the spec's own worked examples for a merge `HITL`), since the DSL requires an explicit answer list of identifiers.

- **No `FALLBACK`.** The requirement says nothing about what should happen if the human's response is insufficient or never comes. I did not invent a fallback flow. Per the spec's `HITL` rules, with no `FALLBACK` attached, an insufficient or unavailable response simply ends execution (as with `STOP`), and no outcome is established — this is the behavior that applies by default.

- **`VERIFY implementation`'s outcome is not branched on.** The requirement only says "verify it" before moving on to the merge decision; it does not say to do anything different depending on whether the implementation was accepted or rejected. Per the spec, `VERIFY` does not itself branch and does not require a following `WHEN`, so I left its `accepted`/`rejected` outcome established but unused.

- **No `REQUIRE`, `LOOP`, or `FORK`.** The requirement describes a single straight-line sequence (delegate → verify → decide → transition) with no mention of a prerequisite that must be available first, any repetition/retry, or concurrent work, so none of these constructs were used.

- **No `TRANSITION` before the decision.** The requirement only specifies the two post-decision states, `"Merged"` and `"Rework"`; it does not name any state the process should be in beforehand, so no earlier `TRANSITION` was added.

- **Order of `AUTO HITL` relative to `DELEGATE`/`VERIFY`.** The requirement's sentence order ("Delegate... verify it. Then a merge decision...") directly determines the statement order, so this required no assumption beyond translating "then" into sequential statements.
