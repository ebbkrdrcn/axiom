# Validity check of the four snippets

## Snippet A — INVALID (rule V5)

```
HITL:release[approved, rejected]("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

`AUTO` is used as a standalone statement, followed by an indented block (`WHEN decision.uncertain → HITL(...)`), rather than appearing directly before a decision `HITL:<name>[...]` on the same line.

- Per the `AUTO` section: "`AUTO` is written directly before `HITL`, on the same line... `AUTO` is not a statement on its own and applies to nothing else (rule V5)."
- Per rule **V5**: "`AUTO` is not immediately followed, on the same line, by a decision `HITL:<name>[…]`" → INVALID.
- This is in fact essentially the exact invalid example given in the specification itself:
  ```invalid
  AUTO
    WHEN decision.uncertain
      → HITL("Approve?")
  ```
  which the spec explicitly lists as INVALID.
- Additionally, `AUTO` "never contains a flow," which this snippet also violates, but that failure is subsumed under V5 since `AUTO` here has no attached decision `HITL` at all.

Verdict: **INVALID — rule V5** (AUTO not immediately followed on the same line by a decision HITL).

## Snippet B — INVALID (rule V2)

```
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

`BREAK` appears inside a `WHEN` flow, but there is no enclosing `LOOP` anywhere in the snippet.

- Per the `BREAK` section: "Leaves the innermost enclosing `LOOP` immediately... INVALID outside a `LOOP` (V2)."
- Per rule **V2**: "`BREAK` is not inside a `LOOP`" → INVALID.

Verdict: **INVALID — rule V2** (BREAK is not inside a LOOP).

## Snippet C — VALID

```
AUTO HITL:approve[yes, no]("Approve release?")
WHEN approve.yes
  → EMIT release
```

Checked against the validity rules:

- **V5** (AUTO must be immediately followed, same line, by a decision `HITL:<name>[…]`): satisfied — `AUTO HITL:approve[yes, no]("Approve release?")` is a decision HITL with a name and answer list, on the same line as `AUTO`.
- **V6** (a `WHEN` must test a subject/outcome the program can produce): satisfied — `WHEN approve.yes` tests the subject `approve` with outcome `yes`, and `HITL:approve[yes, no]` lists `yes` as one of its declared answers.
- **V7** (no duplicate HITL/VERIFY names, no empty/repeated answer lists): satisfied — only one `HITL` name (`approve`), answers `yes` and `no` are distinct and non-empty.
- **V4** (arrow items only under WHEN/FORK/FALLBACK, etc.): satisfied — `→ EMIT release` is correctly nested under `WHEN`.
- No `FALLBACK` is required for a `HITL`; it is optional ("`REQUIRE`/`HITL` ... only a `→ FALLBACK`" is permitted, not mandatory), so its absence is not a defect.
- No `BREAK`, `FORK`/`JOIN`, or indentation issues are present.

There is no `WHEN approve.no` branch, but the specification does not require an "else" — "there is no 'else' and no 'first match'" (Quick reference, `WHEN` row; Execution rule 3) — so an uncovered answer is permitted.

Verdict: **VALID** (no rule V1–V10 is violated).

## Snippet D — INVALID (rule V8)

```
HITL:region[eu, us]("Which region?")
  → FALLBACK
      → TRANSITION "Blocked"
WHEN region.eu
  → DELEGATE eu-deployment
```

The `FALLBACK` flow attached to `HITL:region` contains only `→ TRANSITION "Blocked"` and does not end with `STOP` or `BREAK`.

- Per the `FALLBACK` section: "Its last item MUST be `STOP` or `BREAK` (rule V8). The fallback never continues into the normal flow."
- Per rule **V8**: "the last item of a fallback flow is not `STOP` or `BREAK`" → INVALID.

Verdict: **INVALID — rule V8** (fallback flow's last item is not STOP or BREAK).
