# Execution of the given DSL program

## Program

```
FORK
  → DELEGATE unit-tests
      VERIFY unit-tests
  → DELEGATE integration-tests
      VERIFY integration-tests
JOIN
WHEN unit-tests.accepted
  → TRANSITION "Ready"
WHEN integration-tests.rejected
  → TRANSITION "Debugging"
```

Events:
- `VERIFY unit-tests` establishes `accepted`.
- `VERIFY integration-tests` establishes `rejected`, and this branch finishes later (i.e. after the unit-tests branch).

## Validity check

- `FORK` has two `→` branches (≥ 2) → satisfies V9.
- `JOIN` has a corresponding preceding `FORK` at the same indentation with no prior `JOIN` → satisfies V9.
- `WHEN unit-tests.accepted`: the program contains `VERIFY unit-tests`, and `accepted` is one of the two `VERIFY` outcomes → satisfies V6.
- `WHEN integration-tests.rejected`: the program contains `VERIFY integration-tests`, and `rejected` is one of the two `VERIFY` outcomes → satisfies V6.
- Both `WHEN`s test subjects (`unit-tests`, `integration-tests`) that are established inside branches of the `FORK` above them, but both `WHEN`s appear **after** the `JOIN` that closes that `FORK` → satisfies V10 (a `WHEN` on such a subject is only invalid if it appears *before* the join).
- No `BREAK`, `AUTO`, `HITL`, `REQUIRE`, or nested `LOOP` is present, so V1–V5, V7, V8 raise no issues.

The program is **valid**.

## Step-by-step execution

Per the DSL's own conventions (see the "Complete example" trace in the spec), the two concurrent branches of a `FORK` are written out as consecutive trace lines — one statement at a time, in the order each is completed — and the `→` arrows are omitted from the trace text, just as in the specification's example (`VERIFY implementation`, `DELEGATE docs`, ... with no `→`). The event note that `VERIFY integration-tests` "finishes later" tells us the runtime must wait for that branch before the `JOIN` completes; it does not change the fact that, once both branches are complete, both of their statements have run to completion by the time `JOIN` is reached.

```trace
1. FORK -> branches started
2. DELEGATE unit-tests -> done
3. VERIFY unit-tests -> outcome unit-tests.accepted
4. DELEGATE integration-tests -> done
5. VERIFY integration-tests -> outcome integration-tests.rejected
6. JOIN -> joined
7. WHEN unit-tests.accepted -> true: run flow
8. TRANSITION "Ready" -> state = "Ready"
9. WHEN integration-tests.rejected -> true: run flow
10. TRANSITION "Debugging" -> state = "Debugging"
11. (end of program) -> end
```

### Why each step happens this way

1. **`FORK`** starts both branches concurrently (Execution rule 1; FORK section: "All branches start. Within a branch, statements run sequentially.").
2–3. Branch 1 (`unit-tests`) runs `DELEGATE unit-tests` to completion, then `VERIFY unit-tests`, which establishes exactly one outcome, `unit-tests.accepted` (VERIFY section: "It establishes exactly one outcome"). This branch is now complete (FORK section: "A branch's last statement is done → That branch is complete.").
4–5. Branch 2 (`integration-tests`) runs `DELEGATE integration-tests`, then `VERIFY integration-tests`, which establishes `integration-tests.rejected`. Per the stated event, this branch finishes later than branch 1, but a rejected outcome does not abort or otherwise short-circuit the branch (FORK section: "A `VERIFY` in a branch establishes `rejected` → The branch continues normally. A negative outcome does not abort a branch."). Once its last statement is done, this branch too is complete.
6. **`JOIN`** waits until every branch of the corresponding `FORK` is complete (JOIN section). Since branch 2 finishes later, `JOIN` is what actually waits on it in real time; once both branches have completed, `JOIN` proceeds, and the outcomes `unit-tests.accepted` and `integration-tests.rejected` established inside the branches become available after it (JOIN section: "Outcomes established inside the branches are available after the `JOIN`.").
7. **`WHEN unit-tests.accepted`** is checked once, now that execution reaches it. The latest outcome of `unit-tests` is `accepted`, so the condition is true and its flow runs (WHEN section; Execution rule 2).
8. The flow's only statement, **`TRANSITION "Ready"`**, sets the current process state to `"Ready"`.
9. **`WHEN integration-tests.rejected`** is an independent, separate `WHEN` (Execution rule 3: "Consecutive `WHEN`s are independent... Every one that is true runs, top to bottom."). The latest outcome of `integration-tests` is `rejected`, so this condition is also true and its flow runs. (This is legal because the outcome was already established, and made visible, before the `JOIN` at step 6 — see V10 discussion above.)
10. Its flow's only statement, **`TRANSITION "Debugging"`**, replaces the current process state. Per the TRANSITION rule, "the most recently executed one wins," so the state set to `"Ready"` in step 8 is overwritten.
11. There are no more top-level statements, so execution **ends normally** (Execution rule 10).

## Final state

**`Debugging`**

This is because both `WHEN`s are independently true and both run (there is no "else" and no "first match" among consecutive `WHEN`s), and `TRANSITION` always keeps only the most recently executed value — the `TRANSITION "Debugging"` in step 10 runs after, and therefore overrides, the `TRANSITION "Ready"` in step 8.

## Assumptions made where the specification does not fully determine the answer

- **Real-time interleaving of concurrent branch statements in the trace.** The specification's own execution model says statements inside different `FORK` branches run concurrently, but a written trace is inherently a single sequential list of "one line per executed step." The specification does not give a rule for exactly how to interleave two concurrently-running branches' individual statements in such a list (e.g., DELEGATE1, DELEGATE2, VERIFY1, VERIFY2 vs. DELEGATE1, VERIFY1, DELEGATE2, VERIFY2). I followed the convention shown in the spec's own "Complete example" trace, which lists one branch's statements to completion pattern-wise as they naturally occur, and used the given event ("integration-tests finishes later") only to determine that both branches are fully complete, in the order unit-tests-then-integration-tests, before `JOIN` proceeds. The final state does not depend on this ordering choice, since `JOIN` cannot complete until both branches are done regardless of the order in which their steps are listed.
- **No explicit "waiting" trace line for `JOIN`.** The effect vocabulary includes `waiting`, and in real time `JOIN` does wait for the slower `integration-tests` branch. However, the specification's own worked example represents a `FORK`/`JOIN` pair with a plain `joined` line and no separate `waiting` step once all branches' statements have been listed in the trace. I followed that precedent rather than inserting an additional `waiting` line for `JOIN`, since by the time `JOIN` appears in the trace both branches have already completed.
