# Execution of the DSL program

## 1. Validity check (V1–V10)

The program is well-formed:

- **V1** (indentation): consistent, no violation.
- **V2/V3** (`BREAK`): the single `BREAK` is nested under `WHEN ship.yes`, which is nested under `WHEN build.accepted`, which is in the `LOOP:release` body, and none of this is inside a `FORK` branch. Valid.
- **V4** (`→` placement / `FALLBACK`): every `→` item is under a `WHEN` or a `FORK`; the one `→ FALLBACK` is directly under the `HITL` (`AUTO HITL:ship[...]`) and is the only `FALLBACK` there. Valid.
- **V5** (`AUTO`): `AUTO` is immediately followed on the same line by the decision `HITL:ship[yes, no](...)`. Valid.
- **V6** (`WHEN` subjects declared): `build.rejected`/`build.accepted` ← `VERIFY build`; `changelog.rejected` ← `VERIFY changelog`; `ship.yes` ← `HITL:ship[yes, no]`. Valid.
- **V7** (names/answers): only one `HITL` (`ship`), its name doesn't collide with any `VERIFY` subject, and its answer list `[yes, no]` is non-empty with no repeats. Valid.
- **V8** (`FALLBACK` ending): the fallback flow is `→ TRANSITION "Stalled"`, `→ STOP` — ends in `STOP`. Valid.
- **V9** (`FORK`/`JOIN`): the `FORK` has exactly 2 branches and is followed by a matching `JOIN`. Valid.
- **V10** (`WHEN` vs. un-joined `FORK`): `WHEN build.rejected`, `WHEN changelog.rejected`, `WHEN build.accepted` all appear **after** `JOIN`, so they may safely test outcomes the branches established. `WHEN ship.yes` tests an outcome from `HITL`, unrelated to the `FORK`. Valid.

No rule is broken, so the program **may be executed**.

## 2. Assumptions (the spec doesn't fully determine these)

1. **`AUTO HITL:ship` certainty.** The spec says `AUTO` may resolve automatically only when the agent can determine one single answer with certainty, and that "uncertainty" is a runtime judgment, not an algorithm the DSL defines (Semantic Principles: "`AUTO` defines when automatic decision resolution is permitted, not an algorithm or confidence threshold"). The task's context gives an explicit, unambiguous criterion ("ship exactly when build and changelog are both accepted in the same iteration") and states the agent has authority to act on it. By the time `WHEN build.accepted` is reached, both `build`'s and `changelog`'s latest outcomes for that iteration are already established (the preceding `FORK` was already joined). I therefore treat the decision as **certain in every iteration that reaches this `WHEN`**: answer `yes` if `changelog.accepted` also holds, otherwise `no`. This is an interpretation of "certain," not something the DSL itself computes — the spec leaves that judgment to the runtime/agent.
2. **No human ever needed.** Because the decision is certain in all iterations reached, "no human is available at any time" never actually matters for `ship`: the human is never asked, and the `FALLBACK` under it is never triggered. If a future iteration made the decision uncertain, execution would wait at the `HITL` indefinitely (no timeout is defined for `HITL`), since no human is available to answer and the spec does not say when a runtime "gives up" waiting and treats a response as unavailable — that threshold is left to the runtime, not the DSL.
3. **`FORK` branch trace ordering.** The DSL only guarantees each branch's statements run sequentially within that branch and that both branches are running concurrently after `FORK`; it does not fix an interleaving for a written trace. Following the convention used in the specification's own complete example, I list branch 1 (`VERIFY build`) fully before branch 2 (`DELEGATE changelog` → `VERIFY changelog`) in each iteration's trace; this is a presentation choice, not a claim about real-time ordering.
4. **`LOOP` itself is not a traced step.** As in the spec's own worked example, entering the loop body the first time is not logged as a separate line; only the repeat is logged, as `LOOP:release -> loop again`.

## 3. Full execution trace

```trace
1.  REQUIRE service-spec -> done
2.  DELEGATE build -> done
3.  FORK -> branches started
4.  VERIFY build -> outcome build.rejected
5.  DELEGATE changelog -> done
6.  VERIFY changelog -> outcome changelog.accepted
7.  JOIN -> joined
8.  WHEN build.rejected -> true: run flow
9.  TRANSITION "Fixing" -> state = "Fixing"
10. DELEGATE fix -> done
11. WHEN changelog.rejected -> false: skip
12. WHEN build.accepted -> false: skip
13. LOOP:release -> loop again

14. DELEGATE build -> done
15. FORK -> branches started
16. VERIFY build -> outcome build.accepted
17. DELEGATE changelog -> done
18. VERIFY changelog -> outcome changelog.rejected
19. JOIN -> joined
20. WHEN build.rejected -> false: skip
21. WHEN changelog.rejected -> true: run flow
22. DELEGATE changelog-fix -> done
23. WHEN build.accepted -> true: run flow
24. AUTO HITL:ship[yes, no]("Ship this build?") -> outcome ship.no
25. WHEN ship.yes -> false: skip
26. TRANSITION "Holding" -> state = "Holding"
27. LOOP:release -> loop again

28. DELEGATE build -> done
29. FORK -> branches started
30. VERIFY build -> outcome build.accepted
31. DELEGATE changelog -> done
32. VERIFY changelog -> outcome changelog.accepted
33. JOIN -> joined
34. WHEN build.rejected -> false: skip
35. WHEN changelog.rejected -> false: skip
36. WHEN build.accepted -> true: run flow
37. AUTO HITL:ship[yes, no]("Ship this build?") -> outcome ship.yes
38. WHEN ship.yes -> true: run flow
39. BREAK -> break
40. EMIT release -> done
41. TRANSITION "Released" -> state = "Released"
42. (end of program) -> end
```

Notes on the two `AUTO HITL:ship` resolutions:

- **Step 24 (iteration 2):** `build.accepted` but `changelog.rejected` → not both accepted → per the criterion the certain answer is `no`. Resolved automatically, no human asked, `FALLBACK` not used.
- **Step 37 (iteration 3):** `build.accepted` and `changelog.accepted` → both accepted → per the criterion the certain answer is `yes`. Resolved automatically, no human asked, `FALLBACK` not used. `WHEN ship.yes` is then true, so `BREAK` fires and ends `LOOP:release`.

## 4. Final state

**`"Released"`** (set by the final `TRANSITION "Released"` after the loop ends and `EMIT release` runs).

## 5. How many times does `DELEGATE build` run?

**Three times** — once per loop iteration (steps 2, 14, and 28), one for each of the three iterations described in the events (the loop runs exactly 3 times before `BREAK` ends it in iteration 3).
