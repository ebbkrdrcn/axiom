# DSL Solution

## DSL Code

```
LOOP:deliver
  DELEGATE implementation
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
EMIT source-code
```

## Assumptions

1. **Loop name**: The specification requires `LOOP:<name>`, but the requirement does not specify a name. I chose "deliver" as a descriptive label for the repetitive process.

2. **Work item identifiers**: I assumed the work items are named "implementation" and "correction" based on the requirement's wording. The specification does not prescribe how work items are named in the runtime; the names are provided by the requirement itself.

3. **Verification outcomes**: I assume that `VERIFY implementation` will establish either `implementation.accepted` or `implementation.rejected`. The specification defines these as the only two possible outcomes from any VERIFY statement (V6), so this is not an assumption but follows directly from the spec.

4. **Artifact identifier**: The requirement says "emit source-code" (with a hyphen). I used "source-code" as the artifact identifier in the `EMIT` statement. The specification does not define how artifacts are named; this naming comes from the requirement.

5. **Loop flow on rejection**: When verification rejects, the requirement says "delegate a correction and then repeat from the start." I assume this means: after the WHEN statement runs `DELEGATE correction`, the loop's last statement is complete, so the next iteration begins (per rule 1 of "Execution in ten rules"). The next iteration re-enters at `DELEGATE implementation`. This assumes the correction addresses the issue such that re-delegating and re-verifying is the intended behavior.

6. **No fallback needed**: I assumed that neither the DELEGATE, VERIFY, nor WHEN statements require a `→ FALLBACK` clause. The requirement describes the successful path only, and the specification treats FALLBACK as optional (required only for REQUIRE and HITL in error cases).

7. **No external requirements**: The requirement does not mention any unavailable items or dependencies. I assumed no `REQUIRE` statement is needed, and the process can begin immediately.
