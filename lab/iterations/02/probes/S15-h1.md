# go_harness DSL Execution Trace and Analysis

## Program
```
FORK
  → DELEGATE lint
      VERIFY lint
      WHEN lint.rejected
        → STOP
  → DELEGATE docs
      EMIT docs
JOIN
EMIT build
```

## Events
- `VERIFY lint` establishes `rejected`
- At that moment, the docs branch has executed `DELEGATE docs` but not `EMIT docs`

## Execution Trace

```
1. FORK -> branches started
2. DELEGATE lint -> done
3. VERIFY lint -> outcome lint.rejected
4. WHEN lint.rejected -> true: run flow
5. STOP -> stop
```

## Answers

### Is `EMIT docs` executed?
**No.** STOP terminates the entire execution immediately, including all running branches. Although DELEGATE docs has completed, EMIT docs never starts or executes.

### Is `JOIN` completed?
**No.** According to the specification, "A pending `JOIN` never completes" when STOP is reached. Execution terminates before the JOIN statement is ever reached.

### Is `EMIT build` executed?
**No.** Since execution stops at the STOP statement in branch 1, the program never reaches JOIN or any subsequent statements. Therefore, EMIT build is never executed.

## Explanation

When STOP executes at step 5, the specification states (from **Execution in ten rules**, rule 6):
- "No further statement runs anywhere, including other `FORK` branches."
- The remaining statements in branch 2 (EMIT docs), the JOIN statement, and EMIT build all become unreachable.

This is a key difference from BREAK, which only exits the innermost loop. STOP terminates the entire execution immediately and unconditionally.

**Final State:** Execution terminated by STOP; branch 2 incomplete; all statements after FORK unexecuted.
