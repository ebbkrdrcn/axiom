# DSL

```
LOOP:implementation
  DELEGATE implementation
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
EMIT source-code
```

## Assumptions

1. **Subject name for outcomes**: The verification subject is named `implementation`. The WHEN conditions reference `implementation.accepted` and `implementation.rejected`, established by the single `VERIFY implementation` statement.

2. **Delegate work names**: The work delegated is named `implementation` (first delegation) and `correction` (second delegation when rejection occurs).

3. **Loop semantics**: "Repeat from the start" means the next iteration of the loop begins at its first statement (`DELEGATE implementation`). This is the natural behavior when the loop body completes without a `BREAK` or `STOP`.

4. **Emit artifact name**: The artifact to emit after the loop ends is named `source-code`, matching the requirement's phrasing.

5. **Verification outcomes**: "If the verification accepts it" maps to `WHEN implementation.accepted`, and "if the verification rejects it" maps to `WHEN implementation.rejected`. These are the only two outcomes `VERIFY` can establish per the specification (rule V6).

6. **Correction handling**: The `DELEGATE correction` statement represents the work done to fix the implementation. The requirement does not specify whether the correction result itself is verified; the DSL only delegates the correction and then naturally repeats the loop to verify the (corrected) implementation again.

7. **Sequential execution**: All statements run sequentially. The correction is completed before the next iteration begins, consistent with rule 1 of **Execution in ten rules**.
