# Analysis of go_harness DSL Program

## Question 1: When `VERIFY fix` establishes `accepted`, which loop does the `BREAK` exit, and which statement executes next?

**Answer:** The `BREAK` exits the **`LOOP:fix`** (the innermost loop), and the next statement to execute is **`TRANSITION "Fixed"`**.

**Reasoning:** According to the specification section on **BREAK** (line 195): "Leaves the innermost enclosing `LOOP` immediately." Since the `BREAK` statement is nested inside `LOOP:fix`, which is itself nested inside `LOOP:release`, the `BREAK` exits only the innermost loop (`LOOP:fix`). Execution then continues with the first statement after `LOOP:fix` at the same indentation level as `LOOP:fix`, which is `TRANSITION "Fixed"`.

## Question 2: Could the author write `BREAK release` inside `LOOP:fix` to leave both loops at once?

**Answer:** No, this is not possible. The syntax for `BREAK` is incorrect, and the DSL does not support leaving a named loop.

**Reasoning:** From the BREAK section (line 88): "`<name>` is only a label. No statement refers to it; `BREAK` takes no name." The grammar (line 589) shows `BREAK` has no parameters: `( "JOIN" | "BREAK" | "WAIT" | "STOP" ) , NL`. Therefore, `BREAK release` would be syntactically invalid. Furthermore, `BREAK` always leaves only the innermost enclosing loop—there is no mechanism to leave multiple loops at once. To exit both loops, the code would need to either establish the condition that causes `BREAK` in the outer loop, or use `STOP` to end the entire execution.

## Question 3: If `VERIFY release-candidate` establishes `rejected`, what executes next?

**Answer:** The program **loops back to the beginning of `LOOP:release`**, which means the next execution starts with `LOOP:fix`.

**Reasoning:** The program structure shows that `VERIFY release-candidate` and `WHEN release-candidate.accepted` are the last two statements in the body of `LOOP:release`. When `VERIFY release-candidate` establishes `rejected`, the outcome is `release-candidate.rejected`, not `release-candidate.accepted`. According to Execution rule 2 (line 58): "A `WHEN` is checked once, when execution reaches it. True → run its flow, then continue after the `WHEN`. False → skip it." Since the condition is false, the `WHEN` is skipped. After the `WHEN`, we have reached the end of the `LOOP:release` body. According to Execution rule 5 (line 61): "At the end of a loop body, the body starts again from its first statement." Therefore, execution loops back and begins another iteration of `LOOP:release`, starting with `LOOP:fix`.
