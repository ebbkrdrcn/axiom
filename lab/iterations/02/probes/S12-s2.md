# Execution of the DSL Program (Runs A–D)

## Program

```
DELEGATE release-notes
HITL:notes[approved, rejected]("Approve the release notes?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN notes.approved
  → TRANSITION "Published"
  → EMIT release-notes
WHEN notes.rejected
  → TRANSITION "Rework"
```

- **V2/V3**: no `BREAK` in the program; not applicable.
- **V4**: `→ FALLBACK` appears directly under the `HITL`, and there is exactly one `FALLBACK`; no violation.
- **V5**: no `AUTO` used; not applicable.
- **V6**: `WHEN notes.approved` and `WHEN notes.rejected` both refer to answers listed in `HITL:notes[approved, rejected]`; no violation.
- **V7**: only one `HITL` (named `notes`), no `VERIFY` reuses that name, the answer list is non‑empty and has no repeats; no violation.
- **V8**: the fallback flow's last item is `STOP`; no violation.
- **V9**: no `FORK`/`JOIN`; not applicable.
- **V10**: no `FORK`; not applicable.

The program is **valid** and may be executed.

## Assumptions (not determined by the specification)

The specification does not say when `DELEGATE release-notes` completes, since only the human's `HITL` response is described as an event for each run. I assume the delegated work is delivered (i.e., `DELEGATE release-notes` finishes) before the `HITL` is reached in all four runs, since the task's events concern only the human's response to the `HITL`. This does not affect the final state of any run; it only fixes step 1 of every trace as `done`.

For **Run D**, the response "Not like this, rewrite the intro." is not one of the exact listed answer words (`approved`/`rejected`). Per the rule "Clearly selects exactly one listed answer (in any wording)" is usable, I treat "Not like this" as an unambiguous rejection (it is not ambiguous between `approved` and `rejected`, and it is on‑topic — it directly answers the approval question). The additional remark "rewrite the intro" is extra commentary that does not change which of the two listed answers was selected, and `HITL:notes[...]` establishes only the outcome, not any extra content. I therefore classify this response as **usable**, selecting `rejected`. This is an interpretive judgment call, not a literal-word match, and the specification does not fully pin down borderline wording like this; a different reading (treating it as "insufficient" because it doesn't use the word "rejected") is not what I chose, but is the main alternative worth flagging.
