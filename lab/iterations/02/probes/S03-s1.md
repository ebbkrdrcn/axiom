```text
FORK
  → DELEGATE security-review
      VERIFY security-review
  → DELEGATE performance-review
      VERIFY performance-review
JOIN
TRANSITION "Release"
```

## Assumptions

- **No conditional branching on the review outcomes.** The requirement says only to "continue" after both flows finish and then transition to `"Release"`; it does not say what should happen if a review is rejected. So no `WHEN` on `security-review.accepted/rejected` or `performance-review.accepted/rejected` is added, and the program transitions to `"Release"` regardless of whether either `VERIFY` establishes `accepted` or `rejected`. (The spec explicitly allows this: `VERIFY` "does not branch"; a `WHEN` is optional, and outcomes need not be tested at all.)
- **Identifiers for the delegated work/results.** The spec doesn't fix vocabulary for "security review" and "performance review," only that identifiers are letters/digits/`-`/`_` starting with a letter. I used `security-review` and `performance-review` as the `DELEGATE`/`VERIFY` argument in each branch, treating the delegated work and the thing verified as the same named item (consistent with the spec's own `DELEGATE implementation` / `VERIFY implementation` pattern).
- **"Each review is delegated and then verified within its own parallel flow"** is read as: each `FORK` branch is a two-step sequential flow (`DELEGATE` then `VERIFY` of the same item), which matches the DSL's rule that `→` items under `FORK` are separate concurrent branches and statements within a branch run sequentially.
- **"Continue only after both flows have finished"** maps directly to `JOIN`, since `JOIN` waits for every branch of the nearest open `FORK` to complete, and a `VERIFY` establishing `rejected` still counts as branch completion (per the FORK/JOIN rules).
- **No `REQUIRE`, `HITL`, `LOOP`, or `STOP` is used**, since the requirement mentions none of these constructs and the spec says to execute/write exactly what is stated — nothing more. Execution ends normally after the `TRANSITION "Release"` statement (the last top-level statement), per rule 10 of the ten execution rules, so no trailing `STOP` is needed.
- **Two branches satisfy V9** (`FORK` needs at least two `→` branches, and `JOIN` needs a corresponding `FORK`), and the `JOIN` is placed at the same indentation as `FORK` with nothing else between, so it unambiguously corresponds to this `FORK`.
