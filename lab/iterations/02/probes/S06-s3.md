# Trace of the `LOOP:build` program

## Program

```text
LOOP:build
  DELEGATE build
  VERIFY build
  WHEN build.accepted
    → BREAK
EMIT build-report
```

Given event: in every iteration, `VERIFY build` establishes `build.rejected`.

## Step-by-step reasoning

**Validation.** The program is well-formed under V1–V10: the indentation is a single `LOOP` body containing `DELEGATE`, `VERIFY`, and a `WHEN` whose only child is a `→ BREAK` item; `BREAK` is inside the `LOOP` it leaves (no `FORK` involved), so V2/V3 are satisfied; `WHEN build.accepted` tests an outcome that `VERIFY build` can produce (`accepted`/`rejected`), satisfying V6. `EMIT build-report` is a top-level statement after the loop. No `FORK`/`JOIN`, `HITL`, or `REQUIRE` appear, so V4, V5, V7, V9, V10 don't apply. The program is valid and may be executed.

**Iteration 1**

1. `DELEGATE build` → the actor performs the work; the statement is done only once a result is delivered. Effect: `done`.
2. `VERIFY build` → evaluates the delivered result against acceptance criteria. Per the given event, this establishes the outcome `build.rejected` (this becomes the *latest* value for the subject `build`). Effect: `outcome build.rejected`.
3. `WHEN build.accepted` → checked once, now, at the moment execution reaches it (rule: "A `WHEN` is checked once, when reached"). The latest outcome of `build` is `rejected`, not `accepted`, so the condition is false. Per rule 2/Quick reference, false → skip the flow (the `→ BREAK` item is not run) and continue after the `WHEN`. This is not an error and execution does not wait. Effect: `false: skip`.
4. End of loop body reached (the `WHEN` was the last statement of the body, and it is "done" whether it ran its flow or was skipped). Per the `LOOP` rule ("at the end of a loop body, the body starts again from its first statement") and rule 5, the next iteration starts at `DELEGATE build`. Effect: `loop again`.

**Iteration 2**

5. `DELEGATE build` → runs again from the top of the body. Effect: `done`.
6. `VERIFY build` → again establishes `build.rejected`. This is a *new* establishment of the outcome; per the "Latest value" rule it replaces the previous `build.rejected` value with a new one (the value happens to be the same, but it is a fresh evaluation, not a carried-over one — `VERIFY` always evaluates the current result, it does not read stale state). Effect: `outcome build.rejected`.
7. `WHEN build.accepted` → checked again, independently of iteration 1 (a `WHEN` is "never re-checked" automatically, but here execution has physically reached this line again as part of the repeated body, and it is evaluated fresh against the current latest outcome). Latest outcome of `build` is still `rejected`, so the condition is false again. Effect: `false: skip`.
8. End of loop body reached again → the body starts a third time at `DELEGATE build`. Effect: `loop again`.

As formal trace lines:

```trace
1. DELEGATE build -> done
2. VERIFY build -> outcome build.rejected
3. WHEN build.accepted -> false: skip
4. LOOP:build -> loop again
5. DELEGATE build -> done
6. VERIFY build -> outcome build.rejected
7. WHEN build.accepted -> false: skip
8. LOOP:build -> loop again
```

(Execution then proceeds into a third iteration, identical in shape, and so on.)

## Is / when `EMIT build-report` executed?

`EMIT build-report` is **not** executed during either of the first two iterations, and is not reached at all as long as the stated event holds.

Reasoning from the specification:

- `EMIT build-report` is a top-level statement positioned *after* the `LOOP`. Execution can only reach it in one of two ways: (a) the loop's `BREAK` fires, transferring control to "the first statement after that loop" (the `BREAK` section), or (b) the loop's whole execution is ended by `STOP` (which would end everything, not just reach `EMIT`).
- `BREAK` only runs if the flow under `WHEN build.accepted` is executed, which requires the condition `build.accepted` to be true when the `WHEN` is checked.
- Since `VERIFY build` establishes `build.rejected` in every iteration (as given), the latest outcome of `build` is always `rejected` at the moment each `WHEN build.accepted` is checked. Per the outcome rules, a subject holds only its most recently established outcome, and a `WHEN` is false unless that exact outcome matches; `rejected ≠ accepted`, so the condition is false every time.
- Consequently `BREAK` never runs, the loop never ends, and execution keeps restarting the body indefinitely ("the loop repeats indefinitely" — this matches the specification's own worked example of this exact program).
- Since the loop never ends, the statement after the loop (`EMIT build-report`) is never reached.

**Conclusion:** Under the stated events, `EMIT build-report` is executed only if and when some iteration's `VERIFY build` instead establishes `build.accepted`, causing that iteration's `WHEN build.accepted` to be true, running `BREAK`, and thereby exiting the loop so that execution falls through to `EMIT build-report`. Given that the task specifies `build.rejected` is established "in every iteration," `EMIT build-report` does not execute in the first two iterations (or in any iteration described by that event) — it remains permanently unreached under those events, with execution perpetually looping and waiting to run `DELEGATE build` again.

## Assumptions / points not determined by the specification

- The task states the rejection event holds "in every iteration" but the program itself has no bound on the number of iterations; the specification does not define a maximum iteration count or a termination condition other than `BREAK`/`STOP`. I have assumed (as the specification's own example for this identical program states explicitly) that this means the loop runs indefinitely under these events, and that iterations 3, 4, … would repeat the same pattern shown for iterations 1–2.
- The specification does not specify what "identifier" `build` denotes operationally (what "delegating build" or "verifying build" concretely does); per the Semantic Principles section, this is intentionally left to the runtime/actor and is out of scope for the trace.
- Whether `VERIFY build`'s two establishments of `build.rejected` (iteration 1 and iteration 2) constitute "the same value" or "two distinct events with the same value" is not explicitly addressed beyond the general "latest value" rule; I have treated each `VERIFY` as a fresh act of establishing the outcome (not a no-op), consistent with `VERIFY` "evaluating a result" each time it runs, though the observable effect is the same value both times.
