# Analysis of the go_harness program

```text
VERIFY review
WHEN review.rejected
  → DELEGATE correction
      VERIFY correction
  → TRANSITION "Rework"
EMIT review-report
```

This program is validated by indentation/scope rules 1–5 and the grammar (`when = "WHEN" ... INDENT flow DEDENT`, `flow = item, {item}`, `item = "→", statement, [INDENT, block, DEDENT]`). It matches, statement‑for‑statement, the spec's own "Example of nesting" (Syntax → The arrow →), so no ambiguity needs to be assumed away here.

## 1. Which statements belong to the WHEN flow?

The `WHEN review.<outcome>` statement has two `→` children, indented one level under it:

- `→ DELEGATE correction`, which itself has one further nested line, `VERIFY correction`, indented under it.
- `→ TRANSITION "Rework"`

Per **Indentation and scope**, rule 4: "any `→` item (lines that continue that item's flow or branch)" — `VERIFY correction` is not itself a `LOOP`, `WHEN`, `FORK`, `HITL`, or `REQUIRE`, so the special "own children" clause does not apply to it; instead it is a continuation line of the same flow, i.e. the next step after `DELEGATE correction` in the `WHEN`'s one sequential flow (Quick reference, `WHEN` row: "the `→` items under a `WHEN`... form one sequential flow").

So the WHEN flow consists of exactly three statements:
- `DELEGATE correction`
- `VERIFY correction`
- `TRANSITION "Rework"`

`EMIT review-report` is not indented under the `WHEN` (it sits back at the same depth as `VERIFY review` and `WHEN`), so by scope rule 3 ("a scope ends at the first following line indented at the same depth as, or less than, the line that opened it") it is outside the `WHEN` flow entirely.

This matches the spec's own description of this exact example: "The flow is `DELEGATE correction`, then `VERIFY correction`, then `TRANSITION "Rework"`. `EMIT review-report` is outside the `WHEN` and runs afterwards in every case."

## 2. Sequential or concurrent, and in what order?

Sequential. Execution rule 4 states that `→` items under a `WHEN` (as opposed to under a `FORK`) form one sequential flow, not concurrent branches; only `FORK`'s `→` items are concurrent branches. There is no `FORK` here, so nothing runs concurrently.

Order, given `review.rejected` is true and the `WHEN` therefore runs its flow (rule 2 of "Execution in ten rules"):

1. `DELEGATE correction`
2. `VERIFY correction`
3. `TRANSITION "Rework"`

then, since none of these is `BREAK` or `STOP`, execution continues after the `WHEN` (rule 2/8 of the ten rules), i.e.:

4. `EMIT review-report`

## 3. Is `VERIFY correction` part of the WHEN flow?

Yes. As explained in (1), it is the second step of the `WHEN`'s single sequential flow, nested under the `→ DELEGATE correction` item as a continuation of that flow (Indentation and scope, rule 4, "any `→` item" clause). It runs only when the `WHEN` condition is true, and it runs after `DELEGATE correction` completes and before `TRANSITION "Rework"`.

## 4. Is `EMIT review-report` part of the WHEN flow? Is it executed?

It is **not** part of the WHEN flow — it is written at the same indentation level as `VERIFY review` and `WHEN`, i.e. it is a top‑level statement that follows the `WHEN` construct as a whole, not one of the `WHEN`'s `→` children (Indentation and scope, rules 2–3).

It **is** executed regardless of the outcome of the `WHEN`. By execution rule 2: "True → run its flow, then continue after the `WHEN`. False → skip it. ... continue after the `WHEN`" in both cases, unless the flow that ran contained `BREAK` or `STOP` (which would end a loop or the whole execution). Here the flow (`DELEGATE correction` → `VERIFY correction` → `TRANSITION "Rework"`) contains neither `BREAK` nor `STOP`, so control simply falls through to the next top‑level statement, `EMIT review-report`, which then executes (and the program ends normally afterward, per rule 10 of the ten rules, since it's the last top-level statement).

## 5. If `VERIFY review` had established `review.accepted` instead

The `WHEN review.rejected` condition tests the latest outcome of subject `review`. If that outcome were `review.accepted`, then `review.rejected` is not the latest outcome, so the condition is false (Outcomes: "Each subject holds its most recently established outcome"; WHEN section: "The condition is true only if the latest outcome of `<subject>` is exactly `<outcome>`").

Per execution rule 2, a false condition means: "Skip the flow and continue after the `WHEN`. This is not an error." So:

- `DELEGATE correction`, `VERIFY correction`, and `TRANSITION "Rework"` would **not** execute.
- Execution would fall straight through to `EMIT review-report`, which **does** execute.

So the full set of executed statements in that scenario would be:

1. `VERIFY review` → establishes `review.accepted`
2. `WHEN review.rejected` → false: skip
3. `EMIT review-report` → done

and the program ends normally (last top-level statement done, ten rules #10). No process state is set in this run (no `TRANSITION` executes), so — since `TRANSITION` is the only statement that sets state and the spec doesn't define a default/initial state — the current process state is simply whatever it was before this program ran; the specification does not determine an initial/default state, so nothing further can be said about it here.

## Assumptions

- The specification does not name an initial process state before any `TRANSITION` runs; this is only relevant to question 5, where no `TRANSITION` executes, so I explicitly note the state stays unset/unchanged rather than assuming a default.
- No other point in the spec left this program's structure or behavior underdetermined: it is syntactically identical to the spec's own "Example of nesting," so its parse and execution follow directly from the stated rules without further assumptions.
