# Modified DSL program

## Reasoning

Requirement (1): the deploy decision may be resolved by the agent itself when it is
clearly determined, while the announce decision must stay strictly human-only.
The DSL's only mechanism for letting the agent answer a `HITL` is the `AUTO`
modifier (`AUTO HITL:<name>[...](...)`), which resolves the decision automatically
only when it is certain, and otherwise falls back to asking the human (see the
**AUTO** section and the "Who decides a HITL" table). So `AUTO` is added to
`HITL:deploy` only. `HITL:announce` is left without `AUTO`, which is exactly what
keeps it human-only per the same table ("no AUTO → the human; the agent MUST NOT
answer").

Requirement (2): "no usable answer is obtained" for the announce question matches
the spec's own category "Insufficient or unavailable" for a `HITL` response (see
the **HITL** "What happens" table: a usable response continues normally; an
insufficient or unavailable one runs `FALLBACK` if present, or else ends execution
like `STOP`). The spec's mechanism to react to that case is `→ FALLBACK`, attached
directly under the `HITL` it qualifies, ending in `STOP` or `BREAK` (rule V8). To
make the process land in state `"Quiet"` and stop in that case, a `FALLBACK` is
added under `HITL:announce` consisting of `TRANSITION "Quiet"` then `STOP`.

Nothing else in the program was changed: the `DELEGATE deployment-plan` line, the
two `WHEN deploy...` branches, and the `WHEN announce.yes` branch are unchanged in
wording, order and indentation depth (only the announce block gained a nested
`FALLBACK`).

Validity check against the given rules:
- V4: the new `→ FALLBACK` is written directly under `HITL:announce`, and it is
  the only `FALLBACK` under that `HITL`. OK.
- V5: `AUTO` appears immediately before `HITL:deploy[...]` on the same line, and
  that `HITL` is a decision (has a name and an answer list). OK.
- V8: the fallback flow's last item is `STOP`. OK.
- V7: `deploy` and `announce` are still distinct `HITL` names, each with a
  non-empty, non-repeating answer list. OK.

Assumption (the spec does not fully determine this): the spec does not say
whether `HITL:deploy` should also gain its own `FALLBACK` for the case where its
answer (human- or `AUTO`-supplied) turns out to be insufficient/unavailable. The
task only asks to change behavior for (1) who may decide, and (2) the announce
question's no-usable-answer case. So `HITL:deploy` is left with no `FALLBACK`,
exactly as in the original program: per the spec's own rule, if that ever becomes
insufficient/unavailable, execution simply ends (as with `STOP`), which is the
existing, unmodified behavior.

## Modified program

```text
DELEGATE deployment-plan
AUTO HITL:deploy[approved, rejected]("Deploy the plan?")
WHEN deploy.approved
  → DELEGATE deployment
WHEN deploy.rejected
  → TRANSITION "Replanning"
HITL:announce[yes, no]("Announce the release publicly?")
  → FALLBACK
      → TRANSITION "Quiet"
      → STOP
WHEN announce.yes
  → EMIT announcement
```
