# Execution of the FORK/STOP program

## 0. Validation (rules V1–V10)

Before executing, the program must be checked. It is well-formed:

- **V9** — the `FORK` has two branches (`→ DELEGATE lint …` and `→ DELEGATE docs …`), and the `JOIN` is the nearest preceding, still-open `FORK` in the same flow. OK.
- **V4** — every `→` item is under a `FORK`, and the lines nested under each `→ DELEGATE …` continue that item's own flow ("any `→` item … lines that continue that item's flow", Indentation and scope, rule 4). So branch 1 is `DELEGATE lint` → `VERIFY lint` → `WHEN lint.rejected` (with `→ STOP` nested under the `WHEN`), and branch 2 is `DELEGATE docs` → `EMIT docs`. OK.
- **V6** — `WHEN lint.rejected` refers to `lint`, and the program contains `VERIFY lint`, which can establish `lint.rejected`. OK.
- **V2/V3** — there is no `BREAK` in the program, so these do not apply.
- **V10** — `WHEN lint.rejected` is tested *inside* the same branch that establishes it (after its own `VERIFY lint`), not after the `FORK` and before a `JOIN`, so this is not the case V10 forbids.

No rule is broken, so the program is **valid** and may be executed.

## 1. Step-by-step trace

Given event: `VERIFY lint` establishes `rejected`; at that moment the docs branch has completed `DELEGATE docs` but has not yet run `EMIT docs`.

```trace
1. FORK -> branches started
2. DELEGATE lint -> done
3. DELEGATE docs -> done
4. VERIFY lint -> outcome lint.rejected
5. WHEN lint.rejected -> true: run flow
6. STOP -> stop
```

At step 6, `STOP` ends the entire execution immediately. Per the **STOP** section: "No further statement runs anywhere, including other `FORK` branches," and per the **FORK** table: "`STOP` in any branch → The whole execution ends, including all other branches." Consequently:

- `EMIT docs` (the remaining statement of the docs branch) is **never executed** — it had not run yet when `STOP` occurred, and `STOP` prevents any further statement, in any branch, from running.
- `JOIN` is **never reached/never completed** — it would have run only after the `FORK`'s block, but execution ends at `STOP` before getting there. This also matches the explicit rule under **STOP**: "A pending `JOIN` never completes."
- `EMIT build`, the top-level statement after `JOIN`, is likewise **never executed**, since it is only reached after `JOIN` and execution ended before that point.

Final state: no `TRANSITION` ever ran, so the process state is whatever it was before this program started (the program itself never sets one). Execution ended via `STOP`, not by reaching the last top-level statement normally.

## 2. Answers

- **Is `EMIT docs` executed?** No. The docs branch had only completed `DELEGATE docs` when the lint branch established `lint.rejected`. The very next statements in the lint branch — `WHEN lint.rejected` (true) then `STOP` — run without any intervening point at which the docs branch could reach `EMIT docs` (statements finish one at a time, per Execution rule 1), and once `STOP` executes, no statement anywhere, including `EMIT docs` in the still-running docs branch, is allowed to run.
- **Is `JOIN` completed?** No. `JOIN` is never reached at all, because `STOP` ends the whole execution first. Even if it had already been reached and were pending, the spec is explicit that "a pending `JOIN` never completes."
- **Is `EMIT build` executed?** No. It is a top-level statement that only runs after `JOIN`, which is never reached; `STOP` ends the entire execution before either `JOIN` or `EMIT build` can run.

## 3. Assumptions / where the specification underdetermines the trace

- The DSL does not define a fixed global interleaving order for statements in *different* concurrent `FORK` branches — only that "within a branch, statements run sequentially" and that a branch's own statements finish one at a time. The relative order of `DELEGATE lint` and `DELEGATE docs` in the trace above (step 2 vs. step 3) is therefore not fixed by the specification itself; I ordered them consistent with the stated event (docs branch had already finished `DELEGATE docs` by the time `VERIFY lint` established `rejected`). Any other interleaving consistent with that same event (e.g., `DELEGATE docs` listed before `DELEGATE lint`) would not change the answer, since the decisive fact — that `EMIT docs` had not yet run when `STOP` fired — is given directly by the task's events, not inferred from an assumed interleaving order.
- The specification does not name what the process's "final state" is when execution ends via `STOP` without any `TRANSITION` ever having run; I treated this as: no state is set by this program, so none is reported as the outcome of this execution.
