# go_harness DSL Solution

## DSL Code

```
LOOP:implementation-cycle
  DELEGATE implementation
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
EMIT source-code
```

## Assumptions

1. The outcome `implementation.accepted` and `implementation.rejected` are the only two possible outcomes produced by `VERIFY implementation` (as required by the DSL specification that VERIFY produces exactly one outcome: `accepted` or `rejected`)

2. After `DELEGATE correction` completes, the correction is incorporated into the implementation state, so when the loop repeats and `DELEGATE implementation` runs again, it operates on the corrected version

3. The loop name `implementation-cycle` is descriptive but arbitrary and does not affect execution (it is only a label per the specification)

4. The artifact to emit is literally named `source-code` as stated in the requirement

5. The loop continues indefinitely until a `BREAK` is executed (i.e., there is no maximum iteration count specified in the requirement)

6. The requirement "repeat from the start" means the loop naturally repeats at the end of its body, which is the built-in behavior of the LOOP construct per the specification
