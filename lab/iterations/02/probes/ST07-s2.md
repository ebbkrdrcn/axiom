```text
REQUIRE repository
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
LOOP:delivery
  FORK
    → DELEGATE implementation
    → DELEGATE documentation
  JOIN
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
AUTO HITL:release[now, later]("Release now or later?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN release.now
  → EMIT release
  → TRANSITION "Released"
WHEN release.later
  → TRANSITION "Scheduled"
```

## Assumptions

1. **Loop name is arbitrary.** The spec says a `LOOP:<name>` label is never referenced by any statement, so any identifier (`delivery`) satisfies the requirement; the requirement text does not name the repeated activity.

2. **"wait for both" is modeled as `JOIN`, not `WAIT`.** The spec defines `WAIT` as suspension until an unnamed *external* event, whereas `JOIN` is specifically "wait until every branch of the corresponding `FORK` is complete." Since the two things being waited on are exactly the two `FORK` branches (implementation, documentation), `JOIN` is the construct that matches, not `WAIT`.

3. **`VERIFY` is applied only to `implementation`, not to `documentation`.** The requirement explicitly says "then verify the implementation" and never asks for the documentation result to be evaluated, so `DELEGATE documentation` is left unverified. This is permitted: `VERIFY` is optional per `DELEGATE`'s rules ("Use `VERIFY` to evaluate it," not "must").

4. **"repeat" after the correction is left implicit.** The DSL has no explicit "repeat" statement; per rule 5 of the execution rules, a loop body automatically restarts from its first statement once its last statement is done. So "delegate a correction and repeat" is expressed simply as `WHEN implementation.rejected → DELEGATE correction`, with the repetition following automatically because this `WHEN` is the last statement of the loop body and no `BREAK`/`STOP` occurred.

5. **No data link between `correction` and the next `implementation` delegation is expressed.** The DSL is explicitly non-prescriptive about *how* delegated work relates across iterations (semantic principles: "`DELEGATE` defines responsibility, not execution mechanics"), so the correction is delegated but the mechanism by which it feeds into the next `DELEGATE implementation` is left unspecified, as the spec requires.

6. **Identifiers chosen for items/work/results:** `repository`, `implementation`, `documentation`, `correction`, `release` are taken directly from the requirement's wording, formed as valid identifiers (letters only, satisfying the grammar).

7. **HITL decision name and answers:** the human decision is modeled as `HITL:release[now, later]`, with `<name>` = `release` and answers `now` / `later`, since the requirement's question ("Release now or later?") and its two branches ("If now…", "If later…") map directly onto the decision form's name/outcome pattern (`release.now`, `release.later`).

8. **`AUTO` applies to the release decision only**, per the requirement's "the agent may itself decide … when that is clearly determined; otherwise ask a human." This matches the `AUTO HITL` semantics exactly: the agent decides only when certain, otherwise the human is asked, and (per the spec's AUTO table) `FALLBACK` never fires on the agent's own automatic answer — it only applies to the human-asked path if that response turns out to be insufficient or unavailable.

9. **"If no usable answer is obtained: move to state 'Waiting' and stop" is modeled as the `FALLBACK` of the `HITL`.** Per the spec, `FALLBACK` runs precisely when a `HITL` response is "insufficient or unavailable" (i.e., no usable answer), so this clause maps directly onto `→ FALLBACK → TRANSITION "Waiting" → STOP`, ending with `STOP` as rule V8 requires.

10. **"if it cannot be obtained, move to state 'Blocked' and stop" is modeled as the `FALLBACK` of `REQUIRE repository`,** matching the spec's own worked example for `REQUIRE` almost verbatim.

11. **Order of the two terminal `WHEN`s (`release.now` before `release.later`) is not semantically significant** — the spec states consecutive `WHEN`s are independent and evaluated top to bottom with no "else," so either order is valid; the order chosen simply follows the order in which the requirement lists the two cases.

12. **`EMIT release` is placed before `TRANSITION "Released"`** in the `now` branch, since the requirement lists "emit release and move to state 'Released'" in that order, and within a `WHEN` flow, `→` items execute sequentially in the order written.
