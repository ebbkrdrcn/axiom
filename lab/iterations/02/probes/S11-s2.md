# Execution of the given go_harness program

## Step 1 — Validate first

Per **Executing a program**, rule 1: *"Validate first. Check rules V1–V10. If any is broken, do not execute."* Rule 552 (Validity rules) adds: *"A program that breaks any of these rules is INVALID. It MUST be rejected as a whole and MUST NOT be executed in part."*

The program:

```
LOOP:review
  FORK
    → DELEGATE security-review
        VERIFY security-review
        WHEN security-review.rejected
          → BREAK
    → DELEGATE docs-review
        VERIFY docs-review
  JOIN
  TRANSITION "Reviewed"
EMIT review-summary
```

**Result: the program is INVALID.**

### Broken rule: V3

> V3 — INVALID if: `BREAK` is inside a `FORK` branch, and the `LOOP` it would leave is outside that branch.

Walking the structure:

- `LOOP:review` opens a loop body containing `FORK … JOIN … TRANSITION "Reviewed"`.
- `FORK` starts two concurrent branches (via `→`): the `security-review` branch and the `docs-review` branch.
- Inside the **first branch** (`→ DELEGATE security-review`), the nested lines `VERIFY security-review` and `WHEN security-review.rejected → BREAK` are children of that `→` item, i.e. part of that branch's own sequential flow (per **Indentation and scope**, rule 4: lines nested under a `→` item continue that item's flow/branch).
- The `BREAK` therefore sits inside a `FORK` branch.
- The only enclosing `LOOP` is `LOOP:review`, which is *outside* that branch (the branch is nested inside the loop's body via the `FORK`, not the other way around — there is no loop nested *inside* the branch itself).
- This is exactly the case the **FORK** section calls out explicitly:

  > `BREAK` in a branch → INVALID (rule V3). To leave a loop based on a branch's result, `JOIN` first, then use `WHEN … → BREAK`.

So `WHEN security-review.rejected → BREAK` as written inside the `security-review` branch is INVALID.

### Other rules checked (no violations found)

- **V1 (indentation):** The nesting is consistent — `FORK`'s two `→` branches are siblings at the same depth, each branch's continuation lines are indented under its own `→`, and `WHEN`'s `→ BREAK` is indented one level further as `WHEN`'s own child. No indentation violation.
- **V2:** `BREAK` is inside a `LOOP` (transitively), so V2 (`BREAK` outside any `LOOP`) does not apply — V3 is the specific, applicable rule for a `BREAK` inside a `FORK` branch.
- **V4:** The `→` items are correctly placed under `WHEN` and `FORK`; there is no `HITL`/`REQUIRE`/`FALLBACK` here, so no violation.
- **V5:** No `AUTO` in this program.
- **V6:** `WHEN security-review.rejected` refers to `security-review`, and the program contains `VERIFY security-review`, which can establish `accepted`/`rejected` — `rejected` is a valid outcome. No violation.
- **V7:** No duplicate `HITL` names, no name shared between `HITL` and `VERIFY`, no empty/duplicate answer lists (there are no `HITL`s at all).
- **V8:** No `FALLBACK` present.
- **V9:** `JOIN` has a corresponding `FORK`, and that `FORK` has two branches (≥ 2). No violation.
- **V10:** The `WHEN security-review.rejected` is inside the same branch that establishes `security-review` (via the preceding `VERIFY security-review` in the same sequential branch flow) — it is not a test, outside the `FORK`/before `JOIN`, of an outcome a *concurrently running other branch* might still establish. This is not the situation V10 targets, so it is not a violation in its own right — but it is moot regardless, since V3 already invalidates the program.

## Conclusion

Because the program violates **V3**, it is INVALID as a whole. Per the execution procedure, the agent MUST NOT execute it, not even in part — so no step-by-step execution trace can be produced for the program as written. The injected events (`VERIFY security-review` establishing `rejected` while the `docs-review` branch is still running) are never reached, because execution never begins.

**What would make it valid:** move the loop-exit decision after the `JOIN`, as the spec prescribes — e.g.:

```text
LOOP:review
  FORK
    → DELEGATE security-review
        VERIFY security-review
    → DELEGATE docs-review
        VERIFY docs-review
  JOIN
  TRANSITION "Reviewed"
  WHEN security-review.rejected
    → BREAK
EMIT review-summary
```

In this corrected form, `BREAK` is no longer inside a `FORK` branch — it is a top-level statement of the `LOOP:review` body, reached only after `JOIN`, which satisfies V3 and matches the guidance in the **FORK** section ("`JOIN` first, then use `WHEN … → BREAK`"). I did not execute this corrected version, since the task's program is the one given verbatim and the specification requires validating exactly the program as written; this rewrite is offered only to explain the fix, per the "state what you assumed"/explain-the-issue instruction.
