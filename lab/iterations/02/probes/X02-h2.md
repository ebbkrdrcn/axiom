# go_harness DSL Program

## DSL Code

```
AUTO HITL:notes[short, detailed]("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:release[approved, rejected]("Approve the release?")
WHEN release.approved
  → EMIT release
WHEN release.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. The answer "short" to the first HITL maps to outcome `notes.short`; "detailed" maps to `notes.detailed`. This follows the standard pattern where HITL answers become outcomes directly.

2. The answer "approved" to the second HITL maps to outcome `release.approved`; "rejected" maps to `release.rejected`.

3. For the first HITL with AUTO: The agent may automatically establish the `notes.<answer>` outcome only when one answer is clearly determined from the available information and criteria. If uncertain, the human is asked.

4. For the second HITL without AUTO: The human must provide a usable response. If the response is unavailable (human doesn't answer) or insufficient (ambiguous), execution ends with no outcome established, since no FALLBACK is provided.

5. The consecutive WHEN statements after each HITL are independent (rule 3 under Execution). Every WHEN that is true runs, top to bottom.

6. Execution ends normally after the last top-level statement completes.

7. No FALLBACK is needed for either HITL. If the approval decision has no usable response, the process ends.

8. The delegation statements (short-notes, detailed-notes) are named actors that produce results. No VERIFY is required here by the specification—the delegated work is done when the actor delivers a result.
