# Execution of the `polish` program

## Program

```
LOOP:polish
  WHEN draft.accepted
    → BREAK
  DELEGATE draft
  VERIFY draft
TRANSITION "Done"
```

Events: iteration 1 `VERIFY draft` → `rejected`; iteration 2 `VERIFY draft` → `accepted`.

## Validation

The program is well-formed:

- Indentation follows the rules (`WHEN` has a `→` child, the `→` child is `BREAK`, which is a valid `→ statement` form; `DELEGATE`/`VERIFY`/`TRANSITION` are simple statements at the correct depths).
- `BREAK` is inside `LOOP:polish` and not inside any `FORK` branch → V2/V3 satisfied.
- `WHEN draft.accepted` refers to `draft.accepted`, and the program contains `VERIFY draft` (whose only possible outcomes are `accepted`/`rejected`) → V6 satisfied.
- No `HITL`/`VERIFY` name collisions (V7), no `FALLBACK` issues (V4/V8 — there is no fallback here), no `JOIN`/`FORK` issues (V9 — none present), no V10 issue (no `FORK` involved).

The program is valid and may be executed.

## Step-by-step trace

Per rule 7 ("Before anything establishes [an outcome], every `WHEN` on it is false"), the first time execution reaches `WHEN draft.accepted` no outcome has yet been established for `draft`, so it is false.

Per rule 5 / the `LOOP` table, at the end of the body (after `VERIFY draft`, since `BREAK` was not taken) the loop repeats from its first statement (`WHEN draft.accepted`), logged as `LOOP:polish -> loop again`, following the style of the specification's own worked example (its step 10: `LOOP:delivery -> loop again`).

```trace
1. WHEN draft.accepted -> false: skip
2. DELEGATE draft -> done
3. VERIFY draft -> outcome draft.rejected
4. LOOP:polish -> loop again
5. WHEN draft.accepted -> false: skip
6. DELEGATE draft -> done
7. VERIFY draft -> outcome draft.accepted
8. LOOP:polish -> loop again
9. WHEN draft.accepted -> true: run flow
10. BREAK -> break
11. TRANSITION "Done" -> state = "Done"
12. (end of program) -> end
```

Walkthrough:

- **Iteration 1**: `draft` has no outcome yet, so `WHEN draft.accepted` is false (step 1) and is skipped (rule 7, and the `WHEN` table: "The condition is false → Skip the flow and continue after the `WHEN`."). `DELEGATE draft` runs to completion (step 2). `VERIFY draft` establishes `draft.rejected` (step 3). The body's last statement is done, so the loop restarts from its first statement (step 4, "loop again", per the `LOOP` rule: "The last statement of the body is done → The next iteration starts at the first statement of the body.").
- **Iteration 2**: `WHEN draft.accepted` is checked again; the latest outcome of `draft` is still `rejected` (rule 7's "latest value" / **Outcomes** section: "Each subject holds its most recently established outcome"), so it is still false (step 5) and skipped. `DELEGATE draft` runs again (step 6). `VERIFY draft` now establishes `draft.accepted`, replacing the previous outcome (step 7). The body finishes, so the loop restarts again (step 8).
- **Iteration 3**: `WHEN draft.accepted` is checked once more; the latest outcome of `draft` is now `accepted`, so the condition is true (step 9) and its flow runs. That flow is `→ BREAK` (step 10), which per the `BREAK` rules ends the innermost `LOOP` immediately: "The remaining statements of the current iteration are not executed" (so `DELEGATE draft` and `VERIFY draft` do **not** run a third time), and execution continues with the first statement after the loop, at the indentation of `LOOP` — i.e. `TRANSITION "Done"`.
- `TRANSITION "Done"` sets the current process state to `"Done"` (step 11).
- `TRANSITION "Done"` is the last top-level statement, so execution ends normally (step 12, rule 10).

## Answers

**How many times is `DELEGATE draft` executed?**
Twice — once in iteration 1 (before `draft.rejected` is established) and once in iteration 2 (before `draft.accepted` is established). In iteration 3, `WHEN draft.accepted` is true and its `BREAK` ends the loop before `DELEGATE draft` is reached again, so a third execution never happens.

**What is the final state?**
`"Done"` — the only `TRANSITION` in the program is `TRANSITION "Done"`, which runs exactly once, right after the loop is broken out of, and the most recently executed `TRANSITION` is the process's current state (rule under **TRANSITION**: "the most recently executed one wins").

## Assumptions / points the specification does not explicitly settle

- The specification's own worked example logs a loop's repetition as a distinct trace step, `LOOP:<name> -> loop again` (its step 10 and, implicitly, wherever the body would restart again), rather than folding that signal into the last body statement's own effect. I followed that same convention here (steps 4 and 8), since the spec does not give an alternative notation for "the body restarts." This is a formatting choice for the trace, not a semantic ambiguity — the underlying behavior (body restarts from its first statement) is fully determined by the `LOOP` section and rule 5.
- The spec does not say whether the very first `WHEN draft.accepted` check (before any `VERIFY draft` has run) should be written as `-> false: skip` or given some other special notation for "outcome not yet established." I used `false: skip`, since rule 7 states plainly that "Before anything establishes it, every `WHEN` on it is false," making an unestablished outcome behave identically to an established false one for `WHEN`'s purposes.
