# DSL Validity Check

## Snippet A — INVALID (rule V5)

```
HITL:release[approved, rejected]("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

`AUTO` appears on its own line, not immediately followed, on the same line, by a decision `HITL:<name>[…]`. Per the **Who decides a `HITL`** table and the **AUTO** section, `AUTO` "is written directly before `HITL`, on the same line," and "is not a statement on its own." Rule **V5** states the program is INVALID if `AUTO` is not immediately followed, on the same line, by a decision `HITL:<name>[…]`. Here `AUTO` stands alone with an indented `WHEN` block under it — this is in fact the exact `invalid` example given in the specification itself (the "`AUTO` / `WHEN decision.uncertain`" pattern), which the spec explicitly labels INVALID.

As a secondary defect, even setting V5 aside, the nested `WHEN decision.uncertain` would independently violate **V6**: `decision` is never a `VERIFY` result nor a `HITL` name declared anywhere in the program, so the subject/outcome pair `decision.uncertain` is not one the program can produce. (The spec also separately notes "Uncertainty is not a DSL condition, state, variable, or keyword.") But V5 alone is sufficient to reject the program as a whole.

## Snippet B — INVALID (rule V2)

```
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

`BREAK` appears inside a `WHEN` flow that is not nested inside any `LOOP`. The **BREAK** section says `BREAK` is "INVALID outside a `LOOP`," and rule **V2** states the program is INVALID if `BREAK` is not inside a `LOOP`. There is no `LOOP` anywhere in this snippet, so the `BREAK` under `WHEN implementation.rejected` has nothing to leave. (Note: this is different from V3, which concerns a `BREAK` inside a `FORK` branch whose `LOOP` lies outside the branch — no `FORK` is present here, so V2 is the applicable rule, not V3.)

## Snippet C — VALID

```
AUTO HITL:approve[yes, no]("Approve release?")
WHEN approve.yes
  → EMIT release
```

Checking each relevant rule:

- **V5**: `AUTO` is immediately followed, on the same line, by a decision `HITL:approve[yes, no](...)` — satisfied.
- **V7**: only one `HITL` statement, and it does not share its name with any other `HITL` or `VERIFY`; the answer list `[yes, no]` is non-empty and has no repeated answers — satisfied.
- **V6**: `WHEN approve.yes` tests `approve.yes`; the program contains `HITL:approve[yes, no]`, which lists `yes` as one of its answers — satisfied, this is a declared subject/outcome pair.
- **V4/V1**: the single `→ EMIT release` line is a `→` item under a `WHEN`, correctly indented as its flow — satisfied.
- No `FALLBACK` is present, but a `FALLBACK` under `HITL` is optional (the grammar shows `[fallback]`), so its absence is not a defect.

No rule in V1–V10 is broken, so the snippet is well-formed as written. (Note: per the **AUTO** section, whether the agent or the human ultimately answers `approve` depends on run-time certainty, not on well-formedness — that does not affect validity.)

## Snippet D — INVALID (rule V8)

```
HITL:region[eu, us]("Which region?")
  → FALLBACK
      → TRANSITION "Blocked"
WHEN region.eu
  → DELEGATE eu-deployment
```

The `FALLBACK` flow attached to `HITL:region` consists of a single item, `→ TRANSITION "Blocked"`, and does not end with `STOP` or `BREAK`. The **FALLBACK** section states: "Its last item MUST be `STOP` or `BREAK` (rule V8). The fallback never continues into the normal flow." Rule **V8** states the program is INVALID if the last item of a fallback flow is not `STOP` or `BREAK`. Since the fallback here ends on `TRANSITION "Blocked"` with nothing after it, the program is INVALID under V8.

(The rest of the snippet is otherwise unremarkable: `region.eu` is a declared outcome of `HITL:region[eu, us]`, satisfying V6, and there is exactly one `FALLBACK` directly under the `HITL`, satisfying V4 — but the V8 defect alone is enough to reject the whole program, since an INVALID program "MUST be rejected as a whole and MUST NOT be executed in part.")
