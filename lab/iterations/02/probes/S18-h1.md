# DSL Analysis: Execution Order Questions

## Program Structure
```
DELEGATE design
DELEGATE implementation
FORK
  → DELEGATE docs
  → DELEGATE changelog
EMIT release
```

## Analysis of Questions

### 1. Can `DELEGATE implementation` start before the design has been delivered?

**Answer: NO**

**Reasoning:**
According to Execution Rule 1: "Statements run one at a time, in the order written. Each statement finishes before the next starts. Only `FORK` runs things concurrently."

Since `DELEGATE design` appears before `DELEGATE implementation`, the `design` delegation must complete (i.e., the actor must deliver the result) before the next statement can start. `DELEGATE implementation` cannot begin execution until `DELEGATE design` has finished.

---

### 2. When is `EMIT release` executed relative to the docs and changelog branches?

**Answer: Immediately after the FORK starts, while both branches are still running concurrently**

**Reasoning:**
The specification states for FORK: "No `JOIN` → continue immediately"

The execution flow is:
1. `DELEGATE design` finishes (after a long time)
2. `DELEGATE implementation` finishes
3. `FORK` is reached, which starts two concurrent branches:
   - `DELEGATE docs` (takes 1 hour)
   - `DELEGATE changelog` (takes 5 minutes)
4. Since there is **no `JOIN`** statement following the `FORK`, execution continues immediately to the next statement (`EMIT release`)

This means `EMIT release` executes while both `docs` and `changelog` are still being processed by their actors. The branches run concurrently in the background after `EMIT release` has already executed.

---

### 3. Is it guaranteed that docs exist when `EMIT release` executes?

**Answer: NO**

**Reasoning:**
Since there is no `JOIN` statement after the `FORK`, execution does not wait for the branches to complete. From Execution Rule 1: branches run concurrently while execution continues past the `FORK`.

Given that `DELEGATE docs` takes 1 hour to complete, and `EMIT release` executes immediately after the `FORK` starts (without waiting), there is no guarantee that the docs have been delivered and exist when `EMIT release` executes. In fact, in this scenario, it is virtually certain that docs do not exist at the moment `EMIT release` runs, since 1 hour has not elapsed.

To guarantee that docs exist when `EMIT release` executes, the program would need a `JOIN` statement between the `FORK` and `EMIT release`, causing execution to wait for all branches to complete before proceeding.

---

## Summary

1. **No**: implementation cannot start before design is delivered (sequential execution rule)
2. **Immediately**: EMIT release runs right after FORK starts, while both branches are still running
3. **No**: docs are not guaranteed to exist when EMIT release executes (no JOIN to wait for branches)
