# go_harness DSL for Merge Decision Process

## DSL Code

```
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **The merge decision happens regardless of verification outcome.** The requirement states "verify it. Then a merge decision is needed" but does not specify conditional behavior based on whether verification was accepted or rejected. I assume the merge decision proceeds in all cases. (A real implementation might add `WHEN implementation.accepted` to branch conditionally, but the requirement does not specify this.)

2. **Answer list for the HITL is `[approved, declined]`.** The requirement says "a human must be asked 'Merge this change?'" but does not specify the exact answer options. I interpreted the positive answer as "approved" (merge) and the negative answer as "declined" (do not merge). Alternatives such as `[yes, no]` or `[merge, skip]` would also satisfy the requirement.

3. **No fallback flow for the HITL.** If the human does not respond or provides an insufficient answer, execution ends (as per specification rule V8: an insufficient or unavailable response with no fallback causes execution to end like `STOP`). The requirement does not specify fallback behavior.

4. **The agent's decision criteria are external to the DSL.** The requirement states the agent may decide "when it is clearly determined by the available information and criteria," but the DSL does not need to specify what those criteria are. The `AUTO` keyword enables the agent to attempt automatic resolution when certainty exists; the runtime determines whether the decision is actually certain.

5. **No looping.** The requirement does not mention iteration or loops, so the process runs once through.
