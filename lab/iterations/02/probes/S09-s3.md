# Analysis of the DSL Program

```
DELEGATE implementation
VERIFY implementation
WHEN implementation.passed
  → TRANSITION "Review"
WHEN tests.failed
  → TRANSITION "Debugging"
```

## 1. Is this program valid?

**No. The program is INVALID.** It fails rule **V6** twice, once for each `WHEN`.

> V6 — INVALID if: *a `WHEN` tests `x.y`, and the program contains neither `VERIFY x` with `y` being `accepted` or `rejected`, nor `HITL:x[…]` listing `y`.*

**a) `WHEN implementation.passed`**

- The **Outcomes** table states that `VERIFY <result>` can only ever establish `<result>.accepted` or `<result>.rejected` ("There are no other VERIFY outcomes: `passed`, `failed`, `ok` and similar are INVALID in a `WHEN` (V6)" — VERIFY section, and repeated in the Quick reference).
- The program does contain `VERIFY implementation`, but the outcome name used in the `WHEN` is `passed`, which is neither `accepted` nor `rejected`.
- There is no `HITL:implementation[...]` listing `passed` as an answer either.
- So neither branch of V6's exception applies → this `WHEN` is INVALID. (Note: this failure is independent of whatever `VERIFY implementation` actually returns — `passed` is simply not an outcome this DSL can ever produce for a `VERIFY`.)

**b) `WHEN tests.failed`**

- The subject here is `tests`. The program contains no `VERIFY tests` statement anywhere, and no `HITL:tests[...]` declaration.
- Per V6, a `WHEN` may only test a subject/outcome pair that the program actually produces (via a matching `VERIFY` giving `accepted`/`rejected`, or a `HITL` whose answer list contains that outcome). `tests.failed` is not producible by anything in this program → this `WHEN` is also INVALID under V6.

**Other rules checked (no violations found):**
- **V1** (indentation): the two `→` items are each nested one level under their respective `WHEN`, consistent with "Indentation and scope" — fine.
- **V2/V3** (`BREAK`): no `BREAK` present — n/a.
- **V4** (`→` placement): each `→` item sits directly under a `WHEN`, which is a permitted parent — fine.
- **V5** (`AUTO`): no `AUTO` present — n/a.
- **V7** (name collisions / HITL answer lists): no `HITL` statements, no duplicate names between `HITL`/`VERIFY` — fine.
- **V8** (`FALLBACK` must end in `STOP`/`BREAK`): no `FALLBACK` present — n/a.
- **V9** (`JOIN`/`FORK` pairing): no `FORK`/`JOIN` — n/a.
- **V10** (`WHEN` on an unjoined `FORK` branch's outcome): no `FORK` — n/a.

**Conclusion:** the program is INVALID solely under **V6**, on two independent grounds — the first `WHEN` uses a non-existent VERIFY outcome name (`passed` instead of `accepted`/`rejected`), and the second `WHEN` tests a subject (`tests`) that no statement in the program ever produces an outcome for.

Per the Validity rules section: *"A program that breaks any of these rules is INVALID. It MUST be rejected as a whole and MUST NOT be executed in part."* And per "Executing a program", step 1: *"Validate first. Check rules V1–V10. If any is broken, do not execute. Report each broken rule by its number."*

## 2. If `VERIFY implementation` is negative, what does an executing agent do?

Strictly per the specification, this question does not arise during execution, because the program never reaches execution at all: since it is INVALID, the agent's required procedure is to validate first, refuse to execute, and report the broken rule(s) — in this case **V6** (cited twice, as above). The agent MUST NOT execute any part of it, including `DELEGATE implementation` or `VERIFY implementation`, even though those two lines are individually well-formed.

For completeness, if the question is read hypothetically — i.e., "supposing the agent were to run just this fragment and `VERIFY implementation` came back negative" — the specification lets us reason about it, with one explicit assumption:

- **Assumption (spec does not name "negative" directly):** the spec only ever speaks of `VERIFY` establishing `accepted` or `rejected`. I assume "negative" means the outcome `implementation.rejected` is established, since that is the only negative outcome `VERIFY` can produce.
- Per the VERIFY section: *"VERIFY does not branch. Execution continues with the next statement whatever the outcome; only a WHEN makes the flow depend on it."* So after `VERIFY implementation` establishes `implementation.rejected`, execution would proceed unconditionally to `WHEN implementation.passed`.
- That `WHEN` checks whether the **latest outcome of `implementation` is exactly `passed`** (WHEN section: "The condition is true only if the latest outcome of `<subject>` is exactly `<outcome>`"). Since the latest outcome is `rejected`, not `passed`, the condition is false regardless of whether the actual result was accepted or rejected — **`passed` can never be true**, because `VERIFY` never establishes that value in the first place.
- So the effect would be: `WHEN implementation.passed -> false: skip` (using the trace vocabulary), and execution would fall through to `WHEN tests.failed`, whose subject `tests` has no outcome established anywhere in this program, so under rule 7 ("Before anything establishes it, every `WHEN` on it is false") that condition would also be false, and the (fragment of the) program would end normally having taken neither branch.

But this hypothetical trace is only illustrative — under the actual rules, none of it is licensed, because the whole program is rejected at validation and the agent must report the V6 violations instead of executing anything.
