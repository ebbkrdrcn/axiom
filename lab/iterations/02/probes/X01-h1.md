# DSL for Merge Decision Process

## DSL Program

```
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, rejected]("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **No branching on verification result.** The requirement does not specify behavior based on whether `implementation.accepted` or `implementation.rejected`. The program proceeds to the merge decision regardless of the implementation verification outcome. If the requirement intended different flows for accepted vs. rejected implementation, this would require `WHEN` statements after `VERIFY implementation`.

2. **AUTO allows agent resolution.** The requirement states "the agent may make the merge decision itself when it is clearly determined by the available information and criteria." I interpret this as the condition for `AUTO` in the DSL: the agent answers only when the decision is certain and within its authority; otherwise the human is asked.

3. **Answer list: "approved" and "rejected".** I chose these names following the DSL's standard pattern for approval decisions (see the `HITL:release[approved, rejected]` example in the specification). Alternative interpretations might use "yes"/"no" or "merge"/"no-merge", but the requirement's phrasing ("If the decision is to merge") maps naturally to "approved" = merge.

4. **FALLBACK handles insufficient or unavailable responses.** The DSL defines three classifications of human responses (usable, insufficient, unavailable). The requirement states "If the human gives no usable answer," which corresponds to insufficient or unavailable responses. The `FALLBACK` clause under the `HITL` correctly handles this case by transitioning to "Blocked" and stopping, as required.

5. **No explicit STOP at program end.** The program ends normally after the last `WHEN` statement. The DSL permits this: "STOP is not required at the end of a program. Execution ends normally after the last top-level statement" (rule 10 in Execution in ten rules).

6. **No loop structure.** The requirement describes a single pass through the process (delegate, verify, decide, transition). No `LOOP` is used, as the requirement contains no indication of iteration.

7. **Process state is set by TRANSITION alone.** The DSL defines `TRANSITION` as setting the process state; it performs no work. The three transitions ("Blocked", "Merged", "Rework") set the state for different outcomes, and no other work depends on reading the state within this program.
