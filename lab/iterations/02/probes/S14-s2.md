# Execution of the given go_harness program

## Program

```
FORK
  → DELEGATE unit-tests
      VERIFY unit-tests
  → DELEGATE integration-tests
      VERIFY integration-tests
JOIN
WHEN unit-tests.accepted
  → TRANSITION "Ready"
WHEN integration-tests.rejected
  → TRANSITION "Debugging"
```

Events:
- `VERIFY unit-tests` establishes `accepted`.
- `VERIFY integration-tests` establishes `rejected`, and this branch finishes later (after the unit-tests branch).

## Validity check

- `FORK` has two `→` branches → satisfies V9 (at least two branches).
- `JOIN` has a corresponding preceding `FORK` at the same indentation, not yet joined → satisfies V9.
- `WHEN unit-tests.accepted`: the program contains `VERIFY unit-tests`, and `accepted` is one of the two outcomes `VERIFY` can establish → satisfies V6.
- `WHEN integration-tests.rejected`: the program contains `VERIFY integration-tests`, and `rejected` is a valid `VERIFY` outcome → satisfies V6.
- Both `WHEN`s test subjects (`unit-tests`, `integration-tests`) that are established inside branches of the `FORK` in the same flow, but both `WHEN`s appear **after** the `JOIN` that closes that `FORK` → satisfies V10 (no `WHEN` on a FORK-branch subject appears before the corresponding `JOIN`).
- No `BREAK`, no `AUTO`, no `FALLBACK`, no repeated `HITL`/`VERIFY` names, indentation follows the arrow/child rules.

No rule V1–V10 is broken. **The program is valid** and may be executed.

## Assumptions (not fully determined by the spec)

The spec (rule 1 and the `FORK` section) guarantees that statements *within* a branch run sequentially, and that both branches start when `FORK` is reached, but it does not prescribe the exact interleaving of steps *between* concurrent branches, only their relative completion order. The events given state that the `unit-tests` branch's `VERIFY` establishes its outcome, and the `integration-tests` branch "finishes later." I therefore assume:
- Both `DELEGATE` statements start when `FORK` is reached.
- The `unit-tests` branch (its `DELEGATE` and `VERIFY`) completes in full before the `integration-tests` branch completes, consistent with "finishes later."
- The trace below lists the `unit-tests` branch's two steps first, then the `integration-tests` branch's two steps, since only completion order — not fine-grained interleaving — is specified or observable in the resulting outcomes/state. This ordering choice does not affect the final outcomes or final state, since `WHEN` testing of these subjects only happens after `JOIN`, by which point both branches are complete (rule V10, "Visibility" under **Outcomes**).

## Execution trace

```trace
1. FORK -> branches started
2. DELEGATE unit-tests -> done
3. VERIFY unit-tests -> outcome unit-tests.accepted
4. DELEGATE integration-tests -> done
5. VERIFY integration-tests -> outcome integration-tests.rejected
6. JOIN -> joined
7. WHEN unit-tests.accepted -> true: run flow
8. TRANSITION "Ready" -> state = "Ready"
9. WHEN integration-tests.rejected -> true: run flow
10. TRANSITION "Debugging" -> state = "Debugging"
11. (end of program) -> end
```

## Notes on the trace

- Step 1: `FORK` starts both branches concurrently (rule: "All branches start. Within a branch, statements run sequentially.").
- Steps 2–3: the `unit-tests` branch runs to completion, and `VERIFY unit-tests` establishes exactly one outcome, `accepted` (per the **VERIFY** section: "It establishes exactly one outcome: `<result>.accepted` or `<result>.rejected`").
- Steps 4–5: the `integration-tests` branch runs to completion; `VERIFY integration-tests` establishes `rejected`. Per the **FORK** section, "A `VERIFY` in a branch establishes `rejected`. The branch continues normally. A negative outcome does not abort a branch" — so this does not stop or otherwise affect the fork.
- Step 6: `JOIN` waits until *every* branch of the corresponding `FORK` is complete (both branches, regardless of their `VERIFY` outcome, count as complete once their last statement is done). After this point, both outcomes (`unit-tests.accepted` and `integration-tests.rejected`) are visible ("Outcomes are visible everywhere once established, including after a `JOIN`").
- Step 7: `WHEN unit-tests.accepted` is checked once, reached after `JOIN`; the latest outcome of `unit-tests` is `accepted`, so the condition is true and its flow runs.
- Step 8: `TRANSITION "Ready"` sets the current process state to `Ready`.
- Step 9: `WHEN integration-tests.rejected` is checked independently of the previous `WHEN` ("Consecutive `WHEN`s are independent... Every one that is true runs, top to bottom"). The latest outcome of `integration-tests` is `rejected`, so this condition is also true and its flow runs.
- Step 10: `TRANSITION "Debugging"` replaces the current state. Per **TRANSITION**: "The process has exactly one current state. Each `TRANSITION` replaces it; the most recently executed one wins." This is now the latest `TRANSITION` executed.
- Step 11: this is the last top-level statement; execution ends normally (rule 10 of **Execution in ten rules**).

## Final state

**`Debugging`**

This is the final state because both `WHEN` blocks are true and run (they are independent, not mutually exclusive — there is no "else" and no "first match"), and the second `TRANSITION "Debugging"` is executed after the first `TRANSITION "Ready"`, so it is the most recently executed `TRANSITION` and therefore wins.
