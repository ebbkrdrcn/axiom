```text
AUTO HITL:notes[short, detailed]("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:release[approved, rejected]("Approve the release?")
WHEN release.approved
  → EMIT release
WHEN release.rejected
  → TRANSITION "Rework"
```

## Assumptions

The specification does not fully determine every detail of this program. Where it left something open, I made the following assumptions:

1. **No `REQUIRE`.** The requirement does not mention any precondition (information, context, or resource) that must be available before starting. So no `REQUIRE` statement was written.

2. **No `FALLBACK` on either `HITL`.** The requirement does not describe what should happen if a response to either question is insufficient or unavailable. I left both `HITL` statements without a `→ FALLBACK`. Per the spec's own rule, this means that if a response is ever insufficient/unavailable, execution simply ends (as with `STOP`) at that point — I assumed this default behavior is acceptable since the requirement gives no other instruction.

3. **`AUTO` only on the notes question.** The requirement explicitly allows the agent to answer "Short or detailed release notes?" itself when the answer is clearly determined, so `AUTO` is used there. It explicitly says the approval question "must always be given by a human, never by the agent," so `AUTO` is deliberately omitted from `HITL:release[...]`, matching the spec's rule that without `AUTO` the agent MUST NOT answer.

4. **No trailing `STOP`.** The spec states `STOP` is not required at the end of a program; execution ends normally after the last top-level statement (rule 10). So the program ends after the second pair of `WHEN`s with no explicit `STOP`.

5. **Identifier choices.** The requirement doesn't give exact identifier names, so I chose:
   - `notes` as the `HITL` decision name for the short/detailed question, with answers `short` and `detailed` (taken directly from the requirement's wording).
   - `short-notes` and `detailed-notes` as the `DELEGATE` work items (matching "delegate short-notes" / "delegate detailed-notes" in the requirement).
   - `release` as the `HITL` decision name for the approval question, with answers `approved` and `rejected` (taken directly from "If approved... if rejected...").
   - `release` as the `EMIT` artifact name (matching "emit release" in the requirement).
   Note: the `HITL` name `release` and the `EMIT` artifact `release` are the same identifier text but occur in different statement contexts (a `HITL` name vs. an `EMIT` argument). The spec's naming-collision rule (V7) only restricts reuse of a name between `HITL` and `VERIFY`, so this is not a violation, but I flag it since the two uses share a name coincidentally.

6. **No loop.** The requirement is phrased as a single, one-time sequence ("First ask... Then ask..."), not a repeating process, so no `LOOP` was used.

7. **No `TRANSITION` before "Rework".** The requirement only names one explicit process state, `"Rework"`, reached on rejection. No other `TRANSITION` (e.g., before or between the two questions) is implied, so none was added.

8. **No `VERIFY`.** Nothing in the requirement is described as an actor's delivered result needing acceptance/rejection evaluation distinct from the human decisions already modeled via `HITL`; the two `DELEGATE` statements (`short-notes`, `detailed-notes`) are not followed by `VERIFY` because the requirement does not ask for their results to be evaluated — it moves directly to the approval question.
