# Answers

Program under discussion:

```text
LOOP:release
  LOOP:fix
    DELEGATE fix
    VERIFY fix
    WHEN fix.accepted
      → BREAK
  TRANSITION "Fixed"
  VERIFY release-candidate
  WHEN release-candidate.accepted
    → BREAK
EMIT release
```

## 1. When `VERIFY fix` establishes `accepted`, which loop does the `BREAK` exit, and which statement executes next?

The `BREAK` at issue is the one inside `WHEN fix.accepted`, which is nested inside `LOOP:fix`. Per the `BREAK` rule ("Leaves the innermost enclosing `LOOP` immediately") and the Quick reference ("leave the innermost `LOOP` now"), `BREAK` always exits the **innermost** enclosing loop — here, `LOOP:fix` — not `LOOP:release`.

Per the `LOOP` rule: "`BREAK` inside the body … The loop ends now. Execution continues with the first statement after the loop, at the indentation of `LOOP`."

So:
- The `BREAK` exits `LOOP:fix` only.
- Execution continues with the first statement after `LOOP:fix`, at `LOOP:fix`'s indentation level, which is `TRANSITION "Fixed"`.

`LOOP:release` is not exited or otherwise affected by this `BREAK`; it is still "in progress" (its body has simply advanced to the statement after the inner loop).

## 2. Could the author write `BREAK release` inside `LOOP:fix` to leave both loops at once?

No. The specification does not permit a named or parameterized `BREAK`:

- The `LOOP` section states explicitly: "`<name>` is only a label. No statement refers to it; `BREAK` takes no name."
- The `BREAK` section's form block is simply `BREAK`, with no argument.
- The syntax table lists `BREAK` among the keywords that appear "`<keyword>` alone."
- The grammar confirms this: `simple = … | ( "JOIN" | "BREAK" | "WAIT" | "STOP" ) , NL ;` — `BREAK` takes no identifier or argument in the grammar.

`BREAK release` is therefore not a well-formed statement in this DSL at all (it does not match any production in the grammar), and even if tolerated informally, the spec's semantics for `BREAK` unconditionally target "the innermost enclosing `LOOP`" — there is no mechanism for a `BREAK` to name an outer loop and skip the inner one.

To leave both loops from inside `LOOP:fix`, the author cannot do it with a single statement. The specification's only tools for making the outer loop's exit depend on an inner result are: `BREAK` the inner loop, then (after `JOIN` if the value comes from a `FORK` branch — not applicable here) test the relevant outcome with a `WHEN … → BREAK` in the outer loop's body so that the outer loop also breaks on its next check. For example, the outer loop would need its own `WHEN fix.accepted → BREAK` (or equivalent) placed in its body to also exit `LOOP:release` — two separate `BREAK` statements, one per loop, since a single `BREAK` cannot reach past its innermost loop.

## 3. If `VERIFY release-candidate` establishes `rejected`, what executes next?

`VERIFY release-candidate` establishes exactly one outcome, `release-candidate.rejected` (per the `VERIFY` rule: "It establishes exactly one outcome: `<result>.accepted` or `<result>.rejected`").

The next statement is `WHEN release-candidate.accepted`. Since the latest outcome of `release-candidate` is `rejected`, not `accepted`, this condition is false. Per the `WHEN` rule: "The condition is false → Skip the flow and continue after the `WHEN`. This is not an error."

`WHEN release-candidate.accepted` is the last statement in `LOOP:release`'s body. Skipping its flow means execution reaches the end of the loop body. Per Execution rule 5 / the `LOOP` table: "At the end of a loop body, the body starts again from its first statement."

So, in order, what happens next is:
1. `WHEN release-candidate.accepted` -> false: skip (no flow runs).
2. End of `LOOP:release`'s body is reached, so the loop repeats: execution goes back to `LOOP:release`'s first statement, `LOOP:fix` (which begins again with `DELEGATE fix`).

`EMIT release` does **not** run in this case, since it is only reached after `LOOP:release` ends (via a `BREAK` from a true `WHEN release-candidate.accepted`, or a `STOP`), and neither occurs here.

## Note on scope of this answer

This answer relies solely on the provided specification. Where the specification does not state something explicitly, that is noted above (e.g., the spec gives no combined "break N levels" construct, and no example directly shows a nested-`LOOP` `BREAK` scenario like this one); the conclusions above are derived directly from the stated general rules for `BREAK`, `WHEN`, and `LOOP`, which are unambiguous on innermost-loop scoping, "no name" for `BREAK`, and loop-body repetition.
