# Execution of the given program

## Program

```text
TRANSITION "Testing"
WHEN tests.accepted
  → TRANSITION "Review"
DELEGATE tests
VERIFY tests
EMIT test-report
```

Event: `VERIFY tests` establishes `accepted`.

## Validity check

- **V6** (`WHEN` must refer to a producible subject/outcome): `WHEN tests.accepted` refers to `tests`, and the program contains `VERIFY tests`, which can establish `tests.accepted` — satisfied.
- **V1–V5, V7–V10**: no indentation problems, no `BREAK`/`FORK`/`JOIN`/`HITL`/`REQUIRE` constructs at all, so these rules are vacuously satisfied.

The program is **valid** and may be executed.

## Step-by-step trace

```trace
1. TRANSITION "Testing" -> state = "Testing"
2. WHEN tests.accepted -> false: skip
3. DELEGATE tests -> done
4. VERIFY tests -> outcome tests.accepted
5. EMIT test-report -> done
6. (end of program) -> end
```

**Final state: `"Testing"`**

## Why step 2 is `false: skip`

Per the **Execution in ten rules** (rule 7) and the `WHEN` table:

- "Before anything establishes it, every `WHEN` on it is false."
- A `WHEN` is "checked once, when reached."

At the moment execution reaches `WHEN tests.accepted` (step 2), no statement has yet established any outcome for the subject `tests` — `VERIFY tests` does not run until step 4, three lines later in program order. So at step 2 the latest outcome of `tests` is "not yet established," which makes the condition false. The flow under the `WHEN` (`→ TRANSITION "Review"`) is skipped, and execution continues with `DELEGATE tests`.

## Is `TRANSITION "Review"` ever executed?

**No.**

Two independent rules make this certain, not just a consequence of statement order:

1. **A `WHEN` is checked exactly once, at the moment execution reaches it**, and is never re-checked later. From the `WHEN` table: "The outcome is established later → Nothing happens. A `WHEN` is not a standing trigger and is never re-checked." Even though `VERIFY tests` later (step 4) establishes `tests.accepted` — the very outcome the `WHEN` at step 2 was testing — that later establishment has no effect on a `WHEN` that has already been checked and found false.
2. Because the `WHEN` construct sits *before* `DELEGATE tests` / `VERIFY tests` in the program text, and statements "run one at a time, in the order written" (Execution in ten rules, rule 1), there is no path through this program on which the `WHEN` is checked after `tests.accepted` has been established. The condition is therefore always false, for any event, not only for this one.

Since the `WHEN`'s flow never runs, `TRANSITION "Review"` never executes, and the process state set by the first `TRANSITION "Testing"` is never replaced. It remains the current (and final) state when execution ends normally after the last top-level statement, `EMIT test-report` (rule 10 of Execution in ten rules).

## Assumptions

The specification fully determines this trace; no assumption was needed to resolve an ambiguity. One point worth making explicit for clarity:

- `tests` is used consistently as a single subject name throughout (as the argument to `DELEGATE`, to `VERIFY`, and as the subject in `WHEN tests.accepted`). The DSL does not require the `DELEGATE`/`VERIFY` argument name and the `WHEN` subject name to be textually identical beyond ordinary identifier matching, and here they are identical, so no name-resolution ambiguity arises.
