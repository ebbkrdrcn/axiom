```text
DELEGATE tests
VERIFY tests
WHEN tests.accepted
  → TRANSITION "Review"
WHEN tests.rejected
  → TRANSITION "Debugging"
  → DELEGATE diagnosis
```

## Assumptions

- **"the test suite" is a single delegable unit of work**, named with the identifier `tests`. The spec says `DELEGATE <work>` takes an identifier and does not prescribe what the work item represents, so "the test suite" is treated as one `DELEGATE` target.
- **"verify it" refers to that same delegated result**, so `VERIFY tests` uses the same identifier as the `DELEGATE` statement. This mirrors the spec's own `DELEGATE implementation` / `VERIFY implementation` example and is not a V7 violation, since V7 only forbids a name shared between a `HITL` and a `VERIFY` (or between two `HITL`s), not between a `DELEGATE` and a `VERIFY`.
- **"pass" / "fail" map onto the DSL's only `VERIFY` outcomes**, `accepted` and `rejected` respectively, since the spec states `VERIFY` establishes exactly `<result>.accepted` or `<result>.rejected` and no other outcomes (e.g. `passed`, `failed`) are valid in a `WHEN` (rule V6).
- **No `HITL`, `REQUIRE`, `LOOP`, or `FORK` is needed.** The requirement describes a single linear pass with a two-way branch based on a verification outcome, so the minimal correct construct is `DELEGATE` → `VERIFY` → two `WHEN`s, with no looping, human interaction, concurrency, or external requirement implied by the text.
- **The two `WHEN` branches are independent, not mutually exclusive via an "else."** The DSL has no "else"; since `VERIFY` establishes exactly one of `accepted`/`rejected` (never both), writing both `WHEN tests.accepted` and `WHEN tests.rejected` correctly captures the "if tests pass … if tests fail …" branching without needing an else construct.
- **"delegate a diagnosis" is a new, distinct piece of work**, given the identifier `diagnosis`, delegated only inside the `tests.rejected` flow, after `TRANSITION "Debugging"`, matching the stated order ("move to state ... and delegate a diagnosis").
- **State name capitalization** ("Review", "Debugging") is taken verbatim from the requirement text as the `TRANSITION` string argument, since the spec does not constrain state-name casing or format.
- **The program ends normally after the last top-level statement** (rule 10 / the `EMIT`-less, `STOP`-less complete-example pattern); no explicit `STOP` is required or added, since the requirement describes no further steps after either branch.
