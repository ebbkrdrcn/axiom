# Analysis of go_harness DSL Program

## Question 1: When `VERIFY fix` establishes `accepted`, which loop does the `BREAK` exit, and which statement executes next?

**Answer:** The `BREAK` exits **`LOOP:fix`** (the innermost loop), and the next statement that executes is **`TRANSITION "Fixed"`**.

**Reasoning:**

According to the specification's BREAK section:
- "Leaves the innermost enclosing `LOOP` immediately."
- When `VERIFY fix` establishes `fix.accepted`, the `WHEN fix.accepted` condition becomes true
- The flow under this `WHEN` contains `→ BREAK`
- Since `BREAK` always leaves the **innermost** enclosing loop, it exits `LOOP:fix`, not `LOOP:release`
- The next statement at the same indentation level as `LOOP:fix` is `TRANSITION "Fixed"`, which then executes

---

## Question 2: Could the author write `BREAK release` inside `LOOP:fix` to leave both loops at once?

**Answer:** No, the author cannot write `BREAK release`. This would be **syntactically invalid**.

**Reasoning:**

The specification explicitly states in the BREAK section:
- "`<name>` is only a label. No statement refers to it; `BREAK` takes no name."
- The syntax for BREAK is defined as simply `BREAK` with no arguments

The specification also confirms this in the Quick reference and Grammar sections, where BREAK is listed as a keyword taking no arguments. Writing `BREAK release` would violate the DSL syntax because BREAK accepts no parameters or labels.

Additionally, Rule V2 (under Validity rules) states: "`BREAK` is not inside a `LOOP`" makes it invalid, but there is no rule allowing named breaks to escape multiple loops. The DSL design intentionally does not support this feature.

## Question 3: If `VERIFY release-candidate` establishes `rejected`, what executes next?

**Answer:** **`EMIT release`** executes next.

**Reasoning:**

Following the execution flow:
1. After `LOOP:fix` completes (when the `BREAK` is executed), execution continues to `TRANSITION "Fixed"`
2. Then `VERIFY release-candidate` executes and establishes the outcome `release-candidate.rejected`
3. Next, the `WHEN release-candidate.accepted` statement is evaluated
4. Since the latest outcome is `release-candidate.rejected` (not `accepted`), the condition is **false**
5. According to the WHEN specification: "False → skip" and "Execution does not wait"
6. The `WHEN` flow is skipped, and execution continues to the next statement after the `WHEN`
7. The next statement is `EMIT release`, which executes

The key principle from the specification is: "A `WHEN` is checked once, when execution reaches it. True → run its flow, then continue after the `WHEN`. False → skip it."
