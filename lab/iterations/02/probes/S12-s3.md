# Execution of the DSL program (Runs A–D)

## The program

```text
DELEGATE release-notes
HITL:notes[approved, rejected]("Approve the release notes?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN notes.approved
  → TRANSITION "Published"
  → EMIT release-notes
WHEN notes.rejected
  → TRANSITION "Rework"
```

## Validation (rule 1: "Validate first")

- V1 (indentation): the `→ FALLBACK` block is directly under the `HITL`, and its own `→` items are nested one level deeper, consistent with **Indentation and scope**. OK.
- V2/V3 (BREAK): no `BREAK` in the program. N/A.
- V4 (`→` placement): the only `→` items are under `WHEN` (twice) and under `FALLBACK` (once, itself directly under the `HITL`); the `HITL` has exactly one `FALLBACK`. OK.
- V5 (AUTO): no `AUTO` used. N/A.
- V6 (declared outcomes): `WHEN notes.approved` and `WHEN notes.rejected` both refer to answers declared in `HITL:notes[approved, rejected]`. OK.
- V7 (name collisions): `notes` is used only once, as a `HITL` name; no `VERIFY notes` exists; the answer list `[approved, rejected]` has no repeats. OK.
- V8 (fallback ending): the fallback flow is `TRANSITION "Blocked"` → `STOP`, ending in `STOP`. OK.
- V9 (JOIN/FORK): no `FORK`/`JOIN`. N/A.
- V10 (WHEN vs. unjoined FORK branch): no `FORK` exists. N/A.

**The program is valid.** It may be executed.

## Assumption made (spec does not fully determine this)

The spec does not specify how long `DELEGATE <work>` takes before the actor delivers a result, nor does it list a "waiting" effect for `DELEGATE` (only `HITL`/`REQUIRE`/`WAIT` are shown suspending in the reference examples). As in the specification's own "Complete example" (where `DELEGATE implementation -> done` is shown with no preceding wait line), I assume the delegated result is delivered without an externally-visible wait step, so `DELEGATE release-notes` is traced simply as `done`. This assumption is identical for all four runs and does not affect the outcome-related behavior asked about in the task.

## Run A — the human responds "Approved."

**Classification of the response:** "Approved." clearly and unambiguously selects the listed answer `approved` (rule: "Clearly selects exactly one listed answer (in any wording)" is *usable*).

```trace
1. DELEGATE release-notes -> done
2. HITL:notes[approved, rejected]("Approve the release notes?") -> waiting
3. HITL:notes[approved, rejected]("Approve the release notes?") -> outcome notes.approved
4. WHEN notes.approved -> true: run flow
5. TRANSITION "Published" -> state = "Published"
6. EMIT release-notes -> done
7. WHEN notes.rejected -> false: skip
8. (end of program) -> end
```

**Final state: `Published`**

(The fallback flow is never entered: rule states "A usable response never runs the fallback flow.")

---

## Run B — the human never responds and the runtime stops waiting

**Classification of the response:** no response is ever given, and the runtime determines it has stopped waiting → this matches *unavailable* ("No response, and the runtime has stopped waiting"). No outcome is established. Since a `FALLBACK` is present, the fallback flow runs instead of the normal flow.

```trace
1. DELEGATE release-notes -> done
2. HITL:notes[approved, rejected]("Approve the release notes?") -> waiting
3. HITL:notes[approved, rejected]("Approve the release notes?") -> fallback
4. TRANSITION "Blocked" -> state = "Blocked"
5. STOP -> stop
```

**Final state: `Blocked`**

Neither `WHEN notes.approved` nor `WHEN notes.rejected` ever runs or is even reached: `notes.<outcome>` is never established (so both would have been false in any case), and `STOP` ends the whole execution immediately, before either `WHEN` line is reached. The fallback "runs instead of the normal flow" and "never continues into the normal flow," per its rule.

## Run C — the human responds "I haven't had time to look yet."

**Classification of the response:** this is essentially the specification's own example of an *insufficient* response — the table lists "I haven't looked yet" verbatim as an example of a response that is "ambiguous between answers, or is off-topic," hence *insufficient*. It selects neither `approved` nor `rejected`. No outcome is established, and the `FALLBACK` runs (same rule as for an unavailable response: "Insufficient or unavailable, and there is a `FALLBACK` → Run the fallback flow. No outcome is established.").

```trace
1. DELEGATE release-notes -> done
2. HITL:notes[approved, rejected]("Approve the release notes?") -> waiting
3. HITL:notes[approved, rejected]("Approve the release notes?") -> fallback
4. TRANSITION "Blocked" -> state = "Blocked"
5. STOP -> stop
```

**Final state: `Blocked`**

(Identical trace shape to Run B, because both are handled by the same rule row: "Insufficient or unavailable, and there is a `FALLBACK`.")

## Run D — the human responds "Not like this, rewrite the intro."

**Classification of the response:** the response contains extra content (an instruction to "rewrite the intro") that is not itself one of the declared answers, but the classification test is only whether the response "clearly selects exactly one listed answer (in any wording)." "Not like this" is an unambiguous rejection of the release notes in answer to a binary approve/reject question — it does not leave any doubt between `approved` and `rejected`, and it is not off-topic (unlike "I haven't looked yet" in Run C, it directly addresses the question asked). The additional remark ("rewrite the intro") is extra feedback riding along with a clear decision, not a source of ambiguity about which of the two listed answers was chosen. Under the stated test, this is therefore a **usable** response selecting `rejected`.

(This is the one point in the task where the spec leaves some room for judgment, since it does not give a rule for responses that carry extra unstructured content alongside a clear choice; I resolved it by applying the literal usable/insufficient/unavailable test, which asks only whether exactly one listed answer is clearly selected, not whether the response is otherwise limited to that answer.)

```trace
1. DELEGATE release-notes -> done
2. HITL:notes[approved, rejected]("Approve the release notes?") -> waiting
3. HITL:notes[approved, rejected]("Approve the release notes?") -> outcome notes.rejected
4. WHEN notes.approved -> false: skip
5. WHEN notes.rejected -> true: run flow
6. TRANSITION "Rework" -> state = "Rework"
7. (end of program) -> end
```

**Final state: `Rework`**

(The fallback flow is not entered, since a usable response never runs the fallback flow — even though the response carries feedback text beyond a bare "rejected.")
