```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **Identifiers.** The requirement names no concrete identifiers, so I chose `implementation` as the `DELEGATE`/`VERIFY` subject and `merge` as the `HITL` name. These are arbitrary but consistent identifiers (letters/digits/`-`/`_`, starting with a letter, per **Names and strings**).

2. **Answer list for the merge decision.** The requirement gives two outcomes ("decision to merge" / "not"), so the `HITL` answer list is `[approved, declined]`, and `WHEN merge.approved` / `WHEN merge.declined` are the two branches. Any other pair of words would have worked equally well; the spec does not fix the wording.

3. **`VERIFY implementation` is not wired into the merge decision.** The requirement says only "Delegate the implementation and verify it. Then a merge decision is needed" — it does not state that the merge decision depends on `implementation.accepted`/`implementation.rejected`, nor does it give criteria linking the two. Per the DSL's semantic principles, `VERIFY` only establishes an outcome; nothing requires every established outcome to be consumed by a `WHEN`. I therefore left `VERIFY implementation` standing on its own rather than inventing a dependency the requirement never states, since the DSL forbids inventing outcomes, results, or their relationships (rule 9 / "Never invent").

4. **"May make the merge decision itself when clearly determined... otherwise a human must be asked" maps exactly to `AUTO HITL`.** This is the DSL's built-in semantics for `AUTO` (Situation: "certain and within authority" → agent decides; "anything else" → human is asked), so no extra `WHEN`/uncertainty logic was added — and none would be valid, since `AUTO` "never contains a flow" and uncertainty is not a DSL condition/keyword.

5. **"If the human gives no usable answer, transition to Blocked and stop" is modeled as the `FALLBACK`.** Per the spec, `FALLBACK` runs for both "insufficient" and "unavailable" responses (no distinction is drawn in the requirement either), so a single `FALLBACK` flow (`TRANSITION "Blocked"` then `STOP`) covers "no usable answer," satisfying rule V8 (fallback must end in `STOP` or `BREAK`).

6. **No `REQUIRE`, `LOOP`, `FORK`, or retry logic.** The requirement describes a single straight-line process (delegate → verify → decide → transition) with no mention of prerequisites, repetition, or concurrency, so none of those constructs were introduced.

7. **No explicit `STOP`/`EMIT` at the end of the "Merged"/"Rework" paths.** The requirement does not ask for any further action after transitioning state in either case, and rule: "`STOP` is not required at the end of a program. Execution ends normally after the last top-level statement" — so both `WHEN` branches simply end, and the program ends normally per rule 10.

8. **Order of the two `WHEN` blocks** (approved before declined) follows the order the requirement lists them ("If the decision is to merge... If not...") but is not semantically significant, since consecutive `WHEN`s are independent and unordered in effect (rule 3 in **Execution in ten rules**).
