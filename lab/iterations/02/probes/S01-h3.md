## Solution

### DSL Program

```
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

### Assumptions

1. **Answer names for the merge decision.** The requirement specifies two outcomes ("merge" vs "not to merge") but does not name them. I named them `approved` and `declined` to match the semantic intent and follow common convention, but the spec does not mandate these names.

2. **Independence of verification and merge decision.** The requirement says to "delegate... and verify it," then make a merge decision without specifying how the verification result affects that decision. I assumed the merge decision is made independently—the merge question is asked regardless of whether the implementation was accepted or rejected. The specification provides no other basis to branch on the verification outcome before the merge question.

3. **No fallback for the HITL.** The requirement does not describe what to do if the human provides an unusable response to the merge question, or if no response is available. Per rule 8 of the Execution section, in the absence of a `FALLBACK`, execution ends (as with `STOP`).

4. **Outcomes are separate subjects.** I treated `implementation` (from `VERIFY`) and `merge` (from `HITL`) as distinct subjects with their own outcomes, with no coupling between them. This satisfies validity rule V7.
