```text
AUTO HITL:notes[short, detailed]("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:release[approved, rejected]("Approve the release?")
WHEN release.approved
  → EMIT release
WHEN release.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **First interaction is a decision `HITL`, not a request.** The requirement says the outcome (short vs. detailed) determines which branch runs, so it must establish an outcome — that requires the decision form `HITL:<name>[<a>, <b>](...)`, not the plain request form `HITL("...")`, which establishes no outcome. I named the subject `notes` and used the answers `short` and `detailed`, taken directly from the requirement's wording ("If short… if detailed…").

2. **`AUTO` is used only on the notes decision.** "The agent may answer this question itself when the answer is clearly determined" is exactly the semantics of `AUTO` (rule: resolve automatically only when certain, otherwise ask the human). No confidence threshold or determination algorithm is specified, and the spec says `AUTO` doesn't prescribe one, so none is assumed.

3. **`AUTO` is deliberately omitted on the release-approval `HITL`.** The requirement states approval "must always be given by a human, never by the agent," which matches a plain `HITL:<name>[...]` (no `AUTO`) exactly, since only `AUTO` permits agent resolution.

4. **No `FALLBACK` is included for either `HITL`.** The requirement does not describe what should happen if the human's response is insufficient or unavailable for either question, and `FALLBACK` is optional in the spec. Per the spec's default rule, if a response is insufficient/unavailable and there is no `FALLBACK`, execution simply ends (as with `STOP`). I assumed this default behavior is acceptable rather than inventing fallback steps (e.g., what state to transition to, or whether to stop/break) that the requirement never mentions.

5. **No `REQUIRE`, `LOOP`, `FORK`/`JOIN`, `WAIT`, or `BREAK` are used.** The requirement describes a single, linear, one-shot sequence (ask → branch → delegate → ask → branch → emit/transition) with no repetition, no concurrency, no stated preconditions to load, and no explicit external-event suspension beyond the `HITL`s themselves (which already suspend execution per the spec). Adding any of these constructs would introduce behavior not present in the requirement.

6. **No `TRANSITION` on the approved path.** The requirement only specifies `TRANSITION "Rework"` for the rejected case; for the approved case it only says to `EMIT release`. I did not invent a state name (e.g., "Released"/"Done") for the approved branch since none was given.

7. **Identifiers chosen for work items.** The requirement names the delegated work as "short-notes" and "detailed-notes" and the emitted artifact as "release," which I used verbatim as identifiers (letters/digits/`-`/`_`, starting with a letter, as required by the grammar).

8. **Two `WHEN`s per decision, none exhaustive by construction.** Per the spec, each `WHEN` is independent and there is no "else." Since the answer lists (`[short, detailed]` and `[approved, rejected]`) are each exhaustive (only two possible answers, one of which is always established once the `HITL` is answered usably), exactly one `WHEN` in each pair will be true at run time; this is a consequence of the spec's rules, not an extra assumption requiring an explicit exhaustiveness construct.
