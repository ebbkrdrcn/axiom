# go_harness DSL for Parallel Reviews

## DSL Program

```text
FORK
  → DELEGATE security-review
      VERIFY security-review
  → DELEGATE performance-review
      VERIFY performance-review
JOIN
TRANSITION "Release"
```

## Assumptions Made

1. **Review identifier names**: The requirement uses natural language ("security review" and "performance review"). I converted these to valid identifiers using hyphens as separators: `security-review` and `performance-review`, per the specification's identifier syntax (letters, digits, `-`, `_`).

2. **No branching on verification outcomes**: The requirement says to "continue only after both flows have finished, then transition". It does not specify conditional flows based on whether reviews are accepted or rejected. Therefore, I assumed the process transitions to "Release" regardless of verification outcomes. If review failures required different handling, the program would need `WHEN` statements after the `JOIN` to branch on `security-review.rejected` or `performance-review.rejected`.

3. **No prerequisites**: The requirement does not explicitly state that anything must be available before starting. Therefore, I did not include a `REQUIRE` statement. If the security and performance review capabilities, documentation, or code needed to be verified as available before proceeding, a `REQUIRE` statement would be needed before the `FORK`.

4. **State persistence**: The specification states that `TRANSITION` sets the current process state and "the latest `TRANSITION` wins". I assumed the process has no prior state, or that transitioning to "Release" is the intended final state regardless of any previous state.

5. **No fallback handling**: The requirement does not mention handling unavailable reviews or failed delegations. I assumed all delegations succeed and all verifications can proceed to completion, so no `FALLBACK` is needed.
