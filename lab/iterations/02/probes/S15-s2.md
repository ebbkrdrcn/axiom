## 2. Note on interleaving (what the spec does and doesn't fix)

Rule 1 says only `FORK` runs things concurrently, and within a branch statements run strictly sequentially — but the specification does not fix the relative interleaving *between* the two branches' statements. That is left to the runtime/events. The task's **Events** sentence fixes it for us here: at the moment `VERIFY lint` establishes `rejected`, the docs branch has already run `DELEGATE docs` but has *not yet* run `EMIT docs`. So the docs branch's `DELEGATE docs` happens no later than `VERIFY lint`, and `EMIT docs` has not yet been reached when the lint branch resolves. This fixes the ordering used in the trace below; it is an assumption drawn directly from the stated events, not from an interleaving rule the DSL itself specifies.

## 3. Trace

```trace
1. FORK -> branches started
2. DELEGATE lint -> done
3. DELEGATE docs -> done
4. VERIFY lint -> outcome lint.rejected
5. WHEN lint.rejected -> true: run flow
6. STOP -> stop
```

Explanation of the last three steps:

- `VERIFY lint` establishes `lint.rejected` (step 4). Per the **VERIFY** rules, this does not branch by itself; it just sets the outcome.
- `WHEN lint.rejected` (step 5) is checked once, immediately reached in the lint branch's sequential flow. The condition is true, so its flow runs.
- The flow is `→ STOP` (step 6). Per **STOP**: "Ends the entire execution immediately... No further statement runs anywhere, including other `FORK` branches." The **FORK** table states the same thing explicitly: "`STOP` in any branch → The whole execution ends, including all other branches." So execution halts globally right here.

Because `STOP` fires before the docs branch reaches `EMIT docs`, and before execution reaches the `JOIN` statement at all, none of `EMIT docs`, `JOIN`, or `EMIT build` ever run. The **STOP** section is explicit that "a pending `JOIN` never completes" in this situation — though here it is even more direct than that: execution ends while both branches are still logically "in flight" (the docs branch had not finished), so the top-level flow never even arrives at the `JOIN` line.

## 4. Answers

- **Is `EMIT docs` executed?** No. The docs branch had completed only `DELEGATE docs` when `VERIFY lint` resolved to `rejected`. The `STOP` triggered by `WHEN lint.rejected` ends the entire execution immediately, including the still-running docs branch, before it reaches `EMIT docs`.
- **Is `JOIN` completed?** No. `JOIN` is never even reached: `STOP` ends the whole execution (both branches and the top-level flow) before the branches would have converged there. This matches the spec's rule for `STOP`: "A pending `JOIN` never completes."
- **Is `EMIT build` executed?** No. It is the statement after `JOIN`, and execution never gets past the `STOP` inside the `FORK`. Per **STOP**: "No further statement runs anywhere."

## Assumption stated explicitly

The DSL specification does not itself dictate the fine-grained interleaving of statements across concurrent `FORK` branches (only that each branch is internally sequential and that `STOP` anywhere ends everything). The exact ordering used above (`DELEGATE lint`, `DELEGATE docs`, then `VERIFY lint` before `EMIT docs`) was taken directly from the task's stated **Events**, not inferred from an interleaving rule in the spec.
