```text
REQUIRE repository
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
LOOP:delivery
  FORK
    → DELEGATE implementation
    → DELEGATE documentation
  JOIN
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
AUTO HITL:release[now, later]("Release now or later?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN release.now
  → EMIT release
  → TRANSITION "Released"
WHEN release.later
  → TRANSITION "Scheduled"
```

## Assumptions

1. **Identifiers chosen for unnamed items.** The requirement never gives literal DSL names, so I picked identifiers that mirror the requirement's own words: `repository` (the `REQUIRE` item), `implementation` and `documentation` (the two `DELEGATE`/`VERIFY` subjects), `correction` (the corrective `DELEGATE`), `release` (both the `AUTO HITL` decision name and the `EMIT` artifact), and the loop label `delivery`. The spec does not determine these names, only their identifier syntax (letters/digits/`-`/`_`, starting with a letter), so any other legal choice would be equally valid.
2. **`release` reused for both `HITL:release` and `EMIT release`.** Rule V7 only forbids two `HITL`s sharing a name, or a name shared between a `HITL` and a `VERIFY`. It says nothing about a `HITL` name coinciding with an `EMIT` artifact name, and `EMIT` establishes no outcome, so I treated this reuse as permitted. If a stricter separation was intended, the `EMIT` artifact should be renamed (e.g. `EMIT release-artifact`).
3. **`FORK` branch order.** The requirement lists "delegate the implementation and, at the same time, delegate the documentation," so I put `→ DELEGATE implementation` before `→ DELEGATE documentation`. Since `FORK` branches are concurrent, this order has no execution-order meaning; it only reflects the order named in the prose.
4. **No explicit "repeat" statement.** Per Execution rule 5 ("At the end of a loop body, the body starts again from its first statement"), the loop automatically repeats after `DELEGATE correction` finishes; I did not add any extra construct for "and repeat," since none exists in the DSL and none is needed.
5. **Order of effects inside the `now` branch.** The requirement says "emit release and move to state 'Released'"; I preserved that literal order (`EMIT release` then `TRANSITION "Released"`). The spec does not require any particular order among `→` items beyond "top to bottom as written," so this is a direct transcription choice, not a semantic necessity.
6. **Order of effects inside each `FALLBACK`.** Both fallbacks ("move to state X and stop") are written as `TRANSITION` followed by `STOP`, matching the literal wording and rule V8 (a fallback flow must end in `STOP` or `BREAK`).
7. **`AUTO HITL` answer identifiers `now`/`later`.** The requirement's question "Release now or later?" and its two branches ("If now," "If later") were mapped to the answer list `[now, later]` and tested via `WHEN release.now` / `WHEN release.later`. The spec does not dictate these tokens' spelling, only that they be valid identifiers matching the `HITL`'s declared answer list (V6).
8. **Scope of the human decision boundary.** "The agent may itself decide ... when that is clearly determined; otherwise ask a human" was mapped directly to `AUTO HITL`, per the spec's definition that `AUTO` resolves automatically only under certainty and otherwise falls through to asking the human — this is a direct application of the spec, not an assumption beyond identifier naming.
9. **No `FALLBACK` on `VERIFY` or on the `FORK`/`JOIN`.** The requirement gives no fallback behavior for rejected verification (it explicitly says "otherwise delegate a correction and repeat," which is handled by `WHEN implementation.rejected`) nor for the fork/join step, so none was added; the DSL does not attach `FALLBACK` to `VERIFY`, `FORK`, or `JOIN` in any case (only `HITL`/`REQUIRE` may have one, per V4).
