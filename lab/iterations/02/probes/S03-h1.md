# DSL Solution

## Program

```text
FORK
  → DELEGATE security-review
      VERIFY security-review
  → DELEGATE performance-review
      VERIFY performance-review
JOIN
TRANSITION "Release"
```

## Assumptions

1. **Work delegation names**: I assumed the delegated work should be named `security-review` and `performance-review` as identifiers. The specification does not prescribe specific work names, only that `DELEGATE <work>` requires an identifier. These names reflect the requirement directly.

2. **No outcome-based branching**: The requirement does not specify what to do if either review is rejected. Per the specification, "A branch whose `VERIFY` established `rejected` still counts as complete," and execution continues after `JOIN` regardless of verification outcomes. I therefore did not add `WHEN` statements to conditionally handle accept/reject outcomes.

3. **No error handling or fallback**: The requirement does not specify fallback behavior if a review cannot be completed. The specification permits execution to continue or end without a `FALLBACK`. I assumed neither error handling nor fallback is required.

4. **Initial process state**: The requirement does not specify an initial state before the transition. I assumed the process begins with no explicit state, and the first `TRANSITION` sets it to "Release".

5. **Execution-time availability**: The specification defines `DELEGATE` as "done when the actor has delivered its result" and `VERIFY` as "evaluate a result." I assumed both work items and their results are available at execution time; the DSL does not require a `REQUIRE` statement to declare their availability upfront.

6. **No concurrency of verification outside branches**: The specification requires `FORK` for concurrent branches. I assumed both `DELEGATE` and `VERIFY` must occur inside the fork branches to satisfy "each review... verified within its own parallel flow," not sequentially after the `JOIN`.
