# Analysis of the DSL Snippet

## Snippet under analysis

```text
VERIFY review
WHEN review.rejected
  → DELEGATE correction
      VERIFY correction
  → TRANSITION "Rework"
EMIT review-report
```

Assumption given by the task: `VERIFY review` establishes the outcome `rejected`.

---

## 1. Which statements belong to the WHEN flow?

The WHEN flow consists of everything indented under `WHEN review.rejected`:

- `DELEGATE correction`
- `VERIFY correction` (nested/indented under `DELEGATE correction`, so it belongs to the same flow, as a statement following it)
- `TRANSITION "Rework"`

`EMIT review-report` is **not** indented under `WHEN`, so per the Scope rule ("Indented statements belong to the preceding scoped construct"), it is not part of the WHEN flow — it is a sibling statement that follows the WHEN construct in the outer flow.

**Assumption / spec gap:** The specification's `WHEN` section always illustrates exactly one `→` per `WHEN` (each additional outcome gets its *own* `WHEN <condition>` block, e.g. the `tests.passed` / `tests.failed` example). The Syntax section, however, shows a `WHEN` with two `→` arrows and says only that "the statements following `→` belong to the conditional flow" (singular "flow"), unlike `FORK`, whose spec explicitly states "each `→` starts an independent flow." Because the DSL never says a `WHEN` block's multiple `→` arrows constitute separate branches (that behavior is reserved for `FORK`), and because `WHEN` is described as producing one flow that executes "when the condition is satisfied," I have treated both `→` arrows in this `WHEN` as part of a single, ordinary sequential flow — i.e., two consecutive statements of the same conditional flow, not concurrent or alternative branches. This is an assumption filling a gap the spec does not explicitly resolve for a `WHEN` with multiple `→` arrows.

---

## 2. Are the statements in the WHEN flow executed sequentially or concurrently, and in what order?

Sequentially, in declaration order:

1. `DELEGATE correction`
2. `VERIFY correction`
3. `TRANSITION "Rework"`

Justification: the general Flow rule states "Statements execute in declaration order unless an explicit control construct changes the flow." Concurrency is only introduced explicitly by `FORK` ("Starts multiple concurrent flows... each `→` starts an independent flow"). `WHEN` carries no such statement about concurrency; it is described only as "a conditional flow," not a fork of concurrent flows. In the absence of an explicit `FORK`, the default sequential-execution rule applies, so the two `→` items under this `WHEN` run one after another, and `VERIFY correction`, being indented beneath `DELEGATE correction`, runs immediately after it and before `TRANSITION "Rework"`.

---

## 3. Is `VERIFY correction` part of the WHEN flow?

Yes. `VERIFY correction` is indented beneath `DELEGATE correction`, which is itself one of the `→` statements of the `WHEN review.rejected` flow. Per the Scope rule, an indented statement belongs to the preceding scoped construct — here, that is the `DELEGATE correction` step within the WHEN flow. So `VERIFY correction` is a nested statement of the WHEN flow, executed as part of it (see the `DELEGATE`/`VERIFY` pairing example in the spec, where a `VERIFY` follows a `DELEGATE` to evaluate its result).

---

## 4. Is `EMIT review-report` part of the WHEN flow? Is it executed?

**Part of the WHEN flow:** No. It is written at the same indentation level as `WHEN review.rejected` itself (not indented under it), so by the Scope rule it does not belong to the WHEN's conditional flow. It is a statement in the outer/enclosing flow that textually follows the entire `WHEN` construct.

**Is it executed:** Yes. Since `VERIFY review` established `rejected`, the `WHEN review.rejected` condition is satisfied and its flow runs; but nothing in that flow is a construct that halts subsequent execution. Specifically:
- `TRANSITION "Rework"` "represents a state change, not execution of work" — it does not stop the flow or exit any scope.
- There is no `STOP` (which "terminates execution") and no `BREAK` (which "exits the current LOOP") in this snippet, and indeed there is no enclosing `LOOP` at all.

Per the Flow rule, statements execute in declaration order unless an explicit control construct changes that flow. No such construct here prevents continuation, so after the WHEN flow finishes (`DELEGATE correction` → `VERIFY correction` → `TRANSITION "Rework"`), execution proceeds to the next statement in the outer flow, `EMIT review-report`, which therefore executes.

---

## 5. If `VERIFY review` had established `accepted` instead, which statements would execute?

Sequence of execution:

1. `VERIFY review` — always executes (it precedes the `WHEN`).
2. `WHEN review.rejected` — the condition `review.rejected` is *not* satisfied (the outcome is `accepted`, not `rejected`). Per the spec, "the statements following `→` form the flow executed when the condition is satisfied." Since the condition is false, none of the WHEN flow's statements execute:
   - `DELEGATE correction` — does not execute
   - `VERIFY correction` — does not execute
   - `TRANSITION "Rework"` — does not execute
3. `EMIT review-report` — executes. As established in Q4, this statement lies outside the WHEN scope, in the outer sequential flow, and nothing in the snippet (no `STOP`, no `BREAK`, no other WHEN branch shown) prevents the outer flow from reaching it.

**Note on completeness:** The specification says that "multiple `WHEN` constructs may describe different outcomes of the same process state" (as in its own `tests.passed` / `tests.failed` example), implying a well-formed process would typically pair `WHEN review.rejected` with a corresponding `WHEN review.accepted` to describe what happens on acceptance. This snippet, however, defines no `WHEN review.accepted` block. The specification does not state what, if anything, should represent "acceptance handling" in that case, so under the `accepted` outcome the only defined behavior is: `VERIFY review` executes, the WHEN's rejection-flow is skipped, and `EMIT review-report` executes. Nothing in the given snippet defines any additional accepted-specific behavior — this is the DSL's literal, spec-driven answer, not an inferred one.
