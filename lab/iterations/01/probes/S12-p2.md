# Execution Trace: `release-notes` HITL/FALLBACK Program

## Program under analysis

```text
DELEGATE release-notes
HITL("Approve the release notes?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
TRANSITION "Published"
EMIT release-notes
```

## Assumptions made where the specification does not fully determine behavior

The specification does not settle every detail needed to trace this program mechanically. The following reading choices are made explicitly, each grounded as closely as possible in the given text:

1. **Multiple `→` lines under `FALLBACK` are a single sequential flow, not independent branches.**
   The spec's only worked example of `FALLBACK` shows one `→ <flow>`. The construct that defines multiple `→` lines as *independent concurrent flows* is `FORK` ("Each `→` starts an independent flow"). `FALLBACK` is not `FORK`. The closer analogy is `WHEN`, whose spec text says "The statements following `→` form the flow executed when the condition is satisfied" (singular flow, plural statements). Accordingly, the two `→` lines under `FALLBACK` — `TRANSITION "Blocked"` and `STOP` — are read as one flow executed in order: first the transition, then the stop.

2. **"The human never responds" is treated as the "response unavailable" case that `FALLBACK` exists for.**
   The spec defines `FALLBACK` as the flow used "when an expected response is unavailable or insufficient," but it does not define *any* timeout or waiting-duration mechanism for `HITL` (nothing in `HITL`, `WAIT`, or the semantic principles specifies how long the runtime waits or what triggers a decision that a response is not coming). Since the task states as a categorical fact that no response is ever given, this is read as the direct, literal instance of "response is unavailable," and is treated as sufficient to invoke `FALLBACK`. The specification does not state the mechanism or timing by which the runtime would reach this determination — that is left unspecified, and it is only assumed that "never responds" *counts as* "unavailable" once and if reached.

3. **`DELEGATE release-notes` is assumed to have produced release notes available for approval by the time `HITL` runs.**
   The spec says `DELEGATE` "does not mean that the work is correct, complete, or accepted" and defines responsibility, not execution mechanics or timing. Declaration-order execution (per the "Flow" syntax rule) is assumed to mean the delegated work is at least available in some form when `HITL` asks for its approval, but the spec does not specify whether `DELEGATE` blocks until the actor's work is finished. This detail is treated as outside the DSL's scope and irrelevant to the control-flow trace requested.

4. **Reaching the end of the statement list with no explicit `STOP` is assumed to mean the execution simply ends.**
   The spec defines what `STOP` does ("Terminates execution... No subsequent statement is executed after `STOP`") but does not explicitly state what happens when statements simply run out. This is inferred from the "Flow" section ("Statements execute in declaration order unless an explicit control construct changes the flow") as the natural, unstated default, not as a keyword-defined behavior.

5. **`AUTO` is not present in this program**, so no automatic resolution of the `HITL` decision is ever permitted in any run; per spec, `HITL` "must not be silently replaced by an agent decision unless the surrounding definition explicitly permits automatic resolution through `AUTO`." This is why in Run C the agent may not itself decide whether the ambiguous human reply counts as approval or rejection — only `FALLBACK` handling applies.

## Run A — human responds "Approved."

| Step | Statement / Event | Semantics applied |
|---|---|---|
| 1 | `DELEGATE release-notes` | Work of producing release notes is assigned to an actor. This does not itself imply the work is correct, complete, or accepted (spec: "`DELEGATE` does not mean that the work is correct, complete, or accepted"). |
| 2 | `HITL("Approve the release notes?")` | A human decision boundary is opened. Execution suspends pending a human response (spec: "Requests a decision, input, or action from a human," "establishes a human decision boundary"). |
| 3 | Human responds: "Approved." | This is an unambiguous, usable response to the approval request. Per the spec, `FALLBACK` applies only "when the expected response cannot be used to continue the normal flow" — here it can be used, so `FALLBACK` is **not** entered. |
| 4 | `TRANSITION "Published"` | Normal flow resumes at the statement following the `HITL`/`FALLBACK` block. The process state changes to `Published`. Per spec, this represents a state change only — it does not itself mean any work (e.g. publishing mechanics) was performed. |
| 5 | `EMIT release-notes` | The `release-notes` artifact is produced as an externally meaningful output. The DSL does not prescribe how it is created, stored, or transmitted. |
| 6 | (end of statements) | No further statements remain; execution ends normally (see Assumption 4). |

**Outcome of Run A:** State = `Published`. Artifact `release-notes` emitted. `FALLBACK` never invoked.

| Step | Statement / Event | Semantics applied |

| 2 | `HITL("Approve the release notes?")` | Decision boundary opened; execution suspends pending a human response. |

**Outcome of Run C:** State = `Blocked`. No artifact emitted. Execution terminated via `STOP` inside the fallback flow — identical externally-observable outcome to Run B, reached because the response, though present, was insufficient rather than absent.

## Summary

| Run | Human response | `FALLBACK` triggered? | Final state | `release-notes` emitted? |
|---|---|---|---|---|
| A | "Approved." | No — response usable | `Published` | Yes |
| B | (none, ever) | Yes — response unavailable | `Blocked` | No |
| C | "I haven't had time to look yet." | Yes — response insufficient | `Blocked` | No |

In all three runs, `DELEGATE release-notes` executes identically and does not by itself determine acceptance. The divergence occurs entirely at the `HITL`/`FALLBACK` boundary: only a response that can actually be used to continue the normal flow (Run A) allows execution to reach `TRANSITION "Published"` and `EMIT release-notes`; any response that is absent (Run B) or exists but does not resolve the requested decision (Run C) routes into the `FALLBACK` flow, which unconditionally transitions to `Blocked` and then `STOP`s, per this program's specific fallback definition — the DSL itself does not mandate that a fallback must stop; it only permits it ("A fallback may explicitly terminate, defer, request another action, or otherwise handle the unresolved situation").
