```text
REQUIRE deployment-target

HITL("Which region should we deploy to?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP

DELEGATE deployment
EMIT deployment-log
```

## Assumptions

1. **"needs the deployment-target before anything else"** is expressed by placing `REQUIRE deployment-target` as the very first statement of the process. Per the spec, `REQUIRE` only declares what must be available and that it "must be satisfied before execution continues" — it does not prescribe *how* the requirement is obtained, so nothing further is asserted about loading/fetching it.

2. **"ask a human"** maps directly to `HITL("Which region should we deploy to?")`, using the exact wording from the requirement as the message string, per the `HITL("<message>")` syntax.

3. **"If no usable answer is obtained from the human"** is treated as the case the spec calls "an expected response is unavailable or insufficient," i.e. exactly the case `FALLBACK` is defined for. The spec gives no DSL condition/keyword (e.g. no `response.unusable`) for testing "usability" of a human answer the way `VERIFY` produces `.accepted`/`.rejected` outcomes for `WHEN`; since `HITL`/`FALLBACK` is itself defined as the construct for handling an unusable/unavailable response, I used `FALLBACK` directly rather than inventing a `WHEN` condition.

4. **The "otherwise" (success) path** is not given any explicit keyword or condition in the spec either (unlike `VERIFY`, `HITL` has no documented `.accepted` style outcome). I therefore modeled it as the normal declaration-order continuation of the flow: the statements after the `HITL`/`FALLBACK` block (`DELEGATE deployment`, `EMIT deployment-log`) run only when the fallback flow was not taken, following the general Flow rule that "statements execute in declaration order unless an explicit control construct changes the flow." This is an inference, since the spec never explicitly states what happens to statements following a `HITL` + `FALLBACK` block when the fallback is not triggered.

5. **Nesting inside `FALLBACK`**: the spec's own example for `FALLBACK` shows only a single placeholder line (`→ <flow>`) and does not define the syntax for multiple statements inside a fallback flow. I reused the convention documented for `FORK` branches ("a forked flow consists of the statement associated with that branch and its nested statements") — so `TRANSITION "Blocked"` is the statement associated with the `FALLBACK` arrow, and `STOP` is a further-indented statement nested within that same fallback flow.

6. **`STOP` vs `BREAK`**: I used `STOP` because the requirement says to "terminate the whole execution," which matches `STOP`'s definition ("Terminates execution... No subsequent statement is executed after STOP"). `BREAK` was not used because it only exits a `LOOP` scope, and this process contains no `LOOP`.

7. **No `LOOP` or `FORK`** is used, since the requirement describes a single linear sequence with one conditional branch (the human-response outcome), with no indication of repetition or concurrent work.

8. **No `VERIFY`** is used, since the requirement only asks to delegate the deployment and emit a log — it does not ask for the delegated result to be evaluated against acceptance criteria.

9. **Identifiers**: `deployment-target`, `deployment`, and `deployment-log` are treated as plain identifiers (per the `<identifier>` syntax rule) naming, respectively, a requirement, a unit of delegated work, and an artifact. The spec does not define or constrain their internal structure, so none is assumed beyond what's needed to reference them.

10. **No explicit prior/initial state** is declared before the `TRANSITION "Blocked"` — the requirement does not ask for an initial-state transition, and the spec does not require one before the first `TRANSITION`.
