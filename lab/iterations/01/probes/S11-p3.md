# Trace of the `DSL` Program

## Program under trace

```text
LOOP:review
  FORK
    → DELEGATE security-review
        VERIFY security-review
        WHEN security-review.rejected
          → BREAK
    → DELEGATE docs-review
        VERIFY docs-review
  JOIN
  TRANSITION "Reviewed"
EMIT review-summary
```

Injected events:
- Iteration 1: both `FORK` branches start.
- `VERIFY security-review` establishes `rejected` while the docs-review branch is still running (its `VERIFY` has not yet occurred).

## Step-by-step execution

1. **`LOOP:review` begins iteration 1.** Per spec, `LOOP` "does not imply any particular number of iterations" and "continues until `BREAK`, `STOP`, or another explicit control flow terminates it." Iteration 1 begins normally.

2. **`FORK` starts two independent concurrent flows.** Per the `FORK` spec, "each `→` starts an independent flow" and "the branches may execute concurrently." Per the injected events, both branches start together:
   - Branch A: `DELEGATE security-review` → `VERIFY security-review` → `WHEN security-review.rejected → BREAK`
   - Branch B: `DELEGATE docs-review` → `VERIFY docs-review`

3. **Branch A — `DELEGATE security-review` executes.** Work is assigned to an actor. Per spec, this "does not mean that the work is correct, complete, or accepted" — it only assigns responsibility.

4. **Branch A — `VERIFY security-review` executes and establishes `rejected`.** Per spec, `VERIFY` "evaluates a result against the applicable acceptance criteria" and "may establish outcomes that can be used by `WHEN`." Per the injected event, this establishes `security-review.rejected` at a point when branch B's `VERIFY docs-review` has *not yet* run.

5. **Branch A — `WHEN security-review.rejected` is satisfied.** `WHEN` "does not itself perform work, change state, delegate work, or produce an artifact" — it is a pure gate. Since the condition holds, its associated flow (`→ BREAK`) is taken.

6. **Branch A — `BREAK` executes.** Per spec: "Exits the current `LOOP`," "`BREAK` does not terminate the entire execution," and "`BREAK` may only exit a loop scope." The current loop is `LOOP:review`, so this loop is exited.

7. **Consequence for the loop body: `JOIN` and `TRANSITION "Reviewed"` are never reached.** Both statements are lexically inside `LOOP:review`, positioned *after* the `FORK` block, in the same loop scope that `BREAK` exits. Because `BREAK` exits that scope, execution never reaches these statements in this iteration, and — since the loop is exited outright rather than merely re-iterated — it never reaches them in any later iteration either (there is no later iteration: the loop is done).

8. **Consequence for branch B (docs-review): its remaining execution has no defined continuation.** See the "Unresolved by the specification" section below — the spec does not say whether an independent forked flow is cancelled when the loop scope that contains it is exited by `BREAK`, or whether it keeps running as an "independent flow" regardless. Either way, nothing downstream can use its result, because the only construct that would ever consume it — `JOIN` — is itself bypassed by `BREAK` (step 7). So `docs-review`'s `VERIFY` outcome (accepted or rejected) has no effect on the remainder of the trace under either reading.

9. **Execution resumes after the exited loop.** Per spec, "`BREAK` does not terminate the entire execution," so execution must continue with whatever follows the loop in the enclosing flow. In declaration order, that is `EMIT review-summary`, which sits at the same indentation level as `LOOP:review` (i.e., outside/after it, not inside it).

10. **`EMIT review-summary` executes.** Per spec, `EMIT` "produces an output or artifact defined by the surrounding process" and "represents an externally meaningful output." This executes unconditionally at this point — it is not inside the loop, so it is unaffected by the `BREAK`, and nothing in the trace prevents reaching it.

11. **Execution ends.** There is no statement after `EMIT review-summary`, and nothing (`STOP`, another `LOOP`, etc.) reopens further flow, so execution terminates normally here.

## Explicit answers to the four items asked

- **`docs-review` branch:** It is still running (its `VERIFY docs-review` has not fired) at the moment `BREAK` exits `LOOP:review`. The specification does not define what happens to an independent forked flow when the loop scope containing it is exited by `BREAK`. Under the assumption used here (see below), it is treated as abandoned along with the loop scope it was created in. Regardless of that assumption, its outcome cannot affect anything else in the program, because the only construct that could consume it (`JOIN`) never executes.

- **`JOIN`:** Never executes. It is inside `LOOP:review`, after the point where `BREAK` exits that loop, so control never reaches it in this iteration, and there is no further iteration.

- **`TRANSITION "Reviewed"`:** Never executes, for the same reason as `JOIN` — it is inside the loop scope that `BREAK` exits, after the (skipped) `JOIN`. The process therefore never transitions to the `"Reviewed"` state along this path.

- **`EMIT review-summary`:** Executes. It lies outside `LOOP:review` (declared at the same indentation as the loop, i.e., after it), and per spec `BREAK` "does not terminate the entire execution," so execution continues with the next statement in the enclosing flow once the loop is exited. This is the last statement, so execution ends immediately afterward.

## Where the specification does not determine the outcome, and what was assumed

1. **Whether `BREAK` inside one `FORK` branch immediately exits the enclosing `LOOP`, even while a sibling branch (from the same `FORK`, not yet reconciled by `JOIN`) is still running.**
   The spec defines `BREAK` ("exits the current LOOP"), `FORK` (independent concurrent branches), and `JOIN` (waits for all branches) separately, but never states how `BREAK` interacts with an in-flight `FORK`/`JOIN` pair. There is no rule saying `BREAK`'s effect is deferred until `JOIN`, nor one saying it is immediate.
   *Assumption made:* `BREAK` takes effect immediately when executed, regardless of the state of sibling concurrent branches, consistent with the unqualified wording "exits the current LOOP" and "may only exit a loop scope." This is the reading used throughout the trace above.

2. **What happens to an independent forked flow (`docs-review`) that is still running when the loop containing its `FORK` is exited by `BREAK`.**
   The spec says a forked branch is "an independent flow" but gives no cancellation, interruption, or orphaning semantics for such a flow when its enclosing scope terminates early. It also gives no mechanism by which `BREAK` (or any construct) reaches into a sibling branch to stop it.
   *Assumption made:* Because `docs-review`'s `DELEGATE`/`VERIFY` steps are declared only inside the `FORK` that itself is declared only inside `LOOP:review`, once that loop scope is exited the branch is treated as abandoned (it has no scope left to complete "into"). This assumption does not change the rest of the trace: even if one instead assumed the branch keeps running to completion as a genuinely independent flow, its eventual `VERIFY docs-review` outcome would still have no defined consumer, since `JOIN` — the only construct that could wait for or use it — never executes.

3. **Whether "exiting the loop" implies control resumes at the statement following the loop.**
   This is not stated verbatim, but is the only reading consistent with the explicit statement "`BREAK` does not terminate the entire execution" together with the general flow rule that statements execute in declaration order unless changed by a control construct. This was treated as a direct (not merely assumed) consequence of the spec rather than a free assumption, and it is what allows `EMIT review-summary` to execute.
