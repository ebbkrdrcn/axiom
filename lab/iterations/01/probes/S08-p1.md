# Analysis: `REQUIRE staging-credentials` cannot be satisfied

```text
REQUIRE staging-credentials
DELEGATE deployment
EMIT deployment-log
```

All answers below are derived only from the `go_harness` specification given. Where the specification leaves something undetermined, that is stated explicitly, along with the assumption made to give a complete answer.

## 1. What happens at `REQUIRE staging-credentials`?

Per the specification:

> `REQUIRE` declares information, context, state, or another condition required for subsequent execution.
>
> The requirement must be satisfied before execution continues.
>
> If a required condition cannot be satisfied, execution must not proceed as if the requirement were satisfied.

Since `staging-credentials` cannot be obtained, the requirement is **not satisfied**. The specification is explicit that in this case execution "must not proceed as if the requirement were satisfied." So at this statement, the flow reaches an unmet requirement: the precondition for everything that follows in this flow fails to hold, and the DSL forbids treating it as if it had succeeded.

The specification does **not** define:
- any error/exception object, "requirement.failed" state, or outcome variable produced by `REQUIRE` (contrast with `VERIFY`, which explicitly "may establish outcomes that can be used by `WHEN`");
- any implicit escalation to `HITL`, `FALLBACK`, or `STOP` when a requirement fails.

So the DSL text only tells us the *constraint* (must not proceed as if satisfied), not the *mechanism* by which the flow is diverted or the failure is signaled. This is a genuine gap in the specification, which is consistent with its stated design principle: `REQUIRE` "defines what must be available, not how it is loaded," and by extension not how failure to obtain it is handled procedurally.

## 2. Is `DELEGATE deployment` executed?

**No.** The specification states statements "execute in declaration order unless an explicit control construct changes the flow," and that execution continues past a `REQUIRE` only once "the requirement must be satisfied before execution continues." Since `staging-credentials` was not satisfied, the specification directly bars proceeding "as if the requirement were satisfied" — and executing the next statement in sequence, `DELEGATE deployment`, would be exactly that: treating the unmet requirement as met and moving on regardless.

`DELEGATE` itself does not rescue this: "`DELEGATE` does not mean that the work is correct, complete, or accepted," but this is orthogonal — the issue here is not the quality of delegated work, it is that the precondition for reaching the `DELEGATE` statement at all was never met. So `DELEGATE deployment` must not run.

## 3. Is `EMIT deployment-log` executed?

**No.** Two independent reasons from the spec:

- Sequential flow: `EMIT deployment-log` is the statement after `DELEGATE deployment`. Since `DELEGATE deployment` did not execute (per #2), and nothing in the spec provides a control construct that would skip forward independently of the blocked `REQUIRE`, this statement is likewise never reached in this flow.
- Semantics of `EMIT`: "`EMIT` represents an externally meaningful output" of "an output or artifact defined by the surrounding process." A `deployment-log` artifact is defined by the specification's own example (`EMIT test-report`, `EMIT source-code`) as representing a real produced output. Since no deployment was ever delegated (or performed), emitting a `deployment-log` would misrepresent that deployment activity occurred — which is precisely the kind of "proceeding as if satisfied" the `REQUIRE` clause forbids one step earlier.

## 4. What exactly should the executing agent do in this situation?

From the specification alone, the following is determined:

- The agent must **not** execute `DELEGATE deployment` or `EMIT deployment-log`, per #2 and #3.
- The agent must **not** fabricate, substitute, or otherwise treat `staging-credentials` as available. The spec's parallel principle for `HITL` ("must not be silently replaced by an agent decision unless the surrounding definition explicitly permits automatic resolution through `AUTO`") and for `VERIFY` ("must not silently modify the result it evaluates") reflects a consistent design stance in this DSL: an agent must not silently substitute its own resolution for something the DSL marks as an evaluation/decision/requirement boundary. `REQUIRE` is exactly such a boundary — it "describes what is required, not how it is obtained" — so the agent has no license to invent a way around the missing credentials (e.g., proceeding without them, using placeholder/alternate credentials, or assuming success).
- The flow as written **cannot continue**. This process fragment defines no fallback, error branch, `WHEN` on a requirement outcome, `HITL`, or `STOP` for the case where `REQUIRE` fails, so nothing in the given text tells the agent what happens *next* — only that it must not fall through to `DELEGATE`/`EMIT`. This is where the specification underdetermines the answer.

**Explicit assumption (specification does not determine this):** Because the given fragment contains no explicit handling for a failed `REQUIRE` (no `WHEN requirement.failed`, no `HITL`, no `STOP` authored around it), the correct behavior for the agent is not fully specified by the DSL text. The most defensible reading, consistent with the DSL's stated principles, is:

- Treat this as the flow being blocked/halted at the `REQUIRE` statement — the agent should stop advancing this flow rather than pick one of `DELEGATE`/`EMIT`/skip-ahead on its own initiative, since none of those is licensed by the spec.
- Surface the unmet requirement to whatever governs the surrounding process (e.g., a human via `HITL`, or a `STOP` of this flow) **only if** such a construct is authored elsewhere in the full process definition — the three-line fragment given here contains none, so within this fragment alone, the only DSL-sanctioned action is to not proceed past `REQUIRE`.
- This is an assumption, not a spec-derived fact, because the specification does not state a default/implicit escalation path for a failed `REQUIRE` the way it does for `HITL` (which has `FALLBACK`) or `VERIFY` (which has `WHEN ...rejected`). If the full process (outside this excerpt) defines a `WHEN` branch on a requirement-failure outcome, or a `HITL`/`FALLBACK`/`STOP` around this `REQUIRE`, that authored behavior would govern; absent it, the specification only guarantees that execution does not proceed as though the requirement were met.
