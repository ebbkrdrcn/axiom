# Analysis of the go_harness DSL Snippet

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.passed
  → TRANSITION "Review"
WHEN tests.failed
  → TRANSITION "Debugging"
```

This analysis uses only the definitions given in the specification. Where the
specification leaves something undetermined, that is stated explicitly along
with the assumption made.

---

## 1. Which outcome names can `VERIFY implementation` establish?

The specification does not define a fixed, closed vocabulary of outcome
names that `VERIFY` may produce. It only states, generically:

> "Verification may establish outcomes that can be used by `WHEN`."

The one worked example in the spec is:

```text
VERIFY implementation

WHEN implementation.accepted
  → BREAK

WHEN implementation.rejected
  → DELEGATE correction
```

This shows the *pattern* `<subject>.<outcome>` (`implementation.accepted` /
`implementation.rejected`), but the spec never states that these are the
only legal names, nor does it give a naming grammar beyond the general
`Identifier` rule ("identifiers may be used to refer to requirements,
results, states, artifacts, or other process-defined entities").

**Conclusion:** The specification does not determine a specific, enumerable
set of outcome names for `VERIFY implementation`. It only guarantees that
`VERIFY implementation` establishes *some* outcome(s) tied to the subject
`implementation`, usable by subsequent `WHEN` statements. Any concrete name
(e.g. `implementation.accepted`, `implementation.rejected`,
`implementation.passed`, `implementation.failed`) would have to be defined
by the surrounding, process-specific definition — which is not included in
this snippet.

**Assumption:** Following the spec's own example as the closest available
guidance, the "canonical" pair it demonstrates for a `VERIFY <subject>`
statement is `<subject>.accepted` and `<subject>.rejected`. I assume this is
illustrative rather than exhaustive, since nothing in the spec restricts
outcome names to that pair.

---

## 2. Is `WHEN implementation.passed` a valid condition here?

**Syntactically:** Yes. It matches the general statement grammar
`<keyword> <argument>` and `WHEN <condition>`, where `implementation.passed`
is a valid `Identifier`.

**Semantically:** It is valid *only if* the surrounding process definition
treats `implementation.passed` as one of the outcomes established by
`VERIFY implementation`. The specification's own worked example uses the
names `implementation.accepted` / `implementation.rejected`, not
`implementation.passed`. Since the spec does not prescribe or forbid
particular outcome names (see Q1), it does not confirm that `VERIFY
implementation` actually establishes an outcome called
`implementation.passed` — nor does it deny it.

**Conclusion:** The condition is well-formed and consistent with the DSL's
general pattern of `WHEN <subject>.<outcome>`, but whether it corresponds to
an outcome that `VERIFY implementation` truly produces is not determined by
the specification alone. This is a gap that would need to be resolved by the
surrounding process definition (not shown in the snippet).

**Assumption:** For the purposes of this snippet, I assume
`implementation.passed` is intended as a process-specific synonym for what
the spec's example calls `implementation.accepted` — i.e., the positive
outcome of `VERIFY implementation`.

---

## 3. Is `WHEN tests.failed` valid here, and where does `tests` come from?

**Syntactically:** Yes, `tests.failed` is a valid `Identifier` and `WHEN
tests.failed` matches the general `WHEN <condition>` grammar.

**Where `tests` comes from:** Nothing in this snippet establishes `tests` as
an entity. The only operations present are `DELEGATE implementation` and
`VERIFY implementation` — there is no `REQUIRE tests`, `DELEGATE tests`, or
`VERIFY tests` anywhere in the given code. The specification says
identifiers "may be used to refer to requirements, results, states,
artifacts, or other process-defined entities," which implies `tests` would
need to be defined somewhere in the broader process (e.g., a `VERIFY tests`
statement elsewhere, or a requirement declared via `REQUIRE`) that is simply
not shown in this excerpt.

The specification also states that "Multiple `WHEN` constructs may describe
different outcomes of the same process state," which suggests the two
`WHEN` blocks in a well-formed snippet would normally refer to the same
underlying state (here, the result of verifying `implementation`). The fact
that the second `WHEN` refers to a differently-named subject (`tests`
instead of `implementation`) is not explained or grounded anywhere in the
visible code.

**Conclusion:** `WHEN tests.failed` is syntactically valid, but within this
snippet alone it is **not semantically grounded** — `tests` is an
identifier with no declared source. The specification does not state that
every identifier referenced by `WHEN` must be established within the same
visible block, so this could be valid if `tests` is defined elsewhere in the
full process; but based solely on the given specification and this excerpt,
its origin **cannot be determined**, and it may equally indicate a mismatch
between the two `WHEN` clauses in the example (i.e., the second `WHEN` may
have been intended to also read `implementation.failed`/`.rejected` rather
than `tests.failed`).

**Assumption:** I assume `tests` refers to some other, unshown part of the
larger process (e.g., a separate `VERIFY tests` step) rather than being an
error, since the spec does not forbid referencing state from outside the
displayed excerpt. This assumption cannot be confirmed from the given
material alone.

---

## 4. If the verification of the implementation is negative, which `TRANSITION` (if any) is executed?

Given the snippet exactly as written:

- `WHEN implementation.passed → TRANSITION "Review"` — if verification is
  negative, `implementation.passed` does not hold, so this branch's
  condition is false and `TRANSITION "Review"` is **not** executed.
- `WHEN tests.failed → TRANSITION "Debugging"` — this condition concerns
  `tests`, an entity not established anywhere in this snippet (see Q3). The
  specification gives no basis for asserting that a negative verification of
  `implementation` also makes `tests.failed` true; these are presented as
  independent identifiers/subjects. So this branch cannot be said to fire
  as a consequence of `implementation`'s verification result.

**Conclusion:** Based strictly on what the specification and this snippet
establish, a negative outcome of `VERIFY implementation` does not
necessarily trigger *either* `TRANSITION` shown here:
- `TRANSITION "Review"` is explicitly gated on the positive outcome
  (`implementation.passed`), so it does not run.
- `TRANSITION "Debugging"` is gated on `tests.failed`, a condition whose
  truth is not determined by, or connected to, the verification of
  `implementation` anywhere in the given text.

In other words, this snippet **omits an explicit handler for the negative
verification outcome of `implementation`** (there is no `WHEN
implementation.rejected` / `implementation.failed` clause corresponding to
the spec's own example pattern). The specification does not define an
implicit "else" or default transition for `WHEN` — each `WHEN` only acts
when its own condition is satisfied — so nothing in the DSL semantics
supplies a transition in this case by default.

**Assumptions used to reach this conclusion:**
1. `WHEN` has no implicit "otherwise" branch; unmatched conditions simply
   result in no action for that construct (consistent with "`WHEN` does not
   itself perform work... when the condition is satisfied").
2. `tests.failed` is not implicitly equivalent to, or triggered by, a
   negative result of `VERIFY implementation`, since the spec never
   establishes such a link and treats `implementation` and `tests` as
   distinct identifiers.

**Net answer:** As written, if `VERIFY implementation` is negative, neither
`TRANSITION "Review"` nor `TRANSITION "Debugging"` is guaranteed to execute
by the specification alone — the snippet does not define what happens on a
negative verification of `implementation`. This is a gap in the process
definition as given, not something the DSL semantics resolve automatically.
