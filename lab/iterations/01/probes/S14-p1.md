# Execution Trace: FORK/JOIN with Two VERIFY Outcomes

## Program under analysis

```text
FORK
  → DELEGATE unit-tests
      VERIFY unit-tests
  → DELEGATE integration-tests
      VERIFY integration-tests
JOIN
WHEN unit-tests.accepted
  → TRANSITION "Ready"
WHEN integration-tests.rejected
  → TRANSITION "Debugging"
```

Injected events:
- `VERIFY unit-tests` establishes `accepted`.
- `VERIFY integration-tests` establishes `rejected`; this branch finishes **later** than the unit-tests branch.

---

## Step-by-step execution

**Step 1 — `FORK`**
`FORK` starts two independent concurrent flows (per "Each `→` starts an independent flow" and "The branches may execute concurrently"):
- Branch A: `DELEGATE unit-tests` → `VERIFY unit-tests`
- Branch B: `DELEGATE integration-tests` → `VERIFY integration-tests`

Within each branch, statements still execute in declaration order (the general "Flow" rule — "Statements execute in declaration order unless an explicit control construct changes the flow" — applies inside a branch; `FORK` only makes the *branches* concurrent with each other, it does not reorder statements within a branch).

**Step 2 — Branch A: `DELEGATE unit-tests`**
Work "unit-tests" is assigned to an actor. Per the spec, `DELEGATE` "does not mean that the work is correct, complete, or accepted" — it only records that responsibility is assigned. No state changes yet.

**Step 3 — Branch A: `VERIFY unit-tests`**
The result of the unit-tests work is evaluated. By the injected event, this evaluation establishes `unit-tests.accepted`. Per the spec, "Completion of delegated work is not equivalent to successful verification," but here verification itself succeeds and yields an outcome usable by `WHEN`. Branch A now completes.

**Step 4 — Branch B: `DELEGATE integration-tests`**
Work "integration-tests" is assigned to an actor, concurrently with Branch A (order relative to Steps 2–3 is not determined by the spec, since `FORK` branches "may execute concurrently").

**Step 5 — Branch B: `VERIFY integration-tests`**
The result of the integration-tests work is evaluated. By the injected event, this evaluation establishes `integration-tests.rejected`. This step is stated to finish **later** than Branch A's `VERIFY unit-tests` (Step 3). Branch B now completes.

**Step 6 — `JOIN`**
`JOIN` "waits for the concurrent flows started by the corresponding `FORK`," and "execution continues only after all required forked flows have completed." Both branches (A and B) are the forked flows here, so `JOIN` must wait until the later-finishing branch — Branch B — completes. Execution therefore blocks from the end of Step 3 until Step 5 finishes, then proceeds.

At the point `JOIN` releases execution, both outcomes are established:
- `unit-tests.accepted` = true
- `integration-tests.rejected` = true

**Step 7 — `WHEN unit-tests.accepted`**
The condition `unit-tests.accepted` is satisfied (established in Step 3). Per the spec, `WHEN` is "a control construct" whose `→` statements "form the flow executed when the condition is satisfied." The nested flow executes:

**Step 7a — `TRANSITION "Ready"`**
The process state changes. Per the spec, "`TRANSITION` represents a state change" — "the process has moved to the `Ready` state." Current process state is now `Ready`.

**Step 8 — `WHEN integration-tests.rejected`**
This is declared as a separate, subsequent `WHEN` construct. The spec explicitly allows this: "Multiple `WHEN` constructs may describe different outcomes of the same process state," and nothing in the spec makes a later `WHEN` conditional on an earlier `WHEN` not having matched (there is no `ELSE`/`ELIF` construct in the specification, and statements otherwise "execute in declaration order unless an explicit control construct changes the flow"). The condition `integration-tests.rejected` is satisfied (established in Step 5), so its nested flow also executes:

**Step 8a — `TRANSITION "Debugging"`**
The process state changes again, per the same `TRANSITION` semantics. Current process state is now `Debugging`.

**Step 9 — End of program**
No further statements remain.

---

## Final process state

**`Debugging`**

This is the state left by the last `TRANSITION` statement that actually executed (Step 8a), which itself executed because `integration-tests.rejected` was true and nothing in the spec exempted it from running after `WHEN unit-tests.accepted` had already matched and transitioned the process to `Ready`.

---

## Points the specification does not determine (stated explicitly, with assumptions made)

1. **Whether multiple satisfied `WHEN` blocks are all executed, or whether matching one `WHEN` suppresses evaluation of subsequent `WHEN`s (if/elif-style exclusivity).**
   The spec only says "Multiple `WHEN` constructs may describe different outcomes of the same process state" and shows one example where the two conditions (`tests.passed` / `tests.failed`) are naturally mutually exclusive, so that example doesn't resolve this case, where the two conditions come from two independent `VERIFY` results and are *not* mutually exclusive.
   **Assumption made:** Each `WHEN` is evaluated independently in declaration order, and every `WHEN` whose condition is satisfied has its flow executed (no implicit "first match wins" / `else` semantics), since the spec defines no such exclusivity rule and the general "Flow" rule says statements run in declaration order unless a control construct changes that. Under this assumption, both `WHEN` blocks fire.

2. **How conflicting/sequential `TRANSITION`s to different states are resolved when both occur in the same execution.**
   The spec defines `TRANSITION` only for a single state change ("the process has moved to the `X` state") and says nothing about what happens when two `TRANSITION` statements execute in the same run.
   **Assumption made:** `TRANSITION` is last-write-wins — the current process state is whatever the most recently executed `TRANSITION` set it to. This is the most direct reading of "`TRANSITION` represents a state change" applied twice in sequence, but the spec does not explicitly rule out an alternative such as treating this as an ambiguous/invalid outcome requiring human resolution (there is no rule in the spec that two transitions in one run is an error). Given the DSL provides no validation or conflict rule for this, and no `HITL`/error construct is invoked in the program, last-write-wins in declaration order is the assumption used to produce a definite final state.

3. **Relative interleaving of `DELEGATE`/`VERIFY` between the two branches before `JOIN`.**
   The spec states branches "may execute concurrently" but does not define a scheduling model. This does not affect the final answer, since `JOIN`'s only documented requirement is that it waits for *all* forked flows to complete, and the problem explicitly tells us which branch's `VERIFY` finishes later.

Everything else in the trace (branch semantics of `FORK`, blocking semantics of `JOIN`, non-prescriptive semantics of `DELEGATE`/`VERIFY`, and the state-change-only semantics of `TRANSITION`) follows directly from the specification text without need for additional assumptions.
