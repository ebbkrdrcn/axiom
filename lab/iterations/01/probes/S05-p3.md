# DSL — Validity Analysis

## Snippet A

```text
HITL("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

**Verdict: INVALID**

**Rule cited (### AUTO):**

> `AUTO` is not a control-flow container.
> It does not contain `WHEN`, `→`, or an arbitrary flow.
> Uncertainty is not a DSL condition, state, variable, or keyword.

The specification even gives this exact shape as its own worked counter-example:

> For example, the following is invalid:
> ```text
> AUTO
>   WHEN decision.uncertain
>     → HITL("Approve?")
> ```

Snippet A reproduces that invalid pattern almost verbatim (only the message string differs).

**What is wrong:**

1. `AUTO` is nested with an indented `WHEN` block underneath it, i.e. it is being used as a scoping/container construct the way `LOOP`, `WHEN`, or `FORK` are used. The spec explicitly forbids this: `AUTO` "does not contain `WHEN`, `→`, or an arbitrary flow."
2. The `WHEN` condition is `decision.uncertain`. The spec explicitly states "Uncertainty is not a DSL condition, state, variable, or keyword." So even considered on its own, `decision.uncertain` is not a legal condition expression — uncertainty is something "the DSL runtime determines... as part of automatic decision resolution," not something the author can branch on.
3. Consequently, the attempt to manually re-invoke `HITL("Approve release?")` when uncertain is the author trying to hand-implement the exact behavior that `AUTO` is defined to provide implicitly ("Resolve automatically when sufficiently determined; otherwise require human input."). Per the spec, that escalation-to-human behavior is intrinsic to how the runtime resolves `AUTO`, not something expressed via `WHEN`/`→` in the DSL text.

**What would happen / correct form:** Because this construct is invalid DSL, an implementation should reject it rather than execute it. The specification's suggested way to express "fall back to a human when the automatic/expected path can't be used" is `FALLBACK` attached to the relevant `HITL`/response-handling point (see `### FALLBACK`), not a `WHEN decision.uncertain` clause inside `AUTO`. A conforming rewrite would drop the nested `WHEN` entirely and either use a bare `AUTO` (letting the runtime silently escalate to human input on its own when uncertain) or use `HITL(...) → FALLBACK → <flow>` if a fallback flow needs to be specified explicitly.

**Explicit gap / assumption:** The specification never defines the syntactic relationship between a preceding `HITL(...)` statement and a following bare `AUTO` statement (e.g., whether `AUTO` here is meant to modify/resolve that specific `HITL`, or whether they are two unrelated sequential statements). This is not determined by the spec, so beyond flagging it as an open point, I make no assumption about intended linkage — it does not change the verdict, since the fatal defect (the `WHEN decision.uncertain` container) is independently and explicitly invalid regardless of how `AUTO` relates to the prior `HITL`.

## Snippet B

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

**Verdict: INVALID**

**Rule cited (### BREAK):**

> Exits the current `LOOP`.
> ...
> `BREAK` does not terminate the entire execution.
> `BREAK` may only exit a loop scope.
> Use `STOP` to terminate the entire execution.

**What is wrong:**

The snippet contains no `LOOP:<name>` construct at all — `DELEGATE`, `VERIFY`, and `WHEN` all appear at the top level (per the Scope rule, "Indented statements belong to the preceding scoped construct," and nothing here is indented under a `LOOP`). `BREAK` is defined to exit "the current `LOOP`" and the spec is explicit that "`BREAK` may only exit a loop scope." With no enclosing `LOOP` scope, there is no loop for `BREAK` to exit, so the statement has no valid target and violates this constraint.

Note that everything else in the snippet is well-formed and in fact mirrors the specification's own example almost exactly:

```text
VERIFY implementation

WHEN implementation.accepted
  → BREAK

WHEN implementation.rejected
  → DELEGATE correction
```

`DELEGATE implementation` followed by `VERIFY implementation`, and branching on `implementation.rejected` via `WHEN`, is exactly the sanctioned `DELEGATE`/`VERIFY`/`WHEN` pattern from the `### VERIFY` section. The only defect is substituting `→ BREAK` for the rejected branch instead of `→ DELEGATE correction` (or some other in-flow action), while the surrounding `LOOP` that would make `BREAK` legal is absent from the snippet.

**What would happen:** Since `BREAK` has no loop scope to exit, this is not a case where it degrades gracefully (e.g., into a `STOP`) — the spec defines `BREAK` and `STOP` as distinct, non-interchangeable operations ("`BREAK` does not terminate the entire execution... Use `STOP` to terminate the entire execution"), so an implementation cannot silently reinterpret an out-of-scope `BREAK` as either. The specification gives no defined behavior for a `BREAK` with no enclosing loop, so this must be treated as a malformed/invalid statement rather than as executable with some fallback semantics.

**Correct form:** Either (a) wrap the whole sequence in a `LOOP:<name>` scope so that `BREAK` has a loop to exit, e.g.:

```text
LOOP:review
  DELEGATE implementation
  VERIFY implementation
  WHEN implementation.rejected
    → BREAK
```

(with the intended meaning that the loop is exited once the delegated result is no longer being rejected — though whether that reading is even what's wanted is itself undetermined without more context), or (b) if termination of the entire process is intended rather than exiting a loop, replace `BREAK` with `STOP`.

**Explicit gap / assumption:** The specification does not state what a compliant runtime must do when it encounters a `BREAK` outside any `LOOP` (reject at parse/validation time vs. some other defined error behavior) — it only states that this usage is not permitted ("may only exit a loop scope"). I assume, per the task's classification of VALID/INVALID, that any statement whose use is stated as impermissible by the spec is to be marked INVALID, without needing the spec to also define the runtime's error-handling behavior for that case.
