# Analysis: `REQUIRE` failure in DSL

```text
REQUIRE staging-credentials
DELEGATE deployment
EMIT deployment-log
```

Given: `staging-credentials` cannot be obtained.

## 1. What happens at `REQUIRE staging-credentials`?

The specification states, for `REQUIRE`:

> The requirement must be satisfied before execution continues.
> If a required condition cannot be satisfied, execution must not proceed as if the requirement were satisfied.

`REQUIRE` "describes what is required, not how it is obtained" — the spec deliberately does not prescribe *how* `staging-credentials` would be fetched (filesystem, API, vault, etc.), so nothing can be said about the mechanics of the failed attempt. What the spec does determine is the **outcome**: since the credentials cannot be obtained, the requirement is **not satisfied**, and execution is therefore not permitted to continue past this statement as though it had been. In effect, `REQUIRE staging-credentials` blocks / gates the flow at this point.

The spec does **not** state explicitly what state the process enters as a result (e.g., whether this constitutes a distinct "failed" process state, an error, or simply a blocked flow) — that is an implementation/process detail the DSL leaves open. **Assumption:** I treat "execution must not proceed" as meaning the flow is halted/blocked at this statement, pending some resolution, rather than continuing forward.

## 2. Is `DELEGATE deployment` executed?

No. Statements execute "in declaration order unless an explicit control construct changes the flow," and `REQUIRE` establishes a precondition that "must be satisfied before execution continues." Since `staging-credentials` is not satisfied, execution does not continue to the next statement in sequence. `DELEGATE deployment` is therefore **not executed** — assigning the deployment work to an actor cannot occur while the declared prerequisite for "subsequent execution" is unmet.

## 3. Is `EMIT deployment-log` executed?

No, for the same reason, and additionally because `EMIT` "produces an output or artifact defined by the surrounding process" — here, a log of a deployment. Since the deployment (`DELEGATE deployment`) never executed, there is nothing for `EMIT deployment-log` to represent, and it sits later in declaration order, after both blocked statements. It is **not executed**.

## 4. What exactly should the executing agent do in this situation?

What the specification clearly determines:

- The agent must **not** proceed as if `staging-credentials` were available (explicit text of `REQUIRE`).
- The agent must **not** fabricate, guess, or silently substitute a result for the unmet requirement — this follows from the general semantic principle that the DSL defines *what* is required/must happen, not a license for the agent to invent a way to satisfy it, and mirrors the same discipline the spec imposes elsewhere (e.g., `VERIFY` "must not silently modify the result it evaluates"; `AUTO` "is not a request to guess").
- The agent must not execute `DELEGATE deployment` or `EMIT deployment-log`, per points 2–3.

What the specification does **not** determine (and must be flagged rather than invented):

- This snippet contains **no `WHEN`, `HITL`, `FALLBACK`, or `STOP`** tied to the failure of `REQUIRE staging-credentials`. The DSL's only defined mechanisms for handling an unresolved/unavailable situation are:
  - `STOP` — terminates execution entirely, but nothing in the snippet invokes it;
  - `HITL` — establishes a human decision boundary, but nothing in the snippet invokes it here;
  - `FALLBACK` — handles an unavailable/insufficient *response*, but it is explicitly associated with response handling for constructs like `HITL`, and none is declared here;
  - `WHEN` — branches on established outcomes (e.g., of `VERIFY`), but `REQUIRE` is not described as producing a condition usable by `WHEN`, and no such `WHEN` is present in this snippet anyway.

  Because none of these are present, the specification, strictly as given, does not say what the agent should do *next* after the requirement fails — it only says what the agent must **not** do (proceed, fabricate, delegate, emit).

- **Assumption:** In the absence of any declared recovery path, the spec-consistent behavior is for the agent to treat this as a blocked process: halt forward progress at `REQUIRE staging-credentials`, and surface the unmet requirement outside the DSL flow (since the DSL "does not prescribe implementation mechanisms," how that surfacing happens — an error report, a human notification via some out-of-DSL channel, a retry policy, etc. — is not something the specification defines). This is consistent with the DSL's general stance that `REQUIRE`, `DELEGATE`, `VERIFY`, `TRANSITION`, `EMIT`, `WAIT`, `HITL`, and `AUTO` all define *meaning*, not *mechanism*.
- I explicitly do **not** assume the agent should invoke `HITL` or `STOP` automatically, since neither appears in the given process definition and the spec gives no rule that an unmet `REQUIRE` implicitly becomes a `HITL` or a `STOP` — that would be inventing control flow the author of this particular process did not write. If the intent was for a human decision or explicit termination on this failure, the specification would need the process definition itself to include a `HITL`, `FALLBACK`, or `STOP`/`WHEN` clause addressing the unmet requirement; as written, that is a gap in the given process, not something the DSL semantics fill in automatically.

**Summary:** The agent stops advancing through the flow at `REQUIRE staging-credentials`; it does not run `DELEGATE deployment` or `EMIT deployment-log`; and it must not treat the requirement as satisfied or invent a substitute outcome. Beyond that, the specification does not itself define a recovery action for this scenario because the given process defines none (no `HITL`/`FALLBACK`/`STOP`/`WHEN` for this case) — this is a gap in the process definition, not a rule the DSL specifies, and I've assumed the appropriate spec-consistent behavior is to halt and surface the unmet requirement outside the DSL rather than to guess at an unwritten control path.
