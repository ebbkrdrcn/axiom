```text
LOOP:implementation-cycle
  DELEGATE implementation
  VERIFY implementation

  WHEN implementation.accepted
    → BREAK

  WHEN implementation.rejected
    → DELEGATE correction

EMIT source-code
```

## Assumptions

The specification determines most of this task directly (the `DELEGATE implementation` / `VERIFY implementation` example, the `VERIFY` → `WHEN implementation.accepted` / `WHEN implementation.rejected` example, and `BREAK` exiting the enclosing `LOOP`). Where it does not fully determine something, I assumed the following:

1. **Implicit repetition ("repeat from the start").** The spec gives no explicit "continue" or "restart loop" keyword. It only says a `LOOP` "continues until `BREAK`, `STOP`, or another explicit control flow terminates it," implying that if none of those is reached, execution simply returns to the top of the loop body. I assumed that after the `WHEN implementation.rejected` branch (`DELEGATE correction`) finishes with no `BREAK`/`STOP`, the loop implicitly re-executes from its first statement (`DELEGATE implementation`) — no explicit statement is needed to express "repeat from the start."

2. **What "repeat from the start" restarts.** The task says: delegate correction, "then repeat from the start." I took "the start" to mean the top of the `LOOP` body (`DELEGATE implementation`), not a resumption at `DELEGATE correction`. This is a literal reading of the requirement text, not something the spec itself defines, since the spec has no notion of "start of loop" as an addressable point other than the loop body's first statement.

3. **The `LOOP` name.** `LOOP:<name>` requires an identifier, but the spec does not say how this name should be derived or what it should reference. I chose the descriptive identifier `implementation-cycle`; any other name would be equally valid per the spec.

4. **Identifier linking `DELEGATE`, `VERIFY`, and `WHEN`.** I used the identifier `implementation` for both `DELEGATE implementation` and `VERIFY implementation`, and derived the condition names `implementation.accepted` / `implementation.rejected` from it, mirroring the spec's own worked example under `VERIFY`. The spec does not formally define a dot-notation grammar for outcome conditions beyond that example, so this naming convention is assumed by analogy rather than specified as syntax.

5. **`correction` is not itself re-verified inside this loop.** The task only says to "delegate a correction and then repeat from the start"; it does not ask for an explicit `VERIFY correction` step. Under assumption 1/2, the corrected work would be picked up again by the next iteration's `DELEGATE implementation` / `VERIFY implementation` pair, so no separate verification statement was added for `correction` — the spec does not mandate one, and the task does not request one.

6. **Placement of `EMIT source-code`.** The task says this happens "after the repetition ends." Since `BREAK` is the only exit from the loop described in the task, and `BREAK` "does not terminate the entire execution," I placed `EMIT source-code` as an unindented statement immediately following the `LOOP` block, so it executes once control leaves the loop via `BREAK`. The spec does not state a syntactic marker for "immediately after a loop" beyond de-indentation back to the loop's own level, which I assumed is sufficient to express this.

7. **No outcome other than accepted/rejected.** The spec's `AUTO`/uncertainty machinery and `HITL`/`FALLBACK` constructs are not invoked because the task states only two verification outcomes (accept/reject) and does not mention any human-decision boundary or unavailable-response handling. I assumed no `HITL`, `AUTO`, or `FALLBACK` construct is needed since the requirement text gives no indication of missing/uncertain information requiring them.
