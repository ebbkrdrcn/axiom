# Execution Trace

## Program

```text
FORK
  → DELEGATE unit-tests
      VERIFY unit-tests
  → DELEGATE integration-tests
      VERIFY integration-tests
JOIN
WHEN unit-tests.accepted
  → TRANSITION "Ready"
WHEN integration-tests.rejected
  → TRANSITION "Debugging"
```

## Injected events

- `VERIFY unit-tests` establishes `unit-tests.accepted`.
- `VERIFY integration-tests` establishes `integration-tests.rejected`, finishing **later** than the unit-tests branch.

## Step-by-step execution

**Step 1 — `FORK`**
Two independent concurrent flows are started (per the FORK spec: "Each `→` starts an independent flow. ... The branches may execute concurrently."):

- Branch A: `DELEGATE unit-tests` → `VERIFY unit-tests`
- Branch B: `DELEGATE integration-tests` → `VERIFY integration-tests`

Neither branch's contents run "inside" the other; they proceed independently until `JOIN`.

**Step 2 — Branch A: `DELEGATE unit-tests`**
Work is assigned to an actor responsible for `unit-tests`. Per spec, `DELEGATE` "does not mean that the work is correct, complete, or accepted" — no outcome is established yet.

**Step 3 — Branch B: `DELEGATE integration-tests`**
Concurrently (order relative to Step 2 is not determined by the spec, since both branches run independently), work is assigned for `integration-tests`. No outcome established yet.

**Step 4 — Branch A: `VERIFY unit-tests`**
Evaluates the delegated `unit-tests` result against acceptance criteria. Per the injected event, this establishes the outcome `unit-tests.accepted`. This branch completes first (the task states the integration-tests branch "finishes later than the unit-tests branch").

**Step 5 — Branch B: `VERIFY integration-tests`**
Evaluates the delegated `integration-tests` result. Per the injected event, this establishes the outcome `integration-tests.rejected`. This branch completes second (later).

**Step 6 — `JOIN`**
Per spec: "Execution continues only after all required forked flows have completed." `JOIN` blocks until *both* branches (A and B) are complete. Since Branch B finishes later, `JOIN` unblocks at the moment Branch B's `VERIFY integration-tests` completes. At that point both outcomes exist simultaneously:
- `unit-tests.accepted` = established
- `integration-tests.rejected` = established

The earlier completion of Branch A does not let execution proceed past `JOIN` on its own; nor does the relative finishing order of the two branches otherwise affect what happens afterward — `JOIN` only cares that both are done.

**Step 7 — `WHEN unit-tests.accepted`**
Statements execute "in declaration order unless an explicit control construct changes the flow," so this is the next statement evaluated after `JOIN`. The condition `unit-tests.accepted` is satisfied (established in Step 4), so its flow executes:
- `TRANSITION "Ready"` — the process state changes to **"Ready"**.

**Step 8 — `WHEN integration-tests.rejected`**
The next statement in declaration order. The condition `integration-tests.rejected` is satisfied (established in Step 5), so its flow executes:
- `TRANSITION "Debugging"` — the process state changes to **"Debugging"**.

This `TRANSITION` overwrites the state set in Step 7, since `TRANSITION` acts on "the current process state" (singular) and there is no statement between Step 7 and Step 8 that reads or consumes the "Ready" state before it is replaced.

**Step 9 — End of program**
No `STOP` is present and no further statements remain. Execution ends after the last statement runs.

## Final process state

**"Debugging"**

Both `WHEN` blocks fire because their conditions concern two independent results (`unit-tests` and `integration-tests`) that are not mutually exclusive — nothing in the specification makes satisfying one condition preclude the other from also being satisfied, and both were established as true before either `WHEN` was evaluated. Because both associated flows run, in declaration order, and each contains a `TRANSITION`, the process undergoes two state changes: first to `"Ready"`, then to `"Debugging"`. The second `TRANSITION` is the one in effect when execution ends, so `"Debugging"` is the final state.

## Where the specification does not determine the outcome (assumptions made)

The specification leaves the following points open; the trace above makes the stated assumption in each case:

1. **Relative execution order of statements *within* the two FORK branches (Steps 2–3, and 4–5 relative to each other before JOIN).** The spec says branches "may execute concurrently" but does not define interleaving semantics. Assumption: this does not affect the outcome, since `JOIN` waits for both regardless of interleaving, and the task explicitly fixes the relative *completion* order of the two `VERIFY`s (unit-tests first, integration-tests later), which is what matters here.

2. **Whether multiple simultaneously-true `WHEN` conditions all fire, or only one is chosen (e.g., first-match/exclusive-or semantics).** The spec states `WHEN` is a per-condition evaluation ("Multiple `WHEN` constructs may describe different outcomes of the same process state") and gives no if/elif/exclusivity rule, no priority mechanism, and no notion of a "condition already handled." Assumption: each `WHEN` is evaluated independently against the facts available at that point in the flow, and *every* `WHEN` whose condition is satisfied executes its flow, in declaration order like any other statement.

3. **Whether "process state" is single-valued (i.e., a later `TRANSITION` overwrites an earlier one in the same execution) or can hold multiple concurrent values.** The spec describes `TRANSITION` as changing "the current process state" (singular, definite article) and gives no mechanism for multiple concurrent states or for merging/rejecting a second `TRANSITION`. Assumption: process state is a single current value, so the second `TRANSITION` ("Debugging") replaces the first ("Ready").

4. **What happens when the statement list is exhausted without a `STOP`.** The spec only defines what `STOP` does ("Terminates execution... No subsequent statement is executed after `STOP`") but does not define behavior when execution simply reaches the end of the program. Assumption: execution ends normally once there are no more statements to run, equivalent in effect to reaching `STOP` at that point.

5. **Timing/ordering of `DELEGATE` relative to the other branch's `DELEGATE`.** The spec says `DELEGATE` "does not mean that the work is correct, complete, or accepted" and doesn't state when delegation is considered "sent" relative to a concurrent branch's delegation. This has no bearing on the final answer here, since only the `VERIFY` completion order (given explicitly by the task) matters for `JOIN` and the subsequent `WHEN`s.
