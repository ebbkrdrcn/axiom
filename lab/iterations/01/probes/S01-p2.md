```text
DELEGATE implementation
VERIFY implementation

AUTO merge-decision
HITL("Merge this change?")

WHEN merge-decision.merge
  → TRANSITION "Merged"

WHEN merge-decision.no-merge
  → TRANSITION "Rework"
```

## Assumptions

1. **No explicit syntax is given in the specification for combining `AUTO` and `HITL` into one decision point.** The spec only states the semantic relationship — in the `HITL` section: "`HITL` must not be silently replaced by an agent decision unless the surrounding definition explicitly permits automatic resolution through `AUTO`" — and in the `AUTO` section: "Resolve automatically when sufficiently determined; otherwise require human input." Since `AUTO` "is not a control-flow container" and "does not contain `WHEN`, `→`, or an arbitrary flow," I could not nest `HITL` inside `AUTO`. I represented the pairing as two adjacent statements, `AUTO merge-decision` followed by `HITL("Merge this change?")`, meaning "attempt automatic resolution of this decision; the runtime falls back to the human prompt when the decision is uncertain or outside the agent's authority." This composition (including which statement is written first) is an assumption, not something the spec defines.

2. **The identifier `merge-decision` is invented.** The task does not name the decision, and the spec's `Identifier` section only says identifiers "may be used to refer to requirements, results, states, artifacts, or other process-defined entities" without prescribing naming conventions. I chose `merge-decision` for readability.

3. **The outcome names `merge-decision.merge` and `merge-decision.no-merge` are invented.** The spec shows dot-notation outcomes only for `VERIFY` (`implementation.accepted` / `implementation.rejected`) and says "Verification may establish outcomes that can be used by `WHEN`." It does not state whether/how an `AUTO`-or-`HITL` decision produces outcomes consumable by `WHEN`, nor what those outcomes would be named. I extrapolated the same dot-notation pattern by analogy.

4. **No `FALLBACK` was used.** Per the spec, `FALLBACK` handles the case where "an expected response is unavailable or insufficient" after a `HITL` request — a different scenario from routing between automatic and human resolution. The task only describes the AUTO-vs-human branching, not a case where the human fails to respond, so I did not add a `FALLBACK` block. This is an interpretive choice; the spec does not say whether a merge `HITL` should also define a `FALLBACK`.

5. **No `REQUIRE` statement was added.** The task does not mention any precondition (e.g., required repository access, criteria, or context) that must be declared before delegation/verification/decision, and the spec does not force every process to include a `REQUIRE`.

6. **The two `WHEN` branches were modeled directly on the spec's `VERIFY`/`WHEN` example** ("Multiple `WHEN` constructs may describe different outcomes of the same process state"), applying the same pattern to the merge decision's two possible outcomes (merge / no-merge) rather than to a `VERIFY` outcome.

7. **No `LOOP` was used**, since the task describes a single linear sequence (delegate → verify → decide → transition), not a repeating scope.

8. **No `STOP` was added at the end.** The spec does not require execution to explicitly terminate after a `TRANSITION`, and the task does not state that execution should end after reaching "Merged" or "Rework."
