# Analysis of the DSL Snippet

```text
VERIFY review
WHEN review.rejected
  → DELEGATE correction
      VERIFY correction
  → TRANSITION "Rework"
EMIT review-report
```

Given: `VERIFY review` establishes the outcome `rejected`.

A preliminary note on ambiguity, stated up front since it bears on questions 1–3:

> **Assumption.** The specification's "Conditional Flow" syntax block shows a `WHEN` with two `→` lines (`WHEN <condition> / → <statement> / → <statement>`), but the specification's only worked `WHEN` example uses a single `→` per `WHEN`. The spec never states whether multiple `→` lines under one `WHEN` are (a) sequential statements that together make up "the conditional flow" (singular, per "The statements following `→` form the flow executed when the condition is satisfied" and "The statements following `→` belong to the conditional flow"), or (b) independent concurrent branches, as `→` denotes under `FORK` ("Each `→` starts an independent flow").
>
> I assume interpretation (a): under `WHEN`, `→` is only a flow-item marker, and concurrency is a property the spec grants explicitly and only to `FORK` ("Starts multiple concurrent flows... Each `→` starts an independent flow"). `WHEN` is described only as producing "the flow executed when the condition is satisfied" (singular), with no mention of concurrency, and the general "Flow" rule ("Statements execute in declaration order unless an explicit control construct changes the flow") applies by default. So all `→` items under a single `WHEN`, plus their indented sub-statements, form one ordered sequence.

With that assumption stated, here are the answers.

## 1. Which statements belong to the WHEN flow?

The `WHEN review.rejected` flow consists of every statement indented under it:

- `DELEGATE correction`
- `VERIFY correction` (indented further, under `DELEGATE correction`)
- `TRANSITION "Rework"`

This follows directly from the Scope rule ("Indented statements belong to the preceding scoped construct") and the Conditional Flow rule ("The statements following `→` belong to the conditional flow"). `VERIFY correction` is nested one level deeper than `DELEGATE correction`; the spec's `FORK` section illustrates the identical nesting pattern (`DELEGATE security-review` / `VERIFY security-review`) and says such nested statements belong together with the statement they are nested under, so `VERIFY correction` is part of the same flow item as `DELEGATE correction`, not a separate top-level member of the `WHEN` flow.

`EMIT review-report` is **not** indented under `WHEN` (it is at the same indentation level as `VERIFY review` and `WHEN` itself), so it does not belong to the `WHEN` flow — see question 4.

## 2. Sequential or concurrent, and in what order?

Sequential, in declaration order:

1. `DELEGATE correction`
2. `VERIFY correction`
3. `TRANSITION "Rework"`

Rationale: the specification grants concurrent semantics explicitly and only to `FORK` ("Starts multiple concurrent flows," "The branches may execute concurrently"). `WHEN` carries no such statement — it is described only as producing a single flow to execute when its condition holds. The default "Flow" rule then governs: "Statements execute in declaration order unless an explicit control construct changes the flow." No control construct here (`BREAK`, `STOP`, `JOIN`, etc.) alters that order, so the three statements run one after another in the order written. (See the assumption note above — the spec does not explicitly rule out reading multiple `→` under `WHEN` as parallel branches, but nothing supports that reading either, and the concurrency language is reserved for `FORK`.)

## 3. Is `VERIFY correction` part of the WHEN flow?

Yes. It is indented under `DELEGATE correction`, which is itself one of the `WHEN` flow's `→` items. Per the Scope rule, indented statements belong to the preceding scoped construct — here, that chain of indentation places `VERIFY correction` inside the `WHEN review.rejected` flow, executing right after `DELEGATE correction` and before `TRANSITION "Rework"`.

## 4. Is `EMIT review-report` part of the WHEN flow? Is it executed?

**Part of the flow: no.** `EMIT review-report` is written at the same indentation as `VERIFY review` and `WHEN review.rejected` — i.e., it is not indented under `WHEN` at all. By the Scope rule, only indented statements belong to the preceding construct, so `EMIT review-report` is a sibling top-level statement in the outer flow, not a member of the conditional flow.

**Executed: yes.** Since `EMIT review-report` sits outside the `WHEN` construct entirely, its execution is not conditioned on `review.rejected` (or on anything else); it is simply the next statement in declaration order after the `WHEN` construct has run its course. The general "Flow" rule ("Statements execute in declaration order unless an explicit control construct changes the flow") applies, and nothing in this snippet (no `STOP`, `BREAK`, or other terminator) prevents execution from reaching it. So `EMIT review-report` executes unconditionally after the `WHEN` block finishes — in this case, after `TRANSITION "Rework"` completes, since `review.rejected` is the established outcome and the `WHEN` flow does run.

## 5. If `VERIFY review` had established `accepted` instead, which statements would execute?

Only:

1. `VERIFY review`
2. `EMIT review-report`

Because the only condition present is `review.rejected`, and the established outcome would now be `accepted` (not `rejected`), that condition is not satisfied. Per the `WHEN` definition, the statements following `→` form "the flow executed when the condition is satisfied" — with the condition unsatisfied, none of `DELEGATE correction`, `VERIFY correction`, or `TRANSITION "Rework"` execute. Execution then continues, per the default declaration-order Flow rule, to the next statement outside the `WHEN` construct, which is `EMIT review-report`.

> **Note on what the spec leaves undetermined here:** the snippet contains no second `WHEN` (e.g., a `WHEN review.accepted` branch) to handle the accepted case explicitly — unlike the spec's own `WHEN`/`WHEN` pairing example (`tests.passed` / `tests.failed`). The specification does not state what should happen when an outcome is established but no `WHEN` condition matches it; it only defines that a `WHEN`'s flow runs when its stated condition is satisfied. I assume — as the most direct reading of "Statements execute in declaration order unless an explicit control construct changes the flow" — that an unmatched `WHEN` is simply skipped (no flow, no error, no implicit alternative branch), and execution falls through to the next statement in the outer flow, `EMIT review-report`. The spec does not define any "otherwise"/`else` construct, so no such fallback branch can be inferred to exist or to run.
