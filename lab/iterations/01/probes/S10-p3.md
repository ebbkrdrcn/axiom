# Analysis of the DSL Snippet

```text
VERIFY review
WHEN review.rejected
  → DELEGATE correction
      VERIFY correction
  → TRANSITION "Rework"
EMIT review-report
```

Assumption given by the task: `VERIFY review` establishes the outcome `rejected`.

Before answering, one point of ambiguity in the specification needs to be surfaced (see "Assumptions" at the end): the **Conditional Flow** section shows `WHEN` with two `→` lines, but every worked example of `WHEN` in the spec's body uses only a single `→`. The spec never says that multiple `→` entries under a `WHEN` are independent/concurrent branches — that concurrency semantics is explicitly reserved for `FORK` ("Each `→` starts an independent flow... The branches may execute concurrently"). For `WHEN`, the spec only says "The statements following `→` form the flow executed when the condition is satisfied" (singular "the flow"), and the general **Flow** rule says statements execute in declaration order unless an explicit control construct changes that. Since `WHEN` is not documented as introducing concurrency, the two `→` lines under `WHEN` are read here as two sequential statements belonging to **one** conditional flow, not as parallel branches. This is stated explicitly as an assumption below.

---

## 1. Which statements belong to the WHEN flow?

Three statements belong to the `WHEN review.rejected` flow:

- `DELEGATE correction`
- `VERIFY correction` (nested/indented beneath `DELEGATE correction`)
- `TRANSITION "Rework"`

Reasoning: per **Scope**, "Indented statements belong to the preceding scoped construct." Both `→` lines are indented under `WHEN review.rejected`, so both belong to the conditional flow it introduces. `VERIFY correction` is indented one level further, under the `→ DELEGATE correction` line, so it belongs to that statement's own nested scope — the same nesting pattern the spec uses in the `FORK` example (`→ DELEGATE security-review` / `VERIFY security-review`). Since `DELEGATE correction` is itself part of the `WHEN` flow, its nested `VERIFY correction` is transitively part of the `WHEN` flow as well.

`EMIT review-report` is **not** indented under `WHEN`, so it does not belong to this flow (see Q4).

## 2. Are the statements in the WHEN flow executed sequentially or concurrently, and in what order?

Sequentially, in declaration order:

1. `DELEGATE correction`
2. `VERIFY correction`
3. `TRANSITION "Rework"`

The spec attributes concurrent/independent-branch semantics only to `FORK` ("Each `→` starts an independent flow... may execute concurrently... Use `JOIN` when execution must wait"). `WHEN` has no such language and no paired `JOIN`. The general **Flow** rule ("Statements execute in declaration order unless an explicit control construct changes the flow") therefore governs: the two `→` items under `WHEN` are ordered steps of the single flow that runs when the condition holds, not parallel branches.

## 3. Is `VERIFY correction` part of the WHEN flow?

Yes. It is indented directly beneath `→ DELEGATE correction`, which is itself one of the `WHEN` flow's statements. By the **Scope** rule, indentation nests it under `DELEGATE correction`, and since that statement is part of the `WHEN review.rejected` flow, `VERIFY correction` is transitively part of that same flow — it runs as the step following `DELEGATE correction`, evaluating the delegated work's result, before `TRANSITION "Rework"` runs.

## 4. Is `EMIT review-report` part of the WHEN flow? Is it executed?

**Part of the flow:** No. `EMIT review-report` is written at the same indentation level as `VERIFY review` and `WHEN review.rejected` — it is not indented under `WHEN`. Per **Scope**, only indented statements belong to the preceding scoped construct, so `EMIT review-report` is a top-level statement in the outer sequential flow, not a member of the `WHEN` flow.

**Is it executed:** Yes. `WHEN` is "a control construct, not an operation" that conditionally runs its own nested flow; nothing in the spec says a `WHEN` block (taken or not) suppresses subsequent top-level statements, and none of the statements involved (`DELEGATE`, `VERIFY`, `TRANSITION`) are documented as altering control flow the way `BREAK`, `STOP`, or `JOIN` do. Per **Flow**, "Statements execute in declaration order unless an explicit control construct changes the flow," and no such construct (`STOP`, `BREAK`) appears here. So after `VERIFY review` runs and the `WHEN review.rejected` flow (`DELEGATE correction` → `VERIFY correction` → `TRANSITION "Rework"`) completes (since the condition holds by assumption), execution falls through to the next top-level statement, `EMIT review-report`, which runs.

Full execution order under the given assumption (`rejected`):
1. `VERIFY review`
2. `DELEGATE correction`
3. `VERIFY correction`
4. `TRANSITION "Rework"`
5. `EMIT review-report`

## 5. If `VERIFY review` had established `accepted` instead, which statements would execute?

Only:

1. `VERIFY review`
2. `EMIT review-report`

Reasoning: `WHEN review.rejected` guards a specific condition. If the outcome is `accepted` rather than `rejected`, that condition is not satisfied, so per the **WHEN** semantics ("The statements following `→` form the flow executed when the condition is satisfied") none of the flow's statements (`DELEGATE correction`, `VERIFY correction`, `TRANSITION "Rework"`) execute. There is no `WHEN review.accepted` branch defined in this snippet, so no replacement flow is triggered for the `accepted` outcome — the process simply has no conditional work to do at that point. Execution falls through the (untaken) `WHEN` construct to the next top-level statement, `EMIT review-report`, which still executes since it does not depend on the `WHEN` condition.

---

## Assumptions made (where the specification underdetermines the answer)

1. **Sequential vs. concurrent semantics for multiple `→` lines under a single `WHEN`.** The specification's `WHEN` prose and every one of its worked examples show only one `→` per `WHEN` block; the two-`→` form appears only in the abstract **Conditional Flow** syntax box, without commentary on ordering or concurrency. Since concurrency is explicitly and only attributed to `FORK` (with `JOIN` as its counterpart), and since `WHEN` is described as producing "the flow" (singular) for a satisfied condition, this analysis assumes the two `→` statements under `WHEN` are sequential steps of one flow, executed in declaration order, not independent concurrent branches. The spec does not explicitly rule out an alternative reading in which multiple `→` under `WHEN` are themselves independent flows (as in `FORK`); it simply gives no basis for that reading, so it is not adopted here.
2. **Nested-statement attribution under `WHEN`'s `→`.** The spec's only worked example of an indented statement following a `→` is under `FORK`, not `WHEN`. This analysis assumes the same **Scope** rule ("indented statements belong to the preceding scoped construct") applies uniformly regardless of whether the enclosing `→` is inside `FORK` or `WHEN`, so `VERIFY correction` nests under `DELEGATE correction` in the same way it would under a `FORK` branch.
3. **`WHEN` does not block fall-through.** The spec never states directly that execution continues past a `WHEN` block to subsequent top-level statements when the branch is or isn't taken; this is inferred from the general **Flow** rule and from `WHEN` being defined purely as a conditional-execution construct with no stated ability to halt or gate later, unrelated statements the way `STOP`/`BREAK` explicitly do.
