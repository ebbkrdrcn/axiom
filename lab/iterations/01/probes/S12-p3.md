# Step-by-step execution of the go_harness program

## Program under analysis

```text
DELEGATE release-notes
HITL("Approve the release notes?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
TRANSITION "Published"
EMIT release-notes
```

## Reading the program structure (per spec)

- `DELEGATE release-notes` assigns the work of producing release notes to another actor. It does **not** assert that the work is correct, complete, or accepted (spec: "`DELEGATE` does not mean that the work is correct, complete, or accepted").
- `HITL("Approve the release notes?")` establishes a human decision boundary. The human response may determine the subsequent flow (spec, HITL section).
- The `→ FALLBACK` block nested under `HITL` is the flow used "only when the expected response cannot be used to continue the normal flow" (spec, FALLBACK section) — i.e., when the response is unavailable or insufficient.
- `TRANSITION "Published"` and `EMIT release-notes` are **not** nested under `HITL`/`FALLBACK` (no indentation shown relative to the `HITL` statement's own top-level column), so per the Scope rule ("Indented statements belong to the preceding scoped construct") they are the continuation of the **normal** flow — the flow that runs when the `HITL` response *can* be used to continue, i.e., when `FALLBACK` is not invoked.

## Explicit assumptions (the spec does not fully determine these)

The spec is deliberately silent on several mechanics needed to trace this program to completion. I made the following assumptions, each flagged as such:

1. **What makes a human response "usable" vs. "insufficient/unavailable."** The spec defines `HITL`/`FALLBACK` only in terms of whether the response "can be used to continue the normal flow"; it does not define how natural-language text is interpreted as approval, rejection, or neither. I assumed:
   - "Approved." is a clear, unambiguous affirmative decision → usable → normal flow continues.
   - "I haven't had time to look yet." is a response that exists but does not constitute a decision (it neither approves nor rejects) → per FALLBACK's definition ("unavailable **or insufficient**"), this counts as an insufficient response → `FALLBACK` is invoked.
   - No response at all is the clearest case of "unavailable" → `FALLBACK` is invoked. The spec does not say *when* (after how long, or by what detection mechanism) a non-response is deemed "unavailable" — per the semantic principles, `HITL` "defines a human interaction boundary, not the ... communication mechanism," so the exact timing/timeout is left to the runtime and is outside the DSL's scope. I assumed the surrounding process eventually determines the response is unavailable and triggers `FALLBACK` accordingly; the DSL alone does not fix *when*.
2. **No `AUTO` is present in this program**, so there is no automatic resolution path. Per spec, "`HITL` must not be silently replaced by an agent decision unless the surrounding definition explicitly permits automatic resolution through `AUTO`." Since `AUTO` is absent, an agent may not substitute its own judgment for the human's in any of the three runs — this holds even in Run B and Run C, where the response is unusable.
3. **Ordering of the two `→` lines under `FALLBACK`.** The spec's own `FALLBACK` syntax example shows only one `→ <flow>` line under `FALLBACK`, where `<flow>` may itself be a sequence of statements. This task's program instead shows two separate `→` lines (`→ TRANSITION "Blocked"` and `→ STOP`) at the same indentation under `FALLBACK`. The spec defines multiple `→` lines at one indentation level in two different constructs with different meanings: under `WHEN`, multiple `→` lines are sequential statements forming one flow; under `FORK`, multiple `→` lines are independent concurrent branches. `FALLBACK` is not a concurrency construct (nothing in its definition suggests independent branches, and there is no matching `JOIN`), so I assumed the `WHEN` convention applies: the two `→` lines are sequential statements of the single fallback flow, executed in order — first `TRANSITION "Blocked"`, then `STOP`. This is the most consistent reading available, but the spec does not explicitly cover this exact syntactic shape.
4. **`DELEGATE release-notes` never returns an explicit "done" or is `VERIFY`-ed** in this program. The spec pairs `DELEGATE` with `VERIFY` in its own example, but does not require a `VERIFY` step, and this program has none. I assumed the absence of `VERIFY` simply means no evaluation of the delegated work occurs before `HITL` is reached — the DSL does not say `DELEGATE` implies automatic completion or acceptance, so I treat the delegated work as "assigned" and note that the program does not itself establish that the release notes were finished before the human is asked to approve them. This is a gap in the program, not something I can resolve from the spec, so it is simply carried forward as a caveat in the trace below.

With these assumptions stated, here are the three traces.

## Run A — human responds "Approved."

| Step | Statement executed | Effect / notes |
|---|---|---|
| 1 | `DELEGATE release-notes` | Work of producing release notes is assigned to another actor. This does not, by itself, mean the notes are correct or complete (spec). |
| 2 | `HITL("Approve the release notes?")` | A human decision boundary is established; execution reaches a point requiring human input. |
| — | (human responds "Approved.") | Per Assumption 1, this is a clear, usable affirmative response — it can be used to continue the normal flow. `FALLBACK` is therefore **not** invoked (spec: fallback is used "only when the expected response cannot be used to continue the normal flow"). |
| 3 | `TRANSITION "Published"` | The process state changes to `Published`. Per spec, this represents a state change only — it does not itself mean any work was performed. |
| 4 | `EMIT release-notes` | The `release-notes` artifact is produced as an externally meaningful output. The DSL does not prescribe how it is created, stored, or transmitted. |

**Outcome of Run A:** Execution reaches the end of the program normally. Final state: `Published`; artifact `release-notes` emitted. The `FALLBACK` flow (`TRANSITION "Blocked"` / `STOP`) is never executed.

## Run B — human never responds

| Step | Statement executed | Effect / notes |
|---|---|---|
| 1 | `DELEGATE release-notes` | Work of producing release notes is assigned to another actor. |
| 2 | `HITL("Approve the release notes?")` | A human decision boundary is established; execution reaches a point requiring human input and no response arrives. |
| — | (no response ever arrives) | Per Assumption 1, the DSL does not define *when* a non-response becomes "unavailable" (no timeout mechanism is specified — this is explicitly left to the runtime by the semantic principles). Under the assumption that the surrounding process eventually determines the response is unavailable, the response "cannot be used to continue the normal flow," so `FALLBACK` is invoked. |
| 3 | `→ TRANSITION "Blocked"` (inside `FALLBACK`) | Per Assumption 3, this is the first statement of the fallback flow. Process state changes to `Blocked`. |
| 4 | `→ STOP` (inside `FALLBACK`) | Execution terminates entirely (spec: "`STOP` terminates execution... No subsequent statement is executed after `STOP`"). |
| — | `TRANSITION "Published"` | **Not executed** — `STOP` prevents any subsequent statement, and this statement belongs to the normal flow, which was already bypassed once `FALLBACK` was invoked. |
| — | `EMIT release-notes` | **Not executed**, for the same reason. |

**Outcome of Run B:** Execution never receives a usable human decision; the `FALLBACK` flow runs, transitioning the process to `Blocked` and then terminating execution entirely via `STOP`. Final state: `Blocked`. No artifact is emitted, and the process never reaches `Published`. Caveat: the exact point at which "never responds" is recognized as "unavailable" is not determined by the spec (Assumption 1).

## Run C — human responds "I haven't had time to look yet."

| Step | Statement executed | Effect / notes |
|---|---|---|
| 1 | `DELEGATE release-notes` | Work of producing release notes is assigned to another actor. |
| 2 | `HITL("Approve the release notes?")` | A human decision boundary is established; execution reaches a point requiring human input. |
| — | (human responds "I haven't had time to look yet.") | A response is received, but per Assumption 1 it is neither an approval nor a rejection — it does not constitute a decision. This is an **insufficient** response: it exists but "cannot be used to continue the normal flow" (spec, FALLBACK section explicitly covers "unavailable **or insufficient**"). `FALLBACK` is therefore invoked. Per spec, `FALLBACK` "does not authorize the agent to invent a replacement decision" — the agent must not interpret this text as either an approval or a rejection on its own. |
| 3 | `→ TRANSITION "Blocked"` (inside `FALLBACK`) | Per Assumption 3, first statement of the fallback flow executes. Process state changes to `Blocked`. |
| 4 | `→ STOP` (inside `FALLBACK`) | Execution terminates entirely; no subsequent statement executes. |
| — | `TRANSITION "Published"` | **Not executed.** |
| — | `EMIT release-notes` | **Not executed.** |

**Outcome of Run C:** The human did respond, but the response is not a usable decision (it neither approves nor rejects), so it is treated as insufficient and triggers the same `FALLBACK` flow as Run B. Final state: `Blocked`. No artifact is emitted, and the process never reaches `Published`. Note that Run B and Run C produce the same observable outcome under this DSL, even though one is a total non-response and the other is an actual (but non-decisive) reply — the spec's `FALLBACK` definition ("unavailable **or** insufficient") explicitly groups both cases as triggering the same fallback flow.
