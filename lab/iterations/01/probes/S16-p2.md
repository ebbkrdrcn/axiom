# Execution Trace of the `tdd` Process

## Program

```text
LOOP:tdd
  DELEGATE implementation
  DELEGATE tests
  VERIFY tests
  WHEN tests.passed
    → TRANSITION "Review"
    → BREAK
  WHEN tests.failed
    → TRANSITION "Debugging"
    → DELEGATE diagnosis
EMIT source-code
```

Injected events:
- Iteration 1: `VERIFY tests` establishes `failed`.
- Iteration 2: `VERIFY tests` establishes `passed`.

## Step-by-step execution

### Enter `LOOP:tdd` — Iteration 1

1. **`DELEGATE implementation`** — Work on `implementation` is assigned to another actor. Per spec, this only assigns responsibility; it says nothing about the work being correct, complete, or accepted.
2. **`DELEGATE tests`** — Work on `tests` is assigned to another actor, same caveat as above.
3. **`VERIFY tests`** — The result of the delegated `tests` work is evaluated against acceptance criteria. The injected event establishes the outcome `tests.failed`. (Per spec, completion of delegated work is not equivalent to successful verification, and verification establishes an outcome usable by `WHEN`.)
4. **`WHEN tests.passed`** — Condition is not satisfied (the established outcome is `failed`, not `passed`). `WHEN` itself performs no work; since the condition is false, the flow under it (`TRANSITION "Review"`, `BREAK`) is not executed.
5. **`WHEN tests.failed`** — Condition is satisfied. Its flow executes:
   - **`TRANSITION "Debugging"`** — The process state changes to `Debugging`. This is a state change only; no work is performed by this statement itself.
   - **`DELEGATE diagnosis`** — Work on `diagnosis` is assigned to another actor.
6. End of the loop body is reached for this pass. No `BREAK` or `STOP` occurred, so per the `LOOP` semantics ("the loop continues until `BREAK`, `STOP`, or another explicit control flow terminates it" and "does not imply any particular number of iterations"), the loop repeats from the top of its body.

*(State after iteration 1: process state = `Debugging`.)*

### `LOOP:tdd` — Iteration 2

7. **`DELEGATE implementation`** — Work on `implementation` is (re-)assigned, as the full loop body is re-executed.
8. **`DELEGATE tests`** — Work on `tests` is (re-)assigned.
9. **`VERIFY tests`** — Evaluation of the `tests` result. The injected event establishes the outcome `tests.passed`.
10. **`WHEN tests.passed`** — Condition is satisfied. Its flow executes:
    - **`TRANSITION "Review"`** — The process state changes to `Review`.
    - **`BREAK`** — Exits the current loop (`tdd`) immediately. Per spec, `BREAK` only exits the loop scope; it does not terminate the entire execution.
11. Because `BREAK` exits the loop scope immediately, execution transfers directly out of `LOOP:tdd` to the statement following the loop. The remaining statement inside the loop body, **`WHEN tests.failed`**, is not reached/evaluated in this pass — `BREAK` already ended the loop's execution before control would reach it.

*(State after iteration 2: process state = `Review`.)*

### After the loop

12. **`EMIT source-code`** — An artifact, `source-code`, is produced. `EMIT` represents an externally meaningful output; the DSL does not prescribe how it is created, stored, or transmitted.
13. No further statements remain in the program, and no `STOP` was ever reached. Execution ends because the statement sequence is exhausted (see "Assumptions" below).

## Final process state

**`Review`** — set by `TRANSITION "Review"` during iteration 2, and not altered afterward (the loop was exited via `BREAK` immediately after, and `EMIT source-code` does not change process state).

## Explicit assumptions (where the specification does not determine behavior)

1. **Loop repetition mechanics.** The spec states `LOOP` "continues until `BREAK`, `STOP`, or another explicit control flow terminates it" and "does not imply any particular number of iterations," but it does not explicitly spell out that reaching the end of the loop body (with no terminating construct triggered) causes control to return to the top of the body for another pass. I assumed this standard loop re-entry behavior, since it is the only reading consistent with "the loop continues."
2. **Effect of `BREAK` on sibling statements in the same scope.** The spec says `BREAK` "exits the current `LOOP`," which I read as an immediate transfer of control out of the loop scope. Consequently, the second `WHEN tests.failed` block — which follows the first `WHEN` block in the same loop body — is never evaluated in iteration 2, since the loop has already been exited before execution would reach it. The spec does not explicitly state whether sibling statements after a `BREAK`-triggering branch are skipped or not; I assumed they are skipped, treating `BREAK` as an immediate, unconditional exit rather than something that takes effect only at the "natural" end of the loop body.
3. **Mutual exclusivity of `tests.passed` / `tests.failed`.** The spec's own example (`WHEN implementation.accepted` / `WHEN implementation.rejected`) shows `VERIFY` establishing one outcome among named alternatives usable by different `WHEN` constructs. I assumed `tests.passed` and `tests.failed` are likewise mutually exclusive outcomes of `VERIFY tests`, and that only the `WHEN` matching the currently-established outcome has its flow executed (the spec states "Multiple `WHEN` constructs may describe different outcomes of the same process state" and that `WHEN` does not itself perform work).
4. **Termination when statements are exhausted.** The spec defines `STOP` as what terminates execution, but it does not state what happens when the statement sequence simply runs out without an explicit `STOP`. I assumed execution ends naturally once there are no further statements to execute (i.e., `STOP` is presented as a way to terminate early/explicitly, not as mandatory for every program to end).
5. **`DELEGATE diagnosis` (iteration 1) is left unverified.** The spec does not require every `DELEGATE` to be paired with a `VERIFY`; since the program text contains no `VERIFY diagnosis`, I assumed this delegated work simply remains outstanding/unevaluated within the DSL's terms and does not itself affect subsequent control flow.
6. **Re-delegation identity across iterations.** The spec does not state whether repeating `DELEGATE implementation` / `DELEGATE tests` in iteration 2 refers to new work or continuation of the same work item. This does not affect the control-flow trace, but is noted as underdetermined by the spec (`DELEGATE` "defines responsibility, not execution mechanics").
