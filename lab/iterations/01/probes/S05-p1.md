# go_harness DSL Snippet Review

## Snippet A

```text
HITL("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

**Verdict: INVALID**

**Rule cited (AUTO section):**

> `AUTO` is not a control-flow container.
> It does not contain `WHEN`, `→`, or an arbitrary flow.
> Uncertainty is not a DSL condition, state, variable, or keyword.
>
> For example, the following is invalid:
> ```text
> AUTO
>   WHEN decision.uncertain
>     → HITL("Approve release?")
> ```

**What is wrong:**

Snippet A's `AUTO` block is, statement-for-statement, the exact construct the specification names as an invalid example. It nests a `WHEN` conditional (with a `→` branch) inside `AUTO`, which the spec explicitly forbids: "`AUTO` is not a control-flow container. It does not contain `WHEN`, `→`, or an arbitrary flow."

It also violates the rule that "Uncertainty is not a DSL condition, state, variable, or keyword." The condition `decision.uncertain` treats runtime uncertainty as something the DSL author can branch on, but the spec states uncertainty determination is internal to the `AUTO` runtime resolution ("The DSL runtime determines uncertainty as part of automatic decision resolution"), not something exposed to `WHEN`.

**What would happen / what is misunderstood:**

The author appears to be trying to express "if the automatic decision is uncertain, ask the human again," but that behavior is already what `AUTO` *means* by definition — "Resolve automatically when sufficiently determined; otherwise require human input." The correct way to express this is simply to write `AUTO` with no nested flow; the fallback-to-human behavior on uncertainty is intrinsic to `AUTO`'s semantics and does not need (and must not be expressed as) an explicit `WHEN`/`→` branch. A runtime encountering this snippet cannot execute it as written because `AUTO` has no defined semantics for containing sub-statements — it would have to reject/refuse the construct rather than "run" it.

Note: the leading `HITL("Approve release?")` statement is not itself flagged as invalid by the spec (a bare `HITL` is legal, and `FALLBACK` association is only shown as an example, not mandated for every `HITL`), but its relationship to the following `AUTO` block is undefined by the spec — the two statements are not connected by any control construct, so it is unclear (and the spec does not say) whether the `AUTO` is meant to resolve the same decision the `HITL` just requested. This is left ambiguous by the specification.

## Snippet B

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

**Verdict: INVALID** (as a standalone snippet)

**Rule cited (BREAK section):**

> Exits the current `LOOP`.
> `BREAK` does not terminate the entire execution.
> `BREAK` may only exit a loop scope.
> Use `STOP` to terminate the entire execution.

**What is wrong:**

The `DELEGATE implementation` / `VERIFY implementation` / `WHEN implementation.rejected → ...` portion is well-formed and mirrors the specification's own example almost exactly (compare to the spec's `VERIFY implementation` / `WHEN implementation.accepted → BREAK` / `WHEN implementation.rejected → DELEGATE correction` example). `DELEGATE` assigns the work, `VERIFY` evaluates it, and `WHEN` branches on the outcome — all consistent with the rules for those constructs.

The problem is `BREAK`. Per the "Scope" and "Flow" syntax rules, indentation determines nesting: a statement belongs to "the preceding scoped construct," and `LOOP:<name> ... ` is the only construct defined as establishing a loop scope. As written, Snippet B contains no `LOOP:<name>` header at all — `DELEGATE`, `VERIFY`, and `WHEN` are all at the top level (unindented), so there is no enclosing loop scope for `BREAK` to exit. This directly conflicts with "`BREAK` may only exit a loop scope" — there is no current loop for it to exit.

**What would happen:**

Since `BREAK` "does not terminate the entire execution" (that is `STOP`'s role) and it "may only exit a loop scope," a `BREAK` with no enclosing `LOOP` has no defined target and no defined effect under this specification. The runtime cannot legally treat it as a no-op, as equivalent to `STOP`, or as exiting some outer scope, because the spec defines none of those behaviors for it. The snippet is therefore invalid for lack of a `LOOP` scope to `BREAK` out of.

**Assumption stated:** The specification's "Scope" rule says indented statements belong to "the preceding scoped construct," which implies scope membership is determined structurally from what literally precedes a statement in the text. Since the task presents Snippet B as a complete, self-contained snippet with no `LOOP:<name>` line above it, I assumed it should be evaluated as written (i.e., not assumed to be an excerpt silently nested inside a `LOOP` defined elsewhere). If Snippet B were understood to be an indented excerpt from inside some unshown `LOOP:<name>` block, then the `BREAK` would be valid; the specification does not say whether a "snippet" should be read as necessarily complete or as a possible excerpt of a larger program, so this is an explicit assumption on my part rather than something the spec determines.
