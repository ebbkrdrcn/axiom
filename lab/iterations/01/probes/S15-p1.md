# Execution Trace

## Program

```text
FORK
  → DELEGATE lint
      VERIFY lint
      WHEN lint.rejected
        → STOP
  → DELEGATE docs
      EMIT docs
JOIN
EMIT build
```

## Relevant spec rules used

- **FORK**: "Each `→` starts an independent flow... The branches may execute concurrently."
- **JOIN**: "Execution continues only after all required forked flows have completed."
- **STOP**: "Terminates execution... No subsequent statement is executed after `STOP`."
- **BREAK** (used only by contrast): "`BREAK` does not terminate the entire execution... `BREAK` may only exit a loop scope. Use `STOP` to terminate the entire execution." — the spec deliberately scopes `BREAK` to "the current loop" while leaving `STOP` unscoped ("terminates execution", "the entire execution"). This asymmetry is the basis for treating `STOP` as global rather than branch-local (see Assumption A below).
- **WHEN**: "a control construct, not an operation... does not itself perform work."
- **VERIFY**: "Verification may establish outcomes that can be used by `WHEN`."
- **DELEGATE**: "does not mean that the work is correct, complete, or accepted" — i.e. `DELEGATE docs` having executed does not mean the docs work, or the docs branch, is finished.

## Step-by-step

1. **FORK** starts two independent, concurrent flows:
   - Branch **A** (lint): `DELEGATE lint` → `VERIFY lint` → `WHEN lint.rejected → STOP`
   - Branch **B** (docs): `DELEGATE docs` → `EMIT docs`

2. Branch A executes `DELEGATE lint` (work assigned to an actor).
   Branch B executes `DELEGATE docs` (work assigned to an actor).

3. Per the injected events, by the time Branch A's `VERIFY lint` produces its outcome, Branch B has completed `DELEGATE docs` but has **not yet** executed its next statement, `EMIT docs`. So at this instant, Branch B is paused between its two statements.

4. Branch A executes `VERIFY lint`. This is an evaluation, not a pass-through of the delegated result ("Completion of delegated work is not equivalent to successful verification"). It establishes the outcome `lint.rejected`.

5. Branch A evaluates `WHEN lint.rejected`. The condition is satisfied (matches the outcome `VERIFY` just established), so its flow (`→ STOP`) is taken. `WHEN` itself performs no work — it only routes control to `STOP`.

6. Branch A executes `STOP`.
   - By spec, `STOP` "terminates execution" — full stop, with no scope qualifier — and this is explicitly what distinguishes it from `BREAK`, which the spec restricts to "the current loop scope." Since `STOP` carries no such restriction, and the spec calls out `STOP` as the construct that "terminate[s] the entire execution" (in direct contrast to `BREAK`), `STOP` here terminates the whole program's execution, not merely Branch A's flow.
   - "No subsequent statement is executed after `STOP`" — unqualified by branch, loop, or flow. This is read as applying to the execution as a whole, including flows running concurrently with the one that issued `STOP`.

7. Consequence for Branch B: `EMIT docs` is a statement that has not yet executed at the moment `STOP` takes effect. Under the global-termination reading of `STOP` (step 6), it is a "subsequent statement" relative to the point of termination and therefore **is not executed**. Branch B's flow is left incomplete (it never reaches `EMIT docs`).

8. Consequence for `JOIN`: `JOIN` requires "all required forked flows have completed." Branch B never completes (it is cut off before its final statement), and in any case execution as a whole has already been terminated by `STOP` before the runtime would reach evaluating `JOIN`'s wait condition. Either way, `JOIN`'s completion condition is never satisfied, so **`JOIN` does not complete**.

9. Consequence for `EMIT build`: this statement is declared after `JOIN` in the outer flow ("Statements execute in declaration order unless an explicit control construct changes the flow"). Since `JOIN` never completes and the overall execution has already been terminated by `STOP`, control never reaches this statement, so **`EMIT build` is not executed**.

## Answers

- **Is `EMIT docs` executed?** No. `STOP`, triggered in the lint branch, terminates the entire execution before Branch B reaches `EMIT docs`; Branch B is left having executed only `DELEGATE docs`.
- **Is `JOIN` completed?** No. `JOIN`'s stated condition ("all required forked flows have completed") is never met — the docs branch does not finish, and execution is terminated beforehand — so `JOIN` never completes.
- **Is `EMIT build` executed?** No. It is reachable only after `JOIN` completes, which never happens, and execution has already ended via `STOP`.

## Assumptions / places the specification underdetermines the answer

- **Assumption A — scope of `STOP` under `FORK`.** The specification never explicitly states what happens when `STOP` occurs inside one branch of a `FORK` while sibling branches are still mid-flight. I inferred a *global* scope for `STOP` from the explicit contrast the spec draws with `BREAK`: `BREAK` is expressly restricted ("may only exit a loop scope"), while `STOP` is described only as terminating "execution" / "the entire execution," with no scope restriction given at all. This asymmetry is the strongest textual signal available, and it is what the above trace relies on.
  - *Alternative reading:* one could instead read `STOP` as terminating only the flow it lexically belongs to (i.e., just Branch A), since `FORK`'s branches are declared "independent." Under that narrower reading, whether `EMIT docs` still runs would depend on runtime scheduling/timing that the spec does not define at all (it only says branches "may execute concurrently," with no statement about preemption, atomicity, or a global halt signal). The spec gives no mechanism for an alternative interpretation to actually determine an outcome — it would remain undetermined by the text. I therefore treat Assumption A's global reading as the one the specification most directly supports, and used it to produce a determinate answer.
- **Under either reading, `JOIN` does not complete and `EMIT build` is not executed**, because `JOIN`'s completion is contingent on the docs branch itself finishing (reaching `EMIT docs`), and nothing in the trace ever gets Branch B past `DELEGATE docs`.
- **Definition of "completed" for a forked flow that hits `STOP` is not given.** The specification does not say whether a branch that is terminated via `STOP` (rather than running off the end of its statements) counts as "completed" for `JOIN`'s purposes. This does not affect the answers above, since Branch B (docs) never executes `STOP` at all — it simply never gets the chance to finish — but it is a gap in the spec worth flagging for the lint branch itself.
- **No retroactive/cancellation semantics are defined.** The spec does not say whether already-dispatched work (e.g., the `DELEGATE docs` assignment, which "assigns work to an actor") is cancelled, left dangling, or otherwise handled once `STOP` occurs. I assumed only that the *DSL statement* `EMIT docs` does not execute; the spec gives no basis for reasoning about the real-world state of the delegated docs actor/work itself.
