# Execution Trace of the `DSL` Program

## Assumptions made where the specification does not fully determine behavior

The specification defines what each keyword *means* but leaves several mechanical details of program execution unstated. To produce a concrete step-by-step trace, the following assumptions were made explicitly:

1. **Loop re-entry.** The spec says only that "`LOOP` continues until `BREAK`, `STOP`, or another explicit control flow terminates it" and "does not imply any particular number of iterations." It does not explicitly say what happens when the end of the loop body is reached without hitting `BREAK`/`STOP`. The natural reading (and the only one consistent with "continues until...") is assumed: if the body runs to completion without an explicit terminator, the loop body is re-executed from its first statement (i.e., `DELEGATE implementation` and `DELEGATE tests` are redone on iteration 2, not skipped).
2. **Mutual exclusivity of `WHEN` outcomes.** The spec states "Multiple `WHEN` constructs may describe different outcomes of the same process state" but does not state whether they are evaluated as an exclusive dispatch or independently. Since the injected events establish a single outcome per `VERIFY` (`failed` in iteration 1, `passed` in iteration 2), it is assumed each `WHEN` is checked in declaration order and only the `WHEN` whose condition matches the established outcome executes its flow; the other is checked and simply does not match (its condition is false), so nothing happens for it.
3. **Effect of `BREAK` on sibling statements.** The spec says `BREAK` "exits the current `LOOP`." It does not explicitly say whether statements that textually follow the branch containing `BREAK`, but are still inside the same loop scope (here, the second `WHEN tests.failed` block), are evaluated first. It is assumed that once `BREAK` executes, the loop scope is exited immediately, so no further statements belonging to that loop scope (including the second `WHEN`) are evaluated.
4. **`DELEGATE diagnosis` has no explicit `VERIFY`.** The task's DSL never verifies the diagnosis, so it is treated as delegated work whose completion/acceptance is simply not evaluated within this program — consistent with "`DELEGATE` does not mean that the work is correct, complete, or accepted," and no further meaning is assumed for it.
5. **End of program.** After the loop is exited and `EMIT source-code` runs, there are no further statements and no `STOP` was reached. It is assumed execution simply ends when the statement list is exhausted (a "natural" end), since `STOP` is only needed to terminate execution *before* the end of the program; nothing in the spec requires an explicit `STOP` for the program to end at its last statement.

## Step-by-step execution

### LOOP:tdd — Iteration 1

1. `DELEGATE implementation` — Work of implementing is assigned to another actor. This does not itself mean the implementation is complete or correct.
2. `DELEGATE tests` — Work of writing/producing tests is assigned to another actor.
3. `VERIFY tests` — The tests result is evaluated against acceptance criteria. Per the injected event for this iteration, this evaluation establishes the outcome `tests.failed`.
4. `WHEN tests.passed` — Condition checked against the established outcome (`failed`). Condition is not satisfied; this `WHEN`'s flow (`TRANSITION "Review"`, `BREAK`) does **not** execute.
5. `WHEN tests.failed` — Condition checked against the established outcome (`failed`). Condition **is** satisfied; this `WHEN`'s flow executes:
   - `TRANSITION "Debugging"` — The process state changes to `Debugging`. (No work is performed by this statement itself — it only records a state change.)
   - `DELEGATE diagnosis` — Work of diagnosing the failure is assigned to another actor.
6. End of loop body reached. No `BREAK` or `STOP` occurred during this iteration, so (per Assumption 1) the loop continues and the body is re-executed.

### LOOP:tdd — Iteration 2

7. `DELEGATE implementation` — Implementation work is (re-)assigned to another actor.
8. `DELEGATE tests` — Test work is (re-)assigned to another actor.
9. `VERIFY tests` — The tests result is evaluated again. Per the injected event for this iteration, this evaluation establishes the outcome `tests.passed`.
10. `WHEN tests.passed` — Condition checked against the established outcome (`passed`). Condition **is** satisfied; this `WHEN`'s flow executes:
    - `TRANSITION "Review"` — The process state changes to `Review`.
    - `BREAK` — Exits the current loop (`LOOP:tdd`) immediately.
11. Because `BREAK` has exited the loop scope (per Assumption 3), the second construct, `WHEN tests.failed`, belongs to the now-exited loop scope and is **not** evaluated in this iteration.
12. The `LOOP:tdd` scope has ended (exited via `BREAK`, not by exhausting iterations — `BREAK` does not terminate the entire execution, only the loop).

### After the loop

13. `EMIT source-code` — The next statement in the enclosing flow after `LOOP:tdd` executes: an externally meaningful output/artifact (`source-code`) is produced. The DSL does not prescribe how this artifact is created, stored, or transmitted.
14. No further statements remain in the program, and no `STOP` was reached. Execution ends (per Assumption 5) because the statement list is exhausted.

## Final process state

**`Review`**

This was the last (and only surviving) `TRANSITION` to take effect: it was set in iteration 2 immediately before `BREAK` exited the loop, and nothing after it (`EMIT source-code`, or any other `TRANSITION`) changed the state again. The earlier `TRANSITION "Debugging"` from iteration 1 was superseded by this later transition.
