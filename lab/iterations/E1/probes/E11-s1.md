# go_harness program for TASK-0100

```text
t1:Task = TASK-0100
a1:ADR = t1.adr
LOOP:work
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.accepted
    → TRANSITION t1 "Review"
    → BREAK
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"
HITL:done[approved, rejected]("Is TASK-0100 done?")
WHEN done.approved
  → TRANSITION t1 "Done"
WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Assumptions

1. **Bindings.** `t1:Task = TASK-0100` and `a1:ADR = t1.adr` are the two bindings the requirement asks for ("the ADR linked to the task must be bound as well"). Per the fixtures, `TASK-0100.adr = ADR-0100`, so the relation binding resolves; if the task had no `adr` field, the binding would fail and execution would end (as with `STOP`) before any other statement, per V11/binding rules. `a1` is bound but not otherwise used, since the requirement does not ask any operation on the ADR — this is allowed (a binding just makes the entity available under a name).
2. **Loop and verification cycle.** "repeatedly have the rate limiter implemented and verify the task, until the verification accepts it" is modeled as `LOOP:work` with `DELEGATE implementation` then `VERIFY t1`, using `WHEN t1.accepted → BREAK` to end the loop, matching the DSL's canonical `LOOP` example.
3. **Rejected branch.** "move the task to Debugging, have a diagnosis done, and move it back to InProgress before trying again" is the `WHEN t1.rejected` flow: `TRANSITION t1 "Debugging"`, `DELEGATE diagnosis`, `TRANSITION t1 "InProgress"`. These transitions are declared by the Task Definition (`InProgress → Debugging` on `verified: rejected`, `Debugging → InProgress` on `none`) and their preconditions hold at that point in the flow.
4. **Undecidable verification.** "If a verification cannot decide, set the process state to Blocked and stop" is placed as the `FALLBACK` of `VERIFY t1` (not of the entity `TRANSITION`), since the requirement's "cannot decide" describes exactly `VERIFY`'s undetermined-outcome failure mode. The fallback is `TRANSITION "Blocked"` (process state, per the quoted phrase "process state") followed by `STOP`, satisfying rule V8 (fallback must end in `STOP`/`BREAK`).
5. **Move to Review after acceptance.** `TRANSITION t1 "Review"` is placed inside the `WHEN t1.accepted` flow, immediately after the loop's own `VERIFY t1` established `accepted`, so its precondition `verified: accepted` holds. It is placed before `BREAK` since the requirement says the review transition happens right "after acceptance," as part of leaving the loop.
6. **Human decision.** "ask the human whether it is done" is modeled as a plain `HITL:done[approved, rejected]("Is TASK-0100 done?")` with no `AUTO`, because the requirement does not indicate the agent may ever decide this itself, and the Task Definition's `Review → Done` transition requires a `human: approved` precondition, which (per the DSL) can only be satisfied by a `HITL` without `AUTO`.
7. **No `FALLBACK` on the `HITL`.** The requirement only specifies "approved" and "rejected" outcomes and does not describe what happens if the human's answer is insufficient or unavailable; per the DSL's default behavior, an unanswered/insufficient `HITL` with no `FALLBACK` simply ends execution (as with `STOP`). This is left unhandled by choice, since the requirement gives no instruction for that case.
8. **Final transitions.** `WHEN done.approved → TRANSITION t1 "Done"` uses the `Review → Done` transition (precondition `human: approved`, satisfied because this `TRANSITION` is inside the flow of `WHEN done.approved` for a `HITL:done` without `AUTO`). `WHEN done.rejected → TRANSITION t1 "InProgress"` uses the `Review → InProgress` transition (precondition `none`), matching the requirement "if the human rejects, move it back to InProgress."
9. **No `REQUIRE`.** The requirement does not mention any precondition resource (e.g. repository access) to require before starting, so none is included.
10. **HITL name uniqueness.** The name `done` is not otherwise bound as an entity name in this program, satisfying V7/V12.
