# Solution for E11

## Program

```text
t1:Task = TASK-0100
a1:ADR = t1.adr
LOOP:verify-loop
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.accepted
    → BREAK
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"
TRANSITION t1 "Review"
HITL:done[approved, rejected]("Is TASK-0100 done?")
WHEN done.approved
  → TRANSITION t1 "Done"
WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Assumptions

1. **Entity availability**: TASK-0100 exists, is of type Task, is structurally valid, is in InProgress status, and has ADR-0100 linked via the `adr` field. ADR-0100 exists, is of type ADR, and is structurally valid.

2. **Delegated work**: The actors performing `DELEGATE implementation` and `DELEGATE diagnosis` will eventually produce results that enable `VERIFY t1` to make a determination.

3. **Verification criteria**: The Task Definition's verification criteria for TASK-0100 are sufficient and non-contradictory. Evidence for each Acceptance Criteria item is available when the task is ready for verification. If criteria are missing, ambiguous, or evidence is unavailable, the VERIFY fails and triggers the FALLBACK (as required).

4. **Human response**: The human will provide a usable answer to the HITL (either "approved" or "rejected" corresponding to one of the declared answers).

5. **Transition preconditions**: 
   - InProgress → Review requires `verified: accepted`, which is satisfied by the VERIFY in the loop before BREAK.
   - InProgress → Debugging requires `verified: rejected`, which is satisfied by the VERIFY in the loop when rejected.
   - Debugging → InProgress requires `none`, always satisfied.
   - Review → Done requires `human: approved`, satisfied because the TRANSITION is inside the flow of WHEN done.approved for a HITL without AUTO.
   - Review → InProgress requires `none`, always satisfied.

6. **Process state**: The process state is "Blocked" only if a VERIFY cannot determine an outcome. Otherwise, the process transitions through implicit states (no `TRANSITION "<state>"` before the BLOCKED fallback).

## Validation Summary

The program satisfies all DSL validity rules (V1–V12):
- Bindings are at the top, unindented, before all statements
- BREAK is inside a LOOP (not crossing FORK boundaries)
- WHEN conditions test outcomes from VERIFY and HITL
- No duplicate names or misused bound names
- FALLBACK ends with STOP
- All entity transitions use bound names and declared statuses
