# Validity Check of Snippets A–D

## Snippet A

```
t1:Task = TASK-0100
LOOP:work
  a1:ADR = t1.adr
  VERIFY t1
  WHEN t1.accepted
    → BREAK
```

**INVALID — breaks V11.**

`a1:ADR = t1.adr` is a binding, but it appears indented inside the body of `LOOP:work`, not at the top of the program before every other statement. Rule V11 states a binding is INVALID if "it is indented, or follows a statement that is not a binding". Here the binding both is indented and follows `LOOP:work` (a non-binding statement). Per the DSL, "Bindings are written at the top of the program, before every other statement, without indentation" (rule V11), and the same is echoed in the Entity Model example of INVALID usage ("Binding inside a scoped construct (V11)").

## Snippet B

```
a1:ADR = t1.adr
t1:Task = TASK-0100
VERIFY a1
```

**INVALID — breaks V11.**

The first binding, `a1:ADR = t1.adr`, is a relation binding whose base name is `t1`. But `t1` is not bound until the *next* line — it has not been bound on an earlier line. Rule V11 states a binding is INVALID if "its relation starts from a name not bound on an earlier line." This is exactly that case, independent of the fact that `t1` does get bound later in the program.

## Snippet C

```
t1:Task = TASK-0102
TRANSITION t1 "Done"
```

**VALID — breaks no rule.**

Structurally this program is well-formed: `t1` is bound once, unindented, at the top of the program (satisfying V11), and `TRANSITION t1 "Done"` refers to the bound name `t1` (satisfying V12). No `WHEN`, `HITL`, `FORK`/`JOIN`, or `BREAK` appears, so V1–V10 are not implicated.

Whether the transition actually *succeeds* at execution time is a separate, non-validity question. Per the fixture, `TASK-0102` has `status: Todo`, and the Task Definition's transition table only declares `Todo → InProgress` from `Todo` — there is no declared `Todo → Done` change. This mirrors the Entity Model's own "Invalid Usage" example ("Undeclared transition... The program is well-formed, but from `InProgress` the Task Definition does not declare `Done`, so the `TRANSITION` fails when executed"). So this `TRANSITION` will *fail* when executed (per dsl.md's Failures table: "the status or change is not declared... → its FALLBACK runs; if none, execution ends"), but a runtime failure of a well-formed statement does not make the *program* INVALID. There is no `FALLBACK` attached here, so execution would end (as with `STOP`) when this statement is run — but that is an execution-time outcome, not a validity verdict.

## Snippet D

```
t1:Task = TASK-0100
HITL:t1[approved, rejected]("Done?")
TRANSITION t2 "Done"
```

**INVALID — breaks V12 (twice).**

1. The name `t1` is bound as an entity (`t1:Task = TASK-0100`) and then reused as a `HITL` name (`HITL:t1[...]`). Rule V12 states it is INVALID if "a bound name is used as a `HITL` name." This is exactly that situation — the binding rule in the Entity Model also states "A bound name must not be used as a `HITL` name."

2. `TRANSITION t2 "Done"` refers to the name `t2`, which is never bound anywhere in the program (only `t1` is bound). Rule V12 states it is INVALID if "`TRANSITION <name> "<status>"` uses a name that is not bound." This is the same situation as the spec's own example of INVALID usage: "An entity `TRANSITION` on a name that is not bound (V12): `TRANSITION t2 "Done"`."

Both defects fall under V12, so the program is INVALID for two independent V12 violations.
