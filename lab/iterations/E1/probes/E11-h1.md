# go_harness DSL Program for TASK-0100

## Program

```
t1:Task = TASK-0100
a1:ADR = t1.adr

LOOP:work
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.accepted
    → BREAK
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"

TRANSITION t1 "Review"
HITL:done[approved, rejected]("Is TASK-0100 done?")
  → FALLBACK
      → TRANSITION t1 "InProgress"
      → STOP
WHEN done.approved
  → TRANSITION t1 "Done"
WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Assumptions

1. **Implementation availability:** The delegated work "implementation" represents completing the rate limiter and will be available for the runtime to execute.

2. **Diagnosis availability:** The delegated work "diagnosis" represents identifying and documenting issues found during verification and is available for the runtime to execute.

3. **Verification outcomes:** The `VERIFY t1` statement will result in exactly one outcome:
   - `accepted`: all acceptance criteria are satisfied with evidence
   - `rejected`: at least one criterion is not satisfied
   - failure (cannot decide): evidence is unavailable or criteria are ambiguous, which triggers the FALLBACK

4. **Human responsiveness:** The human will eventually provide a response to the HITL asking whether the task is done. If the response is insufficient or unavailable and there is no FALLBACK, execution ends; the FALLBACK here moves the task back to InProgress.

5. **Task preconditions:** All status transitions respect the Task Definition's preconditions:
   - InProgress → Review requires verified: accepted (satisfied by the loop)
   - Review → Done requires human: approved (satisfied by the WHEN inside the HITL context)
   - Both can return to InProgress (always allowed)

6. **Entity validity:** TASK-0100 exists, is of type Task, is structurally valid, has status InProgress, and its linked ADR field points to ADR-0100, which exists and is valid.

7. **Process state changes:** The process state remains "none" until a TRANSITION sets it explicitly. The Blocked state is set only if verification cannot determine an outcome.

8. **Loop termination:** The loop terminates on accepted outcome via BREAK, not by failure or external intervention.
