# Solution for E11

## DSL Program

```
t1:Task = TASK-0100
a1:ADR = t1.adr

LOOP:implement
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"
  WHEN t1.accepted
    → TRANSITION t1 "Review"
    → BREAK

HITL:done[approved, rejected]("Is TASK-0100 done?")
WHEN done.approved
  → TRANSITION t1 "Done"
WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Assumptions

1. **Entity existence and validity**: TASK-0100 and ADR-0100 both exist, are of the correct types (Task and ADR respectively), and are structurally valid per their Templates.

2. **Relation binding**: TASK-0100 has the `adr` field set to `ADR-0100`, satisfying the relation binding `a1:ADR = t1.adr`.

3. **Initial status**: TASK-0100 starts in the `InProgress` status (as shown in the fixture).

4. **Transition validity**: All status transitions follow the Task Definition:
   - `InProgress → Review` (requires `verified: accepted`)
   - `InProgress → Debugging` (requires `verified: rejected`)
   - `Debugging → InProgress` (no precondition)
   - `Review → Done` (requires `human: approved`)
   - `Review → InProgress` (no precondition)

5. **Delegated work availability**: The actors performing `implementation` and `diagnosis` work will deliver their results to the process.

6. **Verification decidability**: The verification criteria in the Task Definition (Acceptance Criteria items) can be evaluated to either `accepted` or `rejected`. If undecidable (criteria missing, contradictory, or evidence unavailable), the FALLBACK executes as specified.

7. **Human interaction**: The human answering the HITL question will provide either `approved` or `rejected`, matching one of the declared answers. The human will not provide an insufficient or ambiguous response.

8. **Process state**: The process has no pre-existing state; the initial state is `none`. The FALLBACK may set it to `"Blocked"` if verification fails.

9. **Outcome persistence**: Outcomes established by `VERIFY t1` and `HITL:done` persist within the execution scope, allowing subsequent `WHEN` conditions to test them.
