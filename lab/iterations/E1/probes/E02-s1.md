# Execution of the program against the fixtures

```text
t1:Task = ADR-0100
TRANSITION "Started"
DELEGATE work
```

## 1. Validity verdict

**VALID.**

Checking V1–V12 against the program as written:

- The single line is a binding (`t1:Task = ADR-0100`), unindented, at the top of the program, before every other statement, and `t1` is not bound anywhere else → V11 is satisfied.
- `t1` is not used as a `HITL` name anywhere → V12 is satisfied (the second clause of V12, "a bound name is used as a `HITL` name," does not apply either).
- There is no `TRANSITION <name> "<status>"` on an unbound name (the only `TRANSITION` in the program is the process-state form `TRANSITION "Started"`, which takes no name) → the first clause of V12 does not apply.
- There is no `BREAK`, `FORK`, `JOIN`, `WHEN`, `HITL`, `FALLBACK`, or indentation beyond the flat top-level list → V1–V10 have nothing to violate.

The program is syntactically well-formed. (Whether the binding can actually be *satisfied* at run time is a separate, execution-time question — see below; per the spec, a binding that cannot be satisfied, e.g. a type mismatch, is explicitly *not* a validity violation, only a runtime failure — see `entity-model.md`, "Invalid Usage": "Type mismatch. The program is well-formed, but the binding is not satisfied.")

## 2. Execution trace

Per rule 11 of the Execution rules, bindings are resolved first, top to bottom. Resolving `t1:Task = ADR-0100`:

- The interpreter looks up the entity whose identity is `ADR-0100`. Exactly one representation declares that identity: `docs/adr/ADR-0100.md`.
- Its front matter states `type: ADR`.
- The binding declares `<Type>` as `Task`.
- The entity's declared type (`ADR`) does not match the declared type of the binding (`Task`).

Per **Binding** in `dsl.md` ("Exactly one entity has the identity, it is of type `<Type>`, ... The name refers to that entity" vs. "Anything else → Execution ends, as with `STOP`. No statement after the bindings runs.") and per **Failures** ("binding: fails when it is not satisfied; then execution ends, as with `STOP`"), this binding fails. A binding has no `FALLBACK` form in the grammar, so there is nothing to run instead; execution simply ends.

```trace
1. t1:Task = ADR-0100 -> failed: ADR-0100 is type ADR, not Task; stop
2. (end of program) -> end
```

`TRANSITION "Started"` and `DELEGATE work` are never reached — they are statements after the (failing) binding, and "No statement after the bindings runs."

## 3. Final status of bound entities / files changed

- `t1` was never successfully bound: the binding was not satisfied (type mismatch), so `t1` does not refer to any entity for the rest of the (non-existent) execution.
- No entity was read for data purposes beyond identity/type resolution, no `VERIFY` or `TRANSITION <name> "<status>"` ran, and no `DELEGATE` ran.
- **No entity files changed.** In particular:
  - `docs/adr/ADR-0100.md` is unchanged (still `status: Accepted`).
  - No `Task` file is touched, since no Task was ever bound.

## 4. Final process state

**`none`.**

`TRANSITION "Started"` (the only statement that could have set a process state) never executed, because execution ended at the failed binding on line 1, before any other statement ran. Per `dsl.md`, "Before the first `TRANSITION`, the process state is `none`," and that remains the state at the end of this (aborted) execution.
