# Validity Check of Snippets A–E

## Snippet A

```
LOOP:deploy
  DELEGATE deploy
  VERIFY deploy
  WHEN deploy.accepted
    → BREAK release
```

**INVALID — V1**

`BREAK` takes no argument; per the grammar, `simple` allows `BREAK` only as a bare keyword on its own line (`"BREAK" , NL`). The line `→ BREAK release` matches no statement form (this is the exact example the spec itself gives for V1: "for example `BREAK release`"). No other rule is broken: the `BREAK` is inside a `LOOP` (so V2 would not apply even if the syntax were legal) and it is not inside a `FORK` branch (so V3 is not implicated).

Broken rules: **V1**.

## Snippet B

```
FORK
  → LOOP:retry
      DELEGATE upload
      VERIFY upload
      WHEN upload.accepted
        → BREAK
  → DELEGATE docs
JOIN
```

**VALID**

This is the exact "valid `BREAK` inside a branch" example from the spec (Control › FORK). `FORK` has two branches (satisfies V9's "at least two branches"). The `BREAK` is inside a `LOOP:retry` that is itself nested inside the same `FORK` branch, so it leaves only that inner loop and the branch continues — this is explicitly permitted ("`BREAK` in a branch that leaves a `LOOP` nested inside the same branch" → Valid), so V3 is not violated. `JOIN` has a corresponding `FORK` (satisfies V9). Indentation follows the rules (a `→ LOOP:retry` item has the loop's body as its own nested children, per Indentation and scope rule 4). No `WHEN` outside the fork tests a branch outcome before a `JOIN`, so V10 does not apply.

Broken rules: **none**.

## Snippet C

```
FORK
  → VERIFY api
  → VERIFY ui
WHEN api.accepted
  → EMIT api-report
```

**INVALID — V10**

`FORK` has two branches (fine for V9). However, `WHEN api.accepted` tests a subject (`api`) whose outcome is established inside a `FORK` branch, and no `JOIN` of that `FORK` appears between the `FORK` and this `WHEN`. Per V10, this makes the outcome untestable at that point in the program text ("a `WHEN` MUST NOT test an outcome that a still-running branch may establish; `JOIN` first"). There is no `JOIN` anywhere in this snippet, so the condition is judged directly on the text and fails.

`VERIFY api` and `VERIFY ui` are otherwise fine (they establish `accepted`/`rejected`, satisfying V6 for the later `WHEN api.accepted`).

Broken rules: **V10**.

## Snippet D

```
HITL:release[approved, rejected]("Release now?")
WHEN release.approved
  → EMIT release
```

**VALID**

This is a decision `HITL` with a two-item answer list (`approved`, `rejected`), no repeated or empty answers (satisfies V7), no `AUTO` (so V5 does not apply), and no `FALLBACK` is required (a `HITL` may have zero fallbacks; `[fallback]` is optional in the grammar). `WHEN release.approved` refers to a subject/outcome pair that the `HITL:release[approved, rejected]` declares, satisfying V6. There is no requirement to also handle `release.rejected` — "no else" is explicit in the spec, and an unhandled outcome is not a validity violation.

Broken rules: **none**.

## Snippet E

```
t1:Task = TASK-0100
VERIFY t1
WHEN t1.accepted
  → TRANSITION t2 "Review"
```

**INVALID — V12**

The binding section only binds `t1` (`t1:Task = TASK-0100`), unindented and first, satisfying V11. `VERIFY t1` and `WHEN t1.accepted` correctly refer to the bound name `t1` (and `accepted`/`rejected` are valid `VERIFY` outcomes, satisfying V6). However, `TRANSITION t2 "Review"` uses the name `t2`, which is never bound anywhere in the program. Per V12, "`TRANSITION <name> "<status>"` uses a name that is not bound" is INVALID.

Broken rules: **V12**.
