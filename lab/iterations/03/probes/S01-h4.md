# S01: DSL Solution

## DSL Program

```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, rejected]("Merge this change?")
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Answer mapping**: "approved" means the human (or agent, if AUTO resolves it) decides to merge; "rejected" means do not merge.

2. **No fallback flow**: If the AUTO HITL cannot determine the answer with certainty and the human does not respond, execution ends (no explicit FALLBACK provided).

3. **Verification outcomes**: VERIFY implementation establishes either `implementation.accepted` or `implementation.rejected`. The program continues regardless of the outcome (VERIFY does not branch).

4. **No gate on VERIFY**: The merge decision proceeds even if verification was rejected. The requirement does not state that a failed verification should prevent the merge decision; only that the merge decision itself depends on available information and criteria.

5. **Sequential execution**: The DELEGATE completes before VERIFY starts, and both complete before the merge decision is made. No concurrent branches are needed.

6. **Initial process state**: The process starts in the `none` state (as defined in the spec). The first TRANSITION statement will set it to "Merged" or "Rework".

7. **Outcome persistence**: The outcome `merge.approved` or `merge.rejected` established by the AUTO HITL persists and is available for the WHEN conditions that follow.
