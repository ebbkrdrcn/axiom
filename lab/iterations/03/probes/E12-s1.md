# Validity check of the four snippets

## Snippet A

```
1  t1:Task = TASK-0100
2  LOOP:work
3    a1:ADR = t1.adr
4    VERIFY t1
5    WHEN t1.accepted
6      → BREAK
```

**Verdict: INVALID**

Broken rules:
- **V11** (line 3) — `a1:ADR = t1.adr` is a binding, but it is indented (nested inside `LOOP:work`'s body) instead of being written unindented at the top of the program, before every other statement. Bindings appear only at the top of a program; a binding inside a scoped construct (here, a loop body) is INVALID under V11, exactly as illustrated by the spec's own example (`LOOP:work` / `t1:Task = TASK-0001`).

No other rule is broken: `VERIFY t1` and `WHEN t1.accepted` refer to a properly-established outcome (V6 satisfied), and `BREAK` is directly inside a `LOOP` and not inside a `FORK` branch (V2/V3 satisfied).

## Snippet B

```
1  a1:ADR = t1.adr
2  t1:Task = TASK-0100
3  VERIFY a1
```

**Verdict: INVALID**

Broken rules:
- **V11** (line 1) — the binding `a1:ADR = t1.adr` is a relation-binding whose relation starts from `t1`, but `t1` is not bound on an earlier line (it is only bound afterward, on line 2). V11 explicitly states that a binding is INVALID if "its relation starts from a name not bound on an earlier line."

Everything else about the snippet (both lines being bindings placed unindented at the top, `VERIFY a1` referring to the bound name `a1`) would otherwise be fine, but the ordering violation of V11 alone makes the program INVALID as a whole.

## Snippet C

```
1  t1:Task = TASK-0102
2  TRANSITION t1 "Done"
```

**Verdict: VALID**

No rule from V1–V12 is broken:
- The binding `t1:Task = TASK-0102` is unindented, at the top, before any other statement, and binds a previously-unbound name (V11 satisfied).
- `TRANSITION t1 "Done"` uses the bound name `t1`, and `t1` is not used elsewhere as a `HITL` name (V12 satisfied).

This program is syntactically and structurally well-formed. Whether the transition itself can actually be performed is a separate matter: `TASK-0102` is `Todo`, and the Task Definition's transition table does not declare a `Todo → Done` change. Per the spec, this is **not** a validity error — "a transition that the Definition does not permit ... is not INVALID: the program is well-formed, and the transition fails when it is executed." So at execution time this `TRANSITION` would fail (no `FALLBACK` is present, so execution would end as with `STOP`), but the program itself remains VALID.

## Snippet D

```
1  t1:Task = TASK-0100
2  HITL:t1[approved, rejected]("Done?")
3  TRANSITION t2 "Done"
```

**Verdict: INVALID**

Broken rules:
- **V12** (line 2) — `t1` is a bound entity name (bound on line 1) and is reused as the name of the `HITL:t1[...]` decision. V12 states: "a bound name is used as a `HITL` name" is INVALID.
- **V12** (line 3) — `TRANSITION t2 "Done"` uses the name `t2`, which is never bound anywhere in the program. V12 states: "`TRANSITION <name> "<status>"` uses a name that is not bound" is INVALID.

(Note V7 is a closely related rule about two `HITL`s sharing a name or a name shared between `HITL` and `VERIFY`; it does not itself cover the bound-name-as-HITL-name case, which V12 covers directly.)
