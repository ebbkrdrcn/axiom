# go_harness DSL for Merge Decision Process

## DSL Program

```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions Made

1. **No REQUIRE statement**: Assumed the context for implementation work is already available and does not need an explicit REQUIRE statement. The DSL begins directly with delegating the work.

2. **No FALLBACK for VERIFY**: Assumed that if verification fails (cannot determine exactly one outcome), execution ends normally rather than running a fallback flow.

3. **No FALLBACK for HITL**: Assumed that if the human's response to the merge decision is insufficient or unavailable, execution ends normally rather than running a fallback flow. The program does not specify what to do in that case.

4. **Process state transitions**: The `TRANSITION` statements set the process state (from initial state `none` to either "Merged" or "Rework"), not entity statuses. No entities are bound in this program.

5. **Consecutive WHEN independence**: The two `WHEN` statements after the HITL are independent and consecutive. Both are checked top to bottom; only the one matching the established outcome runs.

6. **Answer list completeness**: The HITL decision has exactly two possible answers: "approved" and "declined", covering all outcomes specified in the requirement (merge or not merge).

7. **Automatic decision authority**: Under `AUTO`, the agent is permitted to establish `merge.approved` or `merge.declined` only when the decision is certain and within its authority. When uncertainty exists, the human is asked, exactly as without `AUTO`.

8. **No verification failure handling**: The requirement implies the implementation is successfully verified. If `VERIFY implementation` establishes `rejected`, the subsequent merge decision would still proceed. No conditional flow based on verification outcome is specified in the requirement.
