# DSL Solution for Merge Decision Process

## DSL Code

```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **Verification completes regardless of outcome**: The DSL delegates and verifies implementation without conditional handling. It proceeds to the merge decision whether the verification result is `accepted` or `rejected`.

2. **FALLBACK required for robustness**: The requirement states "otherwise a human must be asked", implying the human will answer. However, the specification allows for insufficient or unavailable responses. A `FALLBACK` block is included to handle cases where the human's response is unclear or the response time expires. The fallback transitions to state `"Blocked"` as a safe default (not specified in the requirement).

3. **Two-outcome HITL**: The merge decision uses `[approved, declined]` as the two explicit answers. The requirement says "If the decision is to merge" and "If the decision is not to merge", which map cleanly to these two outcomes.

4. **AUTO HITL interpretation**: The agent is permitted to answer automatically only when the decision is certain and within its authority. In all other cases, the human is asked. This aligns with the requirement's phrasing: "the agent may make the merge decision itself when it is clearly determined by the available information and criteria; otherwise a human must be asked".

5. **Process state transitions**: The requirement specifies only two transition targets: `"Merged"` and `"Rework"`. The FALLBACK introduces a third state `"Blocked"` to handle the edge case of insufficient response (not explicitly required but necessary for well-formed execution).

6. **No explicit error handling for verification rejection**: The requirement does not specify what to do if the implementation verification fails. The DSL proceeds to the merge decision regardless. This could mean: (a) the process trusts the implementation will pass verification, or (b) even rejected implementations go to merge review.

7. **WHEN statements at process level**: The two `WHEN` statements follow the HITL at the same indentation level (not nested), meaning they check outcomes established by the HITL and execute sequentially if their conditions are true.
