# DSL for Merge Decision Process

## DSL Code

```
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **Answer options**: The merge decision uses answer options `[approved, declined]` to represent the two possible merge outcomes.

2. **Always ask after verification**: The merge decision is asked after verification completes, regardless of whether verification was accepted or rejected. This means the HITL executes in all paths.

3. **AUTO is appropriate**: The `AUTO` keyword is used because the requirement explicitly states the agent "may make the merge decision itself when it is clearly determined by the available information and criteria; otherwise a human must be asked." This matches the AUTO semantics exactly—automatic resolution only when certain and within authority, otherwise deferred to the human.

4. **No fallback needed**: No `FALLBACK` clause is included for the HITL. If the human's response is insufficient or unavailable, execution ends (as per rule 8 of **Execution rules** in the specification).

5. **Process state initialization**: The process state is assumed to be uninitialized (value `none`) before these statements run. The `TRANSITION` statements will set it to either "Merged" or "Rework" based on the merge decision.

6. **Consecutive WHEN statements**: The two `WHEN` statements are independent and consecutive. Both are checked if reached, but only one will run its flow (since a subject holds only one outcome at a time). This is rule 3 of **Execution rules**.
