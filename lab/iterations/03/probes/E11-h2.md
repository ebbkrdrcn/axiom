# go_harness DSL Program for TASK-0100

## Program

```text
t:Task = TASK-0100
adr:ADR = t.adr

LOOP:verify-and-fix
  DELEGATE implementation
  VERIFY t
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t.accepted
    → TRANSITION t "Review"
    → BREAK
  WHEN t.rejected
    → TRANSITION t "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t "InProgress"

HITL:done[approved, rejected]("Is TASK-0100 done?")
  → FALLBACK
      → TRANSITION t "InProgress"
      → STOP

WHEN done.approved
  → TRANSITION t "Done"

WHEN done.rejected
  → TRANSITION t "InProgress"
```

## Assumptions

1. **Binding availability:** TASK-0100 exists in the authoritative representation (docs/tasks/TASK-0100.md), is of type Task, is structurally valid, and is currently in a state (InProgress) that permits the required transitions. Its linked ADR (ADR-0100) also exists, is of type ADR, and is structurally valid.

2. **Verification determinism:** The VERIFY operation will be able to determine a single outcome (accepted or rejected) based on the Acceptance Criteria of TASK-0100. The criteria are evaluable when the implementation is complete.

3. **Verification failure handling:** If VERIFY cannot determine an outcome (due to missing or ambiguous acceptance criteria, unavailable evidence, or contradictory criteria), it triggers the FALLBACK flow, which sets the process state to "Blocked" and stops execution.

4. **Work delegation:** The "implementation" and "diagnosis" work can be delegated and will eventually complete without indefinitely blocking execution.

5. **Status transitions:** All status transitions required by the program are permitted by the Task Definition:
   - InProgress → Review (precondition: verified: accepted)
   - InProgress → Debugging (precondition: verified: rejected)
   - Debugging → InProgress (precondition: none)
   - Review → Done (precondition: human: approved)
   - Review → InProgress (precondition: none)

6. **Human response:** The human will provide a response to the HITL question that is either usable as "approved" or "rejected", or the response will be unavailable/insufficient, triggering the FALLBACK.

7. **Process state support:** The runtime supports "Blocked" as a valid process state.

8. **FALLBACK for insufficient HITL response:** If the human's response to the HITL is insufficient or unavailable, the process transitions the task back to InProgress and stops (rather than continuing in an undefined state).

9. **Precondition "human: approved":** The precondition is satisfied when the TRANSITION is inside the flow of WHEN done.approved, the HITL:done has no AUTO, and the HITL question contains TASK-0100's identity (which it does: "Is TASK-0100 done?").
