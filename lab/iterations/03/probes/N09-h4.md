# N09 Solution: ADR Review Process

## DSL Program

```text
a1:ADR = ADR-0101
VERIFY a1
HITL:review[approved, rejected]("Do you accept ADR-0101?")
  → FALLBACK
    → TRANSITION "Waiting"
    → STOP
WHEN review.approved
  → TRANSITION a1 "Accepted"
    → FALLBACK
      → STOP
WHEN review.rejected
  → TRANSITION a1 "Rejected"
```

## Explanation

**Line 1:** Bind the name `a1` to ADR-0101, which must be of type ADR and structurally valid.

**Line 2:** Verify a1 against the ADR Definition's verification criteria. This establishes either `a1.accepted` or `a1.rejected`.

**Lines 3-6:** Ask the human to choose between `approved` or `rejected`. If the human gives a usable response, execution continues with the appropriate `WHEN`. If the response is insufficient or unavailable, the `FALLBACK` runs: set the process state to "Waiting" and stop execution.

**Lines 7-10:** If the human approved:
- Attempt to transition a1 from Proposed to Accepted
- The precondition requires: `verified: accepted` (from the VERIFY) AND `human: approved` (from WHEN review.approved with question containing the identity)
- If the precondition holds, the transition succeeds
- If it fails (e.g., verification was rejected), the FALLBACK runs and stops execution

**Lines 11-12:** If the human rejected:
- Transition a1 from Proposed to Rejected
- The precondition is `human: rejected`, which holds because we are inside the WHEN review.rejected flow
- This transition always succeeds given a rejection answer

## Assumptions

1. **ADR-0101 exists** and can be bound successfully: it is of type ADR, has identity `ADR-0101`, and is structurally valid.

2. **ADR-0101 is in Proposed status** and can be verified. Its Context, Decision, and Consequences sections are present and evaluable.

3. **Verification can be conclusive**: the verification criteria either clearly accept or reject ADR-0101 (missing or contradictory evidence would cause VERIFY to fail).

4. **The HITL question satisfies the precondition**: The question "Do you accept ADR-0101?" contains the entity's identity, which satisfies the `human: approved` precondition for the Accepted transition per the Entity Model's Preconditions rule.

5. **Process state "Waiting" is recognized** by the runtime and is a valid target for the `TRANSITION` statement (the DSL does not validate state names).

6. **Verification failure is handled gracefully**: If verification is rejected and the human chooses "approved", the TRANSITION to Accepted fails due to the `verified: accepted` precondition not holding, triggering the FALLBACK to stop execution. This is the correct behavior given the requirement and the ADR Definition.

7. **Execution ends normally** after the final `WHEN` blocks, or via explicit `STOP` in the fallback paths.
