# E11: DSL Program for TASK-0100

## Program

```text
t1:Task = TASK-0100
a1:ADR = t1.adr

LOOP:rate-limiter
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"
  WHEN t1.accepted
    → BREAK

TRANSITION t1 "Review"
HITL:done[approved, rejected]("Is TASK-0100 done?")
WHEN done.approved
  → TRANSITION t1 "Done"
WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Assumptions

1. The delegated work item `implementation` represents performing the rate limiter implementation for the endpoint.

2. The delegated work item `diagnosis` represents performing diagnostic work to understand why the verification failed.

3. The HITL question "Is TASK-0100 done?" can be answered by the human with either `approved` (meaning the work is ready) or `rejected` (meaning it needs more work).

4. The process presumes that after a successful verification establishing `t1.accepted`, the task's data has not changed; thus the precondition `verified: accepted` holds for the transition to Review.

5. A human's answer `approved` to the HITL provides the precondition `human: approved` required for the transition from Review to Done.

6. The ADR binding (from the `adr` field of TASK-0100) will resolve to ADR-0100, as indicated in the fixture data.

7. If VERIFY cannot determine an outcome (criteria missing, contradictory evidence, or ambiguous), the FALLBACK runs, setting the process state to "Blocked" and stopping execution, as specified in the requirement.
