# Execution of the program (two runs)

```text
DELEGATE release-candidate
VERIFY release-candidate
HITL:ship[approved, rejected]("Ship the release candidate?")
  → FALLBACK
      → TRANSITION "Blocked"
      → HITL("Tell the release manager that shipping is blocked")
      → STOP
WHEN ship.approved
  → EMIT release
```

## Run A

Events: `VERIFY release-candidate` establishes `accepted`. The human answers the ship question "Maybe, ask me later." (ambiguous/deferred → insufficient, per the specification's own example of "Let me think about it next week."). This runs the `FALLBACK`. Inside it, `TRANSITION "Blocked"` sets the process state, then the release manager is asked to be told shipping is blocked, and answers "Noted." — this confirms the requested action was received/carried out, so it is a usable response to the request `HITL`. Execution then reaches `STOP`.

### Trace

```trace
0. validate -> VALID
1. DELEGATE release-candidate -> done
2. VERIFY release-candidate -> outcome release-candidate.accepted
3. HITL:ship[approved, rejected]("Ship the release candidate?") -> waiting
4. HITL:ship[approved, rejected]("Ship the release candidate?") -> failed: response insufficient ("Maybe, ask me later." selects no listed answer); fallback
5. TRANSITION "Blocked" -> state = "Blocked"
6. HITL("Tell the release manager that shipping is blocked") -> waiting
7. HITL("Tell the release manager that shipping is blocked") -> done
8. STOP -> stop
```

Notes on the trace:
- No outcome is established for `ship`: the response was insufficient, so `ship.accepted`/`ship.rejected` is never set, and `WHEN ship.approved` is never reached (the fallback ends with `STOP`, which ends the whole execution before the `WHEN`).
- The nested `HITL("Tell the release manager...")` is a request form: it establishes no outcome; "Noted." confirms the requested action, so it counts as a usable response and execution simply continues to the next statement.

### (3) Bound entities

None. The program binds no entity, so there is no entity status to report and no entity file changed.

### (4) Final process state

`"Blocked"` — set by the `TRANSITION "Blocked"` in the fallback and never overwritten afterward (execution ends at `STOP` right after).

## Run B

Events: `VERIFY release-candidate` establishes `accepted` (same as Run A). The human answers the ship question "Maybe, ask me later." — again insufficient, so the `FALLBACK` runs and `TRANSITION "Blocked"` sets the process state. Then the request `HITL("Tell the release manager that shipping is blocked")` is reached, but nobody answers it and the runtime stops waiting: the response is **unavailable**. This `HITL` has no `FALLBACK` of its own (the only `FALLBACK` in the program belongs to `HITL:ship`, not to this nested request), so per the Failures rule, execution ends as with `STOP`. The `STOP` statement written after it is never reached.
