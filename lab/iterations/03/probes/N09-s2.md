# DSL program

```text
a1:ADR = ADR-0101
VERIFY a1
HITL:decision[approved, rejected]("Accept ADR-0101?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN decision.approved
  → TRANSITION a1 "Accepted"
WHEN decision.rejected
  → TRANSITION a1 "Rejected"
```

## Validity check (V1–V12)

- **V11**: the only binding (`a1:ADR = ADR-0101`) is at the top, unindented, before every other statement. Valid.
- **V12**: `TRANSITION a1 …` uses the bound name `a1`; `a1` is never used as a `HITL` name. Valid.
- **V7**: the `HITL` name (`decision`) is distinct from the `VERIFY`/binding name (`a1`); the answer list `[approved, rejected]` has no duplicates and no other `HITL` reuses `decision`. Valid.
- **V6**: `WHEN decision.approved` and `WHEN decision.rejected` both refer to answers declared in `HITL:decision[approved, rejected]`. Valid.
- **V4 / V8**: exactly one `→ FALLBACK`, written directly under the `HITL`; its flow ends with `STOP`. Valid.
- **V5, V2, V3, V9, V10**: not applicable — no `AUTO`, `BREAK`, `FORK`/`JOIN` are used.

The program is **VALID**.

## Why it is written this way

- `a1:ADR = ADR-0101` binds the ADR by identity, as required for `VERIFY a1` and `TRANSITION a1 "<status>"` to be usable (DSL **Entities**; V12).
- `VERIFY a1` performs the first instruction ("Verify ADR-0101"), evaluating it against the ADR Definition's verification criteria (Context/Decision/Consequences present, Decision is a single unambiguous decision, Consequences name at least one effect). It establishes `a1.accepted` or `a1.rejected`, or fails if the criteria don't determine one outcome.
- The decision `HITL:decision[approved, rejected]("Accept ADR-0101?")` implements "ask the human whether to accept it." It is a plain `HITL` (no `AUTO`), since the requirement gives the agent no authority to decide this itself, and the ADR Definition's `human: approved` / `human: rejected` preconditions can only be satisfied by a human answer to a `HITL` without `AUTO`.
- The question text contains the entity's identity (`ADR-0101`), which is required by the Entity Model for the `human: <answer>` precondition on `TRANSITION a1` to hold (it must be "about that entity").
- `WHEN decision.approved → TRANSITION a1 "Accepted"` and `WHEN decision.rejected → TRANSITION a1 "Rejected"` implement "if the human accepts… if the human rejects…". These map directly onto the ADR Definition's declared transitions `Proposed → Accepted` and `Proposed → Rejected`.
- The `FALLBACK` under the `HITL` implements "if the human gives no usable answer, set the process state to 'Waiting' and stop": per the DSL, an insufficient or unavailable `HITL` response runs the `FALLBACK` (or ends execution if there is none); here `TRANSITION "Waiting"` (a **process**-state transition, no bound name) followed by `STOP` matches the requirement and satisfies V8 (fallback ends with `STOP`).

## Assumptions

1. **ADR-0101 is in status `Proposed`.** The fixture file `docs/adr/ADR-0101.md` shows `status: Proposed`, which is the only status from which both `Accepted` and `Rejected` are reachable per the ADR Definition's transition table. The program does not check status itself — that is enforced by `TRANSITION`'s own precondition check at execution time — but the requirement's two branches ("if accepts → Accepted", "if rejects → Rejected") only make sense starting from `Proposed`.
2. **`TRANSITION a1 "Accepted"` also needs `verified: accepted`**, per the ADR Definition (`Proposed → Accepted` precondition is `verified: accepted; human: approved`, both parts required). The requirement text only mentions the human's answer as the accept/reject condition, so I assume it intends the normal case where `VERIFY a1` established `accepted` and the human then approves. If `VERIFY a1` had established `rejected` but the human nonetheless answered "approved," the `TRANSITION a1 "Accepted"` step would fail its precondition (no `FALLBACK` is attached to it, per the requirement's silence on this case), and execution would end as with `STOP`. I did not add extra handling for this case because the requirement does not describe one, per rule 9/12 of the DSL ("the agent MUST NOT invent... a requirement").
3. **No `FALLBACK` is attached to `VERIFY a1`.** The requirement does not describe what should happen if verification cannot determine a single outcome, so by the DSL's default rule, such a failure simply ends execution (as with `STOP`). I did not invent a fallback flow for it.
4. **No `FALLBACK` is attached to the two entity `TRANSITION` statements** (`Accepted` / `Rejected`), for the same reason: the requirement specifies only the "no usable answer" case's fallback (state `Waiting` + `STOP`), not a fallback for a transition precondition failure.
5. **The binding uses `ADR-0101` as a literal identity**, per "Identity comes only from the `id` that a representation declares" — resolved against `docs/adr/ADR-0101.md`, the sole file whose front-matter `id` is `ADR-0101`.
6. **`TRANSITION "Waiting"` is a process-state transition** (no bound name), since "set the process state to 'Waiting'" is explicitly about the process state (DSL: `TRANSITION "<state>"`), not the ADR's own status — the ADR's status vocabulary (`Proposed`, `Accepted`, `Rejected`, `Superseded`) has no `Waiting` status, so `TRANSITION a1 "Waiting"` would be invalid usage; only the process-state form applies.
7. **The `HITL` is a plain (non-`AUTO`) decision.** The requirement does not grant the agent authority to accept or reject an ADR on its own, and the ADR Definition's `human: <answer>` precondition can be satisfied only by a human response to a `HITL` without `AUTO`; using `AUTO` here would make the "human" precondition unsatisfiable by design and contradict "ask the human."
