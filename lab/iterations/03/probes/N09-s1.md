# DSL program

```text
a1:ADR = ADR-0101
VERIFY a1
HITL:decision[approved, rejected]("Accept ADR-0101?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN decision.approved
  → TRANSITION a1 "Accepted"
      → FALLBACK
          → STOP
WHEN decision.rejected
  → TRANSITION a1 "Rejected"
      → FALLBACK
          → STOP
```

This program is VALID against V1–V12: the binding is the first, unindented statement (V11); `decision` is used only as a `HITL` name, never as a `VERIFY` name, and its answer list has no duplicates (V7); both `WHEN` conditions test outcomes (`approved`, `rejected`) that `HITL:decision[...]` actually lists (V6); every `→ FALLBACK` sits directly under a `HITL` or `TRANSITION <name>` and each construct has at most one (V4); both fallback flows end in `STOP` (V8); there is no `FORK`/`JOIN`/`BREAK` to violate V2, V3, V9, V10; and `TRANSITION a1 "..."` only ever uses the bound name `a1` (V12).

## Assumptions

1. **Binding, no `REQUIRE`.** `ADR-0101` is treated as already identifiable from the task statement, so the program binds it directly (`a1:ADR = ADR-0101`) rather than issuing a `REQUIRE` for repository/document access first. Per the fixtures, exactly one file (`docs/adr/ADR-0101.md`) declares `id: ADR-0101` with `type: ADR` and is structurally valid (all required fields and sections present), so the binding is satisfiable.

2. **`VERIFY a1` has no `FALLBACK`.** The requirement does not say what to do if the ADR's verification criteria (Context/Decision/Consequences present, Decision unambiguous, Consequences name an effect) cannot be decided. Per the DSL default (`VERIFY` fails → `FALLBACK`, else execution ends), I let an undecidable verification simply end execution, since the requirement gives no alternative flow for that case.

3. **HITL answers are named `approved` / `rejected`, matching the ADR Definition's precondition vocabulary exactly** (`human: approved`, `human: rejected`), and the question text includes the identity `ADR-0101` so that the `human: <answer>` precondition (which requires the question to contain the entity's identity) can hold for the later `TRANSITION`.

4. **No `AUTO`.** The requirement explicitly says "ask the human," so the decision is a plain `HITL` (not `AUTO HITL`) — the agent never answers it itself.

5. **"No usable answer" covers both insufficient and unavailable responses**, per the DSL's definition of `HITL` failure (an ambiguous/off-topic/no-decision response, or no response once the runtime stops waiting). Both cases run the same `FALLBACK`: `TRANSITION "Waiting"` (process state) then `STOP`, exactly as the requirement asks ("set the process state to 'Waiting' and stop").

6. **Important semantic gap between the requirement and the ADR Definition, resolved in favor of the Definition:** the requirement says "if the human accepts, move the ADR to Accepted," implying the human answer alone should drive that transition. However, the ADR Definition's transition table declares `Proposed → Accepted` with precondition **`verified: accepted; human: approved`** — both conditions must hold (the DSL states "If a change lists several, all MUST hold"). So if `VERIFY a1` established `a1.rejected` but the human still answers "approved" to the accept/reject question, `TRANSITION a1 "Accepted"` fails (its precondition does not hold), its `FALLBACK` runs, and execution stops — the ADR is **not** moved to `Accepted` in that case. I chose to apply the entity Definition's explicit precondition exactly (as the Entity Model requires: "Apply explicit rules exactly as written," "Do not extend a closed vocabulary," rule 8 "Fail what the contracts do not decide") rather than let the human's answer alone override it. The `Proposed → Rejected` transition only requires `human: rejected`, so it is unaffected by the `VERIFY` outcome and always succeeds once the human answers "rejected."

7. **The inner `FALLBACK`s under each `TRANSITION a1 "..."` just `STOP`** (no additional `TRANSITION "<state>"` to a process state first), since the requirement specifies a distinct fallback only for the "no usable answer" case, not for a transition-precondition failure after a usable answer. If a richer failure state were wanted here, it is not specified by the requirement, so I kept the minimal, contract-compliant behavior: fail and stop.

8. **The process state is left at `none` on the success paths** (accepted/rejected via `TRANSITION a1`), since the requirement only asks for the ADR's own status to change on those paths, and only specifies a process-state change (`"Waiting"`) for the no-usable-answer case.
