```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[merge, no-merge]("Merge this change?")
WHEN merge.merge
  → TRANSITION "Merged"
WHEN merge.no-merge
  → TRANSITION "Rework"
```

## Assumptions

1. **No entities involved.** The requirement mentions no task, ADR, or other identifiable entity to bind, so no `<name>:<Type> = <identity>` binding is used. `TRANSITION "Merged"` / `TRANSITION "Rework"` are treated as process-state transitions (`TRANSITION "<state>"`), not entity-status transitions, since no bound entity is named.
2. **`DELEGATE`/`VERIFY` name.** "Delegate the implementation and verify it" is modeled as `DELEGATE implementation` followed by `VERIFY implementation`, using the same identifier so the `VERIFY` refers to the delegated result, as the spec requires for them to refer to the same thing.
3. **The merge decision proceeds regardless of the verification outcome.** The requirement does not say what happens if `VERIFY implementation` is rejected (or fails), so no `WHEN implementation.accepted/rejected` branching and no `FALLBACK` on `VERIFY` were added; execution simply continues to the merge decision after `VERIFY implementation` completes (or ends, per the default failure rule, if `VERIFY` itself fails with no `FALLBACK`).
4. **Answer names for the merge decision.** The requirement's two outcomes ("merge" / "not merge") are modeled as the answer list `[merge, no-merge]` for `HITL:merge`, since the DSL requires an explicit, non-empty, non-repeating list of identifiers and the requirement did not supply exact labels. `no-merge` is a valid identifier (letters, digits, `-`, `_`, starting with a letter).
5. **`AUTO` semantics.** "The agent may make the merge decision itself when it is clearly determined... otherwise a human must be asked" maps directly to `AUTO HITL:...`, per the spec's definition of `AUTO` (agent decides only when certain and within authority; otherwise the human is asked). No additional wording was needed beyond the standard `AUTO HITL` construct.
6. **No `FALLBACK` on the `HITL`.** The requirement does not describe what to do if the merge decision is insufficient/unavailable (e.g., an ambiguous or missing human response), so no `→ FALLBACK` was added under `HITL:merge`; per the spec, execution then ends (as with `STOP`) if the response is insufficient or unavailable, which is the safe default given no instructions otherwise.
7. **Question wording.** The question string is taken verbatim from the requirement: `"Merge this change?"`.
8. **No `REQUIRE`, `LOOP`, `FORK`, or `WAIT`.** The requirement describes a single linear decision process with no repetition, concurrency, explicit prerequisite resource, or external-event suspension, so none of these constructs were used.
9. **Process states.** `"Merged"` and `"Rework"` are used exactly as named in the requirement as the two process states set by `TRANSITION`.
