# go_harness program for TASK-0100

```text
t1:Task = TASK-0100
a1:ADR = t1.adr

LOOP:work
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.accepted
    → TRANSITION t1 "Review"
    → BREAK
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"
HITL:done[approved, rejected]("Is TASK-0100 done?")
WHEN done.approved
  → TRANSITION t1 "Done"
WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Why it is written this way

- `t1:Task = TASK-0100` and `a1:ADR = t1.adr` are both bindings, so both sit unindented at the top of the program, before any other statement (rule V11). The requirement says the linked ADR "must be bound as well"; `t1.adr` is the only relation the Task Template declares, and `TASK-0100`'s front matter sets `adr: ADR-0100`, so this binds `a1` to `ADR-0100`. `a1` is not otherwise used, since the requirement gives it no further role beyond being bound.
- `LOOP:work` repeats "have the rate limiter implemented and verify the task, until the verification accepts it." `DELEGATE implementation` does the work; `VERIFY t1` evaluates the bound Task entity against the Task Definition's verification criteria (the Acceptance Criteria of TASK-0100).
- The `FALLBACK` under `VERIFY t1` covers "If a verification cannot decide, set the process state to 'Blocked' and stop": `TRANSITION "Blocked"` (a process-state transition, no bound name) then `STOP`, as required by rule V8 (a fallback flow must end in `STOP` or `BREAK`) and by the DSL's own equivalent example.
- `WHEN t1.accepted` → `TRANSITION t1 "Review"` then `BREAK`: this both leaves the loop ("until the verification accepts it") and performs "After acceptance, move the task to Review" in the same step, since a `WHEN` flow is one sequential flow and `TRANSITION` before `BREAK` still runs. The Task Definition permits `InProgress → Review` with precondition `verified: accepted`, which the immediately preceding `VERIFY t1` establishes.
- `WHEN t1.rejected` → `TRANSITION t1 "Debugging"`, `DELEGATE diagnosis`, `TRANSITION t1 "InProgress"`: this is "move the task to Debugging, have a diagnosis done, and move it back to InProgress before trying again." `InProgress → Debugging` requires `verified: rejected` (just established); `Debugging → InProgress` requires `none`. Because `BREAK` was not taken, the loop body ends and repeats from the top (rule 5), so the next iteration re-delegates the implementation and re-verifies.
- After the loop, `HITL:done[approved, rejected]("Is TASK-0100 done?")` asks the human "whether it is done." The question text contains the entity's identity `TASK-0100`, and the `HITL` carries no `AUTO`, which is required for the Task Definition's `human: approved` precondition on `Review → Done` to ever hold.
- `WHEN done.approved` → `TRANSITION t1 "Done"`: `Review → Done` has precondition `human: approved`, satisfied by this `HITL`.
- `WHEN done.rejected` → `TRANSITION t1 "InProgress"`: "if the human rejects, move it back to InProgress"; `Review → InProgress` has precondition `none`, so it always succeeds once reached.

## Assumptions

1. **No `FALLBACK` on the `HITL:done` decision.** The requirement describes only the `approved` and `rejected` outcomes and gives no instruction for an insufficient or unavailable human response. Per the DSL's default (`HITL` failure with no `FALLBACK` → execution ends, as with `STOP`), the program lets execution end in that case rather than inventing a recovery flow.
2. **`VERIFY t1` refers to the bound Task entity, not a separately named "verification" work item.** The requirement's "verify the task" is read as evaluating the entity `t1` itself (per **Entities › `VERIFY` on an entity**), using the Task Definition's Acceptance-Criteria-based criteria, rather than verifying a `DELEGATE`d result under some other name.
3. **`DELEGATE implementation` and `DELEGATE diagnosis` are the delegated work items** for "have the rate limiter implemented" and "have a diagnosis done" respectively; the DSL does not prescribe how delegation is carried out, only that these are distinct pieces of work.
4. **The ADR binding (`a1`) is bound only, per the explicit instruction, and not read or acted upon further**, since the requirement does not ask for any ADR operation (no `VERIFY a1` or `TRANSITION a1`). Its purpose here is to satisfy "the ADR linked to the task must be bound as well" and to fail the whole execution up front (per binding rules) if `TASK-0100`'s `adr` relation were ever missing or unsatisfiable — which the fixtures show it is not (`adr: ADR-0100`, and `ADR-0100.md` exists, is structurally valid, and declares `type: ADR`).
5. **The loop's `FALLBACK` transitions the process state, not the entity's status.** "Set the process state to 'Blocked'" maps to `TRANSITION "Blocked"` (no bound name), consistent with the DSL's distinction between process state and entity status; the task's own status is left as `TRANSITION t1` last set it (unset by this failure).
6. **Re-verification after `Debugging → InProgress`** is assumed to require a fresh `DELEGATE implementation` before the next `VERIFY t1`, which the loop structure provides naturally by returning to the first statement of the body (rule 5), rather than re-verifying stale, already-rejected data.
