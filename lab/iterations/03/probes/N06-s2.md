# Execution of the program against the fixtures

## Program

```text
t1:Task = TASK-0100
VERIFY t1
DELEGATE polish
TRANSITION t1 "Review"
  → FALLBACK
      → TRANSITION "Reverify"
      → STOP
```

## 1. Validity verdict

**VALID**

Checked against V1–V12:

- One binding, at the top, unindented, before any other statement (V11 satisfied).
- No `HITL`, so V5/V7 don't apply.
- No `WHEN`, so V6/V10 don't apply.
- No `LOOP`/`FORK`, so V2/V3/V9 don't apply.
- The only `→ FALLBACK` is written directly under `TRANSITION t1 "Review"` (a `TRANSITION <name>`), and it is the sole `FALLBACK` for that statement (V4 satisfied).
- The fallback flow's last item is `STOP` (V8 satisfied).
- `TRANSITION t1 "Review"` uses the name `t1`, which is bound and not used as a `HITL` name (V12 satisfied).

No rule is broken.

## 2. Execution trace

```trace
0. validate -> VALID
1. t1:Task = TASK-0100 -> bound TASK-0100
2. VERIFY t1 -> outcome t1.accepted (evidence: item 1: the "5 failed attempts in 10 minutes -> HTTP 429" test passes; item 2: the "limit resets after 10 minutes without a failed attempt" test passes)
3. DELEGATE polish -> done
4. TRANSITION t1 "Review" -> failed: precondition "verified: accepted" no longer holds — t1's data (the Description section) changed since VERIFY t1, by DELEGATE polish, not by TRANSITION; fallback
5. TRANSITION "Reverify" -> state = "Reverify"
6. STOP -> stop
```

### Why step 4 fails

`TRANSITION t1 "Review"` requires (Task Definition, `InProgress → Review`) the precondition `verified: accepted`. That precondition holds only if "the most recent `VERIFY <name>` in this execution established `<name>.accepted`, **and** the entity's data has not changed since that `VERIFY` (other than by `TRANSITION <name>`)" (dsl.md, Preconditions).

Between step 2 (`VERIFY t1` → `accepted`) and step 4, step 3 (`DELEGATE polish`) rewrote the Description section of `TASK-0100.md`. Description is part of the entity's Data (Template §Sections), and this change was made by `DELEGATE`, not by `TRANSITION`. This is a permitted edit under the Task Definition ("Delegated work may edit Description, Acceptance Criteria and Notes only while the Task is `Todo`, `InProgress` or `Debugging`" — t1 is `InProgress`), but it invalidates the `verified: accepted` precondition. So the `TRANSITION` fails (condition 4 of **Entities › TRANSITION on an entity** is not met), nothing about `t1` changes, and its `→ FALLBACK` runs instead of the normal continuation.

The fallback flow runs `TRANSITION "Reverify"` (a *process*-state transition, distinct from the failed entity transition) and then `STOP`, ending execution. Since execution ends via `STOP`, no `(end of program) -> end` line is written.

## 3. Bound entities: final status and file changes

Only one entity is bound: `t1` = `TASK-0100`.

- **Final status:** `InProgress` — unchanged. The only attempted status change (`TRANSITION t1 "Review"`) failed its precondition and was not performed; a failed operation "changes nothing" (dsl.md, Failures).
- **File changed:** `docs/tasks/TASK-0100.md` — yes, but only its **Description** section, rewritten by `DELEGATE polish` ("Limit failed login attempts per account." → whatever the delegate wrote; the fixture text shown is pre-change). No other field or section changed: `id`, `type`, `status`, `adr`, and Acceptance Criteria all remain as in the fixture. This edit is within what the Task Definition permits for an `InProgress` task ("Delegated work may edit Description, Acceptance Criteria and Notes only while the Task is `Todo`, `InProgress` or `Debugging`... It never changes `id`, `type`, `status` or `adr`").
- The `accepted` outcome established by `VERIFY t1` in step 2 is still the latest recorded outcome of `t1` for the rest of the execution (outcomes are not retracted by a later data change — only the precondition check for `verified: accepted` treats that data change as disqualifying); however, this has no further effect since execution stops immediately afterward.

No other entity (e.g. `ADR-0100`) is bound or touched by this program.

## 4. Final process state

`"Reverify"` — set by the `TRANSITION "Reverify"` statement inside the fallback flow (the most recently executed `TRANSITION "<state>"` wins; there was no process-state `TRANSITION` earlier in the program, so the state was `none` until this point).
