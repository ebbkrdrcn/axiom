# DSL Program

## Program

```
a1:ADR = ADR-0101
VERIFY a1
HITL:decision[approved, rejected]("Accept ADR-0101?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN decision.approved
  → TRANSITION a1 "Accepted"
WHEN decision.rejected
  → TRANSITION a1 "Rejected"
```

## Assumptions

1. **ADR-0101 exists and is structurally valid.** The binding will resolve ADR-0101 from the authoritative representation and confirm it is of type ADR with all required fields and sections present.

2. **Verification will establish `a1.accepted`.** Based on the ADR Definition verification criteria, ADR-0101 contains Context ("Logs are free text..."), Decision ("All services log JSON objects..."), and Consequences ("Log queries become possible..."). All three sections are present, the Decision states one clear decision that can be followed, and the Consequences name effects on the project, so VERIFY will establish `a1.accepted`.

3. **Entity data does not change between VERIFY and TRANSITION.** The precondition `verified: accepted` for the transition Proposed → Accepted requires that the entity's data has not changed since the VERIFY operation. This program assumes no external modifications occur during the HITL wait.

4. **The human provides a clear, usable response to the HITL.** If the human responds with "yes", "approved", or equivalent clearly meaning approval, the outcome `decision.approved` is established. If "no", "rejected", or equivalent clearly meaning rejection, the outcome `decision.rejected` is established. If the response is insufficient, ambiguous, or unavailable, the FALLBACK flow runs.

5. **The execution environment can persist status changes.** The TRANSITION statements will successfully write the new status to the authoritative representation (the Markdown file for ADR-0101).

6. **HITL precondition is satisfied.** For the transition Proposed → Accepted, the precondition `human: approved` requires that the TRANSITION is inside a `WHEN decision.approved` flow from a `HITL:decision` with no AUTO, and the HITL question contains the entity identity. This program satisfies all these conditions.

## Explanation

The program:
1. Binds the name `a1` to entity ADR-0101
2. Verifies the ADR against its Definition criteria, establishing `a1.accepted` (all required sections are present and complete)
3. Asks the human to approve or reject the ADR
4. If the human approves:
   - Transitions the ADR status to Accepted (preconditions satisfied: verified: accepted ✓, human: approved ✓)
5. If the human rejects:
   - Transitions the ADR status to Rejected (precondition satisfied: human: rejected ✓)
6. If the human gives no usable answer:
   - Runs the FALLBACK flow, which sets the process state to "Waiting" and stops execution

This design aligns with the ADR Definition transitions and preconditions, which require both verification and human approval for acceptance, but only human decision for rejection.
