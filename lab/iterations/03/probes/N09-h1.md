# Solution: go_harness DSL Program for ADR-0101 Review

## Program

```text
adr:ADR = ADR-0101
VERIFY adr
HITL:decision[approved, rejected]("Accept ADR-0101?")
  → FALLBACK
    → TRANSITION "Waiting"
    → STOP
WHEN decision.approved
  → TRANSITION adr "Accepted"
WHEN decision.rejected
  → TRANSITION adr "Rejected"
```

## Explanation

1. **Binding**: `adr:ADR = ADR-0101` binds ADR-0101 to the name `adr` for use in the process.

2. **Verification**: `VERIFY adr` evaluates the ADR against the Definition's verification criteria (Context, Decision, and Consequences present and well-formed). The fixture shows ADR-0101 satisfies all criteria, so this establishes `adr.accepted`.

3. **Human Decision**: `HITL:decision[approved, rejected]("Accept ADR-0101?")` asks the human to choose between `approved` and `rejected`. The question includes the entity's identity (required for the `human: <answer>` precondition).

4. **Fallback**: If the human gives no usable answer or the response is unavailable, the fallback runs: set the process state to "Waiting" and stop execution.

5. **Conditional Transitions**:
   - `WHEN decision.approved`: If human approves, transition the ADR to "Accepted". The preconditions are satisfied: `verified: accepted` (from step 2) and `human: approved` (from the WHEN flow and HITL without AUTO).
   - `WHEN decision.rejected`: If human rejects, transition the ADR to "Rejected". The precondition `human: rejected` is satisfied.

## Assumptions

1. **Verification succeeds**: Based on the ADR Definition criteria and ADR-0101's content, the VERIFY step establishes `adr.accepted`. All required sections (Context, Decision, Consequences) are present and well-formed.

2. **HITL classification**: The runtime correctly interprets human responses as either `approved` (e.g., "yes", "approve", "accept") or `rejected` (e.g., "no", "reject", "decline").

3. **No external changes**: The ADR's data does not change between verification and the transition (except by the TRANSITION statement itself).
