# E11 Solution: DSL Program

## Program

```
t:Task = TASK-0100
a:ADR = t.adr
LOOP:work
  DELEGATE implementation
  VERIFY t
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t.accepted
    → BREAK
  WHEN t.rejected
    → TRANSITION t "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t "InProgress"
TRANSITION t "Review"
HITL:done[approved, rejected]("Is TASK-0100 done?")
  → FALLBACK
      → STOP
WHEN done.approved
  → TRANSITION t "Done"
WHEN done.rejected
  → TRANSITION t "InProgress"
```

## Assumptions

1. **Entity prerequisites**
   - TASK-0100 exists as a structurally valid Task entity in status `InProgress`.
   - TASK-0100's `adr` field contains a valid ADR identity (ADR-0100 in the fixture).
   - The binding `a:ADR = t.adr` can be satisfied with an existing, structurally valid ADR entity.

2. **Delegated work capability**
   - The runtime provides mechanisms to delegate "implementation" and "diagnosis" work to available actors.
   - Each delegation eventually produces a result, allowing execution to continue.

3. **Verification determinism**
   - The `VERIFY t` operation can evaluate TASK-0100 against its Acceptance Criteria and definitively establish either `accepted` or `rejected`.
   - If verification criteria cannot be evaluated unambiguously (evidence unavailable, criteria contradictory), the VERIFY fails and triggers the FALLBACK.

4. **Human responsiveness**
   - A human user is available to respond to the `HITL:done` decision.
   - The human's response unambiguously selects one of the listed answers (`approved` or `rejected`), or is unavailable/insufficient (triggering the FALLBACK to stop).

5. **Data consistency**
   - The task's entity data (including status) is not modified by external processes between the `VERIFY` and the `TRANSITION t "Review"` statement, ensuring the precondition `verified: accepted` remains valid.

6. **Definition compliance**
   - All `TRANSITION` operations use only statuses and transitions declared in the Task Definition.
   - The preconditions for each transition are satisfied when the transition is executed:
     - `InProgress → Debugging`: requires `verified: rejected` ✓
     - `Debugging → InProgress`: precondition `none` ✓
     - `InProgress → Review`: requires `verified: accepted` ✓
     - `Review → Done`: requires `human: approved` (satisfied by `WHEN done.approved` flow) ✓
     - `Review → InProgress`: precondition `none` ✓

## Program Correctness

**Validity**: The program satisfies all DSL validity rules (V1–V12):
- Bindings are at the top, unindented, with `t` bound before `a` ✓
- All `WHEN` conditions have corresponding outcome producers (`VERIFY t` and `HITL:done`) ✓
- All FALLBACK flows end with `STOP` or `BREAK` ✓
- All `BREAK` statements are inside the `LOOP:work` ✓
- Bound names (`t`, `a`) do not conflict with HITL names (`done`) ✓

**Execution flow**:
1. Bind TASK-0100 and its ADR
2. Enter loop: implement → verify
3. If accepted: break loop
4. If rejected: debug → move to InProgress → retry
5. If verify fails: set state to Blocked → stop
6. After acceptance: move to Review
7. Ask human if done
8. If approved: move to Done
9. If rejected: move back to InProgress
10. If human doesn't respond: stop
