# go_harness program for TASK-0100

```text
t1:Task = TASK-0100
a1:ADR = t1.adr
LOOP:work
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.accepted
    → TRANSITION t1 "Review"
    → BREAK
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"
HITL:done[approved, rejected]("Is TASK-0100 done?")
WHEN done.approved
  → TRANSITION t1 "Done"
WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Why it is shaped this way

- **Bindings first.** `t1:Task = TASK-0100` and `a1:ADR = t1.adr` are the only two statements before the block, unindented, as V11 requires. The requirement says the linked ADR "must be bound as well," so `a1` is bound even though the program never otherwise refers to it — a binding needs no later use.
- **Loop and retry.** "Repeatedly have the rate limiter implemented and verify the task, until the verification accepts it" is `LOOP:work` containing `DELEGATE implementation` then `VERIFY t1`, with `BREAK` only on `t1.accepted`. Per DSL rule 5/Quick reference, the loop restarts at its first statement whenever the body ends without a `BREAK`, so no explicit "repeat" instruction is needed.
- **Rejection path.** "Move the task to Debugging, have a diagnosis done, and move it back to InProgress before trying again" is exactly the `WHEN t1.rejected` flow: `TRANSITION t1 "Debugging"` → `DELEGATE diagnosis` → `TRANSITION t1 "InProgress"`. Falling off the end of the loop body (whether via this flow or via a false `WHEN t1.accepted`) lands back at `LOOP:work`'s first statement, satisfying "before trying again."
- **Undecidable verification.** "If a verification cannot decide, set the process state to Blocked and stop" is the `VERIFY t1 → FALLBACK` flow. Per the DSL, `VERIFY` failing (criteria don't determine exactly one outcome) runs its `FALLBACK`, which here does `TRANSITION "Blocked"` (process state, not the entity) then `STOP`, satisfying rule V8 (fallback must end with `STOP` or `BREAK`).
- **After acceptance.** `WHEN t1.accepted` runs `TRANSITION t1 "Review"` (permitted from `InProgress` under the Task Definition's `verified: accepted` precondition, which is satisfied because this `VERIFY t1` is the most recent one and nothing has changed the entity since) and then `BREAK`, leaving the loop.
- **Human decision.** "Ask the human whether it is done" is `HITL:done[approved, rejected]("Is TASK-0100 done?")`. No `AUTO` is used because the requirement calls for asking a human, not for automatic resolution, and the `Review → Done` transition's `human: approved` precondition can only be satisfied by an un-`AUTO`'d `HITL` whose question names the entity's identity — hence the question text includes `TASK-0100`.
- **Human answer paths.** `WHEN done.approved → TRANSITION t1 "Done"` performs `Review → Done` (precondition `human: approved`, satisfied as above). `WHEN done.rejected → TRANSITION t1 "InProgress"` performs `Review → InProgress` (precondition `none`), matching "if the human rejects, move it back to InProgress."
- No `FALLBACK` is attached to the `HITL`: the requirement gives no instruction for an insufficient/unavailable response, so per the DSL's default ("no FALLBACK → execution ends"), an unusable response simply ends execution, which is consistent with the requirement's silence on that case.

## Assumptions

1. The work delivered before each verification is named `implementation` (an identifier), matching `VERIFY t1`'s subject via the shared entity binding rather than via a matching `DELEGATE` name — `DELEGATE` and `VERIFY` need not share a name when `VERIFY` targets a bound entity.
2. The diagnosis work is named `diagnosis`.
3. The `HITL` decision is named `done`, with answers `[approved, rejected]`, matching the wording "the human approves / the human rejects" and reusing the outcome vocabulary already used for `VERIFY` elsewhere in the spec's examples (kept consistent here, not required by the DSL).
4. `TRANSITION "Blocked"` in the `VERIFY` fallback sets the **process** state (unnamed `TRANSITION "<state>"`), not an entity status, since "Blocked" is not a status declared by the Task Definition; setting an entity status to an undeclared value would be a failed/invalid transition.
5. No `FALLBACK` is attached to `HITL:done`, since the requirement specifies behavior only for "approves" and "rejects" (the two declared answers) and says nothing about an insufficient or unavailable response; by the DSL's default rule, such a case simply ends execution.
6. Per the fixtures, `TASK-0100` is already `InProgress` and has `adr: ADR-0100` set, so both bindings and the first `Todo → InProgress` transition are not needed; the program starts directly with the verification loop, consistent with the requirement's wording ("repeatedly have the rate limiter implemented and verify the task"), which does not mention an initial `Todo → InProgress` step.
7. "The ADR linked to the task must be bound as well" is satisfied by binding `a1:ADR = t1.adr` immediately after `t1`; the requirement does not ask for any operation on `a1`, so none is included.
