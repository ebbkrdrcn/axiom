```text
DELEGATE implementation
VERIFY implementation
HITL:merge("Merge this change?") AUTO
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

The specification leaves several things open that this task required a choice on. Assumptions made:

1. **Answer identifiers for the merge decision.** The spec says `HITL:<name>` establishes outcomes `<name>.<answer>` where `<answer>` is "one of the answers tested by the `WHEN <name>.<answer>` constructs that follow," but it does not fix vocabulary for a "merge or not" decision. I assumed the two possible answers are named `approved` and `declined` (following the naming used in the spec's own `HITL:merge` / `AUTO` example), giving conditions `merge.approved` and `merge.declined`.

2. **The `HITL` name itself.** The requirement doesn't name the decision; I named it `merge` (again matching the spec's own worked example for a merge decision), since a name is required for `WHEN` to refer to the outcome.

3. **No `REQUIRE` statement.** The requirement text states no explicit prerequisite ("information, context, state, or condition") that must be declared before execution proceeds, so no `REQUIRE` was added. If the implementation work actually depends on some pre-existing resource (e.g. a repository), the spec would call for a `REQUIRE` before `DELEGATE`, but nothing in the task wording asked for that.

4. **No branching on the implementation `VERIFY` outcome.** The requirement only says "Delegate the implementation and verify it. Then a merge decision is needed" — it does not ask for different behavior depending on whether the implementation is accepted or rejected. Per the spec, "`VERIFY` does not branch by itself... A `VERIFY` with no `WHEN` after it does not gate the process," so `VERIFY implementation` is included but is not followed by a `WHEN`; the flow proceeds unconditionally to the merge decision. I assumed this is the intended reading rather than an implicit accepted/rejected gate that the requirement doesn't mention.

5. **Order of the two `WHEN` outcome checks.** I placed `WHEN merge.approved` before `WHEN merge.declined`, mirroring the order the requirement states them ("If the decision is to merge... If the decision is not to merge..."). The spec states `WHEN` constructs are independent and order between distinct, non-overlapping conditions has no semantic effect, so this ordering is a presentation choice, not a semantic requirement.

6. **"No usable answer" maps to the `FALLBACK` mechanism, covering both "unavailable" and "insufficient" per the spec's definitions** ("The human gives no usable answer" is treated as either no response arriving or an off-topic/non-conforming response — both are handled identically by `FALLBACK` per the spec, so a single fallback flow suffices without further distinction).

7. **`STOP` terminates the entire execution**, which matches the requirement's "transition to state 'Blocked' and stop" — interpreted as ending the whole process, not merely a local flow, consistent with the spec's definition of `STOP`.

8. **Indentation depth/spacing is arbitrary** (only relative nesting matters per the Scope rules); the exact number of spaces used has no semantic significance.

9. **The criteria/authority by which `AUTO` determines the merge decision are external to the DSL.** Per the spec, `AUTO` "defines when automatic decision resolution is permitted, not an algorithm or confidence threshold," so the DSL program does not and cannot specify what makes the decision "clearly determined" — that determination is left to the surrounding process/runtime, exactly as the requirement's own wording ("clearly determined by the available information and criteria") implies criteria that live outside the DSL text.
