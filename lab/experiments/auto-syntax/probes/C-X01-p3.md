```text
DELEGATE implementation
VERIFY implementation
HITL:merge("Merge this change?")
  → AUTO
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **Argument names for `DELEGATE`/`VERIFY`**: The requirement says "the implementation" generically without giving it a specific name, so I used the identifier `implementation` for both, following the exact pattern shown in the spec's own `DELEGATE`/`VERIFY` example.

2. **No `WHEN` after `VERIFY implementation`**: The requirement only says "verify it" as a step before the merge decision; it does not describe any branching on the outcome of that verification (e.g. what happens if the implementation is rejected). Per the spec, "`VERIFY` does not branch by itself... A `VERIFY` with no `WHEN` after it does not gate the process," so I left it as a plain evaluation step with no conditional flow attached.

3. **`HITL` name `merge`**: The spec requires a `<name>` on `HITL` whenever a `WHEN <name>.<answer>` refers to it. Since the requirement needs to distinguish "merge" vs. "don't merge" outcomes, I named the decision `merge`. The requirement itself does not supply this identifier.

4. **Answer identifiers `approved` / `declined`**: The requirement describes the two possible human/agent decisions only in prose ("the decision is to merge" / "the decision is not to merge"). The DSL requires concrete `<name>.<answer>` identifiers for `WHEN`, but the spec does not fix a vocabulary for answers, so I chose `merge.approved` and `merge.declined` as reasonable, human-readable identifiers consistent with the spec's own `AUTO` example (which uses `merge.approved` / `merge.declined` for an analogous scenario).

5. **`HITL` message text**: Used verbatim as given in the requirement: `"Merge this change?"`.

6. **Placement and order of `→ AUTO` and `→ FALLBACK`**: The spec requires that when both are present, `→ AUTO` must come before `→ FALLBACK` under the `HITL`. I followed this fixed order; the requirement's prose order (agent-decision case mentioned first, then human, then no-answer case) happens to match this required order.

7. **Mapping "no usable answer" to `FALLBACK`**: The spec defines `FALLBACK` as covering both an unavailable response (none arrives) and an insufficient one (arrives but doesn't answer the question). The requirement's phrase "the human gives no usable answer" was read as covering both of these cases collectively, so a single `FALLBACK` flow handles it, per spec's definition rather than requiring two separate constructs (the DSL has no separate syntax to distinguish "unavailable" from "insufficient" — both route to the same `FALLBACK`).

8. **Fallback flow body (`TRANSITION "Blocked"` then `STOP`)**: The requirement says "transition to state 'Blocked' and stop," which I read as a sequential order — transition first, then stop — matching the spec's own `FALLBACK` example verbatim in structure (`→ TRANSITION "Blocked"` then nested `STOP`, using the equivalent nested-child form the spec shows as identical to two separate `→` lines).

9. **No `LOOP` construct**: The requirement describes a single, one-shot sequence (delegate → verify → decide → transition), not a repeating process, so no `LOOP` wrapper was used. The spec states `LOOP` is only for explicitly repeated execution, which nothing in the requirement calls for.

10. **No `REQUIRE` or `EMIT` statements**: The requirement does not mention any precondition that must be available before execution (`REQUIRE`) nor any artifact/output to be produced (`EMIT`), so neither was added. The spec does not mandate that every process include these.

11. **No `TRANSITION` before the merge decision**: The requirement does not mention any state change prior to the merge decision (e.g., no "Review" or similar intermediate state named), so none was inserted; only the three transitions explicitly named in the requirement (`Merged`, `Rework`, `Blocked`) appear.

12. **Top-level flow, not inside a `WHEN`/`FORK`**: The requirement describes one straightforward linear process with a single human-decision point, so it was written as a flat top-level sequence of statements rather than nested inside any other conditional or concurrent construct, consistent with there being no concurrency or additional outer conditions mentioned in the requirement.
