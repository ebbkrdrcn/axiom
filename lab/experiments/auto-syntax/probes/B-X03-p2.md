# Execution of the DSL program

## Program

```text
DELEGATE dependency-upgrade
VERIFY dependency-upgrade
HITL:merge("Merge the dependency upgrade?") AUTO
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Deferred"
```

## Given context (from the task, used as the facts the DSL operates on)

- Merge criterion (external to the DSL, supplied by "the surrounding process"): *merge when verification accepts the upgrade **and** the changelog announces no breaking change*.
- The agent has authority to merge dependency upgrades.
- `VERIFY dependency-upgrade` establishes `accepted`.
- The changelog lists only bug fixes.
- No human is currently online.

## Step-by-step execution

**1. `DELEGATE dependency-upgrade`**
Work is assigned to an actor. Per spec, `DELEGATE` "does not mean that the work is correct, complete, or accepted" — it only records that the work is someone else's responsibility. Execution proceeds to the next statement once this delegated work has been produced (the mechanics of "how" are outside the DSL, per Semantic Principles).

**2. `VERIFY dependency-upgrade`**
The delegated result is evaluated against acceptance criteria. The task states this establishes the outcome `accepted`. Per spec, `VERIFY` "does not branch by itself" — it only records the outcome; nothing conditional happens here. Execution continues unconditionally to the next statement.

**3. `HITL:merge("Merge the dependency upgrade?") AUTO`**
This is a `HITL` marked `AUTO`, so before asking a human the runtime checks whether the decision is "sufficiently determined by the available information, criteria, and authority":

- Information available: `dependency-upgrade` is `accepted` (from step 2); the changelog lists only bug fixes.
- Criteria: "merge when verification accepts the upgrade and the changelog announces no breaking change."
- Applying the criteria to the information: verification accepted → first condition satisfied. The changelog lists only bug fixes, i.e. it announces no breaking change → second condition satisfied. Both conjuncts of the criterion hold, and no other information contradicts this, so exactly one protocol-compatible decision follows: **approve**.
- Authority: the agent has authority to merge dependency upgrades (given), so the "outside the agent's authority" disqualifier from the spec's uncertainty list does not apply.

Since the decision is sufficiently determined and within the agent's authority, per the `AUTO` execution table (row: `AUTO` = yes, sufficiently determined = yes): **the agent resolves the decision itself, the human is not asked**, and the outcome `merge.approved` is established "exactly as if a human had given that answer."

The fact that "no human is currently online" is not consulted at all in this branch: `AUTO` does not fail over to asking a human because a human happens to be unavailable; it only asks a human when the decision itself is uncertain or outside the agent's authority. Here the decision is certain and in-authority, so no human is contacted, and whether a human is online is irrelevant to this outcome.

Because the human is never asked, the response is neither "unavailable" nor "insufficient" (those categories only describe an actual solicited human response). Per spec, "`FALLBACK` applies only afterwards, if the human's response is unavailable or insufficient" and "`AUTO` and `FALLBACK` are different mechanisms. When `AUTO` cannot resolve a decision, the decision goes to the human through the normal `HITL`; this is not a fallback." Since `AUTO` *did* resolve the decision, the fallback flow (`→ FALLBACK → TRANSITION "Blocked" → STOP`) is **not entered**.

Execution continues with the statement after the whole `HITL` construct (the `FALLBACK` block is part of the `HITL` construct's syntax, so "after the construct" means after that nested block too), i.e. with the first `WHEN`.

**4. `WHEN merge.approved`**
Evaluated once, in declaration order. The outcome `merge.approved` was just established in step 3, so the condition is satisfied. Its flow executes:
- `→ TRANSITION "Merged"` — the current process state becomes `Merged`.

Execution then continues with the statement after this `WHEN` (no `BREAK`/`STOP` occurred in its flow).

**5. `WHEN merge.declined`**
Evaluated independently of the previous `WHEN` (per spec: "no implicit else", "no first match wins"). The outcome established was `merge.approved`, not `merge.declined`, so this condition is not satisfied. Per spec, "an unmatched `WHEN` is not an error; it does not stop, wait, or escalate." The flow is skipped.

**6. End of program**
This was the last top-level statement. Per spec, "`STOP` is not required at the end of a process. When the last top-level statement has completed, execution ends normally." Execution ends.

## Trace summary

| Step | Statement | Effect |
|---|---|---|
| 1 | `DELEGATE dependency-upgrade` | Work assigned (no outcome yet) |
| 2 | `VERIFY dependency-upgrade` | Establishes `dependency-upgrade.accepted` |
| 3 | `HITL:merge(...) AUTO` | Criterion fully satisfied by available info + agent has authority → agent auto-resolves → establishes `merge.approved`; human not asked; `FALLBACK` not entered |
| 4 | `WHEN merge.approved` | Condition true → `TRANSITION "Merged"` (state = `Merged`) |
| 5 | `WHEN merge.declined` | Condition false → skipped |
| 6 | (end) | Execution ends normally, no `STOP` needed |

## Answers

- **Final process state:** `Merged` (set by the `TRANSITION "Merged"` executed under `WHEN merge.approved`).
- **Is a human asked?** No. The `AUTO` marking allows the agent to resolve the decision itself because the available information (verification accepted the upgrade) and the changelog (bug fixes only, i.e. no breaking change) jointly and unambiguously satisfy the stated merge criterion, and the agent has the authority to make that call. Per the spec's `AUTO` table, when the decision is sufficiently determined the human is not asked at all — this holds regardless of the (here, moot) fact that no human is currently online.
- **Is `FALLBACK` used?** No. `FALLBACK` is only used when a human was actually asked and that human's response is unavailable or insufficient. Since `AUTO` resolved the decision and no human was ever asked, the `FALLBACK` flow (`TRANSITION "Blocked"` then `STOP`) never runs.

## Assumptions / points the specification does not itself determine

The DSL specification deliberately does not define *how* `AUTO`'s "sufficiently determined" judgment is computed (it explicitly says `AUTO` "defines when automatic decision resolution is permitted, not an algorithm or confidence threshold"). The concrete merge criterion, the fact that `VERIFY` established `accepted`, the changelog content, the authority grant, and human availability are all supplied by the task's context, not by the specification. Given the specification's rule set, the only assumption needed to reach a determinate answer is:

- Interpreting "the changelog lists only bug fixes" as satisfying the criterion's clause "the changelog announces no breaking change" (i.e., a changelog containing only bug-fix entries is read as announcing no breaking change). This is a natural, essentially unambiguous reading of the given facts, not a specification gap, but it is stated explicitly here since the specification itself has no notion of "changelog" or "breaking change" — those are process-specific criteria supplied outside the DSL, and the DSL only requires that such criteria, once given, be applied to determine whether a decision is "sufficiently determined."

No other part of the task is underdetermined by the specification: the `HITL`/`AUTO`/`FALLBACK` interaction, the independent evaluation of the two `WHEN` constructs, and normal termination without an explicit `STOP` are all fully fixed by the rules quoted above.
