# Execution of the go_harness program

## Program under analysis

```text
DELEGATE dependency-upgrade
VERIFY dependency-upgrade
AUTO HITL:merge("Merge the dependency upgrade?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Deferred"
```

All statements are at the top level (no enclosing `LOOP`/`WHEN`/`FORK`), so they form a single sequential flow executed in declaration order (per **Flow**: "A statement starts only after the previous statement in the same flow has completed"). The `→ FALLBACK` block is nested *inside* the `HITL` construct (per the grammar: `hitl = [AUTO] HITL ... NL [INDENT "→" "FALLBACK" NL INDENT flow DEDENT DEDENT]`), not a separate top-level statement. The two `WHEN` statements sit at the same indentation as `HITL`, so they are the statements that follow the whole `HITL` construct (fallback included).

## Step-by-step trace

**Step 1 — `DELEGATE dependency-upgrade`**
Work is assigned to an actor. Per the spec, `DELEGATE` "does not mean that the work is correct, complete, or accepted" — it only records that another actor is responsible for the work. No outcome is established by this statement itself.

**Step 2 — `VERIFY dependency-upgrade`**
The delegated result is evaluated against acceptance criteria. The task states this establishes `accepted`, i.e. the outcome `dependency-upgrade.accepted` is established (parallel to the spec's own example, `VERIFY implementation` establishing `implementation.accepted`). Per the spec, `VERIFY` "does not branch by itself" — execution simply continues to the next statement regardless of the outcome; the outcome is only *available* for later use.

**Step 3 — `AUTO HITL:merge("Merge the dependency upgrade?")`**
This is a `HITL` marked `AUTO`, so automatic resolution is attempted first (per the `AUTO` execution table).

- Applicable criterion (given by the surrounding process, not the DSL): "merge when verification accepts the upgrade and the changelog announces no breaking change."
- Available information: `dependency-upgrade.accepted` was just established (Step 2), and the changelog lists only bug fixes, i.e. it announces no breaking change.
- Both conditions of the criterion are met, and neither is missing, contradictory, or ambiguous; no second, materially different decision is compatible with this evidence and criterion. So the decision is "sufficiently determined" in the sense required by `AUTO`.
- Authority: the spec lists "the agent does not have the authority required to make the decision" as a source of uncertainty. Here the context states the process explicitly gives the agent authority to merge dependency upgrades, so this source of uncertainty is absent.

Consequently, per the `AUTO` table (row "yes / yes"): **the agent resolves the decision itself. The human is not asked.** The outcome `merge.approved` is established "exactly as if a human had given that answer."

Because the human is never asked, the question of the response being "unavailable" (e.g. because no human is online) never arises — the fact that "no human is currently online" given in the context turns out to be irrelevant to this run, since the flow never reaches the point of waiting for a human response. Per the spec, `FALLBACK` is used "only if the human is asked and the response is unavailable or insufficient," and `AUTO` resolution is explicitly distinguished from `FALLBACK`: "When `AUTO` cannot resolve a decision, the decision goes to the human through the normal `HITL`; this is not a fallback. `FALLBACK` applies only afterwards, if the human's response is unavailable or insufficient." Here `AUTO` *does* resolve the decision, so this fallback machinery is never entered.

**→ FALLBACK block: not executed.** It exists in the program text as part of the `HITL` construct but is only ever used when the human is asked and gives no usable answer; that condition never occurs in this run.

**Step 4 — after the `HITL` construct**
Per `AUTO`'s execution rule: "After the decision is made, by the agent or by the human, execution continues with the statement after the `HITL` construct." The `HITL` construct (including its nested `FALLBACK`) is now complete, with `merge.approved` established. Execution proceeds to the next top-level statement.

**Step 5 — `WHEN merge.approved`**
This `WHEN` is evaluated once, now, in declaration order. Its condition (`merge.approved`) matches the outcome just established, so it is satisfied. Its flow executes:
- `TRANSITION "Merged"` — the current process state becomes `"Merged"`.

After the flow completes (no `BREAK`/`STOP` occurred inside it), execution continues with the statement after this `WHEN`.

**Step 6 — `WHEN merge.declined`**
Evaluated once, now. `merge.declined` was not established (only `merge.approved` was), so the condition is not satisfied. Per the spec, "each `WHEN` is independent... there is no implicit 'else'"; this unmatched `WHEN` is simply skipped, and this is not an error. No flow executes.

**End of program**
There is no further statement, and `STOP` was never reached. Per the spec, "`STOP` is not required at the end of a process. When the last top-level statement has completed, execution ends normally." Execution ends normally after Step 6.

## Final process state

**`"Merged"`** — established by `TRANSITION "Merged"` in Step 5, and never overwritten afterward (the only other `TRANSITION` in the program, `TRANSITION "Deferred"`, is inside the `merge.declined` flow, which did not execute; the `FALLBACK`'s `TRANSITION "Blocked"` also did not execute).

## Is a human asked?

**No.** The `AUTO` marker permits automatic resolution when the decision is "sufficiently determined" by the available information, applicable criteria, and the agent's authority. Here the process's explicit merge criterion is fully satisfied by known facts (verification accepted; changelog shows no breaking change) and the agent has been explicitly granted authority to merge dependency upgrades — there is no missing/contradictory information, no ambiguous criterion, and no competing decision compatible with the evidence. Per the `AUTO` execution table, this is exactly the "yes / yes" case: the agent resolves `merge.approved` on its own, and "the human is **not** asked."

The context detail "no human is currently online" does not change this: it would only matter if the decision were *not* sufficiently determined (forcing a real `HITL` ask, which could then find no one available); since `AUTO` already resolves the decision, that path is never taken.

## Is the FALLBACK used?

**No.** `FALLBACK` is defined as the flow to use "when an expected response is unavailable or insufficient," and applies "only if the human is asked and the response is unavailable or insufficient." Since the human is never asked in this run (the decision was resolved automatically by `AUTO`), there is no response to be unavailable or insufficient, so `FALLBACK`'s trigger condition is never met. The `→ FALLBACK` block (`TRANSITION "Blocked"`, `STOP`) remains present in the program but unexecuted for this run.

## Assumptions made (spec does not itself determine these)

The DSL specification is explicit that operations like `VERIFY`, `AUTO`, and `HITL` describe *what* happens semantically, not the implementation mechanism, and that `AUTO`'s determination of "sufficiently determined" is not governed by any DSL-defined algorithm or threshold. The following judgment calls were needed to apply the spec to this task's context, and are stated explicitly:

1. **Outcome naming for `VERIFY`.** The spec does not give a formal rule for how `VERIFY <result>` names its outcomes beyond its own example (`implementation.accepted`/`implementation.rejected`). I assumed, by the same pattern and because the task explicitly says "`VERIFY dependency-upgrade` establishes `accepted`," that the outcome established is `dependency-upgrade.accepted`.
2. **Treating the given merge criterion and context facts as the "applicable criteria" and "available information" for `AUTO`.** The DSL itself does not encode process-specific criteria (e.g., what "merge criterion" means, what counts as "no breaking change"); these are supplied by the task's surrounding-process context, which the spec explicitly allows (`AUTO` resolves using "the available information, criteria, and authority" from the surrounding process, not from the DSL). I assumed the task intends these context statements to be read as jointly and unambiguously satisfying the stated criterion, with no hidden contradiction — since the spec says a confidence score alone would not be enough, but here there is no scored/uncertain judgment involved, only a direct match of two explicitly stated boolean facts (verification accepted; changelog contains only bug fixes) against an explicit two-part criterion.
3. **Treating "the process gives the agent authority to merge dependency upgrades" as satisfying the authority precondition for `AUTO`.** The spec lists lack of authority as a source of uncertainty but does not define how authority is represented in the DSL; I treated the context's explicit grant of authority as dispositive, since the DSL leaves authority to be a property of "the surrounding process," which the task states directly.
4. **Scope of the `FALLBACK` block.** The spec's grammar nests `→ FALLBACK ... flow` inside the `hitl` production itself, and states "statements after the `HITL` construct... are not part of the fallback flow." I therefore treated the two `WHEN` statements (written at the same indentation as `HITL`) as following the entire `HITL` construct, including its `FALLBACK`, rather than as being somehow separate from or racing with the fallback. This follows directly from the indentation/scope rules, but is stated explicitly since it determines that reaching the `WHEN`s does not depend on whether the fallback flow ran.

No other indeterminacies were encountered: the program is well-formed under the grammar (single `HITL` with attached `FALLBACK` at top level, followed by two independent `WHEN`s), and every executed statement's behavior is fully pinned down by the spec's stated execution rules given the outcomes established above.
