```text
DELEGATE implementation
VERIFY implementation
HITL:merge("Merge this change?")
  → AUTO
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **Argument identifier for the delegated/verified work**: the requirement says "the implementation" without giving it a formal identifier, so I used the identifier `implementation` for both `DELEGATE` and `VERIFY` (matching the spec's own recurring example), on the assumption that `VERIFY implementation` evaluates the result of `DELEGATE implementation`.

2. **No `WHEN` after `VERIFY implementation`**: the requirement does not say the implementation's verification outcome (accepted/rejected) itself branches the flow — it only says a merge decision follows. Per the spec, "`VERIFY` with no `WHEN` after it does not gate the process," so I let execution proceed unconditionally from `VERIFY implementation` into the merge decision. I assumed the requirement intends the merge decision to be the only gating point, not the implementation's own verification.

3. **`HITL` name**: I named the decision `merge` (`HITL:merge(...)`) because the spec requires a name whenever `WHEN <name>.<answer>` constructs reference it, and the requirement needs two such references (merge vs. no-merge outcomes).

4. **Answer identifiers `approved` / `declined`**: the spec says the human's answer must correspond to "one of the answers tested by the `WHEN <name>.<answer>` constructs," but it does not fix vocabulary. I chose `merge.approved` and `merge.declined` as reasonable identifiers for "decision is to merge" / "decision is not to merge." Any other consistent pair of identifiers (e.g. `merge.yes`/`merge.no`) would be equally valid under the spec.

5. **`AUTO` placement and ordering**: since the requirement allows the agent to resolve the merge decision automatically when clearly determined, and otherwise requires asking a human, I attached `→ AUTO` directly under the `HITL`. Per the spec, when both `AUTO` and `FALLBACK` are present, `AUTO` must come first, which I followed.

6. **`FALLBACK` handling of "no usable answer"**: I mapped "the human gives no usable answer" to the spec's `FALLBACK` mechanism (covering both "unavailable" and "insufficient" responses), since the DSL does not distinguish between those two failure modes for the requirement's purpose — both mean the normal flow cannot continue.

7. **`STOP` inside `FALLBACK` ends the whole execution**, per the spec, so no further statement (including the `WHEN merge.approved` / `WHEN merge.declined` checks) executes after the fallback runs. This matches the requirement's "transition to state 'Blocked' and stop," since a human never actually answers `merge.approved` or `merge.declined` in that case.

8. **No `REQUIRE` statement**: the requirement does not mention any precondition or required resource, so I did not introduce a `REQUIRE`. The spec does not force one to exist.

9. **No `EMIT`**: the requirement does not ask for any artifact to be produced, only state transitions and delegation/verification, so no `EMIT` statement was included.

10. **No `LOOP`**: the requirement describes a single, one-shot sequence (implement → verify → decide → transition/stop) with no repetition or retry described, so I did not wrap any part of it in a `LOOP`.

11. **Top-level flow, no enclosing scope assumed**: per "Programs, fragments, and validity," a construct is not assumed to be enclosed in a scope not shown. I wrote the whole program as a flat, top-level sequence of statements (with `WHEN` and `HITL` introducing their own indented children), since the requirement gives no indication of an outer `LOOP` or other enclosing construct.

12. **Two `WHEN` after `HITL`/`AUTO` resolution, not nested inside `HITL`**: per the grammar, a `HITL`'s only children are `→ AUTO` and `→ FALLBACK`; the subsequent `WHEN merge.approved` / `WHEN merge.declined` constructs are separate statements at the same indentation as `HITL`, executed afterward in the normal flow, consistent with "after the decision is made, by the agent or by the human, execution continues with the statement after the `HITL` construct."

13. **Both `WHEN` constructs are independent, not else-branches**: per the spec, `WHEN` has no implicit "else." Since `merge.approved` and `merge.declined` are mutually exclusive outcomes from a single `HITL`/`AUTO` resolution (only one answer is ever established), only one of the two `WHEN` blocks will ever match in practice, even though both are always evaluated.

14. **Message string reproduced verbatim**: I used `"Merge this change?"` exactly as quoted in the requirement, treating it as the literal string argument to `HITL`.
