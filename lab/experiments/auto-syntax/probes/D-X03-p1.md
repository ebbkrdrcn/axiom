# Execution Trace

## Assumptions made where the specification does not determine something

The specification defines the DSL's control flow precisely but deliberately leaves several things to "the surrounding process" or "the runtime" (see *Semantic Principles*). For this trace I assume:

1. **`DELEGATE` completes successfully as a statement.** The spec says `DELEGATE` "does not mean that the work is correct, complete, or accepted," and says nothing about the statement itself failing to complete. I treat `DELEGATE dependency-upgrade` as completing (control simply passes to the next statement); whether the *work* is good is a separate question, settled afterward by `VERIFY`.
2. **The "applicable criteria" for `AUTO` are exactly the merge criterion given in the task's context** ("merge when verification accepts the upgrade and the changelog announces no breaking change"). The DSL itself does not define what the applicable criteria are (`AUTO` "defines when automatic decision resolution is permitted, not an algorithm or confidence threshold" — the criteria are supplied by the surrounding process, per *Semantic Principles*). The task context supplies this process-level criterion, so I use it as the standard against which "sufficiently determined" is judged.
3. **The "no human currently online" fact is a fact about response availability, not about whether `AUTO` may resolve the decision.** The spec's table for `AUTO` conditions resolution only on whether the decision is *sufficiently determined* from information/criteria/authority — human availability is not listed as a factor in that determination. So I treat "no human online" as relevant only if the human actually needed to be asked; if `AUTO` resolves the decision first, this fact never comes into play. I flag this explicitly since it is easy to (wrongly) assume the offline human forces a `FALLBACK`.

With these assumptions, the trace below is fully determined by the specification.

## Step-by-step execution

**Step 1 — `DELEGATE dependency-upgrade`**
Work is assigned to an actor. The statement completes; per `DELEGATE`'s definition this says nothing yet about correctness or acceptance. Control moves to the next statement.

**Step 2 — `VERIFY dependency-upgrade`**
The result is evaluated against acceptance criteria. Per the task context, this establishes the outcome `accepted`. Per the spec, `VERIFY` "does not branch by itself" — it only records the outcome; nothing branches here. Control moves to the next statement.

**Step 3 — `AUTO` (on the line directly before the `HITL`)**
`AUTO` marks the immediately following `HITL:merge(...)` as automatically resolvable *if* sufficiently determined. `AUTO` performs no work itself and is not a container; it only sets up how the next statement (`HITL:merge`) is handled.

**Step 4 — `HITL:merge("Merge the dependency upgrade?")` (marked `AUTO`)**
Per the `AUTO` execution table, since this `HITL` carries `AUTO`, the agent must check whether the decision is *sufficiently determined* from available information, criteria, and authority:

- Information: `VERIFY dependency-upgrade` established `accepted` (context), and the changelog lists only bug fixes, i.e. no breaking change (context).
- Criteria: the process's stated merge criterion — "merge when verification accepts the upgrade and the changelog announces no breaking change" — is fully satisfied by that information (both conjuncts hold).
- Authority: the context states the process gives the agent authority to merge dependency upgrades.
- No contradiction, ambiguity, or missing element is present; a single protocol-compatible decision — "approve the merge" — follows from the criteria, and it corresponds to one of the answers tested by the `WHEN merge.approved` / `WHEN merge.declined` constructs that follow, so it is a usable, protocol-compatible resolution.

Because the decision is sufficiently determined and the agent has the authority to make it, per the `AUTO` table (row "yes / yes"): **the agent resolves the decision itself. The human is not asked.** The outcome `merge.approved` is established, exactly as if a human had answered "approved" to the `HITL`.

Since the human is never asked, the *only* condition under which `FALLBACK` is used — "the expected response is unavailable or insufficient," which presupposes the human was asked for a response — does not arise. **`FALLBACK` (`TRANSITION "Blocked"` then `STOP`) is not used.** (The fact that "no human is currently online" is consequently irrelevant here: it would only matter if the human needed to be asked, which never happens.)

Execution continues with the statement after the `HITL` construct.

**Step 5 — `WHEN merge.approved`**
This `WHEN` is evaluated once, in declaration order. The condition `merge.approved` was established in Step 4, so it is satisfied. Its flow executes:
- **`→ TRANSITION "Merged"`** — the current process state becomes `Merged`.

Execution then continues with the statement after this `WHEN` construct (no `BREAK`/`STOP` occurred inside its flow).

**Step 6 — `WHEN merge.declined`**
This `WHEN` is evaluated independently of the previous one (per spec: "no implicit else," "every one whose condition is satisfied executes"). The condition `merge.declined` was never established (the established outcome was `merge.approved`), so this condition is not satisfied. Its flow is skipped; this is not an error. Execution continues with the statement after this `WHEN`.

**End of program**
There are no further top-level statements. `STOP` is not required at the end of a process; per spec, "when the last top-level statement has completed, execution ends normally." Execution ends normally after Step 6.

## Final process state

**`Merged`** — established by `TRANSITION "Merged"` in Step 5, and never subsequently changed (the only other `TRANSITION` in the program, `TRANSITION "Deferred"`, sits inside the `WHEN merge.declined` flow, which did not execute).

## Is a human asked?

**No.** The `HITL:merge(...)` is marked `AUTO`, and the decision was sufficiently determined: `VERIFY dependency-upgrade` established `accepted`, the changelog contains no breaking change, and the agent has the authority to merge — jointly satisfying the process's stated merge criterion with a single, protocol-compatible answer (`approved`). Per the `AUTO` execution rule, when `AUTO` is present and the decision is sufficiently determined, "the agent resolves the decision. The human is **not** asked." The human being offline is immaterial, since the agent never needs to reach them.

## Is `FALLBACK` used?

**No.** `FALLBACK` is triggered only when an expected human response is unavailable or insufficient — which presupposes that the human was asked in the first place. Since `AUTO` resolved the decision automatically and no human was ever asked, the condition for invoking `FALLBACK` never arises. The `FALLBACK` flow (`TRANSITION "Blocked"` then `STOP`) is not executed, and the program does not stop early; it proceeds to establish `merge.approved`, execute `TRANSITION "Merged"`, and end normally.
