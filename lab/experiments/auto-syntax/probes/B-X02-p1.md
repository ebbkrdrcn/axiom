```text
HITL:notes("Short or detailed release notes?") AUTO
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:approval("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Outcome/answer names are invented.** The specification says a `HITL:<name>` response establishes `<name>.<answer>` for whatever answers the following `WHEN <name>.<answer>` constructs test, but it does not fix vocabulary. I chose `notes` as the decision name with answers `short`/`detailed`, and `approval` as the decision name with answers `approved`/`rejected`, since these map directly to the wording of the requirement ("Short or detailed...", "If approved... if rejected...").

2. **No `FALLBACK` is included.** The requirement does not describe what should happen if the human gives no usable response to either `HITL`. Since `FALLBACK` is optional in the grammar (`[ INDENT , "→" , "FALLBACK" , ... ]`) and the task gives no instructions for an unavailable/insufficient response, I omitted it rather than inventing fallback behavior.

3. **`AUTO` is placed only on the first `HITL`.** The requirement explicitly says the notes-format question "may" be answered by the agent when clearly determined (matching `AUTO`'s semantics: resolve automatically when sufficiently determined, otherwise ask the human), while the approval question "must always be given by a human, never by the agent" — this is exactly the default (non-`AUTO`) `HITL` behavior, so no `AUTO` marker is used there.

4. **No `REQUIRE`, `VERIFY`, `LOOP`, `FORK`/`JOIN`, `WAIT`, `BREAK`, or `STOP` are used.** The requirement describes a single straight-line sequence of a decision, a delegation, a second decision, and a terminal action — nothing in the text implies repetition, concurrency, an explicit suspension point, a verification step, or an early/total termination, so none of those constructs were introduced.

5. **The two `WHEN notes.*` branches only `DELEGATE`; no corresponding `VERIFY` follows.** The requirement only says to "delegate short-notes" / "delegate detailed-notes" — it does not ask for the delegated result to be evaluated, so per the spec (`DELEGATE` does not imply correctness or acceptance, and nothing requires a `VERIFY` to follow it) none is added.

6. **`notes.short` and `notes.detailed` are treated as mutually exclusive in practice**, even though the spec says each `WHEN` is evaluated independently with no implicit "else." Since the single `HITL:notes` response can only establish one of the two answers, only one of the two `WHEN` flows will ever match at runtime; both are still written explicitly per the spec's rule that there is no first-match-wins / else construct.

7. **Same independence assumption applies to `approval.approved` / `approval.rejected`** — both `WHEN` blocks are written as independent, sequentially-evaluated constructs, relying on the single `HITL:approval` response to establish exactly one of the two outcomes.

8. **Argument/identifier forms** (`short-notes`, `detailed-notes`, `release`, `"Rework"`) are chosen as plain identifiers or strings per the grammar's `argument = identifier | string` rule; the requirement's own wording ("short-notes", "detailed-notes", "release", "Rework") is used directly since the spec does not prescribe naming beyond identifier syntax (letters, digits, `-`, `_`, starting with a letter).
