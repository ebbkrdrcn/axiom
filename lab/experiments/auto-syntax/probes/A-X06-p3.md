# Answers

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **`wording`** decision may be resolved by the agent itself. It is the only `HITL` marked with `AUTO`:

```text
AUTO HITL:wording("Short or detailed release notes?")
```

The **`release`** decision (`HITL:release("Approve the release?")`) is a plain `HITL` with no `AUTO`. Per the spec, "`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`." Since it is not marked, the agent may never decide it by itself, under any condition — the human must always be asked.

The condition under which the agent may resolve `wording` automatically is given by the `AUTO` semantics: automatic resolution is permitted **only when the decision is sufficiently determined**, i.e. the agent "can determine a single protocol-compatible decision from the available information and applicable criteria." Concretely, this requires that none of the spec's listed forms of uncertainty apply, e.g.:

- the required information (about whether notes should be short or detailed) is present and not contradictory;
- the applicable criteria for choosing between "short" and "detailed" are present, unambiguous, and not contradictory;
- exactly one of `wording.short` / `wording.detailed` is reasonably compatible with the available evidence and criteria (not both, not neither);
- the outcome does not depend on an unresolved interpretation;
- the agent has the authority to make this particular decision.

If all of that holds, the agent establishes `wording.short` or `wording.detailed` itself, exactly as if a human had answered, and execution continues with the `WHEN wording.short` / `WHEN wording.detailed` checks without asking anyone. If any uncertainty of the kinds above exists, the human must be asked instead (see Q3).

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No. This question concerns the **`release`** `HITL`, which in this program is written **without `AUTO`**:

```text
HITL:release("Approve the release?")
```

The spec states: "`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`." Since this `HITL` carries no `AUTO`, the `AUTO`/uncertainty mechanism does not apply to it at all — the table in the spec is explicit: "no [AUTO] → The human is asked. The agent must not decide." regardless of how the decision would be reached.

The fact that "all automated checks are green" and the agent is "highly confident" does not change this. The spec explicitly anticipates and rejects exactly this kind of reasoning for `AUTO`-marked decisions ("A confidence score alone does not establish certainty"), and here it is even more decisive: since `release` is not marked `AUTO` in the first place, confidence/certainty is not even the relevant question — the agent has no authorization to resolve this `HITL` automatically under any level of confidence. The human must be asked "Approve the release?", and only their response can establish `release.approved` or `release.declined` (whichever answers the surrounding `WHEN`s test — here only `release.approved` is tested).

## 3. If the wording decision is not clearly determined, what happens?

This is exactly the "yes `AUTO`, but not sufficiently determined" row of the `AUTO` execution table: "The human is asked, as for a `HITL` without `AUTO`."

So concretely:

- The agent does **not** guess or pick between `wording.short` and `wording.detailed` on its own; `AUTO` is "not a request to guess," and uncertainty must not be resolved by the agent.
- The human is asked the `HITL`'s message, `"Short or detailed release notes?"`, just as if `AUTO` had not been written at all.
- Execution suspends at the `HITL:wording` construct until a usable response is available (per the general `HITL` rule: "The flow containing a `HITL` waits at the `HITL` until either a usable response is available or its `FALLBACK` flow is used").
- Once the human gives an answer that maps to one of the tested answers (`short` or `detailed`), the corresponding outcome — `wording.short` or `wording.detailed` — is established exactly as if the human had answered directly (this is the same as the "no `AUTO`" case), and execution continues with the next statement, i.e. the `WHEN wording.short` / `WHEN wording.detailed` checks, whichever matches.
- **Assumption / gap in the spec as written for this program:** this `HITL:wording(...)` has no attached `→ FALLBACK` flow in the given program. The spec defines `FALLBACK` as optional (the grammar shows the `FALLBACK` block in `[ ... ]`) and says it is used "only when the expected response cannot be used to continue the normal flow" (i.e., the response is unavailable or insufficient). The spec does not state what happens when no `FALLBACK` is present and the response turns out to be unavailable or insufficient. Since "the DSL defines no timeout" for waiting and nothing here substitutes for a missing/insufficient response, the only conclusion supported by the text is that the flow simply remains suspended at `HITL:wording` until a usable response (i.e., an answer that is `short` or `detailed`) eventually arrives — it does not proceed, does not fail, and does not default to either wording choice. I flag this as an explicit assumption because the spec does not directly describe the no-`FALLBACK` case; it only describes the case where a `FALLBACK` flow exists.
