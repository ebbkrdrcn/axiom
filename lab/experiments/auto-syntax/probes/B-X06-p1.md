# Analysis of the go_harness Program

```text
HITL:wording("Short or detailed release notes?") AUTO
WHEN wording.short
  → DELEGATE short-notes
WHEN wording.detailed
  → DELEGATE detailed-notes
HITL:release("Approve the release?")
WHEN release.approved
  → EMIT release
```

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **`wording`** decision (`HITL:wording("Short or detailed release notes?")`) may be resolved by the agent itself. This is the only `HITL` in the program marked with `AUTO`; per the spec, `AUTO` is written directly after the closing parenthesis of one specific `HITL(...)` and "applies only to `HITL`" — it marks *that one* `HITL` as automatically resolvable and no other statement.

The `release` decision (`HITL:release("Approve the release?")`) carries no `AUTO` marker. The spec states: "`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`." Since `HITL:release` is not so marked, the agent may never resolve it itself — a human must always be asked for that decision.

**Condition** under which the agent may resolve `wording` itself: automatic resolution is permitted only when "the agent can determine a single protocol-compatible decision from the available information and applicable criteria" (i.e., the decision is "sufficiently determined"). Per the spec, uncertainty — which forces human involvement even though `AUTO` is present — exists when any of the following hold:

- required information is missing or contradictory;
- applicable criteria are missing, ambiguous, or contradictory;
- multiple materially different decisions (here, `short` vs. `detailed`) remain reasonably compatible with the available evidence and criteria;
- the result depends on an unresolved interpretation;
- the agent lacks the authority required to make the decision.

Only if none of these hold — i.e., the agent can reliably determine a single one of `wording.short` / `wording.detailed` — may it resolve the decision automatically, establishing that outcome "exactly as if a human had given that answer," without asking anyone.

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No. `HITL:release("Approve the release?")` has no `AUTO` marker in this program, and `AUTO` is not inherited, implied, or transferable between `HITL` statements — it applies only to the one `HITL` it is textually attached to (here, `wording`). Since `release` is a plain `HITL` without `AUTO`, the spec's rule applies directly: "The human is asked. The agent must not decide."

The stated confidence ("highly confident") does not change this, for two independent reasons:
- There is no `AUTO` on this `HITL` at all, so the confidence-based determination test never even comes into play.
- Even where `AUTO` is present, the spec explicitly says "A confidence score alone does not establish certainty," so high confidence by itself would not be sufficient grounds for automatic resolution even if `AUTO` had been used.

Green automated checks may be part of the *information* a human uses when answering, but they do not authorize the agent to substitute its own answer for the human's on this `HITL`.

## 3. If the wording decision is not clearly determined, what happens?

`HITL:wording` is marked `AUTO`, so the execution table in the spec applies: "`AUTO` yes, decision sufficiently determined: no (uncertain, or outside the agent's authority) → The human is asked, as for a `HITL` without `AUTO`." So:

- The agent does **not** guess or pick one of `short`/`detailed` on its own.
- The human is asked the message "Short or detailed release notes?", exactly as if `AUTO` were not present.
- Execution at this point in the flow suspends: per the general `HITL` rule, "the flow containing a `HITL` waits at the `HITL` until either a usable response is available or its `FALLBACK` flow is used." Only once a usable human response arrives does execution continue with the next statement (the two `WHEN wording.…` constructs), which will then match `wording.short` or `wording.detailed` according to that response.
- The two `WHEN wording.short` / `WHEN wording.detailed` constructs are evaluated only after the decision (automatic or human) is made; each is evaluated once, in order, and only the one whose condition matches executes its `→ DELEGATE …` flow.

**Explicit note on a gap the specification does not resolve:** This `HITL:wording` has no `→ FALLBACK` block attached in the given program. The spec defines `FALLBACK` as the flow used when a response is "unavailable" (no response ever arrives) or "insufficient" (a response arrives but doesn't answer the question), but it does not state what happens if no `FALLBACK` is written at all and the human's response is unavailable or insufficient. By analogy with `WAIT` ("The DSL defines no timeout... If the event never becomes available, execution remains suspended"), I assume the same applies here: absent a `FALLBACK`, the flow simply remains suspended at `HITL:wording` until a usable response is eventually given; there is no defined mechanism in this program to terminate, defer, or otherwise proceed in the meantime. This is an assumption on my part, not something the specification states outright.
