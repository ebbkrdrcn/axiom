# Analysis of the DSL Program

```text
HITL:wording("Short or detailed release notes?")
  → AUTO
WHEN wording.short
  → DELEGATE short-notes
WHEN wording.detailed
  → DELEGATE detailed-notes
HITL:release("Approve the release?")
WHEN release.approved
  → EMIT release
```

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **`wording`** decision may be made by the agent itself. It is the only `HITL` in this program annotated with `→ AUTO` (per the grammar, `AUTO` is written directly under a `HITL`, indented one level, and "`AUTO` applies only to `HITL`"). The `release` decision (`HITL:release("Approve the release?")`) carries no `→ AUTO`, and the spec is explicit: *"`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`."* So `release` can never be resolved by the agent under this program — it always requires asking the human.

The condition under which the agent may resolve `wording` itself is exactly the condition the spec attaches to `AUTO`:

> "Automatic resolution is permitted only when the agent can determine a single protocol-compatible decision from the available information and applicable criteria."

Concretely, per the AUTO/Uncertainty rules, the agent may decide `wording` itself only if:

- the information needed to choose "short" vs. "detailed" is present and not contradictory,
- the applicable criteria for that choice are present, unambiguous, and not contradictory,
- exactly one of `wording.short` / `wording.detailed` is reasonably compatible with the evidence and criteria (no materially different decision remains equally supportable),
- the decision does not depend on an unresolved interpretation, and
- the agent has the authority to make that decision.

If any of these fail, the decision is "uncertain" and, per the AUTO table, the human must be asked — even though `→ AUTO` is present. (Note also that the spec does not define what "the available information and applicable criteria" for `wording` actually consist of — this program fragment gives no criteria for choosing short vs. detailed notes. The spec does not determine this, so whether `wording` is ever *in practice* sufficiently determined depends on process context not shown here; that is an assumption/gap, not something the DSL resolves.)

## 2. All automated checks are green and the agent is highly confident the release should be approved — may it answer "Approve the release?" itself?

No. `HITL:release("Approve the release?")` has no `→ AUTO` anywhere in this program, so by the rule above the agent must not decide it — regardless of how confident it is. This is reinforced independently by two spec statements:

- `HITL` must not be silently replaced by an agent decision *unless* that specific `HITL` is marked with `AUTO`. This one is not.
- Even where `AUTO` *is* present, "`AUTO` is not a request to guess," and "a confidence score alone does not establish certainty." So even if `→ AUTO` had been attached to `release`, high confidence alone (without it being "sufficiently determined" by information/criteria/authority) would not be enough to license an automatic answer.

So the agent must ask the human "Approve the release?" and wait for a usable response; only that response (or a `FALLBACK`, if one existed — none is defined here) can establish `release.approved` or `release.declined`.

## 3. If the wording decision is not clearly determined, what happens?

Per the `AUTO` execution table, the row "`AUTO` on this `HITL`? yes / Decision sufficiently determined? no (uncertain, or outside the agent's authority)" gives: *"The human is asked, as for a `HITL` without `AUTO`."* So:

1. The agent does **not** guess or pick a default; it asks the human the message `"Short or detailed release notes?"`.
2. Per the `HITL` rules, "the flow containing a `HITL` waits at the `HITL` until either a usable response is available or its `FALLBACK` flow is used." Execution therefore suspends at `HITL:wording`.
3. This particular `HITL:wording` has **no `→ FALLBACK`** attached (only `→ AUTO`). The spec defines `FALLBACK` as being used "only if the human is asked and the response is unavailable or insufficient," but it does not state what happens when no `FALLBACK` is defined at all for that `HITL`. This is not determined by the specification, so here is the assumption I make: absent a `FALLBACK`, there is simply no fallback flow to use, and execution behaves like `WAIT` with no timeout — it "remains suspended" until a usable human response arrives establishing `wording.short` or `wording.detailed` (the only two answers tested by the following `WHEN` constructs). No fabricated or degraded continuation is permitted (this mirrors the `REQUIRE` principle that execution must not proceed as if satisfied).
4. Once a usable response arrives (i.e., "short" or "detailed"), execution continues with the statement after the `HITL:wording` construct: the two `WHEN wording.short` / `WHEN wording.detailed` constructs are evaluated in order, and whichever one matches the human's answer runs its `→ DELEGATE ...` flow (only one will match, since the human gave one answer). Execution then proceeds to `HITL:release(...)`.

### Explicit assumptions made

- The spec does not specify the criteria by which "wording" would be considered sufficiently determined (no acceptance/decision criteria for short-vs-detailed notes are given in this fragment); whether automatic resolution is ever actually possible for `wording` in a real run depends on process context outside this program, which the DSL by design does not prescribe.
- The spec does not state what occurs when a `HITL` has no `→ FALLBACK` and the human must be asked. I assumed (by analogy to `WAIT`'s "no timeout, remains suspended" rule and to `REQUIRE`'s "must not proceed as if satisfied") that execution simply waits indefinitely at that `HITL` for a usable response, rather than terminating, erroring, or proceeding some other way.
