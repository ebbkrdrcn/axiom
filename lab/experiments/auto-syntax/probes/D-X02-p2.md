```text
AUTO
HITL:notes("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:approve("Approve the release?")
WHEN approve.approved
  → EMIT release
WHEN approve.rejected
  → TRANSITION "Rework"
```

## Assumptions

The specification leaves several things undetermined for this requirement; the DSL above reflects the following explicit choices:

1. **Outcome/answer identifiers are not given by the task and had to be invented.**
   - The first decision is named `notes` (arbitrary label), with answers `short` and `detailed`, taken directly from the task's own wording ("If short, ... if detailed, ..."). The spec only requires that `<name>.<answer>` match some `WHEN <name>.<answer>` that follows it; it does not prescribe the answer vocabulary.
   - The second decision is named `approve` (arbitrary label), with answers `approved` and `rejected`, taken directly from the task's wording ("If approved, ... if rejected, ..."). Again, the spec does not fix this vocabulary.

2. **`AUTO` is placed only on the first `HITL`.** The task says the agent "may answer this question itself when the answer is clearly determined," which matches `AUTO`'s defined semantics (resolve automatically only when sufficiently determined, otherwise ask the human). The second question is explicitly required to "always be given by a human, never by the agent," so no `AUTO` line precedes the second `HITL` — per the spec, the absence of `AUTO` means the human is always asked and the agent must not decide.

3. **No `FALLBACK` is included for either `HITL`.** The task does not describe what should happen if a human response is unavailable or insufficient, and the spec makes `FALLBACK` optional (the grammar shows it in brackets). Since the specification says a program must not have behavior invented for it beyond what is stated, no fallback flow was added.

4. **No `REQUIRE` was added.** The task states no precondition (e.g., a repository or prior artifact) that must be available before this flow runs, so none is declared.

5. **DELEGATE/EMIT/TRANSITION arguments are taken verbatim from the task's nouns as identifiers/strings:**
   - `DELEGATE short-notes` / `DELEGATE detailed-notes` — treated as identifiers (letters, digits, `-`, `_`, starting with a letter), matching the task's own hyphenated phrasing.
   - `EMIT release` — treated as an identifier naming the artifact, per the task's "emit release."
   - `TRANSITION "Rework"` — written as a string, consistent with the spec's own `TRANSITION "Code Review"` example style for named states.

6. **No `VERIFY` statements were added.** The task never asks for delegated work (`short-notes`/`detailed-notes`) to be evaluated against acceptance criteria — it only asks for delegation followed directly by the approval question. Since `VERIFY` is a distinct operation from `DELEGATE` and the task gives no acceptance criteria for the notes, none was inserted.

7. **No `LOOP` or `FORK`/`JOIN` was used.** The task describes a single linear sequence of two human decisions with no repetition and no concurrent work, so no looping or concurrency constructs were introduced.

8. **Indentation depth/spacing is an arbitrary but consistent choice** (2 spaces per level); the spec states only relative depth matters, not the exact number of spaces.

9. **The two `WHEN` blocks after each `HITL` are treated as mutually exclusive in practice** (since a single human/agent answer to one question yields exactly one `<name>.<answer>` outcome), but per the spec each `WHEN` is independently evaluated — there is no implicit "else." This has no practical effect here since only one of `notes.short`/`notes.detailed` (and likewise for `approve`) can be established by a single answer, but it is worth noting as a semantic point rather than an assumption that changes the DSL.
