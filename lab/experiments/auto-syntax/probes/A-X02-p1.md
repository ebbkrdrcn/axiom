```text
AUTO HITL:notes("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:approve("Approve the release?")
WHEN approve.approved
  → EMIT release
WHEN approve.rejected
  → TRANSITION "Rework"
```

## Assumptions

- **Answer identifiers**: The requirement names the two choices only in prose ("short or detailed", "approved or rejected"). The spec says a `HITL` response establishes `<name>.<answer>` where `<answer>` is whatever the following `WHEN` constructs test, but it does not fix the literal spelling of these identifiers. I chose `notes.short` / `notes.detailed` and `approve.approved` / `approve.rejected` as the natural mapping.
- **`AUTO` only on the first `HITL`**: The requirement explicitly allows the agent to answer the notes-format question when it is "clearly determined," which matches `AUTO`'s definition (resolve automatically only when sufficiently determined; otherwise ask a human). The approval question is explicitly required to "always be given by a human, never by the agent," so it is written as a plain `HITL` without `AUTO`, per the spec's rule that `HITL` must not be silently replaced by an agent decision unless marked `AUTO`.
- **No `FALLBACK`**: The requirement does not describe what should happen if a human response is unavailable or insufficient for either question. Since the spec makes `FALLBACK` optional (a `HITL` may appear without one) and does not let me invent unrequested behavior, I omitted `FALLBACK` for both `HITL` statements. Per the spec, this means each flow simply waits at its `HITL` until a usable response becomes available; there is no defined timeout or escalation.
- **No `VERIFY` after `DELEGATE short-notes` / `DELEGATE detailed-notes`**: The requirement does not ask for the delegated notes to be evaluated or gated on an outcome, so no `VERIFY`/`WHEN` pair was added after these delegations. `DELEGATE` alone only assigns the work; per the spec it does not imply the work is correct or complete, but the requirement gives no acceptance criteria to check.
- **No `REQUIRE`**: The requirement states no prerequisite information, context, or state that must be available before execution, so no `REQUIRE` statement was included.
- **Sequential, not concurrent, structure**: The requirement's "First ... Then ..." phrasing describes one sequential process, so the two `HITL`/`WHEN` groups are written as a plain sequential flow at the top level, not inside a `FORK`/`JOIN`.
- **No `LOOP`**: The requirement describes a single pass through the two decisions with no repetition, retry, or "loop until accepted" language, so no `LOOP` construct was used.
- **No explicit `STOP`**: The spec states `STOP` is not required at the end of a process; execution ends normally once the last top-level statement (the second pair of `WHEN` constructs) completes. So no trailing `STOP` was added.
- **Naming the `HITL` decisions**: Both `HITL` statements are named (`notes`, `approve`) because subsequent `WHEN` constructs refer to their outcomes, which the spec requires (`<name>` may be omitted only "when no `WHEN` refers to the decision").
- **Identifier choice for delegated work**: `short-notes` and `detailed-notes` are used as `DELEGATE` arguments (valid identifiers: letters, digits, `-`, `_`, starting with a letter), taken directly from the requirement's own wording ("delegate short-notes", "delegate detailed-notes").
- **`EMIT release` / `TRANSITION "Rework"` as the only outcome-handling statements**: The requirement specifies exactly one action per approval outcome (emit an artifact on approval, transition state on rejection), so each `WHEN` flow contains exactly that one statement, with no additional implied behavior (e.g., no `STOP` or `BREAK` after either, since there is no enclosing `LOOP` and the requirement does not ask execution to halt).
