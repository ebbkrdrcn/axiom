# Validity Analysis of DSL Snippets

## Snippet 1

```text
HITL:deploy("Deploy to production?")
  → AUTO
WHEN deploy.yes
  → EMIT deployment
```

**Verdict: VALID**

Rule basis:

- The grammar for `hitl` is: `"HITL" , [ ":" , identifier ] , "(" , string , ")" , NL , [ INDENT , [ "→" , "AUTO" , NL ] , [ "→" , "FALLBACK" , ... ] , DEDENT ]`. A `HITL:deploy("...")` followed by an indented `→ AUTO` with no `→ FALLBACK` matches this production exactly (`→ FALLBACK` is optional).
- Syntax section, Statement table: `→ AUTO` is listed as valid "(only directly under a `HITL`)" — and here it is written directly under, and indented one level under, the `HITL:deploy(...)` line, exactly as required by the `AUTO` section: "`→ AUTO` is written directly under a `HITL`, indented one level."
- `<name>` on the `HITL` is `deploy`, and the outcome tested afterward is `deploy.yes`, i.e. `<name>.<answer>` with `<name>` matching the `HITL`'s name, consistent with: "The response establishes the outcome `<name>.<answer>`, where `<answer>` is one of the answers tested by the `WHEN <name>.<answer>` constructs that follow."
- After the `HITL` construct (with its `AUTO` child) ends, `WHEN deploy.yes` appears at the same indentation as `HITL`, which is the normal flow continuing after the `HITL` construct, per "After the decision is made, by the agent or by the human, execution continues with the statement after the `HITL` construct."

No rule in the specification is violated; the snippet is well-formed.

## Snippet 2

```text
DELEGATE implementation
  → AUTO
VERIFY implementation
```

**Verdict: INVALID**

Rule basis:

- This matches the specification's own explicit counter-example verbatim in the `AUTO` section: "Invalid, because `AUTO` applies only to `HITL`: `DELEGATE implementation` / `→ AUTO`".
- More generally: "`AUTO` applies only to `HITL`." `DELEGATE` is a `simple` statement in the grammar (`simple = ("REQUIRE"|"DELEGATE"|"VERIFY"|"TRANSITION"|"EMIT") , argument , NL`), which has no `INDENT`/children in the grammar at all — a `simple` statement cannot have anything nested under it. Scope rule 4 confirms only `LOOP`, `WHEN`, `FORK`, `HITL` (for `→ AUTO`/`→ FALLBACK`), `→ FALLBACK`, and `→` items may have indented children; `DELEGATE` is not among them, so indenting `→ AUTO` beneath it is also an illegal indentation under Scope rule 6 ("Any other indentation is invalid... an indented line under a plain statement that is not a `→` item... is invalid").

The program must be rejected as a whole (per "Programs, fragments, and validity": a program violating a "must not" rule is not well-formed and is rejected, not executed with the offending part skipped).

## Snippet 3

```text
AUTO HITL:deploy("Deploy to production?")
WHEN deploy.yes
  → EMIT deployment
```

**Verdict: INVALID**

Rule basis:

- Syntax, "Statement" section: "Each statement occupies one line and starts with a keyword." A line beginning with `AUTO` followed by `HITL:deploy(...)` on the same line is not any of the listed statement forms — it is neither a bare `HITL[:<name>]("<message>")` statement nor a `→ AUTO` item; it does not match the `hitl` grammar production (`"HITL" , [":" , identifier] , "(" , string , ")" , NL , ...`) because the line does not start with the `HITL` keyword at all.
- The `AUTO` section is explicit about the only valid placement: "`→ AUTO` is written directly under a `HITL`, indented one level." Grammatically, `AUTO` can only appear as the token sequence `"→", "AUTO", NL` inside the `INDENT ... DEDENT` block that follows a `HITL`'s `NL`, on its own line, after the `HITL` line is already complete. Prefixing `HITL` with `AUTO` on the same line has no corresponding grammar production, so it is not a well-formed statement.

The snippet is not well-formed and must be rejected as a whole.

## Snippet 4

```text
AUTO
  WHEN decision.uncertain
    → HITL("Approve?")
```

**Verdict: INVALID**

Rule basis:

- This matches the specification's own explicit counter-example verbatim in the `AUTO` section: "Also invalid, because `AUTO` never contains a flow and uncertainty is not a condition: `AUTO` / `  WHEN decision.uncertain` / `    → HITL("Approve?")`".
- Supporting rules: "`AUTO` is not a control-flow container. It does not contain `WHEN`, `→`, or an arbitrary flow." and "Uncertainty is not a DSL condition, state, variable, or keyword." Also "`AUTO` is not a statement of its own and applies to no other statement. `AUTO` applies only to `HITL`" — here `AUTO` appears as a bare top-level construct with its own nested block, which the grammar does not define at all (there is no `auto` production in the EBNF; `AUTO` only exists as the fixed token sequence `"→", "AUTO", NL` inside a `hitl` construct).
- Additionally, `WHEN decision.uncertain` treats "uncertain" as if it were a condition outcome (`<identifier>.<identifier>`), which the grammar permits syntactically as a `condition`, but the specification explicitly states this is not a legitimate use: uncertainty is determined by the runtime as part of `AUTO` resolution, not a condition a `WHEN` can test ("The DSL runtime determines uncertainty as part of automatic decision resolution.").

The snippet is not well-formed and must be rejected as a whole.

---

## Note on assumptions

The specification fully determines the validity of all four snippets — three of the four (Snippets 2 and 4 exactly, and Snippet 3 by direct application of the same "AUTO applies only to HITL"/statement-form rules) are covered by explicit worked examples or explicit grammar/syntax statements in the text, and Snippet 1 is a straightforward positive instance of the `hitl` grammar production with `→ AUTO` and no `→ FALLBACK`. No assumption beyond the given specification was required.
