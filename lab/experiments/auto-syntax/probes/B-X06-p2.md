# Answer

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **`wording`** decision (`HITL:wording("Short or detailed release notes?") AUTO`) may be resolved by the agent itself. This is because `AUTO` is written directly after the closing parenthesis of that `HITL`, and per the spec "`AUTO` is written directly after the closing parenthesis of `HITL(...)`, on the same line. It marks that one `HITL` as automatically resolvable." `AUTO` applies to no other statement.

The `release` decision (`HITL:release("Approve the release?")`) has no `AUTO` marker, so it may **not** be resolved by the agent under any condition — the spec states "`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`."

The condition under which the agent may resolve `wording` by itself: automatic resolution is permitted **only when the agent can determine a single protocol-compatible decision from the available information and applicable criteria** — i.e., the decision is "sufficiently determined." Per the execution table for `AUTO`:

- If sufficiently determined → the agent resolves it; the outcome `wording.short` or `wording.detailed` is established exactly as if a human had answered, and the human is not asked.
- If uncertain (required information/criteria missing, ambiguous, or contradictory; multiple materially different answers remain reasonably compatible; the result depends on an unresolved interpretation; or the agent lacks the authority) → the human is asked, exactly as for a `HITL` without `AUTO`.

The spec is explicit that "a confidence score alone does not establish certainty," so determinacy must come from the available information and applicable criteria, not merely from the agent's self-assessed confidence.

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No. The `HITL:release("Approve the release?")` statement carries no `AUTO` marker. Per the spec, `AUTO` "applies directly after the closing parenthesis of `HITL(...)`, on the same line," and only marks "that one `HITL`" — it is not inherited, implied, or extended to other `HITL` statements from context or from a preceding `AUTO` on `wording`. Since this `HITL` is a plain `HITL` (no `AUTO`), the rule "`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`" applies directly: the agent must not decide it, however confident it is.

This is reinforced independently by the general `AUTO` rule that "a confidence score alone does not establish certainty" — so even if `release` *had* carried `AUTO`, high confidence based on green checks alone would not by itself be sufficient grounds for automatic resolution unless the applicable criteria for approval are actually, determinately met. But the more fundamental reason here is simply that `release`'s `HITL` is not marked `AUTO` at all, so the human must be asked; the agent must not decide.

## 3. If the wording decision is not clearly determined, what happens?

This is exactly the "uncertain" case in the `AUTO` execution table (`AUTO` present, decision **not** sufficiently determined). Per the spec: "The human is asked, as for a `HITL` without `AUTO`." Concretely:

- The agent does not guess or fabricate an answer for `wording`; `AUTO` "is not a request to guess."
- The human is asked the message "Short or detailed release notes?"
- The flow containing the `HITL` "waits at the `HITL` until either a usable response is available or its `FALLBACK` flow is used." No `FALLBACK` is attached to `HITL:wording` in this program, so per the grammar `FALLBACK` is optional and none is defined here — the specification does not state what occurs if a response is unavailable/insufficient and no `FALLBACK` exists. **The specification does not determine this case explicitly, so I assume** (consistent with `WAIT`'s rule that "if the event never becomes available, execution remains suspended") that execution simply remains suspended at `HITL:wording` until a usable response ("short" or "detailed") arrives, since there is no fallback flow to divert to.
- Once a usable human response is available, execution continues with the next statement after the `HITL:wording` construct: the two `WHEN` statements are evaluated in order. Each `WHEN` is evaluated independently (no "else"/"first match wins"), so whichever of `wording.short` / `wording.detailed` matches the human's answer has its flow (`DELEGATE short-notes` or `DELEGATE detailed-notes`) executed; the other `WHEN` is simply skipped (an unmatched `WHEN` is not an error). Execution then proceeds to `HITL:release`.

## Assumptions made where the specification did not determine something

- The specification's `HITL`/`FALLBACK` sections describe behavior "unavailable or insufficient" only in the context of a `FALLBACK` being present. For `HITL:wording` in this task, no `FALLBACK` is written. The spec does not explicitly state what happens when a response is unavailable/insufficient and no `FALLBACK` exists. I assumed, by analogy with `WAIT`'s explicit "no timeout... execution remains suspended" rule, that the flow simply remains suspended at the `HITL` until a usable response eventually arrives, since there is no fallback to route to instead.
- The spec does not define what "sufficiently determined" means in operational/technical terms beyond the listed examples of uncertainty; I have treated the listed examples (missing/contradictory information, ambiguous/contradictory criteria, multiple reasonably compatible answers, unresolved interpretation, lack of authority) as the governing test, per the spec's own wording, rather than inferring any additional criteria.
