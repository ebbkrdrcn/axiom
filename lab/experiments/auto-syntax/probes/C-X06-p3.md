# Analysis of the go_harness program

```text
HITL:wording("Short or detailed release notes?")
  → AUTO
WHEN wording.short
  → DELEGATE short-notes
WHEN wording.detailed
  → DELEGATE detailed-notes
HITL:release("Approve the release?")
WHEN release.approved
  → EMIT release
```

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **`wording`** decision may possibly be made by the agent itself. It is the only `HITL` in the program that carries a `→ AUTO` child (`HITL:wording(...)` is immediately followed by `→ AUTO`, indented one level under it, exactly matching the required syntax `HITL:<name>("<message>") / → AUTO`).

The `release` decision (`HITL:release("Approve the release?")`) has **no** `→ AUTO` under it. Per the spec:

> `HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`.

Since `release` is not marked with `AUTO`, the agent may never resolve it on its own, regardless of circumstances — the human must always be asked for that decision.

For `wording`, `AUTO` still does not mean the agent may always decide it. Per the `AUTO`/execution table, the agent may resolve it automatically only when:

- the decision is **sufficiently determined** by the available information, applicable criteria, and the agent's authority — i.e. the agent "can determine a single protocol-compatible decision from the available information and applicable criteria" (and has the authority to make it).

If instead there is missing/contradictory information, missing/ambiguous/contradictory criteria, multiple materially different but reasonably compatible decisions, dependence on an unresolved interpretation, or the decision is outside the agent's authority, then it counts as uncertain and the human must be asked exactly as if `AUTO` were absent.

So: **only `wording`**, and only **when the choice between "short" and "detailed" is unambiguously determined by the available information/criteria and lies within the agent's authority.** Otherwise, even for `wording`, a human is asked.

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No. The `release` `HITL` has no `→ AUTO` attached in this program at all, so the `AUTO` mechanism does not apply to it in the first place — the spec's default rule governs: `HITL` must not be silently replaced by an agent decision unless explicitly marked with `AUTO`. Since it isn't marked, the agent must not decide it under any circumstances, however green the checks are.

Even setting that aside, the spec explicitly warns that confidence is not sufficient grounds for automatic resolution: "A confidence score alone does not establish certainty," and `AUTO` "is not a request to guess." So even if `release` *had* been marked `AUTO`, high confidence by itself would not automatically justify the agent deciding — the decision would still need to be sufficiently determined by information/criteria/authority, not just by a confidence score. But here that question doesn't even arise: without `→ AUTO` on `HITL:release`, the human must be asked, and execution waits at that `HITL` for the human's response (or its `FALLBACK`, if one existed — none is given here).

## 3. If the wording decision is not clearly determined, what happens?

Per the `AUTO` execution table: `AUTO` present, but decision **not** sufficiently determined (uncertain, or outside the agent's authority) → "The human is asked, as for a `HITL` without `AUTO`." The agent must not guess or substitute its own answer.

Concretely for this program:
- `HITL:wording("Short or detailed release notes?")` waits until a usable human response is available. A usable response establishes `wording.short` or `wording.detailed` (the two answers tested by the following `WHEN` constructs).
- Once a usable response arrives, execution continues with the statement after the `HITL` construct — i.e., the two `WHEN wording.short` / `WHEN wording.detailed` constructs are evaluated in order, and whichever one matches runs its `DELEGATE` flow.

One point the specification does not determine, which I flag explicitly: `HITL:wording` in this program has **no `→ FALLBACK`** attached. The spec says the flow "waits at the `HITL` until either a usable response is available or its `FALLBACK` flow is used," and that `FALLBACK` is used only when the expected response is unavailable or insufficient. Since no `FALLBACK` is defined here, the specification does not say what occurs if the human's response to `wording` turns out to be unavailable or insufficient — there is no fallback flow to use in that case. My assumption is that, absent a `FALLBACK`, the flow simply continues waiting at the `HITL:wording` indefinitely until a usable response (one of `short`/`detailed`) is eventually given — consistent with `WAIT`'s general principle that "the DSL defines no timeout" and, absent an escape mechanism, suspension persists until a usable response resolves it. This is an assumption on my part, not something the spec states outright for the no-`FALLBACK` case.
