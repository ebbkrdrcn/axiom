```text
HITL:notes("Short or detailed release notes?")
  → AUTO
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes

HITL:approve("Approve the release?")
WHEN approve.approved
  → EMIT release
WHEN approve.rejected
  → TRANSITION "Rework"
```

## Assumptions

- **Answer vocabulary.** The DSL does not prescribe the set of valid `<answer>` values for a `HITL.<name>`; they are established by whichever `WHEN <name>.<answer>` constructs follow. I named the two answers to the first question `short` and `detailed`, and the two answers to the second question `approved` and `rejected`, taking these directly from the task's own wording ("If short... if detailed...", "If approved... if rejected..."). Any other names (e.g. `notes.brief`, `approve.yes`) would be equally valid under the spec; this is a naming choice, not a semantic one.
- **`HITL:notes` needs a name; `HITL:approve` needs one too.** Per the spec, "`<name>` may be omitted when no `WHEN` refers to the decision." Since both questions are followed by `WHEN` constructs that test their outcome, both `HITL` statements require a name. I chose the names `notes` and `approve` — the spec does not constrain the choice of name itself, only that it must match what the `WHEN` conditions reference.
- **`AUTO` only on the first `HITL`.** The task says the release-notes choice "may" be answered by the agent when clearly determined, which maps directly to `→ AUTO`. The approval question is stated to "always be given by a human, never by the agent," so no `→ AUTO` is attached to `HITL:approve` — per the execution table, omitting `AUTO` means "The human is asked. The agent must not decide," which is exactly the required behavior. No other mechanism in the spec is needed to force a human-only decision.
- **No `FALLBACK` on either `HITL`.** The task does not describe what should happen if a response is unavailable or insufficient for either question, so I did not add a `→ FALLBACK` flow. Per the `HITL` semantics, in the absence of `FALLBACK`, the containing flow simply waits at the `HITL` until a usable response (human or, for the first question, an AUTO-resolved one) becomes available; the DSL defines no timeout, so this is left open-ended, matching the fact that the task gave no instructions for that case.
- **Delegated notes are not separately verified.** The task only says to "delegate short-notes" / "delegate detailed-notes," with no mention of evaluating that work, so I did not add a `VERIFY` step after either `DELEGATE`. Adding one would have introduced an acceptance/rejection outcome the task never asked for.
- **No enclosing scope, `LOOP`, or `FORK`.** The requirement describes a single linear sequence (ask → branch → delegate → ask → branch → emit/transition) with no repetition and no concurrency, so the program is written as flat, sequential top-level statements. Per "Programs, fragments, and validity," a construct is not assumed to be enclosed in a scope that is not shown, so this flat, unwrapped form is treated as a complete, valid program on its own.
- **`short-notes` / `detailed-notes` as identifiers.** These are used as the `<work>` argument to `DELEGATE`. Under the grammar, an identifier consists of letters, digits, `-`, and `_`, and starts with a letter, so `short-notes` and `detailed-notes` are valid identifiers (as opposed to quoted strings), consistent with how the spec's own examples name delegated work (e.g. `dependency-upgrade`).
- **Ordering between the two questions.** The task presents the release-notes question, then (later, unconditionally) the approval question. I encoded this as strict sequential order at the top level: the notes `HITL`/`WHEN` block runs to completion (including whichever `DELEGATE` fires), and only then does execution reach `HITL:approve`. Nothing in the task suggests the approval question depends on which notes variant was delegated, so no data/state dependency between the two blocks was assumed beyond ordering.
- **`EMIT release` and `TRANSITION "Rework"` are terminal for their branches.** The task does not say what happens after emitting the release or after moving to `Rework`, and since these are the last stated actions, no further statements were added after them (no implicit `STOP`, since the spec says `STOP` is not required and execution simply ends normally after the last top-level statement completes).
