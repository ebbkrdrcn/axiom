# Answer

The analysis below uses only the `DSL` DSL specification given in the prompt, applied to this program:

```text
AUTO
HITL:wording("Short or detailed release notes?")
WHEN wording.short
  → DELEGATE short-notes
WHEN wording.detailed
  → DELEGATE detailed-notes
HITL:release("Approve the release?")
WHEN release.approved
  → EMIT release
```

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **wording** decision (`HITL:wording("Short or detailed release notes?")`) may be resolved by the agent itself.

Reasoning from the spec:

- `AUTO` is written on its own line "directly before a `HITL`, at the same indentation," and it "marks only the `HITL` on the immediately following line as automatically resolvable" (`AUTO` section; grammar rule `hitl = [ "AUTO" , NL ] , "HITL" , ...`). In the given program, the single `AUTO` line is immediately followed by `HITL:wording(...)`, so it attaches only to that `HITL`. It does not attach to `HITL:release(...)`, which has no `AUTO` line before it.
- Per the spec, "`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`." Since `HITL:release` is not marked with `AUTO`, the agent may never resolve it itself — it always requires a human answer.
- For `HITL:wording`, which *is* marked with `AUTO`, the agent may resolve the decision itself, but only under the condition stated in the `AUTO` section: "Automatic resolution is permitted only when the agent can determine a single protocol-compatible decision from the available information and applicable criteria." Concretely, per the execution table in `AUTO`, this means the agent may decide `wording.short` or `wording.detailed` itself only when that choice is "sufficiently determined" — i.e., the available information and criteria unambiguously pick out exactly one of the two answers, with no missing/contradictory information, no ambiguous/contradictory criteria, no remaining materially different reasonable alternative, and the matter is within the agent's authority. If the decision is uncertain (as defined by the "Uncertainty exists when..." list) or outside the agent's authority, the agent must not decide it, even though `AUTO` is present.

So: the agent may make the **wording** decision by itself, and only when it is sufficiently determined (no uncertainty as defined in `AUTO`); it may never make the **release** decision by itself, regardless of certainty, because that `HITL` carries no `AUTO` marker.

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No.

`HITL:release("Approve the release?")` has no `AUTO` line before it in the program. Per the spec, "`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`," and the execution table states plainly: "no `AUTO` → the human is asked. The agent must not decide." Since this `HITL` is unmarked, the agent must not resolve it itself no matter how confident it is or how green the checks are.

This is reinforced independently by the spec's statement that "a confidence score alone does not establish certainty" — so even if `HITL:release` *had* carried `AUTO`, high confidence alone would not by itself be sufficient grounds for automatic resolution; determination would still have to come from "available information, criteria, and authority." But that second point is moot here, since the absence of `AUTO` on `HITL:release` already forbids automatic resolution outright.

## 3. If the wording decision is not clearly determined, what happens?

This is the "yes `AUTO`, but not sufficiently determined (uncertain)" row of the `AUTO` execution table: "The human is asked, as for a `HITL` without `AUTO`."

So concretely:

- The agent does not decide `wording.short` or `wording.detailed` itself, and must not guess ("`AUTO` is not a request to guess").
- Execution proceeds exactly as an ordinary (non-`AUTO`) `HITL`: the flow "waits at the `HITL` until either a usable response is available or its `FALLBACK` flow is used." A usable response is one that gives `wording.short` or `wording.detailed`, since `<name>.<answer>` must be "one of the answers tested by the `WHEN <name>.<answer>` constructs that follow" (here, `wording.short` and `wording.detailed`).
- Once a usable human response arrives, the corresponding outcome (`wording.short` or `wording.detailed`) is established, execution continues with the next statement after the `HITL:wording` construct (i.e., the two `WHEN` statements are evaluated in order), and the matching `WHEN` flow (`DELEGATE short-notes` or `DELEGATE detailed-notes`) runs.
- Per the spec, `AUTO` and `FALLBACK` are distinct mechanisms: "When `AUTO` cannot resolve a decision, the decision goes to the human through the normal `HITL`; this is not a fallback." `FALLBACK` would only become relevant afterward, if the human's response to `HITL:wording` turns out to be unavailable (no response arrives; the runtime decides when this counts as unavailable, since the DSL has no timeout syntax) or insufficient (a response arrives but is not one of `short`/`detailed`, e.g. "I haven't decided yet").

**Note on what the specification does not determine here:** the given program attaches no `→ FALLBACK` block to `HITL:wording`. The spec says a `FALLBACK` is used "when the fallback flow is used" i.e. when the response turns out unavailable or insufficient, and it separately says a response matching none of the tested answers "is insufficient (see `FALLBACK`)" — but it does not state what happens when a response to a `HITL` is unavailable or insufficient and that `HITL` has *no* `FALLBACK` attached at all (the grammar makes the `FALLBACK` block optional: `hitl = [ "AUTO" , NL ] , "HITL" , ... , [ INDENT , "→" , "FALLBACK" , ... ] ;`, and nothing elsewhere in the spec fills this gap). The specification does not determine this case, so no claim is made about it here beyond what is certain: as long as the response is usable (matches `short` or `detailed`), execution proceeds normally as described above; the behavior for an unavailable/insufficient response to this particular (fallback-less) `HITL:wording` is left unspecified by the text given, and I assume no default behavior beyond "execution remains suspended" (by analogy with `WAIT`'s stated behavior — "If the event never becomes available, execution remains suspended" — since the spec gives no other mechanism for an unhandled unavailable/insufficient `HITL` response) rather than inferring, e.g., an implicit termination or an implicit re-prompt, since the spec states no such implicit behavior.
