# Analysis of the DSL Program

```text
AUTO
HITL:wording("Short or detailed release notes?")
WHEN wording.short
  → DELEGATE short-notes
WHEN wording.detailed
  → DELEGATE detailed-notes
HITL:release("Approve the release?")
WHEN release.approved
  → EMIT release
```

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **wording** decision (`HITL:wording`) may be resolved by the agent itself.

Reason: per the grammar, `AUTO` is "written on its own line directly before a `HITL`, at the same indentation," and it "marks only the `HITL` on the immediately following line as automatically resolvable." In this program, `AUTO` appears immediately before `HITL:wording(...)`, so only that `HITL` is eligible for automatic resolution.

`HITL:release("Approve the release?")` has no `AUTO` line directly before it, so it is not marked, and per the spec, "`HITL` must not be silently replaced by an agent decision unless that `HITL` is explicitly marked with `AUTO`." The release decision must therefore always be asked to a human.

The condition under which the agent may resolve `wording` itself (rather than asking a human) is given by the `AUTO` semantics: "Resolve automatically when sufficiently determined; otherwise require human input." Concretely, per the AUTO execution table, the agent may decide `wording` itself only when it "can determine a single protocol-compatible decision from the available information and applicable criteria" — i.e., the decision is not uncertain by the spec's definition (no missing/contradictory information, no missing/ambiguous/contradictory criteria, no multiple materially different compatible decisions, no unresolved interpretation dependency, and the agent has the authority to decide). If any of those uncertainty conditions holds, the human must be asked even though `AUTO` is present.

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No.

Two independent reasons from the spec, either of which is sufficient on its own:

- `HITL:release(...)` is not preceded by an `AUTO` line. Since `AUTO` "applies only to `HITL`" and only to "the `HITL` on the immediately following line," and no `AUTO` appears before `HITL:release`, this decision is a plain `HITL`. The table states explicitly: "no — The human is asked. The agent must not decide." So regardless of confidence, the agent may not resolve it.
- Even if `AUTO` had been present, the spec explicitly rules out confidence-based auto-resolution: "A confidence score alone does not establish certainty." Automated checks being green and high agent confidence describe confidence/evidence, not a demonstration that "a single protocol-compatible decision" is determined by "the available information ... and applicable criteria" together with the agent having the requisite authority. The spec does not state what the applicable "approval" criteria are, so it cannot be verified from the DSL text alone whether the decision is "sufficiently determined" in the specification's sense — but this is moot here because `AUTO` was never attached to this `HITL` in the first place.

So the agent must ask the human "Approve the release?" and wait for a usable response.

## 3. If the wording decision is not clearly determined, what happens?

"Not clearly determined" is exactly the uncertainty case described by `AUTO`'s semantics ("the agent cannot reliably determine that decision"). Per the `AUTO` execution table, row "yes / no (uncertain, or outside the agent's authority)": **"The human is asked, as for a `HITL` without `AUTO`."**

So concretely:

- The agent must not guess or fabricate an answer merely because `AUTO` is present ("`AUTO` is not a request to guess").
- The flow suspends at `HITL:wording(...)` and the human is asked "Short or detailed release notes?", exactly as if `AUTO` were absent.
- Execution waits, per the general `HITL` rule, "until either a usable response is available or its `FALLBACK` flow is used." A usable response here is one that corresponds to one of the answers tested by the following `WHEN` constructs, i.e. `short` or `detailed` (per the rule that "the response establishes the outcome `<name>.<answer>`, where `<answer>` is one of the answers tested by the `WHEN <name>.<answer>` constructs that follow").
- Once a usable response arrives, the outcome `wording.short` or `wording.detailed` is established "exactly as if a human had given that answer," and execution continues with the statement after the `HITL` construct — i.e., the two `WHEN wording.short` / `WHEN wording.detailed` constructs are evaluated in order, and whichever matches executes its `DELEGATE` (`short-notes` or `detailed-notes`); the non-matching `WHEN` is simply skipped (no error, per the `WHEN` rules). Execution then proceeds to `HITL:release(...)`.

**Explicit gap / assumption (not determined by the specification):** This particular `HITL:wording(...)` has no attached `→ FALLBACK` block. The spec defines `FALLBACK` behavior only for a `HITL` that has one attached; it does not state what happens when the human's response to a `HITL` without `FALLBACK` is unavailable or insufficient. By analogy with `WAIT` ("The DSL defines no timeout... If the event never becomes available, execution remains suspended") and with the general rule that a `HITL` "waits ... until either a usable response is available or its `FALLBACK` flow is used" (which presupposes a `FALLBACK` exists to be used), I assume that in the absence of a `FALLBACK`, an unavailable or insufficient response simply leaves execution suspended at `HITL:wording` indefinitely — the process does not proceed, terminate, or default to any wording, until a usable response (`short` or `detailed`) is eventually given. The specification does not explicitly confirm this for the no-`FALLBACK` case, so this is stated here as an assumption rather than a directly cited rule.
