```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

The specification does not fix several details of this scenario; the following choices were made to produce a well-formed program, and are stated explicitly because the spec does not determine them:

1. **Names for the `HITL` decision and its answers.** The specification says `<name>` names the decision and answers appear as `<name>.<answer>`, but it does not prescribe what those names should be for "a merge decision." I used `merge` as the decision name and `approved` / `declined` as the two answers (`merge.approved`, `merge.declined`), following the same naming pattern used in the spec's own `AUTO`/`HITL` example (`DELEGATE dependency-upgrade` … `AUTO HITL:merge(...)` … `merge.approved` / `merge.declined`), since the task's scenario is structurally identical to that example.

2. **Placement of `AUTO`.** The requirement says "the agent may make the merge decision itself when it is clearly determined … otherwise a human must be asked." This is exactly the semantics the spec assigns to `AUTO HITL`, so `AUTO` is placed directly before `HITL:merge(...)` on the same line, per the required syntax `AUTO HITL:<name>("<message>")`. No separate "uncertain" condition is written, since the spec explicitly forbids `AUTO` from containing a flow or branching on an uncertainty condition — the determination of certainty is left entirely to the runtime, as the spec requires.

3. **The message text.** The requirement gives the exact human-facing string `"Merge this change?"`, which I used verbatim as the `HITL` message. Since no `WHEN` needs to distinguish this from another decision and the flow only ever has this one `HITL`, a name was still included (`merge`) because the two `WHEN` constructs that follow must reference `merge.approved` / `merge.declined`; the spec permits omitting `<name>` only when no `WHEN` refers to the decision, which is not the case here.

4. **"No usable answer" maps to `FALLBACK`.** The spec defines `FALLBACK` as used when a response is unavailable (never arrives) or insufficient (arrives but doesn't answer the question). The requirement's "the human gives no usable answer" is treated as exactly this case, so the `Blocked`/`STOP` handling is written as the `FALLBACK` flow attached to the `HITL`, per the required syntax `HITL(...) → FALLBACK → ...`. This is only reachable when a human was actually asked (i.e., `AUTO` could not resolve the decision), consistent with the spec's statement that `FALLBACK` applies only after the human is asked and the response is unavailable or insufficient — it is never triggered by the `AUTO` path itself.

5. **`STOP` terminates the whole process, not just this flow.** The requirement says "transition to state 'Blocked' and stop," and the spec defines `STOP` as terminating the entire execution (not just the current flow/branch). Since there is no enclosing `LOOP` or `FORK` in this program, `STOP` here simply ends the (single, sequential) top-level flow — but per the spec's semantics it would also be understood to terminate any concurrent branches or loops if this fragment were nested inside one, which the task's requirement does not specify one way or the other.

6. **No requirement for the code/artifact being merged.** The requirement does not mention needing repository access, prior context, or any precondition before delegating the implementation, so no `REQUIRE` statement was added. Nothing in the task text calls for one, and the spec does not imply `DELEGATE` needs a preceding `REQUIRE`.

7. **No `EMIT`.** The requirement describes state transitions and a stop/gate but never mentions producing an artifact or output, so no `EMIT` statement was included.

8. **Top-level (non-looping) flow.** The requirement describes a single linear decision process ("delegate → verify → decide → transition") with no mention of repetition or retry, so the program is written as a flat top-level sequence of statements rather than wrapped in a `LOOP`. This also avoids any need for `BREAK`, which the spec disallows outside a `LOOP`.

9. **Two independent `WHEN` constructs rather than an if/else.** Per the spec, `WHEN` has no "else" semantics — each `WHEN` is evaluated independently. Since `merge.approved` and `merge.declined` are mutually exclusive answers to the same `HITL`/`AUTO` decision (only one can be established), writing them as two separate `WHEN` blocks correctly captures "if merge → Merged" and "if not merge → Rework" without relying on any if/else construct the DSL does not provide.
