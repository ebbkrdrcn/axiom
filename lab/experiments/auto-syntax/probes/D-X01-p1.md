```text
DELEGATE implementation
VERIFY implementation
AUTO
HITL:merge("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **HITL decision name.** The requirement's merge decision needs a name so that `WHEN` can refer to its outcome (`<name>.<answer>`), per the rule "The name may be omitted when no `WHEN` refers to the decision." Since two `WHEN` constructs must reference it, I named it `merge`.

2. **Answer vocabulary.** The spec does not fix which answer identifiers correspond to "merge" vs. "not merge" for a given message; it only requires that `WHEN merge.<answer>` matches one of the answers the human (or `AUTO`) can produce. I chose `merge.approved` for "decision is to merge" and `merge.declined` for "decision is not to merge," mirroring the spec's own worked example for an analogous merge question. Any other consistent pair of answer names would be equally valid under the spec.

3. **Placement and scope of `AUTO`.** `AUTO` is written on its own line directly before the `HITL` it modifies, per the required syntax `AUTO NL HITL ...`. I applied it to this single `HITL:merge(...)`, since the requirement explicitly allows the agent to resolve the merge decision itself "when it is clearly determined by the available information and criteria," which is exactly what `AUTO` grants — automatic resolution only when sufficiently determined, human asked otherwise. No implementation of "clearly determined" is specified or needed, per the Semantic Principles ("not an algorithm or confidence threshold").

4. **Scope of `FALLBACK`.** Per spec, "A usable response never triggers the fallback flow," and `AUTO`'s automatic resolution is not a fallback case at all ("`AUTO` and `FALLBACK` are different mechanisms"). So the requirement's clause "If the human gives no usable answer, transition to `Blocked` and stop" was encoded as the `FALLBACK` flow, which by definition only runs when the human was asked (i.e., `AUTO` could not resolve it) and the response is unavailable or insufficient. It does not run when `AUTO` resolves the decision or when the human gives a usable answer.

5. **"Stop" means the DSL `STOP` statement**, terminating the entire execution after the `TRANSITION "Blocked"`, as opposed to `BREAK` (which requires an enclosing `LOOP`, absent here) or simply ending the flow. This matches "`STOP` is not required at the end of a process," but here it is used because the requirement explicitly says execution should stop, and no `LOOP` encloses this program, so `BREAK` would be invalid (a `BREAK` outside a `LOOP` is not well-formed).

6. **Mutual exclusivity of `merge.approved` / `merge.declined` is assumed, not enforced by the DSL.** The spec states each `WHEN` is independent and there is "no implicit else," so nothing in the DSL itself prevents both outcomes from being established. I assumed the surrounding process (outside the DSL, per "outcomes... defined by the surrounding process") guarantees the merge decision yields exactly one of the two answers, so at most one of the two `WHEN` blocks executes in practice, consistent with the requirement's "if... if..." (mutually exclusive) phrasing.

7. **No `REQUIRE` statement was added.** The requirement text does not mention any precondition (e.g., a repository or context) that must be available before delegating the implementation, so none was introduced. The task says to use only the specification and the stated requirement; inventing an unstated `REQUIRE` would go beyond the requirement given.

8. **Identifier choice for the delegated/verified work.** The requirement says "Delegate the implementation and verify it." I used the identifier `implementation` for both `DELEGATE implementation` and `VERIFY implementation`, matching the spec's own recurring example (`DELEGATE implementation` / `VERIFY implementation`) and the rule that `VERIFY` evaluates the same result that was delegated.

9. **No `WHEN` on the `VERIFY implementation` outcome.** The requirement does not say anything conditional should happen based on whether the implementation is accepted or rejected before the merge decision — it moves straight from "verify it" to "a merge decision is needed." Per spec, "A `VERIFY` with no `WHEN` after it does not gate the process," so `VERIFY implementation` is included (since the requirement asks for it) but nothing branches on it, and execution proceeds unconditionally to the merge decision.

10. **Top-level, non-looping program.** The requirement describes a single linear sequence (delegate → verify → decide → transition [→ stop]) with no repetition language ("until," "again," "retry"), so no `LOOP` was used. This also makes `STOP` (rather than `BREAK`) the only valid way to end execution early, consistent with assumption 5.
