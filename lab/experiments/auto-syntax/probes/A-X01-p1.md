```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

- **Answer names `approved` / `declined`.** The requirement says "the decision is to merge" / "the decision is not to merge" but the DSL requires concrete answer identifiers for `<name>.<answer>` conditions tested by `WHEN`. The specification does not fix these names for this scenario; I used `approved` and `declined`, matching the naming used in the specification's own `AUTO`/`HITL` example (`merge.approved`, `merge.declined`), since that example describes the same kind of merge decision.
- **The `HITL` is named `merge`.** A `HITL` name is only required when a `WHEN` refers to it, which is the case here (`WHEN merge.approved`, `WHEN merge.declined`), so I supplied the name `merge`.
- **No `VERIFY` on the merge decision itself.** The task only asks to delegate and verify the *implementation*; the merge decision is produced directly by `AUTO HITL`/human response, and the specification does not suggest verifying a `HITL` outcome, so no `VERIFY` was added for it.
- **"No usable answer" maps to `FALLBACK`.** The specification states the fallback flow is used when a response is "unavailable" (never arrives) or "insufficient" (arrives but does not answer the question). "No usable answer" in the task is treated as covering both cases, so a single `FALLBACK` handles it, per spec ("A usable response never triggers the fallback flow").
- **`STOP` terminates the whole program, as required.** Per spec, `STOP` ends the entire execution, not just the fallback flow, which matches the requirement "transition to state 'Blocked' and stop."
- **No enclosing `LOOP`.** The requirement describes a single linear process with no repetition, so the program is a plain top-level block (the grammar allows a program to be a `block` with no `LOOP`).
- **No `REQUIRE`.** The task does not mention any precondition/prerequisite resource, so no `REQUIRE` statement was introduced.
- **`implementation` is used as the identifier argument for both `DELEGATE` and `VERIFY`**, assuming they refer to the same delegated work/result, per the specification's own `DELEGATE`/`VERIFY` example pattern.
- **Only two `WHEN` outcomes are handled (`approved`, `declined`) plus the `FALLBACK`.** The specification allows a `HITL` response to correspond to none of the tested answers, in which case it is "insufficient" and handled by `FALLBACK` — this covers the task's "no usable answer" case without needing a third `WHEN`.
- **Ordering of `WHEN` statements after `HITL`.** The specification says statements after the `HITL` construct, at the indentation of `HITL`, form the normal flow, executed in order after a usable decision is obtained (from either `AUTO` or the human). The two `WHEN` constructs are placed there in the order given by the requirement (merge case, then no-merge case); since `WHEN` conditions are independent and mutually exclusive here (`approved` vs `declined`), their relative order has no effect on behavior.
