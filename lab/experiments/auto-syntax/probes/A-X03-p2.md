# Execution of the DSL program

## Program (for reference)

```text
DELEGATE dependency-upgrade
VERIFY dependency-upgrade
AUTO HITL:merge("Merge the dependency upgrade?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Deferred"
```

Structurally: the `AUTO HITL:merge(...)` has one attached construct, `→ FALLBACK`, whose flow is `TRANSITION "Blocked"`, `STOP` (two `→` items under `FALLBACK` are one sequential flow, not concurrent branches — "Several `→` lines under `FALLBACK` are **not** concurrent branches"). The two `WHEN` statements are at the same indentation as `AUTO HITL:...`, so they are **not** part of the `HITL`/`FALLBACK` scope; they are ordinary statements that follow the `HITL` construct in the top-level flow (Scope rule 3: "A scope ends at the first following line indented at the same depth as, or less than, the line that opened it.").

## Assumptions made where the spec is silent

- The spec does not define the mechanics of when delegated work "completes" (`DELEGATE` "defines responsibility, not execution mechanics"). I assume `DELEGATE dependency-upgrade` runs to completion so that `VERIFY dependency-upgrade` has a result to evaluate — this is required simply to reach the next statement in sequential order.
- The task context states directly that "`VERIFY dependency-upgrade` establishes `accepted`", so no assumption is needed there.
- The spec does not name the mechanism by which "sufficiently determined" is computed for `AUTO`; I only apply the given merge criterion ("merge when verification accepts the upgrade and the changelog announces no breaking change") to the given facts, as the spec instructs ("Automatic resolution is permitted only when the agent can determine a single protocol-compatible decision from the available information and applicable criteria").

## Step-by-step execution

1. **`DELEGATE dependency-upgrade`** — work is assigned to an actor. Per the spec, this does not itself mean the work is correct, complete, or accepted; it only records that the work is delegated. (Assumption: it completes, allowing the flow to proceed to the next statement.)

2. **`VERIFY dependency-upgrade`** — evaluates the delegated result. Per the task context, this establishes the outcome `dependency-upgrade.accepted`. `VERIFY` does not itself branch or gate anything ("A `VERIFY` with no `WHEN` after it does not gate the process"); execution simply continues to the next statement.

3. **`AUTO HITL:merge("Merge the dependency upgrade?")`** — this is a `HITL` marked `AUTO`, so the agent first checks whether the decision is "sufficiently determined by the available information, criteria, and authority":
   - The process's merge criterion is "merge when verification accepts the upgrade **and** the changelog announces no breaking change."
   - `VERIFY dependency-upgrade` established `accepted` → first condition satisfied.
   - The changelog lists only bug fixes, i.e. it announces no breaking change → second condition satisfied.
   - Both conditions of the criterion are met, so exactly one protocol-compatible decision follows: approve the merge. There is no missing/contradictory information, no ambiguous criterion, and no competing decision reasonably compatible with the evidence.
   - The process also explicitly gives the agent "authority to merge dependency upgrades", so the authority requirement ("the agent does not have the authority required to make the decision" would block AUTO) is satisfied.
   - Per the `AUTO` execution table: `AUTO` = yes, sufficiently determined = yes → **"The agent resolves the decision. The human is not asked. The outcome `<name>.<answer>` is established exactly as if a human had given that answer."**
   - The agent therefore establishes the outcome **`merge.approved`** itself. The fact that "no human is currently online" is not consulted here — availability of a human is only relevant *after* a human has actually been asked (for `FALLBACK`'s "unavailable" case); it plays no role in whether `AUTO` can resolve the decision.
   - Since the human is not asked, the `FALLBACK` flow (`TRANSITION "Blocked"`, `STOP`) is **not entered**: "`FALLBACK` applies only afterwards, if the human's response is unavailable or insufficient" — there is no human response here at all, because none was requested.
   - After the decision is made, execution continues with the statement after the `HITL` construct.

4. **`WHEN merge.approved`** — evaluated once, in declaration order. The outcome `merge.approved` was just established in step 3, so the condition is satisfied. Its flow executes: **`TRANSITION "Merged"`** — the current process state becomes `"Merged"`. After the flow completes, execution continues with the statement after this `WHEN`.

5. **`WHEN merge.declined`** — evaluated in declaration order. The outcome `merge.declined` was never established (only `merge.approved` was), so this condition is not satisfied. Per the spec, "each `WHEN` is independent... If the condition is not satisfied, the flow is skipped... An unmatched `WHEN` is not an error." Its flow (`TRANSITION "Deferred"`) does **not** execute.

6. There are no further statements. `STOP` is not required at the end of a process — "When the last top-level statement has completed, execution ends normally." Execution ends normally after step 5.

## Final process state

**`"Merged"`** — established by the `TRANSITION "Merged"` executed in step 4. `TRANSITION "Deferred"` never ran (its `WHEN merge.declined` did not match), so it never overwrote the state. Since the process has exactly one current state and the most recently executed `TRANSITION` determines it, `"Merged"` is final.

## Is a human asked?

**No.** Because `AUTO` marks this `HITL`, and the decision is sufficiently determined (both parts of the merge criterion are satisfied by the given facts, and the agent has the required authority), the agent resolves the decision itself and establishes `merge.approved` "exactly as if a human had given that answer." Per the spec's `AUTO` table, the human is asked only when `AUTO` is absent, or when `AUTO` is present but the decision is uncertain or outside the agent's authority — neither applies here. The stated fact that "no human is currently online" is therefore never acted upon, since no human interaction is initiated at all.

## Is the `FALLBACK` used?

**No.** `FALLBACK` is defined for the case where "the expected response cannot be used to continue the normal flow" — i.e., a human was asked but the response is unavailable or insufficient. Here, no human is ever asked (the decision is resolved automatically by `AUTO`), so there is no human response to be unavailable or insufficient in the first place. As the spec states, "`AUTO` and `FALLBACK` are different mechanisms... `FALLBACK` applies only afterwards, if the human's response is unavailable or insufficient" — that precondition (a human having been asked) is never met, so the fallback flow (`TRANSITION "Blocked"`, `STOP`) never executes.
