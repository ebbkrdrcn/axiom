# Execution Trace

## Program

```text
DELEGATE dependency-upgrade
VERIFY dependency-upgrade
HITL:merge("Merge the dependency upgrade?") AUTO
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Deferred"
```

## Step by step

**Step 1 — `DELEGATE dependency-upgrade`**
Work is assigned to an actor. Per spec, `DELEGATE` "does not mean that the work is correct, complete, or accepted" — it only records responsibility. Execution proceeds to the next statement once the delegated work has been performed (the DSL does not prescribe how).

**Step 2 — `VERIFY dependency-upgrade`**
The result is evaluated against the applicable acceptance criteria. Per the task context, this establishes the outcome `accepted`. Per spec, `VERIFY` "does not branch by itself" and does not silently modify the result — it only records the evaluation outcome. Execution continues unconditionally to the next statement.

**Step 3 — `HITL:merge("Merge the dependency upgrade?") AUTO`**
This is a human decision boundary marked `AUTO`, so automatic resolution is *attempted* first. Per spec, `AUTO` means: "Resolve automatically when sufficiently determined; otherwise require human input." Automatic resolution is permitted only when the agent "can determine a single protocol-compatible decision from the available information and applicable criteria."

Applying that test here:

- The stated merge criterion is "merge when verification accepts the upgrade," and verification did establish `accepted`. Taken alone, this would point to `merge.approved`.
- However, the changelog reports a breaking API change, and the criterion as given does not address breaking changes at all. This is exactly the spec's example of "applicable criteria are missing, ambiguous, or contradictory" with respect to this case.
- In addition, two maintainers' notes disagree about whether breaking changes may be merged — a second, independent instance of contradictory information/authority bearing on the same decision, and also an example of "the result depends on an unresolved interpretation."
- The agent's 90% confidence does not change this: the spec explicitly states "A confidence score alone does not establish certainty."

Because the applicable criteria do not cover the actual situation (a breaking change) and the maintainers' guidance is contradictory, the agent **cannot** reliably determine a single protocol-compatible decision. This is uncertainty as defined by the spec, so — despite `AUTO` being present — automatic resolution is not permitted.

Per the `AUTO` execution table: "yes [AUTO present] / no [not sufficiently determined] → The human is asked, as for a `HITL` without `AUTO`." So the agent does **not** decide `merge.approved` or `merge.declined` itself; it asks the human the message "Merge the dependency upgrade?" and the flow suspends at the `HITL`, waiting for either a usable response or the use of `FALLBACK`.

**Step 4 — the human never responds**
Per spec, under `FALLBACK`: "**Unavailable** means no response arrives. The DSL has no timeout syntax; the runtime decides when a missing response counts as unavailable." The human here never answers at all, so — at whatever point the runtime deems the response unavailable (a runtime decision the DSL itself does not specify) — the response is treated as unavailable. No outcome `merge.approved` or `merge.declined` is ever established, and the normal flow after the `HITL` construct (the two `WHEN` statements) is not reached through the normal path. Instead, the `FALLBACK` flow attached to this `HITL` is used.

**Step 5 — `FALLBACK` flow executes**
The fallback is one sequential flow: `TRANSITION "Blocked"` then `STOP`.

- **`TRANSITION "Blocked"`**: the process's current state changes to `"Blocked"`. Per spec, `TRANSITION` "replaces" the current state; since no other `TRANSITION` has executed before it in this run, `"Blocked"` becomes the current (and, as it turns out, final) state.
- **`STOP`**: terminates execution. Per spec, `STOP` "terminates the **entire** execution, not only the flow that contains it," and "no subsequent statement is executed after `STOP`."

**Step 6 — everything after the `HITL` construct is skipped**
Because `STOP` terminates the entire execution, the two `WHEN` statements that follow the `HITL` (`WHEN merge.approved` / `WHEN merge.declined`) are never evaluated at all — not because their conditions fail to match (indeed neither `merge.approved` nor `merge.declined` was ever established, so they would not have matched even if reached), but because execution has already ended before reaching them. Execution ends normally at this point; no further statement runs.

## Final process state

**`"Blocked"`**

This is the only `TRANSITION` executed during this run, and it is followed by `STOP`, so it is also the state in effect when execution terminates.

## Assumptions made where the specification does not fully determine behavior

1. **Exact moment a missing response becomes "unavailable."** The specification explicitly leaves this to the runtime ("The DSL has no timeout syntax; the runtime decides when a missing response counts as unavailable."). Since the human in this scenario never responds at all, the trace above assumes only that the runtime's unavailability condition is eventually reached (at some unspecified point), which is sufficient to trigger `FALLBACK` regardless of exactly how that threshold is defined. The DSL does not let us say *when* this happens, only *that* it happens given "never responds."
2. **Treating the criteria conflict as "uncertainty" for `AUTO`.** The specification gives illustrative, non-exhaustive examples of uncertainty ("Examples include...") rather than an exhaustive test. The trace assumes that a stated criterion silent on a materially relevant fact (the breaking change), combined with contradictory maintainer guidance on exactly that fact, falls under the spec's own examples of "applicable criteria are missing, ambiguous, or contradictory" and "the result depends on an unresolved interpretation." This is a direct application of the given examples, not an extrapolation beyond them.
3. **No other `TRANSITION`, `WHEN`, or outcome exists outside the shown program.** Per the spec's rule under "Programs, fragments, and validity," the program is judged as written, with no assumed surrounding scope or prior state. The trace therefore assumes the process has no state before the first (and only) `TRANSITION` in this run, and that `merge.approved`/`merge.declined` have no other source of establishment anywhere else in the (unseen) surrounding process.
