```text
DELEGATE implementation
VERIFY implementation
HITL:merge("Merge this change?")
  → AUTO
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **Identifier for the delegated/verified work.** The requirement says "the implementation" without giving a token name. I used the identifier `implementation`, matching the spec's own `DELEGATE implementation` / `VERIFY implementation` example, since the spec does not otherwise fix a vocabulary for work items.

2. **Names of the merge decision's answers.** The requirement describes the outcomes only in prose ("the decision is to merge" / "the decision is not to merge"). The spec does not prescribe answer vocabulary either, so I adopted the identifiers `approved` and `declined` for the `merge` decision (i.e. `merge.approved`, `merge.declined`), following the spec's own worked example of a merge `HITL` (`HITL:merge("Merge the dependency upgrade?")` with `merge.approved` / `merge.declined`), which is the closest analogous case in the specification.

3. **`HITL` naming.** The decision was given the name `merge` because two `WHEN` constructs (`merge.approved`, `merge.declined`) need to refer to its outcome; per the spec, a name may be omitted only when no `WHEN` refers to the decision, which is not the case here.

4. **No `WHEN` after `VERIFY implementation`.** The requirement does not specify any branching based on whether the implementation itself is accepted or rejected — only that it must be delegated and verified before the merge decision. Per the spec, "`VERIFY` does not branch by itself... A `VERIFY` with no `WHEN` after it does not gate the process," so no conditional flow was added there, and execution proceeds unconditionally from `VERIFY implementation` to the `HITL`.

5. **No `REQUIRE` statement.** The requirement does not mention any precondition (context, repository, criteria, etc.) that must be declared as required before the delegated work starts, so none was added.

6. **Order of `→ AUTO` and `→ FALLBACK`.** Both apply to the same `HITL`. The spec mandates that when a `HITL` has both, `→ AUTO` must come before `→ FALLBACK`; this ordering was followed exactly.

7. **Fallback flow content and effect.** "If the human gives no usable answer" corresponds to the spec's `FALLBACK` (a response that is unavailable or insufficient). The fallback flow performs `TRANSITION "Blocked"` followed by `STOP`, using the two-statement-under-one-`→`, nested-line form shown as equivalent in the spec (`→ FALLBACK` / `→ TRANSITION "Blocked"` with `STOP` indented as its child), rather than two separate `→` lines (which under `FALLBACK` would still be sequential per spec, but the single-`→`-with-nested-child form was chosen since `STOP` is a strict continuation of the same fallback flow rather than a second, self-standing fallback step).

8. **No `LOOP` or `FORK`/`JOIN`.** The requirement describes a single, linear process with a one-time conditional decision and no stated repetition (no "until accepted," no retry loop) and no concurrent work, so no looping or forking constructs were introduced.

9. **Scope/placement of the two `WHEN` constructs.** They are placed at the same indentation as the `HITL` (i.e., in the normal flow after the `HITL` construct, not inside it), per the grammar: a `HITL`'s own indented content is limited to `→ AUTO` and `→ FALLBACK` only; outcome-testing `WHEN` constructs belong in the surrounding flow, evaluated only after a usable answer (human or `AUTO`-resolved) has been established, consistent with "After the decision is made... execution continues with the statement after the `HITL` construct."

10. **`STOP` after "Blocked" terminates the entire execution**, not just the fallback flow or the top-level program's remaining statements — this follows directly from the spec ("`STOP` terminates the entire execution, not only the flow that contains it") and matches the requirement's explicit "and stop," so no assumption beyond applying the spec's stated rule was needed here, but it is noted since it means no statement after this program fragment (if any existed in a larger program) would run in that branch.
