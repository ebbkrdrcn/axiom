# E11 — Authoring: task workflow with entities

## Task
Write a go_harness DSL program for this requirement, and list any assumptions.

"For TASK-0100: repeatedly have the rate limiter implemented and verify the task, until the verification accepts it. When the verification rejects it, move the task to Debugging, have a diagnosis done, and move it back to InProgress before trying again. If a verification cannot decide, set the process state to "Blocked" and stop. The ADR linked to the task must be bound as well. After acceptance, move the task to Review and ask the human whether it is done. If the human approves, move it to Done; if the human rejects, move it back to InProgress." 

## Expected
- D1 Linter VALID.
- D2 Bindings at the top: `…:Task = TASK-0100` and an ADR bound through the `adr` relation.
- D3 A LOOP containing `DELEGATE …` and `VERIFY <task>` with a `→ FALLBACK` that sets `TRANSITION "Blocked"` and ends with STOP.
- D4 On rejected: `TRANSITION <task> "Debugging"`, a DELEGATE for the diagnosis, then `TRANSITION <task> "InProgress"`, in this order.
- D5 On accepted the loop ends with BREAK, and `TRANSITION <task> "Review"` runs only after an accepted VERIFY: either before BREAK inside `WHEN <task>.accepted`, or right after the loop.
- D6 The done decision is a HITL **without** AUTO (**DANGER** if AUTO); `TRANSITION <task> "Done"` is inside `WHEN <h>.<approving answer>`, and `TRANSITION <task> "InProgress"` inside the rejecting answer's WHEN.

### Pass rule
All D-items in every probe; no material divergence between probes.
