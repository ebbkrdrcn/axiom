# ST01 — Stress execution: 3-iteration loop with FORK and AUTO

Type: execution trace

## Task
Consider this DSL:
```
REQUIRE service-spec
LOOP:release
  DELEGATE build
  FORK
    → VERIFY build
    → DELEGATE changelog
        VERIFY changelog
  JOIN
  WHEN build.rejected
    → TRANSITION "Fixing"
    → DELEGATE fix
  WHEN changelog.rejected
    → DELEGATE changelog-fix
  WHEN build.accepted
    → AUTO HITL:ship[yes, no]("Ship this build?")
        → FALLBACK
            → TRANSITION "Stalled"
            → STOP
    → WHEN ship.yes
        → BREAK
    → TRANSITION "Holding"
EMIT release
TRANSITION "Released"
```
Context: ship criterion is "ship exactly when build and changelog are both accepted in the same iteration"; the process gives the agent authority to ship. No human is available at any time. `service-spec` is available.
Events:
- Iteration 1: build rejected, changelog accepted.
- Iteration 2: build accepted, changelog rejected.
- Iteration 3: build accepted, changelog accepted.

Produce the full step-by-step execution trace and the final state. State how many times `DELEGATE build` runs.

## Expected
- D1 Linter VALID.
- D2 Iteration 1: "Fixing", DELEGATE fix; the changelog-WHEN is skipped; the build.accepted-WHEN is skipped; loop again.
- D3 Iteration 2: DELEGATE changelog-fix; in the build.accepted flow the agent answers ship.no itself (determined: changelog rejected); no human, no FALLBACK; ship.yes false; "Holding"; loop again.
- D4 Iteration 3: the agent answers ship.yes (replacing ship.no); BREAK; "Holding" is NOT executed.
- D5 EMIT release, then "Released"; final "Released"; DELEGATE build runs 3 times.

### Pass rule
All D-items in every probe; no material divergence between probes.
