# Intent-driven development: a small human team, and uncertainty defined as missing knowledge

## Context

The long-term goal is a company whose development team consists only of an architect, security and DevOps. The rest of the organisation does business development, which means forming intents. The system turns intents into software through the responsibility tree (ADR-0015) and ASK (ADR-0016).

An intent can be incomplete. The system then needs a precise rule for the point at which an agent must stop and ask instead of deciding. Without such a rule, agents fill gaps with silent assumptions. The Test 3 authoring probes did exactly that: they listed 7–10 "assumptions" instead of asking.

## Decision

### Uncertainty is epistemic

- **Definition.** Uncertainty means missing knowledge, that is, epistemic uncertainty. It does not mean low confidence, difficulty, or chance.
- **Knowledge.** An agent's knowledge is exactly what it holds or can verify:
  - the intent;
  - the entities (Tasks, ADRs, Definitions);
  - the context package it was given;
  - earlier recorded answers;
  - tool results it can check, such as files, test output and graph edges tagged `EXTRACTED`.

### Reasoning decides only inside that knowledge

- An agent may decide only what **follows from its knowledge**. Every decision must be able to name the knowledge it follows from.
- **Anything that needs knowledge the agent does not hold becomes an `ASK`.** This covers:
  - a missing fact;
  - sources that contradict each other;
  - a choice of values or preferences that no source settles;
  - a decision outside the agent's authority.
- Guessing, inventing and silent assumptions are forbidden. An assumption is either asked or written down explicitly and then approved.
- `AUTO` gets a precise meaning. "Certain" means "follows from knowledge the node holds". "Within its authority" is set by the node's Role. It is not a feeling of confidence.

### The system is built for incomplete intent

- An incomplete intent is not an error. It returns as `ASK`s until the knowledge is sufficient.
- **Knowledge is sufficient when:**
  - the spec's "Open questions" section is empty;
  - every acceptance criterion can be tested.
- `VERIFY spec` rejects a spec that has open questions, and the questions go to the right role. The answers become context for the next draft.
- **Answers accumulate as knowledge.** They are kept as ADRs, acceptance criteria and project knowledge. A later identical question is answered from that knowledge by the lowest node that holds it. Fewer questions reach humans over time.
- **ASK answers include an option to cancel,** so a clarification loop can always be ended by a human.

### Humans learn to state intent

- The system offers an intent template:
  - what is wanted, and for whom;
  - what "done" means;
  - what is out of scope.
- After each intent, the system shows which questions the intent caused.
- It tracks questions per intent and clarification rounds per person and per team, as a quality signal that should fall over time.
- Intents that finished with few questions are kept as examples.

### Human roles in the tree

| Role | Answers ASKs about | Main work |
|---|---|---|
| Business | the intent, acceptance criteria, and whether work is done | forming intents |
| Architect | ADR acceptance, protocols, actor definitions | writing how the system works: protocols, actors, ADRs |
| Security | security gates, authority grants | the rules of the mechanical layer, permissions, auditing the ledger |
| DevOps | deployment, infrastructure | the harness runtime and CI guards |

- `ASK … @human` generalises to role targets, such as `@business` and `@architect`.

## Consequences

- The DSL spec needs a definition of epistemic uncertainty and a rule for "follows from knowledge". It replaces the undefined "sufficiently determined" wording of `AUTO`.
- The Task protocol starts with a clarification loop driven by open questions.
- The ledger records, for every decision, the knowledge it followed from. This supports security audits.
- It is still hard to detect that the agent does not know something. The rule "no silent assumptions" together with the open-questions gate is the main defence, and it must be tested.

## Alternatives Considered

- **Uncertainty as model confidence:** not observable, and not deterministic across models.
- **Requiring perfect intents from humans:** not realistic. The system should close gaps by asking, while humans improve over time.
