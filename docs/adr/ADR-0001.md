# Behavioral determinism with the model as interpreter

## Context

go_harness has no mandatory runtime. The model reads a DSL program and either writes it from a requirement or executes it step by step. Two interpreters must reach the same states, outcomes and decisions even if their text differs. Nothing enforces the rules; they are followed by reading.

## Decision

The agent is the interpreter of the DSL, for both writing and executing programs. No program performs control flow on its behalf. Every rule in `dsl.md` and `entity-model.md` is written so that it can be followed by reading alone, and every choice a rule leaves open is closed by a contract or a human, never by the interpreter's guess.

## Consequences

- Specifications must be unambiguous and stated once. Any open choice is a defect, logged as a finding.
- A deterministic checker (`dsl-lab/tools/dslcheck.py`) may verify form, but it does not execute programs.
- Execution quality depends on the weakest supported model (see ADR-0002).

## Alternatives Considered

- A Go runtime that executes the DSL: deterministic, but it would have to decide every judgment step the model makes today.
- A hybrid, where a runtime drives control flow and the model performs steps: postponed; the DSL stays runtime-independent (Semantic Principles).
