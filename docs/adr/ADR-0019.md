# Observe first, build later; a central runtime as the target; the test corpus as a model qualification exam

## Context

- **The field is new and competitive.** The agent and model era is young, and the industry is racing. Tools and patterns change every few months.
- **Early action is risky.** Every action taken before the field is understood carries risk. Building is expensive, and it is not yet clear what the right structure is.
- **Observation is paying off.** The work so far has cost only tokens and documents: the DSL, the entity model, blind-probe tests, findings and ADRs. It has produced concepts grounded in observed model behaviour, for example epistemic uncertainty, ASK escalation, and the need for a mechanical layer.

## Decision

### Strategy: observe first, concepts before implementation

- **Stable parts get the investment:**
  - concept definitions: entity, protocol, actor, ASK, the epistemic rule;
  - the protocol library;
  - the test corpus;
  - decision records.
- **Temporary parts get the minimum.** Claude Code hooks and the MCP server are built only as far as a concept needs to be validated. They are placeholders for the central runtime and are not polished.
- **Progress is eclectic and incremental.** Each small, cheap experiment produces a finding or an ADR.

### Target: a central runtime

- **A central application runs the system,** working like an issue tracker. Nobody works inside the code.
  - Its data model is the entity model (`docs/types`).
  - Its workflows are protocols.
  - Its audit log is the ledger.
  - Actors do the work.
- **ASKs are answered in that application's interface,** by the role they target.
- **Durable execution may use Temporal or a similar engine.** Protocols stay the readable contract and may later be compiled to such an engine.
- **Claude Code is the executor for the first version.** It runs a single project, with subagents as actors.
- **Human code inspection is phased out gradually,** as the ledger and test results show that it is no longer needed.

### The test corpus becomes a model qualification exam

- **Scenarios are grouped by capability,** and each capability maps to roles:

  | Capability (scenario group) | Roles |
  |---|---|
  | Protocol execution determinism (S, ST, N) | orchestrator; actors that execute protocols |
  | Protocol authoring (S01–S04, E11, N09) | supervisor |
  | Entity and precondition reasoning (E) | actors that change status |
  | Epistemic honesty: never invent, ask when knowledge is missing (N03, E08, X) | all roles |
  | Validity and rule reading (N10, E12) | verifier |

- **Qualification rule.** A model qualifies for a role when it meets the threshold on that role's scenario group **and** makes zero DANGER errors there.
- **Every result records:**
  - the model;
  - the corpus version;
  - the spec version;
  - the tool layer.

  Qualification belongs to the model together with the tool layer. A mechanical check can make a cheaper model qualify.
- **A new model, for example a cheaper and more capable one, is run through the corpus.** The result says whether it is usable, and for which roles.
- **Initial data (Test 3, DSL v3, no mechanical layer):**
  - Sonnet qualifies for all groups tested.
  - Haiku 4.5 is good at execution and at mapping responses.
  - Haiku 4.5 does not qualify for status-changing roles: 3 DANGER errors.
  - Haiku 4.5 does not qualify for supervisor authoring: it adds FALLBACKs nobody asked for.
- **Protecting the corpus:**
  - It is versioned.
  - Part of it is kept as a private hold-out set, so future models cannot learn it from training data.
  - Every error found in real use becomes a new scenario.

## Consequences

- The work done so far is not throwaway. It is a paper prototype of the target system's data model, workflows and audit log.
- Model choice per role becomes a measured, cost-aware decision instead of a default.
- The corpus needs owners and a process: versioning, the hold-out set, and adding scenarios from incidents.

## Alternatives Considered

- **Build on a current framework now:** lock-in to tools that are still changing fast, at a high cost, before the concepts are clear.
- **Choose models by reputation or general benchmarks:** these do not measure behaviour under our protocols and rules, in particular DANGER errors.
