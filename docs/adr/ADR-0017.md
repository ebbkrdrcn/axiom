# Critical rules are enforced by tools, and actor context comes from graphify

## Context

Test 3 found three DANGER errors in Haiku (ledger: `lab/iterations/03/critic-report.md`). All three came from rules that the spec states in prose: binding identity, and a stale `verified:` precondition. Stating a rule in the spec alone probably tops out at about 98–99% compliance. Supervisors (ADR-0015) also need a cheap way to build the context for each Actor.

## Decision

- **Axiom MCP server.** It provides bind, verify, transition and next-step operations.
  - It is the only writer of the ledger (`.axiom/ledger.jsonl`).
  - It checks binding counts, content hashes at VERIFY time, and the preconditions in the Definitions.
- **Claude Code hooks:**
  - PreToolUse blocks direct edits to `status:` in the target project's `docs/**` and blocks writes to the ledger.
  - PostToolUse on `AskUserQuestion` records the human's answers as `by human`.
  - SubagentStop and PostToolUse record data changes.
  - Stop blocks the end of a turn while a protocol run is unfinished.
- **Final guard.** A git pre-commit hook or CI job rejects any `status` change that has no permitted ledger record.
- **Entity graph.** The entity and process graph is our own and deterministic: explicit fields only. It answers "what is allowed now".
- **Context from graphify.** Supervisors build actor context with graphify (`Graphify-Labs/graphify`) through its MCP server.
  - Decisions use only edges tagged `EXTRACTED`.
  - `INFERRED` and `AMBIGUOUS` edges are hints only.
  - A context package records the graph's commit.
  - Code is extracted by AST, which is cheap and deterministic. Markdown extraction uses an LLM, so entities and project docs stay out of the graph at first.

## Consequences

- DANGER-class errors become mechanical checks and no longer depend on the model's reading.
- The spec gets shorter: a TRANSITION goes through axiom's transition operation, and its result is final.
- Hooks and MCP configuration live in the repository, so cloud sessions behave the same as local ones.
- Judging whether VERIFY criteria are actually met remains with the model. Mechanical criteria, such as a test command's exit code, can narrow this later.

## Alternatives Considered

- **Spec-only rules:** the Test 3 evidence shows that these are not enough for DANGER-class errors.
- **A vector database that watches the project:**
  - its results are probabilistic and cannot be explained;
  - it has no structure;
  - a missing result says nothing about whether the thing exists;
  - its index can go stale between a DELEGATE and the VERIFY that follows.
  - Deferred: it may be added later as a read-only hint layer for large bodies of prose.
