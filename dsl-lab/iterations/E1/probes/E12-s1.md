# Task: Validate the four snippets

## Snippet A

```
t1:Task = TASK-0100
LOOP:work
  a1:ADR = t1.adr
  VERIFY t1
  WHEN t1.accepted
    → BREAK
```

**INVALID — breaks V11.**

`a1:ADR = t1.adr` is a binding. Bindings must appear at the top of the program, unindented, before every other statement (dsl.md, **Binding**; Entity Model, **Binding Rules**). Here the binding:

- is indented (it is written inside the body of `LOOP:work`), and
- follows a statement that is not a binding (`LOOP:work` itself, which is not a binding, precedes it in program order).

Both conditions independently satisfy V11 ("a binding is indented, or follows a statement that is not a binding, or …"). The fact that the binding's relation (`t1.adr`) refers to a name (`t1`) bound on an earlier line is fine — that part of V11 is not violated — but the indentation/position violation alone makes the program INVALID.

## Snippet B

```
a1:ADR = t1.adr
t1:Task = TASK-0100
VERIFY a1
```

**INVALID — breaks V11.**

`a1:ADR = t1.adr` is a relation binding whose source name is `t1`. V11 requires that a relation binding's source name be "bound on an earlier line." Here `t1` is not bound until the *following* line (`t1:Task = TASK-0100`), so at the point `a1` is bound, `t1` has not yet been bound. This violates V11 ("… or its relation starts from a name not bound on an earlier line"). Note this is a well-formedness (syntactic/ordering) defect, distinct from binding *satisfaction* at execution time — the program is rejected before any execution is considered.

## Snippet C

```
t1:Task = TASK-0102
TRANSITION t1 "Done"
```

**VALID — no rule broken.**

- The binding is at the top, unindented, and is the only statement before it — satisfies V11.
- `t1` is bound and used consistently — no V12 issue (it is not also used as a `HITL` name, and `TRANSITION t1` refers to a name that is bound).
- Syntactically this is a well-formed `TRANSITION <name> "<status>"` statement referring to a bound entity.

This is exactly the case the spec calls out explicitly: *"A transition that the Definition does not permit (for example `TRANSITION t1 "Done"` while the task is `InProgress`) is not INVALID: the program is well-formed, and the transition fails when it is executed."* (dsl.md, **Entities**, and Entity Model, **Invalid Usage**, "Undeclared transition").

Per the fixture, `TASK-0102` is `status: Todo`, and the Task Definition's transition table has no `Todo → Done` entry (only `Todo → InProgress` is declared from `Todo`). So at *execution* time this `TRANSITION` would fail (its `FALLBACK` would run, or execution would end if there is none) — but that is a runtime/execution-failure concern, not a validity (well-formedness) concern. The task asks only for VALID/INVALID with respect to the rules V1–V12, so: **VALID**.

## Snippet D

```
t1:Task = TASK-0100
HITL:t1[approved, rejected]("Done?")
TRANSITION t2 "Done"
```

**INVALID — breaks V12 (twice).**

1. `HITL:t1[approved, rejected]("Done?")` uses the name `t1` as a `HITL` name, but `t1` is already a bound entity name (`t1:Task = TASK-0100`). V12: "… or a bound name is used as a `HITL` name." This is also consistent with the Binding Rules in the Entity Model ("A bound name must not be used as a `HITL` name") and with V7's spirit (name reuse across constructs), but the specific, directly-applicable rule is V12.
2. `TRANSITION t2 "Done"` uses the name `t2`, which is never bound anywhere in the program (only `t1` is bound). V12: "`TRANSITION <name> "<status>"` uses a name that is not bound …" — this is exactly the INVALID example given verbatim in dsl.md (`TRANSITION t2 "Done"` under a program that only binds `t1`).

So Snippet D violates V12 for two independent reasons: the reused/conflicting name `t1` as a `HITL` name, and the unbound name `t2` in the entity `TRANSITION`.
