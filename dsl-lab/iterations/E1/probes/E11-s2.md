# go_harness program for TASK-0100

## Program

```text
t1:Task = TASK-0100
a1:ADR = t1.adr

LOOP:work
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.accepted
    → BREAK
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"
TRANSITION t1 "Review"
HITL:done[approved, rejected]("Is TASK-0100 done?")
WHEN done.approved
  → TRANSITION t1 "Done"
WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Why this shape

- **Bindings.** `t1:Task = TASK-0100` and `a1:ADR = t1.adr` are the first two lines, unindented, satisfying V11. `a1` is bound (per the requirement, "The ADR linked to the task must be bound as well") even though the program never operates on it afterward — the requirement only asks that it be bound, not used.
- **The repeat-until-accepted loop.** `LOOP:work` repeats `DELEGATE implementation` + `VERIFY t1` until acceptance. Per DSL rule 5 / the `LOOP` section, the body restarts at its first statement at the end of each iteration, so no explicit "try again" statement is needed — falling through the two `WHEN`s back to the top of the loop *is* "trying again".
- **Rejected branch.** `WHEN t1.rejected` performs exactly the three requested steps in order: `TRANSITION t1 "Debugging"` (precondition `verified: rejected`, satisfied by the `VERIFY t1` just executed), `DELEGATE diagnosis`, then `TRANSITION t1 "InProgress"` (precondition `none`) — "before trying again," which the loop does automatically on its next iteration.
- **Accepted branch.** `WHEN t1.accepted` only `BREAK`s the loop; the reported `TRANSITION t1 "Review"` is written once, after the loop, since it is not part of the retry cycle and must happen exactly once when acceptance is reached ("After acceptance, move the task to Review…"). Its precondition is `verified: accepted`, satisfied because the most recent `VERIFY t1` in the execution established `accepted` (the `WHEN` guaranteed that before the `BREAK`, and no other `VERIFY t1` runs in between).
- **Undecidable verification.** `VERIFY t1`'s own `→ FALLBACK` (attached directly under `VERIFY t1`, per the grammar for `verify`) covers exactly the "cannot decide" case (DSL: a `VERIFY` that cannot determine a single outcome *fails* and runs its `FALLBACK`). It sets the process state with `TRANSITION "Blocked"` and then `STOP`s, satisfying V8 (fallback must end in `STOP` or `BREAK`) and matching "set the process state to Blocked and stop." This fallback does **not** fire on a normal `rejected` outcome — `rejected` is a successfully determined outcome, not a failure — so the retry/Debugging path and the Blocked/stop path are mutually exclusive as required.
- **Human sign-off.** After `TRANSITION t1 "Review"`, `HITL:done[approved, rejected]("Is TASK-0100 done?")` asks the human. `WHEN done.approved → TRANSITION t1 "Done"` has precondition `human: approved`, satisfied because it is inside the flow of `WHEN done.approved` for a `HITL:done` without `AUTO`. `WHEN done.rejected → TRANSITION t1 "InProgress"` matches the `Review → InProgress` transition (precondition `none`).
- **No `AUTO`.** The requirement never says the agent may decide the "is it done" question itself, so `HITL:done` is a plain (human-only) decision, per the DSL's default (a `HITL` "MUST NOT be replaced by an agent decision, unless it is marked with `AUTO`").
- **No `FALLBACK` on `HITL:done`.** The requirement only describes what happens for `approved` and `rejected` (the two listed answers); it says nothing about an insufficient/unavailable response, so no `FALLBACK` is added — per the DSL, an unhandled `HITL` failure simply ends execution as with `STOP`, which is the correct default when the requirement is silent.
- **Outcome names are declared.** `t1.accepted` / `t1.rejected` come from `VERIFY t1` (Task Definition's only two verification outcomes); `done.approved` / `done.rejected` come from `HITL:done[approved, rejected]`. This satisfies V6.
- **Transitions are all declared by the Task Definition:** `InProgress→Debugging` (`verified: rejected`), `Debugging→InProgress` (`none`), `InProgress→Review` (`verified: accepted`), `Review→Done` (`human: approved`), `Review→InProgress` (`none`) — every `TRANSITION t1 "…"` in the program matches one of these rows and its stated precondition.

## Assumptions

1. **Starting status.** The program assumes `TASK-0100` is read at whatever status it actually has when execution starts (the fixture shows `InProgress`); the DSL binds by identity and re-reads data as needed, so the program itself does not hard-code a starting status, but the very first `TRANSITION t1 "Debugging"` or `"Review"` will only succeed if the task is in fact `InProgress` at that point (per the fixture, it is).
2. **The ADR binding is unused otherwise.** The requirement says only that the ADR "must be bound as well," not that any operation (e.g. `VERIFY a1`, or a `WHEN` on it) is performed on it. `a1` is therefore bound and left unreferenced, which is valid DSL (nothing requires a bound name to be used further).
3. **No `AUTO` on the human "is it done" question.** The requirement describes a human question with two branches and gives no criterion for the agent to decide it itself, so it is modeled as a plain `HITL`, not `AUTO HITL`.
4. **No `FALLBACK` for `HITL:done`.** The requirement specifies behavior only for the two listed answers (`approved`, `rejected`); an insufficient or unavailable response is out of scope for the requirement, so it is left to the default DSL behavior (execution ends, as with `STOP`) rather than inventing an unrequested fallback flow.
5. **`REQUIRE` is not used.** The requirement does not mention any precondition resource (e.g. "the repository must be available") to establish before starting work, so no `REQUIRE` statement was added.
6. **"Verify the task"** is read as `VERIFY t1` (verification of the bound `Task` entity), per the DSL's "`VERIFY` on a bound entity" construct, evaluated against the Task Definition's Acceptance-Criteria-based criteria — not a `VERIFY` of some other unnamed result.
7. **The `Blocked` state is a process state, not an entity status.** "Set the process state to Blocked" is modeled with `TRANSITION "Blocked"` (no bound name — the DSL form for process state), matching the DSL's own worked example, and is distinct from the Task's own status field (which is untouched when this fallback runs).
8. **"Move it back to InProgress before trying again"** is satisfied structurally by the loop restarting after the `rejected` flow's final `TRANSITION t1 "InProgress"`, without needing an extra explicit statement — the DSL's `LOOP` semantics (body restarts at its first statement) make the next `DELEGATE implementation` the "trying again."
