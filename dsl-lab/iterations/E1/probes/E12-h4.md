# E12 Validation Results

## Snippet A

```
t1:Task = TASK-0100
LOOP:work
  a1:ADR = t1.adr
  VERIFY t1
  WHEN t1.accepted
    → BREAK
```

**INVALID**

**Rules broken:** V11

**Reason:** The binding `a1:ADR = t1.adr` is indented inside the `LOOP:work` scope. According to V11, bindings MUST appear at the top of the program, unindented, before every other statement. A binding anywhere else is invalid.

---

## Snippet B

```
a1:ADR = t1.adr
t1:Task = TASK-0100
VERIFY a1
```

**INVALID**

**Rules broken:** V11

**Reason:** The binding `a1:ADR = t1.adr` on the first line attempts to follow a relation from `t1`, but `t1` is not bound on an earlier line. According to V11, a binding's relation "starts from a name not bound on an earlier line" violates the rule. The correct order would require `t1:Task = TASK-0100` to appear first.

---

## Snippet C

```
t1:Task = TASK-0100
TRANSITION t1 "Done"
```

**VALID**

**Reason:** This snippet violates no syntax or validity rules (V1-V12). The binding is correctly placed at the top level, and the `TRANSITION` statement uses a name that is bound. While the transition from `InProgress` to `Done` is not declared by the Task Definition (a runtime failure), that is a semantic/runtime issue, not a static validity violation. The program is well-formed.

---

## Snippet D

```
t1:Task = TASK-0100
HITL:t1[approved, rejected]("Done?")
TRANSITION t2 "Done"
```

**INVALID**

**Rules broken:** V12, V12

**Reasons:**
1. The `HITL:t1[...]` statement uses `t1` as a HITL name, but `t1` is a bound entity name. According to V12, a bound name MUST NOT also be used as a `HITL` name.
2. The `TRANSITION t2 "Done"` statement uses `t2`, which is not bound in this program. According to V12, `TRANSITION <name> "<status>"` MUST NOT use a name that is not bound.
