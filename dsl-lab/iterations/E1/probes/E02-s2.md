# Execution of the program

```text
t1:Task = ADR-0100
TRANSITION "Started"
DELEGATE work
```

## 1. Validity verdict

**VALID.**

The program is syntactically well-formed: a single binding at the top, unindented, followed by two simple statements (`TRANSITION "<state>"` and `DELEGATE <work>`). There is no `LOOP`, `BREAK`, `WHEN`, `FORK`/`JOIN`, `HITL`, `AUTO`, or `FALLBACK`, so none of V1–V10 can be violated. The single binding is the first statement, is not indented, and does not rebind an already-bound name, so V11 is not violated. No `TRANSITION <name> "<status>"` or `HITL` referencing a name occurs, so V12 is not violated.

(Note: validity concerns only well-formedness, not whether the binding will actually resolve at execution time — that is a runtime **Failure**, not an INVALID program.)

## 2. Execution trace

At execution, the binding `t1:Task = ADR-0100` is checked against the fixtures. `ADR-0100` exists (in `docs/adr/ADR-0100.md`), but its front matter declares `type: ADR`, not `Task`. Per the DSL (**Entities › Binding**), a binding is satisfied only when exactly one entity with that identity exists, **it is of the declared type**, and it is structurally valid. Since `ADR-0100` is of type `ADR` and the binding declares `Task`, the binding is not satisfied. Per rule 11 / the Failures table, an unsatisfied binding ends execution as with `STOP`; no statement after the bindings runs.

```trace
1. t1:Task = ADR-0100 -> failed: ADR-0100 is type ADR, not Task (declared type Task not satisfied); stop
2. (end of program) -> end
```

`TRANSITION "Started"` and `DELEGATE work` are never executed, because execution ends at the failed binding before any statement after the bindings runs.

## 3. Final status of bound entities / file changes

- **`t1`**: never successfully bound — the binding failed, so `t1` does not refer to any entity for the rest of (the non-existent remainder of) the execution. There is no bound entity `t1` to report a status for.
- **`ADR-0100`** (the entity the program attempted to bind `t1` to): unchanged. Its status remains `Accepted`, exactly as in `docs/adr/ADR-0100.md`. `VERIFY`/`TRANSITION` were never reached, and a failed binding "changes nothing and establishes no outcome."
- **No entity files changed.** No `TRANSITION <name> "<status>"` was ever executed (the program contains none), and the only entity-touching statement (the binding) failed before any read/write of data occurred beyond identity/type resolution.

## 4. Final process state

**`none`.**

`TRANSITION "Started"` (a process-state transition, not an entity transition) is never executed, because execution ends at the failed binding before reaching it. Per the DSL, "Before the first `TRANSITION`, the process state is `none`," and since no `TRANSITION` ever ran, the process state stays `none`.
