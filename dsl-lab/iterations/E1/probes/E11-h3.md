# Solution: go_harness DSL Program for Rate Limiter Task

## Program

```
t:Task = TASK-0100
a:ADR = t.adr

LOOP:rate-limit
  DELEGATE implementation
  VERIFY t
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t.accepted
    → TRANSITION t "Review"
    → BREAK
  WHEN t.rejected
    → TRANSITION t "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t "InProgress"

HITL:done[approved, rejected]("Is the rate limiter implementation complete and ready?")
  → FALLBACK
      → TRANSITION t "InProgress"
      → STOP

WHEN done.approved
  → TRANSITION t "Done"

WHEN done.rejected
  → TRANSITION t "InProgress"
```

## Assumptions

1. **Entity Availability**: TASK-0100 and its linked ADR (ADR-0100) exist, are structurally valid, and satisfy their binding requirements. The `adr` field references exactly one ADR entity.

2. **Actor Capability - Implementation**: The "implementation" actor has the knowledge and tools to implement the rate limiter according to the task description and accepts responsibility for delivering the work.

3. **Actor Capability - Diagnosis**: The "diagnosis" actor can analyze and report why the rate limiter implementation does not meet the acceptance criteria when verification rejects it.

4. **Verification Criteria**: VERIFY t evaluates the task against its acceptance criteria:
   - _accepted_: After 5 failed login attempts within 10 minutes, the next attempt returns HTTP 429; the limit resets after 10 minutes without a failed attempt; and each criterion names its evidence.
   - _rejected_: At least one acceptance criterion is not satisfied, with each unsatisfied criterion named.
   - If evidence is unavailable or criteria are ambiguous, VERIFY fails and the FALLBACK executes.

5. **Verification Outcomes**: VERIFY establishes exactly one outcome (`t.accepted` or `t.rejected`). If criteria do not determine a single outcome, the FALLBACK runs.

6. **Human Response**: A usable response to the HITL clearly selects one of the two declared answers: "approved" or "rejected". An insufficient or unavailable response triggers the FALLBACK.

7. **Status Transitions**: All entity status transitions satisfy the preconditions defined by the Task Definition:
   - InProgress → Review: precondition `verified: accepted` ✓ (inside WHEN t.accepted after VERIFY t)
   - InProgress → Debugging: precondition `verified: rejected` ✓ (inside WHEN t.rejected after VERIFY t)
   - Debugging → InProgress: precondition `none` ✓ (always allowed)
   - Review → Done: precondition `human: approved` ✓ (inside WHEN done.approved after HITL:done without AUTO)
   - Review → InProgress: precondition `none` ✓ (always allowed)

8. **Representation Updates**: Each TRANSITION operation completes only when the authoritative representation (docs/tasks/TASK-0100.md) records the new status.

9. **ADR Binding**: The binding `a:ADR = t.adr` succeeds because TASK-0100's `adr` field contains `ADR-0100`, which exists as a valid ADR entity with type ADR.

10. **Loop Termination**: The loop terminates when VERIFY establishes `t.accepted`, at which point the task transitions to Review and control moves to the human decision.
