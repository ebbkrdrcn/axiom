# Execution of the go_harness Program

## Program

```
DELEGATE release-notes
HITL:notes[approved, rejected]("Approve the release notes?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN notes.approved
  → TRANSITION "Published"
  → EMIT release-notes
WHEN notes.rejected
  → TRANSITION "Rework"
```

## Validity (per the ten validation rules)

The program is well-formed:

- Indentation follows the rules: the `→ FALLBACK` is directly under the `HITL`, and the fallback flow's last item is `STOP` (satisfies V4, V8).
- No `BREAK`, `LOOP`, or `FORK`/`JOIN` appear, so V2, V3, V9 do not apply.
- The two `WHEN` conditions (`notes.approved`, `notes.rejected`) both refer to answers listed in `HITL:notes[approved, rejected]`, so V6 is satisfied.
- `notes` is used by exactly one `HITL` and no `VERIFY`, and the answer list has two distinct, non-empty answers, so V7 is satisfied.
- V1, V5, V10 do not apply (no AUTO, no irregular indentation, no FORK to join before a WHEN).

The program is therefore valid and MUST be executed as written.

---

## Run A — the human responds "Approved."

**Classification of the response:** "Approved." clearly selects the listed answer `approved` (rule: "Clearly selects exactly one listed answer (in any wording)" → usable). It establishes `notes.approved` and the fallback is not used (a usable response never runs the fallback flow).

```trace
1. DELEGATE release-notes -> done
2. HITL:notes[approved, rejected]("Approve the release notes?") -> waiting
3. HITL:notes[approved, rejected]("Approve the release notes?") -> outcome notes.approved
4. WHEN notes.approved -> true: run flow
5. TRANSITION "Published" -> state = "Published"
6. EMIT release-notes -> done
7. WHEN notes.rejected -> false: skip
8. (end of program) -> end
```

**Final state: `Published`**

---

## Run B — the human never responds and the runtime stops waiting

**Classification of the response:** no response at all, and the runtime has stopped waiting, which the specification classifies exactly as "unavailable." An unavailable response with a `FALLBACK` present runs the fallback flow; no outcome is established for `notes`.

```trace
1. DELEGATE release-notes -> done
2. HITL:notes[approved, rejected]("Approve the release notes?") -> waiting
3. HITL:notes[approved, rejected]("Approve the release notes?") -> fallback
4. TRANSITION "Blocked" -> state = "Blocked"
5. STOP -> stop
```

Because the fallback ends in `STOP`, execution ends entirely; the two `WHEN` statements are never reached (and could never have been true anyway, since no outcome was established).

**Final state: `Blocked`**

---

## Run C — the human responds "I haven't had time to look yet."

**Classification of the response:** this is off-topic / does not select either listed answer. The specification gives almost this exact wording as its example of "insufficient" ("or is off-topic (for example 'I haven't looked yet')"). Insufficient with a `FALLBACK` present runs the fallback flow; no outcome is established.

```trace
1. DELEGATE release-notes -> done
2. HITL:notes[approved, rejected]("Approve the release notes?") -> waiting
3. HITL:notes[approved, rejected]("Approve the release notes?") -> fallback
4. TRANSITION "Blocked" -> state = "Blocked"
5. STOP -> stop
```

**Final state: `Blocked`**

---

## Run D — the human responds "Not like this, rewrite the intro."

**Classification of the response — assumption stated explicitly:** the specification allows a listed answer to be selected "in any wording," and classifies a response as insufficient only if it "selects none of the listed answers, is ambiguous between answers, or is off-topic." "Not like this" is an unambiguous refusal of the release notes as delivered — it clearly is not approval, and there are only two possible answers (`approved`, `rejected`), so it clearly selects `rejected`. The additional remark ("rewrite the intro") is extra content the DSL has no construct to capture (a `HITL:name[...]` establishes only the chosen outcome, nothing else), so it does not change the classification. Under this reading the response is **usable**, establishing `notes.rejected`.

(The specification does not explicitly resolve how to treat a rejection that is bundled with additional free-text feedback; the above is the stated assumption. Had this been judged ambiguous/off-topic instead, the trace would follow the fallback path exactly as in Run B/Run C, ending in state `Blocked`.)

```trace
1. DELEGATE release-notes -> done
2. HITL:notes[approved, rejected]("Approve the release notes?") -> waiting
3. HITL:notes[approved, rejected]("Approve the release notes?") -> outcome notes.rejected
4. WHEN notes.approved -> false: skip
5. WHEN notes.rejected -> true: run flow
6. TRANSITION "Rework" -> state = "Rework"
7. (end of program) -> end
```

**Final state: `Rework`**
