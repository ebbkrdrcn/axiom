# go_harness DSL Program

## DSL Code

```text
AUTO HITL:notes[short, detailed]("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:release[approved, rejected]("Approve the release?")
WHEN release.approved
  → EMIT release
WHEN release.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **No VERIFY after DELEGATE**: The requirement asks to delegate short-notes or detailed-notes, but does not ask to verify the results. Therefore, the DELEGATE statements stand alone without VERIFY, and execution continues when the delegation completes.

2. **No FALLBACK for release approval**: The requirement specifies what to do if the release is approved or rejected, but does not specify what happens if the human provides an insufficient response or no response to the release HITL. Per the specification (rule in section **What happens** under HITL), if there is no FALLBACK and the response is unavailable or insufficient, execution ends as with STOP. This is appropriate for a release approval process.

3. **"Never by the agent" means no AUTO**: The requirement "This approval must always be given by a human, never by the agent" is interpreted as: do not mark the release HITL with AUTO. The first HITL (notes) is marked with AUTO because the requirement says "The agent may answer this question itself when the answer is clearly determined," which matches the AUTO semantics in the specification.

4. **Consecutive WHEN statements for branches**: Both HITLs have two possible outcomes, and the requirement specifies an action for each. The consecutive WHEN statements (one for each outcome) are independent and both are checked, as specified in rule 3 of **Execution in ten rules**.

5. **Sequential execution order**: The program executes in the order written: first HITL for notes, then conditional DELEGATEs based on the notes outcome, then HITL for release approval, then conditional actions (EMIT or TRANSITION) based on the release outcome.
