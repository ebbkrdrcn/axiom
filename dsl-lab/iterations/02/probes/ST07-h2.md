# go_harness DSL for Release Process

```text
REQUIRE repository
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
LOOP:delivery
  FORK
    → DELEGATE implementation
    → DELEGATE documentation
  JOIN
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
AUTO HITL:release[now, later]("Release now or later?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN release.now
  → EMIT release
  → TRANSITION "Released"
WHEN release.later
  → TRANSITION "Scheduled"
```

## Assumptions Made

1. **Work item identifiers**: The delegated work items in the requirement ("implementation", "documentation", "correction") correspond to the identifiers used in DELEGATE statements, and "release" is the identifier for the EMIT artifact.

2. **Correction handling**: After a correction is delegated in response to implementation rejection, the entire loop body repeats from the beginning, meaning both implementation and documentation are re-delegated (not just re-verified).

3. **Documentation verification**: The requirement does not specify verification of documentation, so it is delegated without VERIFY. It succeeds or fails without affecting the loop condition.

4. **HITL answers**: The phrase "Release now or later?" maps to a binary choice with answer identifiers "now" and "later" (not "approved"/"declined" or other variants).

5. **AUTO decision criteria**: The runtime determines what makes the release decision "clearly determined" (e.g., implementation acceptance, iteration count, other available signals). The agent may automatically answer only when certainty is established; otherwise the human is asked.

6. **FALLBACK behavior**: If the human's response to the release HITL is insufficient, ambiguous, or unavailable, the FALLBACK executes—it does not represent a timeout or automatic fallback, only an explicit "no usable answer" scenario.

7. **Loop termination**: The loop exits only via BREAK (when implementation is accepted), not by exhaustion of attempts. The requirement implies unlimited correction attempts.

8. **Final state semantics**: After the release HITL (or its FALLBACK), the program ends. States "Released", "Scheduled", and "Waiting" are terminal states in this process.
