# Trace of the `LOOP:build` program, first two iterations

Program:

```text
LOOP:build
  DELEGATE build
  VERIFY build
  WHEN build.accepted
    → BREAK
EMIT build-report
```

Given: in every iteration `VERIFY build` establishes `build.rejected`.

## Step-by-step

**Iteration 1**

1. `DELEGATE build` — the loop body's first statement runs. An actor is assigned the work; the statement is done once the actor delivers its result (rule: DELEGATE, "Agentic Operations"). The DSL does not say who the actor is or what the result contains — that is a runtime/mechanism detail the spec deliberately leaves open ("Semantic Principles": DELEGATE defines responsibility, not execution mechanics).
2. `VERIFY build` — evaluates the delivered result. Per the task's premise, it establishes the outcome `build.rejected` (one of the only two possible VERIFY outcomes, `accepted`/`rejected`). This replaces any previous value of the `build` subject (Outcomes: "Latest value").
3. `WHEN build.accepted` — checked once, now that execution reaches it (Execution rule 2 / WHEN semantics). The condition tests whether the *latest* outcome of `build` is exactly `accepted`. It is `rejected`, so the condition is **false**. The flow (`→ BREAK`) is skipped; this is not an error, and execution does not wait (WHEN: "The condition is false").
4. End of the loop body is reached (the `WHEN` was the last statement in the body), and no `BREAK` or `STOP` occurred. Per LOOP's rule, "the next iteration starts at the first statement of the body." The loop restarts.

**Iteration 2**

5. `DELEGATE build` — the body runs again from its first statement, exactly as in iteration 1.
6. `VERIFY build` — again establishes `build.rejected` (per the task's premise), overwriting the outcome from iteration 1 with the same value.
7. `WHEN build.accepted` — checked again, independently of the previous iteration's check (a `WHEN` is "never re-checked" from a prior evaluation; this is a fresh check reached anew). It is again `false: skip`, since the latest outcome is still `rejected`.
8. End of body again, no `BREAK`/`STOP` → the loop restarts a second time, beginning iteration 3.

## Trace (steps for the first two iterations)

```trace
1. DELEGATE build -> done
2. VERIFY build -> outcome build.rejected
3. WHEN build.accepted -> false: skip
4. LOOP:build -> loop again
5. DELEGATE build -> done
6. VERIFY build -> outcome build.rejected
7. WHEN build.accepted -> false: skip
8. LOOP:build -> loop again
```

(Note: entering the loop the very first time is not itself a traced "effect" — execution simply begins at the body's first statement, `DELEGATE build`. The `LOOP:build -> loop again` line marks each subsequent restart of the body, matching the pattern shown in the specification's own complete example, where the `loop again` line appears when the body is re-entered, not on the initial entry. The specification does not spell this out explicitly, so this is the assumption used above; it does not change what actually executes, only how the trace is annotated.)

## Whether and when `EMIT build-report` executes

`EMIT build-report` is **not** executed during the first two iterations, and — under the stated premise that "in every iteration `VERIFY build` establishes `build.rejected`" — it is **never** executed at all, for as long as that premise holds.

Reasoning from the specification:

- `EMIT build-report` is the first statement *after* the loop (it is written at the same indentation as `LOOP:build`, i.e. outside its body).
- Per the LOOP rules, "only `BREAK` or `STOP` ends it," and execution continues after the loop only once it has ended. There is no `STOP` anywhere in this program, so the only way to reach `EMIT build-report` is via `BREAK`.
- The only `BREAK` in the program sits inside `WHEN build.accepted`'s flow. `BREAK` only runs if that `WHEN` is true, i.e. only if some iteration's `VERIFY build` establishes `build.accepted` instead of `build.rejected`.
- Since the task states that `VERIFY build` establishes `build.rejected` in every iteration, `WHEN build.accepted` is false every time it is checked, `BREAK` never runs, the loop never ends, and control never reaches `EMIT build-report`.

This matches the specification's own worked example of this identical program (under "LOOP", "Example"), which states directly: "While `VERIFY build` establishes `build.rejected`, the `WHEN` is false and the loop repeats indefinitely. `EMIT build-report` runs only after a `BREAK`."

## Assumptions stated explicitly

- The specification does not define the content or source of the result that `DELEGATE build` produces, or of what `VERIFY build` evaluates it against; per the DSL's semantic principles, this is intentionally left to the runtime and is irrelevant to the control-flow trace requested here.
- The specification does not explicitly say whether the first entry into a `LOOP` body is annotated in a trace as its own step; the assumption used here (no separate trace line for the very first entry, a `LOOP:<name> -> loop again` line at each subsequent restart) follows the pattern shown in the specification's own "Complete example" trace and does not affect which statements actually execute.
