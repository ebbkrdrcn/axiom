# Answers to go_harness DSL Questions

## Question 1: When `VERIFY fix` establishes `accepted`, which loop does the `BREAK` exit, and which statement executes next?

**Answer:** The `BREAK` exits the **innermost loop, `LOOP:fix`**.

**Reasoning:**
- The `BREAK` statement appears inside the `WHEN fix.accepted` flow within `LOOP:fix`
- According to the specification: "BREAK leaves the innermost enclosing LOOP immediately"
- The innermost loop at this point is `LOOP:fix`, not `LOOP:release`
- After `BREAK` exits `LOOP:fix`, execution continues with the first statement after the loop at the same indentation level as `LOOP:fix`

**Next statement:** `TRANSITION "Fixed"`

The statement after `LOOP:fix` in the source is `TRANSITION "Fixed"`, which is a sibling statement at the same indentation level within `LOOP:release`.

---

## Question 2: Could the author write `BREAK release` inside `LOOP:fix` to leave both loops at once?

**Answer:** No, this is not valid syntax and cannot be written.

**Reasoning:**
- According to the specification: "`<name>` is only a label. No statement refers to it; `BREAK` takes no name."
- The syntax for `BREAK` is simply `BREAK` with no arguments
- `BREAK release` would be invalid because `BREAK` does not accept a name parameter
- The specification explicitly states that `BREAK` cannot target a specific named loop

To leave both loops at once from within `LOOP:fix`, the author would need to use `STOP` (which ends entire execution) or restructure the logic using conditions and `WHEN` statements after a `JOIN` (if loops were in concurrent branches).

---

## Question 3: If `VERIFY release-candidate` establishes `rejected`, what executes next?

**Answer:** The program loops back to the start of `LOOP:release` and executes `LOOP:fix` again.

**Reasoning:**
- `VERIFY release-candidate` establishes `release-candidate.rejected`
- The next statement is `WHEN release-candidate.accepted`, which tests for the `accepted` outcome
- Since the outcome is `rejected` (not `accepted`), the `WHEN` condition is false
- According to the specification: "False → skip the flow and continue after the `WHEN`"
- After skipping the `WHEN`, we reach the end of the body of `LOOP:release`
- According to the LOOP specification: "The last statement of the body is done → The next iteration starts at the first statement of the body"
- Therefore, execution loops back to the beginning of `LOOP:release`, starting with `LOOP:fix` again

This repeating behavior continues indefinitely unless `VERIFY release-candidate` eventually establishes `accepted`, allowing the `BREAK` to exit `LOOP:release`, or some other exit condition (like `STOP` via a fallback) is triggered.
