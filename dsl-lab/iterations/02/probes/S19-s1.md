## Step 1 — Validate first (required before any execution)

The execution procedure states: *"Validate first. Check rules V1–V10. If any is broken, do not execute."* So the program must be checked in full before anything is run.

```

TRANSITION "Deploying"
```

Checking each rule:

This matches **Indentation and scope**. No violation.
- **V2** (`BREAK` outside a `LOOP`): no `BREAK` in the program. N/A.
- **V3** (`BREAK` inside a `FORK` branch leaving a `LOOP` outside it): no `BREAK`, no `FORK`. N/A.
- **V4** (`→` item misplaced, or `→ FALLBACK` not directly under `HITL`/`REQUIRE`, or more than one `FALLBACK`): `→ FALLBACK` is directly under the `HITL`, there is exactly one `FALLBACK`, and its own `→` items (`TRANSITION`, `EMIT`) are under that `FALLBACK`. No violation.
- **V5** (`AUTO` not immediately followed by a decision `HITL`): no `AUTO` used. N/A.
- **V6** (`WHEN` on an undeclared subject/outcome): no `WHEN` statement appears anywhere in the program. N/A.

## Result of validation

**The program is INVALID — it breaks rule V8.**

The specification is explicit that this is fatal to the whole program, not just to the fallback: *"A program that breaks any of these rules is INVALID. It MUST be rejected as a whole and MUST NOT be executed in part."* Rule 1 of the execution procedure likewise says: *"If any [rule] is broken, do not execute."*

Because validation happens before execution and does not depend on runtime events, the stated event ("the human never responds") never comes into play: the program never reaches a point where anyone waits for that response, because it is never executed at all.

## Is `TRANSITION "Deploying"` executed?

**No.** Not because of the fallback, the missing response, or anything about the `HITL`'s own behavior — but because the program as a whole is INVALID (V8) and per the specification it "MUST NOT be executed in part." Since execution never starts, *no* statement runs: not `HITL:region[...]`, not `TRANSITION "Deferred"`, not `EMIT deferral-notice`, not `TRANSITION "Deploying"`, and not `DELEGATE deployment`.

## Assumptions / things the specification does not determine

- The task frames this as an execution question with an event ("the human never responds"), which would normally matter for classifying the `HITL` response as *unavailable* (per the **Usable, insufficient, unavailable** table: "No response, and the runtime has stopped waiting"). The specification does not say precisely when a runtime "stops waiting" for a `HITL` (unlike `WAIT`, for which it explicitly states there is no timeout; `HITL` has no equivalent explicit statement either way). I did not need to resolve this ambiguity because validation precedes and is independent of execution — the program is rejected at the validation stage regardless of how or whether that event is ever classified.
- If the fallback had instead correctly ended in `STOP` or `BREAK` (e.g., `→ EMIT deferral-notice` followed by `→ STOP`), the program would be valid, and then the answer would turn on the unresolved timing question above: while the `HITL` is still waiting, `TRANSITION "Deploying"` is not executed (rule: "Stop at a boundary... the execution waits there"); if/when the runtime eventually treats the missing response as *unavailable*, the fallback runs and ends in `STOP`, which "ends the entire execution immediately," so `TRANSITION "Deploying"` still would never execute. This alternative is noted only for context — it is not what the given (invalid) program actually does.
