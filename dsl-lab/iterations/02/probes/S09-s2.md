# Analysis of the go_harness Program

```
DELEGATE implementation
VERIFY implementation
WHEN implementation.passed
  → TRANSITION "Review"
WHEN tests.failed
  → TRANSITION "Debugging"
```

## 1. Is this program valid?

**No. The program is INVALID**, under rule **V6**:

> V6 | a `WHEN` tests `x.y`, and the program contains neither `VERIFY x` with `y` being `accepted` or `rejected`, nor `HITL:x[…]` listing `y`

It is broken in two separate places:

**a) `WHEN implementation.passed`**

The only statement in the program that can produce an outcome on the subject `implementation` is `VERIFY implementation`. Per the `VERIFY` section:

> It establishes exactly one outcome: `<result>.accepted` or `<result>.rejected`. There are no other VERIFY outcomes: `passed`, `failed`, `ok` and similar are INVALID in a `WHEN` (V6).

`passed` is not `accepted` or `rejected`, so `implementation.passed` is not an outcome the program can ever produce. This `WHEN` violates V6.

**b) `WHEN tests.failed`**

The subject here is `tests`. The program contains no `VERIFY tests` and no `HITL:tests[…]` anywhere. Per the **Outcomes** section, "No other statement produces outcomes," and per V6 the program must contain a `VERIFY x` (with `y` = `accepted`/`rejected`) or a `HITL:x[…]` listing `y` for a `WHEN x.y` to be valid. Neither exists for `tests`/`failed`, so this `WHEN` also violates V6 (independently: the subject `tests` is never declared at all, and `failed` is not a legal `VERIFY` outcome regardless).

**Other rules checked (all satisfied / not applicable):**
- V1 (indentation): the two `→` items are each indented consistently under their `WHEN`, matching the `form`/EBNF; no violation.
- V2/V3 (`BREAK`): no `BREAK` statement is present; not applicable.
- V4 (`→` placement): both `→` items are directly under a `WHEN`, which is a permitted parent; no `FALLBACK` is used; no violation.
- V5 (`AUTO`): not used; not applicable.
- V7 (`HITL`/`VERIFY` name collisions, answer lists): no `HITL` statements at all, so no collision or empty/repeated-answer issue.
- V8 (fallback must end in `STOP`/`BREAK`): no `FALLBACK` present; not applicable.
- V9 (`JOIN`/`FORK` pairing and branch count): no `FORK`/`JOIN`; not applicable.
- V10 (`WHEN` on an unjoined `FORK` branch outcome): no `FORK`; not applicable.

**Conclusion:** the program is INVALID solely (but doubly) under **V6** — once for `implementation.passed` (wrong outcome vocabulary for a `VERIFY`-derived subject) and once for `tests.failed` (subject never declared by any `VERIFY` or `HITL` in the program).

## 2. If `VERIFY implementation` is negative, what does an executing agent do?

The specification's execution procedure states:

> 1. **Validate first.** Check rules V1–V10. If any is broken, do not execute.

and, on validity generally:

> A program that breaks any of these rules is INVALID. It MUST be rejected as a whole and MUST NOT be executed in part.

Since this program is already INVALID under V6 (as shown above), an executing agent **never reaches the point of running `VERIFY implementation` at all**. Validation happens before any execution, and it fails, so the agent must reject the whole program and report the broken rule (V6, cited twice — once per offending `WHEN`). It must not partially execute the `DELEGATE`/`VERIFY` statements and then stop, and it must not "fix" the program on its own initiative (e.g., silently treating `passed` as `accepted`) — the specification gives the agent no license to reinterpret or repair an invalid program.

So, strictly per the spec: **the agent does nothing with the outcome of `VERIFY implementation`, because execution never starts.** What "negative" would even mean here is itself ambiguous, since the DSL's only vocabulary for a negative `VERIFY` result is `rejected` (the spec is explicit that terms like "failed" are invalid), and the task's wording ("negative") is not a term the specification defines — this is a case where the specification does not determine something and I flag the assumption below.

**For completeness, a purely hypothetical note** (not something the spec actually licenses executing, since the program as a whole is rejected): if one were to ignore the invalidity and imagine `VERIFY implementation` executing on its own and establishing `implementation.rejected` (the DSL's actual "negative" outcome per the **VERIFY** section), then:
- `WHEN implementation.passed` would be false and skipped, because the latest outcome on `implementation` is `rejected`, not `passed` (and, as noted, `passed` could in fact never be established by any statement in this program).
- `WHEN tests.failed` would also be false and skipped, because no statement in the program ever establishes any outcome on the subject `tests` (rule 7: "Before anything establishes it, every `WHEN` on it is false").
- Both `WHEN`s being the last top-level statements, execution would end normally per rule 10, with no state `TRANSITION` having occurred.

This hypothetical trace is offered only to show what the written statements would do mechanically; it does not override the primary answer that the program is INVALID and MUST NOT be executed at all.

## Assumptions

The specification does not determine, and I explicitly assume:
- That "negative" in the task's second question is intended to mean the DSL's `rejected` outcome (the only negative `VERIFY` outcome the DSL defines), since the spec never uses the word "negative" itself.
- That indentation in the given program (two-space indents under each `WHEN`, consistent depth) is exactly as intended and not corrupted by whitespace not visible in the task text; under that reading V1 is not violated. If the actual indentation differed from what is shown, that could introduce an additional V1 violation, but nothing in the given text suggests that.
