# Answer

## Preliminary: is the program valid?

```
REQUIRE staging-credentials
DELEGATE deployment
EMIT deployment-log
```

Yes. It is three top-level statements, none indented, no `WHEN`, `HITL`, `FORK`, `LOOP`, or `BREAK` involved, so none of V1–V10 are triggered. In particular, the `REQUIRE` here has **no attached `→ FALLBACK`** — per the grammar, `fallback` after `require` is optional (`require = "REQUIRE" , identifier , NL , [ fallback ] ;`), so a bare `REQUIRE` with no fallback is well-formed. The program may be executed.

## 1. What happens at `REQUIRE staging-credentials`?

Per the `REQUIRE` rules:

| Situation | What happens |
|---|---|
| The item is not yet available | Wait at the `REQUIRE`. |
| The runtime determines the item cannot be obtained, and there is a `FALLBACK` | Run the fallback flow. |
| The runtime determines the item cannot be obtained, and there is no `FALLBACK` | Execution ends, as with `STOP`. |

Execution first waits at `REQUIRE staging-credentials`. The runtime then determines the item cannot be obtained. Because this `REQUIRE` has no `→ FALLBACK` attached, the third row applies directly: **execution ends, as with `STOP`.** This means no further statement runs anywhere (there are no other branches here, but the same "ends everything immediately" semantics as `STOP` apply), and no outcome is established (`REQUIRE` establishes no outcome under any circumstance).

A trace of this, using the spec's trace vocabulary, would read:

```trace
1. REQUIRE staging-credentials -> waiting
2. REQUIRE staging-credentials -> stop
```

(There is no dedicated effect keyword in the spec's list for "ends as with STOP because the required item is unobtainable and there is no fallback"; the closest and most faithful rendering is `stop`, since the spec explicitly equates the outcome to `STOP`'s effect. Immediately after, execution ends, i.e. an `end` line would follow if the program had a defined "after" point — but here nothing follows since `STOP`-like termination ends everything.)

## 2. Is `DELEGATE deployment` executed?

No. `REQUIRE` states that the item MUST be available *before continuing*, and when it cannot be obtained and there is no `FALLBACK`, "execution ends, as with `STOP`." `STOP`'s own rule is unambiguous: "No further statement runs anywhere." Since `DELEGATE deployment` is the statement immediately after the `REQUIRE`, execution never reaches it.

## 3. Is `EMIT deployment-log` executed?

No, for the same reason. It is even later in the program than `DELEGATE deployment`, and since execution already ended at the `REQUIRE`, none of the subsequent statements — `DELEGATE deployment` or `EMIT deployment-log` — run.

## 4. What exactly should the executing agent do?

Based on the "Executing a program" procedure and the `REQUIRE` and `STOP` rules, the agent MUST:

- Wait at `REQUIRE staging-credentials` until the runtime resolves the situation (per "Stop at a boundary": "If an event, response, or result is not yet available, the execution waits there. Do not assume what it will be.").
- Once the runtime determines the credentials cannot be obtained, treat this as terminal for this `REQUIRE` since no `FALLBACK` is attached: end the entire execution immediately, exactly as `STOP` would — running no further statement anywhere in the program.
- Not execute `DELEGATE deployment` or `EMIT deployment-log`.
- Not establish any outcome for this event (`REQUIRE` establishes no outcome under any circumstance).
- Not invent, assume, fabricate, or substitute the missing item (`staging-credentials`), and not continue in any "degraded mode" — this is explicit in the `REQUIRE` section: "The agent MUST NOT assume, fabricate, or substitute the item. It MUST NOT skip the `REQUIRE` or continue in a degraded mode."
- Not skip the `REQUIRE` construct or route around it, since `REQUIRE` describes *what* must be available, and only the runtime's own determination that the item is unobtainable licenses ending execution — the agent cannot decide this on its own initiative, invent that determination, or override it.
- Report the execution as ended (per the "Never invent" and "Stop at a boundary" principles, and consistent with `STOP`'s effect), rather than reporting deployment or the emitted log as having occurred.

No assumptions were needed to answer this task: the specification's `REQUIRE` table and the `STOP` rule together fully and unambiguously determine the outcome for a `REQUIRE` with no `FALLBACK` whose item the runtime finds unobtainable.
