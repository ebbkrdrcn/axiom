# go_harness program

```text
DELEGATE tests
VERIFY tests
WHEN tests.accepted
  → TRANSITION "Review"
WHEN tests.rejected
  → TRANSITION "Debugging"
  → DELEGATE diagnosis
```

## Assumptions

The specification does not fix the identifiers used for the delegated work or the verified result, so the following had to be assumed or chosen:

1. **Identifier for the test suite.** The requirement names "the test suite" but the DSL requires an identifier for both `DELEGATE` and `VERIFY`. I used `tests` for both, so that `VERIFY tests` evaluates the result of `DELEGATE tests` and establishes the outcome under the subject `tests`. The spec does not state a rule binding a `VERIFY`'s argument to a preceding `DELEGATE`'s argument by name — this link is only implied by convention (as in the spec's own `DELEGATE implementation` / `VERIFY implementation` example) and by needing a consistent subject for the `WHEN` conditions.

2. **Mapping "pass"/"fail" to `accepted`/`rejected`.** `VERIFY` only ever establishes `accepted` or `rejected` (rule V6, and the Outcomes table lists no other `VERIFY` outcomes). Since the requirement says "pass" and "fail," and these are not valid `WHEN` outcomes for a `VERIFY` subject, I mapped "tests pass" → `tests.accepted` and "tests fail" → `tests.rejected`, which is the only mapping the DSL's fixed vocabulary allows.

3. **Identifier for the diagnosis work.** The requirement says "delegate a diagnosis" without naming it; I used the identifier `diagnosis` for `DELEGATE diagnosis`.

4. **No `REQUIRE`, `HITL`, `LOOP`, or `FORK`.** The requirement describes a single linear delegate-verify-branch sequence with no mention of prerequisites, human decisions, repetition, or concurrency, so none of these constructs were introduced. Since there is no `HITL` or `REQUIRE`, no `→ FALLBACK` is needed or permitted (`FALLBACK` only attaches to those two constructs, per the grammar and V4).

5. **Order and independence of the two `WHEN` blocks.** Per rule 3 ("Consecutive `WHEN`s are independent... there is no 'first match'"), the `WHEN tests.accepted` and `WHEN tests.rejected` blocks are mutually exclusive in practice only because `VERIFY` establishes exactly one of the two outcomes (rule per `VERIFY` section: "establishes exactly one outcome"). I placed the accepted case first purely for readability, following the order of the requirement's phrasing ("if tests pass... if tests fail..."); the spec does not require a particular order for independent `WHEN`s.

6. **No explicit `STOP` at the end.** Per rule 10 ("When the last top-level statement is done, execution ends normally") and the `STOP` section ("`STOP` is not required at the end of a program"), no trailing `STOP` was added; the program ends normally after either branch completes.

7. **Two separate `TRANSITION`/`DELEGATE` statements in the rejected branch are sequential.** Under a `WHEN`, `→` items form one sequential flow (rule 4 / Quick reference), so `TRANSITION "Debugging"` runs before `DELEGATE diagnosis`, matching the requirement's stated order ("move to state 'Debugging' and delegate a diagnosis").
