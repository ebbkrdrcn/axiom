# go_harness DSL Validation

## Snippet A: INVALID - V5

**Rule violated:** V5 - `AUTO` is not immediately followed, on the same line, by a decision `HITL:<name>[…]`

**Issue:** The `AUTO` keyword appears on a separate line from the `HITL` statement. According to the specification, `AUTO` must be written directly before `HITL`, on the same line. The specification explicitly marks this pattern as invalid (lines 408-412 of the specification).

**Correct form would be:**
```
AUTO HITL:release[approved, rejected]("Approve release?")
```

---

## Snippet B: INVALID - V2

**Rule violated:** V2 - `BREAK` is not inside a `LOOP`

**Issue:** The `BREAK` statement is not enclosed within a `LOOP` body. Although `BREAK` appears inside a `WHEN` construct, `WHEN` does not satisfy the requirement. `BREAK` must be inside a loop body to leave the innermost enclosing loop.

**Correct form would require:**
```
LOOP:name
  DELEGATE implementation
  VERIFY implementation
  WHEN implementation.rejected
    → BREAK
```

## Snippet C: VALID

**Analysis:** All validity rules are satisfied.

- The `AUTO HITL:approve[yes, no]("Approve release?")` statement is valid: `AUTO` appears on the same line immediately before the decision (✓ V5)
- The `WHEN approve.yes` condition is valid: it tests an outcome that the `HITL:approve` statement can produce (✓ V6)
- The `EMIT release` statement is a valid flow item within the `WHEN` construct
- No other validity constraints are violated

## Snippet D: INVALID - V8

**Rule violated:** V8 - the last item of a fallback flow is not `STOP` or `BREAK`

**Issue:** The fallback flow ends with `TRANSITION "Blocked"` but contains neither `STOP` nor `BREAK`. According to the specification, every fallback flow must end with one of these statements because the fallback never continues into the normal flow after the `HITL` or `REQUIRE`.

**Correct form would be:**
```
HITL:region[eu, us]("Which region?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN region.eu
  → DELEGATE eu-deployment
```
