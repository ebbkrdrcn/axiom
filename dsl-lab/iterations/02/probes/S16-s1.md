# Execution of the `tdd` program

## 1. Validation

Program:

```
LOOP:tdd
  DELEGATE implementation
  DELEGATE tests
  VERIFY tests
  WHEN tests.accepted
    → TRANSITION "Review"
    → BREAK
  WHEN tests.rejected
    → TRANSITION "Debugging"
    → DELEGATE diagnosis
EMIT source-code
```

Checking V1–V10:

- **V1** (indentation): The loop body (`DELEGATE implementation`, `DELEGATE tests`, `VERIFY tests`, the two `WHEN`s) is indented one level under `LOOP:tdd`; each `WHEN`'s `→` items are indented one level under that `WHEN`. `EMIT source-code` returns to the depth of `LOOP:tdd`, ending the loop's scope. No violation.
- **V2** (`BREAK` inside a `LOOP`): `BREAK` is inside the `WHEN tests.accepted` flow, which is inside `LOOP:tdd`. Satisfied.
- **V3** (`BREAK` across a `FORK` branch): there is no `FORK` in this program, so this cannot be violated.
- **V4** (`→` placement): all `→` items are directly under a `WHEN`. No `FALLBACK`. No violation.
- **V5** (`AUTO`): not used. N/A.
- **V6** (`WHEN` refers to a declared outcome): `tests.accepted` and `tests.rejected` are both outcomes of `VERIFY tests` (the only two `VERIFY` outcomes). Both `WHEN`s test one of these two. Satisfied.
- **V7** (name collisions / answer lists): only one subject name (`tests`), used only by `VERIFY`. No `HITL`. No violation.
- **V8** (fallback must end in `STOP`/`BREAK`): no `FALLBACK` present. N/A.
- **V9** (`JOIN`/`FORK` pairing, branch count): no `FORK`/`JOIN` present. N/A.
- **V10** (`WHEN` on an unjoined `FORK` branch outcome): no `FORK` present. N/A.

**The program is VALID.** No rule is broken; it may be executed.

## 2. Assumption

The specification does not explicitly state whether the `LOOP:<name>` header itself is written as a numbered trace step the first time the loop is entered. The worked "Complete example" in the specification (`LOOP:delivery`) shows the loop header appearing in the trace **only** when the body repeats (as `loop again`); on first entry, execution simply starts at the loop's first body statement with no separate line for `LOOP:delivery`. I follow that same convention here: `LOOP:tdd` is not given its own trace line on first entry, but is given one (`-> loop again`) each time the body restarts.

## 3. Step-by-step execution trace

Events given: iteration 1 — `VERIFY tests` establishes `rejected`; iteration 2 — `VERIFY tests` establishes `accepted`.

```trace
1. DELEGATE implementation -> done
2. DELEGATE tests -> done
3. VERIFY tests -> outcome tests.rejected
4. WHEN tests.accepted -> false: skip
5. WHEN tests.rejected -> true: run flow
6. TRANSITION "Debugging" -> state = "Debugging"
7. DELEGATE diagnosis -> done
8. LOOP:tdd -> loop again
9. DELEGATE implementation -> done
10. DELEGATE tests -> done
11. VERIFY tests -> outcome tests.accepted
12. WHEN tests.accepted -> true: run flow
13. TRANSITION "Review" -> state = "Review"
14. BREAK -> break
15. EMIT source-code -> done
16. (end of program) -> end
```

### Notes on individual steps

- **Step 3**: `VERIFY tests` establishes exactly one outcome, `tests.rejected` (rule: a `VERIFY` establishes `accepted` or `rejected`, nothing else).
- **Step 4**: at this point the latest outcome of `tests` is `rejected`, so `WHEN tests.accepted` is false ("Latest value" rule under **Outcomes**); its flow is skipped, execution continues to the next statement — it does **not** wait and does not error.
- **Step 5**: `WHEN tests.rejected` is checked independently of the previous `WHEN` ("Consecutive `WHEN`s are independent... every one that is true runs"); it is true, so its flow runs sequentially: `TRANSITION "Debugging"` then `DELEGATE diagnosis`.
- **Step 8**: the last statement of the loop body (`DELEGATE diagnosis`) is done, so the body restarts at its first statement (`LOOP` rule: "end of body → start body again").
- **Step 11**: a new `VERIFY tests` replaces the previous outcome; the latest value of `tests` is now `accepted` ("A later `VERIFY x` ... replaces it").
- **Step 12**: `WHEN tests.accepted` is now true (top-to-bottom, checked once when reached), so its flow runs.
- **Step 13**: `TRANSITION "Review"` replaces the current process state; the previous state ("Debugging", set in step 6) is overwritten — "the most recently executed one wins."
- **Step 14**: `BREAK` leaves the innermost loop (`tdd`) immediately. Per the `BREAK` rule, "the remaining statements of the current iteration are not executed, including later `WHEN`s" — so `WHEN tests.rejected` (the second `WHEN` in the loop body) is **not** evaluated at all in this iteration; it is skipped without a trace line, not run and found false.
- **Step 15**: execution continues with the first statement after the loop, at the loop's indentation, which is `EMIT source-code`.
- **Step 16**: `EMIT source-code` was the last top-level statement, so execution ends normally (rule 10 of "Execution in ten rules"); no explicit `STOP` was needed.

## 4. Final state

**`Review`**

This is the value set by the last executed `TRANSITION` (step 13, `TRANSITION "Review"`), which overwrote the earlier `"Debugging"` state from iteration 1. No later `TRANSITION` runs after it, since the second `WHEN` in iteration 2 is never reached (the `BREAK` exits the loop first) and no `TRANSITION` appears after the loop.
