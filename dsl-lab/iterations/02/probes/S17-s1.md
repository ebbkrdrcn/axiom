```text
DELEGATE test-suite
VERIFY test-suite
WHEN test-suite.accepted
  → TRANSITION "Review"
WHEN test-suite.rejected
  → TRANSITION "Debugging"
  → DELEGATE diagnosis
```

## Assumptions

The specification determines most of this program directly (a `DELEGATE`/`VERIFY` pair followed by two independent `WHEN`s testing `accepted`/`rejected`, exactly as in the spec's own `WHEN` example). Where the specification does not determine something, I assumed:

1. **Identifier for "the test suite".** Identifiers may only contain letters, digits, `-` and `_` (no spaces), so I named the delegated work and the verified result `test-suite`. The spec requires `DELEGATE` and `VERIFY` to name the same subject for `VERIFY`'s outcome to attach to the thing delegated, so both statements use the identical identifier `test-suite`.

2. **Mapping "pass"/"fail" to `accepted`/`rejected`.** `VERIFY` establishes only `accepted` or `rejected` (no `passed`/`failed`, which the spec explicitly marks INVALID in a `WHEN`, rule V6). I treated "the tests pass" as `test-suite.accepted` and "the tests fail" as `test-suite.rejected`.

3. **No `FALLBACK`.** The requirement never mentions an unusable response, a missing verification, or an unavailable requirement, so I did not add a `→ FALLBACK`. Nothing in this requirement involves `HITL` or `REQUIRE`, so `FALLBACK` (which only attaches to those) is not applicable.

4. **Identifier for the diagnosis work.** "delegate a diagnosis" has no explicit name in the requirement, so I introduced the identifier `diagnosis` for the `DELEGATE` argument.

5. **Order within the "fail" branch.** The requirement says "move to state 'Debugging' and delegate a diagnosis," which I read as sequential (state change first, then delegation), matching the word order and the spec's own analogous example (`TRANSITION "Debugging"` before `DELEGATE diagnosis`).

6. **No loop, fork, or repetition.** The requirement describes a single one-shot check (delegate once, verify once, branch once), not a repeating process, so no `LOOP` was introduced. Nothing in the requirement implies concurrency, so no `FORK`/`JOIN` was used.

7. **Two independent `WHEN`s rather than an if/else.** The DSL has no "else" construct (per the Quick reference and rule for consecutive `WHEN`s), so "if tests pass … if tests fail …" was expressed as two separate, independently-checked `WHEN test-suite.accepted` / `WHEN test-suite.rejected` blocks, which is exhaustive here since `VERIFY` establishes exactly one of these two outcomes.

8. **No top-level `STOP`.** The spec states execution ends normally after the last top-level statement, so no explicit `STOP` was added; the program ends after the second `WHEN` block regardless of which branch (or neither, if unreached) ran.

9. **Program scope.** The requirement describes only this delegate/verify/branch sequence, so nothing before it (e.g., a `REQUIRE`) or after it (e.g., an `EMIT`) was assumed to exist, since none was mentioned.
