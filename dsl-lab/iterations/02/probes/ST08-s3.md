## 2. The key decision: does `AUTO` resolve the refund decision itself?

`AUTO HITL:refund[approve, deny]("Approve the refund of 4,000 EUR?")` may only be answered by the agent if the decision is **certain and within the agent's authority** (Quick reference table "Who decides a `HITL`"; **AUTO** section).

The spec lists, as an explicit example of uncertainty under `AUTO`:

> "the agent does not have the authority required to make the decision."

Here:
- `VERIFY refund-assessment` establishes `accepted`, and the context states the eligibility criteria clearly show the customer is eligible. This makes the *merits* of the refund certain.
- However, company policy restricts approval of refunds above 1,000 EUR to a finance manager, and the agent is not a finance manager. The refund in question is 4,000 EUR, i.e. above that threshold.

Certainty about eligibility does not supply certainty about **authority**, and the two are independent conditions in the spec's list of uncertainty triggers. Because the agent lacks the authority required to make *this* decision, the decision is not "certain and within the agent's authority" as a whole, regardless of how clear the underlying merits are. Per the table:

> "Anything else → The human is asked, exactly as for a `HITL` without `AUTO`."

So the agent MUST NOT answer `refund.approve` itself; it must wait for the human. There is no `FALLBACK` attached to this `HITL`, so if the eventual response were insufficient or unavailable, execution would end as with `STOP` (rule table under **HITL**). That does not happen here: the finance manager later responds "approve", which clearly selects the listed answer `approve` (a usable response, per **Usable, insufficient, unavailable**), so the outcome `refund.approve` is established and execution continues after the `HITL` construct.

## 3. Step-by-step trace

```trace
1. DELEGATE refund-assessment -> done
2. VERIFY refund-assessment -> outcome refund-assessment.accepted
3. AUTO HITL:refund[approve, deny]("Approve the refund of 4,000 EUR?") -> waiting
4. AUTO HITL:refund[approve, deny]("Approve the refund of 4,000 EUR?") -> outcome refund.approve
5. WHEN refund.approve -> true: run flow
6. DELEGATE payout -> done
7. TRANSITION "Refunded" -> state = "Refunded"
8. WHEN refund.deny -> false: skip
9. (end of program) -> end
```

Notes on the trace:
- Step 2 establishes the outcome `refund-assessment.accepted`. No `WHEN` in this program tests `refund-assessment.*`, so it is recorded but not otherwise used later — this is permitted; the DSL does not require every outcome to be consumed.
- Steps 3–4 follow the same two-line pattern as the specification's own complete example (`AUTO HITL:merge...` in the "Complete example" trace): the construct first waits (the decision cannot be resolved automatically, so the human is asked), then, once the finance manager's response arrives, the outcome is established. Per rule 9 of "Execution in ten rules" and the **HITL** rules, only the human's actual response after the `HITL` is reached may establish this outcome — the agent never substitutes its own judgment here, exactly because it lacks authority.
- Step 5 runs the `refund.approve` flow because that outcome is now `approve`.
- Steps 6–7 are the two `→` items of that flow, executed sequentially: `DELEGATE payout` completes, then `TRANSITION "Refunded"` sets the process state.
- Step 8: `WHEN refund.deny` is independently checked (consecutive `WHEN`s are independent, rule 3 of "Execution in ten rules") and is false, since the latest — and only — outcome on `refund` is `approve`.
- Step 9: the last top-level statement is done, so execution ends normally (rule 10).

## 5. Assumptions made where the specification does not fully determine the answer

The specification does not name any DSL construct for "authority" or "policy thresholds" — these are ordinary real-world facts fed into the `AUTO` uncertainty judgment, not DSL keywords or states (the spec explicitly says "Uncertainty is not a DSL condition, state, variable, or keyword; the runtime determines it"). Applying the spec's own listed example ("the agent does not have the authority required to make the decision") to this fact pattern is the most direct reading, but two points are worth flagging as assumptions rather than rules stated verbatim for this exact scenario:

1. **Authority overrides certainty of merits.** The spec does not explicitly state a priority order between "the eligibility criteria are clearly met" and "the agent lacks authority" when both concern the same `AUTO HITL`. I assumed that *either* condition on the uncertainty list being present is sufficient to make the decision not "certain and within the agent's authority," since the table's left-hand condition is a conjunction ("certain **and** within the agent's authority") and any single failing conjunct makes the whole condition false. This reading follows directly from the wording of the table but is stated here explicitly since the task pairs a certain fact (eligibility) with an authority gap, inviting the opposite (incorrect) conclusion.
2. **Who counts as "the human."** The `HITL`/`AUTO` sections only ever refer to "the human," with no role restriction. I assumed the finance manager's reply qualifies as a response from "the human" for the purposes of this `HITL`, since the spec places no constraint on which human must answer — it only requires that the response be given to this `HITL` after execution reached it (which it was).
3. **No `FALLBACK` is attached to this `HITL`.** Since the finance manager's answer was usable, this never became relevant, but if the response had been insufficient or absent, the specification says execution would end "as with `STOP`" (no outcome established) since there is no `→ FALLBACK` in the program as written. I did not add one, since the task gives no fallback and the DSL does not require every `HITL` to have one.
