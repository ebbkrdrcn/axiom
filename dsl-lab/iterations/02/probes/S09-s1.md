# 1. Is the program valid?

```
DELEGATE implementation
VERIFY implementation
WHEN implementation.passed
  → TRANSITION "Review"
WHEN tests.failed
  → TRANSITION "Debugging"
```

**No. The program is INVALID, under rule V6 — twice.**

Rule V6: *"a `WHEN` tests `x.y`, and the program contains neither `VERIFY x` with `y` being `accepted` or `rejected`, nor `HITL:x[…]` listing `y`."*

- **`WHEN implementation.passed`** — The program does contain `VERIFY implementation`, so the subject `implementation` exists, but per the **Outcomes** table and the `VERIFY` section, `VERIFY <result>` can only ever establish `<result>.accepted` or `<result>.rejected`. `passed` is not one of those two outcomes. The spec is explicit that this is exactly the failure V6 is for: *"`passed`, `failed`, `ok` and similar are INVALID in a `WHEN` (V6)."* So this `WHEN` tests an outcome the program cannot produce.
- **`WHEN tests.failed`** — The subject is `tests`, not `implementation`. Nothing in the program verifies or asks about `tests`: there is no `VERIFY tests` and no `HITL:tests[…]`. So no statement in the program can ever establish `tests.accepted`, `tests.rejected`, or any `HITL` answer for a subject named `tests`. This `WHEN` also violates V6 — independently of the first one, since `tests` is an entirely different subject from `implementation`.

Checking the rest of the validity rules for completeness (none of them are violated):
- **V1** (indentation): the `→` lines under each `WHEN` are consistently indented; fine.
- **V2/V3** (`BREAK`): no `BREAK` statement is present; not applicable.
- **V4** (`→` placement): both `→` items are directly under a `WHEN`, which is allowed; no `FALLBACK` is used; fine.
- **V5** (`AUTO`): not used; not applicable.
- **V7** (name collisions): only one `HITL`/`VERIFY`-style name (`implementation`) is used by `VERIFY`; no `HITL` at all, so no name reuse or duplicate/empty answer lists; fine.
- **V8** (fallback ending): no fallback flow is present; not applicable.
- **V9** (`FORK`/`JOIN`): neither is present; not applicable.
- **V10** (`WHEN` on an unjoined `FORK` branch's outcome): no `FORK` is present; not applicable.

So the sole (but doubled) defect is **V6**: both `WHEN` conditions test outcomes the program cannot produce — `implementation.passed` is not a possible `VERIFY` outcome (only `accepted`/`rejected` exist), and `tests.*` is never established by anything in the program at all.

Per **Validity rules**, *"A program that breaks any of these rules is INVALID. It MUST be rejected as a whole and MUST NOT be executed in part."* Per **Executing a program**, step 1: *"Validate first... If any is broken, do not execute."* So a compliant executing agent would not run any part of this program; it would report the broken rule (V6) for both `WHEN` lines and stop.

# 2. If `VERIFY implementation` is negative, what does an executing agent do?

**Primary answer, following the spec exactly:** Nothing — because the program is INVALID. The spec's execution procedure requires validation *before* execution ("Validate first... If any is broken, do not execute"), and an INVALID program "MUST be rejected as a whole and MUST NOT be executed in part." Since this program fails V6 (as shown above), a compliant agent never reaches `VERIFY implementation` at all: it validates the program, finds V6 broken twice, reports rule V6 for each faulty `WHEN`, and does not execute — regardless of what `VERIFY implementation` would have produced. The premise "if `VERIFY implementation` is negative" describes a step of execution that a correctly-behaving agent never gets to perform on this program.

**Secondary answer — the hypothetical execution, if the program had been well-formed:**

Since the task asks what happens if this `VERIFY` is "negative," I'll answer that too, stating the assumption it requires: the spec never uses the word "negative," so I assume it means `VERIFY implementation` establishes `implementation.rejected` — the only two outcomes `VERIFY` can produce are `accepted` and `rejected` (Outcomes table; `VERIFY` section), so "negative" is read as `rejected`. Under that assumption, and setting aside the invalidity finding above purely to trace what the mechanical rules would do:

1. `DELEGATE implementation` runs; the statement is done once the actor delivers a result (no outcome established).
2. `VERIFY implementation` runs and establishes `implementation.rejected` (per the assumption above).
3. `WHEN implementation.passed` is checked once. The condition is true only if the latest outcome of `implementation` is exactly `passed` (rule 7/rule 2 of **Execution in ten rules**). The latest outcome is `rejected`, not `passed`, so the condition is false. Per the spec this is not an error at the execution-semantics level — "False → skip it. This is not an error. Execution does not wait." — so this line is skipped and execution continues after it. (Note: as established in Part 1, this `WHEN` is only reachable at all in an already-invalid program; V6 means the `passed` outcome could never legitimately arise from this `VERIFY`, positive or negative.)
4. `WHEN tests.failed` is checked once, independently of the previous `WHEN` ("Consecutive `WHEN`s are independent... every one that is true runs"). The subject `tests` has no outcome established anywhere in the program — "Before anything establishes it, every `WHEN` on it is false" — so this is also false and is skipped, regardless of whether `implementation` was accepted or rejected.
5. There is no further statement. Per rule 10, "When the last top-level statement is done, execution ends normally."

So, even under the hypothetical, a negative (`rejected`) `VERIFY implementation` would **not** trigger `TRANSITION "Review"` (that branch is gated on a `passed` outcome that `VERIFY` can never produce) nor `TRANSITION "Debugging"` (that branch is gated on a `tests` subject nothing in the program ever verifies). No `TRANSITION` would execute at all, so the process's current state would remain whatever it was before this fragment ran (the spec does not define a default/initial state — that is left unspecified, so I note it rather than assume a value). Execution would simply reach the end of the program and end normally, with no state change and no error surfaced by the runtime — silently discarding both the accept and the reject cases, which is itself a symptom of why the program is invalid.
