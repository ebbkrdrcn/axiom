```text
FORK
  → DELEGATE security-review
      VERIFY security-review
  → DELEGATE performance-review
      VERIFY performance-review
JOIN
TRANSITION "Release"
```

## Assumptions

- **Identifiers for the work items.** The requirement names the reviews only in prose ("a security review", "a performance review"). The DSL requires identifiers, so I used `security-review` and `performance-review` as both the `DELEGATE` argument and the matching `VERIFY` result name in each branch. The specification does not dictate a naming convention, so this naming is my choice.
- **No outcome handling required.** The requirement says only to "continue" after both flows finish and then transition; it does not say anything should happen differently based on `accepted`/`rejected`. So I did not add any `WHEN` on `security-review.accepted/rejected` or `performance-review.accepted/rejected`. `VERIFY` still establishes these outcomes per the spec, but nothing in the requirement asks them to be consumed, and the spec does not require every established outcome to be tested.
- **"Continue only after both flows have finished" = `JOIN`.** This is the DSL's defined mechanism for waiting for all branches of a `FORK` to complete, and "each review is delegated and then verified within its own parallel flow" maps directly to `FORK`'s branch model (a `→` item plus its nested lines forms one sequential branch flow), so I used `FORK` with two `→` branches followed by `JOIN`, rather than, e.g., running the two reviews sequentially.
- **No `REQUIRE`, `HITL`, `LOOP`, or `FALLBACK`.** The requirement mentions no precondition to require, no human decision, no repetition, and no failure/unavailability handling, so none of these constructs were introduced. Per the spec, `DELEGATE`/`VERIFY` alone are sufficient to model "delegated and then verified."
- **Placement of `TRANSITION "Release"`.** It is the last top-level statement, placed after `JOIN`, so it runs exactly once, only after both branches have completed, matching "Continue only after both flows have finished, then transition to state 'Release'."
- **Program is top-level (no enclosing `LOOP`/`WHEN`/etc.).** The requirement describes a single, one-shot sequence (fork → join → transition), with nothing suggesting repetition or a surrounding condition, so the whole program is written at the top level with no wrapping construct.
