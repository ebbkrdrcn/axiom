# Analysis of the go_harness program

```
DELEGATE design
DELEGATE implementation
FORK
  → DELEGATE docs
  → DELEGATE changelog
EMIT release
```

## 1. Can `DELEGATE implementation` start before the design has been delivered?

**No.**

- Execution rule 1 (Quick reference, "Execution in ten rules"): *"Statements run one at a time, in the order written. Each statement finishes before the next starts. Only `FORK` runs things concurrently."*
- The **DELEGATE** section: *"The statement is done when the actor has delivered its result. The next statement starts only then. To delegate concurrently, use `FORK`."*

`DELEGATE design` and `DELEGATE implementation` are two plain, sequential top-level statements — they are not inside a `FORK`. Therefore `DELEGATE implementation` cannot start until `DELEGATE design` is *done*, and `DELEGATE design` is done only when the design actor has delivered its result. Since the spec states the delegate finishes only on delivery (not on assignment, acceptance, or elapsed time), execution simply waits at `DELEGATE design` for however long the actor takes ("a long time" in the given events) before `DELEGATE implementation` can start. The DSL gives no mechanism for starting the next statement early; concurrency is only available via `FORK`, which is not used between these two statements.

## 2. When is `EMIT release` executed relative to the docs and changelog branches?

**`EMIT release` runs immediately after `FORK` starts the branches — it does not wait for either branch, and in general runs concurrently with (in parallel to, and likely before the completion of) both `docs` and `changelog`.**

- Quick reference, `FORK` row: *"start concurrent branches ... no `JOIN` → continue immediately."*
- Quick reference, `JOIN` row: *"wait for all branches of the nearest open `FORK`."*
- **FORK** section: *"`FORK` is reached → All branches start... No `JOIN` follows → Execution continues immediately after the `FORK` while the branches run."*

In this program there is no `JOIN` statement between `FORK` and `EMIT release`. Per the rules above, when there is no `JOIN`, execution proceeds to the next top-level statement (`EMIT release`) immediately once the `FORK` has started its branches, while the `docs` and `changelog` branches continue running concurrently in the background. So `EMIT release` executes right after the fork point, not after either branch completes — it runs concurrently with (and, given the stated timings, before) the completion of both the docs branch (1 hour) and the changelog branch (5 minutes). Note: the DSL itself does not reason about wall-clock durations; the "no JOIN → continue immediately" rule is a structural/ordering rule, not a race based on which branch is faster — `EMIT release` always fires right after `FORK`, regardless of how long the branches take.

## 3. Is it guaranteed that docs exist when `EMIT release` executes?

**No, it is not guaranteed.**

- Because there is no `JOIN` after the `FORK`, `EMIT release` is executed immediately after the branches start, without waiting for either branch's last statement to be done. The **FORK** table states a branch "is complete" only when its last statement is done, and completion is only ever awaited via `JOIN` (*"Waits until every branch of the corresponding `FORK` is complete."*, **JOIN** section). Since no `JOIN` is present, the program provides no synchronization point guaranteeing that `DELEGATE docs` (or `DELEGATE changelog`) has finished before `EMIT release` runs.
- Given the stated events (docs takes 1 hour, changelog takes 5 minutes, and `EMIT release` runs immediately after the fork), `EMIT release` will in practice execute long before the docs branch delivers its result. Even disregarding the specific timings, the DSL's semantics never make `EMIT release`'s execution depend on the branches' completion in this program — that dependency would have to be introduced explicitly with a `JOIN` before `EMIT release`, which the program does not have.

## Assumptions / points not determined by the spec

- The spec does not define or use real-world time units ("1 hour", "5 minutes"); it only defines statement ordering and completion conditions (e.g., "done when the actor delivers a result"). I have treated the stated durations only as narrative color confirming that the branches are still in progress when `EMIT release` fires — the ordering conclusion (no wait without `JOIN`) already follows from the DSL's structural rules alone, independent of any timing.
- The spec does not specify what `EMIT release` "producing an output" entails in terms of whether it can reference the artifacts produced by `docs`/`changelog` (the DSL says `EMIT` "does not prescribe how it is created, stored, or transmitted"). Whether it is *meaningful* for release to be emitted before docs exist is outside the DSL's scope; the DSL only guarantees ordering/synchronization, and here it guarantees none between the fork's branches and `EMIT release`.
