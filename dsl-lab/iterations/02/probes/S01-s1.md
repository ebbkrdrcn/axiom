```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

The specification leaves several things undetermined for this requirement; the following choices were made to produce a valid, executable program:

1. **Answer names for the merge decision.** The requirement only describes the two possible decisions ("to merge" / "not to merge") but does not give the literal answer identifiers. I named them `approved` and `declined` (matching the DSL's own worked examples). Any other pair of distinct identifiers would be equally valid as long as the two `WHEN` conditions match them.

2. **No `FALLBACK` for the `HITL`.** The requirement does not say what should happen if the human's response is insufficient or unavailable, so no `→ FALLBACK` is attached to the `HITL`. Per the spec, that means an insufficient/unavailable response simply ends execution (as with `STOP`), which is the specification's default behavior and was not overridden.

3. **The outcome of `VERIFY implementation` is not branched on.** The requirement says only "verify it," with no instruction to do anything different depending on whether it is accepted or rejected. `VERIFY` does not branch by itself (per its section), so the program establishes `implementation.accepted`/`implementation.rejected` and proceeds unconditionally to the merge decision. No `WHEN implementation....` was added because the requirement gives no behavior to attach to it.

4. **No `REQUIRE`, `LOOP`, or `FORK`.** The requirement describes a single straight-line process (delegate → verify → decide → transition) with no mention of repetition, concurrency, or a precondition that must be available first, so none of these constructs were used.

5. **Actor/mechanism for `DELEGATE implementation`.** The DSL states `DELEGATE` defines responsibility, not execution mechanics, so no actor or delivery mechanism is specified — this is left fully abstract, as the spec requires.

6. **`AUTO` applies only to the merge `HITL`.** The requirement's phrase "the agent may make the merge decision itself when it is clearly determined ... otherwise a human must be asked" maps directly to the `AUTO HITL` semantics (agent decides only when certain; otherwise the human is asked), so `AUTO` was placed on that single `HITL:merge` statement, exactly as the DSL requires (`AUTO` cannot apply to a flow or to any other statement).

7. **Both `TRANSITION` statements are unconditional alternatives.** Since the answer list `[approved, declined]` is exhaustive and mutually exclusive (only one outcome can be the "latest" value for `merge`), the two `WHEN` blocks are written as independent, sequential checks (per the spec's "no else" rule), which correctly yields exactly one of the two transitions running for any given resolved decision.
