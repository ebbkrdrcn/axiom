```
EMIT test-report
```

- V2 (`BREAK` outside `LOOP`): no `BREAK` present.
- V3 (`BREAK` across a `FORK` branch): no `BREAK`, no `FORK`.
- V4 (`→` placement / `FALLBACK` placement): the only `→` item is directly under a `WHEN`; valid.
- V5 (`AUTO` misuse): no `AUTO`.

- V7 (name clashes / answer-list problems): no `HITL` at all, so no clash and no answer-list issue.
- V8 (fallback must end in `STOP`/`BREAK`): no fallback present.
- V9 (`JOIN`/`FORK` mismatch): no `JOIN` or `FORK`.
- V10 (`WHEN` on an unjoined `FORK` branch outcome): no `FORK`.

No rule is broken. **The program is valid** and may be executed.

## Step-by-step execution

Statements run one at a time, in the order written (rule 1). A `WHEN` is checked exactly once, at the moment execution reaches it, using whatever outcome is (or is not) established for its subject at that instant (rule 2, and the outcomes rule "Not yet established. A `WHEN` on a subject with no outcome yet is false."). Importantly, `WHEN` "is never re-checked" once execution has passed it (see the WHEN section: "The outcome is established later → Nothing happens. A `WHEN` is not a standing trigger and is never re-checked.").

Walking through the program in the order it is written:

1. `TRANSITION "Testing"` — sets the current process state to `"Testing"`. Effect: `state = "Testing"`.
2. `WHEN tests.accepted` — execution reaches this statement **before** any `VERIFY tests` (or `HITL:tests`) has run anywhere earlier in the program. No `VERIFY tests` precedes it, so the subject `tests` has no outcome established yet. Per the rule "Before anything establishes it, every `WHEN` on it is false," the condition is false. Effect: `false: skip`. The nested `→ TRANSITION "Review"` is not run.
3. `DELEGATE tests` — an actor is assigned the work `tests`; the statement completes when the actor delivers a result. Effect: `done`.
4. `VERIFY tests` — evaluates the delivered result. Per the stated event, this establishes `tests.accepted`. Effect: `outcome tests.accepted`.
5. `EMIT test-report` — produces the output `test-report`. Effect: `done`.
6. End of program — the last top-level statement is done, so execution ends normally (rule 10). Effect: `end`.

## Trace

```trace
1. TRANSITION "Testing" -> state = "Testing"
2. WHEN tests.accepted -> false: skip
3. DELEGATE tests -> done
4. VERIFY tests -> outcome tests.accepted
5. EMIT test-report -> done
6. (end of program) -> end
```

## Final state

`Testing`

The state was set once, by the first `TRANSITION "Testing"`, and nothing later in the execution changes it, since the only other `TRANSITION` (`"Review"`) is never run (see below). "Each `TRANSITION` replaces it; the most recently executed one wins" — and here only one `TRANSITION` is ever executed.

## Is `TRANSITION "Review"` ever executed?

**No.**

`TRANSITION "Review"` lives inside the flow of `WHEN tests.accepted`, which appears *before* `DELEGATE tests` / `VERIFY tests` in program order. Execution is strictly sequential (rule 1: "Statements run one at a time, in the order written"), so when it reaches `WHEN tests.accepted` at step 2, `VERIFY tests` has not run yet anywhere in the program — the outcome `tests.accepted` does not exist yet. By the outcomes rule ("Before anything establishes it, every `WHEN` on it is false"), the condition is false at that moment, so the flow (`→ TRANSITION "Review"`) is skipped, and execution continues after the `WHEN` (with `DELEGATE tests`).

A `WHEN` is "checked once, when reached" (rule 2) and is explicitly "not a standing trigger": "The outcome is established later → Nothing happens. ... [it] is never re-checked" (WHEN section). So even though `VERIFY tests` establishes `tests.accepted` two statements later (step 4), that happens *after* the one and only check of this `WHEN` has already resolved to false. The specification gives no mechanism for a `WHEN` to be retroactively re-evaluated or for later statements to reach back and re-trigger an earlier, already-skipped `WHEN`.

Consequently, `TRANSITION "Review"` is never executed in this program, regardless of the fact that `tests.accepted` does end up being established — the ordering of statements in the program (the `WHEN` textually precedes the `VERIFY` that would satisfy it) makes the condition permanently moot for that occurrence of the `WHEN`. The process therefore ends in the `"Testing"` state, not `"Review"`.

## Notes on assumptions

The specification fully determines this trace; no assumption beyond the text was required. For completeness:

- The task states only that "`VERIFY tests` establishes `accepted`"; the specification does not describe how `DELEGATE tests` obtains its result or how `VERIFY tests` arrives at `accepted` — per the **Semantic Principles** section, `DELEGATE` and `VERIFY` define responsibility/evaluation, not execution mechanics, so this is intentionally left unspecified and is treated as an external fact supplied by the event description.
- `EMIT test-report`'s effect is listed as `done` (not an `outcome …` line) because the Quick reference and the Outcomes section state that only `VERIFY` and `HITL:<name>[…]` produce outcomes ("No other statement produces outcomes"); `EMIT` merely produces an output.
