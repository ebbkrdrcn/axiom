# go_harness DSL Solution

## DSL Program

```
AUTO HITL:notes[short, detailed]("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:approval[approved, rejected]("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Notes answer outcomes**: I assumed the two possible answers to the first question are `short` and `detailed`, and these become the outcome names when the human responds.

2. **Approval answer outcomes**: I assumed the two possible answers to the approval question are `approved` and `rejected`, matching the conditional logic in the requirement ("if approved" and "if rejected").

3. **Artifact name**: I assumed the artifact to emit when approved is named `release`, derived from "emit release" in the requirement.

4. **AUTO behavior**: I used `AUTO` on the first HITL because the requirement states "the agent may answer this question itself when the answer is clearly determined", which matches the AUTO semantics. I did not use AUTO on the approval question because the requirement explicitly states "This approval must always be given by a human, never by the agent".

5. **No errors or fallbacks**: The requirement does not mention error handling or fallback flows, so I assumed neither FALLBACK nor error cases need to be represented.

6. **Execution flow**: I assumed sequential execution where both WHEN statements after each HITL are evaluated independently (they are consecutive and both true paths lead to their respective delegate/emit/transition statements).
