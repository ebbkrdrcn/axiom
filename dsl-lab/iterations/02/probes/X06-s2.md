# Analysis of the go_harness Program

```
AUTO HITL:wording[short, detailed]("Short or detailed release notes?")
WHEN wording.short
  → DELEGATE short-notes
WHEN wording.detailed
  → DELEGATE detailed-notes
HITL:release[approved, rejected]("Approve the release?")
WHEN release.approved
  → EMIT release
```

## 1. Which of the two decisions may the agent make by itself, and under what condition?

Only the **`wording`** decision (`AUTO HITL:wording[short, detailed](...)`) may be answered by the agent itself. The **`release`** decision (`HITL:release[approved, rejected](...)`) has no `AUTO` marker, and per the "Who decides a `HITL`" table, when there is no `AUTO` the human decides and "the agent MUST NOT answer." So `release` can never be answered by the agent, under any condition.

For `wording`, the agent may answer it itself only when the decision is **certain and within the agent's authority** — i.e. the agent "can determine one single answer from the list, based on the available information and the applicable criteria," with no uncertainty of the kinds the spec lists (missing/contradictory information, missing/ambiguous/contradictory criteria, more than one answer reasonably compatible with the evidence, an unresolved interpretation, or the decision being outside the agent's authority). If any such uncertainty exists, the agent must not guess — the human is asked instead, exactly as for a plain `HITL`.

## 2. All automated checks are green and the agent is highly confident the release should be approved. May it answer "Approve the release?" itself?

No. `HITL:release[approved, rejected]` is not marked `AUTO`. Per the table "Who decides a `HITL`" (row: `AUTO`? no → "the human; the agent MUST NOT answer"), the agent is categorically barred from answering it, regardless of how confident it is. The spec's point that "a confidence score alone, however high, does not establish certainty" is stated in the context of `AUTO` resolution, but here it doesn't even apply, because `release` is not an `AUTO` `HITL` at all — the rule against agent answers is absolute and confidence is irrelevant. The agent must wait at the `HITL:release` statement for an actual human response given after execution reaches it; the automated-checks result and the agent's own confidence are not a "response" to that `HITL` (see "What counts as a response").

## 3. If the wording decision is not clearly determined, what happens?

"Not clearly determined" is uncertainty as defined under **AUTO**. Per the `AUTO` table, "Anything else" (i.e., not certain-and-within-authority) means: "The human is asked, exactly as for a `HITL` without `AUTO`. `FALLBACK` applies to the human's response as usual."

So execution stops trying to resolve `wording` automatically and instead waits at `HITL:wording` for a human answer, just as it would for a non-`AUTO` `HITL`:

- If the human gives a **usable** response (clearly selects `short` or `detailed`), the outcome `wording.short` or `wording.detailed` is established, and execution continues with the statement after the `HITL:wording` construct (the following `WHEN`s).
- If the response is **insufficient or unavailable**: this particular `HITL:wording` statement in the given program has **no `→ FALLBACK`** attached. Per the `HITL` table, "Insufficient or unavailable, and there is no `FALLBACK` → Execution ends, as with `STOP`." No outcome is established, and neither `WHEN wording.short` nor `WHEN wording.detailed` will ever run (both would evaluate false forever, but execution ends before reaching them, per rule: "before anything establishes it, every `WHEN` on it is false").

(Assumption: the task's phrase "not clearly determined" is used as a synonym for the spec's "uncertainty" concept for `AUTO`, since the DSL does not define a separate condition by that name — "Uncertainty is not a DSL condition, state, variable, or keyword; the runtime determines it.")

## 4. If the human answers the release question with "rejected", what happens?

"Rejected" clearly selects one of the listed answers (`approved`, `rejected`), so it is a **usable** response. Per the `HITL` rules:

1. The outcome `release.rejected` is established (the latest/only outcome for subject `release`).
2. Execution continues with the statement after the `HITL:release` construct, i.e. `WHEN release.approved`.
3. `WHEN release.approved` is checked once: the latest outcome of `release` is `rejected`, not `approved`, so the condition is **false**. The flow (`→ EMIT release`) is skipped — "This is not an error. Execution does not wait."
4. There is no `WHEN release.rejected` anywhere in this program, so nothing else reacts to the `rejected` outcome.
5. `WHEN release.approved` was the last top-level statement in the program, so once it is skipped, execution ends normally (rule 10 of "Execution in ten rules": "When the last top-level statement is done, execution ends normally").

Net effect: `release.rejected` is recorded, `EMIT release` does **not** run, and the program ends normally with no state transition and no fallback (since `HITL:release` has no `FALLBACK`, and none is needed here anyway because the response was usable).

## Notes on assumptions

- The specification does not define "not clearly determined" as a formal term; I treated it as equivalent to the spec's "uncertainty" concept governing `AUTO` resolution, since that is the only related concept the DSL defines.
- Neither `HITL` statement in this program carries a `→ FALLBACK`, which is visible directly from the program text as given in the task; the "no FALLBACK" branches of the relevant tables were applied accordingly.
