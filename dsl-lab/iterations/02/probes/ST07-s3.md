# go_harness program

```text
REQUIRE repository
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
LOOP:delivery
  FORK
    → DELEGATE implementation
    → DELEGATE documentation
  JOIN
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
AUTO HITL:release[now, later]("Release now or later?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN release.now
  → EMIT release
  → TRANSITION "Released"
WHEN release.later
  → TRANSITION "Scheduled"
```

## Assumptions

1. **Identifier names.** The requirement does not give explicit DSL identifiers for the repository, the implementation work, the documentation work, the correction work, the release decision, or the loop label. I chose `repository`, `implementation`, `documentation`, `correction`, `release`, and the loop label `delivery`, all valid identifiers under the spec's naming rules. No behavior depends on the particular spelling chosen.

2. **HITL name and answer list.** The question "Release now or later?" was modeled as `HITL:release[now, later](...)`, since the requirement names exactly two possible answers ("now" and "later") and no other name for the decision. `WHEN release.now` / `WHEN release.later` follow directly from this answer list (rule V6).

3. **Documentation is not verified.** The requirement says "delegate the implementation and ... the documentation ... then verify the implementation" — it only mentions verifying the implementation. I therefore only emitted `VERIFY implementation`, leaving the documentation delegation unverified, since `VERIFY` establishes no outcome unless the spec calls for it and the DSL must not invent one.

4. **"At the same time" / "wait for both" → `FORK`/`JOIN`.** `FORK` is the DSL's only concurrency construct and `JOIN` is the only construct that waits for all branches of a `FORK`, so the two simultaneous delegations were modeled as two `FORK` branches followed by `JOIN`, per rule 4 and the JOIN section of the spec.

5. **`VERIFY implementation` runs after `JOIN`, not inside a branch.** Because a `WHEN` must not test an outcome that a still-running `FORK` branch may establish before a `JOIN` (rule V10), and the requirement itself says to delegate concurrently and only "then verify," `VERIFY implementation` is placed as a sequential statement after `JOIN`, not inside either branch.

6. **"The agent may itself decide ... when that is clearly determined; otherwise ask a human" → `AUTO`.** This phrasing matches the spec's definition of `AUTO` precisely (resolve automatically only when the decision is certain and within the agent's authority; otherwise ask the human), so the release `HITL` was marked `AUTO`.

7. **"If no usable answer is obtained" → the `FALLBACK`.** I read this as covering both classifications the spec defines as not usable — "insufficient" (an unclear/off-topic/unlisted response) and "unavailable" (no response before the runtime stops waiting) — since in both cases the spec says no outcome is established and the fallback flow (or, absent one, an end of execution) runs. I supplied a `FALLBACK` that transitions to `"Waiting"` and stops, per "move to state 'Waiting' and stop."

8. **Loop repetition needs no explicit statement.** For the rejected case, "delegate a correction and repeat" required no extra "repeat" instruction: per rule 5, a loop body automatically restarts from its first statement once its last statement finishes, so `DELEGATE correction` being the last statement of that `WHEN` branch (and of the iteration, once `WHEN implementation.accepted` was checked false) is sufficient to produce the repeat.

9. **Order of the two `WHEN`s in the loop.** `WHEN implementation.accepted` is written before `WHEN implementation.rejected`, matching the order in the requirement. Since `VERIFY implementation` establishes exactly one of `accepted`/`rejected` (never both), and `BREAK` short-circuits the remaining statements of the iteration when accepted is true, the relative order of these two `WHEN` blocks does not change the program's behavior.

10. **"Move to state X and stop" → `TRANSITION "X"` then `STOP`.** Both places in the requirement that say "move to state X and stop" (the unavailable-repository case and the no-usable-answer case) were translated as a `TRANSITION` immediately followed by `STOP`, matching the DSL's separate, single-purpose statements for state change and termination, and matching the equivalence shown in the spec's `FALLBACK` section.

11. **`REQUIRE repository` and the `AUTO HITL:release` both use `FALLBACK`, and each fallback flow ends in `STOP`** (rule V8), satisfying the requirement that both of these termination paths end execution entirely rather than merely leaving a loop.
