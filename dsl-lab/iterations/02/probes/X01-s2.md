```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge[approved, declined]("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

The specification does not fully determine every detail of the requirement text, so the following choices were made:

1. **Relationship between the implementation verification and the merge decision.** The requirement says "Delegate the implementation and verify it. Then a merge decision is needed," without stating that the merge decision depends on whether the implementation was `accepted` or `rejected`. I assumed `VERIFY implementation` simply establishes the `implementation.accepted`/`implementation.rejected` outcome (as required by the DSL — `VERIFY` always establishes exactly one such outcome) but that this outcome is **not** used to gate progress to the merge decision, since the requirement never says what should happen differently for an accepted vs. rejected implementation before the merge step. Execution therefore proceeds unconditionally from `VERIFY implementation` to the `HITL` merge decision.

2. **HITL name and answer labels.** The requirement does not give explicit outcome labels for the merge decision ("the decision to merge" / "not"). I named the decision `merge` and used the answers `approved` and `declined`, mirroring the wording the specification itself uses for its own "Merge this change?" example (`HITL:merge[approved, declined](...)` / `AUTO HITL:merge[approved, declined](...)`), since the DSL requires an explicit, finite, non-empty answer list (V7) and the requirement itself does not supply one.

3. **Mapping "if not" to `declined`.** The requirement's "If the decision is to merge... If not..." was interpreted as exactly the two listed answers `approved` and `declined` — i.e., "not merge" corresponds to the human/agent choosing `declined`. This is an assumption because the requirement's natural-language "if not" does not itself name a DSL outcome; it must correspond to one of the declared answers per the answer list, and `declined` is the natural complement of `approved`.

4. **"No usable answer" mapped to the spec's insufficient/unavailable response handling.** The requirement's "If the human gives no usable answer" was mapped to the specification's own `FALLBACK` mechanism, which runs precisely when a `HITL` response is *insufficient* or *unavailable* (no outcome is established in that case). I assumed this phrase covers both of the specification's categories (ambiguous/off-topic/no-selection responses, and no response at all after the runtime stops waiting), since the requirement does not distinguish between them.

5. **AUTO semantics taken as-is.** "The agent may make the merge decision itself when it is clearly determined by the available information and criteria; otherwise a human must be asked" was translated directly to `AUTO HITL:merge[...]`, relying on the specification's own definition of `AUTO` (automatic resolution only when the agent can determine one single answer with certainty and within its authority; otherwise the human is asked). No additional criteria beyond what `AUTO` already specifies were assumed.

6. **No `REQUIRE`, `LOOP`, or `FORK`.** The requirement mentions no prerequisite resource, no repetition, and no concurrent work, so none of these constructs were introduced. `DELEGATE` and `VERIFY` run once, sequentially, as literally described ("Delegate the implementation and verify it").

7. **Single identifier `implementation`.** Both `DELEGATE implementation` and `VERIFY implementation` use the same identifier `implementation`, following the pattern shown in the specification's own `DELEGATE`/`VERIFY` example, since the requirement refers to "the implementation" as one and the same item throughout.

8. **`FALLBACK` ends with `TRANSITION "Blocked"` then `STOP`.** This follows directly from the requirement's own wording ("transition to state 'Blocked' and stop") and satisfies rule V8, which requires a fallback flow's last item to be `STOP` or `BREAK`.

9. **No explicit `EMIT`.** The requirement does not mention producing any artifact/output, so no `EMIT` statement was added.
