# Execution of the `tdd` program

## Program (as given)

```
LOOP:tdd
  DELEGATE implementation
  DELEGATE tests
  VERIFY tests
  WHEN tests.accepted
    → TRANSITION "Review"
    → BREAK
  WHEN tests.rejected
    → TRANSITION "Debugging"
    → DELEGATE diagnosis
EMIT source-code
```

## Validation

- V1 (indentation): the loop body is a single consistently-indented block; the two `WHEN` flows are consistently indented under their `WHEN`. Valid.
- V2/V3 (`BREAK`): the only `BREAK` is inside `LOOP:tdd`'s body, not inside any `FORK` branch. Valid.
- V4 (`→` placement): all `→` items are directly under `WHEN`. Valid.
- V6 (declared outcomes): `WHEN tests.accepted` and `WHEN tests.rejected` both refer to `tests`, and the program contains `VERIFY tests`, whose only possible outcomes are `accepted`/`rejected`. Both are declared. Valid.
- V7 (name reuse): only one subject (`tests`), used only by `VERIFY`. No `HITL` names. Valid.
- V8 (fallback ending): no `FALLBACK` present, so vacuously valid.
- V9 (`JOIN`/`FORK`): no `FORK`/`JOIN` in the program. Vacuously valid.
- V10 (`FORK`-branch visibility): no `FORK`. Vacuously valid.

The program is well-formed; no rule is broken. Execution may proceed.

## Assumption made

The specification's own worked example (`LOOP:delivery` in "Complete example") does not emit a trace line for entering a loop the first time — the first iteration's trace starts directly with the loop body's first statement, and only a *repeat* of the loop is logged, as `LOOP:<name> -> loop again`. The specification does not state this rule explicitly anywhere else (it is only visible from that example's trace), so I follow the same convention here: the first entry into `LOOP:tdd` produces no trace line of its own; only the second iteration logs `LOOP:tdd -> loop again`.

## Events (as given)

- Iteration 1: `VERIFY tests` establishes `tests.rejected`.
- Iteration 2: `VERIFY tests` establishes `tests.accepted`.

## Step-by-step trace

```trace
1. DELEGATE implementation -> done
2. DELEGATE tests -> done
3. VERIFY tests -> outcome tests.rejected
4. WHEN tests.accepted -> false: skip
5. WHEN tests.rejected -> true: run flow
6. TRANSITION "Debugging" -> state = "Debugging"
7. DELEGATE diagnosis -> done
8. LOOP:tdd -> loop again
9. DELEGATE implementation -> done
10. DELEGATE tests -> done
11. VERIFY tests -> outcome tests.accepted
12. WHEN tests.accepted -> true: run flow
13. TRANSITION "Review" -> state = "Review"
14. BREAK -> break
15. EMIT source-code -> done
16. (end of program) -> end
```

## Notes on the trace

- Step 3: `VERIFY tests` establishes exactly one outcome, `tests.rejected` (rule: VERIFY produces only `accepted`/`rejected`).
- Step 4: at this point `tests`'s latest outcome is `rejected`, so `WHEN tests.accepted` is false; execution continues to the next `WHEN` (consecutive `WHEN`s are independent, rule 3 of "Execution in ten rules").
- Step 5–7: `WHEN tests.rejected` is true, so its flow runs sequentially: `TRANSITION "Debugging"` then `DELEGATE diagnosis`.
- Step 8: the loop body's last statement (the second `WHEN`) is done, so the body restarts at its first statement (`DELEGATE implementation`); this is logged as `loop again`, per the convention noted above.
- Step 11: `VERIFY tests` now establishes `tests.accepted`, replacing the previous `rejected` value for the same subject (outcomes hold only the latest value).
- Step 12–14: `WHEN tests.accepted` is now true, so its flow runs: `TRANSITION "Review"` sets the current state to `"Review"`, then `BREAK` leaves the innermost loop (`LOOP:tdd`) immediately.
- Because `BREAK` leaves the loop immediately, the remaining statement of that iteration — the second `WHEN tests.rejected` — is **not executed at all** (not even evaluated/skipped): "The remaining statements of the current iteration are not executed, including later `WHEN`s."
- Step 15: execution continues with the first statement after the loop, `EMIT source-code`.
- Step 16: the last top-level statement is done, so execution ends normally.

## Final state

`Review`

(The last executed `TRANSITION` was `TRANSITION "Review"` in step 13; nothing after it changes the state, since `BREAK`, `EMIT`, and end-of-program perform no state change.)
