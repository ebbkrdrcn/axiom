# go_harness DSL Program

```text
REQUIRE repository
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
LOOP:delivery
  FORK
    → DELEGATE implementation
    → DELEGATE documentation
  JOIN
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
AUTO HITL:release[now, later]("Release now or later?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN release.now
  → EMIT release
      TRANSITION "Released"
WHEN release.later
  → TRANSITION "Scheduled"
```

## Assumptions Made

1. **Concurrent delegation and waiting.** The requirement "delegate the implementation and, at the same time, delegate the documentation; wait for both" is interpreted as using `FORK` to start both delegations concurrently, followed by `JOIN` to wait for both to complete.

2. **Answer list for release decision.** The HITL question "Release now or later?" is mapped to the answer list `[now, later]` based on the subsequent conditional flows "If now:" and "If later:".

3. **Loop repetition and exit.** The phrase "If the implementation is accepted, leave the repetition; otherwise delegate a correction and repeat" is interpreted as:
   - `BREAK` exits the loop when implementation is accepted
   - Delegating correction and allowing the loop to naturally continue (implicitly repeating) when implementation is rejected

4. **Outcomes from verification.** `VERIFY implementation` establishes either `implementation.accepted` or `implementation.rejected` (the only valid outcomes from VERIFY per specification rule V6).

5. **Outcomes from HITL.** `HITL:release[now, later]` establishes either `release.now` or `release.later` as outcomes.

6. **State transitions.** The named states ("Blocked", "Waiting", "Released", "Scheduled") are set via `TRANSITION` statements and represent the process state at specific points.

7. **AUTO HITL interpretation.** "The agent may itself decide when that is clearly determined; otherwise ask a human" is interpreted as `AUTO HITL`, where the agent answers only if the decision is certain, otherwise the human is prompted.

8. **Fallback handling for insufficient/unavailable answers.** If no usable answer is obtained to the release decision, the `FALLBACK` runs, transitioning to "Waiting" and stopping execution.

9. **No additional requirements specified.** The requirement does not mention other prerequisites beyond the repository, so only `REQUIRE repository` is used; no other REQUIRE statements are added.

10. **Program termination.** The program ends normally (rule 10 of "Execution in ten rules") after the final WHEN statements are evaluated, which represents the end of the process workflow.
