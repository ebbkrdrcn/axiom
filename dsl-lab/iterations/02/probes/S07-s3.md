# Analysis of the `data-migration` program

```
DELEGATE data-migration
WAIT
VERIFY data-migration
WHEN data-migration.accepted
  → TRANSITION "Migrated"
```

## 1. What does `WAIT` wait for here?

The specification does not determine this, so this must be stated explicitly rather than assumed away.

What the spec does say about `WAIT`:

> Suspends execution until an external event or response is available. ... The DSL does not name the event. The surrounding process and the runtime determine it. ... There is no timeout.

So `WAIT` by itself never names the event it is suspended on — that is left to "the surrounding process and the runtime." Nothing elsewhere in the spec ties a `WAIT` to the statement before or after it, or to a particular subject/outcome; `WAIT` "does not make a decision and does not imply success or failure," and it establishes no outcome.

There is also a structural point worth flagging: `DELEGATE <work>` is already, by definition, "done when the actor has delivered its result" — i.e. `DELEGATE data-migration` on its own already blocks until the migration actor returns a result. That means the `WAIT` immediately after it is waiting for something *other than* the delegated result being delivered (that part is already covered by `DELEGATE` finishing) — but the spec gives no vocabulary for what that "something else" is.

**Conclusion / assumption stated explicitly:** The specification does not determine what event `WAIT` is suspended on in this program. It is an external event whose identity is defined only by "the surrounding process and the runtime," not by the DSL text. Any more specific reading (e.g. "waiting for the migration to finish running," "waiting for a completion webhook," "waiting for downstream systems to settle") would be an assumption not licensed by the spec, so no such reading is adopted here.

## 2. What executes immediately after `WAIT` ends?

This one *is* fully determined by the spec:

> After the event, the next statement runs.

Execution is strictly sequential ("Statements run one at a time, in the order written. Each statement finishes before the next starts."), and the next statement written after `WAIT` is:

```
VERIFY data-migration
```

So `VERIFY data-migration` runs immediately once `WAIT` ends.

## 3. Does reaching `VERIFY data-migration` imply that the migration succeeded?

No. The spec is explicit on two points that both support this:

- Under `DELEGATE`: "A delivered result is not necessarily correct, complete, or accepted. Use `VERIFY` to evaluate it."
- Under `VERIFY`: "The completion of delegated work is not a successful verification." and "`VERIFY` does not branch. Execution continues with the next statement whatever the outcome; only a `WHEN` makes the flow depend on it."

Reaching `VERIFY data-migration` only means that the prior statements (`DELEGATE data-migration`, then `WAIT`) have finished — i.e. the actor delivered *some* result and the awaited external event occurred. It says nothing about whether that result was good. `VERIFY data-migration` is the step that *establishes* whether the outcome is `data-migration.accepted` or `data-migration.rejected`; until it runs, success/failure is undetermined, and merely arriving at the `VERIFY` statement is not itself evidence of success — it is evaluated only when `VERIFY` runs (and the spec doesn't say which way it comes out; only the actual execution/event data would establish that, which the agent "MUST NOT invent").

## 4. What happens if the awaited event never occurs?

Per the `WAIT` rules:

> There is no timeout. If the event never comes, execution stays at the `WAIT`.

There is no `FALLBACK` attached here in any case — and the spec only allows `→ FALLBACK` directly under a `HITL` or a `REQUIRE` (rule V4); `WAIT` cannot have a `FALLBACK` at all. So there is no alternate path, no timeout-triggered `STOP`, and no automatic ending of execution.

**Conclusion:** If the awaited event never occurs, execution simply remains suspended at the `WAIT` statement indefinitely. `VERIFY data-migration` and everything after it (including the `WHEN data-migration.accepted` check and the `TRANSITION "Migrated"`) never runs, and the program never reaches normal end. This is not treated as an error condition by the DSL — the spec's `WAIT` section defines this as the expected, unremarkable behavior of an event that hasn't happened yet.
