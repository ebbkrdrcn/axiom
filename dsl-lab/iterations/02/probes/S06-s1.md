# Execution of the `build` loop — first two iterations

## Program

```text
LOOP:build
  DELEGATE build
  VERIFY build
  WHEN build.accepted
    → BREAK
EMIT build-report
```

Given fact: in every iteration, `VERIFY build` establishes `build.rejected`.

## Validation

The program is well-formed: `LOOP:build` opens a body of three statements (`DELEGATE`, `VERIFY`, `WHEN`); `WHEN` has one `→` child, `BREAK`, which is inside the `LOOP` it would leave, so V3 is not violated; `BREAK` is inside a `LOOP`, so V2 is not violated; the `WHEN` tests `build.accepted`, and the program contains `VERIFY build`, whose possible outcomes are `accepted`/`rejected` (Outcomes table), so `accepted` is a declared outcome and V6 is not violated. No other rule applies. The program is valid and may be executed.

## Step-by-step behavior

**Iteration 1**

1. `DELEGATE build` — the actor performs the build; the statement is done when the result is delivered (DELEGATE section). Effect: `done`.
2. `VERIFY build` — evaluates the result and establishes exactly one outcome. Per the given fact, it establishes `build.rejected` (VERIFY section: "It establishes exactly one outcome: `<result>.accepted` or `<result>.rejected`"). Effect: `outcome build.rejected`.
3. `WHEN build.accepted` — checked once, now, because execution has reached it (rule 2 of "Execution in ten rules"). The condition is true only if the *latest* outcome of `build` is exactly `accepted` (WHEN section). The latest outcome is `rejected`, so the condition is false. Effect: `false: skip`. The flow (`→ BREAK`) does **not** run.
4. End of loop body — the last statement of the body (the `WHEN`, which was skipped but still "done" as a statement) is done, so per the `LOOP` table ("The last statement of the body is done → The next iteration starts at the first statement of the body") and rule 5 ("At the end of a loop body, the body starts again from its first statement"), the loop starts over. Effect: `loop again`.

**Iteration 2**

5. `DELEGATE build` — done again. Effect: `done`.
6. `VERIFY build` — per the given fact, again establishes `build.rejected`, replacing the previous (identical) latest value for the subject `build` (Outcomes section: "Each subject holds its most recently established outcome. A later `VERIFY x` … replaces it"). Effect: `outcome build.rejected`.
7. `WHEN build.accepted` — re-checked independently for this pass (a `WHEN` is checked once *per time execution reaches it*, and the loop causes execution to reach it again); the latest outcome of `build` is still `rejected`, so it is false again. Effect: `false: skip`.
8. End of loop body — the body starts again. Effect: `loop again`.

Formal trace (per the spec's trace notation):

```trace
1. DELEGATE build -> done
2. VERIFY build -> outcome build.rejected
3. WHEN build.accepted -> false: skip
4. LOOP:build -> loop again
5. DELEGATE build -> done
6. VERIFY build -> outcome build.rejected
7. WHEN build.accepted -> false: skip
8. LOOP:build -> loop again
```

## Is / when is `EMIT build-report` executed?

`EMIT build-report` is **not** executed during the first two iterations, and — on the information given — it is never executed at all.

Reasoning from the spec:

- `EMIT build-report` sits *after* `LOOP:build` at the loop's own indentation level, i.e. it is the "first statement after the loop" (LOOP table). The only ways to reach it are: the loop ends via `BREAK` (LOOP table: "Execution continues with the first statement after the loop, at the indentation of `LOOP`"), or the whole execution is ended by `STOP` (which would end everything, so `EMIT` would not run either), or, since `LOOP` has no defined "N iterations" semantics ("`LOOP` does not imply any particular number of iterations"), simply never, if the loop keeps repeating forever.
- The only path to `BREAK` here is `WHEN build.accepted` being true. That condition depends solely on the latest outcome of `build`, which only `VERIFY build` sets (Outcomes table: no other statement produces the `build` outcome).
- Since the given fact states that `VERIFY build` establishes `build.rejected` in *every* iteration (not just the first two), the latest outcome of `build` is `rejected` at every check of the `WHEN`, so the `WHEN` is false every time, `BREAK` is never reached, and the loop body restarts indefinitely (rule 5; LOOP table row "The last statement of the body is done → next iteration starts").
- `STOP` never appears in this program, so execution never ends "as with `STOP`" either; the loop simply continues forever on the given events.

This matches the spec's own worked example of this exact program (Control → LOOP section): *"While `VERIFY build` establishes `build.rejected`, the `WHEN` is false and the loop repeats indefinitely. `EMIT build-report` runs only after a `BREAK`."*

**Conclusion:** In iterations 1 and 2 (and, per the given fact, in every subsequent iteration), `DELEGATE build` and `VERIFY build` run, `VERIFY build` establishes `build.rejected`, `WHEN build.accepted` evaluates false and is skipped, and the loop restarts. `EMIT build-report` is never executed under these events — it would only execute once some iteration's `VERIFY build` established `build.accepted` instead, causing `BREAK` to fire and hand control to the statement after the loop. No assumption beyond the specification and the stated fact was needed to reach this conclusion.
