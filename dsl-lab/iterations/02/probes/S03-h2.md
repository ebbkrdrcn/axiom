# go_harness DSL Program

## DSL Code

```text
FORK
  → DELEGATE security-review
      VERIFY security-review
  → DELEGATE performance-review
      VERIFY performance-review
JOIN
TRANSITION "Release"
```

## Assumptions

1. **Work item names**: The security and performance review work is named `security-review` and `performance-review` respectively, following the DSL identifier rules (letters, digits, `-`, `_`, starting with a letter).

2. **Verification names match delegation names**: Each `VERIFY` statement uses the same identifier as its corresponding `DELEGATE` statement. The specification requires that verified results must match names produced by `VERIFY` in the program (rule V6).

3. **No conditional branching on verification results**: The requirement specifies "continue only after both flows have finished" without mentioning different paths based on acceptance or rejection. Therefore, no `WHEN` conditions are included. Both branches complete when their `VERIFY` steps finish, regardless of outcome (accepted or rejected).

4. **Direct state transition after JOIN**: After the `JOIN` completes, execution immediately transitions to "Release" state with no intermediate conditions or operations.

5. **No additional operations**: The requirement does not mention emitting artifacts, waiting for external events, requiring resources, or asking humans, so these are not included.

6. **Program ends normally**: After the `TRANSITION "Release"` statement, execution ends normally per rule 10 of "Execution in ten rules"—no explicit `STOP` is needed.
