## 2. Key interpretive point — is the `AUTO` decision "certain"?

The `AUTO` section states that automatic resolution is permitted only when the agent can determine the single answer **and** has the authority to do so, and it explicitly lists as a case of uncertainty: *"the agent does not have the authority required to make the decision."*

Here:
- The eligibility question itself is clear (`VERIFY refund-assessment` → `accepted`, and the criteria clearly show eligibility).
- But the applicable criterion for *this* decision is not eligibility alone — company policy states refunds above 1,000 EUR may only be **approved by a finance manager**. The refund is 4,000 EUR, and the agent is not a finance manager.

Per the spec, a confidence score or a clear underlying fact does not establish certainty when authority is missing — authority is a separate, explicitly named condition for uncertainty under `AUTO`. So even though the agent could confidently guess "approve," it lacks the authority required to make that determination itself. This falls under "Anything else" in the `AUTO` decision table: **the human must be asked**, exactly as for a `HITL` without `AUTO`.

(This is a direct application of the spec's own listed condition, not an added assumption. The one thing the spec leaves to context is *what* counts as "the agent's authority" for a given decision — here that is settled by the given company policy, which is context supplied by the task.)

The finance manager later answers "approve," which clearly selects one of the two listed answers (`approve`, `deny`) — a **usable** response. It establishes `refund.approve` and execution continues after the `HITL` construct.

## 3. Execution trace

```trace
1. DELEGATE refund-assessment -> done
2. VERIFY refund-assessment -> outcome refund-assessment.accepted
3. AUTO HITL:refund[approve, deny]("Approve the refund of 4,000 EUR?") -> waiting
4. AUTO HITL:refund[approve, deny]("Approve the refund of 4,000 EUR?") -> outcome refund.approve
5. WHEN refund.approve -> true: run flow
6. DELEGATE payout -> done
7. TRANSITION "Refunded" -> state = "Refunded"
8. WHEN refund.deny -> false: skip
9. (end of program) -> end
```

Notes on the trace:
- Step 3/4 are shown as two lines for the same `AUTO HITL` construct, matching the pattern used in the specification's own complete example (steps 19–20 there): the construct first waits (the agent cannot resolve it automatically, so the human is asked), then is resolved once the finance manager's response arrives.
- Step 2 establishes `refund-assessment.accepted`, but no `WHEN` in this program tests `refund-assessment.*`; it plays no role in the flow below it, per rule 7/Outcomes ("visible everywhere once established," but only acted on by a `WHEN` that references it).
- `WHEN refund.deny` is checked once refund.approve is already the latest outcome for `refund`; since the latest (and only) established outcome is `approve`, not `deny`, this `WHEN` is false and is skipped (rule: "consecutive `WHEN`s are independent... every one that is true runs").
- There is no `FALLBACK` attached to this `HITL`, so it is irrelevant here (the response was usable) and would only matter had the response been insufficient/unavailable.

## Explicit assumptions

1. The spec does not define a mechanism for "authority" checks; I treated the company policy ("refunds above 1,000 EUR may only be approved by a finance manager") plus "the agent is not a finance manager" as establishing that the agent lacks the authority required to answer this specific `AUTO HITL:refund` decision, which is one of the conditions the spec explicitly names as producing uncertainty under `AUTO`. This is a direct reading of the spec's own rule, not an added rule of my own, but the *fact pattern* that triggers it (an org-external policy about role authority) is supplied by the task context rather than the DSL itself.
2. I assumed "the finance manager" counts as "the human" for purposes of the `HITL` interaction (the spec only speaks of "the human," not of roles); nothing in the spec restricts who among humans may answer, so any human response after the `HITL` is reached is usable if it clearly selects a listed answer.
3. The task does not state whether any time elapses or other events occur between the `AUTO HITL` being reached and the finance manager's answer; per rule 5 ("Stop at a boundary") I treated the construct as simply waiting until that answer arrives, with no other statements executing in between (there is nothing else running concurrently, since there is no `FORK`).
