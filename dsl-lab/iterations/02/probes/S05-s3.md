For each snippet: verdict, the violated/satisfied rule(s), and the reasoning from the specification text.

## Snippet A

```
HITL:release[approved, rejected]("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

**Verdict: INVALID — rule V5** (and also structurally invalid under **Indentation and scope**, rule 4 / V1).

Reasoning:
- Per the **AUTO** section: "`AUTO` is written directly before `HITL`, on the same line," and rule **V5** states a program is INVALID if `AUTO` "is not immediately followed, on the same line, by a decision `HITL:<name>[…]`."
- Here `AUTO` appears alone on its own line, with `WHEN decision.uncertain` indented beneath it — it is not immediately followed on the same line by a `HITL:<name>[…]` construct. This is in fact word-for-word the pattern the specification itself gives as an INVALID example (the `AUTO` / `WHEN decision.uncertain` / `→ HITL("Approve?")` block under "AUTO is not a request to guess...").
- Independently, **Indentation and scope**, rule 4, lists only `LOOP`, `WHEN`, `FORK`, `HITL`/`REQUIRE` (only a `→ FALLBACK`), and `→` items as constructs allowed to have indented children. `AUTO` on its own is not in that list, so a `WHEN` nested under a bare `AUTO` line is also an indentation violation (rule V1).
- Additionally, "Uncertainty is not a DSL condition, state, variable, or keyword" — `decision.uncertain` is not a producible outcome under the **Outcomes** table (only `VERIFY` and `HITL` answers produce outcomes), so a `WHEN decision.uncertain` would separately fail **V6** (no `VERIFY decision` or `HITL:decision[...]` in the program establishes that outcome).

So this snippet fails on at least three independent grounds: V5 (primary/explicit), V1, and V6.

## Snippet B

```
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

**Verdict: INVALID — rule V2**

Reasoning:
- Rule **V2**: INVALID if "`BREAK` is not inside a `LOOP`."
- The **BREAK** section confirms: "Leaves the innermost enclosing `LOOP` immediately... INVALID outside a `LOOP`."
- This snippet has no `LOOP` construct anywhere; `BREAK` appears inside a `WHEN` flow that is at the top level of the program. There is no enclosing loop for it to leave, so it is INVALID under V2.
- (The `WHEN implementation.rejected` condition itself is fine per V6, since `VERIFY implementation` establishes exactly `implementation.accepted`/`implementation.rejected` — the problem is solely the misplaced `BREAK`.)

## Snippet C

```
AUTO HITL:approve[yes, no]("Approve release?")
WHEN approve.yes
  → EMIT release
```

**Verdict: VALID**

Reasoning:
- `AUTO HITL:approve[yes, no]("Approve release?")` satisfies the required form `AUTO HITL:<name>[<answer>, ...]("<question>")` with `AUTO` immediately preceding a decision `HITL` on the same line — satisfies **V5** (not violated).
- The answer list `[yes, no]` is non-empty and has no repeated answers, and the name `approve` is used only once and not reused by any `VERIFY` — **V7** is not violated.
- `WHEN approve.yes` refers to subject `approve` and outcome `yes`, and the program contains `HITL:approve[yes, no]` listing `yes` as one of its answers — this satisfies the requirement of **V6** ("a `WHEN` condition MUST refer to a subject and an outcome that the program can produce").
- There is no `FALLBACK` attached to the `HITL`, but a `FALLBACK` is optional (only mandatory when written, and then subject to V8) — its absence does not make the program invalid; per the spec, "Insufficient or unavailable, and there is no `FALLBACK` → Execution ends, as with `STOP`," which is a defined, valid behavior, not an error.
- There is no `WHEN approve.no` branch, but the spec does not require every listed answer to have a corresponding `WHEN` — "no 'else'" and untested outcomes are simply not acted upon.
- Indentation: `WHEN` is a top-level statement (not nested under `HITL`, since only `→ FALLBACK` may nest under `HITL`), and its `→ EMIT release` child is correctly indented under it per rule 4. No indentation rule (V1) is broken.

All ten validity rules are satisfied, so Snippet C is VALID.

## Snippet D

```
HITL:region[eu, us]("Which region?")
  → FALLBACK
      → TRANSITION "Blocked"
WHEN region.eu
  → DELEGATE eu-deployment
```

**Verdict: INVALID — rule V8**

Reasoning:
- Rule **V8**: INVALID if "the last item of a fallback flow is not `STOP` or `BREAK`."
- The **FALLBACK** section reiterates: "Its last item MUST be `STOP` or `BREAK` (rule V8). The fallback never continues into the normal flow."
- Here the fallback flow attached to `HITL:region[...]` consists of a single item, `→ TRANSITION "Blocked"`, which is neither `STOP` nor `BREAK`. Since it's also the *last* (and only) item of that fallback flow, V8 is violated.
- (Everything else about this snippet is otherwise well-formed: `→ FALLBACK` is directly under the `HITL` as required by V4; `WHEN region.eu` correctly references an outcome listed in `HITL:region[eu, us]`, satisfying V6; there's only one `FALLBACK` under this `HITL`.)
