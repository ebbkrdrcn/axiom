```
TRANSITION "Testing"
WHEN tests.accepted

EMIT test-report
```

## Step-by-step trace

The key fact driving this trace is rule 2 of "Execution in ten rules": *"A `WHEN` is checked once, when execution reaches it."* combined with the Outcomes rule: *"A `WHEN` on a subject with no outcome yet is false."* and *"A `WHEN` is not a standing trigger and is never re-checked."*

In this program, `WHEN tests.accepted` is written, and therefore reached and checked, **before** `VERIFY tests` runs. At the moment execution reaches the `WHEN` (statement 2), nothing has yet established any outcome for `tests` (the only statement that could establish it, `VERIFY tests`, is statement 4, still to come). So the condition `tests.accepted` is — at that moment — not yet established, and by rule 7 / the Outcomes section, the `WHEN` is false. It is skipped, and, per rule 3 of **WHEN** ("The outcome is established later → Nothing happens. A `WHEN` is not a standing trigger and is never re-checked."), it is *never* revisited even though `VERIFY tests` later does establish `tests.accepted`.

```trace
1. TRANSITION "Testing" -> state = "Testing"
2. WHEN tests.accepted -> false: skip
3. DELEGATE tests -> done
4. VERIFY tests -> outcome tests.accepted
5. EMIT test-report -> done
6. (end of program) -> end
```

## Final state

`Testing`

(The only `TRANSITION` ever executed is `TRANSITION "Testing"` at statement 1; it is never overwritten because `TRANSITION "Review"` never runs.)

## Is `TRANSITION "Review"` ever executed?

**No.** `WHEN tests.accepted` is evaluated exactly once, at the point execution reaches it — which in this program is *before* `DELEGATE tests` and `VERIFY tests` have run. At that point `tests` has no established outcome at all, so the condition is false and the `WHEN`'s flow (`→ TRANSITION "Review"`) is skipped. `VERIFY tests` later establishing `tests.accepted` (per the given event) does not retroactively trigger the `WHEN`, because per the specification a `WHEN` "is never re-checked" and outcomes established after a `WHEN` has already been (falsely) evaluated have no effect on it. Consequently, given the program's statement order, `TRANSITION "Review"` is unreachable dead code with respect to this event (and in fact with respect to *any* event, since `tests` can never have an outcome before this `WHEN` is checked in this program as written — the `WHEN` always precedes the only statement, `VERIFY tests`, that could establish that outcome).

## Assumptions

None were needed beyond the specification: the sequencing rule ("Statements run one at a time, in the order written") and the Outcomes rules ("Not yet established… is false" and a `WHEN` is "never re-checked") together fully determine the trace and the answer without requiring any assumption not stated in the spec.
