```text
LOOP:implementation
  DELEGATE implementation
  VERIFY implementation
  WHEN implementation.accepted
    → BREAK
  WHEN implementation.rejected
    → DELEGATE correction
EMIT source-code
```

## Assumptions

1. **Loop label vs. subject name.** The requirement's repeated activity ("the implementation") is used both as the `LOOP:<name>` label and as the argument to `DELEGATE`/`VERIFY` (which makes `implementation` the outcome subject). The specification treats a `LOOP` name purely as a label that no statement refers to, and outcome subjects come from `VERIFY`/`HITL` arguments — nothing in the spec forbids a loop label and an outcome subject from sharing the same identifier, so this is assumed permissible rather than a naming collision.

2. **"Repeat from the start" needs no explicit control-flow statement.** After `DELEGATE correction`, the requirement says to "repeat from the start." Since `DELEGATE correction` is the last statement in the loop body (inside the `WHEN implementation.rejected` flow, which is itself the last construct in the body), rule 5 ("At the end of a loop body, the body starts again from its first statement") makes the loop repeat automatically. No `BREAK`, `STOP`, or other jump is needed or available for this purpose, so nothing further was added.

3. **"Leave the repetition" maps to `BREAK`.** `BREAK` is the only construct that leaves the innermost `LOOP`, so "if the verification accepts it, leave the repetition" is written as `WHEN implementation.accepted → BREAK`, per the `LOOP`/`BREAK` rules.

4. **No `REQUIRE`, `HITL`, `FORK`, or `TRANSITION` needed.** The requirement mentions no precondition to check, no human decision, no concurrency, and no explicit state name, so none of those constructs are used. Only `LOOP`, `DELEGATE`, `VERIFY`, `WHEN`, `BREAK`, and `EMIT` are needed to express it literally.

5. **Identifiers for the delegated work and the emitted artifact.** The requirement doesn't give exact token-like names, so `implementation` (for the thing delegated/verified), `correction` (for the corrective work), and `source-code` (for the emitted artifact, using a hyphen since identifiers allow `-`) were chosen as natural, spec-legal identifiers (letters, digits, `-`, `_`, starting with a letter).

6. **Two independent `WHEN`s, not an if/else.** The DSL has no "else"; per rule 3, consecutive `WHEN`s are independent and each is checked. Since `VERIFY implementation` establishes exactly one of `accepted`/`rejected` (rule from **VERIFY**/**Outcomes**), only one of the two `WHEN` flows will actually run in any given iteration, which is assumed to satisfy the requirement's "if accepted … if rejected …" as mutually exclusive in practice even though the DSL expresses it as two independent checks rather than an explicit branch.

7. **`EMIT source-code` runs exactly once, after the loop.** Placed at the top level after `LOOP:implementation`, at the same indentation as `LOOP`, so per indentation/scope rules it is outside the loop body and runs only once execution reaches it — i.e., only after `BREAK` ends the loop (this matches the `LOOP` example in the spec, where a statement following the loop runs "only after a `BREAK`").
