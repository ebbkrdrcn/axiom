```text
AUTO HITL:notes[short, detailed]("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:release[approved, rejected]("Approve the release?")
WHEN release.approved
  → EMIT release
WHEN release.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **"The agent may answer this question itself when the answer is clearly determined"** maps directly to the `AUTO` modifier on the `HITL:notes` decision. Per the spec's `AUTO` rule, this means: the agent answers only if the decision is certain and within its authority; otherwise the human is asked. No other mechanism in the DSL expresses "the agent may answer, else a human does."

2. **"This approval must always be given by a human, never by the agent"** maps to a plain `HITL:release[...]` (no `AUTO`). The spec states `AUTO` is the only way to let the agent answer a decision `HITL`; omitting it guarantees "the human; the agent MUST NOT answer" per the "Who decides a HITL" table.

3. **No `FALLBACK` is attached to either `HITL`.** The requirement does not describe what should happen if the human gives an insufficient/unavailable response to either question. The spec does not require a `FALLBACK` to be present (it's optional syntax: `[fallback]` in the grammar). I assumed the default behavior applies: "Insufficient or unavailable, and there is no FALLBACK → Execution ends, as with STOP." I did not invent a fallback flow since the requirement gives no instructions for that case.

4. **Answer names.** For the first `HITL`, I used the identifiers `short` and `detailed` (drawn directly from "If short... if detailed..."). For the second, I used `approved` and `rejected` (drawn directly from "If approved... if rejected..."), matching the requirement's own wording exactly rather than inventing synonyms (e.g., the spec's own example used `declined` instead of `rejected`, but the requirement here explicitly says "rejected").

5. **`DELEGATE` targets.** I used the identifiers `short-notes` and `detailed-notes` for the delegated work, since the requirement names them literally ("delegate short-notes"; "delegate detailed-notes") and these are valid identifiers (letters, digits, `-`, `_`, starting with a letter).

6. **`EMIT release` vs. `HITL:release`.** The requirement says "emit release" and separately concerns "approve the release," so I used the identifier `release` both as the artifact emitted and as the name of the second `HITL`. The validity rule V7 only forbids two `HITL`s sharing a name, or a name shared between a `HITL` and a `VERIFY`; it does not mention `EMIT` artifacts, and `EMIT` establishes no outcome, so I assumed this reuse of the string `release` across a `HITL` name and an `EMIT` artifact is not a namespace collision under the spec as written.

7. **No `REQUIRE`, `LOOP`, `FORK`, or `VERIFY`** appear, because the requirement describes a single straight-line flow with two sequential decisions and no repetition, concurrency, or delegated-result verification. I did not add any of these constructs since nothing in the requirement calls for them and the spec says not to invent statements.

8. **Ordering.** The four requirement sentences map to four top-level constructs executed strictly in the order given: the notes decision (with its two `WHEN`s), then the release decision (with its two `WHEN`s), reflecting rule 1 ("Statements run one at a time, in the order written").
