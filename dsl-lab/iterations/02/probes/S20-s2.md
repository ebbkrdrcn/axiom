# Analysis of the nested-loop `go_harness` program

```text
LOOP:release
  LOOP:fix
    DELEGATE fix
    VERIFY fix
    WHEN fix.accepted
      → BREAK
  TRANSITION "Fixed"
  VERIFY release-candidate
  WHEN release-candidate.accepted
    → BREAK
EMIT release
```

## 1. When `VERIFY fix` establishes `accepted`, which loop does `BREAK` exit, and what runs next?

The `BREAK` under `WHEN fix.accepted` exits **`LOOP:fix`**, not `LOOP:release`.

Reasoning from the spec:

- **BREAK**: "Leaves the innermost enclosing `LOOP` immediately." (`BREAK` section, and rule of the LOOP table: "`BREAK` inside the body (not inside a nested `LOOP`) → The loop ends now.")
- The nesting here is: `LOOP:release` contains `LOOP:fix`; the `WHEN fix.accepted → BREAK` is written inside the body of `LOOP:fix`. So the innermost enclosing loop at that point is `LOOP:fix`.
- Per **Execution in ten rules**, rule 6: "`BREAK` leaves the innermost loop immediately." `<name>` on a `LOOP` is only a label ("No statement refers to it; `BREAK` takes no name"), so `BREAK`'s target is determined purely by lexical nesting (innermost), never by choosing a name.
- Per the `LOOP` table: "Execution continues with the first statement after the loop, at the indentation of `LOOP`." The first statement after `LOOP:fix`, at `LOOP:fix`'s own indentation, is `TRANSITION "Fixed"`.

**Answer:** The `BREAK` exits `LOOP:fix`. Execution continues with `TRANSITION "Fixed"` (the statement immediately following `LOOP:fix`, still inside the body of `LOOP:release`). `LOOP:release` itself is not exited — it keeps running and will next execute `VERIFY release-candidate`.

## 2. Could the author write `BREAK release` inside `LOOP:fix` to leave both loops at once?

No. The DSL gives `BREAK` no mechanism to name a target loop, and there is no construct for exiting more than one loop with a single statement. Grounds:

- **Syntax — LOOP form**: "`<name>` is only a label. No statement refers to it; `BREAK` takes no name." This directly rules out `BREAK release` — `BREAK` cannot carry an argument identifying which loop to leave.
- **Grammar (EBNF)**: `simple = ... | ( "JOIN" | "BREAK" | "WAIT" | "STOP" ) , NL ;` — `BREAK` is defined as a bare keyword with nothing following it on the line. `BREAK release` does not match this production, so it is not a well-formed statement at all (it isn't even in the grammar to be judged INVALID by a V-rule against a valid `BREAK`; it simply is not a `BREAK` statement per the grammar).
- **Semantics**: `BREAK`'s effect is fixed as "leaves the innermost enclosing `LOOP` immediately" (BREAK section) — there is no rule anywhere that lets one `BREAK` unwind multiple nested loops.
- The spec's own guidance for the analogous cross-scope case (leaving a loop based on something learned across a boundary) is the `FORK`/`JOIN` note: "To leave a loop based on a branch's result, `JOIN` first, then use `WHEN … → BREAK`." No equivalent escape hatch is given for nested `LOOP`s, and the spec never mentions a multi-level or named break.

**Answer:** No. `BREAK` is syntactically argument-less (`BREAK` alone, per the grammar) and is explicitly documented to take no name; it always leaves exactly the single innermost enclosing loop. To leave both loops, the program would have to be written differently — e.g., have the inner loop's `BREAK` return control to `TRANSITION "Fixed"` as shown, and then have a further condition after that (such as `WHEN fix.accepted → BREAK` again at the outer level, if such an outcome/condition were available at that point) trigger a second, separate `BREAK` for `LOOP:release`. The specification does not provide a single statement that exits two loop levels at once, and nothing in it can be stretched to allow `BREAK release`.

## 3. If `VERIFY release-candidate` establishes `rejected`, what executes next?

- `VERIFY release-candidate` establishes exactly one outcome (`accepted` or `rejected`); here it establishes `release-candidate.rejected`. Per **VERIFY**: "`VERIFY` does not branch. Execution continues with the next statement whatever the outcome."
- The next statement is `WHEN release-candidate.accepted`. Its condition tests for `accepted`, but the latest outcome of `release-candidate` is `rejected`, so the condition is false. Per the `WHEN` table: "The condition is false → Skip the flow and continue after the `WHEN`. This is not an error."
- `WHEN release-candidate.accepted` is the last statement written in the body of `LOOP:release`. Skipping its flow reaches the end of that loop body without a `BREAK` or `STOP` having run. Per the `LOOP` table: "The last statement of the body is done → The next iteration starts at the first statement of the body," and rule 5 of **Execution in ten rules**: "At the end of a loop body, the body starts again from its first statement."

**Answer:** `WHEN release-candidate.accepted` is checked, found false, and its flow (the `→ BREAK`) is skipped — this is not an error, just a normal negative check. Since that `WHEN` is the last statement of `LOOP:release`'s body, reaching its end (without any `BREAK`/`STOP` firing) means the loop body restarts: the next thing to execute is `LOOP:fix`'s first statement again, i.e. `DELEGATE fix`, beginning a new iteration of `LOOP:release` (which itself re-enters `LOOP:fix` from its own start).

## Notes on assumptions

The specification fully determines all three answers; no gap-filling assumption was required beyond the following clarifications, which are direct readings of the text rather than assumptions:

- "Innermost enclosing `LOOP`" is determined purely by lexical/indentation nesting as defined in **Indentation and scope**, since `LOOP` names are declared to be non-referenceable labels.
- `BREAK release` is treated as not a valid instance of the `BREAK` statement at all (fails the grammar's `simple` production for `BREAK`), rather than as a valid statement that is merely INVALID under one of the V-rules; either way, the specification gives it no defined meaning and does not license it.
