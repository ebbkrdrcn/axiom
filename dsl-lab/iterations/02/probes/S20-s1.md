# Answer

Program under discussion:

```text
LOOP:release
  LOOP:fix
    DELEGATE fix
    VERIFY fix
    WHEN fix.accepted
      → BREAK
  TRANSITION "Fixed"
  VERIFY release-candidate
  WHEN release-candidate.accepted
    → BREAK
EMIT release
```

## 1. When `VERIFY fix` establishes `accepted`, which loop does `BREAK` exit, and what runs next?

The `BREAK` in question is nested inside `WHEN fix.accepted`, which is itself inside the body of `LOOP:fix`. Per the **BREAK** section, `BREAK` "Leaves the innermost enclosing `LOOP` immediately," and the LOOP quick-reference entry says the same: "`BREAK` leaves the innermost `LOOP` now." The innermost loop enclosing this `BREAK` is `LOOP:fix` (not `LOOP:release`).

So:

- `VERIFY fix` establishes `fix.accepted` (VERIFY section: it "establishes exactly one outcome: `<result>.accepted` or `<result>.rejected`").
- `WHEN fix.accepted` is checked once, is true, and runs its flow (`→ BREAK`).
- `BREAK` leaves `LOOP:fix` immediately. Per the LOOP table: "Execution continues with the first statement after that loop, at the indentation of `LOOP`."

The first statement after `LOOP:fix`, at `LOOP:fix`'s own indentation, is `TRANSITION "Fixed"`. That is what executes next — still inside `LOOP:release`, which is unaffected by this `BREAK`.

## 2. Could the author write `BREAK release` inside `LOOP:fix` to break out of both loops at once?

No. The specification does not support a named `BREAK`:

- The LOOP section states explicitly: "`<name>` is only a label. No statement refers to it; `BREAK` takes no name."
- The Syntax table classifies `BREAK` among the keywords that stand "`<keyword>` alone" (with `FORK`, `JOIN`, `WAIT`, `STOP`) — i.e., with no argument.
- The Grammar confirms this: `simple = ... | ( "JOIN" | "BREAK" | "WAIT" | "STOP" ) , NL ;` — `BREAK` is followed directly by a newline, with no identifier slot.

`BREAK release` therefore does not match any production of the grammar and is not a well-formed statement at all (it would be rejected as INVALID, since the program must be validated against the grammar/rules before execution, and this construct isn't expressible in the DSL — it's not merely disallowed by a validity rule like V2/V3, it simply doesn't exist as a form).

To leave both loops from inside `LOOP:fix`, the DSL's documented mechanism is different: `BREAK` only ever exits the *innermost* loop. Escaping an outer loop as well requires the outer loop to also test the relevant outcome and `BREAK` itself — outcomes persist as "latest value" and are visible everywhere once established (Outcomes section), so, for example, the outer loop's body could contain its own `WHEN fix.accepted → BREAK` after the inner loop, letting the outer loop break on the same, still-visible `fix.accepted` outcome. (This is an inference from the outcome-visibility and BREAK rules, since the spec does not give a ready-made "break N levels" construct — the spec doesn't determine a single-statement way to do this, so any such restructuring is an assumption beyond what's explicitly specified.) Alternatively, if the intent is to end execution entirely rather than just leave both loops, `STOP` is the documented construct for that ("Ends the entire execution immediately").

## 3. If `VERIFY release-candidate` establishes `rejected`, what executes next?

- `VERIFY` "does not branch. Execution continues with the next statement whatever the outcome" — so after `VERIFY release-candidate` establishes `release-candidate.rejected`, the next statement, `WHEN release-candidate.accepted`, still executes (is reached and checked).
- `WHEN release-candidate.accepted` is checked once: the latest outcome of `release-candidate` is `rejected`, not `accepted`, so the condition is false. Per the WHEN table: "Skip the flow and continue after the `WHEN`. This is not an error."
- `WHEN release-candidate.accepted` is the last statement in the body of `LOOP:release`. Since it was skipped (no `BREAK` ran), execution reaches the end of `LOOP:release`'s body without leaving the loop.
- Per rule 5 / the LOOP table: "At the end of a loop body, the body starts again from its first statement." The first statement of `LOOP:release`'s body is `LOOP:fix`.

So, next: the `WHEN` is evaluated false and skipped, and then `LOOP:release` starts its body again from the top — i.e., `LOOP:fix` (and within it, `DELEGATE fix`) runs again. `EMIT release` is not reached in this case, since the outer loop has not been broken.

## Assumptions

- Where the spec doesn't spell out a multi-level break mechanism, I noted explicitly (in Q2) that any suggested workaround (an outer-loop `WHEN`/`BREAK` relying on outcome persistence) is my own inference from the general outcome-visibility and BREAK rules, not a documented DSL feature — the specification does not determine a single-construct way to break multiple loop levels at once.
