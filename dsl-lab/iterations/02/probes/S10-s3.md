# Analysis of the go_harness Program

```
VERIFY review
WHEN review.rejected
  → DELEGATE correction
      VERIFY correction
  → TRANSITION "Rework"
EMIT review-report
```

This program is structurally identical to the worked example given in the specification's "Syntax → The arrow `→`" section (same shape, same statement kinds, only the subject/result names — `review`/`correction` — coincide exactly with that example). The spec resolves this exact structure explicitly, so the answers below follow directly from the text with no need for assumptions.

## 1. Which statements belong to the WHEN flow?

Three statements belong to the `WHEN review.rejected` flow:

- `DELEGATE correction`
- `VERIFY correction`
- `TRANSITION "Rework"`

Reasoning from the spec's indentation rules (**Indentation and scope**, rule 4): a line nested under a `→` item continues that item's flow, *unless* the statement after the `→` is itself a `LOOP`, `WHEN`, `FORK`, `HITL`, or `REQUIRE` — in which case the nested lines become that statement's own children. Here the first `→` item is `DELEGATE correction`, which is a plain (`simple`) statement, not one of `LOOP`/`WHEN`/`FORK`/`HITL`/`REQUIRE`. So the nested line `VERIFY correction` is not "owned" by `DELEGATE correction` as a private child scope — it continues the same sequential flow as the next step. The spec confirms this reading verbatim for this identical example: "The flow is `DELEGATE correction`, then `VERIFY correction`, then `TRANSITION "Rework"`."

## 2. Sequential or concurrent, and in what order?

Sequential. Per the "Execution in ten rules" table and the `WHEN` rule in **The arrow `→`**: "The `→` items under a `WHEN` or a `FALLBACK` form one sequential flow" (as opposed to a `FORK`, where `→` items are separate concurrent branches). Since this flow hangs off a `WHEN`, its statements run one at a time, each finishing before the next starts.

Order of execution (when the condition is true):
1. `DELEGATE correction`
2. `VERIFY correction`
3. `TRANSITION "Rework"`

## 3. Is `VERIFY correction` part of the WHEN flow?

Yes. As established in (1), `VERIFY correction` is nested under the `→ DELEGATE correction` item and continues that item's sequential flow (because `DELEGATE` is not a construct that takes its own child scope). It is therefore the second step of the `WHEN review.rejected` flow, not a separate top-level statement and not a child of `DELEGATE correction` in any special sense beyond "runs after it, still inside the flow."

## 4. Is `EMIT review-report` part of the WHEN flow? Is it executed?

Not part of the flow. `EMIT review-report` is written at the same indentation level as `WHEN`, i.e., it is a sibling of the `WHEN` statement, not nested under it — so per **Indentation and scope**, its parent is whatever encloses the `WHEN`, not the `WHEN` itself.

It is executed regardless of the outcome of `review`. Per the `WHEN` rules in "Execution in ten rules": when the condition is true, the flow runs and then "continue[s] after the `WHEN`, unless the flow ran `BREAK` or `STOP`"; when false, execution simply "skip[s] the flow and continue[s] after the `WHEN`." In this program's `WHEN` flow, neither `BREAK` nor `STOP` appears, so in both cases (true or false) execution proceeds to the next statement after the `WHEN` construct, which is `EMIT review-report`. This matches the spec's own note on this exact example: "`EMIT review-report` is outside the `WHEN` and runs afterwards in every case."

Given the stated assumption that `VERIFY review` establishes `review.rejected`, the condition is true, the flow runs, and then `EMIT review-report` executes.

## 5. If `VERIFY review` had established `review.accepted`, which statements would execute?

The `WHEN review.rejected` condition tests whether the latest outcome of `review` is exactly `rejected`. With `review.accepted` established instead, the condition is false. Per rule: "The condition is false → Skip the flow and continue after the `WHEN`. This is not an error. Execution does not wait."

So the flow (`DELEGATE correction`, `VERIFY correction`, `TRANSITION "Rework"`) would **not** execute. Only:

1. `VERIFY review` (already executed, establishing `review.accepted`)
2. `WHEN review.rejected` → evaluated false, skipped
3. `EMIT review-report` (executes, since it's outside the `WHEN` and unconditional)

would run. Note there is no `WHEN review.accepted` in this program, so nothing else runs in response to the `accepted` outcome — it simply goes unused by any `WHEN` in this particular program.
