# Answer

Program under analysis:

```text
VERIFY review
WHEN review.rejected
  → DELEGATE correction
      VERIFY correction
  → TRANSITION "Rework"
EMIT review-report
```

Assumption given: `VERIFY review` establishes `review.rejected`.

(This program, and its behavior description, matches the "Example of nesting" given in the specification under **The arrow →**, so the answers below follow directly from the spec's own worked description of it.)

## 1. Which statements belong to the WHEN flow?

The `WHEN review.<outcome>` construct has two `→` items directly nested under it, so both are part of its flow:

- `→ DELEGATE correction` — and, per **Indentation and scope** rule 4 ("If the statement after `→` is itself a `LOOP`, `WHEN`, `FORK`, `HITL` or `REQUIRE`, the lines nested under it are that statement's own children" — and more generally, per rule 4's catch-all "any `→` item (lines that continue that item's flow or branch)"), the line `VERIFY correction` nested under it is a child of that `→` item and therefore also belongs to the WHEN flow.
- `→ TRANSITION "Rework"`

So the WHEN flow consists of three statements: `DELEGATE correction`, `VERIFY correction`, `TRANSITION "Rework"`.

`EMIT review-report` is written at the same indentation as `WHEN`, not nested under it, so it is **not** part of the WHEN flow (see question 4).

## 2. Sequential or concurrent, and in what order?

Sequential. Per **Execution in ten rules**, rule 4: "The `→` items under a `WHEN` ... form **one sequential flow**." (Concurrency only applies to `→` items under `FORK`, which is not the case here.)

Order of execution, once the WHEN flow runs:

1. `DELEGATE correction`
2. `VERIFY correction`
3. `TRANSITION "Rework"`

Each statement finishes before the next starts (Execution rule 1).

## 3. Is `VERIFY correction` part of the WHEN flow?

Yes. It is indented as a child of the `→ DELEGATE correction` item, so it continues that item's flow within the WHEN construct. The specification's own text about this exact example states: "The flow is `DELEGATE correction`, then `VERIFY correction`, then `TRANSITION "Rework"`." This confirms `VERIFY correction` is the second step of the WHEN flow, running after `DELEGATE correction` completes and before `TRANSITION "Rework"` runs.

## 4. Is `EMIT review-report` part of the WHEN flow? Is it executed?

It is **not** part of the WHEN flow. It sits at the same indentation level as `WHEN` itself (not nested under it), so per **Indentation and scope** rule 2/3, its parent is whatever precedes `WHEN` at that same top level, not the `WHEN` construct — it is a sibling statement that comes after the WHEN construct in program order.

It **is** executed, and unconditionally so, regardless of whether the WHEN condition was true or false. This follows from Execution rule 2: "True → run its flow, then continue after the `WHEN`... False → skip it [and] continue after the `WHEN`." Either way, execution proceeds to the next statement after the WHEN, which is `EMIT review-report`. The spec's own commentary on this identical example states this explicitly: "`EMIT review-report` is outside the `WHEN` and runs afterwards in every case."

Given the stated assumption (`review.rejected` is established), the condition is true, the WHEN flow runs (`DELEGATE correction` → `VERIFY correction` → `TRANSITION "Rework"`), and then `EMIT review-report` runs, ending the program (Execution rule 10).

## 5. If `VERIFY review` had established `review.accepted` instead

The single `WHEN` in this program tests `review.rejected`. If `VERIFY review` established `review.accepted` instead, then the latest outcome of `review` would be `accepted`, not `rejected`. Per the condition rule ("The condition is true only if the latest outcome of `<subject>` is exactly `<outcome>`"), `WHEN review.rejected` would evaluate to false.

Per Execution rule 2, a false condition means: "Skip the flow and continue after the `WHEN`. This is not an error. Execution does not wait."

So the statements that would execute are:

1. `VERIFY review` → establishes `review.accepted`
2. `WHEN review.rejected` → false: skip (the flow — `DELEGATE correction`, `VERIFY correction`, `TRANSITION "Rework"` — does **not** run)
3. `EMIT review-report` → runs (as always, unconditionally, after the WHEN)

Then execution ends normally (last top-level statement done).

Note: there is no `WHEN review.accepted` in this program, so establishing `review.accepted` does not itself trigger any flow — it only determines that the sole `WHEN` (which tests `.rejected`) is false. The specification gives no "else" mechanism (Execution rule 2/3: "no 'else'"), so nothing else changes as a result of the outcome being `accepted` rather than something else other than `rejected`.
