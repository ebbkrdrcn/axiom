# Validity check

**Result: INVALID.** Per "Validate first" / rule statement: *"A program that breaks any of these rules is INVALID. It MUST be rejected as a whole and MUST NOT be executed in part."* The program is therefore not executed; only the violations are reported.

Line numbering used below follows the task's instruction (line 1 = `REQUIRE repository`), counting every physical line of the program as written (there are no blank lines to skip):

```
1  REQUIRE repository
2  LOOP:cycle
3    DELEGATE implementation
4    FORK
5      → VERIFY implementation
6          WHEN implementation.rejected
7            → BREAK
8      → DELEGATE review
9          VERIFY review
10   JOIN
11   WHEN review.passed
12     → TRANSITION "Reviewed"
13   HITL:ship[yes, no]("Ship it?")
14     → FALLBACK
15         → TRANSITION "Waiting"
16   WHEN ship.yes
17     → BREAK
18 EMIT source-code
```

## Violated rules

### 1. Rule V3 — line 7 (`→ BREAK`)
> V3: INVALID if `BREAK` is inside a `FORK` branch, and the `LOOP` it would leave is outside that branch.

Line 7's `BREAK` sits inside branch 1 of the `FORK` at line 4 (branch = `→ VERIFY implementation` at line 5, plus its nested `WHEN implementation.rejected` at line 6, plus the `BREAK` at line 7). The loop it would need to leave is `LOOP:cycle` (line 2), which encloses the `FORK` but is not itself contained inside the branch — i.e. the `LOOP` is outside the branch. Per the spec's own commentary on `BREAK`: *"INVALID inside a `FORK` branch unless the `LOOP` it leaves is also inside that branch"* and the `FORK` table: *"`BREAK` in a branch: INVALID (rule V3). To leave a loop based on a branch's result, `JOIN` first, then use `WHEN … → BREAK`."* This program does exactly what that note warns against: it tries to `BREAK` out of `LOOP:cycle` from inside a `FORK` branch instead of joining first (the correct pattern, `WHEN ship.yes → BREAK` at lines 16–17, is used correctly elsewhere in the same program, which only makes the line 7 usage more clearly wrong by contrast).

### 2. Rule V6 — line 11 (`WHEN review.passed`)
> V6: INVALID if a `WHEN` tests `x.y`, and the program contains neither `VERIFY x` with `y` being `accepted` or `rejected`, nor `HITL:x[…]` listing `y`.

Line 11 tests `review.passed`. The only statement in the program that can establish an outcome on the subject `review` is `VERIFY review` (line 9), and per the **Outcomes** section and the `VERIFY` section, `VERIFY <result>` establishes only `<result>.accepted` or `<result>.rejected` — *"There are no other VERIFY outcomes: `passed`, `failed`, `ok` and similar are INVALID in a `WHEN`."* There is also no `HITL:review[…]` anywhere. So `review.passed` is not an outcome the program can ever produce, violating V6.

### 3. Rule V8 — fallback at lines 14–15 (last item is line 15, `→ TRANSITION "Waiting"`)
> V8: INVALID if the last item of a fallback flow is not `STOP` or `BREAK`.

The `FALLBACK` attached to `HITL:ship` (line 13) consists of a single flow item: `→ TRANSITION "Waiting"` (line 15). That is also, by definition, the *last* item of the fallback flow, and it is neither `STOP` nor `BREAK`. The spec is explicit: *"Its last item MUST be `STOP` or `BREAK` (rule V8). The fallback never continues into the normal flow."* Since this fallback ends on a `TRANSITION`, it violates V8 (contrast with the spec's own canonical fallback examples, which always end `… → STOP` or `… → BREAK`).

## Checks that passed (for completeness)

- **V1** (indentation/scope): the nesting is consistent — `LOOP`, `WHEN`, `FORK`, and `HITL`'s `→ FALLBACK` all have the kinds of children the spec allows, and continuation lines under `→` items (e.g. `WHEN implementation.rejected` continuing branch 1, `VERIFY review` continuing branch 2) match the pattern shown in the spec's own `JOIN` example. No indentation violation found.
- **V2**: not applicable to either `BREAK` (both are textually inside `LOOP:cycle`); the line 7 case is instead the more specific V3.
- **V4**: every `→` item is under `WHEN`, `FORK`, or `FALLBACK`; the one `→ FALLBACK` (line 14) is directly under a `HITL`; `HITL:ship` has only one `FALLBACK`. No violation.
- **V5**: no `AUTO` is used in this program, so V5 cannot be violated.
- **V6** otherwise: `implementation.rejected` (line 6) is valid (`VERIFY implementation` at line 5 can establish it); `ship.yes` (line 16) is valid (listed in `HITL:ship[yes, no]`). Only `review.passed` fails, as noted above.
- **V7**: only one `HITL` (`ship`), no name shared between a `HITL` and a `VERIFY`, and `[yes, no]` is non-empty with no repeated answer. No violation.
- **V9**: the `FORK` (line 4) has two branches (≥ 2), and the `JOIN` (line 10) has a corresponding, not-yet-joined `FORK` at the same indentation in the same flow. No violation.
- **V10**: `WHEN review.passed` (line 11) is reached only after `JOIN` (line 10), so the outcome (had it been a valid one) would be safely visible; `WHEN implementation.rejected` (line 6) tests an outcome established earlier in the *same* branch's own sequential flow, not a sibling branch, so no join-ordering problem arises there either.
