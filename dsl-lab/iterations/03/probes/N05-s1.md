# Execution of the program, twice

```text
DELEGATE release-candidate
VERIFY release-candidate
HITL:ship[approved, rejected]("Ship the release candidate?")
  → FALLBACK
      → TRANSITION "Blocked"
      → HITL("Tell the release manager that shipping is blocked")
      → STOP
WHEN ship.approved
  → EMIT release
```

- **V4** — the only `→` items are under the `FALLBACK`, and that `FALLBACK` is written directly under `HITL:ship`, with no second `FALLBACK`. The `WHEN`'s `→ EMIT release` is a `→` item under a `WHEN`, which is permitted. OK.
- **V5** — no `AUTO`. OK.
- **V6** — `WHEN ship.approved` refers to `HITL:ship[approved, rejected]`, which lists `approved`. OK.
- **V7** — only one `HITL` name (`ship`); the inner `HITL("...")` is a request form with no name. No name collides with a `VERIFY`. OK.
- **V8** — the fallback flow's last item is `STOP`. OK.
- **V9** — no `FORK`/`JOIN`. OK.
- **V10** — no `FORK`. OK.
- **V11/V12** — no bindings and no entity `TRANSITION` at all in this program (only the process-state form `TRANSITION "Blocked"` is used). OK.

**Verdict: VALID.**

There are no `<name>:<Type> = ...` bindings anywhere in this program, so **no entity is bound** in either run — part (3) of the task ("final status of every bound entity...") does not apply, and no entity file is read or changed in either run.

Both runs share the same start:

- `DELEGATE release-candidate` completes.
- `VERIFY release-candidate` establishes `release-candidate.accepted`.
- The human's answer to `HITL:ship`, "Maybe, ask me later.", selects none of `[approved, rejected]`, defers the decision, and is not a decision at all → classified **insufficient**. Per the `HITL` failure rule, since there is a `FALLBACK`, it runs; no `ship` outcome is established.
- Inside the fallback flow: `TRANSITION "Blocked"` sets the process state, then the inner `HITL("Tell the release manager that shipping is blocked")` (a request, not a decision) is reached.
- Because the `FALLBACK` "runs instead of the normal flow" and its own `→` sequence has no branch back to the top level, the closing `WHEN ship.approved` at the bottom of the program is never reached in either run — the fallback path ends the execution before that point (via the fallback's own `STOP`, or earlier if the inner `HITL` itself fails).

The two runs differ only in what happens at that inner `HITL("Tell the release manager...")`.

"Noted." confirms that the requested action (telling the release manager) has been acted on/acknowledged — for a request-form `HITL`, a response is usable if it confirms the requested action. So the response is **usable**, no outcome is established (request form establishes none), and execution continues with the next statement, `STOP`.

VALID.

## Run B — nobody answers the inner request; the runtime stops waiting

The inner `HITL("Tell the release manager that shipping is blocked")` gets no response, and the runtime decides to stop waiting → classified **unavailable**. This particular `HITL` has no `FALLBACK` of its own (the only `FALLBACK` in the program belongs to `HITL:ship`, and it does not nest a further `FALLBACK` under the inner `HITL`). Per the `HITL` failure rule, with no `FALLBACK`, execution ends, as with `STOP`. The written `STOP` on the next line is therefore never reached — execution has already ended.
