# Execution of the ADR-0101 acceptance program (three runs)

Program:

```text
a1:ADR = ADR-0101
VERIFY a1
HITL:accept[approved, rejected]("Accept ADR-0101?")
WHEN accept.approved
  → TRANSITION a1 "Accepted"
WHEN accept.rejected
  → TRANSITION a1 "Rejected"
```

## Validity (applies to all three runs — the program text is the same)

- Binding `a1:ADR = ADR-0101` is at the top, unindented, before any other statement — V11 satisfied.
- `a1` is not used as a `HITL` name, and no `HITL` name is reused — V7, V12 satisfied.
- `VERIFY a1` and `HITL:accept[...]` have no `→ FALLBACK`; none is required (a `FALLBACK` is optional). No `FALLBACK` is malformed, so V4/V8 do not apply.
- `WHEN accept.approved` and `WHEN accept.rejected` both test outcomes declared by `HITL:accept[approved, rejected]` — V6 satisfied.
- No `LOOP`, `FORK`, `JOIN`, `BREAK`, or `AUTO` appear, so V2, V3, V5, V9, V10 do not apply.
- No other indentation, arrow placement, or statement-form problem exists — V1 satisfied.

**Verdict (same for Run A, B, C): `0. validate -> VALID`**

## Shared steps (identical in every run up to the HITL answer)

1. `a1:ADR = ADR-0101` — exactly one file (`docs/adr/ADR-0101.md`) declares `id: ADR-0101`, its `type` is `ADR`, and it is structurally valid (all required fields/sections of the ADR Template are present). The binding succeeds.
2. `VERIFY a1` — per the task statement, Context, Decision and Consequences are present, the Decision ("All services log JSON objects with the fields `time`, `level`, `msg` and `trace_id`") is one followable rule, and the Consequences name an effect ("Log queries become possible; existing log parsers must be replaced"). These are exactly the ADR Definition's `accepted` criteria, so `VERIFY` establishes `a1.accepted`.
3. `HITL:accept[approved, rejected]("Accept ADR-0101?")` is reached and waits for the human.

The three runs diverge only in how that response is classified.
