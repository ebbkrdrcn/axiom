# Execution of the program

```text
FORK
  → LOOP:retry
      DELEGATE upload
      VERIFY upload
      WHEN upload.accepted
        → BREAK
  → DELEGATE docs
JOIN
WHEN upload.accepted
  → TRANSITION "Uploaded"
```

## 1. Validity verdict

**VALID.**

Checks of note:

- **V9** — `FORK` has two branches (`→ LOOP:retry …` and `→ DELEGATE docs`); `JOIN` has a corresponding `FORK`. OK.
- **V2/V3** — `BREAK` is inside `LOOP:retry`, and `LOOP:retry` itself is nested *inside* the same `FORK` branch that contains it (the first branch). Per the DSL, a `BREAK` that leaves a loop nested inside its own branch is valid (it is not leaving a loop that lives outside the branch). No violation.
- **V6** — `WHEN upload.accepted` (both occurrences: inside the loop, and after `JOIN`) refers to an outcome that `VERIFY upload` can produce (`accepted`/`rejected`). Declared. OK.
- **V10** — The `WHEN upload.accepted` after `JOIN` tests a subject (`upload`) established inside a `FORK` branch, but a `JOIN` of that `FORK` is written between the `FORK` and that `WHEN`, so it is testable. The `WHEN upload.accepted` inside the loop is part of the same branch's own sequential flow (not crossing branches), so V10 does not apply to it either. No violation.
- **V4/V1/V8** — indentation and `→` placement follow the grammar; there is no `FALLBACK` in this program, so V8 is vacuous.

No rule is broken. There are no bindings, so no entity is bound.

## 2. Execution trace

Events given: first `VERIFY upload` → `rejected`; second `VERIFY upload` → `accepted`; all delegated work is delivered.

```trace
0. validate -> VALID
1. FORK -> branches started
2. DELEGATE upload -> done
3. VERIFY upload -> outcome upload.rejected
4. WHEN upload.accepted -> false: skip
5. LOOP:retry -> loop again
6. DELEGATE upload -> done
7. VERIFY upload -> outcome upload.accepted
8. WHEN upload.accepted -> true: run flow
9. BREAK -> break
10. DELEGATE docs -> done
11. JOIN -> joined
12. WHEN upload.accepted -> true: run flow
13. TRANSITION "Uploaded" -> state = "Uploaded"
14. (end of program) -> end
```

(Lines 2–9 are branch 1 of the `FORK` — `LOOP:retry`; line 10 is branch 2 — `DELEGATE docs`. Since `FORK` runs branches concurrently and neither depends on the other's result, they are shown as complete, sequential sub-flows before the `JOIN` line, in the same style as the specification's own worked example.)

## 3. Entities

The program contains **no bindings** (`<name>:<Type> = <identity>` never appears). `upload` and `docs` are plain identifiers used as `DELEGATE`/`VERIFY` arguments, not bound entity names — the DSL's entity machinery (`VERIFY <name>` on an entity, `TRANSITION <name> "<status>"`) never applies to them.

Consequently:

- No entity is bound.
- No entity has a final status to report.
- No entity file changed.
- The `TRANSITION "Uploaded"` at the end is a **process**-state transition (`TRANSITION "<state>"`, no bound name), not an entity-status transition — it changes no entity and no file.

## 4. Final process state

`Uploaded` (set by the final `TRANSITION "Uploaded"`, which is reached because `upload.accepted` — the outcome from the second, successful `VERIFY upload` — is still the latest outcome of `upload` when execution reaches that `WHEN` after `JOIN`).

## 5. Additional questions

- **How many times does `DELEGATE upload` run?** Twice — once per iteration of `LOOP:retry` (iteration 1: rejected, loop repeats; iteration 2: accepted, loop breaks).
- **What does the `BREAK` end?** Only the innermost enclosing loop, `LOOP:retry`, which is the loop nested inside the first `FORK` branch. It ends that loop (and, since nothing follows the loop in that branch, thereby completes branch 1 of the `FORK`); it does **not** end the `FORK` itself, the other branch (`DELEGATE docs`), or the whole execution — only `STOP` would do that.
