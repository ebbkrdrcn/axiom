# DSL Program for ADR-0101 Verification and Decision

## Program

```
a1:ADR = ADR-0101
VERIFY a1
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
HITL:decision[approved, rejected]("Accept ADR-0101?")
  → FALLBACK
      → TRANSITION "Waiting"
      → STOP
WHEN decision.approved
  → TRANSITION a1 "Accepted"
    → FALLBACK
        → TRANSITION "Waiting"
        → STOP
WHEN decision.rejected
  → TRANSITION a1 "Rejected"
    → FALLBACK
        → TRANSITION "Waiting"
        → STOP
```

## Assumptions

1. **ADR-0101 exists and is of type ADR**: The binding `a1:ADR = ADR-0101` will verify this; if not satisfied, execution ends before any other statement.

2. **ADR-0101 is in Proposed status**: The requirement implies the ADR starts in a status from which it can transition to either Accepted or Rejected. Proposed is the only initial status for ADRs per the ADR Definition.

3. **Structural validity is maintained**: Both the binding resolution and VERIFY step assume the ADR meets the Template requirements (all required fields present, correct formats).

4. **VERIFY can determine an outcome**: If verification criteria are ambiguous or evidence is unavailable, VERIFY fails and runs the FALLBACK (setting state to Waiting).

5. **The human provides a response to the HITL**: The process waits at the HITL until the human provides an answer. If no usable answer is given (insufficient or unavailable response), the FALLBACK runs.

6. **The human's answer is unambiguous**: The response clearly indicates either "approved" or "rejected" (examples: "Yes, accept it" → approved; "No, reject it" → rejected; "Maybe later" → insufficient, triggers FALLBACK).

7. **Transition preconditions are enforced**: 
   - For "Accepted": requires both `verified: accepted` (from the VERIFY step) AND `human: approved` (from being inside the decision.approved WHEN branch with the identity in the question). If verification was rejected, this transition fails and runs its FALLBACK.
   - For "Rejected": requires `human: rejected` (satisfied by being inside the decision.rejected WHEN branch).

8. **Fallback transitions always succeed**: The `TRANSITION "Waiting"` statements are process state changes (not entity status changes), which always succeed.

9. **No other ADR entities share the same identity**: The specification requires exactly one entity with identity ADR-0101; if multiple representations exist, binding fails.
