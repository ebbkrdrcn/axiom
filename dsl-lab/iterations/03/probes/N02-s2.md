# Execution of the review program — five runs

Program (validated once; it is VALID — a single `HITL` decision with a `FALLBACK` ending in `STOP`, followed by two independent `WHEN`s on the declared outcomes `review.approved` / `review.rejected`; no rule V1–V12 is broken):

```text
HITL:review[approved, rejected]("Approve the design document?")
  → FALLBACK
      → TRANSITION "Pending"
      → STOP
WHEN review.approved
  → TRANSITION "Approved"
WHEN review.rejected
  → TRANSITION "Rework"
```

For each run, the human's response to `HITL:review[approved, rejected]` is classified per the DSL's **Usable, insufficient, unavailable** table, which then determines whether the outcome `review.approved`/`review.rejected` is established and which `WHEN` (or the `FALLBACK`) runs.

---

## Run A — "Approved, but fix the typo in section 2 later."

- **Classification:** usable — clearly means the listed answer `approved`. The added comment ("fix the typo … later") is extra content; it answers no other construct and changes nothing else.
- **Outcome:** `review.approved` is established.
- **Flow:** execution continues after the `HITL`. `WHEN review.approved` is true → `TRANSITION "Approved"`. `WHEN review.rejected` is false (latest outcome of `review` is `approved`, not `rejected`) → skipped.
- **Final process state:** `Approved`.

---

## Run B — "Not like this, the API section is wrong."

- **Classification:** usable — it clearly refuses, so it selects the listed answer `rejected`. Per the spec's own worked example ("Not like this, rewrite the intro." → usable: rejected), the accompanying complaint ("the API section is wrong") is extra content that does not change the classification.
- **Outcome:** `review.rejected` is established.
- **Flow:** `WHEN review.approved` is false → skipped. `WHEN review.rejected` is true → `TRANSITION "Rework"`.
- **Final process state:** `Rework`.

---

## Run C — "Looks good to me, ship it!"

- **Classification:** usable — clearly means `approved` (approval plus an instruction to proceed, which is extra content and answers nothing else).
- **Outcome:** `review.approved` is established.
- **Flow:** `WHEN review.approved` is true → `TRANSITION "Approved"`. `WHEN review.rejected` is false → skipped.
- **Final process state:** `Approved`.

---

## Run D — "Maybe, I need to check with legal first."

- **Classification:** insufficient — it defers the decision (no answer is given; a future check is announced instead). It selects neither listed answer.
- **Outcome:** none is established (`review` holds no outcome).
- **Flow:** the `HITL` fails; since it has a `FALLBACK`, that flow runs instead of the normal continuation: `TRANSITION "Pending"`, then `STOP`. Because `STOP` ends the whole execution, the two `WHEN`s after the `HITL` never run (they are not reached — `STOP` ends everything immediately, and in any case the outcome they test was never established).
- **Final process state:** `Pending`.

---

## Run E — "Yes and no."

- **Classification:** insufficient — ambiguous between the two answers (matches the spec's own example "Approve and reject both." → insufficient (ambiguous)).
- **Outcome:** none is established.
- **Flow:** same as Run D — the `HITL` fails, its `FALLBACK` runs: `TRANSITION "Pending"`, then `STOP`. Execution ends there; the `WHEN`s are never reached.
- **Final process state:** `Pending`.
