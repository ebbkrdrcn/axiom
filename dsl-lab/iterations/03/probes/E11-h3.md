# E11 Answer: go_harness DSL Program for TASK-0100 Workflow

## Program

```text
t1:Task = TASK-0100
a1:ADR = t1.adr

LOOP:work
  DELEGATE implementation
  VERIFY t1
    → FALLBACK
        → TRANSITION "Blocked"
        → STOP
  WHEN t1.accepted
    → TRANSITION t1 "Review"
    → BREAK
  WHEN t1.rejected
    → TRANSITION t1 "Debugging"
    → DELEGATE diagnosis
    → TRANSITION t1 "InProgress"

HITL:done[approved, rejected]("Is TASK-0100 done?")
  → FALLBACK
      → STOP

WHEN done.approved
  → TRANSITION t1 "Done"

WHEN done.rejected
  → TRANSITION t1 "InProgress"
```

## Assumptions

1. **Entity availability**: TASK-0100 and ADR-0100 both exist, are of their declared types, and are structurally valid according to their Templates.

2. **Initial state**: TASK-0100 starts in `InProgress` status (as given in the fixture) or another status that permits the required transitions.

3. **Relation binding**: The binding `a1:ADR = t1.adr` resolves successfully to ADR-0100 (the `adr` field in TASK-0100).

4. **Work completion**: The `DELEGATE implementation` and `DELEGATE diagnosis` operations complete with results that can be evaluated, though the result quality or correctness is not assumed.

5. **Verification determinism**: When `VERIFY t1` is executed, it can determine exactly one outcome (`accepted` or `rejected`) based on the Acceptance Criteria and available evidence. If evidence is unavailable or criteria are ambiguous, the verification fails (triggering FALLBACK).

6. **Precondition satisfaction**:
   - `InProgress → Review` requires `verified: accepted`, which holds immediately after successful `VERIFY t1` because entity data has not changed between verification and transition.
   - `InProgress → Debugging` requires `verified: rejected`, which holds immediately after failed `VERIFY t1` for the same reason.
   - `Review → Done` requires `human: approved`. This precondition is satisfied because the transition is inside `WHEN done.approved` (a `WHEN` flow of a non-AUTO `HITL`) whose question contains the entity identity "TASK-0100".
   - `Review → InProgress` requires no precondition and is always permitted.

7. **Human response**: The human will provide either a usable response (`approved` or `rejected`) to the done question, or an unusable response. If unusable, execution ends via the FALLBACK flow.

8. **No concurrent changes**: No external agent modifies TASK-0100 or ADR-0100 while the process is running, except through the delegated work (which is allowed by the Definition).

9. **Indefinite iteration**: The process does not assume a limit on the number of loop iterations. If verification repeatedly rejects, the loop continues indefinitely (or until stopped by an external factor).

10. **Behavioral completeness**: After the human decision, if approved, the task reaches Done; if rejected, it returns to InProgress. No further retry loop is implemented—subsequent retries would require a new process invocation.
