# Execution of the program

```text
FORK
  → LOOP:retry
      DELEGATE upload
      VERIFY upload
      WHEN upload.accepted
        → BREAK
  → DELEGATE docs
JOIN
WHEN upload.accepted
  → TRANSITION "Uploaded"
```

## (1) Validity verdict

**VALID**

Check against V1–V12:

- **V9** (`FORK`/`JOIN` correspondence): the `FORK` has exactly two branches (`→ LOOP:retry …` and `→ DELEGATE docs`), and the `JOIN` corresponds to it. Satisfied.
- **V3** (`BREAK` inside a `FORK` branch): the `BREAK` is inside `LOOP:retry`, and `LOOP:retry` is itself nested inside the same branch (the first `→` of the `FORK`). This is the case the spec explicitly allows: "`BREAK` in a branch that leaves a `LOOP` nested inside the same branch" → valid.
- **V2**: `BREAK` is inside a `LOOP` (`retry`). Satisfied.
- **V6** (`WHEN` refers to a declared outcome): both occurrences of `WHEN upload.accepted` refer to `upload`, and the program contains `VERIFY upload`, which can establish `upload.accepted`. Satisfied.
- **V10** (`FORK` branch outcome tested without `JOIN`): the outcome `upload.*` is established inside a branch of the `FORK`. It is tested again after the `FORK` in the final `WHEN upload.accepted`, but a `JOIN` appears between the `FORK` and that `WHEN`. Satisfied (not a violation). The `WHEN upload.accepted` *inside* the branch, tested within the same branch that establishes it, is not subject to V10 at all (V10 concerns testing a branch's outcome outside that branch without an intervening `JOIN`).
- **V4** (`→` placement): all `→` items are directly under `FORK` (as branches) or under `WHEN` (as flow items). No `FALLBACK` is used, so no `FALLBACK`-placement issue arises. Satisfied.
- **V1** (indentation/statement forms): every line matches a valid statement form and the nesting follows the rules (the `LOOP:retry` and its body are children of the first `→` item, as allowed by "Indentation and scope" rule 4(vi): when the statement after `→` is itself a `LOOP`, the lines nested under it are that `LOOP`'s own children). Satisfied.
- **V5, V7, V8, V11, V12**: not applicable — there is no `AUTO`, no `HITL`, no `FALLBACK`, and no bindings/entity `TRANSITION`s in this program.

No rule is broken. The program is **VALID**.

## (2) Execution trace

Events given: the first `VERIFY upload` establishes `rejected`; the second establishes `accepted`; all delegated work is delivered.

```trace
0. validate -> VALID
1. FORK -> branches started
2. DELEGATE upload -> done
3. VERIFY upload -> outcome upload.rejected
4. WHEN upload.accepted -> false: skip
5. LOOP:retry -> loop again
6. DELEGATE upload -> done
7. VERIFY upload -> outcome upload.accepted
8. WHEN upload.accepted -> true: run flow
9. BREAK -> break
10. DELEGATE docs -> done
11. JOIN -> joined
12. WHEN upload.accepted -> true: run flow
13. TRANSITION "Uploaded" -> state = "Uploaded"
14. (end of program) -> end
```

Notes on the trace:

- Steps 2–9 are the branch starting `→ LOOP:retry …`; step 10 is the branch `→ DELEGATE docs`. `FORK` runs both branches concurrently (rule 1/4 of Execution rules); the two branches have no ordering requirement relative to each other, only within themselves. They are listed one after the other here only for linear readability — `DELEGATE docs` could equally be interleaved at any point among steps 2–9 in real time; the DSL does not define, and this trace does not assume, a specific interleaving.
- No line is written for entering `LOOP:retry` the first time (rule: "Entering a `LOOP` for the first time writes no line"); step 5 (`loop again`) marks the second iteration starting.
- `WHEN upload.accepted` at step 4 is false because the latest (and only, at that point) outcome of `upload` is `rejected`.
- At step 8 the condition is true because the second `VERIFY upload` (step 7) replaced the outcome with `accepted`.
- `BREAK` (step 9) ends `LOOP:retry`. Since the loop is the last statement of the branch, the branch is now complete.
- `JOIN` (step 11) waits for both branches; both are complete (branch 1 completed at step 9, branch 2 at step 10), so it succeeds immediately once both are done.
- The final `WHEN upload.accepted` (step 12) is evaluated after the `JOIN`, using the outcome established inside the branch (`accepted`, from step 7) — outcomes are visible everywhere once established, including after a `JOIN`.
- `TRANSITION "Uploaded"` (step 13) is a **process** state transition (unnamed form), not an entity transition — no bound entity is involved.

**`Uploaded`** — set by the final `TRANSITION "Uploaded"` (step 13), which is the only `TRANSITION` executed and therefore the latest (and only) one to set the process state. Before it, the process state was `none` (no earlier `TRANSITION "<state>"` runs in this program).

## Additional questions

- **How many times does `DELEGATE upload` run?** Twice — once per iteration of `LOOP:retry` (step 2, giving `rejected`; step 6, giving `accepted`). The loop then exits via `BREAK` before a third iteration would start.
- **What does the `BREAK` end?** It ends only the innermost enclosing loop, `LOOP:retry`, which is nested *inside* the first `FORK` branch — per the spec, this is valid because the loop being left is inside the same branch as the `BREAK` (as opposed to a loop outside the branch, which would make the `BREAK` INVALID under V3). It does **not** end the `FORK`, the other branch (`DELEGATE docs`), or the whole execution; it simply completes branch 1 (since the loop was the branch's last statement), after which the branch is done and `JOIN` can proceed once branch 2 also finishes.
