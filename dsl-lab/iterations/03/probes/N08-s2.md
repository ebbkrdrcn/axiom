# Execution of the program

```text
LOOP:outer
  DELEGATE batch
  LOOP:inner
    DELEGATE item
    VERIFY item
    WHEN item.accepted
      → BREAK
  VERIFY batch
  WHEN batch.accepted
    → BREAK
  WHEN batch.rejected
    → TRANSITION "Retry"
EMIT report
```

## 1. Validity verdict

**VALID.**

Check against V1–V12:

- V1: indentation is consistent (LOOP body, nested LOOP body, WHEN flows all properly nested and aligned); every line matches a statement form.
- V2: both `BREAK`s are inside a `LOOP` (the first inside `LOOP:inner`, the second inside `LOOP:outer`).
- V3: no `FORK`, so not applicable.
- V4: the only `→` items are under `WHEN` (`→ BREAK`, `→ BREAK`, `→ TRANSITION "Retry"`); no `FALLBACK` misuse.
- V5: no `AUTO`.
- V6: `WHEN item.accepted` — `VERIFY item` can establish `accepted`/`rejected`, so `accepted` is declared. `WHEN batch.accepted` and `WHEN batch.rejected` — `VERIFY batch` can establish both. All conditions refer to declared outcomes.
- V7: no `HITL`.
- V8: no `FALLBACK` is present at all, so nothing to check.
- V9: no `FORK`/`JOIN`.
- V10: no `FORK`.
- V11: no bindings.
- V12: no bindings, no `TRANSITION <name>` (only process-state `TRANSITION "Retry"`).

No rule is broken → **VALID**.

## 2. Execution trace

Events given: `VERIFY item` results, in order: `rejected`, `accepted`, `accepted`.
`VERIFY batch` results, in order: `rejected`, `accepted`.

```trace
0. validate -> VALID
1. DELEGATE batch -> done
2. DELEGATE item -> done
3. VERIFY item -> outcome item.rejected
4. WHEN item.accepted -> false: skip
5. LOOP:inner -> loop again
6. DELEGATE item -> done
7. VERIFY item -> outcome item.accepted
8. WHEN item.accepted -> true: run flow
9. BREAK -> break
10. VERIFY batch -> outcome batch.rejected
11. WHEN batch.accepted -> false: skip
12. WHEN batch.rejected -> true: run flow
13. TRANSITION "Retry" -> state = "Retry"
14. LOOP:outer -> loop again
15. DELEGATE batch -> done
16. DELEGATE item -> done
17. VERIFY item -> outcome item.accepted
18. WHEN item.accepted -> true: run flow
19. BREAK -> break
20. VERIFY batch -> outcome batch.accepted
21. WHEN batch.accepted -> true: run flow
22. BREAK -> break
23. EMIT report -> done
24. (end of program) -> end
```

Notes on the trace:

- Entering `LOOP:outer` and, within each outer iteration, entering `LOOP:inner` for the first time writes no line (per the trace rules); only a restart of a loop body is logged as `loop again`.
- At step 9, `BREAK` leaves only `LOOP:inner` (the innermost loop); execution continues with `VERIFY batch`, the statement after `LOOP:inner`.
- At step 12, the `WHEN batch.rejected` is the last statement of the outer loop body, so the loop restarts (step 14), per rule 5 / the `WHEN` rule that a `WHEN` at the end of a loop body causes the loop to start again rather than falling through to the code after the loop.
- At step 22, `BREAK` leaves `LOOP:outer`. Because `BREAK` skips the remaining statements of the current iteration (including later `WHEN`s), the second-iteration `WHEN batch.rejected` is never reached/checked and produces no trace line.
- Execution continues after the outer loop with `EMIT report` (step 23), then ends normally (step 24).
