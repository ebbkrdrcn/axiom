# Validity check of the five snippets

## Snippet A — INVALID

```
1  LOOP:deploy
2    DELEGATE deploy
3    VERIFY deploy
4    WHEN deploy.accepted
5      → BREAK release
```

**Broken rule:** V1 (line 5).

`BREAK` is a keyword that stands alone (`"BREAK" , NL` — grammar rule `simple`); it takes no argument and no name (dsl.md, **BREAK**: "`BREAK` takes no name"). `BREAK release` matches no statement form in **Lines and statements**, so it is INVALID under V1. This is in fact the exact example V1 itself gives (`for example `BREAK release``).

## Snippet B — VALID

```
1  FORK
2    → LOOP:retry
3        DELEGATE upload
4        VERIFY upload
5        WHEN upload.accepted
6          → BREAK
7    → DELEGATE docs
8  JOIN
```

No rule is broken:

- `FORK` has two branches (`→ LOOP:retry …` and `→ DELEGATE docs`), satisfying V9 (at least two branches; a `JOIN` follows and corresponds to this `FORK`).
- The `BREAK` at line 6 is inside `LOOP:retry`, and that `LOOP` is itself nested inside the same `FORK` branch (branch 1). Per the `FORK` table and V3, a `BREAK` is INVALID only when the `LOOP` it would leave is *outside* the branch; here the loop is inside the branch, so it is valid (this is precisely the worked example given under **FORK**, "Example of a valid `BREAK` inside a branch").
- `WHEN upload.accepted` refers to an outcome (`accepted`) that a `VERIFY upload` in the same branch establishes — a legitimate subject/outcome pair (V6 satisfied), and it is being tested in the same branch that produces it, not after a `JOIN` for a different branch's outcome, so V10 does not apply.
- Indentation follows the allowed nesting (`FORK` → `→` branch → `LOOP` as the branch's own child → loop body → `WHEN` → `→ BREAK`), satisfying V1/V4.

This snippet is identical to the example in dsl.md's **FORK** section, which is presented there as valid.

## Snippet C — INVALID

```
1  FORK
2    → VERIFY api
3    → VERIFY ui
4  WHEN api.accepted
5    → EMIT api-report
```

**Broken rule:** V10 (line 4).

`FORK` starts two concurrent branches; `VERIFY api` (branch 1) establishes the outcome `api.accepted`/`api.rejected`. There is no `JOIN` between the `FORK` and the `WHEN api.accepted` at line 4 — the `WHEN` tests a subject that a branch of the `FORK` in the same flow establishes, with no intervening `JOIN` of that `FORK`. Per V10 this is INVALID, because on the program text alone the branch's outcome cannot be guaranteed available (and the outcome could be established at any time — the `WHEN` might run concurrently with, or before, the branch that establishes it). The fix would be to add `JOIN` before the `WHEN`, as shown in dsl.md's own `JOIN` example.

(V9 is not broken: the `FORK` has two branches and needs no `JOIN` to be valid on its own — `JOIN` is optional per the **Quick reference** — but the *absence* of a `JOIN` is exactly what triggers V10 once a later `WHEN` depends on a branch outcome.)

## Snippet D — VALID

```
1  HITL:release[approved, rejected]("Release now?")
2  WHEN release.approved
3    → EMIT release
```

No rule is broken:

- `HITL:release[approved, rejected](...)` is a decision `HITL` with a non-empty, non-repeating answer list, and the name `release` is used by no other `HITL` or `VERIFY` (V7 satisfied).
- It has no `AUTO`, so V5 does not apply (V5 only constrains `AUTO`, which is absent here).
- It has no `FALLBACK`; a `FALLBACK` is optional (`[ fallback ]` in the grammar), so its absence is not a violation. If the response is insufficient/unavailable, execution simply ends (dsl.md, **Failures**).
- `WHEN release.approved` tests `approved`, which is one of the declared answers of `HITL:release[...]`, so it refers to a subject/outcome the program can produce (V6 satisfied).
- The `WHEN` needing no `rejected` branch is fine — "no else" is explicit in the spec; an untested answer is not an error.

## Snippet E — INVALID

```
1  t1:Task = TASK-0100
2  VERIFY t1
3  WHEN t1.accepted
4    → TRANSITION t2 "Review"
```

**Broken rule:** V12 (line 4).

The binding section binds only `t1` (`t1:Task = TASK-0100`); no name `t2` is ever bound anywhere in the program. `TRANSITION t2 "Review"` at line 4 therefore uses a name that is not bound, which is exactly what V12 forbids ("`TRANSITION <name> "<status>"` uses a name that is not bound"). This mirrors the INVALID example in dsl.md's **Entities** section (`TRANSITION t2 "Done"` on an unbound name).

No other rule is broken: the binding itself (line 1) is well-formed and at the top, unindented (V11 satisfied); `VERIFY t1` and `WHEN t1.accepted` correctly use the bound name `t1` and a declared outcome (`accepted`, from `VERIFY`, satisfying V6). The only defect is the reference to the never-bound `t2` in the `TRANSITION`.
