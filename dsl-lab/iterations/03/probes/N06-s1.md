## 2. Execution trace

Fixture read for the binding: `docs/tasks/TASK-0100.md` has `id: TASK-0100`, `type: Task`, `status: InProgress`, `adr: ADR-0100`; it has a `Description` section and an `Acceptance Criteria` section with two items (`Notes` is optional and absent). Against the Task Template this is structurally valid, so the binding succeeds.

`VERIFY t1` is evaluated against the Task Definition's verification criteria (every Acceptance Criteria item satisfied, with evidence named). The event states both items' tests pass, so `t1.accepted` is established.

`DELEGATE polish` then rewrites only the `Description` section of `TASK-0100.md`. At the time of this change the Task's status is still `InProgress` (no `TRANSITION` has run yet), and the Task Definition permits delegated work to edit `Description` while the Task is `Todo`, `InProgress` or `Debugging` — so this data change is itself permitted. However, it is a change to the entity's data made by something other than a `TRANSITION`, and it happens **after** the `VERIFY t1` that established `accepted`.

The Task Definition's transition `InProgress → Review` requires the precondition `verified: accepted`, which per `dsl.md` holds only if "the entity's data has not changed since that `VERIFY`, **other than by** `TRANSITION <name>`." Because `DELEGATE polish` changed the Description after the `VERIFY`, that precondition no longer holds when `TRANSITION t1 "Review"` is reached. The transition therefore fails (its criteria are not satisfied), and — since it fails — its attached `FALLBACK` runs instead of the transition being performed.

The fallback flow runs `TRANSITION "Reverify"` (a **process**-state transition, not an entity transition — it always succeeds and simply sets the current process state), then `STOP`, which ends the whole execution immediately.

```trace

1. t1:Task = TASK-0100 -> bound TASK-0100
2. VERIFY t1 -> outcome t1.accepted (evidence: item 1: "after 5 failed attempts within 10 minutes, the next attempt returns HTTP 429" — test passes; item 2: "the limit resets after 10 minutes without a failed attempt" — test passes)
3. DELEGATE polish -> done
4. TRANSITION t1 "Review" -> failed: precondition "verified: accepted" no longer holds (t1's data changed via DELEGATE polish since the VERIFY, and the change was not a TRANSITION); fallback
5. TRANSITION "Reverify" -> state = "Reverify"
6. STOP -> stop
```

No `(end of program) -> end` line is written, because execution ends via `STOP`, not by falling off the end of the program (rule 10 does not apply here).
