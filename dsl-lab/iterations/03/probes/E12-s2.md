# Validity Check — Snippets A–D

## Snippet A

```
1  t1:Task = TASK-0100
2  LOOP:work
3    a1:ADR = t1.adr
4    VERIFY t1
5    WHEN t1.accepted
6      → BREAK
```

**Verdict: INVALID**

**Rules broken: V11**

- Line 3 (`a1:ADR = t1.adr`) is a binding. Per **Binding** in `dsl.md`, "Bindings are written at the top of the program, before every other statement, without indentation," and V11 states a binding is INVALID if "a binding is indented, or follows a statement that is not a binding." Here the binding is indented (nested inside `LOOP:work`) and it follows `LOOP:work`, which is not itself a binding. This is exactly the case the spec illustrates as invalid: "A binding inside a scope (V11)" (`entity-model.md`, *Invalid Usage*; `dsl.md` example under **Entities**).

No other rule is broken: `VERIFY t1` and `WHEN t1.accepted → BREAK` are ordinary, well-formed statements, and `BREAK` is correctly inside a `LOOP` (V2/V3 do not apply).

## Snippet B

```
1  a1:ADR = t1.adr
2  t1:Task = TASK-0100
3  VERIFY a1
```

**Verdict: INVALID**

**Rules broken: V11**

- Line 1 (`a1:ADR = t1.adr`) is a relation binding whose source name is `t1`. Per the **Binding** form, `<name>:<Type> = <bound-name>.<relation>` requires the left-hand entity to already be bound "on an earlier line." Here `t1` is not bound until line 2, i.e., *after* the relation binding that depends on it. V11 explicitly lists this as INVALID: "a binding is indented, or follows a statement that is not a binding, or binds a name that is already bound, or **its relation starts from a name not bound on an earlier line**." Line 1 violates the last clause.

Both lines are (individually) unindented bindings preceding all non-binding statements, so no other clause of V11 is triggered, and no other rule is broken.

## Snippet C

```
1  t1:Task = TASK-0102
2  TRANSITION t1 "Done"
```

**Verdict: VALID**

No validity rule (V1–V12) is broken:

- The binding on line 1 is unindented, is the first statement, and binds `t1` exactly once — it satisfies **Binding**/V11.
- `TRANSITION t1 "Done"` on line 2 uses the bound name `t1`, so V12 ("`TRANSITION <name> "<status>"` uses a name that is not bound") does not apply.
- No `WHEN`, `HITL`, `FORK`/`JOIN`, `BREAK`, or `AUTO` appears, so V2–V10 are vacuously satisfied. There is no `FALLBACK`, which is optional (the grammar shows `[fallback]`), so V4/V8 do not apply.

This program is well-formed even though it will **fail at execution time**: `TASK-0102` is `Todo`, and the Task Definition's transition table (`docs/types/task/definition.md`) does not declare `Todo → Done` (only `Todo → InProgress`, `InProgress → Review`, `InProgress → Debugging`, `Debugging → InProgress`, `Review → InProgress`, `Review → Done`). Per **`TRANSITION` on an entity** / **Failures** in `dsl.md`, an undeclared change simply fails the `TRANSITION` (its `FALLBACK` would run, or, having none, execution ends as with `STOP`). This is explicitly distinguished from invalidity: "A transition that the Definition does not permit ... is not INVALID: the program is well-formed, and the transition fails when it is executed" (`dsl.md`, **Entities**; mirrored in `entity-model.md`, *Invalid Usage*, "Undeclared transition").

## Snippet D

```
1  t1:Task = TASK-0100
2  HITL:t1[approved, rejected]("Done?")
3  TRANSITION t2 "Done"
```

**Verdict: INVALID**

**Rules broken: V12 (twice — line 2 and line 3)**

- Line 2: `HITL:t1[...]` reuses the name `t1`, which was already bound as an entity on line 1. V12: "... or a bound name is used as a `HITL` name." This is also stated in **Binding Rules** (`entity-model.md`): "A bound name must not be used as a `HITL` name," and in `dsl.md` **Binding**: "A bound name MUST NOT also be used as a `HITL` name (V12)."
- Line 3: `TRANSITION t2 "Done"` refers to `t2`, a name that was never bound anywhere in the program (only `t1` is bound). V12: "`TRANSITION <name> "<status>"` uses a name that is not bound." This mirrors the explicit invalid example in `dsl.md`: "An entity `TRANSITION` on a name that is not bound (V12): `TRANSITION t2 "Done"`."

No other rules are implicated: there is only one `HITL`, so the "two `HITL` statements use the same name" clause of V7 does not apply, and no name is shared between a `HITL` and a `VERIFY`.
