# Execution Trace: Release Notes Approval Flow

## Program

```text
DELEGATE release-notes
HITL("Approve the release notes?")
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
TRANSITION "Published"
EMIT release-notes
```

## Reading of the structure (per specification)

- `DELEGATE release-notes` assigns the release-notes work to an actor. It does not itself declare success, completion, or acceptance (spec: "`DELEGATE` does not mean that the work is correct, complete, or accepted").
- `HITL("Approve the release notes?")` establishes a human decision boundary. The human's response, if usable, determines the subsequent flow (spec: "The human response may determine the subsequent flow").
- The nested block:
  ```text
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
  ```
  is the fallback flow attached to this `HITL`. Per the specification, `FALLBACK` "defines the flow to use when an expected response is unavailable or insufficient," and "is used only when the expected response cannot be used to continue the normal flow." The two `→` entries inside the `FALLBACK` block (`TRANSITION "Blocked"` and `STOP`) are sequential statements of that one fallback flow, executed in order — the same list-of-statements convention used for a `WHEN` flow (spec, "Conditional Flow": "The statements following `→` belong to the conditional flow").
- There is no `→` entry at the `HITL` level for a "usable response" case. By the specification's own contrast — "It [FALLBACK] does not mean 'execute this flow after the normal flow'... used only when the expected response cannot be used to continue the normal flow" — the implication is that when the response *can* be used to continue the normal flow, execution simply proceeds to the next statement in the surrounding scope, i.e. `TRANSITION "Published"` followed by `EMIT release-notes`. The specification does not spell out an explicit "approved" arrow, so this continuation-to-surrounding-flow behavior is inferred rather than stated outright.
- `STOP` "terminates execution... No subsequent statement is executed after `STOP`," so once the fallback path is taken, `TRANSITION "Published"` and `EMIT release-notes` never run, in any run.

## Explicit assumptions (the specification does not determine these)

1. **DELEGATE is non-blocking with respect to the next statement.** The spec states that only `WAIT` suspends execution until an event/response is available; `DELEGATE` merely assigns responsibility. No `WAIT` or `VERIFY` appears between `DELEGATE release-notes` and `HITL(...)`, so per "Statements execute in declaration order unless an explicit control construct changes the flow," execution moves straight from `DELEGATE` to `HITL`. The spec does not state whether the runtime otherwise ensures the delegated artifact exists before `HITL` asks about it — I assume the release notes are available by the time the human is asked to approve them, since the scenario presupposes something to approve.
2. **What counts as a "usable" response to `HITL`.** The spec defines `HITL`/`FALLBACK` only in terms of whether a response "can be used to continue the normal flow" — it does not enumerate an acceptance grammar for HITL replies. I treat a reply as usable only if it constitutes an unambiguous approve/reject decision on the stated question ("Approve the release notes?"). A reply that is neither an approval nor a rejection (e.g., a deferral) is "insufficient" per `FALLBACK`'s own wording ("unavailable **or insufficient**").
3. **How "never responds" becomes an unavailable response.** The specification gives `HITL` no timeout, polling, or escalation mechanism (consistent with its principle that the DSL "does not prescribe... the UI or communication mechanism"). It does not say how or when the runtime concludes that a response will never arrive. I assume the runtime (by some unspecified mechanism outside the DSL, e.g. an operational timeout) at some point determines the expected response is unavailable, which is what licenses entry into `FALLBACK`. Until that determination is made, the specification implies execution remains suspended (comparable to `WAIT`'s "suspends execution until... available"), since nothing in the DSL causes it to proceed otherwise.
4. **The two `→` lines under `FALLBACK` are sequential, not concurrent branches.** `FORK` is the only construct defined to start independent concurrent flows from multiple `→` entries; `FALLBACK` is not `FORK`. I therefore read `TRANSITION "Blocked"` and `STOP` as one ordered flow (matching how a `WHEN` flow's multiple `→` statements are read), not as two parallel branches.
5. **No rejection case is defined in this program.** The program only contains a `FALLBACK` (for unusable/unavailable responses); it defines no explicit branch for an outright "rejected" decision. Under assumption 2, an unambiguous rejection would also be a "usable" response in the sense that it is a determinate decision — but since the program supplies no `WHEN`/flow for that outcome, the specification does not determine what happens in that case, and none of Runs A/B/C require it (Run A is an approval, Runs B/C fall under `FALLBACK` for other reasons), so it is not resolved further here.

## Run A — human responds "Approved."

| Step | Statement executed | Effect |
|---|---|---|
| 1 | `DELEGATE release-notes` | Work of producing release notes is assigned to an actor. No claim of correctness, completeness, or acceptance is made (spec: "does not mean that the work is correct, complete, or accepted"). |
| 2 | `HITL("Approve the release notes?")` | A human decision boundary is established; execution is suspended pending a response. |
| 3 | *(response received: "Approved.")* | Under Assumption 2, this is an unambiguous approval — a determinate decision usable to continue the normal flow. Per spec, `FALLBACK` "is used only when the expected response cannot be used to continue the normal flow" — that is not the case here, so `FALLBACK` is **not** entered. |
| 4 | `TRANSITION "Published"` | Execution continues in the surrounding (post-`HITL`) flow. The process state changes to `Published`. Per spec, this is a state change only — it does not itself mean any work is performed. |
| 5 | `EMIT release-notes` | The release-notes artifact is produced as an externally meaningful output. The DSL does not prescribe how it is created, stored, or transmitted. |

End of Run A. No further statements remain.

## Run B — human never responds

| Step | Statement executed | Effect |
|---|---|---|
| 1 | `DELEGATE release-notes` | Same as Run A: work assigned, no completion/acceptance implied. |
| 2 | `HITL("Approve the release notes?")` | Human decision boundary established; execution suspends, awaiting a response. |
| 3 | *(no response ever arrives)* | Per spec, `HITL` "must not be silently replaced by an agent decision" and "does not make a decision" itself; nothing in the DSL causes execution to proceed on its own. Under Assumption 3, the runtime at some point determines the expected response is unavailable. This is exactly the condition `FALLBACK` is defined for: "used only when the expected response cannot be used to continue the normal flow." |
| 4 | `FALLBACK` flow entered | The response cannot be used to continue the normal flow, so control transfers into the fallback flow attached to this `HITL`. |
| 5 | `TRANSITION "Blocked"` | First statement of the fallback flow: process state changes to `Blocked`. Per spec, `FALLBACK` "does not authorize the agent to invent a replacement decision" — this is not treated as an approval or rejection, only as the process's own explicit handling of the unresolved situation. |
| 6 | `STOP` | Execution terminates. Per spec, "No subsequent statement is executed after `STOP`." |

`TRANSITION "Published"` and `EMIT release-notes` are **never executed** in Run B.

## Run C — human responds "I haven't had time to look yet."

| Step | Statement executed | Effect |
|---|---|---|
| 1 | `DELEGATE release-notes` | Same as Run A: work assigned, no completion/acceptance implied. |
| 2 | `HITL("Approve the release notes?")` | Human decision boundary established; execution suspends, awaiting a response. |
| 3 | *(response received: "I haven't had time to look yet.")* | A response is received, but under Assumption 2 it is not an approval or rejection of the release notes — it does not answer the question asked. This makes it an **insufficient** response in the sense of `FALLBACK`'s own definition ("unavailable **or insufficient**"), and it "cannot be used to continue the normal flow." |
| 4 | `FALLBACK` flow entered | Because the response is insufficient to continue normally, the fallback flow attached to this `HITL` is used. Per spec, `FALLBACK` "does not authorize the agent to invent a replacement decision" — the agent must not interpret this reply as either an approval or a rejection. |
| 5 | `TRANSITION "Blocked"` | Process state changes to `Blocked`. |
| 6 | `STOP` | Execution terminates; no subsequent statement runs. |

`TRANSITION "Published"` and `EMIT release-notes` are **never executed** in Run C, for the same structural reason as Run B (an unusable response routes into `FALLBACK`, which ends in `STOP`), even though the *cause* of unusability differs — response never arrived (B) versus response arrived but did not resolve the question (C).

## Summary

| Run | Response | Outcome path | Final state |
|---|---|---|---|
| A | "Approved." | Normal flow continues past `HITL` | `Published`, release-notes emitted |
| B | (none, ever) | `FALLBACK` (response unavailable) | `Blocked`, execution stopped |
| C | "I haven't had time to look yet." | `FALLBACK` (response insufficient) | `Blocked`, execution stopped |

Runs B and C reach the identical concrete effect (`TRANSITION "Blocked"` then `STOP`), but for distinct reasons under the specification's own vocabulary: Run B is the "unavailable" case of `FALLBACK`'s trigger condition, and Run C is the "insufficient" case — a reply exists but does not constitute a usable approve/reject decision.
