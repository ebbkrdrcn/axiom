# Trace of the `build` LOOP

## Program under analysis

```text
LOOP:build
  DELEGATE build
  VERIFY build
  WHEN build.accepted
    → BREAK
EMIT build-report
```

Given: in every iteration, `VERIFY build` establishes the outcome `rejected`.

## Structural reading (from the Syntax section)

- `EMIT build-report` is written at the same indentation as `LOOP:build` (column 0), not indented under it. Per **Scope** ("Indented statements belong to the preceding scoped construct"), `EMIT build-report` is therefore **not** part of the loop body — it is a separate top-level statement that follows the `LOOP:build` construct in the declared **Flow**.
- The loop body consists of exactly three statements, in order: `DELEGATE build`, `VERIFY build`, `WHEN build.accepted → BREAK`.
- Per **Flow**, statements execute in declaration order "unless an explicit control construct changes the flow." `BREAK` is the only construct in this program capable of ending the loop (`STOP` does not appear). Per **LOOP**, the loop "continues until `BREAK`, `STOP`, or another explicit control flow terminates it," and no particular number of iterations is implied.
- The specification does not explicitly describe what happens when the end of a loop body is reached without a terminating construct having fired. I assume — as the natural reading of "repeated execution scope" plus "continues until BREAK/STOP/other explicit terminator" — that reaching the end of the body without termination causes control to return to the top of the loop body (i.e., a new iteration begins with `DELEGATE build` again). This is an assumption, not something stated verbatim in the spec.
- There is no `WHEN build.rejected` branch. Per **WHEN**, "Multiple `WHEN` constructs may describe different outcomes of the same process state," but nothing requires that every outcome have a corresponding `WHEN`. Since only `build.accepted` is handled, the `rejected` outcome has no explicit handler in this program; the spec does not state what should happen in that case beyond the fact that `WHEN` "does not itself perform work, change state, delegate work, or produce an artifact" when its condition is not satisfied. I assume this means: when the condition is not satisfied, the conditional flow simply does not execute, and execution falls through to whatever follows (here, the end of the loop body / next iteration).

## Iteration 1

1. **`DELEGATE build`** — Work described as "build" is assigned to another actor. Per **DELEGATE**, this "does not mean that the work is correct, complete, or accepted" — it only records that responsibility for the work has been assigned. The DSL does not prescribe how or by whom the work is actually carried out.
2. **`VERIFY build`** — The delegated result is evaluated against applicable acceptance criteria. Per the task's stipulation, this evaluation establishes the outcome `build.rejected` (not `build.accepted`). Per **VERIFY**, "Completion of delegated work is not equivalent to successful verification," and `VERIFY` "must not silently modify the result it evaluates" — it only records an outcome.
3. **`WHEN build.accepted → BREAK`** — The condition `build.accepted` is checked against the established state. Since the outcome from step 2 is `rejected`, not `accepted`, this condition is **not satisfied**. Per **WHEN**, the flow following `→` (`BREAK`) is therefore **not executed**.
4. End of the loop body is reached with no `BREAK` or `STOP` having fired. Per **LOOP**, the loop has not been terminated, so (per the assumption above) control returns to the top of the loop body. Iteration 1 ends without exiting the loop.

`EMIT build-report` is **not reached** during iteration 1, because it lies outside the loop and the loop has not exited.

## Iteration 2

The loop body runs again, identically to iteration 1, since the same precondition holds (`VERIFY build` again establishes `rejected`):

1. **`DELEGATE build`** — The build work is (re-)delegated. The spec does not distinguish this from the first delegation mechanically; it is simply a repeated occurrence of the same statement, since the loop scope re-executes its body.
2. **`VERIFY build`** — Evaluation again establishes the outcome `build.rejected`.
3. **`WHEN build.accepted → BREAK`** — The condition is again not satisfied (outcome is `rejected`), so `BREAK` again does not execute.
4. End of loop body reached again with no termination; per the same assumption, control returns to the top of the loop for a further iteration.

`EMIT build-report` is **not reached** during iteration 2 either, for the same reason as iteration 1: the loop has not exited.

## Whether and when `EMIT build-report` executes

- `EMIT build-report` is positioned after the `LOOP:build` construct, not inside it, so per **Flow** it only executes once the `LOOP` construct as a whole finishes.
- The only way this particular loop finishes is via `BREAK` (there is no `STOP` in this program), and per **BREAK** / **WHEN**, `BREAK` only executes when `build.accepted` is satisfied.
- In both iteration 1 and iteration 2, `VERIFY build` establishes `rejected`, so `build.accepted` is never satisfied and `BREAK` never fires. Consequently:
  - **`EMIT build-report` is not executed during the first two iterations.**
  - More generally, given the stated condition that "in every iteration, `VERIFY build` establishes the outcome `rejected`," `build.accepted` is never satisfied at any iteration, so `BREAK` never fires and the loop never exits under this program's own logic. Under this hypothesis, `EMIT build-report` would **never be executed**, not just in the first two iterations — the specification gives no other construct in this program (no `STOP`, no other `WHEN`, no outer control) that could cause the loop to end or `EMIT build-report` to run.
- This conclusion follows only from the DSL's stated semantics (`WHEN` gates `BREAK`; `LOOP` persists absent `BREAK`/`STOP`; `EMIT` is a plain sequential statement outside the loop) and from the task's own stipulation that verification is rejected on every iteration; it does not rely on any assumption about *why* verification keeps failing or on any retry/backoff mechanism, since the spec explicitly states that operations like `DELEGATE` and `VERIFY` "do not prescribe implementation."

## Explicit assumptions made (spec does not determine these)

1. Reaching the end of a `LOOP` body without `BREAK`/`STOP` causes the loop to begin a new iteration from the top of its body. The spec states loops "continue until" terminated but does not spell out the exact re-entry mechanics.
2. When a `WHEN` condition is not satisfied and no other `WHEN` in the same construct matches (here, no `WHEN build.rejected` exists), execution simply proceeds with no additional effect, falling through to the next statement in the enclosing scope (here, the end of the loop body / next iteration). The spec confirms `WHEN` "does not itself perform work" when its flow doesn't run, but does not explicitly describe control flow "falling through" in this exact sense.
3. `EMIT build-report`'s indentation (column 0, same as `LOOP:build`) places it outside the loop's scope, as a statement that runs after the loop construct completes rather than after each iteration. This follows directly from the **Scope** rule but is worth stating explicitly since the visual proximity to the loop could otherwise be misread as "part of it."
