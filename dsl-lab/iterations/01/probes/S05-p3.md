# S05 Probe Answer

## Snippet A

```text
HITL("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

**Verdict: INVALID**

**Rule cited (AUTO section):**

> `AUTO` is not a control-flow container.
> It does not contain `WHEN`, `→`, or an arbitrary flow.
> Uncertainty is not a DSL condition, state, variable, or keyword.

The spec then gives this *exact* construction as its own worked example of invalid syntax:

```text
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

and states directly beneath it: "the following is invalid."

**What is wrong:** `AUTO` is defined as a resolution mode for a decision ("resolve automatically when sufficiently determined; otherwise require human input") — it is not a scope that can hold nested statements. Snippet A nests a `WHEN`/`→` flow underneath `AUTO`, treating `decision.uncertain` as if it were a DSL condition/state that `WHEN` could branch on. The spec explicitly forbids both things: `AUTO` cannot contain `WHEN`/`→`, and `uncertain` is not a condition, state, variable, or keyword the DSL exposes for branching. Per the spec, "The DSL runtime determines uncertainty as part of automatic decision resolution" — it is not something the process author can test with `WHEN`. So this snippet is invalid on two independent, spec-cited grounds, matching the spec's own counter-example almost verbatim.

(Secondary observation, not the primary defect: the leading `HITL("Approve release?")` is a bare statement with no `FALLBACK` or consuming construct attached before `AUTO` begins; the spec does not say two adjacent top-level statements like this are illegal by themselves, so I do not count this as a separate violation — the nested `WHEN` under `AUTO` is the clear, spec-cited defect.)

## Snippet B

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

**Verdict: INVALID, under the reading that this snippet is complete/standalone as shown (no enclosing `LOOP`) — see assumption below.**

**Rule cited (BREAK section):**

> `BREAK` — Exits the current `LOOP`.
> `BREAK` does not terminate the entire execution.
> `BREAK` may only exit a loop scope.

**What is wrong:** `BREAK`'s only defined behavior is to exit an enclosing `LOOP` scope ("may only exit a loop scope"). Snippet B, as written, contains no `LOOP:<name>` construct anywhere — the four statements appear at a single top level with `WHEN`'s `→` branch nested one level under it. There is therefore no loop scope in this snippet for `BREAK` to exit, so the `BREAK` statement has no valid target and cannot be executed as specified.

The `DELEGATE`/`VERIFY`/`WHEN` portion itself is fine and in fact mirrors the spec's own VERIFY example structure (`VERIFY implementation` → `WHEN implementation.accepted/rejected` → an action), so that part is not in question.

**Explicit assumption (spec does not fully determine this):** The spec never states what happens, or whether it's even a defect, when a `BREAK` statement is displayed without a visible surrounding `LOOP` in the fragment shown. Two readings are possible:
1. The snippet is a complete, self-contained program — under this reading, which I adopt as my primary answer, `BREAK` is invalid because no loop scope exists at all.
2. The snippet is an excerpt assumed to be nested inside a `LOOP:<name>` block that simply isn't shown (this is exactly how the spec's own VERIFY example is written — it uses `BREAK` after `WHEN implementation.accepted` with no visible `LOOP` wrapper either). Under this reading, the snippet would be VALID, since the missing `LOOP` is just an artifact of showing a code excerpt rather than a full program, and `implementation.rejected` → `BREAK` would simply exit whatever retry loop the delegate/verify pair lives in.

Since the task presents Snippet B as a standalone snippet (not explicitly framed as an excerpt of a larger flow, unlike the spec's own inline example which appears mid-prose directly under the `VERIFY` heading as an illustration), I default to reading #1 and call it INVALID for lack of an enclosing loop scope. But this determination rests on an assumption the spec text does not resolve — namely, whether a `BREAK` shown without a visible `LOOP` ancestor should be judged on the snippet as literally scoped, or treated as an excerpt of unshown context. I flag this explicitly rather than silently picking one reading.
