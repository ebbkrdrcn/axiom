# S01 — Probe Answer

## DSL

```text
DELEGATE implementation
VERIFY implementation

HITL("Merge this change?")
  AUTO

WHEN merge.approved
  → TRANSITION "Merged"

WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

The specification text does not fully determine several choices made above. Each is listed with the assumption taken.

1. **How `AUTO` and `HITL` combine syntactically.** The spec states (HITL section): "`HITL` must not be silently replaced by an agent decision unless the surrounding definition explicitly permits automatic resolution through `AUTO`." It never shows the concrete syntax for that permission. I assumed nesting a bare `AUTO` statement under the `HITL` statement's scope expresses "this human decision boundary permits automatic resolution first." This does not violate the `AUTO` constraint that "`AUTO` is not a control-flow container" and "does not contain `WHEN`, `→`, or an arbitrary flow," since the `AUTO` here has no children — it is itself nested under `HITL`, not the other way around. But the spec gives no worked example of this combination, so the direction and syntax of nesting is my own inference, not something the spec fixes.

2. **How `WHEN` refers to the outcome of a `HITL`/`AUTO` decision.** The spec demonstrates outcome-referencing only for `VERIFY`, via the pattern `VERIFY implementation` → `WHEN implementation.accepted` / `WHEN implementation.rejected`. It never shows an equivalent for a decision resolved by `HITL`/`AUTO`. I assumed the same dot-notation convention applies, and invented the identifier `merge` (yielding `merge.approved` / `merge.declined`) to name the decision, since the requirement's decision concerns merging. The spec does not license or define this identifier — it is a naming choice, not a spec-derived term.

3. **No explicit `REQUIRE`.** The requirement text names no precondition (context, repository access, etc.), so I did not introduce a `REQUIRE` statement. This is a direct reading of the requirement rather than an uncertain assumption, but noted since other DSL examples in the spec often pair `DELEGATE` with a preceding `REQUIRE`.

4. **No branch for a failed/rejected verification.** The spec's own example shows `VERIFY implementation` typically paired with both `WHEN implementation.accepted` and `WHEN implementation.rejected` (the latter leading to `DELEGATE correction`). The task's requirement text, however, only describes what happens after verification succeeds — it says nothing about what should occur if verification itself fails. I left this path undefined rather than inventing behavior (e.g., a correction loop) that the requirement never specified. This is a gap in the requirement, not something the DSL spec resolves.

5. **Literal strings taken as given.** `"Merge this change?"`, `"Merged"`, and `"Rework"` are used verbatim as the string literal and state identifiers from the requirement, following the spec's `String` syntax rule (`"<string>"`) and the `TRANSITION "Code Review"` example. No assumption of alternate phrasing was made.

6. **Identical outcome vocabulary regardless of resolution path.** I assumed that whether the merge decision is resolved automatically (via `AUTO`) or by a human (via `HITL`), the resulting outcome is expressed through the same `merge.approved` / `merge.declined` identifiers consumed by `WHEN` — mirroring how the spec treats `VERIFY` outcomes as implementation-independent ("The DSL does not prescribe how ... remains independent of specific runtime mechanisms"). The spec does not explicitly confirm that `AUTO`-resolved and `HITL`-resolved decisions share one outcome namespace; this is inferred from the general semantic-independence principle, not stated directly for this case.

7. **No `LOOP`, `FORK`, or `WAIT` used.** The requirement describes a single linear sequence with one decision point and no indication of repetition, concurrency, or waiting on an external event beyond the human/automatic decision itself (which `HITL`/`AUTO` already encapsulate). No assumption was needed here beyond a literal reading of the requirement.
