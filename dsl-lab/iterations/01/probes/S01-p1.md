```text
DELEGATE implementation
VERIFY implementation

HITL("Merge this change?")
  → AUTO

WHEN merge.approved
  → TRANSITION "Merged"

WHEN merge.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Combining `AUTO` with `HITL`**: The specification never gives an explicit syntax for the case "let the agent decide automatically when the decision is clearly determined, otherwise ask a human." The only textual link between the two constructs is: *"`HITL` must not be silently replaced by an agent decision unless the surrounding definition explicitly permits automatic resolution through `AUTO`."* I interpreted this as meaning `AUTO` must be attached to the specific `HITL` it is allowed to short-circuit, and I reused the exact attachment syntax shown for `FALLBACK` (`HITL("<message>") → FALLBACK → <flow>`) to attach `AUTO` the same way: `HITL("Merge this change?") → AUTO`. This is an assumption — the spec only demonstrates this arrow-attachment pattern for `FALLBACK`, not for `AUTO`.

2. **What happens when `AUTO` cannot determine the decision**: I assumed that in this attachment pattern, failing to reach a sufficiently determined automatic decision simply falls back to `HITL`'s own default behavior (asking the human the given message), with no separate `FALLBACK` block needed. The spec does not explicitly state this fallback path; it only defines `AUTO`'s semantics in prose ("resolve automatically when sufficiently determined; otherwise require human input") without specifying the concrete control-flow notation for the "otherwise" branch.

3. **`WHEN` following a `HITL`/`AUTO` decision**: The spec explicitly says only that "`VERIFY` may establish outcomes that can be used by `WHEN`" (with the `tests.passed`/`tests.failed` and `implementation.accepted`/`implementation.rejected` examples). It does not explicitly say a `HITL`/`AUTO` decision can be branched on with `WHEN`, only that "the human response may determine the subsequent flow." I extended the same `WHEN`-on-outcome pattern to the merge decision by analogy, since no other conditional construct is defined in the DSL.

4. **Identifier naming**: `implementation` (for the delegated work and its verification subject) and `merge.approved` / `merge.rejected` (for the two decision outcomes) are identifiers I chose myself, following the naming style of the spec's own examples (`tests.passed`, `implementation.accepted`, etc.). The spec states identifiers may name "requirements, results, states, artifacts, or other process-defined entities" but does not prescribe exact names, so any equivalent identifiers would be equally valid.

5. **Constructs left out**: `REQUIRE`, `LOOP`, `FORK`/`JOIN`, `WAIT`, `EMIT`, `BREAK`, and `STOP` were not used, because the requirement text describes no repetition, no concurrency, no explicit external-event wait, no artifact production, and no early loop exit or full termination — only delegation, verification, a decide-or-ask step, and a resulting state transition.

6. **Mutual exclusivity of the two `WHEN` blocks**: I assumed the "merge" vs. "not merge" outcomes are two mutually exclusive resolutions of the same decision point (mirrored on the spec's `tests.passed` / `tests.failed` example), since the DSL defines no explicit "else"/"otherwise" construct — only independent `WHEN` blocks describing different outcomes of the same process state.
