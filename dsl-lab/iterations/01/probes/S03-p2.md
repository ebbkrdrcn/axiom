```text
FORK
  → DELEGATE security-review
      VERIFY security-review

  → DELEGATE performance-review
      VERIFY performance-review

JOIN
TRANSITION "Release"
```

## Assumptions

- **`JOIN` refers to the single preceding `FORK` without needing a name.** The spec says `JOIN` "waits for the concurrent flows started by the corresponding `FORK`" but never defines how a `JOIN` is matched to a `FORK` when there could be more than one in scope (no naming/labeling syntax for `FORK`/`JOIN` is given). Since this task only has one `FORK`, I assumed the nearest/only enclosing `FORK` is the "corresponding" one. The spec does not determine what happens with multiple nested or sibling `FORK`s.

- **No `WHEN` branch is added after either `VERIFY`.** The spec's own `VERIFY` example is followed by `WHEN ...accepted` / `WHEN ...rejected` branches, but the requirement text only says each review is "delegated and then verified" and says nothing about what to do if a review is rejected. I assumed `VERIFY` alone (with no explicit outcome-handling) is valid and sufficient here, and did not invent failure-handling behavior the requirement didn't ask for.

- **Placing `TRANSITION "Release"` immediately after `JOIN`, at the top level (outside both fork branches), satisfies "continue only after both flows have finished."** This relies on the spec's statement that `JOIN` execution "continues only after all required forked flows have completed" — I treated the two `FORK` branches as the "required forked flows," which the spec doesn't explicitly state (it says "the concurrent flows started by the corresponding FORK," not "all of them" in so many words, though this is the natural reading).

- **Identifiers `security-review` and `performance-review` are reused as-is for both the `DELEGATE` argument and the `VERIFY` argument**, mirroring the spec's own `DELEGATE implementation` / `VERIFY implementation` pattern. The spec does not define naming rules for identifiers beyond "may be used to refer to requirements, results, states, artifacts, or other process-defined entities," so I assumed the same identifier can denote both "the work" (for `DELEGATE`) and "the result" (for `VERIFY`) of that work, as the spec's examples already do.

- **No `LOOP`, `REQUIRE`, `EMIT`, or `HITL` constructs were used**, since the requirement describes a one-shot parallel review process with no repetition, explicit preconditions, artifact production, or human decision points mentioned. The spec doesn't forbid adding these, but nothing in the requirement calls for them, so I omitted them rather than assuming unstated needs.

- **No enclosing `LOOP:<name>` or other named scope wraps the whole sequence.** The requirement doesn't mention repetition or a named process scope, and the spec shows top-level `FORK`/`JOIN` sequences without requiring them to be nested in anything, so I left the whole answer as a flat, unscoped statement sequence.
