```text
FORK
  → DELEGATE security-review
      VERIFY security-review
  → DELEGATE performance-review
      VERIFY performance-review

JOIN

TRANSITION "Release"
```

## Assumptions

- **Identifiers are arbitrary names I chose.** The specification defines `DELEGATE <work>` and `VERIFY <result>` generically and shows an example using matching identifiers (`implementation` / `implementation`). I used `security-review` and `performance-review` as the identifiers for both the delegated work and the corresponding verification, following that same matching-identifier pattern from the spec's own examples. The specification does not prescribe a naming scheme, so any other consistent identifier names would be equally valid.

- **Each `→` branch's nested statement is the `VERIFY` step.** Per the "Forked Flow" syntax section, "Indented statements following a branch belong to that branch until the branch scope ends." I nested `VERIFY security-review` under `→ DELEGATE security-review` (and similarly for performance-review) to express "each review is delegated and then verified within its own parallel flow." The spec's own `FORK` example uses this exact shape (`DELEGATE ... / VERIFY ...` nested under a branch), so this is directly modeled on that pattern.

- **`JOIN` waits for both/all branches of the immediately preceding `FORK`, with no partial-wait syntax.** The spec states `JOIN` "Waits for the concurrent flows started by the corresponding `FORK`" and "Execution continues only after all required forked flows have completed," but does not define any syntax for selecting a subset of branches to wait on. Since the task requires waiting for both reviews, and the DSL gives no mechanism to name a subset, I assumed a single unqualified `JOIN` waits for all branches of the corresponding `FORK` — matching the requirement "Continue only after both flows have finished."

- **No `WHEN` branching on verification outcome (accepted/rejected) was added.** The spec shows `VERIFY` outcomes can be used by `WHEN` (e.g., `implementation.accepted` / `implementation.rejected`), but the task only specifies sequencing ("delegated and then verified," "continue only after both flows have finished, then transition") and does not specify any differing behavior based on whether a review is accepted or rejected. Since the DSL requires `WHEN` conditions to be explicit and I have no stated acceptance criteria or differing downstream behavior to encode, I did not introduce speculative `WHEN` branches. The task's phrase "have finished" (not "have succeeded") supports proceeding to `JOIN`/`TRANSITION` regardless of each verification's outcome.

- **No `REQUIRE` statements were added.** The task does not mention any specific prerequisite information, context, or state needed before the reviews can begin, so none was declared. The specification is explicit that `REQUIRE` is optional/contextual and only used when a requirement needs to be stated.

- **`TRANSITION "Release"` is unconditional and placed directly after `JOIN`.** Per "Flow," statements execute in declaration order unless a control construct changes it, and `TRANSITION` "represents a state change, not execution of work." Since the task says to transition "then," with no conditional language, I placed it as the next statement after `JOIN` with no `WHEN` guarding it.

- **No `LOOP` was used.** The task describes a single one-time parallel review process ending in a state transition, with no indication of repetition, so a `LOOP` scope was not introduced.

- **The two reviews are treated as independent flows with no interaction between them**, consistent with `FORK`'s definition that "Each `→` starts an independent flow" and "The branches may execute concurrently." Nothing in the task suggests one review's result affects the other before `JOIN`.
