# Execution Trace

## Program

```text
FORK
  → DELEGATE lint
      VERIFY lint
      WHEN lint.rejected
        → STOP
  → DELEGATE docs
      EMIT docs
JOIN
EMIT build
```

## Relevant specification rules used

- `FORK` starts multiple **concurrent, independent** flows (branches). "The branches may execute concurrently."
- `JOIN` "waits for the concurrent flows started by the corresponding FORK. Execution continues only after all required forked flows have completed."
- `STOP` "terminates execution. No subsequent statement is executed after STOP." This is explicitly distinguished from `BREAK`, which "does not terminate the entire execution" and "may only exit a loop scope" — the spec's own contrast ("Use `STOP` to terminate the entire execution") establishes that `STOP`'s scope of effect is broader than a single loop or branch: it ends **the entire execution**, not merely the flow it was written in.
- `WHEN` is a pure condition/dispatch construct; it does not itself do work — it just routes to the `→` flow when its condition holds.
- `VERIFY` "may establish outcomes that can be used by `WHEN`."

## Step-by-step execution

1. **`FORK`** starts two independent concurrent flows:
   - Branch A (lint branch): `DELEGATE lint` → `VERIFY lint` → `WHEN lint.rejected → STOP`
   - Branch B (docs branch): `DELEGATE docs` → `EMIT docs`

2. **Branch A: `DELEGATE lint`** — work of linting is assigned to an actor. (No claim of correctness/acceptance yet.)

3. **Branch B (concurrently): `DELEGATE docs`** — work of producing docs is assigned to an actor.

4. **Branch A: `VERIFY lint`** — the lint result is evaluated. Per the injected event, this evaluation **establishes `lint.rejected`**.

5. At this same moment, per the injected event, **Branch B has completed `DELEGATE docs` but has not yet executed `EMIT docs`** — i.e., Branch B's own program counter is sitting right before `EMIT docs`, not yet advanced.

6. **Branch A: `WHEN lint.rejected`** — the condition is satisfied (established in step 4), so its flow is taken: **`STOP`** executes.

7. **`STOP` fires.** By the spec's explicit wording, `STOP` "terminates execution" in the global sense (this is exactly the property that distinguishes it from `BREAK`, which is scoped only to "the current `LOOP`"). Because `STOP` is not described as scoped to the branch/flow that invokes it (unlike `BREAK`, which is explicitly scoped to "the current loop"), the natural reading is that it ends the **whole running process**, including any other concurrently executing forked flows — not just Branch A.

8. Consequently, **no subsequent statement anywhere in the program executes** after this point, including Branch B's pending, not-yet-executed `EMIT docs`.

9. Because execution has been terminated before all forked flows completed, the `JOIN` statement's wait condition ("all required forked flows have completed") is never satisfied. The program never proceeds to a live, completed `JOIN` — it does not get to observe a normal join of finished branches, since the whole execution ended first.

10. `EMIT build`, which follows `JOIN` in the top-level flow, is likewise never reached/executed — both because `STOP` forbids any subsequent statement, and because the point in the flow after `JOIN` is never validly arrived at.

## Answers

- **Is `EMIT docs` executed? No.** At the moment `lint.rejected` is established, Branch B has only completed `DELEGATE docs`. Branch A's `WHEN lint.rejected → STOP` fires immediately afterward, and `STOP` terminates the entire execution (per spec, in explicit contrast to `BREAK`'s loop-only scope), so Branch B's still-pending `EMIT docs` is a "subsequent statement" that never runs.

- **Is `JOIN` completed? No.** `JOIN` completes only when all forked flows have completed. Branch B never finishes (it never reaches/executes `EMIT docs`), and in any case the entire execution is terminated by `STOP` before the program flow could reach a satisfied `JOIN`. `JOIN` is therefore neither reached in a live sense nor completed.

- **Is `EMIT build` executed? No.** It occurs after `JOIN` in program order, and since `STOP` terminates execution before that point is validly reached, it never runs.

## Explicit gap / assumption

The specification does **not** explicitly state what happens to a sibling forked flow that is still mid-execution when `STOP` is triggered in another branch. It defines `STOP` only as terminating "execution" and (by contrast with `BREAK`) says this is "the entire execution," but it does not give a specific rule for the interaction between `STOP` and concurrently running `FORK` branches, nor for whether a branch left incomplete due to a global `STOP` should be considered "completed" for `JOIN`'s purposes.

I assumed the more literal, stated reading: `STOP`'s effect is global ("the entire execution"), not confined to the flow/branch that issued it — this is the only reading that gives real meaning to the spec's contrast between `BREAK` (explicitly loop-scoped) and `STOP` (explicitly described as ending the entire execution, not just a scope). Under that assumption, `STOP` in the lint branch preempts the still-in-progress docs branch, so `EMIT docs` never executes, and `JOIN`/`EMIT build` are never reached. If instead the DSL intended `STOP` to only terminate the flow/branch in which it appears (an interpretation the spec's wording does not support, since it uses that scoped meaning for `BREAK`, not `STOP`), then Branch B could still complete `EMIT docs` and the program could proceed to a completed `JOIN` and `EMIT build`. The specification does not provide enough information to fully rule out that alternative reading with certainty for the FORK/STOP interaction specifically — only the general "STOP terminates the entire execution" wording, which points to the first (global-termination) answer given above.
