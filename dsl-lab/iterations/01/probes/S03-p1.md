```text
FORK
  → DELEGATE security-review
      VERIFY security-review

  → DELEGATE performance-review
      VERIFY performance-review

JOIN
TRANSITION "Release"
```

## Assumptions

- The specification gives `FORK` branches as `→ <statement>` followed by nested indented statements belonging to that branch (see the `FORK` and "Forked Flow" sections). I used this pattern to place `DELEGATE` and its corresponding `VERIFY` together inside each of the two branches, since the task says each review is "delegated and then verified within its own parallel flow."
- The requirement's two reviews ("security review" and "performance review") are treated as identifiers naming the work/result for `DELEGATE` and `VERIFY`, per the "Identifier" syntax rule ("Identifiers may be used to refer to requirements, results, states, artifacts, or other process-defined entities"). I named them `security-review` and `performance-review`, matching the naming style used in the spec's own `FORK` example (`security-review`, `readiness-verification`).
- The spec does not define named forks (only `LOOP:<name>` has an explicit name syntax), so `FORK` is written without a name, exactly as shown in the spec's `FORK` example.
- "Continue only after both flows have finished" maps directly to `JOIN`, which the spec defines as waiting for "all required forked flows" started by the corresponding `FORK`. No condition or outcome check (e.g., via `WHEN` on `.accepted`/`.rejected`) was requested, so I did not add one — the task only asks to continue after both flows finish and then transition, not to branch on verification outcomes.
- `TRANSITION "Release"` is placed after `JOIN`, unconditionally, since the task states to transition to "Release" simply once both flows have finished, without specifying any acceptance/rejection condition. The spec is explicit that `TRANSITION` represents only a state change, not execution of work, which is consistent with placing it after the parallel work completes.
- The spec does not define what happens if a `VERIFY` fails within a branch (e.g., whether the branch retries, or how the `FORK`/`JOIN` behaves on failure) — since the task doesn't ask for failure handling, I left this unspecified and did not invent `WHEN`/rejection-handling logic that the task did not request.
- No `REQUIRE`, `WAIT`, `HITL`, or `AUTO` constructs were used, since the task's requirement does not mention any external prerequisite, suspension, or human decision point.
