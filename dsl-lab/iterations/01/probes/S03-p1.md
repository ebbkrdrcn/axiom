# S03 — Parallel security/performance review, then transition to Release

## DSL

```text
FORK
  → DELEGATE security-review
      VERIFY security-review
  → DELEGATE performance-review
      VERIFY performance-review

JOIN

TRANSITION "Release"
```

## Assumptions

- **Identifier naming.** The spec never states a required naming convention for identifiers passed to `DELEGATE`/`VERIFY`; it only shows illustrative examples (`security-review`, `readiness-verification`, `implementation`). I chose `security-review` and `performance-review` as the identifiers for the two reviews, using the same identifier for both the `DELEGATE` and the corresponding `VERIFY` in each branch, mirroring the spec's own `DELEGATE implementation` / `VERIFY implementation` example. This is a naming choice, not something the spec fixes.

- **No explicit outcome handling (`WHEN`) after each `VERIFY`.** The requirement text only asks that each review be "delegated and then verified within its own parallel flow" and that execution "continue only after both flows have finished" — it does not specify what should happen if a `VERIFY` is rejected (e.g., re-delegate, abort, escalate to `HITL`). The spec shows `WHEN` as the mechanism for branching on verification outcomes (`implementation.accepted` / `implementation.rejected`), but since the task does not describe divergent outcomes to encode, I omitted `WHEN` entirely rather than inventing rejection-handling behavior. This assumes "finished" means the branch's statements (`DELEGATE` then `VERIFY`) have completed execution, regardless of the verification result — the spec does not equate `VERIFY` completion with acceptance, but the requirement's phrasing ("Continue only after both flows have finished") reads as being about completion/synchronization, not about acceptance gating.

- **`JOIN` scope.** The spec states `JOIN` waits for "the concurrent flows started by the corresponding `FORK`" but does not define how a `JOIN` would ever wait for a subset of branches if multiple `FORK`s were nested or sequential in the same scope. Since there is only one `FORK` here, I assumed the single `JOIN` waits for both of its two branches (the natural, unambiguous reading), with no partial-join semantics needed.

- **`TRANSITION "Release"` placement.** The spec's `TRANSITION` example uses a quoted string state name (`TRANSITION "Code Review"`), and the requirement names the target state as `"Release"`. I placed `TRANSITION "Release"` as a plain top-level statement after `JOIN`, executing in declaration order per the `Flow` syntax rule, since the requirement says the transition should happen "then" (after the join), with no conditional gating described.

- **Branch body indentation.** Per the `Forked Flow` syntax section, indented statements following a `→` belong to that branch "until the branch scope ends." I nested `VERIFY security-review` one level under `DELEGATE security-review` (and symmetrically for performance-review) to indicate both statements belong to the same branch — matching the spec's own `FORK` example exactly. The spec does not state whether `VERIFY` must be indented under `DELEGATE` versus written as a sibling `→`-less statement at the same level; I followed the given example's exact shape as the authoritative pattern.

- **No `REQUIRE` declared.** The requirement does not mention any preconditions (e.g., a repository, code, or build artifact needing to be available before review), so I did not add a `REQUIRE` statement. This is an omission based on the requirement text providing no such information, not a DSL-mandated absence.
