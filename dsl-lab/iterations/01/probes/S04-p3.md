# S04 — go_harness DSL Answer

## DSL

```text
REQUIRE deployment-target

HITL("Which region should we deploy to?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP

DELEGATE deployment
EMIT deployment-log
```

## Explanation of mapping

- `REQUIRE deployment-target` — "The process needs the deployment-target before anything else." `REQUIRE` declares this as a precondition that must be satisfied before execution continues, and is placed as the first statement.
- `HITL("Which region should we deploy to?")` — "ask a human ..." `HITL` establishes the human decision boundary with the exact message text as the string argument.
- `→ FALLBACK / → TRANSITION "Blocked" / STOP` — "If no usable answer is obtained from the human, transition to state "Blocked" and terminate the whole execution." The spec defines `FALLBACK` as the flow used "only when the expected response cannot be used to continue the normal flow," which is precisely the "no usable answer" case. Inside that fallback flow, `TRANSITION "Blocked"` performs the state change and `STOP` terminates execution entirely (not `BREAK`, since there is no enclosing `LOOP` and the requirement calls for terminating "the whole execution").
- `DELEGATE deployment` / `EMIT deployment-log` — "Otherwise, delegate the deployment and emit a deployment-log." Per the DSL's flow semantics ("Statements execute in declaration order unless an explicit control construct changes the flow"), these statements sit after the `HITL`/`FALLBACK` block at the outer scope and represent what happens when the fallback is not triggered (i.e., a usable answer was obtained) — the assumed continuation of the normal flow.

## Assumptions

1. **How the "otherwise" (normal) branch after `HITL` is expressed**: The spec never shows an explicit example of what runs when a `HITL`'s `FALLBACK` is *not* triggered. I assumed it falls through to the next statements in the enclosing scope in declaration order (per the general "Flow" rule), rather than requiring some other explicit construct (e.g., a paired `WHEN` on the human response). This is the most direct reading, but the spec does not explicitly confirm it.
2. **`STOP` vs `BREAK`**: There is no `LOOP` in this requirement, and "terminate the whole execution" matches `STOP`'s definition ("Terminates execution... No subsequent statement is executed after STOP") rather than `BREAK` (which only exits a loop scope). Assumed `STOP` is correct and no `LOOP` wrapper is needed or implied by the requirement.
3. **Placement of `STOP` and `TRANSITION` together inside the `FALLBACK` flow**: The spec's `FALLBACK` example shows a single `→ <flow>` line; I assumed multiple statements (`TRANSITION "Blocked"` then `STOP`) can be sequenced there as an indented flow, consistent with how nested statements are described elsewhere for branch scopes (e.g., `FORK` branches).
4. **Identifier spelling with hyphens**: The spec's `Identifier` syntax section gives no explicit grammar (allowed characters) for identifiers. I assumed hyphenated compound identifiers (`deployment-target`, `deployment-log`) are valid, using the exact terms from the requirement text, since the spec's own examples (e.g., `readiness-verification`, `test-report`) also use hyphens.
5. **No `VERIFY` added**: The requirement does not ask for evaluation of the delegated deployment's result, only to delegate it and emit a log. Since `DELEGATE` does not require a paired `VERIFY` (it's shown as a common pattern, not a mandatory one), I did not add one, to avoid inventing unrequested behavior.
6. **No `TRANSITION` after successful deployment**: The requirement specifies a `TRANSITION` to `"Blocked"` only for the failure path. I did not invent a success-path state name (e.g., "Deployed") since none was given, per the principle of not adding unspecified process behavior.
7. **`DELEGATE deployment`**: Assumed `deployment` is the correct identifier for "delegate the deployment," used as a bare identifier (no further qualification) since the requirement gives no more specific name.
8. **No wrapping `LOOP`**: The requirement describes a single linear process (require → ask → branch → delegate/emit), not a repeated scope, so no `LOOP:<name>` wrapper was used.
9. **Order/verbatim message text**: The `HITL` message string is reproduced exactly as quoted in the requirement, per the `String` syntax rule that strings hold literal human-readable text.
