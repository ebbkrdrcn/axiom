```text
REQUIRE deployment-target

HITL("Which region should we deploy to?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP

DELEGATE deployment
EMIT deployment-log
```

## Assumptions

- **Top-level sequencing needs no `LOOP`.** The requirement describes a single, one-shot sequence of steps ("needs X, then asks Y, then either Z or W"), not a repeated scope, so no `LOOP` construct is used. The specification says `LOOP` "does not imply any particular number of iterations" and is only for a "repeated execution scope," which does not apply here.

- **"Needs the deployment-target before anything else" maps directly to a single `REQUIRE` as the first statement.** The spec says `REQUIRE` "describes what is required, not how it is obtained," and gives `REQUIRE repository` as a directly analogous example, so `REQUIRE deployment-target` is used verbatim with no further elaboration of *how* it is satisfied (filesystem, API, config, etc. are all left unspecified, as the spec requires).

- **"Ask a human" maps to `HITL("Which region should we deploy to?")`** using the exact message text given in the requirement, per the `HITL("<message>")` syntax.

- **"If no usable answer is obtained" maps to the `FALLBACK` branch of that `HITL`, not to a `WHEN` condition.** The specification's own worked example is:
  ```text
  HITL("<message>")
    → FALLBACK
        → <flow>
  ```
  and states `FALLBACK` is used "only when the expected response cannot be used to continue the normal flow" — which is exactly the "no usable answer" case in the requirement. I therefore treat "usable answer obtained" as the ordinary continuation of the surrounding flow (the statements after the `HITL` block), and "no usable answer" as the `FALLBACK` branch, rather than inventing named conditions such as `region.provided` / `region.missing` for a `WHEN` construct. The spec does not define any such identifiers for `HITL` outcomes, and `AUTO`/uncertainty handling is explicitly not something `WHEN` or the DSL author gets to name ("Uncertainty is not a DSL condition, state, variable, or keyword.") — I extended that same reasoning to the general "response could not be used" case, preferring the construct (`FALLBACK`) the spec designed for exactly this situation.

- **`AUTO` is not used.** The requirement gives no criteria under which the region question could be resolved automatically — it is stated as unconditionally requiring a human answer — so there is no basis for `AUTO`'s "sufficiently determined" resolution. Introducing `AUTO` would not be supported by the requirement text.

- **"Transition to state 'Blocked' and terminate the whole execution" maps to `TRANSITION "Blocked"` immediately followed by `STOP`, in that order, inside the `FALLBACK` flow.** The spec distinguishes `STOP` ("Terminates execution... No subsequent statement is executed after STOP") from `BREAK` ("Exits the current LOOP... does not terminate the entire execution"). Since the requirement says "terminate the whole execution" and there is no `LOOP` in scope anyway, `STOP` is the only fitting construct. I placed `TRANSITION "Blocked"` before `STOP` because the requirement lists the state change before termination and `TRANSITION` "does not mean... execution of work," so recording the state change is meaningful even though execution ends immediately after.

- **"Otherwise, delegate the deployment and emit a deployment-log" maps to `DELEGATE deployment` followed by `EMIT deployment-log`, placed after the `HITL`/`FALLBACK` block at the same indentation as the `HITL` statement.** Per the syntax rules, statements execute "in declaration order unless an explicit control construct changes the flow," and only the `FALLBACK` branch diverts flow (to `Blocked` + `STOP`); so the un-diverted, normal continuation naturally represents the "otherwise" (usable answer) case without needing an explicit `WHEN`.

- **No `VERIFY` is used for the delegated deployment.** The requirement does not mention any acceptance/evaluation step for the deployment result (unlike the spec's `DELEGATE`/`VERIFY` example), so nothing warranted adding one. `EMIT deployment-log` is treated as the described output of that delegated work, not as itself an acceptance check.

- **Identifiers (`deployment-target`, `deployment`, `deployment-log`) are treated as opaque process-defined identifiers**, per "Identifiers may be used to refer to requirements, results, states, artifacts, or other process-defined entities" — the spec does not define a naming convention for these, so I used the exact terms from the requirement text (hyphenated as given), with `deployment` (no suffix) as the unit of delegated work referenced by `DELEGATE`, and `deployment-log` as the separate emitted artifact named in the requirement.

- **No `FORK`/`JOIN` is used.** Nothing in the requirement indicates concurrent flows; the steps are described sequentially ("before anything else," "then," "otherwise"), so a linear flow is assumed.

- **The `FALLBACK` flow is written as a single nested branch (`→ TRANSITION "Blocked"` with `STOP` indented beneath it as part of that flow)**, consistent with the "Forked Flow"/scope rules that indented statements following a `→` belong to that branch until the branch scope ends — applied here by analogy since the spec's `FALLBACK` example uses the same `→ <flow>` shape as `FORK` branches, and a "flow" per the spec can contain multiple statements in declaration order.
