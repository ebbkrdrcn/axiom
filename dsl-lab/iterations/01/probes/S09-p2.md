# Analysis of the go_harness DSL snippet

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.passed
  → TRANSITION "Review"
WHEN tests.failed
  → TRANSITION "Debugging"
```

## 1. Which outcome names can `VERIFY implementation` establish?

The specification does not enumerate a fixed vocabulary of outcome names. It only says, generically:

> "Verification may establish outcomes that can be used by `WHEN`."

The only concrete illustration given anywhere in the spec is the `VERIFY` example:

```text
VERIFY implementation

WHEN implementation.accepted
  → BREAK

WHEN implementation.rejected
  → DELEGATE correction
```

So the spec's own example names the two outcomes of verifying `implementation` as `implementation.accepted` and `implementation.rejected`. It never states that these are the *only* possible names, nor does it define a closed set of legal outcome suffixes (`accepted`/`rejected`/`passed`/`failed`/etc.). It also explicitly says identifiers may refer to "requirements, results, states, artifacts, or other process-defined entities," which implies the concrete outcome vocabulary is **process-defined**, not fixed by the DSL itself.

**Conclusion:** The specification does not determine a definitive, exhaustive list of outcome names that `VERIFY implementation` can establish. It only shows, by example, that an outcome name takes the shape `<result>.<qualifier>` (e.g. `implementation.accepted`, `implementation.rejected`). Whether `implementation.passed` (used in the task's snippet) is also a legitimate outcome of this same `VERIFY implementation` is not settled by the spec text.

**Assumption stated explicitly:** Since the spec's only worked example pairs `VERIFY implementation` with `implementation.accepted` / `implementation.rejected`, and never with `implementation.passed`, I assume for the rest of this analysis that `implementation.passed` is simply an alternate process-chosen name for the "accepted" outcome (i.e., the DSL does not care about the literal spelling, only that it is an outcome `VERIFY implementation` is defined, by the surrounding process, to produce). This is an assumption, not something the spec states.

## 2. Is `WHEN implementation.passed` a valid condition here?

Two separate questions are bundled here — syntactic validity and semantic/referential validity — and the spec answers them differently.

- **Syntactically:** Yes. `WHEN <condition>` takes an identifier, and identifiers "may be used to refer to requirements, results, states, artifacts, or other process-defined entities." `implementation.passed` is a well-formed identifier referring to a result (`implementation`) with a qualifier (`passed`), directly following a `VERIFY implementation` statement. This matches the shape of the spec's own example (`implementation.accepted`).

- **Semantically:** The spec says "Verification may establish outcomes that can be used by `WHEN`," which licenses a `WHEN` immediately after a `VERIFY implementation` to test an outcome of that verification. Since `implementation.passed` names an outcome of `implementation` and is checked immediately after `VERIFY implementation`, it reads as referring to that verification's result — which is consistent with the spec's intent.

**Conclusion:** `WHEN implementation.passed` is valid in form and in its apparent reference to the preceding `VERIFY implementation`. However, the specification does not literally confirm that "passed" (as opposed to "accepted") is a name `VERIFY` establishes — this is the same gap noted in Q1. So: **structurally valid; its exact semantic legitimacy depends on a process-level definition of the `implementation` outcome vocabulary that the spec does not provide**, and I assume it is intended as the positive-outcome branch of `VERIFY implementation`.

## 3. Is `WHEN tests.failed` valid here, and where does `tests` come from?

**Syntactic validity:** Yes, `tests.failed` is a well-formed identifier by the same rule as above (it may refer to a "result" or "process-defined entity").

**Where does it come from — semantic validity in this snippet:** This is where the specification does *not* determine an answer from the given text alone. Looking at the snippet provided in the task:

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.passed
  → TRANSITION "Review"
WHEN tests.failed
  → TRANSITION "Debugging"
```

There is no `REQUIRE tests`, `DELEGATE tests`, or `VERIFY tests` statement anywhere in this excerpt. The only `VERIFY` present targets `implementation`, not `tests`. Nothing in this snippet establishes an entity named `tests`, let alone an outcome `tests.failed` on it.

Notably, the spec's own canonical `WHEN` example has the identical shape:

```text
WHEN tests.passed
  → TRANSITION "Review"

WHEN tests.failed
  → TRANSITION "Debugging"
```

— but that example is presented in isolation too, with no preceding `VERIFY tests` shown, implying that in the spec's own usage, a `WHEN` condition can legitimately reference an outcome that was established elsewhere in the larger process definition, outside the shown excerpt. The spec never states that a `WHEN` condition must be established by a statement immediately, or even locally, preceding it — only that "Verification may establish outcomes that can be used by `WHEN`," and that "Multiple `WHEN` constructs may describe different outcomes of the same process state" (implying WHEN conditions can be scattered/reused across a larger process state model rather than always being locally derived).

**Conclusion:** `WHEN tests.failed` is syntactically valid, but the specification does not determine, from the material given, where the `tests` entity or its `failed` outcome comes from in this particular snippet — no `DELEGATE`, `VERIFY`, or `REQUIRE` referencing `tests` appears in it. This must be assumed to be defined/established elsewhere in the full process (e.g., a `VERIFY tests` step not shown in this excerpt, run as part of a broader test-suite flow), since the DSL treats identifiers as referring to "process-defined entities" that need not all be declared within any single shown fragment. **Stating the assumption explicitly:** I assume `tests` and its `failed`/`passed` outcomes are established by some other, unshown part of the same process (most plausibly a separate `DELEGATE`/`VERIFY` pair over an entity called `tests`), because nothing in the excerpt itself introduces `tests`.

## 4. If verification of the implementation is negative, which `TRANSITION` (if any) is executed?

Walking through the snippet under the assumption from Q1/Q2 (that `implementation.passed` is the positive-outcome condition established by `VERIFY implementation`, with some negative counterpart, e.g. `implementation.rejected`/`implementation.failed`, that the spec's example calls `implementation.rejected`):

- If verification is **negative**, then `implementation.passed` is false (not established), so:
  - `WHEN implementation.passed → TRANSITION "Review"` does **not** fire.
- `WHEN tests.failed → TRANSITION "Debugging"` is guarded by `tests.failed`, which — per Q3 — is a condition about a *different* entity (`tests`), not established by `VERIFY implementation` at all. A negative result on the implementation's verification does not, according to anything in the spec, set `tests.failed`. These are independent outcomes on independent entities (`implementation` vs. `tests`).
  - So this branch also does **not** fire as a consequence of the implementation verification being negative — it would only fire if the separate `tests` entity's verification (established elsewhere, per Q3) also happened to be failed, which is not stated to be the case, and is not implied by the implementation failing.

**Conclusion:** Given only the statements shown, if `VERIFY implementation` is negative, **neither `TRANSITION` in this snippet is executed**. The snippet as written has no `WHEN` branch that matches "implementation verification negative": there is no `WHEN implementation.rejected` (or `implementation.failed`) condition at all, only `WHEN implementation.passed` (which fails to trigger) and `WHEN tests.failed` (which is about an unrelated entity). Per the spec's `WHEN` semantics ("`WHEN` does not itself perform work, change state, delegate work, or produce an artifact" when its condition is not satisfied) and the `Flow` rule that "statements execute in declaration order unless an explicit control construct changes the flow," execution would simply fall through both `WHEN` blocks without transitioning the process state, and (since there is no further statement, and no `STOP`) the shown fragment ends without any explicit resolution of the negative-verification case.

**Gap explicitly flagged:** The specification does not determine what happens next in that situation (no transition, no `STOP`, no fallback is defined for a negative `implementation` verification in this snippet). This appears to be a gap in this particular process definition — analogous to the spec's own more complete example, which does handle the negative case via `WHEN implementation.rejected → DELEGATE correction`. The task's snippet omits that branch, so, strictly from the given text, a negative implementation verification result leads to **no defined `TRANSITION`** and the flow's continuation is unspecified by the excerpt.
