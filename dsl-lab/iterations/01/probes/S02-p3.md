# S02 Answer

```text
LOOP:implementation-cycle
  DELEGATE implementation
  VERIFY implementation

  WHEN implementation.accepted
    → BREAK

  WHEN implementation.rejected
    → DELEGATE correction

EMIT source-code
```

## Assumptions

The specification underdetermines several points needed to write this DSL. Assumptions made, and why:

1. **Reaching the end of the loop body causes it to repeat.** The spec says `LOOP` "continues until `BREAK`, `STOP`, or another explicit control flow terminates it" and that statements normally execute "in declaration order unless an explicit control construct changes the flow." Neither statement explicitly says what happens when execution falls off the end of a loop's statement list. I assumed that falling through the end of the loop body (without hitting `BREAK`/`STOP`) is precisely what makes the scope "repeated" — i.e., control implicitly returns to the top of the `LOOP` scope. This is how "repeat from the start" after `DELEGATE correction` is achieved, since nothing in the DSL as specified provides an explicit "go to top of loop" statement.

2. **`correction`'s output feeds back into the next iteration's `implementation`.** The task says "delegate a correction and then repeat from the start," which I read as looping back to `DELEGATE implementation` / `VERIFY implementation` again — i.e., whatever `correction` produces is what gets (re-)verified as `implementation` on the next pass. I did not add a separate `VERIFY correction` step, since the task only asks for one verification per cycle ("delegate the implementation, then verify it") and describes the correction as feeding back into that same cycle rather than being independently verified.

3. **Outcome vocabulary: `implementation.accepted` / `implementation.rejected`.** The spec states `VERIFY` "may establish outcomes that can be used by `WHEN`" but does not fix a naming scheme for those outcomes. I reused the exact identifiers from the spec's own worked example (`VERIFY implementation` → `WHEN implementation.accepted` / `WHEN implementation.rejected`), since the task's language ("accepts it" / "rejects it") maps directly onto that example.

4. **These two `WHEN`s are treated as the complete, mutually exclusive set of outcomes.** The task frames it as a strict if/else ("If ... accepts ... If ... rejects"), so I did not add handling for an undetermined or third outcome. The spec's discussion of uncertainty is scoped to `AUTO`, which is not used in this task, so I did not import that concern here.

5. **Loop name is an arbitrary identifier.** `LOOP:<name>` requires a name, but the spec does not prescribe what it should be beyond being an identifier. I chose `implementation-cycle` as a descriptive label; the spec gives no basis for a different specific name being "more correct."

6. **`EMIT source-code` placed unindented, after the `LOOP` scope closes.** "After the repetition ends" is read as: after the loop is exited entirely (via `BREAK`), not as part of any branch inside the loop. Since `BREAK` "does not terminate the entire execution" and only exits the loop scope, placing `EMIT source-code` at the outer indentation level after the loop is the construct the spec provides for "continue after the loop is done."

7. **Blank lines between statements are purely stylistic.** The spec's own examples use blank lines between `VERIFY`/`WHEN` blocks; I followed that formatting convention, but nothing in the "Syntax" section assigns semantic meaning to blank lines, only to indentation.
