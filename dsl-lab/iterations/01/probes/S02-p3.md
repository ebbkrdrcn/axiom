```text
LOOP:implementation-cycle
  DELEGATE implementation
  VERIFY implementation

  WHEN implementation.accepted
    → BREAK

  WHEN implementation.rejected
    → DELEGATE correction

EMIT source-code
```

## Assumptions

1. **Loop name.** `LOOP` requires a `<name>` (`LOOP:<name>`), but the requirement doesn't supply one. I assumed the identifier `implementation-cycle` as a descriptive label; the spec does not constrain what the name should be.

2. **Outcome identifiers for `VERIFY`.** The requirement says "accepts" / "rejects" but doesn't name the resulting condition identifiers. I reused the exact pattern from the spec's own `VERIFY` example (`implementation.accepted` / `implementation.rejected`), assuming `<result>.accepted` / `<result>.rejected` is the intended naming convention for outcomes VERIFY establishes.

3. **"Leave the repetition" = `BREAK`.** I mapped this directly to `BREAK`, per its definition ("Exits the current `LOOP`"), rather than `STOP`, since the requirement only wants to exit the loop, not terminate the whole execution (subsequent `EMIT` must still run).

4. **"Repeat from the start" requires no explicit jump construct.** The spec has no "continue" or "restart" keyword. Since `LOOP` "continues until `BREAK`, `STOP`, or another explicit control flow terminates it," I assumed that simply not issuing `BREAK`/`STOP` in the rejected branch is sufficient for control to return to the top of the loop body (i.e., back to `DELEGATE implementation`) — no additional statement is needed or available to express "repeat."

5. **The correction is not independently re-verified before looping.** "Delegate a correction and then repeat from the start" is read as: the correction becomes (or feeds into) the `implementation` result that gets re-delegated/re-verified on the next iteration, rather than the DSL needing a second, separate `VERIFY correction` step. The spec doesn't define how a "correction" relates back to "implementation" as data — this is an assumption about identifier continuity, not something the DSL's semantics fix.

6. **`EMIT source-code` is a top-level statement outside the loop scope**, executed exactly once after the loop is exited via `BREAK`. This follows from the indentation/scope rule ("Indented statements belong to the preceding scoped construct") — since `EMIT` is not indented under `LOOP`, it executes after the loop scope ends, matching "after the repetition ends, emit source-code."

7. **Exhaustiveness/mutual exclusivity of the two `WHEN` branches is assumed, not enforced.** The DSL spec states `WHEN` constructs "may describe different outcomes of the same process state" but does not require completeness or exclusivity. I assumed (as the requirement implies) that `implementation.accepted` and `implementation.rejected` are the only two possible outcomes of `VERIFY implementation`, so no third/default branch is needed.

8. **No `REQUIRE`, `HITL`, `AUTO`, `FORK`/`JOIN`, or `WAIT` were introduced.** The requirement describes a purely sequential/looping delegate-verify cycle with no mention of prerequisites, human input, concurrency, or external suspension, so none of those constructs were used, even though the spec permits them.
