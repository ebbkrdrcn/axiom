# S05 — Probe Answer

## Snippet A

```text
HITL("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

**Verdict: INVALID**

**Rule cited (verbatim from spec, `AUTO` section):**

> `AUTO` is not a control-flow container.
>
> It does not contain `WHEN`, `→`, or an arbitrary flow.
>
> Uncertainty is not a DSL condition, state, variable, or keyword.
>
> For example, the following is invalid:
>
> ```text
> AUTO
>   WHEN decision.uncertain
>     → HITL("Approve release?")
> ```

**What is wrong:**

The nested block under `AUTO` in Snippet A is character-for-character the exact construct the specification labels invalid. `AUTO` is defined only as a modifier on how a decision is resolved ("resolve automatically when sufficiently determined; otherwise require human input") — it is not a scope that can hold indented statements, a `WHEN`, or a `→` flow. The snippet also treats `decision.uncertain` as if it were a checkable condition, but the spec states uncertainty is determined internally by the runtime as part of automatic resolution and "is not a DSL condition, state, variable, or keyword" — so it cannot legally appear as the argument of a `WHEN`.

What would actually happen: since `AUTO` cannot contain a `WHEN`/`→` flow, this text does not parse as a valid `AUTO` construct at all. The correct pattern per the spec is simply to place `AUTO` on the decision point itself (with no nested flow), and rely on the runtime's own rule — "when the decision is uncertain or outside the agent's authority, human input is required" — to fall back to a human without the DSL author writing an explicit `WHEN decision.uncertain → HITL(...)` branch.

*Note:* The leading `HITL("Approve release?")` statement on its own (not shown connected via `FALLBACK`) is not itself flagged as invalid by any rule in the spec — `HITL` may appear as a bare statement establishing a human decision boundary. The spec does not explicitly state what it means for a `HITL` statement and an unrelated `AUTO` statement to appear back-to-back with no connecting construct between them; I assume this ordering is not itself an error and that the invalidity of the snippet rests entirely on the `AUTO` body, per the exact matching example in the spec.

## Snippet B

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

**Verdict: INVALID**

**Rule cited (verbatim from spec, `BREAK` section):**

> `BREAK`
>
> Exits the current `LOOP`.
>
> `BREAK` does not terminate the entire execution.
>
> `BREAK` may only exit a loop scope.
>
> Use `STOP` to terminate the entire execution.

**What is wrong:**

The `DELEGATE` / `VERIFY` / `WHEN` portion of this snippet is well-formed and in fact mirrors the spec's own worked example almost exactly:

```text
VERIFY implementation

WHEN implementation.accepted
  → BREAK

WHEN implementation.rejected
  → DELEGATE correction
```

`VERIFY` legitimately establishes outcomes such as `implementation.rejected` that `WHEN` can then branch on — that part is correct usage.

The defect is the `→ BREAK` under `WHEN implementation.rejected`. `BREAK` is defined as exiting "the current `LOOP`," and the spec is explicit that "`BREAK` may only exit a loop scope." Snippet B contains no `LOOP` construct anywhere — `DELEGATE`, `VERIFY`, and `WHEN` are all shown at the top level with no enclosing `LOOP:<name>` scope. With no loop scope in effect, there is nothing for `BREAK` to exit, so this use of `BREAK` violates the stated constraint.

Note also that this is the semantically backwards branch: in the spec's own example, `BREAK` is used on the **accepted** branch (to exit a correction loop once the delegated work is finally accepted), while the **rejected** branch re-delegates (`DELEGATE correction`) to continue iterating. Snippet B attaches `BREAK` to the **rejected** outcome instead, which — even if it were placed inside a loop — would exit the retry loop precisely when the work has failed verification, discarding the opportunity to loop again for a correction. The spec does not contain an explicit rule forbidding `BREAK` on a rejected branch; this is a design/logic observation rather than a syntactic rule violation, and I flag it as an assumption/inference rather than a cited rule, since the specification does not state that `BREAK` must correlate with any particular outcome.

**Assumption stated explicitly:** the spec does not describe what happens (parse error vs. runtime error vs. silently doing nothing) when `BREAK` is used with no enclosing `LOOP` in scope — it only states the constraint that `BREAK` "may only exit a loop scope." I assume this means such usage is invalid/disallowed by construction, since the snippet gives `BREAK` no loop scope to act on, rather than assuming some unstated fallback behavior (e.g., silently becoming a no-op or being promoted to `STOP`), since the spec does not define either of those as valid interpretations.
