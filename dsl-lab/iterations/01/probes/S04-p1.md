# S04 Answer

```text
REQUIRE deployment-target

HITL("Which region should we deploy to?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP

DELEGATE deployment
EMIT deployment-log
```

## Assumptions

1. **`REQUIRE` argument form.** The spec's only example is `REQUIRE repository` (a bare identifier). I assumed `deployment-target` (a hyphenated identifier naming the requirement from the task text) is an equally valid argument, since the spec does not restrict identifier vocabulary beyond "Identifiers may be used to refer to requirements, results, states, artifacts, or other process-defined entities."

2. **`HITL` message text.** I used the exact quoted string from the requirement (`"Which region should we deploy to?"`) as the `HITL` argument, per the `HITL("<message>")` syntax.

3. **Attachment point of `FALLBACK`.** The spec shows exactly one pattern for `FALLBACK`:
   ```text
   HITL("<message>")
     → FALLBACK
         → <flow>
   ```
   It never shows `FALLBACK` attached to anything other than `HITL`, and never shows it combined with `WHEN` or other conditionals. I assumed this is the only sanctioned attachment and used it verbatim, rather than inventing a `WHEN response.missing` construct, since the spec explicitly ties `FALLBACK` to "response handling" for a specific interaction.

4. **Mapping "no usable answer" to `FALLBACK`.** The requirement's phrase "If no usable answer is obtained from the human" was mapped directly to `FALLBACK`'s definition: "used only when the expected response cannot be used to continue the normal flow." I treated these as equivalent conditions.

5. **"terminate the whole execution" → `STOP`, not `BREAK`.** The spec is explicit that `BREAK` "may only exit a loop scope" and `STOP` is for terminating "the entire execution." Since there is no enclosing `LOOP` here anyway, `BREAK` would be invalid regardless; `STOP` was the only construct that matches "terminate the whole execution."

6. **Ordering of `TRANSITION "Blocked"` and `STOP` inside the fallback flow.** The spec doesn't give an example with two statements inside a `FALLBACK` branch, but the general Scope/Flow rules (statements execute in declaration order; indented statements belong to the preceding construct) support stacking `TRANSITION "Blocked"` followed by `STOP` as sequential statements in that branch, matching "transition to state Blocked **and** terminate."

7. **Representing "Otherwise" (usable answer obtained).** The spec does not define an explicit "else"/success branch for `HITL`/`FALLBACK` — there is no shown construct like `SUCCESS →` or a paired `WHEN response.obtained`. I assumed that since `FALLBACK` "is used only when the expected response cannot be used to continue the normal flow," the *normal* flow is simply the statements that follow the `HITL`/`FALLBACK` block at the same (outer) scope level. This relies on the general Flow rule: "Statements execute in declaration order unless an explicit control construct changes the flow." Since `STOP` inside the fallback branch prevents that path from ever reaching the following statements, `DELEGATE deployment` / `EMIT deployment-log` are effectively reached only on the "otherwise" (usable answer) path. This is my most significant inference, since the spec never explicitly confirms this fall-through semantics for a non-taken `FALLBACK`.

8. **No `VERIFY` after `DELEGATE deployment`.** The spec's `DELEGATE` examples are frequently paired with `VERIFY` (e.g., `DELEGATE implementation` / `VERIFY implementation`), and notes "A delegated result may subsequently be evaluated by `VERIFY`" (permissive, not mandatory). The task requirement does not mention verifying the deployment, only delegating it and emitting a log, so I omitted `VERIFY` as not required by the stated requirement.

9. **No `LOOP` wrapper.** The requirement describes a single linear sequence with no repetition language ("continues until...", "iterate", etc.), so I did not wrap the process in a `LOOP` scope.

10. **`TRANSITION "Blocked"` string quoting.** Followed the spec's own example `TRANSITION "Code Review"` — state name as a quoted string.

11. **`DELEGATE deployment` / `EMIT deployment-log` as bare identifiers.** Treated `deployment` and `deployment-log` as process-defined identifiers (per the Identifier syntax section) rather than quoted strings, consistent with the spec's own examples (`DELEGATE implementation`, `EMIT source-code`, `EMIT test-report`).
