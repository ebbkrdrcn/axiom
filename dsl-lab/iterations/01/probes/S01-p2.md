```text
DELEGATE implementation
VERIFY implementation

AUTO
HITL("Merge this change?")

WHEN merge.approved
  → TRANSITION "Merged"

WHEN merge.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **How `AUTO` and `HITL` combine.** The spec never shows a valid example of `AUTO` paired with `HITL` — the only example involving `AUTO` is explicitly marked invalid (it shows `AUTO` illegally containing a `WHEN`/`→` block). The spec does state `AUTO` means "resolve automatically when sufficiently determined; otherwise require human input," and separately that `HITL` "must not be silently replaced by an agent decision unless the surrounding definition explicitly permits automatic resolution through `AUTO`." I assumed from this that the intended pattern is two sequential top-level statements — `AUTO` followed by `HITL("...")` — where `AUTO` first attempts automatic resolution of the merge decision, and the `HITL` statement (carrying the human-facing message required by the task) is only actually invoked when `AUTO` cannot determine the decision with sufficient certainty. Both paths are assumed to feed the same underlying decision result used by the subsequent `WHEN` statements. This pairing is my inference, not something the spec states directly.

2. **Identifier names for the decision outcomes.** The spec doesn't define a fixed vocabulary of condition identifiers; it only shows the *pattern* via examples like `tests.passed`, `tests.failed`, `implementation.accepted`, `implementation.rejected`. I invented `merge.approved` and `merge.rejected` following that same `<subject>.<outcome>` pattern.

3. **No `WHEN` branches on `VERIFY implementation`'s outcome.** The requirement says only "verify it," with no instruction for what happens if verification fails, so I did not add `implementation.accepted` / `implementation.rejected` branches (unlike the spec's own `VERIFY` example, which does add a rejection → `DELEGATE correction` branch). This is a deliberate omission based on the requirement text not specifying that behavior, not a spec limitation.

4. **No `REQUIRE` statement.** The requirement text states no preconditions (e.g., repository access, criteria docs), so I did not introduce a `REQUIRE`. The spec allows but doesn't mandate one.

5. **The merge decision is not `DELEGATE`d.** I treated the merge decision as resolved via `AUTO`/`HITL` rather than `DELEGATE`, since `DELEGATE` is defined as assigning work to "another actor," whereas the requirement frames the merge decision as either the agent itself deciding or a human being asked — matching `AUTO`'s and `HITL`'s definitions rather than `DELEGATE`'s.

6. **No `FALLBACK` under `HITL`.** The requirement doesn't describe what should happen if the human doesn't respond or gives an insufficient answer, so I omitted a `FALLBACK` block. The spec presents `FALLBACK` as associated with response handling but doesn't mark it mandatory for every `HITL`.

7. **Binary, mutually exclusive/exhaustive outcome.** I assumed the merge decision (whether resolved by `AUTO` or by the human via `HITL`) yields exactly one of two outcomes — merge or no-merge — matching the two `TRANSITION` targets given in the requirement, with no third/uncertain outcome left dangling in the DSL itself (per the spec's statement that "uncertainty is not a DSL condition, state, variable, or keyword" — i.e., uncertainty is a runtime-internal concern of `AUTO`, not something the DSL text branches on).

8. **Scope.** All statements are assumed to sit in one unnamed top-level flow (no enclosing `LOOP`), since the requirement describes a single linear process with no repetition indicated.
