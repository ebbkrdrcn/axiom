# Execution Trace

## Program (annotated)

```text
LOOP:review                                    (top-level statement)
  FORK
    → DELEGATE security-review        [Branch A]
        VERIFY security-review
        WHEN security-review.rejected
          → BREAK
    → DELEGATE docs-review            [Branch B]
        VERIFY docs-review
  JOIN
  TRANSITION "Reviewed"
EMIT review-summary                            (top-level statement, after the loop)
```

`LOOP:review` encloses `FORK … JOIN … TRANSITION "Reviewed"`. `EMIT review-summary` is a
sibling of `LOOP:review`, not inside it, so per "Flow: Statements execute in declaration
order unless an explicit control construct changes the flow," it is the statement that
follows the loop once the loop's scope is exited by any means (normal completion, `BREAK`,
or `STOP`).

## Step-by-step trace

**Step 0 — Loop entry.**
`LOOP:review` begins iteration 1. The spec says `LOOP` "does not imply any particular
number of iterations" and continues "until `BREAK`, `STOP`, or another explicit control
flow terminates it."

**Step 1 — FORK.**
`FORK` starts two independent flows (per the injected event, "both branches start"):
- Branch A: `DELEGATE security-review` → `VERIFY security-review` → `WHEN
  security-review.rejected` → `BREAK`
- Branch B: `DELEGATE docs-review` → `VERIFY docs-review`

Per spec, "Each `→` starts an independent flow" and "The branches may execute
concurrently."

**Step 2 — DELEGATE (both branches).**
`DELEGATE security-review` assigns the security-review work to an actor; `DELEGATE
docs-review` assigns the docs-review work to an actor. `DELEGATE` "does not mean that the
work is correct, complete, or accepted" — it only establishes responsibility.

**Step 3 — VERIFY security-review resolves first.**
Per the injected event, `VERIFY security-review` evaluates the security-review result and
establishes the outcome `security-review.rejected`, while branch B is still running and
its own `VERIFY docs-review` has not yet executed. Per spec, "Verification may establish
outcomes that can be used by `WHEN`," which is exactly what happens next.

**Step 4 — WHEN security-review.rejected.**
The condition `security-review.rejected` is now established, so the flow following it
executes. `WHEN` itself "does not itself perform work, change state, delegate work, or
produce an artifact" — it only routes to `→ BREAK`.

**Step 5 — BREAK executes.**
Per spec, "`BREAK` exits the current `LOOP`," "`BREAK` may only exit a loop scope," and
"`BREAK` does not terminate the entire execution." The nearest enclosing `LOOP` for this
statement is `LOOP:review` (the `FORK` branch itself is not a loop scope), so `LOOP:review`
is exited now, in the middle of iteration 1, before control ever reaches the loop's `JOIN`
or `TRANSITION "Reviewed"` statements.

**Step 6 — Loop exit; flow continues after the loop.**
Because `BREAK` does not terminate the entire execution, and `EMIT review-summary` is the
next statement in declaration order after `LOOP:review`'s scope, control passes there.

**Step 7 — EMIT review-summary.**
`EMIT review-summary` executes, producing the `review-summary` artifact. Nothing in the
spec makes `EMIT` conditional on `TRANSITION` or `JOIN` having previously executed; it is
simply the next declared statement once the enclosing loop has ended.

**Step 8 — End of execution.**
No further statements are declared after `EMIT review-summary`, and no `STOP` occurs. With
no statements left to execute, execution ends.

## What happens to each construct named in the task

- **The docs-review branch (Branch B):** It is left in an unresolved state. At the moment
  `BREAK` fires, `DELEGATE docs-review` has been issued but `VERIFY docs-review` has not
  run. **The specification does not say what happens to a still-running forked flow when a
  sibling branch's `BREAK` exits the enclosing loop before `JOIN` is reached** — see
  "Unresolved / underdetermined points" below. Under the reading I adopt (see Assumption 3),
  branch B is not forcibly cancelled by any construct defined in the spec (no construct is
  given authority to stop another "independent flow"), but its eventual `VERIFY
  docs-review` outcome becomes moot: the only construct that could consume it, `JOIN`, is
  never reached because the loop that contains it has already ended.

- **JOIN:** It never executes. Control never reaches it in this iteration because `BREAK`
  exits `LOOP:review` earlier in the sequence (from inside branch A), and once the loop is
  exited, the remaining statements of that loop body — `JOIN` and `TRANSITION "Reviewed"`
  — are simply skipped, not executed late or executed partially.

- **TRANSITION "Reviewed":** It never executes, for the same reason as `JOIN`: it is a
  statement inside `LOOP:review`'s scope positioned after `JOIN`, and the loop has already
  been exited before control could reach it. The process therefore never moves to the
  "Reviewed" state on this run.

- **EMIT review-summary:** It does execute, exactly once. It sits outside/after
  `LOOP:review` in declaration order, and `BREAK`'s defined effect is scoped to the loop
  only ("does not terminate the entire execution"), so execution falls through to this
  statement and then ends, since it is the last declared statement.

## Assumptions made where the specification underdetermines behavior

1. **Which `LOOP` a nested `BREAK` exits.** `BREAK` is written inside a `FORK` branch,
   which is itself inside `LOOP:review`. The spec never states how "current LOOP" resolves
   across a `FORK` boundary. I assumed "current LOOP" means the nearest lexically enclosing
   `LOOP` construct — here, `LOOP:review` — since `FORK` and its branches are not
   themselves loop scopes and the spec defines no other loop candidate.

2. **Timing of `BREAK`'s effect relative to concurrent siblings.** The spec states `BREAK`'s
   effect ("exits the current LOOP") unconditionally, with no mention of waiting for
   sibling forked flows or for `JOIN`. I assumed this effect is immediate at the point
   `BREAK` executes within its own branch's sequential flow, not deferred until `JOIN` or
   until branch B completes. (An alternative reading — that a loop-exiting `BREAK` inside a
   `FORK` branch is implicitly held until the corresponding `JOIN` — is not supported by
   any text in the spec, so I did not adopt it.)

3. **Fate of a sibling forked flow when the enclosing loop is exited before `JOIN`.** This
   is the central gap: the spec defines `FORK` branches as "independent flows" and gives no
   construct the authority to cancel, interrupt, or otherwise affect another branch, but it
   also never addresses what should happen to a branch still in flight when the surrounding
   `LOOP` ends without reaching `JOIN`. I assumed branch B is not forcibly terminated (since
   nothing in the spec grants that power to `BREAK` or to loop exit), but that its outcome
   has no further effect on the program, because `JOIN` — the only construct that
   synchronizes on forked flows — is never reached in the terminated loop. The spec does not
   say whether this should instead be treated as an error, a required cancellation, or some
   other resolution; it simply does not address it.

4. **`EMIT review-summary`'s preconditions.** The spec's only stated rule governing when a
   statement executes is declaration order plus explicit control-flow constructs. I assumed
   `EMIT review-summary` has no implicit dependency on `TRANSITION "Reviewed"` or `JOIN`
   having occurred (the spec states no such dependency anywhere), so it executes purely
   because it is next in declaration order once `LOOP:review` has ended.

5. **Meaning of "required forked flows" in `JOIN`'s definition.** `JOIN`'s spec text says
   "Execution continues only after all **required** forked flows have completed," without
   defining which forked flows count as "required" or what happens to non-required ones.
   This did not need to be resolved for this trace (since `JOIN` is never reached at all),
   but it is a general gap in the specification worth flagging.
