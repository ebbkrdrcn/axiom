# S02 — go_harness DSL Answer

## DSL

```text
LOOP:implementation-cycle
  DELEGATE implementation
  VERIFY implementation

  WHEN implementation.accepted
    → BREAK

  WHEN implementation.rejected
    → DELEGATE correction

EMIT source-code
```

## Assumptions

1. **Loop name is arbitrary.** `LOOP:<name>` requires an identifier, but the spec does not prescribe a naming convention or vocabulary for it. I chose the descriptive name `implementation-cycle`; any other identifier would be equally valid per the spec.

2. **"Repeat from the start" is realized implicitly, not with an explicit repeat/continue keyword.** The DSL defines no `CONTINUE`/`REPEAT` construct. The spec states "`LOOP` continues until `BREAK`, `STOP`, or another explicit control flow terminates it," so after `DELEGATE correction` runs (with no `BREAK`/`STOP` in that branch), control falls through to the end of the loop body and the loop naturally re-enters at the top (`DELEGATE implementation`). I assumed this implicit fall-through-and-reloop behavior is what "repeat from the start" means, since the spec offers no other mechanism to express it.

3. **The identifier `implementation` is assumed to refer to the current/latest state of the work across iterations**, i.e., after `DELEGATE correction`, the next iteration's `DELEGATE implementation` / `VERIFY implementation` are understood to act on the corrected version. The spec does not define how identifiers persist, rebind, or accumulate state across loop iterations, so this is an assumption about identifier semantics rather than something the spec states directly. (An alternative reading — that `correction` is a wholly separate, untracked piece of work and the next `DELEGATE implementation` starts over independently — is not ruled out by the spec, but seemed inconsistent with the task's intent of "repeat from the start" fixing and re-verifying the same deliverable.)

4. **Outcome conditions `implementation.accepted` / `implementation.rejected`** are borrowed directly from the spec's own worked example under `VERIFY` (which uses exactly this dot-notation pattern for accept/reject outcomes). The task text says "accepts" / "rejects" in prose, not in DSL vocabulary, and the spec does not mandate a canonical condition-naming scheme — I assumed reusing the spec's own example vocabulary was the intended mapping.

5. **Only two outcomes are modeled (accepted/rejected), with no additional `WHEN` branch or `FALLBACK` for an indeterminate/other verification result.** The spec does not require `WHEN` branches to be exhaustive, and the task only describes these two outcomes, so no third branch was added.

6. **The correction itself is not separately wrapped in its own `VERIFY`.** The task's phrasing ("delegate a correction and then repeat from the start") implies the correction is evaluated by the next iteration's `VERIFY implementation`, not by an additional, separate verification step immediately after `DELEGATE correction`.

7. **`EMIT source-code` executes exactly once, unconditionally, after the loop exits.** Since the only loop-exit path in this flow is `BREAK` (on `implementation.accepted`), and `STOP` is not used, `EMIT source-code` is reachable only via the accepted path — consistent with "after the repetition ends, emit source-code."

8. **`HITL`, `AUTO`, `FORK`/`JOIN`, `REQUIRE`, and `TRANSITION` were omitted entirely.** The task describes no human decision point, no concurrency, no explicit prerequisite/requirement, and no process-state change, so none of these constructs were used.
