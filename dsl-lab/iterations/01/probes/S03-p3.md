# S03 Answer

## DSL

```text
FORK
  → DELEGATE security-review
      VERIFY security-review
  → DELEGATE performance-review
      VERIFY performance-review

JOIN

TRANSITION "Release"
```

## Assumptions

- **Identifiers are free text chosen by me.** The spec's `Identifier` syntax section only says identifiers "may be used to refer to requirements, results, states, artifacts, or other process-defined entities" — it does not define a naming convention. I used `security-review` and `performance-review`, mirroring the exact wording of the requirement and the naming style used in the spec's own `FORK` example (`security-review`, `readiness-verification`).

- **`JOIN` is written as a standalone, unindented statement following the `FORK` block, not nested inside either branch.** The spec's `FORK`/`JOIN` sections describe the semantics ("Waits for the concurrent flows started by the corresponding `FORK`") but the spec never shows a complete `FORK ... JOIN` example together (the `FORK` example ends without a `JOIN`), so the exact placement/indentation convention for `JOIN` relative to the fork's branches is not fixed by the spec. I assumed `JOIN` sits at the same indentation level as `FORK` itself, after all branches, since it applies to the whole fork rather than to any single branch.

- **No `WHEN` branching is added after either `VERIFY`.** The requirement only says each review is "delegated and then verified" and that execution should continue after both finish — it does not specify what should happen if a review is rejected. The spec shows `VERIFY` commonly paired with `WHEN ... .accepted / .rejected`, but this is illustrated as an example, not mandated. Since the task gave no acceptance/rejection handling to encode, I left both branches as bare `DELEGATE` + `VERIFY` pairs rather than inventing rejection-handling logic not present in the requirement.

- **`TRANSITION "Release"` is placed after `JOIN` at top level, not inside a branch.** This follows directly from the requirement text ("Continue only after both flows have finished, then transition...") and from `JOIN`'s defined semantics ("Execution continues only after all required forked flows have completed"), so this part is well-determined by the spec.

- **No `REQUIRE` or `EMIT` statements were added.** The requirement does not mention any preconditions to declare or artifacts to produce, and the spec treats these as separate, optional operations, so I did not introduce them speculatively.

- **No `HITL`/`AUTO`/`FALLBACK` constructs were used.** The requirement describes a fully delegated/automated flow with no mention of human decision points, so these Human Interaction constructs were omitted as not applicable.

- **The two branches are each a single `DELEGATE` statement with one nested `VERIFY` statement**, per the spec's `Forked Flow` syntax rule: "Indented statements following a branch belong to that branch until the branch scope ends." This directly matches the spec's own `FORK` example structure, which I followed as the closest template for "each review is delegated and then verified within its own parallel flow."
