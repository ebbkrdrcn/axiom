```text
FORK
  → DELEGATE security-review
      VERIFY security-review

  → DELEGATE performance-review
      VERIFY performance-review

JOIN

TRANSITION "Release"
```

## Assumptions

- **Identifier names for the delegated work and results**: the requirement names the two reviews only in prose ("a security review and a performance review"). The specification's own `FORK` example uses the identifier `security-review`, so that name was reused verbatim for the first branch; `performance-review` was coined analogously for the second, following the same `<subject>-review` naming pattern. No other naming convention is given in the spec, so any equivalent identifier (e.g. `performance_review`, `perf-review`) would be equally valid.
- **`VERIFY` targets the same identifier as the `DELEGATE` it follows**: the spec's example (`DELEGATE implementation` / `VERIFY implementation`) shows `VERIFY` referring back to the delegated work by the same name. The task says each review is "delegated and then verified within its own parallel flow," so each branch's `VERIFY` was given the same identifier as that branch's `DELEGATE`, since the spec does not define a separate naming scheme for "results" distinct from the "work" that produced them.
- **No `WHEN` branching on verification outcome is included**: the task states only that execution should "continue only after both flows have finished, then transition to state 'Release'." It does not specify what happens if a review is rejected (e.g. `implementation.accepted` / `implementation.rejected` as in the spec's `VERIFY` example). Since the requirement gives no acceptance/rejection handling to encode, none was added — `VERIFY` is included solely to satisfy "delegated and then verified," and the flow proceeds unconditionally to `JOIN` and `TRANSITION`. If the process actually needs conditional handling of a failed review, that would require additional information not present in the requirement.
- **`JOIN` is placed at the top level, immediately after the `FORK` block, with no enclosing `LOOP`**: the requirement describes a single one-shot execution ("run... in parallel... continue... then transition"), not a repeating process, so no `LOOP` scope was introduced. The spec shows `JOIN` as a bare statement that waits for "the concurrent flows started by the corresponding `FORK`," and does not require any particular indentation relative to `FORK`; it was placed unindented, at the same level as `FORK`, to mean "after the fork block" per the spec's `Flow` section (statements execute in declaration order).
- **Each forked branch contains exactly two statements (`DELEGATE` then `VERIFY`), nested under its `→` per the `Forked Flow` syntax rule** ("Indented statements following a branch belong to that branch until the branch scope ends"). This directly matches the spec's own `FORK` example structure, so no assumption beyond following that example was needed here.
- **`TRANSITION "Release"` is treated as a plain state name string**, mirroring the spec's example `TRANSITION "Code Review"`. The requirement calls it a "state," consistent with `TRANSITION`'s defined meaning ("a state change, not execution of work"), so no additional work (e.g. an implied "release process") is implied by this statement.
- **No `REQUIRE`, `HITL`, `EMIT`, or `AUTO` statements were added**, since the requirement text does not mention any prerequisite information, human decision point, artifact output, or automatic-resolution decision — introducing any of these would go beyond what was asked and beyond what the specification allows without a corresponding stated need.
