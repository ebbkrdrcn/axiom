```text
LOOP:implementation-cycle
  DELEGATE implementation
  VERIFY implementation

  WHEN implementation.accepted
    → BREAK

  WHEN implementation.rejected
    → DELEGATE correction

EMIT source-code
```

## Assumptions

1. **Naming the loop.** The syntax requires `LOOP:<name>`, but the specification does not say what the name must be. I used the descriptive identifier `implementation-cycle`; any identifier would be equally valid per the spec.

2. **How "repeat from the start" is expressed.** The DSL has no explicit `CONTINUE`/"repeat" keyword. The spec states a `LOOP` "continues until `BREAK`, `STOP`, or another explicit control flow terminates it," which I take to mean that if none of those terminating constructs fire, execution falls back to the top of the loop body by default. I therefore modeled "repeat from the start" simply as *not* issuing `BREAK`/`STOP` in the rejection branch: after `DELEGATE correction` (the last statement in that flow, and the last statement in the loop body), the loop naturally re-executes from `DELEGATE implementation`.

3. **No mechanism to distinguish a "first" attempt from a "corrected" attempt.** Because looping back re-executes `DELEGATE implementation` and `VERIFY implementation` verbatim, the DSL has no variable/state construct to mark that a correction was already delegated. I assumed this repetition is intentional and sufficient: the next iteration's `DELEGATE implementation` / `VERIFY implementation` pair is what evaluates the corrected work, consistent with the DSL's stated independence from implementation/state mechanics.

4. **Outcome identifiers from `VERIFY`.** I used `implementation.accepted` and `implementation.rejected` as the two outcomes of `VERIFY implementation`, mirroring the spec's own example (`VERIFY implementation` followed by `WHEN implementation.accepted` / `WHEN implementation.rejected`). The spec does not enumerate a fixed vocabulary of outcome names, so these are assumed to be the process-defined outcome identifiers for this verification.

5. **Mutual exclusivity of the two `WHEN` blocks.** I assumed the "accepted" and "rejected" outcomes of a single `VERIFY implementation` call are mutually exclusive and exhaustive for a given iteration, so exactly one `WHEN` branch executes per pass through the loop, as in the spec's own `WHEN` example.

6. **`BREAK` as the exit mechanism.** Per spec, `BREAK` "exits the current `LOOP`" and cannot terminate the whole execution; `WHEN implementation.accepted → BREAK` is used to "leave the repetition" exactly as the requirement states, matching the spec's own example usage of `BREAK` inside a `WHEN` triggered by `VERIFY`.

7. **Placement of `EMIT source-code`.** It is written at the loop's outer indentation level (outside `LOOP:implementation-cycle`), so it executes once, in declaration order, only after the loop has ended (i.e., after `BREAK` fires) — matching "after the repetition ends, emit source-code."

8. **No other constructs needed.** The requirement does not call for `REQUIRE`, `HITL`, `AUTO`, `FORK`/`JOIN`, `WAIT`, `TRANSITION`, or `FALLBACK`, so none were introduced, since the DSL specification does not mandate their use and nothing in the requirement implies a human-interaction boundary, concurrency, external suspension, or a state/artifact beyond `source-code`.

9. **`DELEGATE correction` as an identifier for the corrective work**, analogous to the spec's own example (`WHEN implementation.rejected → DELEGATE correction`), rather than any more specific phrasing, since the requirement only says "delegate a correction."
