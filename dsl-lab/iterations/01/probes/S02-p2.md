# Answer

```text
LOOP:implementation-cycle
  DELEGATE implementation
  VERIFY implementation

  WHEN implementation.accepted
    → BREAK

  WHEN implementation.rejected
    → DELEGATE correction

EMIT source-code
```

## Assumptions

1. **Implicit repetition on fall-through.** The spec states "The loop continues until `BREAK`, `STOP`, or another explicit control flow terminates it," but never explicitly states what happens when execution reaches the end of the loop body without hitting one of those terminators. I assumed this means the loop body implicitly repeats from its first statement in that case — i.e., no explicit "continue" or "repeat" keyword exists in the DSL (none is defined anywhere in the spec), so "repeat from the start" after `DELEGATE correction` is expressed simply by *not* issuing `BREAK`/`STOP` and letting control fall back to the top of `LOOP:implementation-cycle`.

2. **Placement of `WHEN` inside the `LOOP` scope.** The spec doesn't explicitly say whether `WHEN` blocks reacting to a `VERIFY` result must be nested inside the enclosing `LOOP`, but since `BREAK` "may only exit a loop scope," the `WHEN implementation.accepted → BREAK` branch must be inside the loop for `BREAK` to be valid. I assumed both `WHEN` blocks (accepted/rejected) are indented as direct statements of the loop, consistent with the scope rule "Indented statements belong to the preceding scoped construct."

3. **Condition identifiers `implementation.accepted` / `implementation.rejected`.** The spec's own `VERIFY` example uses exactly `implementation.accepted` and `implementation.rejected` as the outcomes established by `VERIFY implementation`. I reused these identifiers verbatim since the requirement text ("the verification accepts it" / "rejects it") maps directly onto that example, and the spec doesn't define any other naming convention for verification outcomes.

4. **`DELEGATE correction` as the identifier for the corrective work.** The spec's own `DELEGATE`/`VERIFY` example pairs `DELEGATE correction` with a rejected result, so I used the identifier `correction` verbatim rather than inventing a different name (e.g., `DELEGATE implementation-fix`).

5. **The corrected work re-enters the same `DELEGATE implementation` / `VERIFY implementation` pair.** The requirement says "repeat from the start," which I took to mean the loop body restarts entirely — including delegating (what is now) the corrected implementation and verifying it again — rather than requiring a separate `VERIFY correction` step. The spec defines no construct for verifying a `DELEGATE correction` result differently from the original implementation, so I assumed the same `implementation` identifier is reused/re-verified on each iteration.

6. **`EMIT source-code` placed after the loop, unindented.** "After the repetition ends" is expressed by placing `EMIT source-code` as a statement following the `LOOP` scope (not indented under it), relying on the general "Flow" rule that "Statements execute in declaration order unless an explicit control construct changes the flow" — since `BREAK` exits the loop scope, the next statement in declaration order after the loop's scope is `EMIT source-code`.

7. **Loop name `implementation-cycle`.** `LOOP:<name>` syntactically requires a name, but the requirement text gives none. I invented a descriptive identifier since the spec gives no rule for naming loops beyond requiring *some* identifier.

8. **No `HITL`/`AUTO` involved.** The requirement describes a fully automated accept/reject/correct cycle with no mention of human decision-making, so no `HITL` or `AUTO` construct was used.

9. **Blank lines between statements are cosmetic only.** The spec doesn't discuss blank lines as significant syntax; I used them only for readability, assuming they carry no semantic meaning (the "Statement," "Scope," and "Flow" syntax sections define significance only for indentation and the `→` marker).
