# S05-p2: go_harness DSL Validity Check

## Snippet A

```text
HITL("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

**Verdict: INVALID**

**Rule cited (AUTO section, lines 303–317 of DSL.md):**

> `AUTO` is not a control-flow container.
> It does not contain `WHEN`, `→`, or an arbitrary flow.
> Uncertainty is not a DSL condition, state, variable, or keyword.

The spec gives, verbatim, the following as an explicit invalid example:

```text
AUTO
  WHEN decision.uncertain
    → HITL("Approve?")
```

Snippet A's `AUTO` block is structurally identical to this named-invalid example (an indented `WHEN decision.uncertain` with a `→ HITL(...)` branch nested under `AUTO`). This is precisely the construct the spec calls out by name as invalid.

**What is wrong / what would happen:**

- `AUTO` resolves a decision automatically when the outcome is "sufficiently determined by the available information, criteria, and authority" — determination of uncertainty is a runtime behavior of `AUTO` itself ("The DSL runtime determines uncertainty as part of automatic decision resolution"), not something the DSL author branches on with `WHEN`.
- By writing `WHEN decision.uncertain → HITL(...)` inside `AUTO`, the author is treating "uncertain" as if it were a condition/state variable that can be tested with `WHEN`. The spec explicitly forbids this: "Uncertainty is not a DSL condition, state, variable, or keyword."
- Per spec, the correct way to express "fall back to a human when `AUTO` can't resolve" is not shown as a positive pattern in this document for `AUTO` directly (the analogous mechanism shown, `FALLBACK`, is defined only in association with `HITL`'s response handling, not with `AUTO`). Since the DSL provides no valid syntax in this spec for attaching conditional logic to `AUTO`, this snippet cannot be corrected by just changing keywords within the same shape — the whole nested-flow-under-`AUTO` structure must be removed.
- Secondary observation: the leading `HITL("Approve release?")` on its own, disconstructed from the `AUTO` block, has no `FALLBACK` or subsequent flow attached to it in this snippet. The spec does not state that every `HITL` must be immediately followed by a `FALLBACK` or response-handling flow, so this alone is not flagged as a violation — it's just an isolated statement whose response is not shown being consumed. (Noted for completeness, but it is not the basis for the INVALID verdict.)

## Snippet B

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

**Verdict: INVALID, as literally given — with an assumption flagged below.**

**Rule cited (BREAK section, lines 95–107):**

> `BREAK` Exits the current `LOOP`.
> `BREAK` does not terminate the entire execution.
> `BREAK` may only exit a loop scope.
> Use `STOP` to terminate the entire execution.

**What is wrong / what would happen:**

Taken as a complete, self-contained snippet, there is no `LOOP:<name>` scope declared anywhere in it. `BREAK`'s defined behavior is to exit "the current `LOOP`," and the spec states `BREAK` "may only exit a loop scope." With no loop scope present in the snippet, there is no loop for `BREAK` to exit, so the statement has no defined target and the snippet is invalid under this rule.

The `DELEGATE`/`VERIFY`/`WHEN` portion is fine on its own and matches the spec's own worked example almost exactly:

```text
VERIFY implementation

WHEN implementation.accepted
  → BREAK

WHEN implementation.rejected
  → DELEGATE correction
```

Note the spec's own example actually pairs `accepted → BREAK` and `rejected → DELEGATE correction` (i.e., break out on success, retry/correct on rejection). Snippet B inverts this — it associates `BREAK` with the **rejected** branch — which is not itself a syntax error (the spec never dictates which outcome must map to which action; `WHEN` "may describe different outcomes" freely), so this inversion is not a basis for invalidity by itself. It only affects what the flow *means* (breaking out of the loop on rejection rather than on success), which is a process-design choice the DSL leaves open.

**Assumption stated explicitly:** The spec's own illustrative example for `VERIFY`/`WHEN` (lines 200–210) uses the identical bare pattern — `DELEGATE`/`VERIFY`/`WHEN ... → BREAK` — with no visible enclosing `LOOP:<name>` in the shown excerpt either. This means the spec is not fully explicit about whether a short snippet like this is meant to be judged as a complete, standalone program (in which case a bare `BREAK` with no visible `LOOP` is invalid) or as an excerpt implicitly assumed to live inside a surrounding loop (a common retry-until-accepted pattern), in which case it would be valid.

The spec does not state a rule for how to interpret partial/excerpted snippets, so this is not determined by the text. I resolved this ambiguity by treating each snippet in the task as a complete, self-contained unit to be judged strictly on what is shown (consistent with how Snippet A must be judged — its invalidity depends on exactly what's nested under `AUTO`, not on assumed surrounding context). Under that assumption, Snippet B is **INVALID** for lacking a `LOOP` scope for `BREAK` to exit.

If instead the reader assumes snippets are excerpts from within an existing `LOOP` (the alternate reading suggested by the spec's own example), Snippet B would be **VALID**, since everything else in it (`DELEGATE` → `VERIFY` → `WHEN` outcome → `BREAK`) follows the documented patterns exactly.
