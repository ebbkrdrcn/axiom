# go_harness DSL — Validity Review

## Snippet A

```text
HITL("Approve release?")
AUTO
  WHEN decision.uncertain
    → HITL("Approve release?")
```

**Verdict: INVALID**

**Rule cited (AUTO section):**

> `AUTO` is not a control-flow container.
> It does not contain `WHEN`, `→`, or an arbitrary flow.
>
> Uncertainty is not a DSL condition, state, variable, or keyword.
>
> For example, the following is invalid:
> ```text
> AUTO
>   WHEN decision.uncertain
>     → HITL("Approve release?")
> ```

**What is wrong:**

1. The nested `WHEN decision.uncertain → HITL(...)` block under `AUTO` is, word for word, the exact example the specification labels invalid. `AUTO` may not host a `WHEN`/`→` flow at all — it is not a control-flow container, so indenting statements beneath it is illegal regardless of what condition they test.
2. Independent of the nesting problem, the condition itself is illegal: `decision.uncertain` treats "uncertainty" as a DSL condition, but the spec explicitly says "Uncertainty is not a DSL condition, state, variable, or keyword." So even if `WHEN` could legally appear elsewhere, this particular condition could never be written by the process author — uncertainty is something "the DSL runtime determines... as part of automatic decision resolution," not something exposed for branching.
3. What would actually happen: per `AUTO`'s definition, "Resolve automatically when sufficiently determined; otherwise require human input." That human-input fallback is the runtime's *built-in* behavior for uncertainty — the author cannot (and need not) hand-code a `WHEN decision.uncertain` branch to trigger it, and attempting to do so is exactly the malformed construct the spec rules out.

**Note on the first line / spec gap:** The specification never defines a syntax for a bare `HITL("...")` statement immediately followed by a bare `AUTO` statement on the next line (as opposed to `AUTO` decorating a decision point, or `HITL` pairing with `FALLBACK`). It is not determinable from the spec whether line 2 (`AUTO`) is meant to qualify line 1's `HITL` call, replace it, or is simply a dangling statement. I assume the author's intent was "let this approval be auto-resolved when possible, otherwise fall back to the human `HITL` request," but the spec does not confirm this composition is legal syntax at all — this is a genuine gap, not something resolvable from the text given. Regardless, the snippet is already invalid on the grounds above.

## Snippet B

```text
DELEGATE implementation
VERIFY implementation
WHEN implementation.rejected
  → BREAK
```

**Verdict: INVALID as a standalone snippet** (assumption-dependent — see below)

**Rule cited (BREAK section):**

> Exits the current `LOOP`.
> ...
> `BREAK` may only exit a loop scope.

**What is wrong:**

- `DELEGATE implementation` / `VERIFY implementation` mirror the spec's own worked example exactly ("DELEGATE implementation / VERIFY implementation") and are individually well-formed: `DELEGATE` assigns the work, `VERIFY` evaluates the delegated result, and `VERIFY` "may establish outcomes that can be used by `WHEN`" — so `WHEN implementation.rejected` is a legitimate use of a verification outcome as a condition, structurally identical to the spec's `WHEN implementation.rejected → DELEGATE correction` example.
- The problem is `BREAK`. The spec is explicit that `BREAK` "may only exit a loop scope" — it exits "the current `LOOP`." As presented, this snippet contains no `LOOP:<name>` construct at all; there is no visible loop scope for `BREAK` to exit. Per the spec, a `BREAK` with no enclosing loop scope has nothing to break out of, which the rule does not permit.
- **Assumption stated explicitly:** the specification does not tell us whether this four-line snippet is the complete flow or an excerpt nested inside a `LOOP:<name>` block that simply isn't shown. I evaluated it literally as given — a standalone, non-indented sequence with no enclosing `LOOP` — in which case `BREAK` is invalid for lack of a loop scope to exit. If, instead, this snippet is assumed to be nested inside some outer `LOOP:<name>` (not shown in the excerpt), then `BREAK` would be valid and would exit that enclosing loop when `implementation` is rejected. The specification gives no basis for choosing between these two readings, so both possibilities are stated here; taken at face value (no `LOOP` present), the snippet is **INVALID**.
- One additional observation (not itself an error, just worth flagging): the spec's own example pairs `WHEN implementation.accepted → BREAK` and `WHEN implementation.rejected → DELEGATE correction` — i.e., breaking out on *acceptance* and re-delegating on *rejection*. Snippet B instead breaks out on *rejection*. Nothing in the spec's semantic rules forbids this — `WHEN` conditions and their associated actions are process-defined, and the DSL does not prescribe which outcome should map to which action — so this reversal is not, by itself, a validity problem, only a difference in process design from the illustrative example.
