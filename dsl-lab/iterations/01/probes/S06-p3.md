# Trace of the `LOOP:build` process

## The DSL under analysis

```text
LOOP:build
  DELEGATE build
  VERIFY build
  WHEN build.accepted
    → BREAK
EMIT build-report
```

Given fact: in every iteration, `VERIFY build` establishes the outcome `rejected` (i.e. `build.accepted` is never established).

## Preliminary reading of the structure

- `LOOP:build` opens a repeated execution scope. Per the specification, a `LOOP` "continues until `BREAK`, `STOP`, or another explicit control flow terminates it" and "does not imply any particular number of iterations."
- The loop body (the statements indented under `LOOP:build`) is: `DELEGATE build`, `VERIFY build`, `WHEN build.accepted → BREAK`.
- `EMIT build-report` is written at the same indentation level as `LOOP:build` itself, i.e. it is **not** indented inside the loop body. Per the "Scope" rule ("Indented statements belong to the preceding scoped construct"), a statement that is *not* indented under `LOOP:build` does not belong to the loop. So `EMIT build-report` is a statement that follows the loop in the overall flow ("Statements execute in declaration order unless an explicit control construct changes the flow"), and is reached only once the loop construct is exited.
- The only exit mechanism present in this snippet is the `BREAK` reachable through `WHEN build.accepted`. There is no `WHEN build.rejected` branch and no `STOP` anywhere in this snippet.

## Step-by-step: Iteration 1

1. **`DELEGATE build`** — Work described as "build" is assigned to another actor. Per the spec, `DELEGATE` "does not mean that the work is correct, complete, or accepted" — it only records that responsibility for the work has been handed off. No verification outcome exists yet at this point.
2. **`VERIFY build`** — The delegated result is evaluated against applicable acceptance criteria. Per the task's stated premise, this evaluation establishes the outcome `rejected` for this iteration. Per the spec, "`VERIFY` must not silently modify the result it evaluates," and "completion of delegated work is not equivalent to successful verification" — so the delegated build having been produced does not itself make it accepted; the outcome here is explicitly rejection.
3. **`WHEN build.accepted → BREAK`** — `WHEN` is a conditional flow: the statements following `→` execute only when the named condition is satisfied. Since this iteration's outcome is `rejected`, the condition `build.accepted` is not satisfied. Per the spec, `WHEN` "does not itself perform work, change state, delegate work, or produce an artifact" and only gates its flow — so `BREAK` is **not executed**.
4. **End of loop body reached** — No `BREAK`, `STOP`, or other explicit control-flow termination occurred in this pass. Per the spec, the `LOOP` "continues until `BREAK`, `STOP`, or another explicit control flow terminates it." Since none of these occurred, iteration 1 ends without terminating the loop, and control returns to the top of the loop body for another pass.

**Note on `EMIT build-report`:** it is not reached during iteration 1, since it lies outside (after) the loop scope and the loop has not been exited.

## Step-by-step: Iteration 2

The loop body is executed again from the top, identically to iteration 1, since the DSL only specifies this fixed body and the premise states every iteration's verification is rejected:

1. **`DELEGATE build`** — work is (again) assigned to an actor. The specification does not say whether this is a new delegation of "build" or a re-delegation/correction of the same work; the DSL snippet given contains no distinct correction step (e.g. no `DELEGATE correction`), so this is simply the same `DELEGATE build` statement executing again as the loop repeats.
2. **`VERIFY build`** — again evaluates the (re-)delegated result; per the given premise, the outcome is again `rejected`.
3. **`WHEN build.accepted → BREAK`** — the condition `build.accepted` is again not satisfied, so `BREAK` is again not executed.
4. **End of loop body reached** — again no termination condition (`BREAK`/`STOP`) occurred, so the loop does not exit, and (per "`LOOP` does not imply any particular number of iterations" and continues until explicitly terminated) it would proceed to a further iteration.

**Note on `EMIT build-report`:** it is not reached during iteration 2 either, for the same reason as iteration 1 — the loop has still not been exited.

## Whether and when `EMIT build-report` executes

- **During the first two iterations: `EMIT build-report` is not executed.** It sits outside the `LOOP:build` scope, and reaching it requires the loop to terminate. Termination in this snippet can only occur via the `BREAK` under `WHEN build.accepted`, and that condition was not satisfied in either iteration (verification established `rejected` both times).
- **More generally, under the stated premise:** the task states that "in every iteration" `VERIFY build` establishes `rejected." Given that premise, and given that this snippet provides no other path out of the loop (no `WHEN build.rejected` branch, no `STOP`, no other `BREAK`), `build.accepted` is never satisfied on any iteration, `BREAK` is never executed, and the loop — per the spec's own rule that a `LOOP` continues until explicitly terminated — never terminates. Consequently, under the stated premise, `EMIT build-report` is never executed, not just in the first two iterations but for as long as (and, per the premise "in every iteration," for all) iterations continue to reject.
- This is a direct consequence of the specification's rules for `LOOP` (continues until explicit termination), `WHEN` (gates its flow strictly on condition satisfaction, performs no work itself), and `BREAK` (only exits the loop, requires being reached to have effect) — combined with the fact that the given snippet defines no other exit route from the loop and no fallback/handling for a rejected outcome.

## Explicit assumptions (where the specification does not fully determine behavior)

The specification is a control/semantics spec, not an operational execution model, so a few points had to be assumed to produce a concrete step-by-step trace:

1. **Loop repetition mechanics.** The spec states a `LOOP` "continues until `BREAK`, `STOP`, or another explicit control flow terminates it" but does not explicitly describe the mechanism by which it "repeats" (e.g., whether control returns to the first statement of the body after the last statement is reached with no termination). I assumed the natural reading: when the end of the loop body is reached without a terminating control construct having fired, execution returns to the start of the loop body for a new iteration.
2. **What "iteration" delegation means the second time.** The spec's example under `VERIFY` (`VERIFY implementation` / `WHEN implementation.rejected → DELEGATE correction`) suggests a distinct `DELEGATE correction` statement is the idiomatic way to model rework after rejection. The DSL given in the task has no such branch or correction step — only a single `DELEGATE build` inside the loop with no handling for `build.rejected`. I assumed this means the same `DELEGATE build` statement is simply re-executed on the next pass through the loop body (since the DSL does not define any alternate statement to run on rejection), rather than inferring an implicit "correction" step not present in the source.
3. **Absence of a rejection branch.** The specification does not state what a runtime must do when a `LOOP` body contains no `WHEN` branch matching the actual outcome (here, no `WHEN build.rejected`). I assumed — consistent with `WHEN` being purely a conditional gate that "does not itself perform work" — that when no `WHEN` condition in the body matches, execution simply falls through to the end of the (loop) body with no additional effect, which for a loop means proceeding to the next iteration (per assumption 1) rather than any other behavior (e.g., an implicit error or implicit exit), since the specification defines no such implicit behavior.
4. **Indefinite/eventual behavior beyond two iterations.** The task only asks about the first two iterations, but also asks "whether and when" `EMIT build-report` executes; answering that fully requires reasoning about what happens beyond iteration 2. I assumed the premise "in every iteration, `VERIFY build` establishes rejected" is meant to hold for all iterations that occur (not just the first two), which is why the analysis concludes `EMIT build-report` is never reached under this premise, rather than merely "not reached in the first two iterations."
