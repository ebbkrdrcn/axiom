# Execution Trace

```text
FORK
  → DELEGATE lint
      VERIFY lint
      WHEN lint.rejected
        → STOP
  → DELEGATE docs
      EMIT docs
JOIN
EMIT build
```

## Step-by-step execution

1. **`FORK`** executes. Per spec, "Each `→` starts an independent flow" and "the branches may execute concurrently." Two independent flows begin:
   - **Flow A (lint branch):** `DELEGATE lint` → `VERIFY lint` → `WHEN lint.rejected` → `STOP`
   - **Flow B (docs branch):** `DELEGATE docs` → `EMIT docs`

2. **Flow A, statement 1 — `DELEGATE lint`.** Work ("lint") is assigned to an actor. Per spec, this "does not mean that the work is correct, complete, or accepted" — it only establishes responsibility.

3. **Flow B, statement 1 — `DELEGATE docs`.** Concurrently (spec does not fix a relative ordering between branches beyond "may execute concurrently"), work ("docs") is assigned to an actor.

4. **Flow A, statement 2 — `VERIFY lint`.** This evaluates the lint result against applicable acceptance criteria. Per the injected event, this evaluation establishes the outcome `rejected`. Per spec, "Verification may establish outcomes that can be used by `WHEN`," so this outcome is now available to flow control.

5. **Flow A, statement 3 — `WHEN lint.rejected`.** The condition `lint.rejected` is satisfied by the outcome just established in step 4. `WHEN` itself "does not perform work, change state, delegate work, or produce an artifact" — it only routes the flow into its `→` branch.

6. **Flow A, statement 4 — `STOP`.** At the exact moment this executes, the injected event states that Flow B "has executed `DELEGATE docs` but has not yet executed `EMIT docs`" — i.e., Flow B is mid-flight, between its two statements.

   `STOP`'s defined effect: "Terminates execution... No subsequent statement is executed after `STOP`." The spec draws this scope explicitly by contrast with `BREAK`: `BREAK` "does not terminate the entire execution" and can only "exit a loop scope," whereas `STOP` is introduced precisely as the construct to use "to terminate the entire execution." `STOP` is therefore not scoped to the current branch, loop, or flow — it terminates the process's execution as a whole.

   Consequently, `STOP` terminates:
   - Flow A itself (trivially, nothing follows it there anyway),
   - Flow B, the sibling flow concurrently started by the same `FORK`, which is interrupted after `DELEGATE docs` and before reaching `EMIT docs`,
   - the top-level flow that contains the `FORK`, before it reaches `JOIN` or `EMIT build`.

## Answers

**Is `EMIT docs` executed?**
No. `EMIT docs` is the next statement in Flow B, and it has not executed at the moment `STOP` fires. Since `STOP` terminates the entire execution (not merely the lint branch/flow it appears in), Flow B does not resume to reach `EMIT docs`. The rule "no subsequent statement is executed after `STOP`" applies to the whole execution, so `EMIT docs` is never executed.

**Is `JOIN` completed?**
No. `JOIN`'s defined behavior is: "Execution continues only after all required forked flows have completed." Two independent reasons both block completion here:
- Flow B never completes (it is cut off before `EMIT docs`), so the condition for `JOIN` to complete is never met; and
- more fundamentally, `STOP` terminates the entire execution before the top-level flow would even reach the `JOIN` statement, so `JOIN` is not merely "left waiting" — it is never reached/executed at all.

**Is `EMIT build` executed?**
No. `EMIT build` follows `JOIN` in the top-level flow, which is itself never reached. It is a subsequent statement relative to the terminating `STOP`, and "no subsequent statement is executed after `STOP`" precludes it.

## Explicit notes on what the specification does not determine (assumptions made)

- **Cross-flow scope of `STOP`:** The specification never states in so many words "`STOP` inside one forked branch terminates sibling branches too." This trace infers that global scope from the only place the spec characterizes `STOP`'s reach — the contrast with `BREAK` ("`BREAK` does not terminate the entire execution... Use `STOP` to terminate the entire execution"). Taking "the entire execution" literally (as opposed to "the entire branch" or "the entire loop," which is how `BREAK` is scoped) is the interpretation used here, and it is the only interpretation consistent with `STOP` and `BREAK` being distinct constructs with distinct guarantees. Under this reading, `STOP` anywhere in the process ends everything, including flows begun by an enclosing or sibling `FORK`.
- **Relative timing of the two `FORK` branches:** The spec only says branches "may execute concurrently," not how their steps interleave. This does not affect the answer, since the injected event fixes Flow B's position (`DELEGATE docs` done, `EMIT docs` not done) at the moment `STOP` fires, regardless of exact interleaving.
- **Fate of the in-flight `docs` delegation itself:** The DSL only governs which *statements* execute; it explicitly disclaims implementation mechanics ("`DELEGATE` defines responsibility, not execution mechanics," and the DSL "remains independent of specific runtime mechanisms"). So while this trace is confident that the DSL statement `EMIT docs` is never executed, the specification says nothing about whether the external actor's already-assigned `docs` work is itself cancelled, abandoned, or left to finish outside the DSL's view — that is outside what the DSL defines.
