# Execution Trace

## Program

```text
FORK
  → DELEGATE unit-tests
      VERIFY unit-tests
  → DELEGATE integration-tests
      VERIFY integration-tests
JOIN
WHEN unit-tests.accepted
  → TRANSITION "Ready"
WHEN integration-tests.rejected
  → TRANSITION "Debugging"
```

## Injected events

- `VERIFY unit-tests` → establishes `unit-tests.accepted`.
- `VERIFY integration-tests` → establishes `integration-tests.rejected`; this VERIFY finishes **later** than the unit-tests branch.

## Step-by-step execution

**Step 1 — `FORK`**
Two independent, concurrent flows are started (per the FORK definition: "each `→` starts an independent flow"; "branches may execute concurrently").

- Branch A: `DELEGATE unit-tests` → `VERIFY unit-tests`
- Branch B: `DELEGATE integration-tests` → `VERIFY integration-tests`

Within each branch, statements execute in declaration order (DELEGATE before VERIFY), since nothing overrides the default "Flow" rule. Across branches, no ordering is imposed by the DSL other than what the injected events specify.

**Step 2 — Branch A: `DELEGATE unit-tests`**
Work is assigned to an actor. Per spec, this does not mean the work is correct, complete, or accepted — only that responsibility for it has been assigned.

**Step 3 — Branch A: `VERIFY unit-tests`**
The result is evaluated against acceptance criteria. The injected event resolves this evaluation as `accepted`. This VERIFY completes (call this time t1). Per spec, "Verification may establish outcomes that can be used by `WHEN`," so the fact `unit-tests.accepted` becomes available to the surrounding flow. Completion of the delegated work here is explicitly *not* the same as this acceptance — acceptance is the independent outcome of VERIFY, which is what happened here.

**Step 4 — Branch B: `DELEGATE integration-tests`**
Work is assigned to an actor, concurrently with Branch A's activity.

**Step 5 — Branch B: `VERIFY integration-tests`**
The result is evaluated. The injected event resolves this evaluation as `rejected`, establishing `integration-tests.rejected`. This VERIFY completes at a time (call it t2) that is *later* than Branch A's VERIFY (t2 > t1).

**Step 6 — `JOIN`**
`JOIN` "waits for the concurrent flows started by the corresponding `FORK`" and "execution continues only after all required forked flows have completed." Both branches (unit-tests and integration-tests) are the flows started by this FORK, so both are required. Execution therefore blocks until the later of the two completions, i.e., until t2 (Branch B's `VERIFY integration-tests` finishes). At this point both facts — `unit-tests.accepted` and `integration-tests.rejected` — are established and available.

**Step 7 — `WHEN unit-tests.accepted`**
This WHEN is evaluated in the flow following JOIN, in declaration order. The condition `unit-tests.accepted` is satisfied (established in Step 3), so its flow executes:

- `TRANSITION "Ready"` — the process state changes to `"Ready"`.

**Step 8 — `WHEN integration-tests.rejected`**
This WHEN is next in declaration order. The condition `integration-tests.rejected` is satisfied (established in Step 5), so its flow executes:

- `TRANSITION "Debugging"` — the process state changes to `"Debugging"`.

No `BREAK`, `STOP`, or other control construct appears anywhere in this program, so nothing prevents both WHEN blocks from being evaluated, and nothing stops execution after either TRANSITION. There is no further statement after Step 8, so execution ends there.

## Final process state

**`"Debugging"`**

`TRANSITION` "changes the current process state" (singular — a process is described as being *in* a state, e.g., the example "the process has moved to the `Code Review` state"). Since both WHEN conditions are independently true given the injected events, both TRANSITIONs fire in declaration order, and the second one (`"Debugging"`) overwrites the first (`"Ready"`) as the current state at the point execution ends.

## Explicit gaps in the specification and assumptions made

The specification does not fully determine this trace. The following points are underdetermined, and the assumptions used above are stated explicitly:

1. **No mutual exclusion between WHEN blocks.**
   The spec's own example (`tests.passed` / `tests.failed`) implies WHEN blocks are typically used to describe mutually exclusive outcomes of *the same* evaluation, but nothing in the spec states that WHEN blocks are exclusive (an if/elif construct) or that only one WHEN may fire per "decision point." Here, the two WHEN conditions come from two *different* VERIFY operations and both are independently true, so — per what the spec does say — both flows execute. **Assumption: WHEN blocks are evaluated independently and non-exclusively; every WHEN whose condition holds executes its flow.** This is a legitimate DSL-level reading, though the resulting double TRANSITION may indicate a process-design issue outside the scope of what the DSL itself forbids.

2. **Overwrite semantics of `TRANSITION`.**
   The spec says TRANSITION "changes the current process state" but does not explicitly state what happens when two TRANSITIONs execute in the same pass (e.g., whether the second overwrite is valid, whether it should be treated as a conflict/error, or whether state is somehow multi-valued). **Assumption: the process has a single current-state value, and each TRANSITION overwrites it; the last TRANSITION to execute (in declaration order) determines the final state.** Under this assumption, the final state is `"Debugging"`, since `WHEN integration-tests.rejected` is declared after `WHEN unit-tests.accepted`.

3. **Ordering of WHEN evaluation relative to JOIN.**
   The spec does not explicitly state that WHEN statements appearing textually after JOIN are only evaluated once JOIN has released execution, but this follows directly from the general "Flow" rule (statements execute in declaration order unless a control construct changes the flow) combined with JOIN's blocking behavior. No assumption beyond direct application of stated rules was needed here.

4. **"Required" forked flows.**
   `JOIN`'s definition refers to "required" forked flows without defining how a flow is marked required or optional. **Assumption: in the absence of any marking, all flows started by the corresponding FORK are required**, so JOIN here waits for both the unit-tests and integration-tests branches.

5. **Concurrent completion ordering.**
   The DSL states branches "may execute concurrently" but does not define a global clock or ordering guarantees between branches. The trace above relies entirely on the injected event's explicit statement that `VERIFY integration-tests` finishes later than the unit-tests branch to establish that JOIN unblocks at that later time; no additional assumption was needed for this beyond taking the injected event at face value.
