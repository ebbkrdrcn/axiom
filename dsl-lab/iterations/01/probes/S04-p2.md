# S04 — go_harness DSL Answer

## DSL

```text
REQUIRE deployment-target

HITL("Which region should we deploy to?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP

DELEGATE deployment
EMIT deployment-log
```

## Assumptions

1. **"needs the deployment-target before anything else" → `REQUIRE` as the first statement.** The spec says `REQUIRE` "declares information, context, state, or another condition required for subsequent execution" and "the requirement must be satisfied before execution continues." It does not itself specify ordering semantics beyond that, but placing it as the first statement in declaration order is the natural way to express "before anything else," since "statements execute in declaration order unless an explicit control construct changes the flow."

2. **Identifier naming.** `deployment-target` and `deployment-log` are used as bare identifiers (per the `Identifier` syntax rule), directly reusing the hyphenated terms from the requirement text. The spec does not define a naming convention for identifiers beyond "may be used to refer to requirements, results, states, artifacts, or other process-defined entities," so this is an assumption about identifier spelling, not something the spec mandates.

3. **No explicit "success" branch after `HITL`.** The spec's only worked example of `HITL` combined with response handling is:
   ```text
   HITL("<message>")
     → FALLBACK
         → <flow>
   ```
   It shows `FALLBACK` as the branch taken "when the expected response is unavailable or insufficient," but it never shows syntax for an explicit "success" arrow alongside `FALLBACK`. I assumed that the normal (successful) continuation is simply the subsequent statements after the `HITL`/`FALLBACK` scope closes — i.e., if the fallback is not triggered, execution falls through to `DELEGATE deployment` / `EMIT deployment-log`. The spec does not explicitly confirm this fall-through model; it only states "the fallback flow is used only when the expected response cannot be used to continue the normal flow," implying a normal flow exists but not diagramming it.

4. **"If no usable answer is obtained" → triggers `FALLBACK`.** I mapped "no usable answer" to the `FALLBACK` condition ("when an expected response is unavailable or insufficient"). This seems like a direct fit, not much of a stretch, but it is still an interpretive mapping since the requirement's wording ("no usable answer") is not a DSL term.

5. **"terminate the whole execution" → `STOP`, not `BREAK`.** The spec is explicit that `BREAK` only exits a `LOOP` scope and `STOP` terminates the entire execution. Since there is no `LOOP` in this process at all, `STOP` is the only construct that matches "terminate the whole execution."

6. **Order of `TRANSITION "Blocked"` then `STOP`.** The requirement states the actions in the order "transition to state Blocked and terminate," so I preserved that order literally. The spec does not say anything about required ordering between `TRANSITION` and `STOP` beyond normal declaration-order execution, and since "no subsequent statement is executed after STOP," the order matters mechanically too — `TRANSITION` must come before `STOP` or it would never run.

7. **No `VERIFY` after `DELEGATE deployment`.** The requirement does not mention evaluating or accepting the deployment result, only delegating it and emitting a log. Since the spec presents `VERIFY` as optional evaluation ("a delegated result may subsequently be evaluated by VERIFY," not "must"), I did not add one, though this is an assumption that no acceptance check is wanted here.

8. **No `WHEN` construct used.** I considered modeling "usable answer obtained" vs. "not obtained" as two `WHEN` branches (mirroring the `VERIFY`/`WHEN` accepted/rejected example), but the spec's only shown pattern for `HITL` response handling is the `HITL → FALLBACK` form, not `HITL` followed by `WHEN`. Since `WHEN` is described as evaluating outcomes established by things like `VERIFY`, and there is no `VERIFY` of the human response in the spec's vocabulary, I used the dedicated `FALLBACK` mechanism instead, which is the construct the spec defines specifically for this "response unavailable/insufficient" scenario.

9. **No `LOOP`, `FORK`/`JOIN`, or `AUTO` used.** Nothing in the requirement implies repetition, concurrency, or automatic decision-making eligible for `AUTO` (which requires the agent to be able to determine a single protocol-compatible decision from available information/criteria/authority — the requirement gives no such criteria for the region decision, and it explicitly is framed as asking a human). So these constructs were omitted rather than assumed-in.

10. **Top-level, unscoped statements.** The whole answer is written as a flat top-level flow with no enclosing `LOOP` or named scope, since the requirement describes a single linear process with no repetition or naming requirement. The spec's `Scope` section implies indentation denotes nesting under a "preceding scoped construct," but does not require the top level itself to be wrapped in any construct.
