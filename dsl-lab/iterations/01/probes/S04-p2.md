```text
REQUIRE deployment-target

HITL("Which region should we deploy to?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP

DELEGATE deployment
EMIT deployment-log
```

## Assumptions

1. **"Before anything else" is expressed by declaration order.** The spec's Flow rule says statements execute in declaration order unless a control construct changes it, and `REQUIRE` "must be satisfied before execution continues." Placing `REQUIRE deployment-target` as the very first statement is assumed to satisfy "needs the deployment-target before anything else"; the spec does not define a stronger "precondition" concept than ordering.

2. **"No usable answer is obtained from the human" maps to `FALLBACK`.** The spec defines `FALLBACK` as the flow used "when an expected response is unavailable or insufficient" after a `HITL`. "No usable answer" is assumed to be exactly this case (unavailable or insufficient response), rather than, e.g., an explicit human "no" decision that would need a `WHEN` on some outcome. The spec provides no `WHEN`-based vocabulary (e.g., `decision.received`) for HITL outcomes, so `FALLBACK` is the only mechanism given for handling an unusable response.

3. **The "otherwise" (usable-answer) path is the plain continuation after `HITL`.** The spec shows no explicit "success" branch syntax for `HITL` other than the surrounding flow continuing normally once a usable response is available ("execution continues according to the surrounding flow" is stated for `WAIT`, and analogous behavior is assumed for `HITL` once its response is usable). So `DELEGATE deployment` / `EMIT deployment-log`, placed after the `HITL`/`FALLBACK` block at the outer indentation level, are assumed to run only when the `FALLBACK` branch was not taken (since the `FALLBACK` branch itself ends in `STOP`, which prevents falling through).

4. **Indentation of multiple statements inside the `FALLBACK` branch.** The spec's only `FALLBACK` example shows a single `→ <flow>` line and does not illustrate multiple statements inside a fallback branch. This is modeled on the `FORK` "Forked Flow" rule ("indented statements following a branch belong to that branch until the branch scope ends"), so `TRANSITION "Blocked"` is written on the `→` line and `STOP` is nested beneath it as a further-indented statement belonging to the same branch.

5. **Order "transition to Blocked, then terminate."** The requirement's stated order (transition first, then terminate) is preserved literally: `TRANSITION "Blocked"` precedes `STOP`. Since "no subsequent statement is executed after `STOP`," this ordering is required for the transition to take effect at all.

6. **Identifiers for delegate/emit targets.** `deployment` and `deployment-log` are used as bare identifiers (per the Identifier syntax rule) for the delegated work and the emitted artifact, respectively, since the spec allows identifiers to "refer to requirements, results, states, artifacts, or other process-defined entities" without further constraint on naming.

7. **No `VERIFY` step is added.** The task does not ask for evaluation of the delegated deployment's result, and the spec treats `DELEGATE` and `VERIFY` as separate, independently-invoked operations. Since verification isn't mentioned in the requirement, none is added, even though the spec's own examples often pair `DELEGATE` with `VERIFY`.

8. **No `LOOP`, `FORK`, or `WHEN` are used.** The requirement describes a single linear process with one human-decision point and no repetition, concurrency, or multiple independently-triggered conditions, so those constructs are omitted as unnecessary.

9. **`REQUIRE deployment-target` is treated as satisfied implicitly before proceeding**, per "the requirement must be satisfied before execution continues" — the DSL does not prescribe how this is checked or what happens if it fails, since the task gives no instruction for a missing deployment-target, only for a missing/unusable HITL response.
