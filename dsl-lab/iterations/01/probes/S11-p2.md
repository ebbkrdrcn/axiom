# Execution trace of `LOOP:review`

## 1. How the program parses (scope only, from the "Syntax" section)

Reading indentation as scope, per the Syntax rules ("Indented statements belong to the preceding scoped construct" and "Indented statements following a branch belong to that branch until the branch scope ends"):

- `LOOP:review` opens a loop scope containing:
  - `FORK` — with two branches:
    - Branch **A** (security-review branch): `DELEGATE security-review` → `VERIFY security-review` → `WHEN security-review.rejected → BREAK`
    - Branch **B** (docs-review branch): `DELEGATE docs-review` → `VERIFY docs-review`
  - `JOIN` (back at the loop-body level, after the `FORK` block)
  - `TRANSITION "Reviewed"` (also at the loop-body level, after `JOIN`)
- `EMIT review-summary` is at the **same indentation as `LOOP:review` itself**, i.e. it is *not* inside the loop. It is the statement that follows the entire loop construct.

This last point is unambiguous from the spec's syntax rules and matters a lot below: whatever happens to the loop, `EMIT review-summary` is outside it and is not repeated per iteration.

## 2. Step-by-step trace, iteration 1

1. **`LOOP:review`** — a loop scope begins. Per spec, "`LOOP` does not imply any particular number of iterations"; it runs until `BREAK`, `STOP`, or another explicit control flow terminates it. Iteration 1 starts.
2. **`FORK`** — per spec, "Each `→` starts an independent flow" and "The branches may execute concurrently." Per the injected events, both branches start:
   - Flow A begins: `DELEGATE security-review` — work is assigned to an actor. Per spec, `DELEGATE` "does not mean that the work is correct, complete, or accepted" — it only assigns responsibility.
   - Flow B begins: `DELEGATE docs-review` — work is assigned to a (presumably different) actor, concurrently with Flow A.
3. **Flow A: `VERIFY security-review`** executes and, per the injected event, establishes the outcome `security-review.rejected`. This is exactly the kind of thing `VERIFY` is defined to do: "Verification may establish outcomes that can be used by `WHEN`." Completion of the delegated work is not itself the same as this outcome — the spec is explicit that "Completion of delegated work is not equivalent to successful verification" — but the injected event tells us the evaluation has concluded and produced `rejected`.
4. **Flow A: `WHEN security-review.rejected`** — the condition is now satisfied. Per spec, `WHEN` "does not itself perform work, change state, delegate work, or produce an artifact"; it only selects which flow executes. The flow selected is `→ BREAK`.
5. **Flow A: `BREAK`** executes. Per spec, `BREAK` "Exits the current `LOOP`." The only `LOOP` in scope here is `LOOP:review`, so there is no ambiguity about *which* loop is targeted. `BREAK` "does not terminate the entire execution" and "may only exit a loop scope" — so this affects `LOOP:review` only, not the whole program.
   - At this point Flow A has executed every statement in its branch. There is nothing left in Flow A.
6. **Meanwhile, Flow B** is still in progress: per the injected event, "the docs-review branch [is] still running (its `VERIFY` has not happened yet)." So at the moment `BREAK` fires, `DELEGATE docs-review` has been issued but `VERIFY docs-review` has not yet executed or produced an outcome.

This is the point at which the two things the task asks about — the fate of the docs-review branch and of `JOIN` — become genuinely underdetermined by the specification.

## 3. Where the specification stops determining the outcome

Two spec statements are both explicit but not reconciled with each other for this exact situation:

- `JOIN`: "Waits for the concurrent flows started by the corresponding `FORK`." "Execution continues only after all required forked flows have completed." This is stated **unconditionally** — no exception is carved out for a sibling branch having triggered a loop-exiting control statement.
- `BREAK`: "Exits the current `LOOP`." This says *what* is exited, but not *when* the exit takes effect relative to a `FORK`/`JOIN` region that is still open, nor what becomes of a sibling forked flow that has not completed.

The specification also gives no mechanism anywhere (in `FORK`, `JOIN`, `BREAK`, or the "Semantic Principles") for cancelling, aborting, or otherwise short-circuiting an in-progress `DELEGATE`/`VERIFY` sequence. Nor do the worked examples show `BREAK` used from inside a `FORK` branch — the `BREAK` example and the `FORK` example are each self-contained and never combined. So the composition in this task (a `BREAK` fired inside one `FORK` branch while a sibling branch is still unfinished, before `JOIN` is satisfied) is **not determined by the specification as given**. Two readings are both defensible from the text alone:

- **Interpretation 1 — JOIN is a strict, literal barrier (adopted below as the primary trace).** `JOIN`'s wait condition is stated without exception, and nothing authorizes treating Flow B as cancelled or as "not required" just because Flow A finished (via `BREAK`) early. Under this reading, the docs-review flow is not abandoned: it keeps running, `VERIFY docs-review` eventually executes and establishes some outcome, and only once *both* flows have completed does `JOIN` unblock. `BREAK`'s effect (exiting the loop) is then applied at the next point where control returns to the loop body's own sequential flow, i.e. immediately after `JOIN` — which means the loop is exited instead of continuing to `TRANSITION "Reviewed"`.
- **Interpretation 2 — BREAK is immediate and pre-emptive.** `BREAK` exits `LOOP:review` the instant it executes, with no deferral. Under this reading, `JOIN` is never reached at all (control leaves the loop scope before the sequential flow gets there), the still-running docs-review flow is simply abandoned/orphaned (its eventual `VERIFY docs-review` outcome, if it ever occurs, no longer has any bearing on `LOOP:review`'s control flow), and `TRANSITION "Reviewed"` is skipped for the same reason.

Neither reading requires inventing more machinery than the other in some places and less in others (Interpretation 2 requires an implicit, spec-unstated notion of "abandon a not-yet-completed concurrent flow"; Interpretation 1 requires only applying `JOIN`'s own literal wording, but requires reading `BREAK`'s effect as deferred rather than instantaneous, which the text also does not state). **I adopt Interpretation 1** for the main trace below because it needs no invented cancellation semantics — everything it does is a direct, unmodified application of `JOIN`'s own stated rule — while flagging Interpretation 2's diverging step explicitly.

## 4. Trace, continued (Interpretation 1)

7. **`JOIN` is reached (in program order) but blocks**, because Flow B ("a concurrent flow started by the corresponding `FORK`") has not completed. Flow A having reached `BREAK` does not reduce the set of "required forked flows" that `JOIN` is defined to wait for — the spec states no such reduction.
8. **Flow B continues**: `DELEGATE docs-review` completes and `VERIFY docs-review` executes, establishing some outcome. (The injected events do not tell us what that outcome is, and it does not matter for this trace: unlike Flow A, this snippet contains no `WHEN docs-review.*` to consume it, so `VERIFY docs-review`'s result has no further effect on the flow shown here.)
9. **`JOIN` unblocks**: both required forked flows (A and B) have now completed, so "execution continues" per spec.
10. **`TRANSITION "Reviewed"` does not execute.** Even though `JOIN` has released the loop body, the `BREAK` recorded in Flow A still governs: `BREAK`'s whole purpose is that "the loop continues until `BREAK` ... terminates it," so the loop-body's remaining statement in this iteration (`TRANSITION "Reviewed"`) is not run, and no further iteration of `LOOP:review` begins. (Had there been no `BREAK`, `TRANSITION "Reviewed"` would have executed and the loop would have gone back to `FORK` for another undetermined iteration.)
11. **`LOOP:review` is exited.** Per spec this only ends the loop scope — "`BREAK` does not terminate the entire execution."
12. **`EMIT review-summary` executes.** It sits outside the loop (see §1), so it is reached exactly once, as the statement following the whole `LOOP:review` construct. Per spec, `EMIT` "represents an externally meaningful output"; the spec does not prescribe how it is produced, stored, or transmitted.
13. **Execution ends.** There is no statement after `EMIT review-summary`, and nothing in the program has invoked `STOP` or created a further pending flow, so the trace ends normally (not because of an error or an unresolved requirement, but simply because the program is finished).

## 5. Same trace under Interpretation 2, for completeness

If instead `BREAK` is read as immediately, pre-emptively exiting `LOOP:review` the moment it executes in Flow A (step 6 above):

- `JOIN` is never executed at all — control leaves the loop scope before the sequential flow reaches it.
- The docs-review branch (Flow B) is abandoned mid-flight: `VERIFY docs-review` may or may not ever run in some sense outside the DSL's control flow, but the specification gives it no way to affect `LOOP:review` any further; it becomes an orphaned concurrent flow the DSL text does not describe how to reconcile.
- `TRANSITION "Reviewed"` is skipped, for the same reason as in Interpretation 1 (never reached).
- `EMIT review-summary` still executes exactly once, and execution still ends afterward, exactly as in §4 steps 12–13.

The two interpretations therefore agree on every outcome the task asks about **except** whether `JOIN` actually executes/blocks and whether the docs-review flow is left to finish or is abandoned. That specific point is what the specification, as given, does not determine.

## 6. Summary answers to the task's specific questions

- **Docs-review branch**: Its fate is the crux of the underdetermined point. Under the literal, unconditional reading of `JOIN` (Interpretation 1, adopted as primary), it is not abandoned — it keeps running and its `VERIFY docs-review` completes, satisfying `JOIN`'s wait condition; its outcome has no further effect here because nothing in this snippet consumes it. Under the alternative, pre-emptive reading of `BREAK` (Interpretation 2), it is abandoned/orphaned when the loop exits early, and the specification does not say what becomes of it after that.
- **`JOIN`**: Under Interpretation 1, it is reached and blocks until docs-review's flow completes, then unblocks per its own literal definition. Under Interpretation 2, it is never reached/executed at all, because the loop exits before control reaches it.
- **`TRANSITION "Reviewed"`**: Does not execute, under either interpretation. `BREAK` having fired in Flow A means the loop is terminated rather than continuing to this statement, whether that termination is applied immediately or only after `JOIN` resolves.
- **`EMIT review-summary`**: Executes exactly once, under either interpretation. It is textually outside the loop (see §1), `BREAK` explicitly "does not terminate the entire execution," and nothing else in the program (no `STOP`, no other terminating construct) prevents it from running once `LOOP:review` has been exited.
- **Overall**: Execution ends normally after `EMIT review-summary`, having run exactly one iteration of `LOOP:review` that was cut short by `BREAK` (skipping that iteration's `TRANSITION "Reviewed"`), with no second iteration attempted.

## 7. Explicit assumptions made

1. `LOOP:review` is the only loop in scope, so `BREAK`'s target ("the current `LOOP`") is unambiguous.
2. Where the spec does not reconcile `JOIN`'s unconditional wait-for-completion rule with a `BREAK` fired in a sibling branch before that branch completes, I assumed `JOIN`'s literal wording governs (it must still wait for the docs-review flow to complete) rather than assuming an unstated cancellation mechanism — this is Interpretation 1 in §3/§4. I have also given Interpretation 2 (§5) as the explicit alternative, since the spec does not rule it out either.
3. `VERIFY docs-review`'s eventual outcome is assumed not to matter to this trace, since the given DSL contains no `WHEN docs-review.*` construct to consume it, and the injected events do not specify what that outcome is.
4. Execution "ending" after `EMIT review-summary` is treated as ordinary program completion (running out of statements), not as an error or a stalled/unsatisfied `REQUIRE`, since nothing in the task's injected events indicates a requirement failed.
