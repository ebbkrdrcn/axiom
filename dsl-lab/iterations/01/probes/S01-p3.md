# S01 — Answer

## DSL

```text
DELEGATE implementation
VERIFY implementation

HITL("Merge this change?")
  → AUTO

WHEN merge.accepted
  → TRANSITION "Merged"

WHEN merge.rejected
  → TRANSITION "Rework"
```

## Assumptions

The specification does not fully determine several things needed to write this DSL. Each assumption below states the gap and the choice made to fill it.

1. **How `AUTO` attaches to `HITL`.** The spec defines `AUTO` and `HITL` separately and states that `HITL` "must not be silently replaced by an agent decision unless the surrounding definition explicitly permits automatic resolution through `AUTO`," but it never shows the concrete syntax for combining them. It also states `AUTO` "is not a control-flow container" and does not contain `WHEN`/`→`/arbitrary flow — but that rule is about what `AUTO` itself may contain, not about whether `AUTO` may appear as a branch under something else. By analogy with the documented `FALLBACK` pattern (`HITL("...") \n → FALLBACK \n → <flow>`), I assumed `AUTO` can appear the same way, as a bare branch under `HITL` (`HITL("...") \n → AUTO`, with no further nested flow, consistent with "not a control-flow container"), meaning: this human decision boundary may be resolved automatically when sufficiently determined, otherwise the human is actually asked. This is my biggest assumption — the spec may intend a different combined form (e.g. `AUTO` preceding `HITL` as a modifier keyword, or `AUTO` and `HITL` as two independent, mutually exclusive statements chosen by the runtime), and no example in the text disambiguates this.

2. **Identifiers produced by the merge decision.** The spec confirms that `VERIFY` "may establish outcomes that can be used by `WHEN`" and shows the pattern `implementation.accepted` / `implementation.rejected`. It does not say whether `HITL`/`AUTO` decisions likewise establish `WHEN`-usable outcomes, or what they would be named. Since the requirement explicitly needs to branch on the merge decision, I assumed (by analogy with the `VERIFY` example) that the resolved decision is exposed as `merge.accepted` / `merge.rejected`. Other names (e.g. `decision.merge`, `merge_decision.approved`) would be equally consistent with the spec; I picked the form that mirrors the one worked example given.

3. **No `FALLBACK` was added.** `FALLBACK` handles the case where "an expected response is unavailable or insufficient" for a `HITL`. The task requirement doesn't describe what should happen if the human doesn't respond or gives an unusable answer, so I omitted `FALLBACK` rather than inventing behavior not present in the requirement. If non-response handling is actually wanted, the spec's `FALLBACK` construct would need to be added under the `HITL`.

4. **No branching on `VERIFY implementation`'s own outcome.** The requirement text says only "delegate the implementation and verify it," then moves straight to the merge decision — it never says what happens if verification fails. The spec's own example (`VERIFY implementation` → `WHEN implementation.accepted/rejected` → possible `DELEGATE correction`) suggests failed verification would normally loop back, but since the task's stated requirement doesn't mention this case, I did not invent a rejection/correction branch for the implementation step, to avoid adding behavior the requirement didn't ask for. This means the DSL as written proceeds to the merge decision unconditionally after `VERIFY implementation`, which is a literal reading of the requirement rather than a claim that this is good process design.

5. **No `REQUIRE` statements.** The requirement doesn't mention any preconditions (e.g. repository access, merge criteria source), so none were added. `REQUIRE` was left out entirely rather than guessed at.

6. **Top-level scope.** The spec shows constructs both bare and inside `LOOP`/`FORK` scopes but doesn't state whether a standalone process must be wrapped in an outer named scope. Since the requirement describes a single linear procedure with no repetition or concurrency, I wrote it as a flat, unscoped sequence of statements, per the "Flow" section's default: "Statements execute in declaration order unless an explicit control construct changes the flow."
