# go_harness DSL

```text
DELEGATE implementation
VERIFY implementation

AUTO
HITL("Merge this change?")

WHEN merge.approved
  → TRANSITION "Merged"

WHEN merge.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Composition of `AUTO` and `HITL`**: The specification defines `AUTO` as "resolve automatically when sufficiently determined; otherwise require human input," and states that `HITL` may be "silently replaced by an agent decision" only when "the surrounding definition explicitly permits automatic resolution through `AUTO`." However, the specification does not give an explicit combinator syntax for attaching `AUTO` to a specific `HITL` statement (its only shown arrow-attachment example for `HITL` is `FALLBACK`, and `AUTO` is explicitly disallowed from containing `WHEN`, `→`, or an arbitrary flow). I assumed that placing `AUTO` immediately before the relevant `HITL("Merge this change?")` statement, in plain sequence, is the intended way to express "attempt automatic resolution of this decision first; when the agent cannot reliably determine a single protocol-compatible decision, the following `HITL` statement is the human decision point that is used instead." This is a reading of the two definitions together, not a syntax the spec states directly.

2. **No `FALLBACK` used**: `FALLBACK` is defined for when "an expected response is unavailable or insufficient" after a `HITL`. The task requirement does not describe what should happen if the human never responds or gives an insufficient answer, so I did not add a `FALLBACK` block. If such handling is required, the specification does not determine what the fallback flow should do (terminate, defer, retry, etc.), so it would need to be stated separately.

3. **Decision outcome identifiers (`merge.approved` / `merge.rejected`)**: The specification does not name any concrete outcome identifiers; it only shows the pattern `implementation.accepted` / `implementation.rejected` as an example of outcomes produced by `VERIFY` and consumed by `WHEN`. Since the merge decision here is resolved by `AUTO`/`HITL` rather than `VERIFY`, the spec does not define what identifier such a decision outcome would carry. I invented `merge.approved` and `merge.rejected` as process-defined identifiers by analogy to the `VERIFY` example, since `WHEN` requires some condition identifier and the spec states identifiers "may be used to refer to requirements, results, states, artifacts, or other process-defined entities" without constraining their exact form.

4. **No branching on `VERIFY implementation`'s own outcome before the merge decision**: The requirement says "Delegate the implementation and verify it. Then a merge decision is needed," which I read as: the flow proceeds unconditionally from verification into the merge decision, without the requirement specifying separate `implementation.accepted` / `implementation.rejected` branches (unlike the spec's own `VERIFY` example, which does branch). Since the task text gives no instruction for a verification-rejected case, I did not invent one.

5. **No `LOOP` wrapper**: The requirement describes a single, one-shot linear sequence (delegate → verify → decide → transition), not a repeated process, so I did not wrap the statements in a `LOOP` scope. The specification does not require every process to be inside a `LOOP`.

6. **`HITL` message text**: Used the exact string from the requirement, `"Merge this change?"`, per the `HITL("<message>")` syntax and the `String` syntax rule (`"<string>"` for human-readable messages).

7. **`TRANSITION` argument form**: Used quoted strings `"Merged"` and `"Rework"` for the target states, matching the spec's own `TRANSITION "Code Review"` example, since the requirement names these as state names ("Merged", "Rework") rather than bare identifiers.

8. **Single `DELEGATE`/`VERIFY` pair, no explicit `WAIT`**: The requirement says "Delegate the implementation and verify it," which maps directly to the spec's `DELEGATE implementation` / `VERIFY implementation` example. The specification does not state that an explicit `WAIT` statement is required between `DELEGATE` and `VERIFY` (unlike `HITL`, which explicitly describes a suspension-until-response boundary only in the `WAIT` section, not as mandatory for every delegation), so none was added.
