# Execution Trace

## Program

```text
LOOP:tdd
  DELEGATE implementation
  DELEGATE tests
  VERIFY tests
  WHEN tests.passed
    → TRANSITION "Review"
    → BREAK
  WHEN tests.failed
    → TRANSITION "Debugging"
    → DELEGATE diagnosis
EMIT source-code
```

Injected events:
- Iteration 1: `VERIFY tests` establishes `failed`.
- Iteration 2: `VERIFY tests` establishes `passed`.

## Assumptions made where the specification does not fully determine behavior

The specification is silent on a few points needed to trace this program mechanically. These are read in the way most consistent with the stated semantics, and are called out explicitly:

1. **Loop body re-execution.** `LOOP` "does not imply any particular number of iterations" and "continues until `BREAK`, `STOP`, or another explicit control flow terminates it." The spec does not explicitly restate that reaching the end of the body without such a terminator returns control to the top of the body, but this is the only reading that makes "the loop continues" meaningful. Assumption: when the body finishes without `BREAK`/`STOP`, execution restarts from the first statement of the `LOOP` scope (i.e., `DELEGATE implementation` is re-issued each iteration).
2. **Scope of a `VERIFY`-established outcome.** The spec says "Verification may establish outcomes that can be used by `WHEN`" but does not state how long an established outcome remains in effect, nor what happens to a prior iteration's outcome. Assumption: each `VERIFY tests` call establishes a fresh outcome for `tests.*` that is what the immediately following `WHEN tests.passed` / `WHEN tests.failed` constructs evaluate for that iteration; it does not carry over to the next iteration's `VERIFY`.
3. **Evaluation of multiple `WHEN`s.** The spec states "Multiple `WHEN` constructs may describe different outcomes of the same process state" but does not give an explicit evaluation algorithm (e.g., short-circuit vs. independent checks). Assumption: each `WHEN` is checked independently against the current outcome; since `tests.passed` and `tests.failed` are mutually exclusive outcomes of the same `VERIFY tests` call, exactly one of the two `WHEN` flows executes per iteration, consistent with the injected events (which specify only one outcome per iteration).
4. **Effect of `BREAK` on later sibling statements in the same iteration.** The spec says `BREAK` "exits the current `LOOP`." Assumption: this exit is immediate — once `BREAK` executes (inside the `WHEN tests.passed` flow), no further statements in the loop body for that iteration are evaluated, including the subsequent `WHEN tests.failed` construct, since exiting the loop scope precludes evaluating anything still lexically inside it.
5. **`DELEGATE diagnosis` and `DELEGATE implementation`/`DELEGATE tests` are never paired with an explicit `VERIFY` for `diagnosis`** in this program, so per the spec they simply represent assigned work with no stated completion/acceptance semantics; no verification outcome is inferred for them beyond what is explicitly given.

## Step-by-step trace

**Enter `LOOP:tdd` — Iteration 1**

1. `DELEGATE implementation` — work "implementation" is assigned to an actor. No claim of correctness or completion is made by this statement alone.
2. `DELEGATE tests` — work "tests" is assigned to an actor.
3. `VERIFY tests` — the result of the delegated "tests" work is evaluated. Injected event: this establishes outcome `failed`.
4. `WHEN tests.passed` — condition not satisfied (outcome is `failed`, not `passed`). The flow under this `WHEN` (`TRANSITION "Review"`, `BREAK`) is not executed.
5. `WHEN tests.failed` — condition satisfied. The flow under this `WHEN` executes:
   a. `TRANSITION "Debugging"` — process state changes to `Debugging`. (This is a state change only; it does not perform debugging work.)
   b. `DELEGATE diagnosis` — work "diagnosis" is assigned to an actor.
6. End of loop body reached for this iteration. No `BREAK` or `STOP` occurred, so per `LOOP` semantics the loop has not been terminated; execution returns to the top of the `LOOP:tdd` scope.

**Iteration 2**

7. `DELEGATE implementation` — work "implementation" is (re-)assigned.
8. `DELEGATE tests` — work "tests" is (re-)assigned.
9. `VERIFY tests` — the result is evaluated. Injected event: this establishes outcome `passed`.
10. `WHEN tests.passed` — condition satisfied. The flow under this `WHEN` executes:
    a. `TRANSITION "Review"` — process state changes to `Review`.
    b. `BREAK` — exits the current `LOOP:tdd` scope. Per the specification, `BREAK` "does not terminate the entire execution," only the enclosing loop.
11. Because `BREAK` has exited the loop scope, the remaining sibling construct `WHEN tests.failed` (and its flow) is not evaluated for this iteration — execution has already left the scope in which that `WHEN` is defined.

**After the loop**

12. Execution resumes at the first statement following the `LOOP:tdd` scope, in declaration order: `EMIT source-code`. This produces the "source-code" artifact as an externally meaningful output. The specification does not prescribe how this artifact is created, stored, or transmitted — only that it is produced.
13. No further statements remain in the program, and no `STOP` was encountered. Execution ends naturally after the last statement completes (`STOP` is not required to end execution — it is only required to guarantee that "no subsequent statement is executed after" it; here there simply are no subsequent statements).

## Final process state

**`Review`**

This is the last state established by a `TRANSITION` statement (`TRANSITION "Review"`, executed in iteration 2 immediately before the loop was exited via `BREAK`). The intervening `TRANSITION "Debugging"` from iteration 1 was superseded by this later transition. The process also produced one artifact, `source-code`, via `EMIT` after the loop concluded, but `EMIT` does not itself constitute a process state — only `TRANSITION` does, per the specification ("`TRANSITION` changes the current process state").
