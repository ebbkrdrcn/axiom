# Trace of the `build` loop

```text
LOOP:build
  DELEGATE build
  VERIFY build
  WHEN build.accepted
    → BREAK
EMIT build-report
```

Given: in every iteration, `VERIFY build` establishes the outcome `rejected` (i.e. `build.accepted` is never satisfied).

## Assumptions (the spec does not fully determine these)

The specification does not explicitly say "control returns to the top of the loop body once the last statement in the body has run without a `BREAK`/`STOP`." It only says:

- "The loop continues until `BREAK`, `STOP`, or another explicit control flow terminates it."
- "`LOOP` does not imply any particular number of iterations."

I am treating "the loop continues" as meaning: when the end of the loop body is reached without having hit `BREAK`, `STOP`, or another terminating control construct, the flow returns to the first statement of the loop body and a new iteration begins. This is the only reading consistent with `LOOP` being a "repeated execution scope," but it is an inference, not a sentence quoted verbatim from the spec, so I flag it explicitly.

Also, the spec does not say whether repeating `DELEGATE build` on each iteration means a brand-new assignment of work or a re-assignment/retry of the same work item — `DELEGATE` only "defines responsibility, not execution mechanics," so this distinction has no defined effect on control flow and does not change the answer below.

Finally, the snippet contains no `WHEN build.rejected` branch. Per the spec, `WHEN` "does not itself perform work, change state, delegate work, or produce an artifact," and its flow runs "when the condition is satisfied." Since no `WHEN` clause exists for the `rejected` outcome, nothing is explicitly triggered by a rejection — the spec gives no instruction for that case other than "the loop continues" (because no exiting construct fired).

## Iteration 1

1. Execution enters the `LOOP:build` scope for the first time.
2. `DELEGATE build` — work is assigned to an actor responsible for producing a build. Per spec, this "does not mean the work is correct, complete, or accepted"; it only establishes responsibility, not an outcome.
3. `VERIFY build` — the delegated result is evaluated against acceptance criteria. Per the task's given fact, this evaluation establishes the outcome `build.rejected` (not `build.accepted`). Per spec, "completion of delegated work is not equivalent to successful verification," and `VERIFY` "must not silently modify the result it evaluates" — it only records/establishes the outcome.
4. `WHEN build.accepted → BREAK` is reached. The condition `build.accepted` is **not** satisfied (the outcome is `rejected`), so, per spec, this `WHEN`'s flow (`BREAK`) is not executed. `WHEN` itself performs no work and causes no state change on its own — nothing happens beyond the (non-)evaluation of the condition.
5. The end of the loop body is reached. No `BREAK`, `STOP`, or other explicit terminating control construct occurred during this pass. Per spec, the loop "continues" in this case (see Assumptions above) — so execution returns to the top of `LOOP:build` and iteration 2 begins.

Nothing outside the loop (i.e. `EMIT build-report`) executes during iteration 1, because that statement is not part of the loop body and is only reached once the loop scope is exited (spec: "statements execute in declaration order unless an explicit control construct changes the flow").

## Iteration 2

1. Execution is back at the top of `LOOP:build`.
2. `DELEGATE build` — work is (re-)delegated. As in iteration 1, this by itself establishes no outcome.
3. `VERIFY build` — per the given fact, this again establishes `build.rejected`.
4. `WHEN build.accepted → BREAK` — again the condition `build.accepted` is not satisfied, so `BREAK` does not execute.
5. End of loop body reached again, with no `BREAK`/`STOP` having occurred, so per the same "continues until BREAK/STOP/other explicit termination" rule, execution loops back to the top again (iteration 3 would begin, though the task only asks about the first two iterations).

`EMIT build-report` again does not execute during iteration 2, for the same reason as iteration 1: it lies outside the loop scope and is only reachable after the loop terminates.

## Whether and when `EMIT build-report` executes

`EMIT build-report` is written at the same indentation level as `LOOP:build`, i.e. it is **not** inside the loop's scope. Per the "Scope" and "Flow" rules, it is the statement that follows the loop in declaration order, so it can only run once the `LOOP:build` scope has ended.

Per the `LOOP` semantics, the scope ends only when `BREAK`, `STOP`, or "another explicit control flow" terminates it. In this program, the only construct capable of doing that is the `BREAK` reachable through `WHEN build.accepted`. Since the task stipulates that `VERIFY build` establishes `rejected` "in every iteration," `build.accepted` is never satisfied, so that `WHEN` flow's `BREAK` never fires. There is no `STOP` anywhere in the program, and no other exiting construct.

Consequently, under the stated behavior (rejection on every iteration, with no bound on the number of iterations and no other exit path defined for the `rejected` case):

- During the first two iterations, `EMIT build-report` is **not** executed — it is never reached because the loop never exits.
- More generally, as specified, the loop has no defined termination condition for the "always rejected" case (no `WHEN build.rejected` branch, no `STOP`), so per the DSL's own rule that a loop continues until an explicit terminating construct fires, the loop keeps iterating indefinitely and `EMIT build-report` is never executed at all under this behavior — it would only execute if/when some iteration's `VERIFY build` instead established `build.accepted` (firing the `BREAK`) or some other explicit control flow (e.g. a `STOP`, which is not present in this snippet) terminated the loop.

This is the point flagged under Assumptions: the specification determines *that* the loop keeps going absent an exiting construct, but it does not itself specify any escape hatch for a persistently-rejected build (e.g., a retry limit, a `WHEN build.rejected` correction branch, or a `STOP`) — the given DSL snippet simply does not include one.
