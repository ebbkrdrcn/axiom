# Execution Trace

## Program

```text
DELEGATE dependency-upgrade
VERIFY dependency-upgrade
HITL:merge("Merge the dependency upgrade?") AUTO
  → FALLBACK
      → TRANSITION "Blocked"
      → STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Deferred"
```

All five top-level statements (`DELEGATE`, `VERIFY`, `HITL:merge(...) AUTO`, `WHEN merge.approved`, `WHEN merge.declined`) are at the same indentation, so they form a single top-level flow executed in declaration order (per **Flow**: "A statement starts only after the previous statement in the same flow has completed").

## Step by step

**Step 1 — `DELEGATE dependency-upgrade`**
Work is assigned to an actor to produce the dependency upgrade. Per spec, `DELEGATE` "does not mean that the work is correct, complete, or accepted" — it only records responsibility for the work, not its result.

**Step 2 — `VERIFY dependency-upgrade`**
The delegated result is evaluated against applicable acceptance criteria. The task states this establishes `accepted` (i.e., the outcome `dependency-upgrade.accepted`, following the same pattern as the spec's own example `VERIFY implementation` → `implementation.accepted`). `VERIFY` "does not branch by itself" and has no `WHEN` attached to it directly in this program, so execution simply continues to the next statement regardless of the outcome value.

**Step 3 — `HITL:merge("Merge the dependency upgrade?") AUTO`**
This is a `HITL` marked `AUTO`, so before asking a human the agent must check whether the decision is "sufficiently determined" by the available information, criteria, and authority (per **AUTO**):

- *Authority*: the context states "the process gives the agent authority to merge dependency upgrades" — authority requirement satisfied.
- *Criteria*: the context gives an explicit, applicable merge criterion: "merge when verification accepts the upgrade and the changelog announces no breaking change." This criterion is not missing, ambiguous, or contradictory.
- *Information*: `VERIFY dependency-upgrade` established `accepted` (Step 2), and the changelog "lists only bug fixes," i.e., it announces no breaking change. Both conjuncts of the criterion are known and both are satisfied.

Because the agent can determine a single protocol-compatible decision ("approve") from the available information and the stated criteria, `AUTO`'s condition for automatic resolution is met (per the table in **AUTO**: `AUTO` present + decision sufficiently determined → "The agent resolves the decision. The human is **not** asked."). The agent therefore resolves the `merge` decision itself and establishes the outcome `merge.approved`, exactly as if a human had answered "approved."

Since the human is never asked, the question of the human's availability ("no human is currently online") never becomes relevant, and the `FALLBACK` attached to this `HITL` is not invoked: per spec, `FALLBACK` "is used only when the expected response cannot be used to continue the normal flow," and it applies "only afterwards, if the human's response is unavailable or insufficient" — a situation that presupposes the human was asked in the first place. Here no human is asked, so there is no unavailable/insufficient response to trigger it, and `AUTO`'s automatic resolution is explicitly distinguished from `FALLBACK` in the spec ("`AUTO` and `FALLBACK` are different mechanisms. When `AUTO` cannot resolve a decision, the decision goes to the human through the normal `HITL`; this is not a fallback.").

Execution continues with the statement after the `HITL` construct (Step 4), carrying the established outcome `merge.approved`.

**Step 4 — `WHEN merge.approved`**
Evaluated once, in declaration order. The condition `merge.approved` matches the outcome established in Step 3, so its flow executes:
- `→ TRANSITION "Merged"`: the current process state changes to `Merged`.

Execution then continues with the statement after this `WHEN` (Step 5), since the flow did not execute `BREAK` or `STOP`.

**Step 5 — `WHEN merge.declined`**
Evaluated independently of Step 4 ("Each `WHEN` is independent... every one whose condition is satisfied executes its flow"). The outcome established was `merge.approved`, not `merge.declined`, so this condition is not satisfied. Per spec, an unmatched `WHEN` "is not an error; it does not stop, wait, or escalate" — its flow is simply skipped.

**End of program**
There is no further statement and no `STOP` was executed. Per **STOP**: "`STOP` is not required at the end of a process. When the last top-level statement has completed, execution ends normally." Execution ends normally after Step 5.

## Answers

- **Final process state:** `"Merged"` (set by the `TRANSITION "Merged"` in Step 4; it is the only `TRANSITION` executed, and per spec "the most recently executed `TRANSITION` determines the current state").
- **Is a human asked?** No. `AUTO` found the decision sufficiently determined from the stated criterion and the known facts (`accepted`, no breaking change, agent has authority), so per the `AUTO` execution table the agent resolves `merge.approved` itself and the human is not asked.
- **Is `FALLBACK` used?** No. `FALLBACK` only activates when a human was asked and the response turns out to be unavailable or insufficient. Since no human is asked in this run, that precondition never arises, so the `FALLBACK` flow (`TRANSITION "Blocked"`, `STOP`) is never entered.

## Assumptions / points the specification leaves open

- The specification does not give a formal algorithm for "sufficiently determined" — it only lists what counts as uncertainty (missing/contradictory information or criteria, multiple materially different compatible decisions, unresolved interpretation, lack of authority) and states that "a confidence score alone does not establish certainty." I treated the decision as determined because none of the listed uncertainty conditions apply here: the criterion is fully stated, both facts it depends on are given and unambiguous, they jointly point to exactly one decision ("approve"), and the agent's authority is explicitly confirmed by the context. This is a judgment call about "sufficiently determined" applied to the given facts, not something the DSL itself formalizes — the spec explicitly says `AUTO` "defines when automatic decision resolution is permitted, not an algorithm or confidence threshold," so any such determination necessarily comes from outside the DSL (from the surrounding process's criteria, as here).
- I assumed `VERIFY dependency-upgrade` establishes the outcome `dependency-upgrade.accepted` (mirroring the spec's own `VERIFY implementation` → `implementation.accepted` example), since the task states VERIFY "establishes `accepted`" without spelling out the full dotted identifier. This naming detail is not actually load-bearing for the answer, since no `WHEN` in the program tests `dependency-upgrade.accepted` directly — the merge criterion referencing "verification accepts the upgrade" is given directly in the context and fed into the `AUTO` determination in Step 3.
- The fact that "no human is currently online" is given in the context but, as explained above, turns out not to affect the trace at all under a correct reading of `AUTO`/`HITL`/`FALLBACK`: it would only matter if the human had to be asked, which does not happen here. I note this explicitly since it could look like a detail meant to force `FALLBACK`, but per the spec's definitions it does not, because `AUTO` resolution and `FALLBACK` (unavailable/insufficient *human response*) are distinct mechanisms and the latter is never reached.
