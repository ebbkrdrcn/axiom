```text
DELEGATE implementation
VERIFY implementation
AUTO
HITL:merge("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

- **No `REQUIRE` statement.** The requirement text does not state any precondition ("required information, context, state, or condition") that must be satisfied before the implementation is delegated, so no `REQUIRE` was added. The specification does not determine one, so none was assumed or fabricated.
- **Decision name `merge` and answer identifiers `approved` / `declined`.** The specification says `<name>` names the decision and that answers are "one of the answers tested by the `WHEN <name>.<answer>` constructs that follow," but it does not mandate specific answer wordings beyond identifier syntax (letters, digits, `-`, `_`, starting with a letter). I chose `merge.approved` / `merge.declined` because these are the exact names the specification itself uses in its own `AUTO`/`HITL` example for an equivalent merge decision, and they map naturally onto "the decision is to merge" / "the decision is not to merge."
- **`VERIFY implementation` has no following `WHEN`.** The requirement only says "verify it" and then moves straight to the merge decision; it does not say what should happen if the implementation is rejected. Per the specification, "`VERIFY` does not branch by itself... A `VERIFY` with no `WHEN` after it does not gate the process," so execution simply proceeds from `VERIFY implementation` to the merge decision regardless of the verification outcome, exactly as the requirement states (it never mentions branching on the implementation's own verification result, only on the later merge decision).
- **`AUTO` placement.** Since the requirement explicitly allows the agent to decide when the decision is "clearly determined by the available information and criteria" and otherwise requires asking a human, this is precisely `AUTO`'s defined behavior, so `AUTO` was placed directly before `HITL:merge(...)` as required by the grammar (`AUTO` on its own line, immediately preceding the `HITL`).
- **`FALLBACK` handles "no usable answer."** "No usable answer" was read as covering both the specification's "unavailable" (no response arrives) and "insufficient" (a response that doesn't answer the question) cases, since the requirement does not distinguish between them and the specification treats both as triggering the same `FALLBACK` flow.
- **No `LOOP`.** The requirement describes a single linear sequence with no repetition, retry, or "until accepted" language, so no `LOOP` construct was used.
- **No `EMIT`.** The requirement does not mention producing any artifact/output, only state transitions, so `EMIT` was not used.
- **No trailing `STOP` after `TRANSITION "Merged"` or `TRANSITION "Rework"`.** The specification states `STOP` is not required at the end of a process and execution ends normally when the last top-level statement completes; the requirement gives no further instructions after reaching either of these two states, so the process is left to end normally there. `STOP` is used only in the `FALLBACK` branch, where the requirement explicitly says to "transition to state 'Blocked' and stop."
- **Message string reproduced verbatim.** The `HITL` message was written exactly as quoted in the requirement: `"Merge this change?"`.
- **Indentation.** Concrete indentation depth is not semantically meaningful per the specification ("Only relative depth matters, not the number of spaces"); the levels chosen mirror the specification's own worked examples (e.g., the `AUTO`/`HITL`/`FALLBACK` example) for readability.
