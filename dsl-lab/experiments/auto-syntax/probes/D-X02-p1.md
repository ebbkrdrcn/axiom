```text
AUTO
HITL:format("Short or detailed release notes?")
WHEN format.short
  → DELEGATE short-notes
WHEN format.detailed
  → DELEGATE detailed-notes

HITL:approval("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Names for the `HITL` decisions.** The spec requires a `<name>` on `HITL` whenever a `WHEN <name>.<answer>` refers to it, but the task text does not supply names. I invented the identifiers `format` (for the short/detailed question) and `approval` (for the approve/reject question), since these are not determined by the specification and had to be chosen.

2. **Answer identifiers.** I mapped the natural-language answers to the identifiers `short`, `detailed`, `approved`, `rejected`, matching the wording of the task ("If short…", "if detailed…", "If approved…", "if rejected…"). The DSL does not constrain what these identifiers must be spelled as; any other consistent spelling would be equally valid.

3. **Binary, exhaustive answer sets.** I assumed each `HITL` has exactly the two answers implied by the task ("short or detailed", "approved or rejected") and did not add a `FALLBACK` for either `HITL`. The task gives no requirement for what happens if the human's response is unavailable or insufficient (e.g., a reply that is neither "short" nor "detailed"), so per the spec such a case would simply leave the flow suspended at the `HITL` (or, if a response arrives but isn't one of the tested answers, it is "insufficient" and — absent a `FALLBACK` — the spec does not define further behavior beyond noting a `FALLBACK` would be needed to handle it). Since the task doesn't describe fallback behavior, I omitted `FALLBACK` rather than invent one.

4. **`AUTO` only on the first `HITL`.** The task explicitly allows the agent to answer the "short or detailed" question itself "when the answer is clearly determined," which maps directly to `AUTO`. It explicitly forbids the agent from ever deciding the approval question ("must always be given by a human, never by the agent"), so the second `HITL` has no `AUTO` — per the spec, a `HITL` without `AUTO` is always asked to the human.

5. **No `REQUIRE`, `VERIFY`, `LOOP`, `FORK`, or `WAIT`.** The task describes a single linear sequence with no stated preconditions to require, no verification of the delegated notes, no repetition, and no concurrency, so none of these constructs were used. In particular, `DELEGATE short-notes` / `DELEGATE detailed-notes` are not followed by a `VERIFY`, since the task does not ask for the delegated work to be evaluated — per the spec this is legal (`VERIFY` is optional; `DELEGATE` alone does not imply acceptance either way).

6. **Sequencing.** I placed the "short or detailed" decision and its two `WHEN` blocks entirely before the "Approve the release?" `HITL`, since the task states "First ask… Then ask…", and both `WHEN format.short` / `WHEN format.detailed` complete (each running its single `DELEGATE`) before execution reaches the second `HITL`, per the `WHEN` execution rule that control returns to the statement after the `WHEN` once its flow finishes.

7. **Program end.** After `EMIT release` or `TRANSITION "Rework"`, no further statement follows and no `STOP` is used. Per the spec, `STOP` is not required at the end of a program; execution ends normally once the last top-level statement completes. Since both `WHEN` outcomes (`approved`/`rejected`) are mutually exclusive answers to the same `HITL`, only one of the two flows will actually run for a given execution, and either way execution ends after it.

8. **Blank lines between top-level statements.** I used a blank line to visually separate the two `HITL` groups. The grammar's tokens are statements and indentation (`NL`, `INDENT`, `DEDENT`); it does not explicitly discuss blank lines. I assumed blank lines are immaterial to parsing (pure formatting) rather than a meaningful token, since nothing in the spec suggests otherwise.

9. **Literal identifiers for delegated work.** I used `short-notes` and `detailed-notes` as the `DELEGATE` arguments, taken verbatim from the task's own phrasing ("delegate short-notes", "delegate detailed-notes"), and `release` as the `EMIT` argument and `"Rework"` as the `TRANSITION` argument, also taken verbatim from the task.
