```text
AUTO HITL:notes("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes

HITL:approval("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Program scope**: The two `HITL` decisions plus their `WHEN` flows form the entire program at top level, not nested inside a `LOOP` or any other enclosing construct. The requirement describes a single linear sequence with no indication of repetition, so no `LOOP` was used. (Per the spec, "A construct is not assumed to be enclosed in a scope that is not shown.")

2. **"May answer this question itself when the answer is clearly determined"** maps directly to `AUTO HITL`, using the spec's own definition of automatic resolution ("Resolve automatically when sufficiently determined; otherwise require human input"). The requirement gives no additional criteria for what counts as "clearly determined," and the spec explicitly states this determination is a runtime concern, not something expressed in the DSL itself, so none was added.

3. **"Must always be given by a human, never by the agent"** for the approval question maps to a plain `HITL` (no `AUTO`). This is the only DSL construct that guarantees a human is always asked.

4. **No `FALLBACK`** was added to either `HITL`. The requirement does not describe what should happen if a response is unavailable or insufficient, and `FALLBACK` is optional per the grammar. Per the spec, a `HITL` without `FALLBACK` simply waits at that point until a usable response becomes available.

5. **No `VERIFY`** was added after `DELEGATE short-notes` / `DELEGATE detailed-notes`. The requirement only asks that the work be delegated, not that its result be evaluated, so no verification step was introduced.

6. **Identifiers/names chosen**: the requirement does not give explicit DSL identifiers, so the following were chosen (valid per the identifier grammar: letters, digits, `-`, `_`, starting with a letter):
   - Decision names `notes` and `approval` (needed because subsequent `WHEN` constructs reference `notes.short`/`notes.detailed` and `approval.approved`/`approval.rejected` — a `HITL` name is required whenever a `WHEN` refers to it).
   - Delegated-work identifiers `short-notes` and `detailed-notes`.
   - Emitted-artifact identifier `release`.
   - State string `"Rework"`, taken verbatim from the requirement.

7. **Exactly two answers per decision** were assumed: `short`/`detailed` for the notes decision and `approved`/`rejected` for the approval decision, matching the only outcomes the requirement mentions ("If short... if detailed", "If approved... if rejected"). No other answers or an unmatched-answer flow are handled, beyond the general `HITL`/`FALLBACK` mechanism noted in point 4.

8. **Ordering**: the two `HITL` decisions and their `WHEN` flows are assumed to execute strictly in the order given in the requirement (notes question and delegation first, then the approval question), since the requirement describes them as a "first... then..." sequence and the DSL executes statements in declaration order unless a control construct changes that.
