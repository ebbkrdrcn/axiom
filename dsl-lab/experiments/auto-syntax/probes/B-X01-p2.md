```text
DELEGATE implementation
VERIFY implementation
HITL:merge("Merge this change?") AUTO
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

- **Identifier for the delegated/verified work**: the requirement only says "the implementation," so I used the identifier `implementation` for both `DELEGATE` and `VERIFY` (mirroring the spec's own `DELEGATE implementation` / `VERIFY implementation` example). Any other identifier naming the same work would be equally valid; the spec does not fix a required name.

- **HITL decision name and answer identifiers**: the requirement describes a binary merge decision ("merge" vs. "not merge") but does not give literal token names. I named the decision `merge` and used the answers `approved` / `declined` (i.e. outcomes `merge.approved` and `merge.declined`), following the exact naming used in the spec's own `AUTO` example, which describes the same kind of merge decision. The spec requires that `<name>.<answer>` match the answers tested by the following `WHEN` constructs, but does not mandate specific answer words, so `approved`/`declined` is a choice consistent with, but not dictated by, the spec.

- **`AUTO` placement**: the requirement's "the agent may make the merge decision itself when it is clearly determined ... otherwise a human must be asked" is precisely the semantics the spec assigns to `HITL ... AUTO`, so I attached `AUTO` to the `HITL:merge(...)` statement rather than modeling "clearly determined" as an explicit DSL condition (the spec explicitly forbids treating uncertainty as a DSL condition/keyword, and states `AUTO` is not a control-flow container). This is a direct application of the spec's given semantics, not really an added assumption, but it depends on reading "clearly determined by available information and criteria" as exactly matching the spec's definition of `AUTO`'s auto-resolution condition.

- **"No usable answer" maps to `FALLBACK`**: the requirement's phrase "if the human gives no usable answer" was mapped to the spec's `FALLBACK` mechanism (used when a response is unavailable or insufficient). The spec does not distinguish "unavailable" vs. "insufficient" in the requirement text, so both are treated as triggering the single `FALLBACK` flow, per spec's definition that either condition uses the fallback flow.

- **`STOP` after `TRANSITION "Blocked"`**: the requirement explicitly says "transition to state 'Blocked' and stop," so both statements were placed in sequence inside the fallback flow, per the spec's fallback-flow example showing exactly this `TRANSITION` + `STOP` pattern.

- **No `REQUIRE`, `LOOP`, `FORK`/`JOIN`, `WAIT`, or `EMIT`**: the requirement describes a single linear decision process with no stated preconditions, repetition, concurrency, external suspension, or artifact output, so none of these constructs were used. The spec does not force any statement to appear beyond what the requirement calls for.

- **No explicit `STOP` after the two `WHEN "Merged"/"Rework"` branches**: the spec states a program need not end with `STOP`; execution ends normally after the last top-level statement completes. Since the requirement gives no further steps after transitioning to "Merged" or "Rework," no trailing `STOP` was added for those branches.

- **Order of the two `WHEN` blocks**: the spec says `WHEN` constructs are independent and each is evaluated once when reached in declaration order, with no "first match wins" semantics; since `merge.approved` and `merge.declined` are mutually exclusive outcomes of the same `HITL`, the order between the two `WHEN` blocks (approved before declined) does not affect behavior, but I preserved the order given in the requirement (merge case first, then non-merge case).

- **Message text**: the exact string `"Merge this change?"` was taken verbatim from the requirement as the `HITL` argument, since the spec requires `HITL`'s argument to be a string and does not prescribe any transformation of the requirement's wording.
