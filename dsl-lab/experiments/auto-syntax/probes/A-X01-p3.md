```text
DELEGATE implementation
VERIFY implementation
AUTO HITL:merge("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

- **Answer identifiers (`merge.approved` / `merge.declined`).** The requirement describes the two possible merge decisions ("merge" / "not merge") but the specification does not fix what identifiers a `HITL` answer must use — it only requires that `<name>.<answer>` match the answers tested by the following `WHEN` constructs. I chose `approved` and `declined` (the same pair used in the spec's own `AUTO`/`HITL` example) since no other naming is prescribed.
- **The `HITL` name `merge`.** A name is only required when a `WHEN` refers to the decision (spec: "The name may be omitted when no `WHEN` refers to the decision"). Since the requirement needs two follow-up branches on the outcome, I named it `merge` so `WHEN merge.approved` / `WHEN merge.declined` can reference it. The requirement doesn't specify this name explicitly, so any other identifier would have been equally valid.
- **No `REQUIRE` statement.** The requirement text does not state any precondition that must be available before delegating the implementation, so I did not add a `REQUIRE`. The DSL does not mandate that every process begin with one.
- **No `LOOP`.** The requirement describes a single, non-repeating decision sequence (delegate → verify → decide → transition, possibly stop). Nothing in the requirement calls for retrying the implementation or the merge decision, so no `LOOP` construct is used.
- **`VERIFY implementation` has no following `WHEN`.** The requirement says "Delegate the implementation and verify it. Then a merge decision is needed," which reads as: the merge decision follows verification unconditionally, not conditionally on its outcome. Per the spec, "A `VERIFY` with no `WHEN` after it does not gate the process," so execution proceeds straight to the `HITL` regardless of the verification's outcome. I assumed the requirement does not intend the verification result itself to branch the flow (only the merge decision does).
- **`FALLBACK` covers "no usable answer."** The requirement's phrase "If the human gives no usable answer" is treated as covering both cases the spec defines for triggering `FALLBACK`: the response being unavailable (no reply) and insufficient (a reply that isn't a usable merge/no-merge decision), since the requirement does not distinguish between these two.
- **Placement of `TRANSITION "Blocked"` and `STOP` only inside the `FALLBACK` flow.** The requirement ties "Blocked" and stopping specifically to the no-usable-answer case, so these two statements are scoped inside `FALLBACK` only, per the two-line form shown as equivalent in the spec (`→ TRANSITION "Blocked"` followed by an indented `STOP` under it, meaning sequential execution of both).
- **Exact `HITL` message text.** I used `"Merge this change?"` exactly as given in the requirement, since `HITL`'s string argument is meant to carry the human-readable message verbatim.
- **`DELEGATE`/`VERIFY` argument name `implementation`.** The requirement refers to "the implementation" as a single delegated unit of work; I used the identifier `implementation` for both statements (matching the spec's own recurring example), since the requirement does not name it otherwise.
- **Order of the two `WHEN` constructs after the `HITL`.** Per the spec, `WHEN` constructs are independent and order does not affect which one's condition is evaluated as true; I placed `merge.approved` before `merge.declined` simply following the order the requirement states the two outcomes ("If the decision is to merge... If the decision is not to merge...").
