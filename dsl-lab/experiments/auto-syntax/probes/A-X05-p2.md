# Answers

## Snippet 1

```text
AUTO HITL:deploy("Deploy to production?")
WHEN deploy.yes
  → EMIT deployment
```

**VALID**

- The `HITL` statement matches the grammar `hitl = [ "AUTO" ] , "HITL" , [ ":" , identifier ] , "(" , string , ")" , NL , [ ... FALLBACK ... ]` (Grammar section): `AUTO` precedes `HITL:deploy("Deploy to production?")` directly, on the same line, exactly as required by "`AUTO` is written directly before `HITL`, on the same line" (AUTO section).
- The named decision `deploy` is followed by a `WHEN deploy.yes` construct, satisfying "The response establishes the outcome `<name>.<answer>`, where `<answer>` is one of the answers tested by the `WHEN <name>.<answer>` constructs that follow" (HITL section). The spec does not restrict which answer-identifiers may be used (e.g. `yes` vs. `approved`/`declined`), so `deploy.yes` is a permissible condition of the required form `<identifier>.<identifier>` (Conditional Flow section).
- `WHEN <condition> → <statement>` matches the `when` grammar rule, and `EMIT deployment` is a valid `simple` statement (`EMIT` + argument).
- No rule in the specification is violated.

## Snippet 2

```text
AUTO DELEGATE implementation
VERIFY implementation
```

**INVALID**

- This is precisely the specification's own example of an invalid construct: "Invalid, because `AUTO` applies only to `HITL`: `AUTO DELEGATE implementation`" (AUTO section).
- Supporting rule: "`AUTO` is not a statement of its own and applies to no other statement. `AUTO` applies only to `HITL`." The syntax table also only lists `[AUTO] HITL[:<name>]("<message>")` as a valid form combining `AUTO`; `DELEGATE` has no `AUTO`-prefixed form in the Statement table or grammar (`simple` production has no `AUTO` alternative).

## Snippet 3

```text
HITL:deploy("Deploy to production?") AUTO
WHEN deploy.yes
  → EMIT deployment
```

**INVALID**

- The grammar fixes the order: `hitl = [ "AUTO" ] , "HITL" , [ ":" , identifier ] , "(" , string , ")" , NL , ...` — `AUTO`, if present, must come *before* `HITL`. Here `AUTO` appears after the `HITL(...)` call instead.
- This directly contradicts the explicit rule: "`AUTO` is written directly before `HITL`, on the same line. It marks that one `HITL` as automatically resolvable" (AUTO section). Placing `AUTO` after `HITL:deploy("Deploy to production?")` does not satisfy "directly before."
- The Statement-form table likewise gives only one valid ordering: `[AUTO] HITL[:<name>]("<message>")`, i.e. `AUTO` (if present) precedes `HITL`.

## Snippet 4

```text
AUTO
  WHEN decision.uncertain
    → HITL("Approve?")
```

**INVALID**

- This is precisely the specification's own example of an invalid construct: "Also invalid, because `AUTO` never contains a flow and uncertainty is not a condition: `AUTO` / `WHEN decision.uncertain` / `→ HITL("Approve?")`" (AUTO section).
- Supporting rules: "`AUTO` is not a control-flow container. It does not contain `WHEN`, `→`, or an arbitrary flow." and "Uncertainty is not a DSL condition, state, variable, or keyword." The grammar also has no production allowing `AUTO` to introduce an `INDENT`/`block`; `AUTO` only appears as an optional prefix token inside the `hitl` production, never as a standalone statement with nested content.

---

**Assumption noted:** The specification does not restrict the set of `<answer>` identifiers usable in `WHEN <name>.<answer>` (e.g., whether they must be drawn from a fixed vocabulary like `approved`/`declined`). I assumed any well-formed identifier (such as `yes`) is permitted as an answer name, since the spec only requires the condition to have the form `<identifier>.<identifier>` and to match a `WHEN` that follows the `HITL`/`AUTO HITL`.
