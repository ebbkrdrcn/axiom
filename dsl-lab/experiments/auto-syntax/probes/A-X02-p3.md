```text
AUTO HITL:notes("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes
HITL:approval("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **No `LOOP` or `FORK` is needed.** The requirement describes a single, straight-line sequence of decisions (ask → branch → delegate → ask → branch → act), with no repetition and no concurrent work, so the program is written as a flat top-level flow.

2. **`AUTO` applies only to the first `HITL`.** The requirement says the notes-format question "may" be answered by the agent when clearly determined — this matches `AUTO HITL`. The approval question is explicitly required to "always be given by a human, never by the agent," so that `HITL` is written without `AUTO`, per the spec's rule that `AUTO` applies only where written directly before `HITL`.

3. **Names chosen for the `HITL` decisions.** The DSL requires a `<name>` on `HITL` whenever a `WHEN <name>.<answer>` follows. I named the first decision `notes` and the second `approval`. These names are not given in the requirement text; they are my own identifiers chosen to be descriptive.

4. **Answer identifiers chosen for the conditions.** The requirement's answers ("short"/"detailed" and the implicit "approved"/"rejected" of an approval question) are mapped to the condition identifiers `notes.short`, `notes.detailed`, `approval.approved`, and `approval.rejected`. The spec does not fix a vocabulary for `HITL` answers beyond "`<name>.<answer>`, where `<answer>` is one of the answers tested by the following `WHEN`", so these exact tokens are an assumption, not something the spec or the requirement text spells out verbatim.

5. **No `FALLBACK` is included for either `HITL`.** The requirement does not describe what should happen if a human response is unavailable or insufficient, so no `FALLBACK` flow is specified. Per the spec, `HITL` without a `FALLBACK` is valid; execution would simply wait at the `HITL` until a usable response is available (there being no fallback and no timeout defined in the DSL).

6. **`DELEGATE`, `EMIT`, and `TRANSITION` arguments are taken as identifiers/strings matching the requirement's own wording** (`short-notes`, `detailed-notes`, `release`, and the string `"Rework"`), since the DSL does not prescribe a fixed vocabulary for these and only requires a valid identifier or string.

7. **No `VERIFY` step is used for the delegated notes work.** The requirement states only "delegate short-notes" / "delegate detailed-notes" with no mention of an acceptance check, so no `VERIFY` was added — adding one would introduce a gating step the requirement does not ask for.

8. **No `REQUIRE`, `WAIT`, `STOP`, or explicit process state before the first `TRANSITION`/`EMIT` is specified**, since the requirement does not mention any precondition, external suspension, or early termination; the DSL leaves these to the process author and none are implied by the given text.

9. **Since `WHEN` has no "else" semantics, both `WHEN notes.short` / `WHEN notes.detailed` and both `WHEN approval.approved` / `WHEN approval.rejected` are written as independent, mutually exclusive conditions** based on the assumption that a resolved `HITL` decision establishes exactly one of the two named outcomes (the spec states a response corresponds to one of the tested answers), so in practice exactly one branch in each pair executes.
