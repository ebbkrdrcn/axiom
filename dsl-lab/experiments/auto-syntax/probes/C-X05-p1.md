# Answers

## Snippet 1 — VALID

```text
HITL:deploy("Deploy to production?")
  → AUTO
WHEN deploy.yes
  → EMIT deployment
```

This matches the grammar exactly:

```ebnf
hitl = "HITL" , [ ":" , identifier ] , "(" , string , ")" , NL ,
       [ INDENT , [ "→" , "AUTO" , NL ] ,
         [ "→" , "FALLBACK" , NL , INDENT , flow , DEDENT ] , DEDENT ] ;
```

`HITL:deploy("Deploy to production?")` followed by an indented `→ AUTO` line is the documented syntax: "`→ AUTO` is written directly under a `HITL`, indented one level. ... `→ AUTO` has no children." (spec lines 417–424). The subsequent `WHEN deploy.yes` sits at the same indentation as the `HITL`, i.e. it is a statement in the normal flow after the `HITL` construct, which is exactly how the worked example is structured:

```text
HITL:merge("Merge the dependency upgrade?")
  → AUTO
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Deferred"
```

(spec lines 438–447).

The condition `deploy.yes` has the required `<identifier>.<identifier>` form (line 599: "`<condition>` has the form `<identifier>.<identifier>`"), and the spec places no restriction on which particular answer-identifiers (e.g. "approved"/"declined" vs. "yes") may be used — `<name>.<answer>` is general: "The response establishes the outcome `<name>.<answer>`, where `<answer>` is one of the answers tested by the `WHEN <name>.<answer>` constructs that follow." (lines 377). Here `deploy` is the `HITL` name and `yes` is the tested answer, so this requirement is satisfied. Nothing in the spec requires `AUTO` to be followed by a `FALLBACK`, and nothing requires more than one `WHEN`. The snippet is therefore well-formed.

**Assumption:** the specification's examples all use answer names like "approved"/"declined"/"accepted"/"rejected", but the grammar and prose only require `<condition> = identifier "." identifier`, with no closed vocabulary of allowed answers. I assumed "yes" is an ordinary identifier and therefore permitted, since the spec does not state or imply a restricted set of legal answer words.

## Snippet 2 — INVALID

```text
DELEGATE implementation
  → AUTO
VERIFY implementation
```

This is invalid for two independent reasons, both directly stated in the specification.

1. **`AUTO` applies only to `HITL`.** The spec gives this exact pattern as its own counterexample: "Invalid, because `AUTO` applies only to `HITL`: `DELEGATE implementation` / `→ AUTO`" (lines 452–457). It also states plainly: "`AUTO` is not a statement of its own and applies to no other statement. `AUTO` applies only to `HITL`." (line 424).

2. **`DELEGATE` cannot take an indented `→` child at all.** Per the grammar, `DELEGATE` is a `simple` statement: `simple = ( "REQUIRE" | "DELEGATE" | "VERIFY" | "TRANSITION" | "EMIT" ) , argument , NL | ( "JOIN" | "BREAK" | "WAIT" | "STOP" ) , NL ;` — it has no `INDENT`/`block` production, so it cannot own indented children. The Scope rules confirm this: only `LOOP`, `WHEN`, `FORK`, `HITL` (for `→ AUTO`/`→ FALLBACK`), `→ FALLBACK`, and `→` items may have indented children (line 556), and "Any other indentation is invalid. This includes an indented line under a plain statement that is not a `→` item, and a `→` line that is not directly under `WHEN`, `FORK`, `FALLBACK`, or `HITL`." (line 558).

Per the "Programs, fragments, and validity" section, a program violating an "invalid" rule "must be rejected as a whole" (line 663), so the snippet is not well-formed.

## Snippet 3 — INVALID

```text
AUTO HITL:deploy("Deploy to production?")
WHEN deploy.yes
  → EMIT deployment
```

There is no grammar production for a line beginning with `AUTO` followed by a `HITL` statement on the same line. The only defined surface form for `AUTO` is:

```text
HITL:<name>("<message>")
  → AUTO
```

as stated explicitly: "`→ AUTO` is written directly under a `HITL`, indented one level." and "`AUTO` is not a statement of its own and applies to no other statement." (spec lines 417–424). The Statement table (lines 525–536) likewise lists only `→ AUTO` (and only as a line by itself, directly under a `HITL`) — never `AUTO` prefixing a `HITL` statement or any other keyword. The grammar's `hitl` production begins with the terminal `"HITL"`, and `statement = loop | when | fork | hitl | simple` contains no alternative in which `AUTO` is a leading token of a statement. `AUTO HITL:deploy(...)` therefore matches no production in the grammar at all, so it is not a well-formed statement, and the snippet must be rejected as a whole (line 663).

## Snippet 4 — INVALID

```text
AUTO
  WHEN decision.uncertain
    → HITL("Approve?")
```

This is the specification's own listed invalid example, verbatim in structure: "Also invalid, because `AUTO` never contains a flow and uncertainty is not a condition: `AUTO` / `WHEN decision.uncertain` / `→ HITL("Approve?")`" (spec lines 459–465). Supporting rules: "`AUTO` is not a control-flow container. It does not contain `WHEN`, `→`, or an arbitrary flow." (lines 411–413), and "Uncertainty is not a DSL condition, state, variable, or keyword." (line 415) — so `decision.uncertain` cannot legally appear as a `WHEN` condition, since a `WHEN` condition must be a process-established `<identifier>.<identifier>` outcome (line 599), and uncertainty is explicitly excluded from being such a thing (it is instead something "The DSL runtime determines ... as part of automatic decision resolution", line 467). Additionally, standalone `AUTO` (with no preceding `HITL` at all) is not a form permitted by the grammar (`AUTO` never appears as a top-level statement production). The snippet is not well-formed.
