```text
HITL:notes("Short or detailed release notes?")
  → AUTO
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes

HITL:approval("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Names for the two `HITL` decisions.** The requirement does not give explicit names for the two questions, but `WHEN <name>.<answer>` requires a name on the `HITL` that it refers to. I named the first decision `notes` and the second `approval`. This is required by the grammar (`WHEN <name>.<answer>`) even though the requirement text never states a name.

2. **Answer identifiers.** I used `short` / `detailed` as the two answers to the first `HITL`, and `approved` / `rejected` as the two answers to the second `HITL`, taking these directly from the words used in the requirement ("short", "detailed", "approved", "rejected"). The spec does not define a fixed vocabulary for answers — it only says the outcome is `<name>.<answer>` where `<answer>` is whatever `WHEN` tests — so this mapping is an assumption, not a spec-mandated form.

3. **Exhaustiveness of the first decision's answers.** I assumed `short` and `detailed` are the only two possible answers to "Short or detailed release notes?", so no other `WHEN notes.*` branch is needed. The spec does not require covering every conceivable answer; an unmatched `WHEN` is simply not an error.

4. **`AUTO` only on the first `HITL`.** "The agent may answer this question itself when the answer is clearly determined" maps directly to `→ AUTO` under `HITL:notes`. Per the spec, `AUTO` still does not guarantee automatic resolution — if the answer is not "sufficiently determined", the human is still asked (the same `HITL` mechanism handles both cases automatically); this is spec behavior, not an added assumption.

5. **No `AUTO` on the second `HITL`.** "This approval must always be given by a human, never by the agent" is expressed by simply omitting `→ AUTO`. Per the spec's table, a `HITL` without `AUTO` always asks the human and the agent must not decide — this exactly matches the requirement, so no other mechanism (e.g., a hypothetical "force-human" keyword, which does not exist in the DSL) was needed.

6. **No `FALLBACK` on either `HITL`.** The requirement does not describe what should happen if a human response is unavailable or insufficient, and `FALLBACK` is optional in the grammar. I assumed no fallback handling was intended, meaning that per the `WAIT`/`HITL` rules, execution simply remains suspended at the `HITL` until a usable response arrives, with no defined timeout behavior — consistent with "The DSL defines no timeout for `WAIT`" and the fact that `FALLBACK` is only invoked "when the fallback flow is used."

7. **No `VERIFY` step.** The requirement does not ask for any verification of the delegated `short-notes` / `detailed-notes` work, so no `VERIFY` statement was added after the `DELEGATE` statements. I assumed the task should be translated literally, without introducing unrequested constructs.

8. **No `LOOP`.** The requirement describes a single linear process (ask → delegate → ask → emit/transition) with no repetition, so no `LOOP` was used. `LOOP` is only for explicitly repeated scopes per the spec.

9. **`DELEGATE` work identifiers.** I used `short-notes` and `detailed-notes` as the delegated work items, taken verbatim from the requirement's own phrasing ("delegate short-notes", "delegate detailed-notes"), treated as identifiers per the `<identifier>` grammar (letters, digits, `-`, `_`, starting with a letter).

10. **`EMIT release` argument.** The requirement says "emit release", so `release` is used as the identifier argument to `EMIT`, per the example style in the spec (e.g. `EMIT source-code`).

11. **`TRANSITION "Rework"` argument form.** I wrote the state name as a quoted string (`"Rework"`), matching the spec's own examples (e.g. `TRANSITION "Code Review"`), since `TRANSITION`'s argument may be an identifier or a string and the state name is human-readable text.

12. **Sequential top-level ordering.** The requirement's "First ... Then ..." wording is translated into plain sequential ordering at the top level: the first `HITL` and its two `WHEN`s, followed by the second `HITL` and its two `WHEN`s, executed in declaration order with no enclosing construct — consistent with the spec's default "Flow" rule that statements execute in declaration order unless a control construct changes this.

13. **Blank line between the two decision blocks.** This is purely a formatting/readability choice; the spec's indentation rules only concern relative depth, not blank lines, so this has no semantic effect.
