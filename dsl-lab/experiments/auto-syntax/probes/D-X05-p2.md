# Validity Analysis of go_harness DSL Snippets

## Snippet 1

```text
AUTO
HITL:deploy("Deploy to production?")
WHEN deploy.yes
  → EMIT deployment
```

**Verdict: VALID**

- `AUTO` is on its own line, immediately followed on the next line by a `HITL` at the same indentation, matching the required syntax: "`AUTO` is written on its own line directly before a `HITL`, at the same indentation" and the grammar production `hitl = [ "AUTO" , NL ] , "HITL" , [ ":" , identifier ] , "(" , string , ")" , NL , ...`.
- `HITL:deploy(...)` supplies a name, `deploy`, and the following `WHEN deploy.yes` tests `deploy.yes`, which is a well-formed condition of the form `<identifier>.<identifier>` (Conditional Flow / Identifier rules).
- Per the `HITL` rule: "The response establishes the outcome `<name>.<answer>`, where `<answer>` is one of the answers tested by the `WHEN <name>.<answer>` constructs that follow." The spec does not restrict `<answer>` to any fixed vocabulary (e.g. it need not be `accepted`/`declined`); `yes` is simply the answer name used by the one `WHEN` that follows, so this satisfies the rule.
- `WHEN deploy.yes` and its `→ EMIT deployment` item are syntactically ordinary (`when = "WHEN" , condition , NL , INDENT , flow , DEDENT`; `EMIT` takes an argument, matching `simple` argument form).
- No rule in the spec is violated; nothing here matches an "invalid" or "must not" case.

## Snippet 2

```text
AUTO
DELEGATE implementation
VERIFY implementation
```

**Verdict: INVALID**

- The spec states: "`AUTO` is not a statement of its own and applies to no other statement. `AUTO` applies only to `HITL`," and gives this exact pattern as its own worked example of invalidity: "Invalid, because `AUTO` applies only to `HITL`: `AUTO` / `DELEGATE implementation`."
- The grammar also only defines `AUTO` as an optional prefix inside the `hitl` production (`hitl = [ "AUTO" , NL ] , "HITL" , ...`); there is no production allowing `AUTO` before `DELEGATE`.
- Also directly relevant: "An `AUTO` line that is not immediately followed by a `HITL` is invalid." Here `AUTO` is immediately followed by `DELEGATE implementation`, not a `HITL`.

## Snippet 3

```text
AUTO HITL:deploy("Deploy to production?")
WHEN deploy.yes
  → EMIT deployment
```

**Verdict: INVALID**

- The specification requires `AUTO` to be "written on its own line directly before a `HITL`, at the same indentation" (AUTO section), and the grammar encodes this as `[ "AUTO" , NL ] , "HITL" , ...` — i.e. a newline (`NL`) must separate the `AUTO` token from the `HITL` token. Placing them on a single line (`AUTO HITL:deploy(...)`) does not conform to this: there is no `NL` between `AUTO` and `HITL`, so the `hitl` production cannot match this line, and the Statement table's `AUTO` row ("only on the line directly before a `HITL`") is not satisfied either, since there is no separate `AUTO` line at all.
- This is not the same failure as Snippet 2 (which correctly places `AUTO` on its own line but before the wrong keyword); here the syntax itself is malformed because `AUTO` and `HITL:deploy(...)` are fused into one non-conforming line with no keyword-starting-a-line structure the grammar recognizes for either token in this combined form.
- Since the program as written violates the required grammar/syntax, it "is not well-formed. It must be rejected as a whole" (Programs, fragments, and validity).

## Snippet 4

```text
AUTO
  WHEN decision.uncertain
    → HITL("Approve?")
```

**Verdict: INVALID**

- This matches the spec's second explicit invalid example verbatim: "Also invalid, because `AUTO` never contains a flow and uncertainty is not a condition: `AUTO` / `WHEN decision.uncertain` / `→ HITL("Approve?")`."
- Supporting rules: "`AUTO` is not a control-flow container. It does not contain `WHEN`, `→`, or an arbitrary flow." Here `WHEN decision.uncertain` is indented under `AUTO`, i.e. treated as `AUTO`'s scoped child, which the grammar does not permit (`AUTO` has no `INDENT ... DEDENT` block of its own in the `hitl` production, and no other production gives `AUTO` a body).
- Also: "Uncertainty is not a DSL condition, state, variable, or keyword," so `decision.uncertain` as used here is not a legitimate condition for `WHEN` in this role, and "The DSL runtime determines uncertainty as part of automatic decision resolution" (i.e., uncertainty is resolved implicitly by `AUTO`'s own semantics, not tested explicitly via `WHEN`).

## Assumptions

- Where a snippet is shown without surrounding context (no enclosing `LOOP`, process, etc.), it is treated as a complete program fragment for validity purposes, per: "A construct is not assumed to be enclosed in a scope that is not shown." None of the four snippets contain a `BREAK` or other construct whose validity depends on an assumed enclosing scope, so this did not affect the verdicts.
- Indentation in the snippets is inferred literally from the given text (leading spaces of "  →" indicate the arrow item's child depth); no additional indentation conventions were assumed beyond the spec's rules 1–6 in **Scope**.
- For Snippet 1, I assumed that `<answer>` in `WHEN <name>.<answer>` may be any identifier chosen by the author (e.g. `yes`) and is not restricted to a specific fixed set of words, since the specification never enumerates a closed set of permitted answers — it only requires that the answer tested by `WHEN` matches what the human/agent response establishes.
