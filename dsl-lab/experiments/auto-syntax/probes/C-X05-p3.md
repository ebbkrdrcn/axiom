# Snippet Validity Analysis

## Snippet 1

```text
HITL:deploy("Deploy to production?")
  → AUTO
WHEN deploy.yes
  → EMIT deployment
```

**VALID**

Rule basis:

- Grammar: `hitl = "HITL" , [ ":" , identifier ] , "(" , string , ")" , NL , [ INDENT , [ "→" , "AUTO" , NL ] , [ "→" , "FALLBACK" , NL , INDENT , flow , DEDENT ] , DEDENT ]`. Here `HITL:deploy("Deploy to production?")` is followed by an indented block containing only `→ AUTO`, which matches this production exactly (the `FALLBACK` part is optional and absent).
- Syntax table: `→ AUTO (only directly under a HITL)` — the `AUTO` line is written directly under the `HITL`, indented one level, with no children, per "`→ AUTO` is written directly under a `HITL`, indented one level ... `→ AUTO` has no children."
- `HITL:<name>(...)`: "`<name>` names the decision. The response establishes the outcome `<name>.<answer>`, where `<answer>` is one of the answers tested by the `WHEN <name>.<answer>` constructs that follow." Here `deploy` is the name and `WHEN deploy.yes` is a `WHEN` construct that follows and tests an answer (`yes`) for that name — this is exactly the documented pattern (paralleling the `merge.approved`/`merge.declined` example under **AUTO**).
- `WHEN` (Conditional Flow / Control): `<condition>` has the form `<identifier>.<identifier>` — `deploy.yes` satisfies this. The `WHEN` sits at the indentation of `HITL`, i.e., it is the statement after the `HITL` construct, consistent with "After the decision is made, by the agent or by the human, execution continues with the statement after the `HITL` construct."

No rule is violated; the construct is well-formed.

## Snippet 2

```text
DELEGATE implementation
  → AUTO
VERIFY implementation
```

**INVALID**

Rule basis:

- This is the spec's own worked counter-example, verbatim in structure: under **AUTO**, "Invalid, because `AUTO` applies only to `HITL`:" followed by exactly `DELEGATE implementation` with an indented `→ AUTO` child.
- Syntax table: the only listed form for `AUTO` is `→ AUTO (only directly under a HITL)`. `DELEGATE` is a `simple` statement (`simple = ( "REQUIRE" | "DELEGATE" | "VERIFY" | "TRANSITION" | "EMIT" ) , argument , NL | ( "JOIN" | "BREAK" | "WAIT" | "STOP" ) , NL`), which has no grammar production allowing an indented `→ AUTO` child.
- Scope rule 6: "Any other indentation is invalid. This includes an indented line under a plain statement that is not a `→` item..." `DELEGATE implementation` is a plain statement, not a `→` item, so an indented line beneath it (here `→ AUTO`) is invalid indentation.
- Per **Programs, fragments, and validity**: a program violating a rule stated as "invalid" is not well-formed and must be rejected as a whole.

## Snippet 3

```text
AUTO HITL:deploy("Deploy to production?")
WHEN deploy.yes
  → EMIT deployment
```

**INVALID**

Rule basis:

- Grammar for `hitl` requires the statement to begin with the keyword `"HITL"` itself (`hitl = "HITL" , [":" , identifier] , "(" , string , ")" , NL , ...`); there is no production in which `AUTO` prefixes or co-occurs on the same line as the `HITL` keyword.
- Syntax table: the only valid written form of `AUTO` is `→ AUTO`, and only "directly under a `HITL`" — i.e., on its own line, indented beneath a `HITL` line, not combined with the `HITL` line itself.
- **AUTO** section: "Syntax: `HITL:<name>("<message>")` / `→ AUTO`. `→ AUTO` is written directly under a `HITL`, indented one level." This snippet instead writes `AUTO` and `HITL:...` as a single line/statement, which matches neither the grammar's `hitl` production nor the `→ AUTO` item form.
- **Statement** table (Syntax section) lists `HITL[:<name>]("<message>")` and `→ AUTO` as two distinct statement forms; concatenating them into one token stream (`AUTO HITL:deploy(...)`) is not one of the defined statement forms, so the line cannot be parsed as any valid statement.

## Snippet 4

```text
AUTO
  WHEN decision.uncertain
    → HITL("Approve?")
```

**INVALID**

Rule basis:

- This reproduces the spec's second explicit counter-example verbatim: under **AUTO**, "Also invalid, because `AUTO` never contains a flow and uncertainty is not a condition:" followed by exactly this `AUTO` / `WHEN decision.uncertain` / `→ HITL("Approve?")` structure.
- **AUTO** section, direct statements: "`AUTO` is not a control-flow container. It does not contain `WHEN`, `→`, or an arbitrary flow." This snippet has `AUTO` directly containing a `WHEN`.
- "Uncertainty is not a DSL condition, state, variable, or keyword." The condition `decision.uncertain` treats uncertainty as a testable condition, which the spec explicitly disallows: "The DSL runtime determines uncertainty as part of automatic decision resolution" (it is not something a `WHEN` can test).
- Grammar: there is no production for a bare `AUTO` statement (`AUTO` only appears in the grammar as the fixed token sequence `"→" , "AUTO" , NL` inside `hitl`); a standalone `AUTO` statement with an `INDENT`ed `block` has no grammar rule permitting it at all.
- Per **Programs, fragments, and validity**, this must be rejected as a whole.

The specification determines all four outcomes explicitly (Snippets 2 and 4 are its own listed invalid examples; Snippet 1 mirrors its own listed valid `merge.approved`/`merge.declined` example; Snippet 3's invalidity follows directly from the fixed grammar/syntax forms for `HITL` and `AUTO`). No assumption beyond the given text was needed for any of the four snippets.
