```text
DELEGATE implementation
VERIFY implementation
HITL:merge("Merge this change?") AUTO
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **Decision name `merge`.** The requirement's merge decision needs a name so that `WHEN <name>.<answer>` can refer to it (per the `HITL` rule that `<name>` is required whenever a `WHEN` tests its outcome). The specification does not prescribe a specific name, so I chose the identifier `merge`.

2. **Answer vocabulary `approved` / `declined`.** The specification does not fix the set of answer names for a `HITL`; it only says the response establishes `<name>.<answer>` for whichever answers the following `WHEN` constructs test. I chose `merge.approved` for "decision is to merge" and `merge.declined` for "decision is not to merge." Any other pair of distinct identifiers would be equally valid under the spec.

3. **`AUTO` placed on the single `HITL:merge(...)`.** The requirement's "the agent may decide itself when clearly determined, otherwise ask a human" maps directly onto the documented `AUTO` semantics (resolve automatically when sufficiently determined; otherwise the human is asked exactly as for a plain `HITL`). No separate agent-decision construct exists in the DSL, so `AUTO` on this one `HITL` is the only mechanism available for this behavior.

4. **"No usable answer" maps to the `FALLBACK` flow.** The spec defines `FALLBACK` as covering both an unavailable response (none arrives) and an insufficient one (arrives but doesn't answer the question). "The human gives no usable answer" was treated as this same fallback condition, not as a third `WHEN` branch (the DSL does not allow `WHEN` to test "no answer"; only `FALLBACK` covers this case).

5. **`TRANSITION "Blocked"` followed by `STOP` inside `FALLBACK`, written as nested statements.** The spec shows two equivalent ways to write a multi-step fallback flow (successive `→` lines, or nesting under the first `→`); I used the nested form. Since `STOP` unconditionally terminates the entire execution, this also makes moot the specification's silence on whether a fallback flow without `STOP` would fall through to the normal flow after `HITL` — that ambiguity does not need to be resolved for this program.

6. **`VERIFY implementation` is not followed by a `WHEN` on its outcome.** The requirement says only "verify it. Then a merge decision is needed," with no branching described on the implementation's accepted/rejected outcome before the merge decision. Per the spec, "`VERIFY` does not branch by itself... a `VERIFY` with no `WHEN` after it does not gate the process," so execution proceeds unconditionally to the merge decision regardless of the verification's outcome. If the requirement intended verification to gate the merge decision (e.g., only ask about merging when accepted), that was not stated and is not represented here.

7. **Identifier for the delegated/verified work is `implementation`.** The requirement calls it "the implementation"; I used the identifier `implementation` for both `DELEGATE` and `VERIFY`, consistent with the spec's own `DELEGATE implementation` / `VERIFY implementation` example.

8. **No enclosing `LOOP`.** The requirement describes a single linear decision sequence with no repetition language ("loop," "retry," "until"), so the program is a flat top-level block with no `LOOP`. This also means `BREAK` is not used (and would be invalid here, since `BREAK` requires an enclosing `LOOP`).

9. **The message strings are quoted exactly as given in the requirement** ("Merge this change?"), since the DSL's `HITL` form requires a string argument and the spec does not mandate any particular wording beyond what the surrounding process supplies.
