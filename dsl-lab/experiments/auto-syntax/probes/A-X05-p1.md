# Answers

## Snippet 1

```text
AUTO HITL:deploy("Deploy to production?")
WHEN deploy.yes
  → EMIT deployment
```

**VALID.**

- The `HITL` line matches the required syntax exactly: `[AUTO] HITL[:<name>]("<message>")` (Syntax table, "Statement"), and the grammar rule `hitl = [ "AUTO" ] , "HITL" , [ ":" , identifier ] , "(" , string , ")" , NL , ...` — here `AUTO` precedes `HITL`, on the same line, with `:deploy` naming the decision, as required by the `AUTO` section: "`AUTO` is written directly before `HITL`, on the same line."
- `deploy` is a valid identifier (Syntax → Identifier), and naming the decision is licensed because a subsequent `WHEN deploy.yes` refers to it: "`<name>` names the decision. The response establishes the outcome `<name>.<answer>`, where `<answer>` is one of the answers tested by the `WHEN <name>.<answer>` constructs that follow" (HITL section).
- `WHEN deploy.yes` has the required `<condition>` form `<identifier>.<identifier>` (Conditional Flow section: "`<condition>` has the form `<identifier>.<identifier>`"), and its `→ EMIT deployment` is a single well-formed conditional flow item (`item = "→" , statement , [...]`, with `EMIT <artifact>` a valid simple statement).
- Nothing in the spec restricts the answer token to a fixed vocabulary (e.g. `accepted`/`declined`); `yes` is just an identifier used as the second part of the condition, which is allowed.

## Snippet 2

```text
AUTO DELEGATE implementation
VERIFY implementation
```

**INVALID.**

- The spec gives this exact pattern as its own counter-example: "Invalid, because `AUTO` applies only to `HITL`: `AUTO DELEGATE implementation`" (AUTO section).
- This is confirmed by the general rule "`AUTO` is not a statement of its own and applies to no other statement. `AUTO` applies only to `HITL`" (AUTO section), and by the grammar, where `AUTO` only appears as an optional prefix inside the `hitl` production (`hitl = [ "AUTO" ] , "HITL" , ...`); it has no place in the `simple` production that `DELEGATE` belongs to (`simple = ( "REQUIRE" | "DELEGATE" | "VERIFY" | "TRANSITION" | "EMIT" ) , argument , NL | ...`).

## Snippet 3

```text
HITL:deploy("Deploy to production?") AUTO
WHEN deploy.yes
  → EMIT deployment
```

**INVALID.**

- The AUTO section is explicit about word order: "`AUTO` is written directly before `HITL`, on the same line. It marks that one `HITL` as automatically resolvable." Here `AUTO` is written *after* `HITL`, not before it.
- The Syntax table gives the statement form as `[AUTO] HITL[:<name>]("<message>")` — `AUTO` (if present) precedes `HITL`, not the reverse — and the grammar rule `hitl = [ "AUTO" ] , "HITL" , [ ":" , identifier ] , "(" , string , ")" , NL , ...` fixes `AUTO` as the first (optional) token of the production, before the `HITL` keyword. `HITL:deploy("Deploy to production?") AUTO` does not match this token order, so it is not a well-formed `hitl` statement.

## Snippet 4

```text
AUTO
  WHEN decision.uncertain
    → HITL("Approve?")
```

**INVALID.**

- The spec gives this exact pattern as its own counter-example: "Also invalid, because `AUTO` never contains a flow and uncertainty is not a condition: `AUTO` / `WHEN decision.uncertain` / `→ HITL(\"Approve?\")`" (AUTO section).
- Supporting rules: "`AUTO` is not a control-flow container. It does not contain `WHEN`, `→`, or an arbitrary flow" and "Uncertainty is not a DSL condition, state, variable, or keyword" (AUTO section). The grammar also has no production allowing `AUTO` to head an indented block — it only appears as the optional prefix token in `hitl`, never as a standalone statement that can open a scope (compare `loop`, `when`, `fork`, `hitl`, the only productions with `INDENT ... DEDENT`).
