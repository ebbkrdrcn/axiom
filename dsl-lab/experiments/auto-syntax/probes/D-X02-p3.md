```text
AUTO
HITL:notes("Short or detailed release notes?")
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes

HITL:approval("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Decision names.** The spec requires a `HITL` to be named (`<name>`) only when a `WHEN` refers to it, but it does not say what the name should be. I named the two decisions `notes` and `approval` to make the `WHEN notes.short`, `WHEN notes.detailed`, `WHEN approval.approved`, `WHEN approval.rejected` conditions readable; any other identifier names would be equally valid per the spec.

2. **Answer identifiers.** The spec says the response establishes `<name>.<answer>` where `<answer>` is "one of the answers tested by the `WHEN <name>.<answer>` constructs that follow," but it does not fix a vocabulary for answers. I chose `short` / `detailed` for the notes question and `approved` / `rejected` for the approval question because these are the natural readings of "short or detailed" and "approve/reject" in the requirement text. The spec does not determine these exact tokens; any consistent naming would satisfy it.

3. **`AUTO` only on the first `HITL`.** The requirement says the notes question "may [be answered] by the agent itself when the answer is clearly determined," which matches `AUTO`'s defined semantics exactly (resolve automatically when sufficiently determined, otherwise ask a human). The approval question is explicitly required to "always be given by a human, never by the agent," so no `AUTO` line precedes that `HITL`. This directly follows the spec's rule that a `HITL` without `AUTO` is never resolved by the agent.

4. **No `FALLBACK` blocks.** The task does not describe what should happen if a response is unavailable or insufficient for either `HITL`. The spec does not require every `HITL` to carry a `FALLBACK` (it is optional syntax: `[ INDENT , "→" , "FALLBACK" , ... ]`), so I omitted it for both. Where the spec does not determine behavior for an unavailable/insufficient response, I have made no assumption about it rather than inventing one.

5. **No enclosing `LOOP`.** The requirement describes a single, one-shot sequence of steps ("first ask... then ask...") with no mention of repetition, retries, or looping back. I therefore wrote the program as a flat top-level sequence of statements, not inside a `LOOP`.

6. **No `VERIFY` on `DELEGATE short-notes` / `DELEGATE detailed-notes`.** The requirement only says to "delegate" the notes work; it does not ask for that delegated work to be evaluated against acceptance criteria. Since `VERIFY` is a distinct, separately-invoked operation in the spec, I did not add one that the task did not request.

7. **No additional `TRANSITION` on approval.** The requirement specifies `EMIT release` on approval and `TRANSITION "Rework"` on rejection, but says nothing about a state change on approval. Per `TRANSITION`'s semantics (a state change is a distinct, explicit operation), I did not infer or add an implicit transition for the approved case.

8. **Sequential ordering of the two `HITL` decisions.** The requirement presents the notes question first and the approval question second, with no indication of concurrency (no `FORK`/`JOIN` implied). I encoded this as two sequential top-level `HITL` blocks in that order, matching the DSL's default sequential-flow semantics.

9. **Blank line between the two `HITL` blocks.** This is purely cosmetic; the grammar has no significance for blank lines, and indentation (not blank lines) determines scope. I used it only for readability and it carries no semantic meaning in the DSL.
