```text
HITL:notes("Short or detailed release notes?") AUTO
WHEN notes.short
  → DELEGATE short-notes
WHEN notes.detailed
  → DELEGATE detailed-notes

HITL:approval("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

- **Names for the `HITL` decisions.** The requirement does not give explicit names for the two questions, but the DSL requires a `<name>` on `HITL` whenever a `WHEN <name>.<answer>` refers to it (per the `HITL` rules: "The response establishes the outcome `<name>.<answer>`... The name may be omitted when no `WHEN` refers to the decision"). Since both decisions are branched on, I assigned the names `notes` and `approval`.

- **Answer identifiers.** The specific tokens `short`, `detailed`, `approved`, and `rejected` are not prescribed by the spec (it only says `<answer>` is "one of the answers tested by the `WHEN <name>.<answer>` constructs that follow"); I chose natural-language-derived identifiers matching the requirement's own wording ("short", "detailed") and the conventional accept/reject pair used in the spec's own examples ("approved"/"rejected", by analogy with `merge.approved`/`merge.declined` and `implementation.accepted`/`implementation.rejected`).

- **`AUTO` placement.** `AUTO` is attached only to the first `HITL` (`notes`), since the requirement states the agent "may answer this question itself when the answer is clearly determined." Per the `AUTO` semantics table, this means: if sufficiently determined, the agent resolves it and no human is asked; otherwise the human is asked exactly as for a plain `HITL`. The second `HITL` (`approval`) intentionally has no `AUTO`, since the requirement states approval "must always be given by a human, never by the agent" — an unmarked `HITL` always asks the human per spec ("no | — | The human is asked. The agent must not decide.").

- **No `FALLBACK`.** The requirement does not describe what should happen if a human response is unavailable or insufficient for either question. The grammar marks the `FALLBACK` clause of `hitl` as optional (`[ INDENT , "→" , "FALLBACK" , ... ]`), so I omitted it for both `HITL` statements. Per the `WAIT`/`HITL` semantics, this means each flow simply waits at its `HITL` until a usable response (human or, for `notes`, agent-via-`AUTO`) becomes available — there is no DSL-defined timeout and no fallback behavior to specify since none was given.

- **`DELEGATE` argument identifiers.** I used `short-notes` and `detailed-notes` as the delegated-work identifiers, taken directly from the requirement's own phrasing ("delegate short-notes", "delegate detailed-notes"), which are valid identifiers under the grammar (letters/digits/`-`/`_`, starting with a letter).

- **`EMIT` argument identifier.** I used `release` as the artifact name, taken directly from "emit release" in the requirement.

- **No `VERIFY`.** The requirement never describes evaluating a delegated result against acceptance criteria — it only asks that the notes be delegated and then a separate human approval be requested. Since `VERIFY` is a distinct evaluation operation not implied by "delegate," I did not insert one.

- **No `LOOP`, `FORK`/`JOIN`, `REQUIRE`, `TRANSITION` before rejection, or `STOP`.** The requirement describes a single linear sequence (ask → branch on notes type → delegate → ask approval → branch on approval), with no repetition, concurrency, explicit prerequisite declaration, or process termination described, so none of these constructs were used.

- **Top-level program.** Per "Programs, fragments, and validity," a construct is not assumed to be enclosed in an unshown scope; I treated the whole answer as a complete, self-contained, well-formed top-level program (no enclosing `LOOP`, `WHEN`, etc.), matching the requirement as a standalone process description.

- **Blank line between the two `HITL` groups.** This is purely a formatting choice for readability and carries no semantic meaning in the DSL; indentation, not blank lines, determines scope.
