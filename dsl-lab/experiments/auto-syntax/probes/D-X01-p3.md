```text
DELEGATE implementation
VERIFY implementation
AUTO
HITL:merge("Merge this change?")
  → FALLBACK
      → TRANSITION "Blocked"
        STOP
WHEN merge.approved
  → TRANSITION "Merged"
WHEN merge.declined
  → TRANSITION "Rework"
```

## Assumptions

1. **Names for the two merge answers.** The spec says `HITL:<name>` establishes outcomes `<name>.<answer>` where `<answer>` matches what the following `WHEN` constructs test, but it does not fix a vocabulary for those answers. I named the decision `merge` and used the answers `approved` / `declined` (mirroring the spec's own `AUTO`/`HITL` example), since the requirement only describes the two outcomes ("to merge" / "not to merge") without naming them.

2. **No `WHEN` after `VERIFY implementation`.** The requirement says only "Delegate the implementation and verify it. Then a merge decision is needed" — it does not state that the implementation's verification outcome (accepted/rejected) should branch the flow before the merge decision. Per the spec, `VERIFY` with no following `WHEN` is legal and simply does not gate the process, so I left it ungated and proceeded straight to the merge decision.

3. **"No usable answer" maps to the `FALLBACK` flow.** The spec defines `FALLBACK` as covering both "unavailable" (no response) and "insufficient" (a response that isn't a usable decision) cases. The requirement's phrase "the human gives no usable answer" is treated as covering both, so both route through the single `FALLBACK` flow rather than being split into two different constructs (the DSL has no way to distinguish them anyway — the runtime decides).

4. **No `REQUIRE` statement.** The requirement text does not explicitly declare any precondition/context that must be available before execution proceeds (e.g., "requires repository" or similar), so no `REQUIRE` was added. `REQUIRE` was not inferred from the general notion that "implementation" presumably needs some input, since the spec ties `REQUIRE` to an explicit declared requirement in the process text, not to work.

5. **No `LOOP`, `FORK`/`JOIN`.** The requirement describes a single linear sequence with one decision point and no repetition or concurrency, so none of these constructs were used.

6. **`AUTO` governs only the merge `HITL`.** Per spec, `AUTO` can only immediately precede a `HITL` and applies only to that one `HITL`. This matches the requirement, which only allows automatic resolution for the merge decision, not for anything else in the process.

7. **`STOP` after `TRANSITION "Blocked"` ends the whole execution**, per spec's definition of `STOP` terminating the entire execution (not just the fallback flow), matching the requirement's explicit "transition to state 'Blocked' and stop."

8. **No blank lines used between statements** in the final DSL, to avoid any ambiguity about whether blank lines are syntactically significant (the grammar's `NL` separators are shown between statements without blank-line allowances, and the spec does not explicitly address blank lines), even though earlier examples in the spec were shown with blank lines between blocks for readability.

9. **Formatting of `→ FALLBACK`'s nested statements** follows the spec's example exactly: `TRANSITION "Blocked"` and `STOP` are written as a single `→` item with `STOP` nested beneath it (per the spec's second equivalent form for `FALLBACK`), since both statements must run in sequence within the one fallback flow.
