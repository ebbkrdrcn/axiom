```text
HITL:notes-length("Short or detailed release notes?") AUTO
WHEN notes-length.short
  → DELEGATE short-notes
WHEN notes-length.detailed
  → DELEGATE detailed-notes

HITL:approval("Approve the release?")
WHEN approval.approved
  → EMIT release
WHEN approval.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Names chosen for the two `HITL` decisions.** The specification requires a `<name>` only when a `WHEN` refers to the decision, but does not prescribe what that name should be. I named the first decision `notes-length` and the second `approval`; any other identifier would be equally valid.

2. **Answer identifiers.** The requirement's answers ("short", "detailed", and implicitly "approved"/"rejected" for the approval question) are not given as DSL identifiers in the requirement text. I used `notes-length.short`, `notes-length.detailed`, `approval.approved`, and `approval.rejected` as the outcome names tested by `WHEN`, since the spec says the response establishes `<name>.<answer>` for whatever answers the following `WHEN` constructs test, without fixing their spelling.

3. **`AUTO` on the first `HITL` only.** "The agent may answer this question itself when the answer is clearly determined" maps directly to `AUTO`'s defined semantics (resolve automatically when sufficiently determined, otherwise ask the human). I attached `AUTO` to `HITL:notes-length(...)` and deliberately omitted it from `HITL:approval(...)`, since the requirement states approval "must always be given by a human, never by the agent" — this is exactly the case the spec says `AUTO` must not be used for.

4. **No `FALLBACK` flows.** The requirement says nothing about what happens if a human's response is unavailable or insufficient, so I did not add a `FALLBACK` to either `HITL`. The specification treats `FALLBACK` as optional (attached "only if" the fallback flow is needed), so its absence does not affect well-formedness; per the `WAIT`/`HITL` semantics, if no usable response ever arrives, that flow simply remains suspended.

5. **No `LOOP`.** The requirement describes a single linear sequence (ask notes format → delegate → ask approval → emit or transition) with no repetition, retry, or "until accepted" language, so the program is a flat top-level block with no `LOOP` wrapping it.

6. **No `REQUIRE`.** The requirement does not state any precondition ("given the repository", "given criteria", etc.) that must be declared before execution, so no `REQUIRE` statement was added.

7. **`VERIFY` not used.** Nothing in the requirement asks for an evaluation of delegated work against acceptance criteria (`short-notes`/`detailed-notes` are simply delegated, not checked), so no `VERIFY` statement follows the `DELEGATE` statements.

8. **Blank line between the two `HITL` blocks is purely visual.** The grammar's statement/block rules do not explicitly discuss blank lines, but the specification's own examples (e.g., the `WHEN` example under "WHEN") use a blank line between sibling top-level constructs with no stated semantic effect, so I follow that convention here; it does not change indentation depth or meaning.

9. **Top-level structure.** Since "a program is a complete DSL text" and "a construct is not assumed to be enclosed in a scope that is not shown," I treated the whole requirement as a self-contained top-level `block` of two `HITL` constructs each followed by their `WHEN` constructs, with no enclosing `LOOP`, `FORK`, or other wrapper implied.
