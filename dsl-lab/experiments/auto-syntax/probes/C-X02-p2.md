```text
HITL:format("Short or detailed release notes?")
  → AUTO
WHEN format.short
  → DELEGATE short-notes
WHEN format.detailed
  → DELEGATE detailed-notes
HITL:approve("Approve the release?")
WHEN approve.approved
  → EMIT release
WHEN approve.rejected
  → TRANSITION "Rework"
```

## Assumptions

1. **Names for the `HITL` decisions.** The spec requires a `<name>` on `HITL` whenever a `WHEN` refers to its outcome (`WHEN <name>.<answer>`). Since both decisions in the requirement are branched on, both `HITL` statements needed a name. The requirement itself does not supply names, so I chose `format` (for "short or detailed release notes?") and `approve` (for "approve the release?").

2. **Outcome identifiers.** The requirement says "if short ... if detailed" and "if approved ... if rejected" but does not spell out the exact answer tokens `HITL` establishes. I used the identifiers `short`, `detailed`, `approved`, and `rejected`, taken directly from the requirement's own wording, giving conditions `format.short`, `format.detailed`, `approve.approved`, `approve.rejected`.

3. **`AUTO` on the first `HITL` only.** "The agent may answer this question itself when the answer is clearly determined" maps directly to the `AUTO` mechanism as specified: the agent resolves the decision only when sufficiently determined, otherwise the human is asked — no extra logic was needed to express this. "This approval must always be given by a human, never by the agent" is expressed by simply omitting `→ AUTO` under the second `HITL`, since the spec states that without `AUTO`, "the human is asked. The agent must not decide."

4. **No `FALLBACK` on either `HITL`.** The requirement does not describe what should happen if a human response is unavailable or insufficient, so I did not add a `FALLBACK` flow for either decision. Per the spec, a `HITL`'s indented block (containing `AUTO`/`FALLBACK`) is optional, so a `HITL` with no `FALLBACK` simply waits at that point until a usable response (or automatic resolution, for the first one) is available; the DSL defines no timeout for this.

5. **DELEGATE argument identifiers.** I used the identifiers `short-notes` and `detailed-notes` for the two delegated work items, taken from the requirement's own phrasing ("delegate short-notes", "delegate detailed-notes").

6. **No `REQUIRE`.** The requirement does not mention any precondition, input, or context that must be established before execution starts, so no `REQUIRE` statement was added.

7. **No `LOOP`.** The requirement describes a single, linear sequence of decisions with no repetition, retry, or "until accepted" semantics, so no `LOOP`/`BREAK` construct was used.

8. **No explicit `STOP`.** The spec states `STOP` is not required at the end of a process; execution ends normally once the last top-level statement (the second pair of `WHEN` constructs) has completed. I therefore did not add a `STOP`.

9. **Sequencing between the two decisions.** The requirement's ordering ("First ask... Then ask...") is expressed simply by declaration order: the first `HITL` and its two `WHEN` constructs are followed, at the same indentation, by the second `HITL` and its two `WHEN` constructs. Per the spec's `WHEN` execution rules, an unmatched `WHEN` is not an error and execution simply continues to the next statement, so control reaches the second `HITL` regardless of which of `format.short`/`format.detailed` matched.
